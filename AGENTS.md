# Repository Guidelines

## Project Structure

Sakura AI is a Python 3.14+ FastAPI service for GitHub PR/Issue review, WebUI administration, a unified notification center (WebUI/Email/Telegram/Webhook providers), RAG, billing, and repository scanning. The main application is under `backend/`: `main.py` owns application setup, while `core/`, `api/`, `services/`, `models/`, `webui/`, `workers/`, and `telegram/` contain infrastructure, routes, domain logic, persistence, UI, background jobs, and the optional Telegram notification-binding bot. Business events enter through `backend/services/notification_events.py` and `notification_business.py`; `notification_dispatch.py` uses the existing endpoint/delivery tables and Provider registry in `notification_service.py`, including legacy announcements. Do not restore Telegram-only business sends in review/issue workers. GitHub webhooks enter through `backend/api/webhook.py`; `backend/workers/review_worker.py` coordinates PR analysis, AI review, comment publication, and Check Runs. Root tests live in `tests/`. The independent `updater/` package uses a `src/` layout and has its own `tests/`. Runtime configuration is stored in the database `app_config` table (including `strategy.*`/`label.*` section keys); `config/` holds deployment connection settings (`connection.json`) and the transient private Setup handoff (`.setup-token`). Configuration is edited through `/settings-center/{category}` and the typed `/api/v1/config-center` API. Legacy configuration URLs redirect to it. `config_metadata.py` owns descriptors and immutable defaults; `config_center_service.py` and `config_store.py` own validation, field resets and durable revisions across existing stores. `config_runtime.py` reconciles committed changes across processes. Configuration frontend modules live in `backend/webui/assets/settings/`, with browser/state-machine tests in `tests/webui/`. Deployment assets are in `docker/`, `docs/`, `res/`, and `start.sh`.

## Setup, Build, and Development Commands

```bash
uv sync
# Classic pip alternative:
python -m pip install -r requirements-dev.txt
python -m uvicorn backend.main:app --reload --host 127.0.0.1 --port 8000
python scripts/dev_bootstrap.py
python -m pytest -q
python -m pytest tests/test_main.py -q
python -m pytest updater/tests -q
python -m pytest sandboxer/tests -q
ruff check .
python run_ruff.py --check
docker compose -f docker/docker-compose.yml up --build
```

`uv sync` is the recommended setup: it creates `.venv`, installs all dependencies including the editable updater package, and locks them in `uv.lock`. In a uv environment, prefix commands with `uv run` (e.g. `uv run python -m pytest -q`) instead of activating `.venv`. `requirements.txt` remains the authoritative dependency source for pip/Docker builds; the root `pyproject.toml` mirrors it line by line, enforced by `tests/test_uv_pyproject.py` — update both when changing dependencies. Install the updater editable package (or use `uv sync`) before running the full suite. Source development supports Windows 11 x86_64, Linux x86_64/arm64 with glibc >= 2.28 (non-musl; Alpine is unsupported), and Apple Silicon macOS 14+. Native Windows PowerShell supports `uv sync --locked`, `uv run pytest`, and Ruff without WSL/Git Bash. Keep portable tests active on every platform; check prerequisites only for POSIX deployment scripts, Linux isolation/systemd, or link privileges. Windows workspace locking and secure reads use native handles; do not remove cross-process exclusion or path-admission checks. The Host Updater, sandboxd, and local read-only Landlock/seccomp process isolation retain their Linux requirements. `run_ruff.py` without `--check` may modify and format files; use the check form for read-only validation.

Classic pip development uses `requirements-dev.txt`, which includes runtime requirements, the editable updater with its test extras, and the SQLite test driver. Keep its development dependencies aligned with the `pyproject.toml` dev group; the pip CI job installs this same manifest.

## Coding Style and Testing

Use four-space indentation, English identifiers, and async-first I/O. Chinese or bilingual comments are acceptable. Keep route handlers thin and delegate business logic to services; use `loguru` for application logging and follow the root `ruff.toml` (`py314`) configuration. User-visible WebUI text must update both `backend/webui/translations/zh-CN.yaml` and `en.yaml`. Pytest and `pytest-asyncio` are used; name files `test_*.py` and functions `test_*`. Mock MySQL, Redis, GitHub, AI providers, and ChromaDB in unit tests. CI runs Ruff and pytest but does not enforce a coverage threshold.

## Architecture Contracts

- **Unified time**: get timestamps from `backend/core/time_service.py` and use the timezone-aware types in `backend/models/time_types.py`; never call `datetime.now()` directly or store naive datetimes.
- **Docker image channels**: updates run on `stable`/`development` channels coordinated across `backend/services/container_registry.py` (registry queries), `backend/core/build_info.py` (current channel/version), and the updater's `registry.py` (channel and digest resolution) — change all three plus the WebUI version manager page together.
- **Setup backup restore**: backup import must not overwrite deployment-time connection settings (DB connection string, Redis address); `backend/core/setup_service.py` preserves them, and any newly imported field must bypass them too.

## Notification Maintenance

Read [docs/NOTIFICATION_CENTER.md](docs/NOTIFICATION_CENTER.md) before changing event producers, delivery, endpoints, subscriptions or migrations. Update that document when the contract changes. The following rules also apply when another feature adds a new terminal status, bulk writer, retry entry point or notification provider.

- **One event and delivery pipeline**: emit channel-independent business events through `notification_events.emit_event` or `notification_business.emit_task_event`; keep provider calls inside the existing delivery/Provider abstraction. Reuse `notification_models.py`, the endpoint/delivery tables and existing Settings/Announcement Center pages. Do not introduce a second sender, Telegram-only business path, message broker or authentication redesign. Provider formatting, configuration, throttling and error classification belong in the provider layer.
- **Transactional producers**: persist critical task state and its event in the same database transaction. `emit_event` must neither commit the caller's transaction nor perform external I/O. Application ORM sessions opt into the outbox; bulk SQL does not trigger ORM history hooks, so every bulk status writer must explicitly emit for the rows it actually transitioned. Conditional updates and cancellation snapshots must retain their concurrency guards. Event/commit failures roll back the state change and propagate after bounded retries with fresh transactions; never log and return success for a rolled-back scan/task transition. Migration/import sessions must not emit historical events. Gateway expiration must emit `payment.failed` atomically without conflating voluntary cancellation; lock and refresh competing order transitions. Successful Agent retry quota consumption must retain the admission transaction and task lock through queue commit.
- **Stable identity and execution rounds**: derive deduplication from persisted event type, resource, audience and business run/reset identity; enforce it with database uniqueness. Repeated callbacks in the same round return the original event and snapshot. A genuine new run must notify again, including failure before the first Agent iteration. Preserve Agent and scan `execution_round` admission under the task row lock, resume/iteration counters and legacy round-zero keys. Do not use process-local flags, callback arrival time or random IDs to deduplicate an existing business transition.
- **Claims and recovery across instances**: preserve database claims, bounded leases, token-fenced result updates, persisted attempt accounting and restart recovery. Fanout must be atomic and unique per user/event and exact endpoint/event; a successful endpoint must not be resent because another endpoint failed. Use the shared SQL provider budgets, including MySQL microsecond precision. In-memory locks/cooldowns cannot be the deployment-wide authority. External acknowledgement loss can still produce a duplicate: do not promise strict end-to-end exactly-once delivery.
- **Eligibility and failure isolation**: explicit denial or an unbound/disabled endpoint terminates delivery without automatic reactivation; an eligibility query/session-factory failure is an observable infrastructure error with a durable retry time, not permanent denial. Preserve the service return contracts on failure. Keep transient, rate-limit, credential/configuration, security and exhausted outcomes distinct. Retry-After for a Webhook receiver is endpoint-scoped; one destination must not pause unrelated endpoints or consume another channel's attempt budget. Cancellation must propagate and bounded background tasks must retain their failures.
- **Optional alert boundaries**: quota denial must retain its established `(False, reason)` result and Agent orphan-task cleanup if the exhaustion alert cannot be inserted or committed. Capture the reason and safe identifiers before rollback expires ORM attributes, roll back the failed alert transaction and record a sanitized warning. Do not convert primary quota/database failures into denial. Redis MFA lockout is already authoritative before its SQL alert; alert failure must not undo the lock. Document any other cross-store degradation boundary explicitly.
- **Resource authorization**: check the current user role/status and the resource's WebUI scope before fanout, external sending and history reads. PR/Issue scopes recognize their authorized authors/owners/admins; scans require an administrator; Agent scopes recognize `started_by` or an administrator, including organization repositories. Repository ownership alone grants neither scan access nor access to another user's Agent task. GitHub identity checks must be case-insensitive in the notification ACL and every corresponding page/list/detail/operation scope on both database dialects. Subscriptions select routing and never grant resource access. Use internal user IDs, not Telegram IDs, and never broadcast an event to administrators merely because its legal recipient lookup returned empty.
- **Exact endpoints and sensitive targets**: recheck endpoint ownership, enabled/verified state and current preferences immediately before sending/retrying; do not fall back to a different channel or address. New business events default to the inbox and external endpoints require matching subscriptions; preserve legacy announcement routing defaults. Security, quota, payment and refund events are intrinsically sensitive and must exclude Webhooks, shared or unverified targets even if a producer forgets the sensitivity flag. Keep existing private Telegram binding and account roles compatible during unbinding.
- **Webhook security**: endpoint creation, verification, testing and delivery share the same authorization and network policy. Require public HTTPS on port 443, deny URL credentials/query/fragment, validate all DNS answers and pin the admitted addresses while retaining TLS hostname checks. Keep private/loopback/link-local/reserved and transition-address rejection, administrator allowlisting, disabled environment proxies/redirects, and bounded DNS/connect/read/response limits. Preserve ownership challenges, encrypted signing credentials, raw-body HMAC with timestamp replay checks, and the stable event ID for receiver deduplication; replacing a signing key invalidates verification. Fence verification results against the exact owner/address/enabled state/configuration generation/encrypted credential challenged; consume Email codes atomically with attempt/expiry checks. Disable/re-enable and credential replacement advance the generation; imports never rewind it and clear pending codes. Backup validation must accept positive exported endpoint generations and remain independent of Provider schema versions; verify an export/restore/export round trip after changing generation semantics. Never hold a database lock during the ownership challenge.
- **Payloads, credentials and diagnostics**: persist only safe summaries and minimal business metadata; do not publish stack traces, private findings or arbitrary provider response bodies. Use the existing secret service for stored credentials and never return plaintext through endpoints, diagnostics or backups. Follow the shared logging/redaction rules below, including credential scopes and sanitizing exception copies before truncation/persistence. Protected diagnostics retain safe categories, correlation and audit evidence without leaking message content or secrets.
- **Configuration and UI compatibility**: keep defaults in Settings and runtime overrides in `app_config`; render effective booleans canonically and preserve numeric zero/explicit empty values. New controls must retain the existing owner/admin permissions, CSRF checks and bilingual labels. Detail links must resolve to an existing authorized page. Exclude delegated announcement rows in SQL before business-history pagination, and preserve legacy announcement publication/read behavior.
- **Migration and regression evidence**: use additive/idempotent MySQL/PostgreSQL upgrades that preserve historical IDs, delivery outcomes/attempts, publication snapshots, read markers, configuration and bindings without rebroadcast. Imported Webhook credentials require fresh verification; retain deployment connection-setting protections and encryption-key requirements. Reuse the `tests/test_notification_*` regressions and the failure/permission counterexamples for the changed boundary. Run `uv run pytest -q`, `uv run ruff check .`, `uv run python run_ruff.py --check` and `git diff --check` after a rebase affecting notification workers or shared infrastructure. For transaction/claim/schema changes, execute `test_notification_live_db_646.py` on isolated MySQL and PostgreSQL through `.github/workflows/notification-databases.yml`; for UI changes, run `scripts/validate_notification_ui_646.py`. Report fixture/local-receiver results separately from real third-party SMTP/Telegram/Webhook delivery, and never exercise production recipients merely to satisfy a test.

## Pricing and Billing

- **Units and precision**: one Credit is 1,000,000 integer micro Credits. Wallet balances, reservations and ledger deltas use integer units; prices, FX and cost calculations use validated `Decimal` values and the billing engine's independent precision context. Reject floats, non-finite or negative prices and ambiguous units. Token prices are per million; request/document/search prices must match actual measured units. Sum unrounded costs within an operation, then round cumulative payable Credits upward to micro Credits and settle only the new delta. Proportional refunds use integer cumulative rounding, retaining remainders.
- **Immutable account prices**: `backend/services/billing_service.py` publishes append-only price versions scoped by `account_id + provider_id + model_id + call_kind`; resolve the Provider from the configured account. Never substitute another account's tariff or silently fall back to a Provider-wide price for an account-bound call. Provider-wide prices with `account_id=None` remain valid for explicitly unbound auxiliary/historical calls. Freeze the price version, usage semantics, currencies, FX, markup and Credit conversion parameters before sending a call; later edits must not reprice existing calls or historical bills.
- **Call kinds and actual usage**: `backend/services/billing_price_identity.py` canonicalizes `chat_stream` pricing to `chat`, while attempts, raw Usage and snapshots retain the actual call kind. Keep compression, embedding and rerank tariffs separate, and preserve pinned legacy stream prices. Charge actual fallback account/Provider/model usage, never display estimates from `TokenTracker`. Missing or incomplete usage differs from zero; preserve provider-specific cache/reasoning semantics and route missing prices, unknown currencies or inconsistent evidence to `pending_pricing`/`pending_reconciliation` instead of inventing a free or exact charge.
- **Configuration and ownership**: pricing and billing settings live in `app_config` with Settings defaults. Preserve activation checks for every configured billable route and fallback. `payment_enabled` controls sales entry points; wallet/history/admin pricing remain available independently. Freeze charging policy and trusted payer/operation/source identity at admission; changes to global switches must not reinterpret existing operations. Keep platform-owned calls observable, and never infer the payer from untrusted webhook or client fields.
- **Result validation and historical replay**: validate rerank responses inside the metered attempt; malformed results retain real Usage with a failed outcome under the frozen failed-call policy. Valid non-strict partial rankings remain supported. Consult successful historical redeem-code orders before issuing benefits and backfill only their replay link, without consuming another use or rewriting purchased history. Learning a verified Stripe payment reference must replay matching earlier refunds; drain busy receipts after payment commit without inverting inbox/order/wallet locks. Every full refund reconciles the subscription summary from remaining same-plan entitlements.
- **Measured responses and admission identity**: validate and extract complete embedding batches before the usage meter completes. Request OpenAI-compatible streamed Usage according to the model's `stream_usage` capability; disabled options do not fabricate usage. Freeze scan ownership and charging policy in its submission transaction, then recover them from the persisted operation regardless of later account-role changes. User usage totals exclude original/late audit observations only after validating their selected reconciliation record, routing identity and audit event. External partial refunds require the configured proportional policy; an atomically verified full native-refund bundle may revoke the complete source under the default rejection policy.
- **Financial replay and locking**: preserve append-only ledgers, purchased snapshots, source-linked entitlements, reservations, debt and reconciliation audits. Use database uniqueness and the established wallet/order/operation lock order across processes. MySQL repeatable-read replay lookups must use a current locking read when a winner may have committed after an earlier snapshot. Redeem uniqueness recovery must roll back the losing order, redemption and consumed slot in a savepoint, return the winning order and preserve the caller's transaction; unrelated integrity failures must still propagate.
- **Refund lifecycle**: reconcile each native refund ID against the same provider, payment source, order, amount and currency. A verified terminal Stripe/Paddle receipt supersedes matching nonterminal receipts, including late delivery/replay, while retaining original received/reviewed evidence and adding a `superseded` audit. Conflicting or incomplete evidence stays pending. Partial cash refunds require the configured policy and a Credits-only purchased snapshot; reject unrepresentable gateway amounts before creating an intent or hold. Unknown upstream outcomes require reconciliation and must not trigger an automatic second refund.
- **Billing diagnostics**: carry `billing_operation_id`, billing feature and payer identity with the existing request/task/Activity context; log internal order, receipt, refund-attempt and price-version IDs, state transitions, pending reasons and safe counters. Service logs after a flush describe staged effects; report committed delivery only after commit. Use the shared logging/redaction pipeline, scope concrete gateway credentials around SDK/HTTP operations and sanitize exception copies before persistence or truncation. Never log full redeem codes, payment credentials, provider payloads, prompts or complete pricing snapshots.
- **Validation and documentation**: keep `docs/billing-2.md`, its acceptance evidence and bilingual user-facing documentation aligned when changing pricing behavior. Verify account isolation, frozen historical prices, real usage versus missing/zero usage, cumulative rounding, idempotency, failed/unknown delivery and concurrent replay as applicable. Use isolated test prices and mocked gateways; do not contact payment providers or change production tariffs during tests.

- **Verified refunds and canonical dashboards**: successful gateway refund amounts must be strict integer minor units matching the frozen intent; mismatches keep the hold and reconciliation audit. Ambiguous attempts keep review requests pending and block rejection until a verified outcome updates the request. Removing a subscription period rechains only queued periods using their purchased durations, preserving active periods, snapshots and remaining benefits with an appended schedule audit. Global totals and local-day trends use the same validated reconciliation links as user usage, never a role label alone. Low-balance alerts use sensitive `billing.low_balance` events in the financial transaction and existing notification routing; preserve historical notice reads without creating a second new inbox.

## Logging and Observability

- **One logging pipeline**: use Loguru for application logs. `backend/core/logging_bridge.py` owns startup configuration, console/file sinks, standard-library interception, source preservation, level filtering, redaction and retention. Route handlers, providers and workers must not add independent sinks or bypass this pipeline with credential-bearing `print()`/traceback output. Preserve the originating standard `LogRecord` module, file, function, line and timestamp, including queued records and `stacklevel` callers.
- **Exception semantics**: in a Python `except` block, use Loguru's `logger.exception(...)` or `logger.opt(exception=True).error(...)`; use `logger.opt(exception=exc)` when recording a specific exception outside its handler or at another severity. `exc_info=True` belongs to standard `logging`, not Loguru. Do not mechanically replace valid standard-logging calls or change severity. Preserve exception identity, type, args, causes, context, notes and groups; propagate cancellation. Keep traceback diagnostics while leaving local-variable dumps disabled (`diagnose=False`, `backtrace=False` on sinks).
- **Central redaction**: use `backend/core/log_sanitizer.py` for messages, structured fields, headers, OAuth values, URL/query credentials and exception text. Redaction must run before formatting, queueing, output or persistence, including fields added by per-logger patchers. Never rely only on recognizable token prefixes: bind opaque credentials with `sensitive_log_scope(...)` around the concrete operation, including retry/fallback and stream cleanup. Preserve useful counters, status codes, endpoints and unrelated diagnostic text.
- **Escaping errors and copies**: `sensitive_log_scope` retains inherited and existing redaction knowledge on escaping exceptions and their cause/context/group graph before resetting its ContextVar. Keep this behavior for Starlette/Uvicorn re-logging, cancellation, group splitting and detached leaves. Do not dump `_log_redaction_secrets` or exception `__dict__` into logs/responses. When creating warning strings, truncated summaries or persisted failure reasons, call `sanitize_exception_text(exc, secrets=...)` before copying/truncating; arbitrary new text without a linked exception does not inherit provenance. Use `sanitize_text`/`sanitize` for other payloads; do not add local masking implementations.
- **Live levels and hot paths**: both sinks read the cached Settings singleton through the shared filter so database loading, WebUI edits and backup restores take effect without replacing sinks or rotating files. Preserve configured levels; production defaults to `INFO`, and unconfigured development to `DEBUG`. Do not hard-code competing thresholds in business code or suppress operational failures to reduce noise. Filters/patchers must not query external services or reread configuration files per record; avoid redundant full scans. Cache live Settings-derived decisions per record or with explicit invalidation, without serializing raw secrets or delaying updates. Keep log timestamps on the shared TimeService and preserve aware source instants.
- **Structured correlation**: use `backend/core/log_context.py` helpers (`log_context`, `task_logging`, `traced_operation`, `invocation_log_fields`, `update_log_context`) and existing Activity identifiers. Put `request_id`, `session_id`, `task_id`, `invocation_id`, `work_unit_id`, `thread_id`, `attempt_id`, `logical_call_id`, `tool_call_id` and `worker` in structured context rather than only message text. Generate HTTP request IDs locally; do not trust an incoming correlation header. Bind actual session/invocation IDs around the entire worker lane, including clone/index/report and terminal failures. After an observed attempt begins, bind its ID before the SDK call for chat, streaming and embedding; unavailable observation must not fabricate a persisted attempt ID.
- **Async isolation and reload**: copy context on update and restore it in `finally`. New task lanes may retain the submission request ID but must clear unrelated task/session/attempt IDs. Use context-propagating thread APIs or explicit snapshots for executors; never reset a ContextVar token from another task. Async generators must restore the consumer context before yielding and run `aclose()` with their own correlation/redaction scope, retaining cleanup errors. `logging_bridge`, `log_context` and `log_sanitizer` are restart-only in `backend/core/hot_reload.py`; do not reload their process state/ContextVars while scopes are active. This does not disable Settings hot updates.
- **Storage and access**: preserve the JSON Lines `text`/`record` shape and structured IDs used by `backend/services/operational_log_service.py`. Activity log lookup must stay authorized, session-scoped, no-cache and bounded; it reads local structured logs, not arbitrary paths or all replicas. Keep application rotation, age and historical-capacity budgets (currently 50 MB, 10 days and 500 MiB, excluding active files). Keep Docker `json-file` limits for Compose, sandboxd and runners (currently `max-size=50m`, `max-file=3`); deployment changes require container recreation. Never delete an active log to enforce a budget.
- **Setup credentials**: never send the Setup Token to application/Docker logs. Keep its handoff beside the active connection config, private from creation: POSIX `0600`, or a protected process-user Windows DACL with a non-inheritable handle and ACL-capability checks. Publish only after atomic replacement succeeds. Revoke the memory credential immediately on completion; a failed file deletion emits a safe warning and must not turn committed Setup/admin state into failure or prevent restart. Keep README/README_EN and deployment instructions aligned with file-based handoff.
- **Regression evidence**: for logging changes, verify actual console and serialized sinks, original source/traceback, live level changes, opaque/encoded secrets, scope exit followed by framework/worker re-logging, groups/cancellation/stream close, concurrent isolation and Activity attempt/session matching as relevant. Reuse `tests/test_logging_security.py`, `test_logging_review_regressions.py`, `test_logging_bridge.py`, `test_log_context.py`, `test_operational_logs.py`, `test_activity_observability_attempts.py`, `test_hot_reload.py` and `test_setup_token.py`. Keep portable tests active; native ACL and symlink tests may check their real platform prerequisites. Do not treat a safe first log or regex-only check as proof that later copies/persistence are safe.

## Commits and Pull Requests

Use English Conventional Commits, for example `feat(updater): add socket recovery` or `fix(ruff): align Python 3.14 rules`. Follow Gitflow: daily work uses `feature/*` from `develop` and targets `develop`; `release/*` and `hotfix/*` follow the repository’s release flow. Do not push directly to `main` or `develop`. PRs should explain behavior changes, list validation commands, note configuration/database/deployment impact, link related issues when applicable, and include screenshots for WebUI changes. Keep `README.md` and `README_EN.md` aligned for user-facing changes.

## Security and Agent Notes

Never hardcode credentials or commit runtime files such as `config/connection.json` or `.deploy/deployment.env`. For structural code questions, prefer the configured CodeGraph index; use `rg` or direct file reads for literal text, configuration, and documentation.

## Code Review Rules

Review changed behavior against the PR's stated intent and the repository contracts above. Report actionable regressions with a concrete failure scenario; leave formatting, import order, and other deterministic checks to Ruff and pytest. Apply each rule only where the changed code makes it relevant.

### Correctness and compatibility

- Flag incomplete fixes, incorrect edge cases, race conditions, and behavior changes not explained by the PR. Check that the implementation addresses the root cause rather than hiding the symptom.
- Preserve existing API endpoints, request semantics, and response fields unless the change explicitly provides a compatible transition. Check webhook event handling for duplicate or out-of-order delivery.
- Keep existing database rows and deployments usable across migrations; flag destructive schema changes or changed column meaning without an explicit migration and compatibility path.
- Check timestamps and persisted time values against `backend/core/time_service.py` and `backend/models/time_types.py`; do not introduce naive datetimes or bypass the shared time service.

### Configuration and provider behavior

- Do not hard-code configurable model capabilities or provider-specific limits in business logic, including output/context token limits, reasoning and image support, streaming behavior, model IDs, and provider URLs. Resolve them from model metadata, provider configuration, or the appropriate configuration layer when available; flag silent constants that alter behavior.
- Review new timeouts, retry counts, rate limits, and concurrency limits for unjustified constants or duplicate sources of truth. Do not flag protocol-required constants or documented invariant defaults merely for being literals.
- Keep dynamic configuration in `app_config` with Settings defaults as the single default source. For `strategy.*` and `label.*`, preserve default deep merging and tolerant recovery when a section key is missing or invalid; do not restore reads from removed config files.
- Keep provider-specific request, response, and capability handling within the provider abstraction. Flag assumptions about one provider or model that leak into shared review logic or silently change other providers' behavior.
- When changing container update channels, verify the registry service, build info, updater registry, and WebUI version manager remain consistent.

### Async, failures, and delivery

- Flag blocking I/O in async handlers and workers, unbounded background work, or fire-and-forget tasks whose exceptions or cancellations can be lost.
- Do not silently swallow failures or convert an operational error into a success-shaped fallback. Intentional degradation must retain an observable signal and preserve the caller's error or retry semantics.
- Preserve idempotency, retry safety, and status consistency across webhook processing, review publication, comments, Check Runs, and notification delivery. Check failure paths as well as the happy path.
- Keep notification channel and recipient eligibility isolated: a disabled channel, failed endpoint, or unauthorized recipient must not receive another channel's delivery or leak its content.

### Security and regression evidence

- Check authentication, authorization, and repository or organization ownership on new or changed protected endpoints; never trust client-supplied IDs without verifying their scope.
- Never expose credentials, cookies or authentication tokens in logs, comments, notifications or client errors. Keep necessary, sanitized stack traces and internal diagnostics in protected operational logs; never publish them in GitHub comments, notifications or client errors. Verify backup restore still excludes deployment-time database and Redis connection settings.
- For changed high-risk behavior, look for focused tests covering the failure mode and a valid counterexample: compatibility, provider differences, configuration fallback, async failure, access control, or delivery isolation as applicable. Do not demand unrelated coverage or style-only changes.
