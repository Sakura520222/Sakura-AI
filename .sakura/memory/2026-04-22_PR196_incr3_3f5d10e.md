## 深度反思报告

### 1. 审查质量评估
- **覆盖度（存在遗漏）**：审查精准捕捉了本次 `+10/-2` 增量中直接引入的重复风险（第78行 `extract_inline_comments` 追加导致重复），并顺藤摸瓜发现了第80行 `_parse_structured_comments` 导致的整体评论重复。但**遗漏了历史上下文中的关键项**：历史上下文明确指出“emoji路径始终包含start_line而JSON路径仅在end_line存在时添加，造成下游处理逻辑不一致”，本次变更恰好是在JSON路径后补充emoji提取，审查未能追问合并后的 `start_line` 字段不一致问题。
- **准确度（合理但有偏软）**：将重复评论定为 `[minor]` 和 `[suggestion]` 是准确的，因为不影响程序稳定性。但在该文件已被标记5次以上热点的情况下，按规范“命中遗留关注点不因策略降级”，去重机制缺失本应被视为具有更高权重的缺陷，而非纯建议。
- **完整性（意图理解到位，全局视野受限）**：准确理解了“JSON为主，Markdown为辅”的补充提取意图，且对日志改进给予了正面反馈。但在完整性上受限于 `quick` 策略，未能对 `result_parser.py` 持续累积的“多源聚合无归一化”架构债务发出足够警告。

### 2. 发现的模式
- **代码模式：累加器反模式**。`result["inline_comments"]` 在本次变更中经历了三次累加：`_apply_json_result` -> `extract_inline_comments` -> `_parse_structured_comments`。这种“只管追加不管去重”的模式正在蔓延，且每次追加的数据结构（如有无 `start_line`）可能存在微妙差异。
- **架构观察：混合解析器的边界模糊**。项目试图从纯 Markdown 解析过渡到 JSON 结构化解析，但采用了“共存叠加”而非“互斥切换”的策略。这导致 `result_parser.py` 成为一个巨大的漏斗，所有格式的输出最终都被混合到同一个 List 中。

### 3. 规范完善建议
- **新增规则：多源聚合去重审视**。当同一变量在同一作用域内被多个不同来源的函数追加赋值时（如 `list.extend()` 连续调用），必须审查是否存在重复元素风险，且必须确认各来源产出的数据结构（Schema）是否完全对齐。
- **新增规则：局部指标全局有效性校验**。当新增局部统计变量（如 `markdown_inline_count`）时，必须验证该变量是否覆盖了目标状态（`inline_comments` 列表长度变化）的**所有**修改路径。遗漏路径导致指标失真应标为 `[minor]`。
- **细化规范：热点文件增量审查底线**。对于历史标记超5次的热点文件，即使是 `quick` 策略，也必须在摘要中强制输出一句“**当前未闭环核心债务：[列表]**”，防止增量隧道视野掩盖即将失控的技术债。

### 4. 经验教训
- **局部精确导致全局失真的陷阱**：第85行新增的 `markdown_inline_count` 看似提升了可观测性，但由于忽略了第80行 `_parse_structured_comments` 的隐式写入，反而可能在未来误导调试（日志显示增加2条，实际增加5条）。**教训：审查指标代码时，必须做变量的“全量写入者扫描”。**
- **“微小改进”在脆弱架构下的边际效益递减**：在一个缺乏统一模型层和去重层的解析器里，增加日志和补充提取逻辑，只是在泥潭上铺砖。**教训：面对热点文件，审查者的更高价值在于指出“停止叠加，重构底座”，而非指导“如何更好地叠加”。**

### 5. 增量审查反思
- **问题解决情况**：本次提交未解决历史遗留的去重问题，反而因为新增了 `_parse_structured_comments` 的调用路径，**扩大了重复的影响面**（从仅行内评论重复，扩大到整体评论也重复）。
- **新风险引入**：引入了“日志误导”的新风险（上述的 `markdown_inline_count` 不准确），以及“隐式双重提取”风险（第80行既提取整体评论又可能提取行内评论的逻辑未被充分剥离）。
