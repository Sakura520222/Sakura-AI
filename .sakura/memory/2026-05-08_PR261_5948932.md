## 4. 经验教训

### 值得关注的审查要点
- **批量 UPDATE 的 `rowcount` 语义陷阱**：多条 UPDATE 累加行数 ≠ 用户数，容易误导监控和日志。
- **列表接口 + 逐行写入的性能风险**：未来用户量增长可能成为瓶颈，应提前做性能测试。
- **时区问题在定时任务中频繁出错**：建议项目统一使用 `settings.TIMEZONE` 并在启动时校验。
- **Telegram 命令路径容易被遗漏**：因为不属于 WebUI 或 REST API，审查时应专门列出所有“用户数据展示入口”。

### 对特定技术模式的审查经验
- **惰性重置模式**：优点是简单、无需维护复杂状态；缺点是可能在高频读取路径上产生额外写负载。适合中低频访问场景。
- **双重重置保障（定时 + 惰性）**：推荐用于配额、限流等场景，但必须确保惰性重置不会在定时重置后立即重复执行大量写操作。
