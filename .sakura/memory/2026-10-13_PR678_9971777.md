### 2. 发现的模式

* **代码模式**：
  * **防御性与边界钳制意识**：在入站安全（SSRF、参数校验）做得非常完备，但**由外向内的控制反转字段（如响应头 `Retry-After`、不可信响应耗时）容易漏掉防线钳制**。
  * **异常翻译分层遗漏**：底层 Provider（如 SMTP/aiohttp）的内建异常（`TimeoutError`, `ConnectionResetError`）容易在中间服务层穿透，导致 Web 层顶层兜底捕获成 500。
* **架构观察**：
  * **基于 SQL 的轻量级可靠事件流**：采用 Postgres/MySQL 行锁及状态字段实现 Outbox 机制，避免了引入 Kafka/RabbitMQ 等重型 Broker，契合中小型自部署系统的设计哲学。
  * **扇出计算（Fanout）倾斜至应用层**：订阅匹配在应用内存中遍历进行，而非下推到数据库复杂 SQL 或专用规则引擎。这使得系统逻辑清晰，但架构对“单用户规则数”和“规则总数”敏感。

---

### 3. 规范完善建议

针对本次审查发现的典型问题，建议在项目审查规范与项目记忆中补充以下规则：

1. **外部控制反转值必须设置硬上限（Hard Clamping）**：
   * *规则*：凡是消费来自不可信外部依赖（HTTP Header、Webhook 响应、第三方 API 返回的限流指令等）用于计算本系统调度时间、睡眠时长或重试间隔（`next_retry_at`、`delay`）的字段，必须强制实施 `min(val, MAX_ALLOWABLE_DELAY)`，默认上限不应超过 1 小时。
2. **异步 Provider 必须实现“异常全翻译”契约**：
   * *规则*：Provider 实现层在暴露给 Dispatcher 前，严禁向外抛出未包装的标准库/第三方网络异常（如 `asyncio.TimeoutError`、`aiohttp.ClientError`、`smtplib.SMTPException`）。必须全部收敛映射至 `NotificationProviderTransientError` 或 `NotificationProviderPermanentError`。
3. **扇出与批处理路径强制容量保护（Capacity Guard）**：
   * *规则*：任何涉及“按规则匹配并产生持久化行”的实体（如订阅规则、通知端点），在创建 API 端必须强制校验配额上限（Tenant/User-level Quota），并在全量载入查询处增加 `LIMIT` 熔断。

### 4. 经验教训

* **“不可信输入”不仅限于 Request，也包括 Response**：
  * 很多安全审查习惯性聚焦在 API 请求体和 URL 参数上，容易忽视**外部服务响应头（Response Headers）和响应体**对内部调度状态机的毒化风险（如构造异常的 HTTP-Date 冻结内部任务）。
* **关注生命周期闭环（Lifecycle Closure）**：
  * 对于新增消息/事件/审计类数据表（Outbox/Deliveries），审查清单应在“建表、索引、并发锁”之外，自动补齐**数据清理/生命周期（Retention/Purge/Vacuum）检查项**。
* **对于高完成度 PR 的警惕性**：
  * 开发者提供了 5000+ 测试通过与完整 CI 验证，容易使审查者产生“全面可靠”的心理定势；本次审查能够穿透大量测试直接抓住 `Retry-After` 和超时异常漏捕获，体现了对**失败分支与边缘语义**审查的价值，未来应继续保持对“Happy Path 测试完备但边缘缺少防线”代码的质疑深度。
