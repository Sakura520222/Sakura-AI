## 深度反思

### 1. 审查质量评估

**覆盖度：存在两处可改进盲区**

- **正则边界未充分穷举**：`(\w+)\s*\["([^\]]*)"\]` 中 `\w+` 仅匹配单词字符，若文件路径经哈希后产生的 node ID 包含非单词字符（如 `-`），会静默丢弃历史节点。审查未对 node ID 生成规则与正则的兼容性做交叉验证。
- **不可逆转义的影响评估缺失**：审查接受 `"` 和 `\` 不可逆的 docstring 声明，但未追问：实际代码仓库中文件路径含 `"` 或 `\` 的概率是否为零？若非零，增量合并时这类路径的历史节点将丢失，属于**静默数据退化**，至少应标 minor。

**准确度：基本合理，有一处偏轻**

- `_parse_previous_graph` 缺直接测试标 minor 正确，且与「新增未测试方法评分硬上限 ≤8」对齐（本次恰为 8 分，合规）。
- 不可逆转义问题未标记偏轻——这本质上是"恒定回退值/静默失败路径"的一种变体，数据静默丢失比抛异常更难发现。

**完整性：意图理解充分，决策声明不完整**

- 增量合并机制（先解析当前 import，再合并历史边；历史节点进入候选池）的理解准确。
- **违反「决策完整性声明」原则**：approve 时存在 1 个未解决 minor，但审查摘要中未显式声明"已知 minor X，接受其风险并 approve"。quick 策略下这条仍须执行。

### 2. 发现的模式

**代码模式**
- **正则解析 Mermaid 作为序列化协议**：用 Mermaid 文本做增量状态的持久化载体，轻量但脆弱（格式依赖、转义不对称）。项目在选择"简单可读"而非"结构化序列化"上有明确倾向。
- **防御性跳过模式**：`node_id_to_path` 查询缺失时自然跳过误匹配边——利用字典 get 的 None 语义做隐式过滤，简洁但无日志，调试时不可见。

**架构观察**
- 增量逻辑嵌在图生成层而非数据采集层，意味着每次仍需全量解析 import，增量仅节省了图的"组装"开销而非"解析"开销。PR 描述称"避免重复全量计算"略有夸大，但未到误导程度。

### 3. 规范完善建议

**建议新增规则**

| 规则 | 触发条件 | 处置 |
|------|---------|------|
| **不可逆转换影响评估** | escape/encode 与 decode 不对称时 | 须声明受影响字符集在业务输入中的出现概率，或加断言/日志 |
| **正则解析方法边界审查** | 新增含 regex 的解析方法 | 须显式列出：(1)正则能匹配的字符集 (2)输入源实际可能产生的字符集 (3)差集的影响 |
| **增量描述精度校验** | PR 描述声称"避免全量"但实际仅部分增量 | 标 minor 描述精度问题（不阻断但须指出） |

**现有规则强化**
- 「决策完整性声明」在 quick 策略下同样强制，当前项目记忆已写明但本次未执行，建议在审查模板中将其作为 approve 前的 checklist 最后一项。

### 4. 经验教训

1. **正面评价越多，越要对"被接受的限制"做二次检查**：本次 5 个 ✅ 之后仅发现 2 个问题，但不可逆转义和数据静默丢失藏在"已验证"项的缝隙中。应反向问：每个 ✅ 的前提假设是什么？前提不成立时会怎样？

2. **正则解析 = 契约不显式**：正则隐含了对输入格式的强假设，但不像类型注解或 schema 那样可机器检查。审查时必须手动做"字符集交叉验证"，不能仅看正则逻辑自洽。

3. **quick 策略不等于跳过决策声明**：8 分是 quick 的硬上限，但达到上限时反而更应严格检查所有前置条件是否满足，否则 8 分失去区分度——所有 quick 审查都会趋同到 8 分。
