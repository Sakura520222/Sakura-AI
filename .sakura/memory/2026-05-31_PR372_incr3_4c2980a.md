## 2. 发现的模式

### 代码模式

1. **Agent 会话使用 system + user 起始消息模式**

   项目中的 agent 逻辑倾向于：

   - system prompt 定义角色、规则、工具使用方式；
   - user message 明确当前任务；
   - 后续循环中由 LLM 响应和工具调用推动流程。

   本次 consolidation agent 向 knowledge extractor 对齐，是一个积极信号。

2. **`_run_agent_conversation` 是核心流程抽象**

   多个 agent 复用该方法，说明它是 agent 行为的核心模板。对该方法的任何微小变更都可能影响：

   - 知识提取；
   - 文件整合；
   - 工具调用；
   - 日志语义；
   - 最大迭代退出逻辑。

   因此即使是 `break` → `return` 的小变更，也需要关注所有调用方语义。

3. **日志语义被测试化**

   新增测试验证“不应误报最大迭代次数”，说明项目开始把日志行为当作可测试契约。这是好现象，尤其适用于 agent 流程、异步流程、重试流程等可观测性强相关代码。

4. **测试中存在私有属性注入模式**

   通过 `_api_client` 直接注入 mock client 可以快速隔离外部依赖，但会加深测试对内部实现的绑定。未来如果 agent client 初始化逻辑重构，测试可能需要同步调整。

### 架构观察

1. **服务层 agent 基类 + 具体 agent 子类**

   项目采用：

   - `SakuraAgentBase` 提供会话循环；
   - `SakuraKnowledgeExtractor`、`SakuraConsolidationAgent` 实现具体任务。

   这是合理的模板方法风格，但需要持续确保基类变更不会破坏子类隐式契约。

2. **LLM 调用失败的处理策略偏向静默终止**

   `return` 之后方法直接结束，调用方是否能感知失败取决于外部日志，而非返回值或异常。这种设计简单，但也带来风险：

   - 上层无法区分“正常完成”“LLM 错误提前结束”“空响应提前结束”；
   - 如果未来需要任务状态上报或重试策略，当前接口表达力不足。

3. **历史热点文件与当前变更脱节**

   `sse.py` 是历史热点，但本次实际变更转向 agent 服务层。审查时需要避免被历史上下文过度牵引，导致忽略当前 PR 描述漂移和实际变更意图。

## 3. 规范完善建议

### 建议新增审查规则

1. **PR 描述与实际 diff 一致性检查**

   规则建议：

2. **审查决策与问题严重程度一致性规则**

   规则建议：

   > 若审查结论为“无严重/重要问题，仅有建议”，决策不得为 `request_changes`。`request_changes` 必须对应至少一个明确的阻断、major 或必须修改项。

   本次 `9/10 + 无重要问题 + request_changes` 明显不一致。

3. **结构化评论严重程度校验规则**

   规则建议：

   > 自动生成的主要评论中，正向评价、摘要、文件列表、测试说明不得被标记为 `critical`、`major` 或 `minor` 问题。严重程度标签只能用于具体可操作问题。

   本次 `[critical]: ✅ 与项目现有模式一致` 是典型误标。

4. **核心基类变更调用方扫描规则**

   规则建议：

   > 修改基类核心控制流方法时，即使 diff 很小，也必须列出所有直接调用方，并检查调用方是否依赖异常传播、返回值、日志、副作用或循环结束语义。

   本次审查有初步提到两个调用方，但还可以更系统化。

5. **Agent 会话起始消息规范**

   规则建议：

   > 所有 agent conversation 应明确使用 `[system, user]` 起始消息模式；如果只依赖 system prompt 启动任务，需要有注释说明原因，并有测试覆盖消息序列。

   本次 consolidation agent 的变更正好可以沉淀为项目规范。

6. **日志行为变更测试规则**

   规则建议：

   > 对错误处理、重试、最大迭代、降级路径的日志语义变更，应新增测试验证关键日志存在或不存在，避免误导性可观测性。

   本次新增测试是正面案例。

### 项目特有规范要点

- agent 基类控制流变更需要关注所有 agent 子类；
- LLM 调用失败路径不应误报“最大迭代”；
- consolidation agent 与 knowledge extractor 应保持启动消息模式一致；
- 测试可使用 mock client，但优先通过公开注入点或 monkeypatch，而不是直接依赖私有属性；
- 历史 PR 上下文不能替代当前 diff 校验。

## 4. 经验教训

1. **小控制流变更也可能是行为契约变更**

   `break` → `return` 看似微小，但改变了循环结束后的公共逻辑是否执行。审查时要重点检查：

   - 循环后是否有日志、清理、状态更新、指标上报；
   - 提前 `return` 是否跳过必要副作用；
   - 是否影响调用方对完成状态的判断。

   本次因为循环后只有“达到最大迭代次数”的 warning，所以 `return` 是合理的。

2. **日志不是附属品，而是可观测性契约**

   错误场景下误报“达到最大迭代次数”会误导排障。日志语义修复应被视为真实质量改进，而不只是 cosmetic change。

3. **Agent 应避免只靠 system prompt 推断任务**

   system prompt 适合描述角色、约束和工具规则；具体任务应通过 user message 明确给出。这样更符合对话模型习惯，也更容易测试和调试。

4. **新增测试要避免过度绑定私有实现**

   直接写 `_api_client` 虽然方便，但长期看会降低测试韧性。更稳妥的方式包括：

   - 通过构造函数注入 client；
   - monkeypatch `_ensure_client`；
   - 提供测试专用 fake client；
   - 使用公开接口触发初始化。

5. **审查输出本身也需要被审查**

   本次代码层面质量较高，但审查结果存在：

   - 决策矛盾；
   - critical 标签误用；
   - PR 描述不一致未指出。

   这说明审查质量不只取决于代码分析，还取决于最终报告结构是否准确、可执行、无噪音。

## 5. 增量审查反思

### 新增提交是否解决了之前审查提出的问题？

本次新增提交并不是直接修改历史关注的 `backend/webui/sse.py`，而是 agent conversation 相关重构和测试。

因此更准确的说法应是：

- 历史 SSE 问题不在本次增量 diff 中；
- 根据历史审查记录，前几轮已认为 SSE 问题修复；
- 本轮没有重新验证 `sse.py`；
- 本轮主要关注 agent conversation 新增变更。

原审查中“之前的问题已确认全部修复”表述偏绝对，容易让人误以为本轮重新检查了相关文件。

### 增量变更是否引入新风险？

整体风险较低，但仍有几个潜在点：

1. **提前 `return` 是否跳过未来逻辑**

   当前看循环后只有最大迭代 warning，因此合理。但如果未来在循环后增加统一清理、指标上报或状态落库，提前 `return` 可能绕过这些逻辑。建议未来将“最大迭代 warning”放入 `for...else` 或显式状态判断中，降低控制流脆弱性。

2. **LLM 失败结果不可被调用方感知**

   当前 `_run_agent_conversation` 似乎没有返回状态。LLM 错误只通过日志体现。短期可接受，但长期可能限制任务状态管理。

3. **测试 mock 策略依赖私有属性**

   不阻断，但需要关注未来维护成本。

4. **PR 元数据漂移**

   PR 描述与实际变更不一致是实际流程风险，可能导致合并记录失真。

### 审查覆盖度是否因只看增量部分下降？

有一定下降。

本次审查较好覆盖了增量代码，但没有充分处理以下跨上下文问题：

- PR 描述和实际 diff 不一致；
- 历史 SSE 变更与当前 agent 变更之间的关系；
- 基类方法修改对所有 agent 子类的长期契约影响；
- 审查决策与正文结论的一致性。

增量审查的正确做法应是：

1. 先确认本次 diff 与 PR 描述是否一致；
2. 再确认历史问题是否仍在本次范围内；
3. 对基类、公共方法、核心循环等变更执行调用方扫描；
4. 最后确保严重程度、评分、合并决策三者一致。

但审查报告本身存在明显质量问题：

- `request_changes` 与“无重要问题、9/10”矛盾；

- 未指出 PR 描述与实际变更严重不一致；

未来类似审查应强化三点：

1. **先校验 PR 元数据与 diff 是否一致；**
2. **核心基类控制流变更必须扫描调用方和后续逻辑；**
3. **审查结论、严重程度和决策必须保持一致。**
