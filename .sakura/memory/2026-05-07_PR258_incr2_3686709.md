### 三、规范完善建议

**新增/修改审查规则**

| 规则 | 类型 | 说明 |
|------|------|------|
| **新增状态必须检查 SSE 事件** | major | 变更涉及状态枚举时，强制扫描 `sse_service.py` 或所有 `send_event()` 调用点 |
| **新增状态必须检查 DB 迁移** | major | 若使用原生 ENUM，要求提供 ALTER TYPE 语句或 Alembic 迁移 |
| **API 响应字段名变更风险分级** | suggestion | 字段语义变更但保留旧名称时，必须标注 breaking change 风险等级（低/中/高） |
| **注释不替代显式异常恢复** | major | session 异常后必须显式 `rollback()` 或 `close()`，禁止仅注释声称“会自动恢复” |

**项目特有规范补充**
- **`cancelled` 状态的转换路径**：应明确哪些状态可以转为 `cancelled`（如 `pending` → `cancelled`？`running` → `cancelled`？），并在审查中验证状态机完整性
- **多轮未修问题的升温机制未触发**：`should_skip` 和 `PRIssueLink` 已连续 2 轮未修，按项目记忆应从 suggestion 升为 major，本轮审查未执行升温

### 四、经验教训

**值得未来关注的要点**
1. **状态变更的全链路清单应标准化**：建议创建固定检查表（DB ENUM → 模型枚举 → API 序列化 → WebUI 模板 → i18n → SSE 事件 → 状态转换矩阵），每次新增状态逐项打勾
2. **增量审查的“调用方扫描”不足**：`webhook.py` 返回 `task_id` 字段，但未检查是否有其他模块解析该响应（如前端或 CLI 工具）。项目记忆要求“修改变更文件时须扫描导入该模块的所有调用方”，但本次未对 API 响应消费者做扫描
3. **注释质量验证应更严格**：`_safe_db_delete` 的注释声称行为与实现不一致，审查仅标记 suggestion，但按“注释 vs 结构决策”原则，此类缺陷应至少为 minor

**对特定技术/模式的审查经验**
- **asyncio + SQLAlchemy 的 session 管理**：捕获异常后 session 进入 `inactive` 是常见陷阱，审查应强制要求显式 `rollback()` 或 `expunge_all()`，不信任文档声称的“隐式恢复”
- **业务键 vs 技术键的 API 设计**：`task_key` (owner/repo#pr_number) 和 `task_id` (UUID) 分离是好的，但 API 响应字段名与内部变量名语义不一致时，审查应要求 **字段名也同步**，否则会在 API 层面永久遗留误导
