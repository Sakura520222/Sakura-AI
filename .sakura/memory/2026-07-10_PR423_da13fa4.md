## 2. 发现的模式

### 代码模式
从变更摘要看，这个仓库的协议解析具有以下特点：
- 解析器是**格式驱动**的，依赖标签和字段消费索引；
- 多行字段存在**兼容多种输入形态**的需求；
- `NONE` 语义被当作一种显式空值协议，而不是普通字符串。

这意味着代码中很可能存在：
- “宽松解析”和“严格校验”并存；
- 解析成功与业务语义转换分层处理；
- 字段状态需要保留 `None / 空串 / 缺失` 的区别。

### 架构观察
依赖图非常简单：
- 只有 `backend/services/issue_protocol.py` 和测试文件直接相关；
- 说明这是一个**局部协议层变更**，影响面集中。

这类架构的优点是：
- 易于定位；
- 回归面相对有限。

但风险也很典型：
- 协议层一旦放宽格式，容易在下游形成**隐式兼容债务**；
- 解析规则如果缺乏统一测试矩阵，后续很容易在“新增一个字段”时重复出错。

## 3. 规范完善建议

### 建议新增或强化的审查规则
1. **解析器变更必须补负面样例**
   - 不仅检查“新增支持什么”，还要检查“原有错误是否仍然报错”。
   - 特别是标签解析、状态机、索引消费类代码。

2. **协议兼容性变更要区分语义层**
   - 例如 `NONE`、空字符串、缺失字段要分别验证；
   - 防止把“兼容单行写法”误扩展成“容忍任意空值”。

3. **quick 模式下必须执行输出合规自检**
   - 包括评分上限、决策声明、负面检查清单。
   - 这次就是典型例子：代码没大问题，但审查结果自身不合规。

4. **对解析逻辑的测试应覆盖“格式矩阵”**
   - 单行闭合
   - 多行闭合
   - 缺失闭合
   - 空白行包裹
   - 标签首尾同一行
   - 非法嵌套/重复标签

### 项目特有规范要点
- `NONE` 是协议语义，不是普通文本；
- 标签格式变更必须保证上下游一致；
- 解析器一旦涉及索引消费，必须关注**状态推进是否稳定**；
- 如果是首个全量审查，应该更强调**边界与回归**，而不是只看新增测试是否存在。

## 4. 经验教训

### 未来审查要点
- **越是看起来“小而稳”的解析修复，越要查负面样例**；
- 兼容性增强常常意味着“隐式接受范围扩大”，这是最容易漏掉的问题；
- 首次全量审查时，不能因为变更集中就默认风险低；
- 对协议解析代码，要特别关注：
  - 标签闭合规则
  - 空白规范化
  - 缺失字段的语义差异
  - 索引推进是否会吞掉后续字段

### 对特定模式的经验
- “支持单行 NONE”这种修复，最容易发生两类问题：
  1. **过度宽松**：把本该报错的格式也吞了；
  2. **局部修复**：只修了一个字段，其他同类字段仍然不一致。
- 如果解析逻辑存在共享函数，测试不能只围绕一个字段写“点状用例”，应尽量写成**表驱动测试**，提高覆盖面和可维护性。
