## 2. 发现的模式  

### 代码模式  

| 模式 | 说明 | 优点 | 潜在问题 |
|------|------|------|----------|
| **集中常量定义 + 公共工具函数** | `backend/webui/auth.py` 中统一管理 `ACCESS_TOKEN_EXPIRE_DAYS`、`WEBUI_TOKEN_COOKIE_NAME`、`WEBUI_TOKEN_COOKIE_MAX_AGE`，并提供 `set_webui_token_cookie`、`renew_webui_token_cookie` | 降低硬编码、易统一修改、提升可读性 | 若常量在多个子模块被直接复制（如 `deps.py` 中仍写 `7 * 24 * 60 * 60`），会出现“常量漂移”。 |
| **依赖注入 (FastAPI `Response`)** | 在 `deps.py` 中把 `Response` 注入到依赖函数，以便在认证成功后直接写 Cookie | 充分利用 FastAPI DI，保持业务函数纯粹 | 依赖函数副作用（写 Cookie）可能与后续中间件冲突，需要文档说明。 |
| **滑动会话实现** | 每次请求成功后重新签发 JWT 并刷新 Cookie | 符合用户体验需求，降低频繁登录成本 | 需要确保 **刷新时不修改原有 claims**（如 `sub`、`role`），否则可能导致权限漂移。 |
| **测试驱动** | 新增专门的 `tests/test_webui_session_renewal.py`，覆盖正向、负向、模式隔离等场景 | 提高改动安全性，CI 通过即保证功能完整 | 测试依赖了内部实现细节（如 `MAX_AGE` 常量），若常量迁移可能导致测试失效，需要保持测试与实现解耦。 |

### 架构观察  

1. **WebUI 与 API 的会话层解耦**：两套依赖文件分别负责 WebUI 与 API 的认证逻辑，且共享 `auth.py` 中的核心实现，体现了 **“统一认证、分层使用”** 的设计。  
2. **Cookie 与 Bearer 双通道**：系统仍保留 Bearer Token 与 Query 参数的认证方式，并在代码中明确排除它们的滑动续期，说明对 **不同客户端（浏览器 vs 脚本）** 的需求有清晰区分。  
3. **未出现全局中间件**：会话续期通过依赖函数完成，而不是统一的中间件，这保持了 **依赖注入的颗粒度**，但可能导致在新增路由时忘记注入 `Response` 而失去续期功能。

## 3. 规范完善建议  

### 1. 审查规则层面  

| 建议 | 说明 | 受影响文件/场景 |
|------|------|----------------|
| **异常路径安全审查** | 对所有涉及 JWT 解码、签名、Cookie 写入的代码，检查是否捕获并脱敏异常，是否避免泄露内部错误信息。 | `backend/webui/auth.py`、`backend/*/deps.py` |
| **常量漂移检测** | 在 CI 中加入脚本检测 `*EXPIRE_DAYS*`、`*MAX_AGE*` 等常量是否出现硬编码（如 `604800`）而未引用统一定义。 | 全项目，尤其是 `deps.py`、`routes/*.py` |
| **Cookie属性统一校验** | 确认所有设置 Cookie 的地方均使用 `Secure=True、HttpOnly=True、SameSite=Lax`（或根据部署环境可配置），并在审查中列为必检项。 | `auth.py` 中的 `set_webui_token_cookie`、`renew_webui_token_cookie` |
| **JWT刷新策略审计** | 检查在刷新 JWT 时是否保留 `jti`、`iat`、`nbf` 等字段，或是否重新生成 `jti` 防止重放。 | `auth.py` 中的 `create_access_token` 调用 |
| **依赖注入完整性** | 对新增路由或已有路由的修改，审查是否仍然注入 `Response`，若缺失则提醒补全。 | `backend/webui/routes/*.py`、`backend/api/v1/routes/*.py` |

### 2. 项目特有的规范要点  

1. **会话常量统一文件**：建议在 `backend/webui/constants.py`（或 `config.py`）中放置所有会话相关常量，所有模块通过 `from .constants import ...` 引入，避免重复定义。  
2. **测试命名约定**：新增的功能性测试文件以 `test_<module>_*.py` 命名，且每个测试文件应包含 **正向、负向、边界** 三类用例；审查时可快速检查是否满足。  
3. **文档同步**：在 `README` 或 API 文档中明确说明 **“Cookie 模式会自动滑动续期，Bearer/Query 不续期”**，避免使用者误解。审查时核对是否已有相应文档更新。

## 4. 经验教训  

| 教训 | 具体体现 | 后续关注点 |
|------|----------|------------|
| **滑动会话实现必须兼顾安全** | 代码只关注了 `exp` 与 `Max-Age`，但未检查 `jti` 重复或 Token 重放风险。 | 在实现 JWT 刷新时，考虑 **重新生成 `jti`** 或在服务器端维护 **黑名单/白名单**。 |
| **依赖注入的副作用容易被遗漏** | 若后续新增路由忘记注入 `Response`，滑动续期会失效而不易察觉。 | 在代码审查 checklist 中加入 **“是否注入 Response 用于 Cookie 写入”** 项。 |
| **硬编码常量是隐蔽的回归入口** | `604800` 直接写在 `deps.py`，若后续改为 14 天，需要同步所有位置。 | 引入 **常量漂移检测脚本**，并在 CI 中强制使用统一常量。 |
| **测试覆盖要与实现解耦** | 测试直接引用 `ACCESS_TOKEN_EXPIRE_DAYS` 常量，若常量迁移路径变化，测试会失效。 | 使用 **黑盒方式**（如通过请求返回的 `Set-Cookie` 中的 `Max-Age`）而不是直接读取内部常量。 |
| **文档与代码同步** | PR 中未看到对应的文档更新（如 API 文档或用户手册）。 | 在审查 checklist 中加入 **“文档是否同步更新”** 检查点，尤其是涉及行为变更的功能。 |
