## 3. 规范完善建议

基于本次审查，建议新增或强化以下规则：

### 新增规则
| 规则 | 严重度 | 说明 |
|------|--------|------|
| **幂等性强制注释** | major | 公共方法若设计为可重复调用（即幂等），必须在 docstring 中用“幂等: 是/否”标注。违反时标记 major。 |

### 强化已有规则
- **“注释语言一致性”（已列为 minor）**：应升级为在首次全量审查中强制检查，并建议配置 pre-commit hook 扫描新增注释的语言混合。

## 4. 经验教训

### 值得在未来审查中关注的要点
- **防御性调用点的“假阴性”风险**：当一个函数声明“异常时返回 0”，审查时必须检查调用方是否真的能容忍“0 代表无操作但实际有操作未执行”。特别是在安全相关逻辑（如驳回旧评审）中，假阴性可能导致安全漏洞。
- **注释与代码的距离漂移**：本次案例中，注释留在原处而代码移动至上方。建议在审查时对“注释位置与实际代码块的距离”保持敏感，若超过 5 行且无引用标记，应要求注释跟随代码或删除。
- **统一入口模式的反模式**：将多条防御逻辑合并到入口虽好，但可能导致中间步骤失败后整个操作中断。应审查是否设计了部分失败的补偿机制。

### 对特定技术/模式的审查经验
- **GitHub API 调用的审查重点**：
  - 分页处理（`dismiss_bot_reviews` 是否处理了超过 30 条旧评审？）
  - 速率限制降级（返回 0 前是否记录了 `X-RateLimit-Remaining`？）
  - 无网络时的行为（是立即失败还是进入队列？）
- **“成功但无操作”的返回值设计**：若返回 `int` 表示操作数量，应额外提供布尔状态或使用 `Result` 类型（如 Rust 的 `Result<u32, Error>`）。Python 项目中可考虑使用 `tuple(bool, int)` 或自定义类。
