## 6. 经验教训

### 值得在今后分析中关注的要点

1. **性能问题分析模板**：  
   - 定位白屏/卡顿时，必须区分前端渲染 vs 后端 API 阻塞  
   - 日志中用 INFO 标记函数进入/退出时间（如本例日志缺乏耗时埋点）  
   - 建议未来分析要求 Issue 提供更详细的时间戳或火焰图

2. **GitHub API / 第三方 API 调用审查模式**：  
   - 任何调用第三方列表接口（如 `get_repos()`）时，需检查是否可带 `per_page` 或过滤参数  
   - “仅需判断是否有安装”的场景，应优先使用轻量校验接口

3. **缓存与阻塞的关系**：  
   - 首次请求无缓存时，性能问题会被完全暴露  
   - 预热缓存（方案 C）适合高频读但首次请求仍会命中慢路径，需配合方案 A 或 B

4. **仓库特有模式应用**：  
   - 本次分析未显式引用项目记忆中的“只读接口禁止嵌入写操作”规则（因为本例是读 GitHub API，不算写操作）。但有一条“只读接口中禁止嵌入写操作”逻辑可类比：*只读接口中不应嵌入不必要的重量级读取*。可新增一条记忆规则：“检查是否存在状态的轻量查询中混杂了批量重量查询”。

5. **`good first issue` 判断改进**：  
   - 明确标准：涉及多模块（webui + github client + cache）、需要理解 API 限流和异步阻塞的问题，不应标为 good first issue。  
   - 建议将置信度阈值提高到 0.75 以上才推荐，否则不输出该标签。
