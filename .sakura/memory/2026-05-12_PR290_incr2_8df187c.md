### 2. 发现的模式

#### 代码模式
1. **路径判断的排除法反模式**：`_is_webui_path` 使用 `path not in exclude_list` 判断，当新增非 WebUI 根路由时容易遗漏。这反映了项目早期路由设计的无前缀混乱历史。

2. **硬编码 URL 的惯性**：`scan_report_service.py` 和 `telegram/handlers.py` 中多次出现 `f"https://{domain}/xxx"` 模式，表明项目长期缺乏统一的链接服务抽象。

3. **私有函数跨模块导出**：`_is_webui_path` 以下划线开头却作为公共 API 使用，反映了命名规范与使用方式的脱节。

#### 架构观察
- **路由层级不清晰**：WebUI 路由挂在根路径，没有明确的命名空间分隔（如 `/webui` 或 `/app`），导致需要通过排除法区分 WebUI 请求和 API 请求。
- **配置与工具函数分散**：链接生成逻辑散落在 service、telegram 模块中，未集中到 `utils/url.py` 或 `services/link_service.py`。
- **依赖倒置不足**：`deps.py` 中定义了 `_is_webui_path`，但 `main.py` 仍直接依赖它，而不是通过中间件或依赖注入标记请求类型。

### 4. 经验教训

#### 值得关注的审查要点
1. **排除法判断路径是高风险模式**：一旦新增非目标路由，排除列表容易遗漏，应优先使用显式路由前缀或中间件注入属性。
2. **硬编码 URL 的衰变风险**：即使此次修改正确，未来路由再次变更时仍可能遗漏，必须推动引入统一服务。
3. **增量审查容易忽略"未修复的历史问题"的追踪**：本次审查列出了排除法问题和硬编码问题，但未在 PR 描述或评论中创建 issue 追踪（违反项目记忆中的"增量审查必须强制输出未修复历史问题的 issue 追踪状态"）。
4. **路由前缀变更的级联影响**：不仅要检查 `.py` 和 `.html`，还要检查 JS 中的 `fetch('/webui/...')`、CSS 中的背景图路径、以及外部系统（如 OAuth 回调配置）。

#### 对特定技术的审查经验
- **FastAPI 路由挂载**：当 `include_router(router, prefix="")` 时，需要特别留意是否存在历史遗留的绝对路径路由（如 `@router.get("/webui/dashboard")` 与新的根路径冲突）。
- **Telegram 机器人的 URL 生成**：由于 Telegram 消息无法自动更新，硬编码链接会永久失效，必须通过环境变量或配置中心动态生成。
