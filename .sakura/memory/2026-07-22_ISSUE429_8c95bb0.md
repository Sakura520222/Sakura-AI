### 6. 经验教训

- **对于部署/配置类 Issue，必须提供阶梯式排查清单，并按概率排序**。本次分析已经做到，但可以进一步提示用户：**“请先检查是否已通过 `/sign` 命令注册 GitHub 账号。”** 未来可直接在分析结果中添加一行“最快验证命令”。
- **仓库特有的模式**：该仓库（Sakura AI Reviewer）的机器人依赖 Telegram 注册，这是与一般 GitHub Action 不同的设计。分析时应始终将注册检查放在首位，并提醒开发者考虑是否需要在 WebUI 中显示注册状态（降低用户排查门槛）。
- **高优先级与用户自助的矛盾**：标记 `high` 意味着开发者应介入，但实际可能只需用户执行简单命令即可解决。建议未来在优先级为 `high` 时，**同时附加“预期用户可自行修复”的标记**，避免开发者处理过度。
- **缺失的排查点**：GitHub App 安装权限、Webhook 的 Secret 配置（如果用户未设置 Secret 可能导致拒绝）。下次应补充到排查列表。
- **分析输出格式优化**：当前摘要列出了 6 点，但未用序号分步骤。建议改为 **“请按顺序检查：1... 2... 3...”** 的格式，方便用户逐一验证。
