### 二、发现的模式

#### 1. **版本号管理反模式**
```python
# 当前问题：分散硬编码
backend/__init__.py: __version__ = "1.0.0"
backend/models/database.py: "app_version": "1.0.0"
main.py: VERSION = "2.9.1"
auth.py: VERSION = "2.9.1"
init.sql: INSERT INTO settings ... '2.9.1'
```
**应集中为**：
```python
# backend/version.py
VERSION = "2.9.1"
```
所有模块从一处导入，SQL通过构建时注入。

#### 2. **增量审查的“历史债务冻结”效应**
- 本次只改格式 → 审查者识别出历史问题但接受“未被修复符合预期”
- **风险**：版本升级PR如果不一次性修复所有版本号，会形成“修复依赖链”，增加后续维护成本
- **建议**：项目规范应要求版本升级PR必须全仓库扫描并统一版本号，格式调整PR单独提交

#### 3. **配置文件与运行时逻辑分离不足**
- fallback值`"1.0.0"`的存在表明系统设计依赖“数据库配置优先，代码fallback兜底”
- 但fallback值是静态硬编码，应改为从环境变量或中心配置读取（如`os.getenv("APP_VERSION", "unknown")`），避免与发布版本强耦合

### 三、规范完善建议

#### 新增/强化规则

| 规则 | 触发条件 | 建议严重度 |
|------|----------|-----------|
| **版本升级必须全语言覆盖检查** | PR标题/描述包含`version`、`升级`、`release`关键词时，强制正则扫描`version\s*=\s*["'][\d.]+["']`（含Python、SQL、JS、Dockerfile、YAML） | major |
| **CHANGELOG强制草案** | minor/major版本升级PR必须包含`CHANGELOG.md`变更（至少为草案），否则阻塞合并 | major |
| **Fallback值与发布版本脱钩** | 检测到硬编码版本号作为fallback（如`"1.0.0"`），建议改为`"unknown"`或从环境变量读取 | suggestion |
| **版本API端点验证** | 如存在`/api/version`或类似端点，必须验证其返回值与当前升级版本一致 | minor |
| **测试中的版本断言** | 涉及版本升级时，应建议在相关测试中添加断言（如验证settings表写入的版本号） | suggestion |

### 四、经验教训

#### 1. **格式化PR应单独提交**
- 本次格式调整与版本升级混在同一个PR中，导致审查者既要关注逻辑（版本号）又要关注格式（不影响逻辑）
- **最佳实践**：纯格式化变更应独立PR，版本升级PR只含功能性变更，降低审查认知负荷

#### 2. **“历史问题追踪表”的价值**
- 清晰区分了“本轮新发现”vs“历史遗留”，避免了开发者感到被重复指责
- **推广价值**：可作为模板纳入审查流程，提升沟通透明度

#### 3. **增量审查的风险提示缺失**
- 审查结论虽标记了“历史问题未修复”，但未明确指出**合并前必须补修**还是**可开新Issue后续处理**
- **改进**：增加明确行动建议：“建议阻塞合并”或“可合并但需建Issue追踪”

#### 4. **测试覆盖盲区**
- 本次审查未要求补充测试用例验证fallback路径，虽非强制但可提升健壮性
- **经验**：凡涉及配置默认值变更，应建议添加单元测试验证不同启动场景下的版本值
