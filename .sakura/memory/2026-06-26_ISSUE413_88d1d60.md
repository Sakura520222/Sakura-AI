# Issue #413 分析结果深度反思

## 1. 分类与优先级准确性

**分类**：`enhancement` 准确无误。

**优先级**：`medium` 基本合理，但存在微妙偏高的风险。关键在于 Issue 原文"在下一次 AI 请求中注入"这个表述本身存在需求边界模糊——是单次快照注入还是工具循环中的动态轮询？两种路径的工作量和价值差异显著。当需求边界不清晰时，优先级应倾向于保守（low-medium），待需求澄清后再上调。当前 `medium` 判断隐含了"假设按简单路径实现"的前提，但分析正文中并未显式声明这一前提。

## 2. 标签推荐质量

- **enhancement (0.95)**：合理。
- **help wanted (0.4)**：**置信度偏高，应降至 0.1-0.2 或不推荐**。该任务涉及核心审查上下文构建、项目硬规则合规（asyncio 包装、untrusted evidence 标记、双层限额）、时序架构决策，对不了解项目规则的贡献者门槛极高。`help wanted` 暗示"适合社区贡献"，与实际门槛不匹配。
- **遗漏标签**：缺少需求澄清类标签（如 `needs-discussion`）。Issue 的时序语义模糊是实现前的阻断点，应显式标记。

## 3. 可行性判断质量

**优点**：数据流方向洞察精准（现有 Check Run 是 write-only，新功能需 read 方向翻转）；时序问题识别为关键复杂点是本次分析最大亮点；三条项目硬规则的引用完整且准确。

**缺陷**：

1. **工作量估算存在乐观偏差**：分析已识别时序问题为"复杂度显著上升"的分支，但 100-200 行估算显然按最简路径给出。应给出区间（简单快照 100-200 行 vs 动态轮询 300-500 行），否则估算与分析自身指出的风险矛盾。
2. **文件修改数偏低**：若遵循现有分层模式，可能需要新增 `external_check_service.py`，加上对应测试文件，实际应是 4-8 个文件而非 2-4 个。
3. **缺少"可验证性"维度**：项目记忆明确要求可行性须含可验证性，但分析未说明如何验证功能正确性（如何模拟外部 Check Run 失败状态？如何确认 AI 利用了注入的上下文？）。
4. **权限前置依赖未深入**：读取其他 Check Run 需要 `checks:read` 权限，分析仅在降级策略中一笔带过"权限不足"，未检查现有 GitHub App 配置是否已包含此权限。若未包含，这是实现前的硬性前置依赖，应单独列出。

## 4. 重复检测准确性

**严重缺陷：重复检测证据链完全缺失。**

项目记忆明确要求四要素：`{被引标题} + {相似点} + {差异点} + {结论}`。当前分析仅输出"可能是 #70 的重复"，无任何证据支撑。这直接违反了项目记忆中的硬性规则。

无法判断 #70 是否真正重复——如果 #70 是关于改善自身 Check Run 展示，则不重复；如果是关于收集外部 Check 状态，则重复。没有证据链，这个判断的置信度应视为零。

## 5. 标题改写适当性

改写**必要且质量良好**。原标题"新功能"信息量为零，建议标题清晰传达了动作（收集失败状态）、对象（PR 外部 Check）、目标（注入审查上下文）。唯一可改进之处是标题稍长，可精简为 `[enhancement] 收集 PR 外部 Check 失败状态并注入审查上下文`，优先级信息可交给标签承载。

## 6. 经验教训

### 本次暴露的核心问题
- **重复检测证据链是硬规则，不可省略**——这是本次反思中最严重的遗漏，未来必须逐项输出四要素，无法获取被引 Issue 信息时应标注"信息不足，无法判断"而非给模糊结论。
- **工作量估算须与分析中识别的风险自洽**——识别了复杂分支却不反映在估算中，会导致下游排期失误。

### 值得沉淀的模式
- **"数据流方向翻转"识别模式**：现有功能是单向 write，新需求引入 read 方向时，往往意味着从零构建获取层+解析层+注入层，工作量不止于"加个字段"。此类增强的可行性分析应显式标注方向翻转。
- **需求模糊时优先级保守原则**：Issue 含"下一次""动态"等时序模糊词时，优先级应带条件标注（如"medium（需求澄清后确认）"），避免模糊需求占据高优先级位。
- **权限前置依赖检查清单化**：涉及读取 GitHub API 新端点时，可行性分析应包含一个固定检查项："App 现有权限是否覆盖？若否，是否需要 Owner 操作？"
