## 2. 发现的模式

### 代码模式
- **“消防不记”模式不一致**：同一逻辑在不同路径使用 `await` vs `create_task`，缺少统一的异步任务调度规范。
- **函数职责过载**：`_notify_lockout` 既负责通知又负责清理内存计数器，违反单一职责。
- **注释后漂移**：注释声称的行为与实际实现差异较大（如 fire‑and‑forget 变成阻塞）。
- **降级路径的细节陷阱**：内存回退字典的实现虽然有了大小/TTL 限制，但清理函数的设计仍存在“所有条目均未过期则无清理”的盲区。

### 架构观察
- **双存储（Redis + 内存 dict）** 作为降级策略是合理的，但清理职责分散：Redis 路径的清理在通知函数中，fallback 路径的清理在记录失败函数中。
- **通知与业务逻辑耦合**：锁定事件的通知被嵌入在 `_record_mfa_failure` 和 `_notify_lockout` 中，而非通过事件总线或发布‑订阅机制。
- **i18n 覆盖完整**：所有新增用户可见字符串均已使用翻译键，这是一个较好的规范执行范例。

### 未来审查关注要点
1. **异步模式的“语义对齐”**：每当看到 `create_task` 或 `await` 调用通知/日志函数时，必须检查同一模块内是否用法一致。
2. **函数命名与副作用**：函数名如 `_notify_xxx` 暗示仅通知，任何额外副作用需立即质疑。
3. **降级路径的极端情况**：审查内存结构时，不仅检查 TTL 和大小限制，还要模拟“所有条目均未过期”的场景。

5. **配置格式的运行时验证**：新增配置字段时，检查是否有 Pydantic validator 或启动时校验，否则应创建 issue 跟踪。
