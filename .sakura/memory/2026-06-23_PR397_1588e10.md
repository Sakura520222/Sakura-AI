# 审查反思：PR #397

## 1. 审查质量评估

### 覆盖度：存在明显盲区

本次审查最大的问题是**被"架构迁移"的叙事牵着走，忽略了对等验证的深度**。

PR 描述明确说这是"PR 审查协议在 Issue 分析链路的对等迁移"，审查确认了"架构风格一致"，但没有执行真正的双向对比：
- `TaggedIssueAnalysisParser` vs `TaggedReviewAnalysisParser` 的字段验证规则是否完全对等？
- 修复策略的触发条件和降级阈值是否一致？
- 错误码/异常类型的集合是否相同？

仅凭"风格一致"就给出正面评价，违反了项目记忆中**"统一模式≠统一行为"**的原则。

### 准确度：标记合理但发现不完整

唯一标记的 minor 问题（早期返回路径缺字段）是准确的，且定位精确。但这个问题暴露了一个更深的模式——**函数的多退出路径字段集不一致**——审查只抓到了其中两条路径，没有系统性地枚举所有退出路径。

### 完整性：对安全机制的验证停留在表面

审查正面评价了 untrusted evidence 边界标记，但没有追问一个经典问题：**如果 Issue 内容本身包含 `=== END UNTRUSTED ISSUE EVIDENCE ===` 字符串会怎样？** 这属于项目记忆中**"安全修复必须向前一步"**的范畴，但审查止步于"有这个机制"而非"这个机制是否可被绕过"。

### 遗漏项清单

| 遗漏点 | 严重程度 | 依据 |
|--------|---------|------|
| 未双向对比两个 Parser 的行为差异 | minor | "对等迁移"的核心验证义务 |
| 未验证边界标记字符串的注入逃逸 | minor | "安全修复必须向前一步" |
| 未追问 temperature=0 修复的失败上限 | suggestion | 修复策略完整性 |
| 测试同源偏差未显式提及 | suggestion | "测试与代码同源偏差"规范 |
| 嵌套集合解析对特殊字符的健壮性 | suggestion | LABEL 含 `>`/换行时的行为 |

## 2. 发现的模式

**代码模式：**
- **信封协议模式成熟化**：`<SAKURA_XXX>` 标签 + 结构化字段 + 代码围栏剥离，已成为项目的标准 LLM 输出契约模式
- **三级降级成为惯用策略**：解析→修复→降级，在 PR 审查和 Issue 分析中复用
- **防御性取值（.get()）作为下游适配手段**：上游协议变更时下游不崩溃，但代价是静默丢失字段

**架构观察：**
- 协议解析作为独立模块（`issue_protocol.py`）与业务逻辑（`issue_analyzer.py`）分离，分层清晰
- 但 `safe_issue_protocol_failure` 这样的降级函数放在哪里没有在审查中确认——是否应该在 protocol 模块中？

## 3. 规范完善建议

### 新增规则：对等迁移必须双向行为验证

> 当 PR 描述为"A→B 对等迁移"时，禁止仅凭"架构风格一致"给出正面评价。必须列出源模块 A 的所有可观测行为特征（字段集、验证规则、错误处理、降级条件），逐项确认 B 是否对等实现。差异点无论大小均须标注。

**归类**：重构类变更审查要点 → 语义迁移的子规则

### 新增规则：防御性取值掩盖字段缺失须标记

> 当下游使用 `.get()` 取值且上游有多条返回路径时，如果不同路径返回的字段集不一致，即使不崩溃也至少标 minor。理由：防御性取值将运行时错误转化为静默数据缺失，后者更难排查。

**归类**：代码质量与安全审查

### 强化规则：固定字符串边界的注入逃逸检测

> 使用固定字符串作为 untrusted data 边界标记时，必须验证 untrusted data 包含该边界字符串时的行为。若未处理，标 minor 并建议使用唯一随机标记或转义机制。

**归类**：安全修复必须"向前一步"的具体化

### 强化规则：同源测试的显式偏差声明

> 当测试文件与被测代码在同一 PR 中由同一作者新增时，审查摘要中必须包含一句显式声明："已注意测试与代码同源偏差风险，额外关注了 XXX 路径"。未包含此声明的审查视为遗漏检查点。

**归类**：测试与验证规范 → 强制化

## 4. 经验教训

**1. 高评分是遗漏的温床**

9/10 的评分容易产生"已经够好了"的心理锚定。实际上，本次审查在安全边界逃逸和对等验证两个维度上有明确遗漏，合理评分应在 7-8 之间。**高评分应该意味着穷尽了所有已知检查点，而非"没看到大问题"。**

**2. "架构风格一致"是危险短语**

这个表述把行为等价性降格为视觉相似性。未来审查中遇到此类表述，应自动触发追问：具体哪些行为一致？哪些有差异？

**3. 多退出路径函数需要画路径图**

`analyze_issue` 至少有 5 条退出路径（API 失败、空响应、解析成功、修复成功、降级）。审查时应该 mentally 或 actually 画出这个路径图，逐条检查返回值。这次只靠"阅读时注意到"来发现遗漏，不够系统。

**4. 信封协议类变更应形成标准审查清单**

项目中对 LLM 输出使用信封协议的模式已经出现两次，未来大概率会继续扩展。应沉淀为标准检查清单：
- [ ] 信封标签定义与解析一致
- [ ] 所有退出路径字段集枚举且一致
- [ ] 代码围栏剥离对嵌套围栏的处理
- [ ] 修复策略的失败上限
- [ ] untrusted data 边界的逃逸防护
- [ ] 与已有同类型 Parser 的行为对比
- [ ] 测试是否覆盖了作者"想不到"的路径（同源偏差检查）
