## 3. 规范完善建议  

### 3.1 新增/修改审查规则  

| 编号 | 规则 | 触发条件 | 期望行为 |
|------|------|----------|----------|
| **R‑001** | **锁文件同步检查** | PR 中任何 `pyproject.toml`、`requirements.txt`、`Pipfile`、`poetry.lock`、`uv.lock` 等声明文件被修改 | 必须在同一 PR 中同步更新对应的锁文件；若未同步，审查器自动标记为 **minor** 并给出 “请运行 `uv lock` 并提交”。 |
| **R‑002** | **依赖一致性校验** | PR 包含依赖声明文件的改动 | 自动运行 `uv sync --locked`（或 `poetry lock --check`）并在 CI 中报错，确保锁文件与声明文件一致。 |
| **R‑003** | **单点消费检查** | 依赖升级 PR | 自动搜索项目代码（`rg`/`grep -R`）确认所有消费点的 API 是否仍兼容，若出现未匹配的 import，提示审查员手动核实。 |
| **R‑004** | **发布产物锁文件检查** | CI 打包阶段 | 检查打包产物中是否包含锁文件且锁文件版本与 `pyproject.toml` 匹配；不匹配则 CI 失败。 |
| **R‑005** | **依赖升级影响评估** | 任何依赖版本提升（尤其跨大版本） | 必须附带官方 Release Notes 链接并列出 **Breaking Changes**，审查员需确认无行为改变。 |

### 3.2 项目特有规范要点  

1. **依赖声明统一入口**：建议在项目根目录添加 `scripts/update_deps.sh`，统一执行  
   ```bash
   uv lock && git add uv.lock pyproject.toml requirements.txt
   ```  
   并在 CI 中强制跑该脚本，防止手动遗漏。  

2. **热重载模块文档**：在 `backend/core/hot_reload.py` 顶部添加 `# watchfiles version: >=1.2.0` 注释，便于后续升级时快速定位。  

3. **发布 CI 检查**：在 `release-on-pr-merge.yml` 前置步骤加入 `uv lock --check`，确保发布包内锁文件为最新。

## 4. 经验教训  

| 教训 | 细节 | 对策 |
|------|------|------|
| **锁文件不随依赖升级同步是常见盲点** | 本次 PR 只改了声明文件，导致 `uv.lock` 失效。 | 将 **锁文件同步检查** 纳入审查必检项，CI 中强制执行 `uv lock --check`。 |
| **单点依赖使用降低升级风险** | `watchfiles` 只在一个模块使用，升级无需代码改动。 | 保持这种“集中化”依赖使用的设计，遇到大幅升级时可快速评估风险。 |
| **多声明文件需要统一的验证脚本** | 项目同时维护 `pyproject.toml`、`requirements.txt`、`uv.lock`，手动维护容易出错。 | 引入统一的依赖同步脚本并在 CI 中跑一次，形成 “声明 → 锁 → 打包” 的闭环。 |
| **审查报告的结构化有助于快速定位问题** | 本次审查在“主要评论”中才指出锁文件问题，若提前在“审查摘要”列出会更易被注意。 | 采用模板：**摘要 → 关键风险 → 修复建议**，确保所有阻断/重要风险在摘要阶段即可看到。 |
| **依赖升级的 Release Note 必须被审查员阅读** | Review 中已经引用了 Watchfiles 的 Release Notes，验证了兼容性。 | 将此步骤写入审查规则（R‑005），确保每次升级都附带官方变更说明。 |
