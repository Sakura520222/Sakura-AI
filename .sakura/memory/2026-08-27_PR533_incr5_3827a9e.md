## 1️⃣ 审查质量评估  

| 维度 | 现状 | 反思 |
|------|------|------|
| **覆盖度** | 本次快速审查聚焦于 **3 个文件**（`docker_runtime.py`、单元/集成测试），并对 **Git linked worktree** 的布局修复、正则任务名校验、测试断言等点给出结论。整体覆盖了提交的直接改动，但未触及 **sandboxer** 其它核心入口（如 `service.py`、`app.py`、配置层 `config.py`）以及 **后端调用链**（`backend/services/agent_team/*`）。因此 **潜在风险点**（如配置默认值、异常路径、跨进程通信）未被审查。 |

## 2️⃣ 发现的模式  

### 代码模式  
| 观察 | 示例 | 风险/建议 |
|------|------|----------|
| **路径硬编码 + 只读/可写子树** | `../..` 相对路径解析、`common` 只读目录 | 容器内部路径依赖于宿主目录结构，升级或迁移时易失效。建议抽象为 `GitMountPlan` 中的常量或配置项，并在单元测试中验证多种相对布局。 |
| **正则白名单** | `^[A-Za-z0-9_.-]+$` | 正则写得相对宽松，仍允许 `.` 开头的隐藏文件。若业务不需要，可进一步限制首字符或使用 `re.fullmatch` 并配合黑名单过滤。 |
| **负向测试直接构造内部对象** | `42,evil` 直接注入 `_GitMountPlan` | 这种“内部实现测试”暴露实现细节，未来若实现改动可能导致测试失效。建议使用公有 API（如 `create_mount_plan`）进行黑盒测试。 |
| **Docker bind‑mount 叠加** | “只读 bind 下叠加子 bind” | 依赖 Docker 的特定行为（只读 bind 支持叠加），在不同 Docker 版本或非 Docker 环境（如 Podman）可能失效。应在 CI 中加入 **不同 Docker 版本** 的兼容性测试或在代码中加入回退路径。 |

### 架构观察  
| 现象 | 影响 |
|------|------|
| **sandboxer 与 backend 强耦合**：`sandbox_client`、`execution`、`git_workspace_service` 等多处直接调用 `docker_runtime` | 代码复用度高，但 **变更传播链** 长。一次底层挂载修复会波及多条业务路径，需要 **全库引用搜索** 与 **集成测试**。 |
| **三层镜像事务（Web / sandboxd / runner）** 统一更新 | 增加了 **发布复杂度**，但也提升了 **回滚一致性**。需要在 **升级/回滚脚本** 中加入 **事务日志**，防止部分镜像成功、部分失败导致不一致状态。 |
| **安全模型分层**：Web → sandboxd → runner，且仅 sandboxd 直接触达 Docker socket | 设计合理，但 **跨层错误码传播** 与 **日志脱敏** 需要统一规范，防止在 UI 层泄露底层实现细节。 |
| **文档双语同步**（中文/英文 README、部署手册） | 增加维护成本，若文档与代码不一致会导致运维错误。建议使用 **文档生成工具**（如 MkDocs + i18n）自动同步关键章节。 |

## 3️⃣ 规范完善建议  

### 3.1 新增/修改审查规则  

| 规则 | 目的 | 适用范围 |
|------|------|----------|
| **全绿 Gate 必须提供链接**（`error/major`） | 防止缺失关键 CI 结果导致隐藏回归 | 所有 PR，尤其涉及底层安全或架构改动 |
| **增量审查触发全库引用搜索**（配置键、API、异常类） | 防止遗漏因局部改动导致的全局 KeyError / ImportError | 任何删除/重命名/签名变更 |
| **Docker 参数统一生成函数**（禁止硬编码 `--mount`、`--network` 等） | 保证跨平台、跨版本一致性 | `sandboxer/src/**/*.py` 中所有 Docker 调用 |
| **异常捕获细化检查**（禁止裸 `except Exception`） | 提升错误可追溯性，防止隐蔽错误被吞掉 | 全项目 `except` 语句 |
| **跨层错误码同步**（后端错误码 → 前端翻译文件） | 防止 UI 展示不匹配的错误信息 | `backend/**/error_codes.py` 与 `frontend/**/i18n/*.json` |
| **测试覆盖“双向断言”**（存在性 + 不存在性） | 防止正向/负向路径遗漏 | 所有新增或修改的业务逻辑测试 |
| **文档-代码同步检查**（关键行为必须在代码中实现） | 防止文档承诺未实现的功能 | `README*`, `docs/*` 与对应实现文件 |
| **安全脱敏标签**（每个 `except` 必须标注 `# USER_INPUT_ERROR` 或 `# INTERNAL_ERROR`） | 明确错误面向对象，便于统一响应 | 所有业务层异常处理 |

### 3.2 项目特有的规范要点  

1. **Git linked worktree 布局**：所有涉及 `GIT_DIR`、`GIT_COMMON_DIR` 的路径必须通过 `GitPathResolver` 接口统一生成，避免硬编码相对路径。  
2. **sandboxd 控制平面**：对外暴露的 HTTP‑UDS 接口必须使用 **OpenAPI** 文档，并在 CI 中使用 `schemathesis` 做契约测试。  
3. **镜像事务升级**：在 `updater` 中加入 **事务日志表**（`upgrade_history`），每次三镜像更新必须写入同一事务 ID，回滚时依据该 ID 恢复。  
4. **多语言文档**：使用统一的 **i18n 资源文件**（`messages.{en,zh}.json`），代码中通过 `gettext` 调用，避免硬编码中文/英文字符串。

## 4️⃣ 经验教训  

| 教训 | 具体表现 | 防范措施 |
|------|----------|----------|
| **规则不一致导致误判** | “全绿 Gate 必须提供链接” 被标记为 `minor` 而非 `error`。 | 在审查工具中硬编码关键规则的 **强制级别**，审查模板自动填充对应标签。 |
| **增量审查易漏全局风险** | 仅审查了 `docker_runtime.py` 与测试，未检查 `sandboxer/service.py`、`backend/services/agent_team/*` 中的调用链。 | 增量审查后强制执行 **全库引用搜索**（`git grep`）并生成影响报告。 |
| **测试覆盖不完整** | 负向测试直接构造内部对象，未覆盖真实入口；集成隔离测试在 Windows 上被跳过。 | 为每个关键路径提供 **正向 + 负向** 两套黑盒测试；在 CI 中加入 **平台矩阵**（Linux/Windows/macOS）并标记跳过原因。 |
| **文档与实现脱节** | README 中提到 “sandboxd 可在非 root 环境运行”，但代码仍有 `os.getuid() == 0` 的检查。 | 引入 **文档-代码同步检查**（自动比对关键段落与实现注释）。 |
| **依赖版本隐式假设** | Docker bind‑mount 叠加只在 Docker 20.10+ 可用，未在 CI 中锁定版本。 | 在 `Dockerfile` 与 CI 中显式声明 **Docker Engine 版本**，并在代码里加入版本检测提示。 |

**改进建议**：  
1. **增量审查后执行全库影响扫描**（`git diff --name-only` → `git grep`），确保没有遗漏的调用链。  
2. **自动化 CI 链接校验**：审查脚本在检测到 `comment` 决策时，自动检查 PR 是否已经附带全绿 run 链接，若缺失则标记为 `error`.  
3. **风险分层评估**：对每个增量文件标记 **风险等级**（`low/medium/high`），并在审查报告中汇总，防止因文件数量少而误判风险低。

### 小结  

本次审查在 **细节实现** 上做得较好，尤其是对 Git layout 与正则校验的验证。但在 **全局风险评估**、**规则一致性** 与 **增量审查的覆盖范围** 上仍有提升空间。通过引入更严格的规则（全绿 Gate 必须提供链接、增量触发全库搜索等），以及在审查流程中加入自动化风险矩阵与平台兼容性测试，可显著提升审查的可靠性与效率。
