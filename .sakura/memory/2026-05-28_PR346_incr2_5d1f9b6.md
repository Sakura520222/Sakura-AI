## 2. 发现的模式
### 代码模式
1. **日志级别策略模糊**：日志阈值调整缺乏统一标准（从三级阈值变为两级），反映日志策略需要更明确的规范
2. **配置管理不一致**：部分配置可通过WebUI管理（如`max_structure_files`），部分只能编辑YAML（如`max_files_for_deep_strategy`），暴露配置管理策略不统一
3. **异常处理模式**：存在“静默捕获+返回默认值”的模式，但缺少必要的日志记录，可能隐藏配置问题
4. **重构清理不完整**：移除批量处理后，相关配置键的清理可能不彻底（如WebUI中缺失的配置项）

### 架构观察
1. **配置层次结构**：项目存在多级配置（YAML文件、动态配置、WebUI管理），但**配置键的可见性管理**不一致
2. **错误处理策略**：压缩工具的错误处理经历了简化，但可能牺牲了**错误分类的精确性**
3. **日志噪音控制**：在工具密集场景（50+轮迭代）下，info级日志确实会产生噪音，需要更精细的**日志分级策略**

1. **日志噪音控制规范**：对于高频执行路径（如工具循环），建议：

2. **配置管理一致性规则**：所有可通过YAML配置的键必须：
   - 在WebUI中提供管理界面
   - 有对应的配置验证逻辑

3. **压缩/重试处理规范**：
   - 重试逻辑必须保留错误分类能力

