# 深度反思报告

## 1. 审查质量评估

### 覆盖度：遗漏了"为什么移动"的追问
函数从第484行移至第862行，审查只关注了移动后的转义逻辑增强，却**完全没有追问移动原因**。这种重构式位置变更通常是信号——可能是为了解决循环导入、避免前向引用、或掩盖依赖关系问题。增量审查的隧道视野在此暴露：看到了"改了什么"，没问"为什么要改"。

### 准确度：major 标记违反三问法
`database.py:928` 的 `ALTER TABLE` 标识符拼接被标为 major，但审查自身已承认"来自 SQLAlchemy 模型定义（非用户输入）"。按项目记忆中的三问法：
- ①实际 bug？否
- ②运行时错误？极不可能（模型定义可控）
- ③安全风险？否（非用户输入）

**这直接违反了"优化建议≠major"和"三问法"规则**。新增加转义逻辑后要求一致性是合理的 suggestion，但拔高为 major 是错误的。

### 完整性：lambda→partial 的"确认修复"值得质疑
原代码 `lambda: repo.get_git_tree("HEAD", recursive=True)` 中 `repo` 是函数参数传入，**不存在循环中闭包捕获变量的问题**。改用 `partial` 是风格偏好，不是 bug 修复。审查将其标记为"已修复"存在误导——这暗示原代码有缺陷，但实际上没有。

## 2. 发现的模式

**代码模式**：
- **点状安全加固**：发现一个转义场景补一个，缺乏统一的 SQL 构建安全层
- **创可贴式重构**：函数位置移动 + 转义补丁，而非审视整个迁移逻辑的设计

**架构观察**：
- `database.py` 已超 900 行，`sakura_memory_service.py` 800+ 行，两个热点文件持续膨胀
- 函数移到文件末尾可能是为了"眼不见为净"，而非真正的结构改善

## 3. 规范完善建议

### 新增规则
| 规则 | 说明 |
|------|------|
| **位置移动必须追问原因** | 纯重构类位置变更，审查必须输出移动动机判断（依赖解耦？可读性？掩盖问题？） |
| **lambda→partial 区分判定** | 循环内捕获变量 = bug（major），参数级替换 = 风格偏好（suggestion），禁止混入"确认修复" |
| **三问法强制自检** | major 标记前必须在评论中显式输出三问结果，否则视为误判 |

### 修改规则
- **"一致性"论点的严重程度上限**：以"与新代码风格不一致"为由的问题，严重程度上限为 suggestion，禁止因一致性要求拔高严重程度

## 4. 经验教训

1. **"作者改了"≠"修复正确"**：增量审查中最容易犯的错误是把"有改动"等同于"问题解决"，必须验证改动方向的正确性
2. **标识符拼接 vs 值拼接**：SQL 安全审查中，标识符（表名/列名）来自代码内部定义时，风险等级与用户输入的值拼接完全不同，不能混淆
3. **函数位置是架构信号**：大文件内的函数移动往往反映依赖关系问题，不能当作无意义重构跳过
