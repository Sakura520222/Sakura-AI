## 二、发现的模式

### 代码模式

1. **注册表 + dataclass 扩展模式**  
   `ai_providers.py` 设计优秀，但存在**静态注册表与动态 config 双写**的风险（provider 列表可能漂移）。

2. **Service 层与路由层职责边界模糊**  
   `setup.py` 的 `get_ai_models` 直接解析 JSON，未下沉到 Service，违反“路由层禁止直接操作数据库/未验证输入”规范。

3. **异常处理模式**  
   多处使用 `except Exception as e` 并直接返回 `str(e)`，缺少 `logger.error` 和脱敏，违反“异常记录+脱敏”双重要求。

### 架构观察

- **配置穿透深度大**：`ai_provider` 同步到 Settings、CORE_CONFIG_KEYS、DYNAMIC_CONFIG_GROUPS、前端 options，维护成本高，容易遗漏。建议引入配置元数据类自动生成。
- **前端与后端状态同步依赖手动拼接**：如 `:selected="m === '{{ item.value }}'"` 这种模式在多个模板出现，应统一为 Alpine store + API 请求。

## 四、经验教训

### 未来审查关注要点

1. **异步 session 异常后的状态**  
   每次 `except Exception` 后，检查是否调用了 `session.rollback()` 或退出 `async with` 块自动回滚。

2. **返回值语义变更时的调用方全量扫描**  
   本次 `test_ai_api` 返回值扩展，未列出调用方（至少 3 处：setup 路由、config API、webui routes），应作为 major 要求。

3. **静态数据（如 provider 列表）与动态配置的一致性**  
   当 provider 注册表更新时，必须检查 `DYNAMIC_CONFIG_SELECT_OPTIONS` 是否同步。

### 技术/模式审查经验

- **注册表模式反模式**：当注册表数据需要与 UI、DB、配置文件三方同步时，应改为**单一真实源（DB 或配置文件）** + 缓存，避免手动维护多处枚举。
- **前端模板注入风险**：Jinja2 + Alpine.js 混用时，所有 `'{{ var }}'` 嵌入 JS 字符串的位置都应视为高危，建议统一使用 `x-data` 存储 + `x-bind`。
- **限流器遗漏的高发区域**：**测试连接类接口**（如 `/test-connection`、`/fetch-models`）最容易遗漏限流，应在审查模板中强制检查。
