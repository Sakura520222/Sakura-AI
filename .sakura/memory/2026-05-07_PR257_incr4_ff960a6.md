### 4. 经验教训

**值得未来关注的要点**：
1. **清理函数的入参防御**：抽取公共函数时，不仅要看调用处的参数非空，还要考虑调用路径中参数可能为空的场景（如任务未创建即取消）
2. **日志 ID 的格式假设**：外部系统可能隐式依赖 ID 格式（长度、字符集、前缀），变更时需全局搜索 `task_id` 的 consumer
3. **变量名与返回值语义漂移**：函数重构后返回值语义改变，但调用方变量名未同步，是技术债务的信号——应触发重命名建议
4. **UUID 截断的隐性风险**：单进程 asyncio 安全，但扩展到多 worker 时碰撞概率剧增。注释是廉价的未来防护

**对特定技术/模式的审查经验**：
- **asyncio 取消模式**：`Event` 仅信号，不支持附带取消原因。如需传递原因，应改用 `Queue` 或 `Future`
- **返回值 0 的二义性**：本项目已识别为高危区，本次未涉及但值得持续警惕
- **DB session 异常后状态**：`_update_review_status` 内部应独立管理 session，本次假设成立但未实测
