- 注释倾向“做什么”而非“为什么”：需推动注释文化向“意图解释”转变。

**架构观察**：
- 项目采用分层路由（webui_router、setup_router、catch-all），优先级清晰。

## 规范完善建议

1. **新增审查规则**：
   - **中间件-路由协同验证**：当修改中间件 ALLOWED_PATHS 或路由优先级时，必须检查两者交互是否产生循环或覆盖漏洞。
   - **注释意图强制要求**：对涉及循环、重定向、权限放行的代码，注释必须解释“为什么”而非仅“做什么”。
   - **路径排除集中化**：建议项目将 Bootstrap 特殊路径维护为配置常量，避免硬编码散落在多个文件。

2. **项目特有规范**：
   - **Bootstrap 模式测试用例**：新增路由或中间件变更时，必须验证 Bootstrap 模式下的重定向路径（包括 /setup/* 边界情况）。
   - **FastAPI 斜杠重定向处理**：对空路径装饰器（`@router.get("")`）的使用需标准化，避免遗漏路径变体。

## 经验教训

1. **审查策略优化**：
   - 对“quick”策略，仍需对核心文件（如 main.py）执行跳跃式全量扫描，避免遗漏关联逻辑。
   - 历史审查上下文缺失时，应主动检查项目记忆库中的类似问题（如路由循环历史案例）。

2. **技术审查要点**：
   - **重定向循环**：始终检查中间件与路由的交互，特别是“放行-重定向-再放行”链路。
   - **路径匹配逻辑**：验证 `startswith` 等匹配方式是否覆盖所有边界（如 trailing slash、大小写）。
   - **配置硬编码**：对路径排除等易变逻辑，推动集中配置化以降低维护成本。

3. **未来关注点**：
   - 若项目扩展多引导模式（如多租户 Bootstrap），需评估当前路由排除逻辑的可扩展性。
   - 监控 Bootstrap 模式下的性能（重定向链路长度），避免过度中间件叠加。
