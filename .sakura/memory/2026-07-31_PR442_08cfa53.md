#### 2. 发现的模式

*   **代码/流程模式**：
    1.  **依赖管理工具与项目治理策略的冲突**：Dependabot 采用 `dependabot/<category>/<target-branch>/<dependency>` 的固定命名，与项目采用的 GitFlow 命名策略 (`^(feature|fix|...)\/.+`) 产生结构性冲突。这是一个**反复出现的模式**，只要 Dependabot 更新主要依赖且项目存在严格的分支策略，此问题就会重现。
    2.  **CI 作为策略执行者**：项目使用外部 Check Run（而非简单的 CI 步骤）来执行分支策略校验，这是一个健壮的设计模式，将“策略”与“实现”解耦，便于独立维护。

*   **架构观察**：
    *   项目对 **CI/CD 流程的规范性和安全性要求很高**（GitFlow 分支策略、外部策略校验）。任何自动化工具（如 Dependabot）的集成都必须首先通过策略校验。审查必须优先考虑工具行为与项目“法律”（治理策略）的兼容性。

#### 3. 规范完善建议

*   **新增审查规则**：
    1.  **依赖升级PR的“策略兼容性”专项检查**：对于 Dependabot、Renovate 等工具自动提交的 PR，审查清单应强制包含：
        *   分支命名是否符合项目 GitFlow/分支策略？
        *   变更范围是否在 PR 描述中准确声明？（避免“标题说升级A，diff里还夹带B”）
        *   新版本是否有影响当前代码行为的 Breaking Change？需结合 Release Notes 做简要判断。
    2.  **CI 健康状态优先原则**：在输出审查摘要时，必须将**阻塞性 CI 问题**（如规则失败、构建错误）置于任何 warning 之前，并使用明确标题（如“🚨 阻塞项”）突出，避免信息层级混淆。

*   **项目特有规范要点**：
    *   明确 **Dependabot 与 GitFlow 的共存协议**：要么在策略文件中为 `dependabot/*` 添加例外，要么配置 Dependabot 生成符合策略的分支前缀。此决策应记录在项目文档或 `.github/dependabot.yml` 中，作为团队共识。

#### 4. 经验教训

*   **经验教训**：
    1.  **自动化工具是“双刃剑”**：Dependabot 能高效更新依赖，但其**默认行为（如分支命名）可能与项目的“手工定制”规则冲突**。引入任何自动化工具前，必须评估其输出是否符合项目既定的治理框架。审查此类 PR，首要任务是**验证工具输出的合规性**，而非代码本身。
    2.  **“破坏性变更”的广义理解**：不仅指 API 不兼容。**破坏“项目内部约定”**（如分支命名规范）同样是需要立即修复的阻塞问题。审查者的视野需从“代码正确性”扩展到“流程合规性”。
    3.  **审查输出的结构化呈现**：为避免重要信息被淹没，可借鉴 **“红-黄-绿”灯系统**：红色（Must Fix）、黄色（Should Fix/Consider）、绿色（Good）。本次审查的 Major 问题是红灯，Warning 是黄灯，在摘要中应优先、醒目地展示红灯。
