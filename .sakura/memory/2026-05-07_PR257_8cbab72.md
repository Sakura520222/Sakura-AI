## 2. 发现的模式

### 代码模式
1. **“前置注册 + 兜底清理”模式**：webhook 注册取消信号，worker 多处检查 + finally 清理。已成为该项目取消路径的标准模式。
2. **延迟导入聚集**：同一函数多处延迟导入同一模块，未提取为公共导入。建议规范：必要时允许延迟导入，但同一文件内应复用导入结果。
3. **枚举全链路变更检查缺失**：多次出现新增枚举值只改 ORM/模型，数据库 schema、模板、筛选器、统计遗漏。

### 架构观察
- **Webhook + Worker 强耦合于 asyncio.Event**：通过内存中的 `_cancel_events` 字典通信，依赖单线程事件循环保证安全。未考虑多进程/分布式部署场景（如多个 worker 进程），这是设计取舍，但应在文档中标注。
- **SSE 事件与状态更新绑定**：`_update_review_status` 自动发布 SSE，设计良好，但前端未同步扫描。

## 4. 经验教训

### 值得未来关注的技术要点
- **asyncio.Event 无法传递取消原因**：该项目只用信号，不需要原因，适合；若未来需要取消原因（如“超时取消 vs PR 关闭取消”），需改用 `Future` 或 `Queue`。
- **8 字符 UUID 前缀**：碰撞概率极低，但若未来任务量 > 10^6 并发，可考虑加长到 12 字符。当前合理。
- **防御性 `.get()` 缺失**：`pr_info['repo_full_name']` 直接索引，虽然上游保证存在，但静态方法应添加 docstring 注明前置条件。

### 对类似项目的审查经验
- 新增**状态枚举**的 PR，应强制要求提交一个“全链路影响清单”作为 PR 描述的一部分，否则自动标记 `request_changes`。
- 涉及**取消/中断**的 PR，必须画出状态机转换图（pending→reviewing→cancelled 等），评审时逐条验证转换路径是否有遗漏。
