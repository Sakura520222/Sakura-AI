**二、发现的模式**  

| 类别 | 观察 | 含义 |
|------|------|------|
| **代码模式** | 1️⃣ **FastAPI 路由函数直接注入 `Response`**：`star_aid_route.auth_callback(..., response: Response)` 采用依赖注入方式返回 Cookie。<br>2️⃣ **单元测试直接调用路由函数**：测试中不走 HTTP 层，而是直接调用函数并手动提供 `Response` 实例。 | 这种模式在后端服务中常见，可提升单元测试速度，但对函数签名的改动极为敏感。每次新增参数都需要同步更新所有直接调用的测试。 |
| **架构观察** | 1️⃣ **依赖图呈星形**：`backend/webui/auth.py` 为核心，多个 `deps.py`、路由文件都依赖它。<br>2️⃣ **滑动会话实现集中**：所有会话续期逻辑统一在 `auth.py` 与 `deps.py`，避免了散落的硬编码。 | 集中式设计便于统一修改（如本次把会话时长从 24h 改为 7d），但也意味着任何签名变更会波及大量调用方（如本次测试），需要严格的接口兼容策略。 |

**三、规范完善建议**  

1. **接口兼容审查规则**  
   - **新增/变更函数签名必须检查所有直接调用点**（单元测试、内部工具、脚本）。  
   - 若函数使用 FastAPI `Response`/`Request` 注入，建议提供 **包装层**（如 `def auth_callback(..., response: Response = Depends(get_response))`），让调用方可以省略该参数，从而降低兼容成本。  

2. **测试文件审查指引**  
   - 对于 **直接调用路由函数** 的单元测试，加入 **“参数完整性检查”** 检查项：确保所有必填依赖参数已显式提供。  
   - 建议在 CI 中加入 **pytest‑typecheck**（如 `mypy`）或 **ruff‑type** 检查，以捕获函数签名不匹配的错误。  

3. **变更影响范围评估**  
   - 即便是 **增量审查**，仍需在审查报告中列出 **“潜在受影响的调用方列表”**（通过静态分析搜索函数名），防止遗漏。  

4. **文档同步**  
   - 当路由函数签名改变（如新增 `response`），应同步更新 **API 文档或 README 中的示例代码**，避免外部使用者误用。  

5. **项目特有规范**  
   - **统一使用 `Response` 注入**：所有需要写 Cookie 的路由统一通过 `Response` 参数，而不是在内部 `Response` 实例上创建。  
   - **滑动会话实现必须在 `auth.py` 中提供 `renew_cookie` 公共函数**，并在 `deps.py` 中统一调用，防止出现“同一逻辑在不同文件重复实现”的情况。
