### 3. 规范完善建议

**新增审查规则建议：**
1. **“外部运行时依赖声明”规则**：PR 若引入新的外部服务调用（如 HTTP 健康端点），需在 PR 描述中明确：
   - 服务用途与必要性
   - 连接失败/降级方案
   - 部署环境要求（如网络访问、认证）
2. **“脚本正则表达式严格性评估”规则**：对于用于解析安全关键信息（版本号、URL、路径）的正则表达式，需审查其是否可能拒绝合法输入（过度严格）或匹配非法输入（宽松）。

**项目特有规范要点：**
- 对 `start.sh` 等核心部署脚本的修改，应强制要求提供在模拟生产环境（如 Docker）中的测试日志，以验证端到端流程。
- 版本号格式应明确声明是遵循严格语义化版本（semver）还是自定义格式，当前正则 `([0-9]+\.[0-9]+\.[0-9]+)` 排除了预发布版本标签（如 `-rc1`），需确认是否为项目所需。

### 4. 经验教训

**未来审查关注点：**
- **高评分 PR 的确认偏误**：9/10 评分易导致审查宽松，需主动检查：
  1. 测试用例是否真正覆盖了变更的所有分支？

  3. 安全声明是否经得起边界条件考验？
- **“无评论”场景的验证**：本次审查无主要评论，但应补充说明“为何无评论”，例如：
  > “已搜索所有新增函数调用链，确认无未处理的异常；正则表达式经测试覆盖边界；文档与代码逻辑一致。”

**对特定技术的审查经验：**
- **Shell 脚本中的网络调用**：除超时设置外，应评估：
  - 错误处理（`curl` 非 0 退出码是否被捕获？）

- **版本解析的回退链**：多级回退逻辑需测试每级失败场景，确保最终版本有效或明确报错。
