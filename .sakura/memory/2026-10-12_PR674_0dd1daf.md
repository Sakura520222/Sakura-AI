### 2. 发现的模式

- **代码与架构模式**：
  - **跨平台白名单/准入防御链**：Windows 实现坚持 **Fail-Closed**，通过 handle 获取规范化路径（`GetFinalPathNameByHandleW`）、显式拦截 reparse point/hardlink/ADS（备用数据流），防止沙箱穿透与符号链接提权。
  - **路径规范化不对称陷阱**：系统底层 API 返回的是物理全解析路径（Un-aliased / Long name），而上层业务（如 `RepositoryContext`、`grep_tool`）传入的往往是用户态输入路径。若对比前未做双向 Canonicalization/Resolution，极易导致“合法访问被误拒”或“安全校验脱靶”。
  - **环境分裂规避**：使用 `SHGetFolderPathW`（LocalAppData）替代不稳定或易受 Worker 环境变量污染的 `TMP`/`TEMP` 来管理跨进程锁，具有极高的工程成熟度。

---

### 3. 规范完善建议

结合本 PR 新增 Windows 平台抽象及已有反思，建议在**项目记忆**中补充以下规则：

1. **Windows 路径安全准入与规范化（Windows Path Canonicalization Guard）**：
   - 涉及 `GetFinalPathNameByHandleW` 或设备级规范化校验时，**基准根路径（Root/Workspace）必须统一显式 `resolve()`**；警惕 8.3 短路径（如 `RUNNER~1`）、Junction 挂载点与驱动器映射导致前缀对比静默失效。
2. **跨平台 OS 特有资源的生命周期闭环**：
   - 平台特定外置资源（如 Windows 下基于卷序列号+文件索引在 LocalAppData 生成的 `.lock` 进程锁、Named Pipes、IPC 事件）须考虑长期运行（Daemon/Service 模式）下的清理机制或无界增长防线。

### 4. 经验教训

- **CI Runner 的路径暗坑**：GitHub Actions Windows Runner 默认工作区路径常常包含 8.3 短名（形如 `C:\Users\RUNNER~1\AppData\Local\Temp`）或特定虚拟驱动器。任何未做 `resolve()` 的路径前缀字符串匹配，在 Linux 上正常而在 Windows CI 上必暴雷。未来对跨平台文件系统 PR，应将“短路径/软链中间件”作为强制审查用例。
- **CI 失败归因定位**：当 CI 标注在 checkout 或环境设置附近（如 `Process completed with exit code 1`），要结合改动范围谨慎区分是“PR 修改引入了语法/导入级故障导致 early-exit”还是“瞬时网络/Runner 故障”，要求附带复跑日志与本地复现方案是正确的防御姿态。
