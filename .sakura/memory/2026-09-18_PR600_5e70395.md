## 3. 规范完善建议  

### 3.1 审查规则层面  

| 建议 | 目的 | 实施方式 |
|------|------|----------|
| **强制非空审查** | 防止 “空审查” 误导团队，确保每次审查都有实质性输出。 | 在 CI 中加入检查：如果 AI/自动审查返回的评论字段为空，则自动标记为 **阻断** 并发送警报。 |
| **外部命令安全审查** | 所有 `subprocess.run / os.system / pip install` 必须有 **前置可安装性检查**、**错误捕获** 与 **日志记录**。 | 编写 lint 规则（如 `flake8-plugin`）检测 `pip install -e .` 前是否调用了 `_pyproject_is_installable` 或等价函数。 |
| **依赖文件一致性校验** | 防止 `pyproject.toml` 与 `requirements.txt` 不同步导致回退逻辑失效。 | CI 步骤加入 `uv lock --check` 或自定义脚本比较两者的包列表；若不一致则阻断合并。 |
| **异常处理统一化** | 禁止裸 `except:`，要求捕获特定异常并统一包装为业务异常。 | AST 检查：捕获 `except:` 并提示改为 `except (FileNotFoundError, TomlDecodeError) as e:`。 |
| **测试覆盖率阈值** | 新增功能必须配套单元/集成测试，且测试文件必须 **明确标记** 受影响的业务模块。 | 在 PR 检查中加入 `pytest --cov=backend/services/agent_team -m "not integration"`，要求覆盖率提升 ≥ 1%。 |
| **文档/注释强制** | 每个新增的公共函数必须提供 **完整的 docstring**（参数、返回值、异常说明）以及 **type hint**。 | 使用 `pydocstyle` 与 `mypy` 强制检查。 |

### 3.2 项目特有规范要点  

1. **Flat‑layout 项目约束**  
   - 项目根目录下的 `pyproject.toml` 若没有 `[build-system]`，必须在 `README` 或 `CONTRIBUTING.md` 明确说明 “此仓库不支持 `pip install -e .`”。审查时检查是否已在文档中声明。  

2. **UV 虚拟项目标记**  
   - 若使用 `uv` 的 `package = false`，应在代码中统一使用 `is_uv_virtual_project()` 判定函数，避免散落的硬编码判断。  

3. **日志关键字统一**  
   - 对于依赖安装相关的日志，统一使用关键字 `dependency-install`，便于在 CI/ELK 中检索。审查时检查日志字符串是否符合约定。  

4. **回退路径优先级**  
   - 明确在项目文档中列出回退顺序（`pyproject → requirements → skip`），并在审查时验证实现是否遵循该顺序。

## 4. 经验教训  

| 教训点 | 具体建议 |
|--------|----------|
| **空审查等同于未审查** | 在审查流水线中加入 “非空评论校验”，任何返回空字符串的审查自动标记为 **阻断**，并要求人工复审。 |
| **依赖检测的边界要写清** | 本次修复聚焦 `pyproject.toml` 的可安装性，然而仍可能出现 **其他不可安装因素**（如缺失 `setuptools`、Python 版本不匹配）。未来应把 “可安装性”抽象为 **统一的可执行检测函数**，并在单元测试中覆盖所有异常路径。 |
| **回退逻辑需显式声明** | 回退到 `requirements.txt` 的实现细节（如是否使用 `--no-deps`）要在代码注释和文档中明确，否则后续维护者容易误以为是 “直接 pip install”。 |
| **测试体量与可维护性** | 108 行的新增测试文件虽然提升了覆盖率，但应避免 **一次性写入大量冗余代码**。建议使用 **参数化测试** (`@pytest.mark.parametrize`) 将相似场景合并，提升可读性与后期维护效率。 |
| **CI 与本地环境保持一致** | 本次回退逻辑在 CI 中通过 `uv sync --locked` 验证通过，但本地开发者可能没有 `uv`，导致手动调试时出现 “Command not found”。建议在项目根目录提供 **dev‑env.sh**，统一依赖安装方式。 |
| **日志与监控** | 只记录 `warning` 可能在高并发环境下被淹没。对 “依赖未安装” 这类业务关键事件，建议使用 **error 级别** 并在监控平台设定告警阈值。 |
| **代码审查的层次** | 对于涉及外部命令的改动，**单元测试** 只能验证逻辑分支，**集成测试** 才能验证真实执行路径。未来审查时应分别检查两类测试是否完整。 |

### 小结  

- 本次审查的 **空输出** 已构成阻断，必须在审查流水线中加入强制非空检查。  
- 从代码本身来看，新增的防御式检测与回退逻辑是合理且必要的改进，但仍需在 **异常覆盖、日志统一、依赖同步** 等方面进一步强化。  
- 建议在审查规则中加入 **外部命令安全、依赖文件一致性、异常捕获统一** 等专项检查，同时对项目特有的 flat‑layout 与 uv 虚拟项目约束做出明确文档与代码约定。  

通过上述改进，可显著提升审查的 **覆盖度、准确度、完整性**，并在后续 PR 中避免类似的 “空审查” 情形。祝后续代码合并顺利！
