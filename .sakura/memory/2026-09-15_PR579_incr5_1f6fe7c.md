## 2. 发现的模式  

### 代码模式  
- **行号白名单**：项目通过 `backend/main.py` 中的 `ALLOWLIST`（或类似结构）对时间原语调用进行审计，行号随文件头部导入变化而需要手动同步。  
- **中间件统一写入 Cookie**：`WebUITokenRenewalMiddleware` 采用 `request.state` 进行“续期挂起”，在 `http.response.start` 阶段统一写入，避免在业务代码中直接操作 `Response`.  
- **常量集中**：会话最大存活时间 (`SESSION_MAX_AGE`) 统一放在 `deps.py`，所有路由/依赖统一引用，便于后续调参。  
- **防重复写保护**：`has_webui_cookie` guard 防止中间件覆盖已显式删除或设置的 Cookie（如 logout）。  

### 架构观察  
- **层级清晰的依赖图**：`backend/main.py` → `deps.py` → `auth.py` → 中间件 → 路由，职责分离明确。  
- **MFA 与会话续期强耦合**：续期仅在 MFA 检查通过后触发，体现安全优先的设计。  
- **API 与 WebUI 共享会话实现**：通过统一的 `SESSION_MAX_AGE` 与 `WebUITokenRenewalMiddleware`，不同入口（API、WebUI）都走同一套续期路径，降低重复实现风险。  
- **测试驱动的迭代**：每轮功能改动均伴随对应的单元/集成测试，形成闭环，但测试仍侧重正向路径，缺少故障注入/负向用例。

## 3. 规范完善建议  

| 现有规范 | 建议改进 |

| **行号白名单** | - 将行号白名单改为 **基于函数/模块的标记**（例如 `@allowlist_time_primitive` 装饰器），避免因文件头部增删导致的手动同步。<br>- 在 CI 中加入自动校验脚本，检测 `ALLOWLIST` 与实际调用位置是否一致。 |
| **中间件写入 Cookie** | - 明确定义 **中间件写入顺序**（文档化 `middleware_stack`），防止后续新增中间件意外覆盖 `webui_token`。<br>- 在代码审查 checklist 中加入 “检查是否使用 `has_webui_cookie` guard” 项。 |
| **安全审查** | - 对所有 **涉及身份凭证续期** 的路径强制要求 **“数据库权威校验”** 关键字检查。<br>- 新增规则：若修改 `SESSION_MAX_AGE` 或 `webui_secret_key`，必须同步 **安全审计日志**（记录变更时间、操作者）。 |

| **测试覆盖** | - 强制每次引入 **负向/异常路径**（如 token 被篡改、MFA 未完成、用户被禁用）对应的测试。<br>- 为中间件新增 **端到端请求/响应链路测试**，确保 `http.response.start` 阶段的 Cookie 写入在所有响应类型（Redirect、Streaming、Plain JSON）均生效。 |

## 4. 经验教训  

1. **行号白名单的脆弱性**  
   - 手动维护行号极易因代码格式化或导入变化失效。使用 **语义化标记**（装饰器或注释关键字）更可靠。  

2. **增量审查的盲点**  
   - 只看增量文件会忽视 **跨文件依赖**（如中间件行为、全局常量修改），导致潜在回归风险。  
   - 建议在增量审查后进行 **快速全局依赖抽查**（grep 关键常量/函数的所有引用）。  

3. **安全路径的时序**  
   - 续期放在 MFA 检查后是正确的安全设计，但需要审查 **所有入口**（包括内部 API、后台任务）是否同样遵循该时序。  

4. **测试与业务逻辑的同步**  
   - 代码改动（如行号偏移）虽小，但对应的 **白名单/审计规则** 也必须同步更新，防止误报/漏报。  

5. **文档同步**  
   - 本次 PR 没有涉及文档变更，但功能（7 天滑动会话）对外部使用者影响显著，建议在每次重大认证改动后 **同步更新 README/API 文档**，并在审查 checklist 中检查。

3. **风险评估**：判断是否引入新的依赖或改变已有安全时序。
