## 2. 发现的模式

### 代码模式
- **重复逻辑跨文件**：两个模块中出现了完全相同的方法实现，反映出缺少公共基类或工具模块抽取。
- **monkey-patching 临时属性**：`_compact_diff_tool` 通过动态属性注入，是临时解耦手法，但易泄漏且不显式。
- **静态方法中直接访问其他类的内部属性**：`_build_tool_handler_with_diff` 依赖 `ToolHandler` 的内部工具名（如 `file_tool`），未来易断裂。

### 架构观察
- **职责边界模糊**：`reviewer.py` 和 `batch_processor.py` 都实现了 context 压缩、token 估算和 compact 模式切换，暗示缺少一个统一的 `ContextCompressor` 或 `PromptOptimizer` 服务。
- **错误处理分散**：`PromptTooLongError` 的捕获逻辑在两处相似但细节不同，增加了行为不一致风险。
- **测试覆盖倾斜**：新增 `test_ai_reviewer_compact_diff.py`，但未同步测试 `batch_processor` 中的 compact 路径。

## 3. 规范完善建议

基于本次审查，建议在项目记忆中新增或强化以下规则：

- **重复逻辑跨文件检测（major）**：增量审查必须扫描两个及以上文件中 >10 行相同的逻辑，强制抽取公共函数或基类。
- **禁止使用 `locals().get()` 进行条件判断（major）**：应显式初始化变量并在作用域内直接使用。
- **临时属性注入必须配套显式清理方法（major）**：若通过 `setattr` 注入临时属性，则必须提供成对的清理方法（如 `set_temp_diff_tool` / `clear_temp_diff_tool`），禁止在 finally 中依赖属性名直接清理。
- **静态工厂方法不得直接依赖其他类的内部属性名（major）**：应通过目标类提供的公开构造方法或复制接口。
- **新增公共估算/压缩方法必须在所有使用处统一调用（major）**：token 估算函数只能有一处实现，所有模块必须调用同一个公共方法。
- **配置重构必须输出调用方统一性检查表（minor）**：当同一个配置逻辑在两个模块中出现时，必须输出对比表并说明是否统一。

## 4. 经验教训

### 值得未来关注的要点
- **单一真实源原则**：token 估算、context 压缩、compact 触发条件等应归属单一服务，避免 reviewer 和 batch_processor 各自实现。
- **异常重试中的变量状态捕获**：在 `except` 块中依赖上层 try 块内赋值的变量时，必须检查是否可能被后续重新赋值（如本例中的 `messages` 替换）。
- **compact 模式的下游影响**：精简后的 messages 可能丢失部分工具调用上下文，未来应测试多轮工具调用场景。
- **测试对称性缺失**：`batch_processor` 的 compact 路径未纳入单元测试，应在增量审查中强制要求。

### 对特定技术的审查经验
- **monkey-patching 临时属性**：常见于避免修改原有对象结构，但极易造成 finally 清理遗漏或属性名漂移。优先使用对象复制或上下文管理器（`with` block）挂载临时能力。
- **静态方法中的对象构造**：若静态方法需要复制另一个对象的大部分属性，强烈建议在原类中提供 `copy_with` 或 `with_xxx` 方法，而不是外部猜测属性名。

综上，本次审查质量较高，识别出了真实的 DRY 违反和脆弱逻辑，但在架构层面的统一抽象建议较少。建议未来对类似“两个模块实现相同能力”的重构，强制要求引入公共服务类。
