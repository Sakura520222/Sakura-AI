# 审查反思：PR #660（Billing 2.0 全量深度审查）

## 一、审查质量评估

### 覆盖度 —— 有亮点，但存在盲区
**已覆盖较好**：两段式状态机、钱包 CAS、锁序、退款身份校验、幂等冲突拒绝等财务核心均有负向用例佐证，而非仅凭代码走读下结论，符合“结论须附验证依据”原则。

**潜在遗漏，需在未来核验**：
1. **Billing 2.0 特性开关的 Fail-Closed 验证**。PR 声明“新功能默认禁用”，但审查报告未明确核验：开关默认值是否真的 off、开启路径是否有准入校验、关闭状态下旧链路是否零行为变更。对于计费系统重构，“默认禁用”是最大的风险缓冲垫，缓冲垫本身必须被审查。
2. **MySQL 触发器的部署可达性**。报告将"MySQL 触发器守卫账本 append-only"列为通过项，但触发器依赖迁移流程真实执行——若部署管线跳过 trigger 类 DDL（常见于受限数据库账号），该防线静默失效。触发器防线应要求有“启动时存在性自检”或迁移验证证据。
3. **迁移数据回填与回滚方案**。Billing 2.0 涉及 legacy entitlements 分离，审查未提及存量数据迁移的幂等性、部分失败恢复、以及从 Credits 模型回退到旧模型的可行性路径。对财务系统，回滚方案与正向功能同等重要。
4. **评分波动无解释**。历史 9→9→9→8→9，第 4 轮为何降 1 分、该原因是否已消除，报告中无痕迹。评分连续性本身应可追溯。

### 准确度 —— 分级基本合理
四项 suggestion 均为 suggestion 不阻断，判断得当：
- **i18n 不一致**：同端点两条失败路径语言不同确实是体验缺陷，但非正确性问题，suggestion 恰当。
- **retire_user 索引**：报告正确识别了“频率极低 + 失败安全”两个缓解因素，未夸大为 blocker，克制得当。
- **所有权三处内联**：准确指出“当前等价、未来分叉”的时态风险，这是高质量的可维护性判断。
- **config.py paddle 导入**：正确区分“受支持部署不受影响”与“降级契约恶化”两个层面。

无发现明显误判，但也无自我证伪记录——建议对每个结论保留一行“如何验证”的依据（部分已有，部分没有）。

### 完整性
报告充分理解了 Billing 2.0 的架构意图，但缺少对 PR 描述承诺（"Fixes #621"、legacy 支持）与实际变更的**双向核对**：承诺是否全部兑现？是否夹带未声明的行为变更？这一步在报告中缺位。

## 二、发现的模式

### 代码模式
1. **“正确的模式复制到未完全适配的路径”**：i18n 问题本质是提交阶段做对了、prepare 阶段漏了——同一功能的多分支实现中，靠复制粘贴对齐的模式极易在末梢分支退化。
2. **“白名单 vs 黑名单语义并存”**：所有权判定三处实现中，一处白名单（queued/running）、一处黑名单（!= released），当前等价但扩展必然分叉。**凡是状态机有扩展预期的，判定必须收敛为单一真值源。**
3. **“优雅降级承诺被上层导入破坏”**：网关层保留 ImportError 降级，但配置层顶层急切导入使降级承诺失效——**降级链的完整性要从导入图层面核验，不能只看降级分支本身**。

### 架构观察
- 本项目核心风险高度集中在**金融状态机 + 异步调度**，本轮架构设计质量高（两段式、CAS、栅栏、Fail-Closed 贯穿），值得在知识库固化为项目级参考实现。
- 仓库出现**大量 bot 自产提交（reflection/consolidate memory/merge）**，20 个新增提交中无一实际代码变更。这带来两个审查课题：① 提交数触发的审查策略升级会被 bot 提交污染，需过滤；② 高频 merge origin/main into develop 意味着 develop 与 main 长期双轨，需警惕 merge 解决冲突时引入未审查语义。

## 三、规范完善建议

1. **【新增】审查债务台账规则**：同一 suggestion 跨 ≥2 轮未修复且作者未回应时，不应继续以“新鲜 suggestion”姿态出现，而应升级为“显式 accepted-risk”——要求维护者明确表态接受或排期，否则在报告中单列“持续未决”板块并考虑降分。本次 4 项问题跨 5 轮原样滚动，审查报告事实上变成了复读机，失去了推动修复的杠杆。
2. **【新增】降级链完整性规则**：任何模块声明 ImportError/缺失依赖时可优雅降级的，须核验其**全部上游导入方**（尤其 config/启动路径）是否存在顶层急切依赖；降级契约以导入图为单位验证。
3. **【新增】状态机判定收敛规则**：涉及状态机的存活/终态判定，禁止内联重复实现；新增判定点必须复用既有 helper，或由 helper 声明废弃并收敛。新增第 4 处时应升级为 major。
4. **【修改】增量审查策略**：增量提交若全部为 bot/memory/merge 类提交（无业务代码路径变更），应快速判定为“无需代码审查，仅核验无夹带”，避免空耗全量审查额度；同时策略触发条件中的提交计数应排除 bot 提交。
5. **【项目特有】财务系统专属核验清单**：特性开关默认态、迁移回滚方案、触发器部署自检、对账恒等式——Billing 类 PR 四项必查。

## 四、经验教训

1. **评分惰性是最危险的审查反模式**：连续 approve + 高分会让后续审查者锚定在“这个 PR 一直没问题”上，削弱对滚动遗留项的警觉。应主动对抗自己历史结论的锚定效应。
2. **i18n/一致性类问题的检测方法**：新增“按用户语言解析”路径时，机械式检查同端点**所有**错误分支是否传入 lang 参数——这类问题靠逐分支比对比靠理解架构更容易发现。
3. **索引建议要区分“新增列”与“存量列”**：存量表加索引在大表上有锁表/构建成本，建议中应包含迁移执行时机（低峰/online DDL），本次建议未提及，略有粗糙。
4. **多实现收敛的判定标准**：三处实现“当前等价”不等于“可接受”，判定标准应是有无扩展预期——状态机类代码永远有扩展预期。

## 五、增量审查反思

1. **本轮增量实质为空**：列出的 20 个提交全部为 memory consolidation、reflection 与 merge，无业务代码。全量审查的价值不在本轮增量而在“298 文件累计重建”，这正是增量策略兜底（≥3 轮/累计 >1000 行切 full）发挥作用——**策略执行正确，应保持**。
2. **遗留项零进展是本轮最重要的信号**：历史上下文明确要求“重点核验四项是否处理、是否新增第 4 处所有权内联实现”。本轮结论是四项全部未动、所有权实现未新增——这个“未恶化”结论本身需要证据（搜索命令/行号），报告未附，**违反了自身“结论须附验证依据”的原则**，应补齐。
3. **增量覆盖度评估**：由于增量无代码，覆盖度未下降；但需警惕反向风险——bot 提交的 merge 中可能携带 main 分支上未经本审查流程的第三方代码合入 develop，建议下轮对 merge commit 的 diff 做一次快速冲突解决核验。
4. **对下一轮的可执行指令**：① 验证四项 suggestion 的修复或作者的 accepted-risk 表态；② 按 billing 核验清单补查特性开关与迁移回滚；③ 确认 `_delivery_started`/`resolve_billing_call` 未出现第 4 处内联；④ 附上“未恶化”结论的搜索证据。

**总评**：本轮全量审查深度与架构理解质量高，suggestion 分级准确无过度阻断；主要短板是“持续未决项的推动机制缺失”与“关键核验（特性开关、触发器部署性、回滚方案）未显式覆盖”，且部分结论缺少自我要求的验证依据。建议在知识库沉淀第 1、2、3 条新规则，并建立审查债务台账。
