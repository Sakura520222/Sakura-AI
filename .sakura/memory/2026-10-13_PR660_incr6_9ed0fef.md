## 三、规范完善建议

1. **新增规则：财务行为变更必须伴随回归测试（同 PR 强制）**。凡涉及资金效果、消耗顺序、状态机分支的提交，若 PR 内无对应测试断言，即使代码逻辑正确也应降级评分或阻断。本轮两个缺口正是此规则的典型适用场景。
2. **新增规则：排序键变更须附行为差异说明**。ORM 排序键的变更（尤其涉及 NULL 语义）必须在提交信息/PR 描述中明确“旧行为 vs 新行为”及存量数据影响，审查时据此验证文档一致性。
3. **强化规则：辅助方法抽取须声明调用点清单**。抽取共享方法时，PR 描述或审查记录中应列出原内联副本的全部位置及迁移状态，防止残留多源实现。
4. **项目特有要点**：`payment_event_service.py` 的 `replay` + savepoint 回滚 + `pending_reconciliation` 是本项目的核心对账模式，审查任何新 Fail-Closed 分支时须验证三件事——异常类型可被 replay 捕获、回滚后状态可恢复、`pending_reason` 可追溯。本轮第 1 条和第 3 条已确认，后续可固化为检查清单。

## 四、经验教训

1. **NULL 排序语义是跨数据库隐雷区**：`expires_at.asc()` 在 PostgreSQL 中 NULL 最后、MySQL 中 NULL 最前，这种隐式方言差异本身就是 bug 来源。审查排序逻辑时，**显式化 NULL 处理（如 `is_(None)` 键）应视为修复而非风格变更**，并要求测试固化。
2. **“暴露面一致”不等于“无需检查”**：迁移/重构后的代码即使行为等价，也应对边界输入（None、非法字符串）做一次快速推演，因为重构常伴随调用上下文变化。
3. **高分轮次的测试缺口要追踪到关闭**：本项目已连续出现“代码正确但测试缺失”的 approve，若不追踪，测试债务会随 PR 膨胀累积。建议在第 7 轮将本轮两个缺口列为**首要核验项**。

### 5.2 增量变更是否引入新风险？
- **行为变更风险（已识别但需强调）**：消耗顺序变更对存量用户是可感知变化——原本（MySQL 下）永久权益先被消耗，现在保留到最后。若业务上“永久权益保留到最后”是用户期望，这是修复；反之则是回归。审查确认了文档背书，但**未验证产品侧确认记录**，建议在下一轮确认这一变更的决策来源。
- **Fail-Closed 收窄的新风险**：混合快照部分退款被拒后进入 `pending_reconciliation`，若无自动化对账闭环或人工处理 SLA，**用户退款会卡在待核对状态**。审查关注了“不产生错误资金效果”（正确），但未追问“合法退款请求被拒后的用户出路”——Fail-Closed 的代价需要有运营侧承接，这是一个客服/运营层面的次生风险。

### 5.3 快速策略下的覆盖度损耗
本轮增量仅 34 行，quick 策略覆盖度损耗可控，审查实际上做了超出 quick 常规的验证（10 个测试文件搜索、跨方言推演）。**但按项目记忆的升级规则检查**：本 PR 累计规模显然已远超 1000 行、增量已第 6 轮，为何本轮仍用 quick 而非 full？第 5 轮是深度全量，第 6 轮 quick 有其合理性（紧随全量之后的小增量），但若第 7 轮仍是快速审查，应触发“增量 ≥3 轮切 full”的规则，重点回扫四个持续 suggestion 是否在新提交中被顺带修复（quick 策略容易漏掉“顺带修复”或“顺带劣化”）。
