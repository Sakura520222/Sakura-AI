### 四、 经验教训（供未来审查参考）

1. **配置加载失败的可观测性**  
   即使 `try/except` 存在，若只记录 error 而不阻断或降级，后续代码可能基于不完整配置运行。这是比移动代码位置更隐蔽的问题。

2. **审查中要追问“若 X 步骤失败会怎样”**  
   特别在启动阶段，每个依赖 DB/外部服务的步骤都应审查失败路径的最终状态。

3. **项目记忆的“规则”应成为审查硬清单**  
   建议在审查工具中强制勾选：  
   - [ ] 是否检查了配置读取的 None/非法值处理  
   - [ ] 是否检查了 fallback 路径的可观测性  
   - [ ] 是否检查了启动顺序中失败后的残留状态

4. **值得在未来关注的技术债**  
   - Settings 单例 + DB 动态配置的双源耦合缺少统一配置服务抽象。
   - 缺少启动阶段的“健康/就绪检查”端点来验证动态配置是否真正加载成功。
