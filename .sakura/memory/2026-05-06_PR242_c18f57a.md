基于提供的审查历史（#242 PR，i18n 实现），我对该次审查结果进行深度反思如下：

## 1. 审查质量评估

### 覆盖度
- **高价值点覆盖全面**：审查准确抓住了 i18n 核心问题——翻译覆盖不完整、重复代码（`_t`、`language_names`）、`document.write` 不可靠、toast 消息硬编码。
- **遗漏点**：
  - **未检查 JS 端的 i18n 集成**：`base.html` 中定义了 `window._t`，但未审查其他 JS 文件（如 `htmx` 回调、`alpine` 组件）是否使用该函数。
  - **未检查 API 返回的非 HTML 内容**：如 `/api` 端点返回的 JSON 错误消息是否已翻译。
  - **未检查数据库存储的用户语言偏好**：`WebUIConfig.language` 的读写路径是否完整。

### 准确度
- 严重程度**基本合理**：major 标记的“重复定义”、“硬编码 toast”、“语义错误翻译”确实影响用户体验和可维护性。
- **可优化**：
  - `_t()` 重复定义标记为 major→minor（重复4处，但功能简单，修复成本低，且不影响运行）。
  - `document.write` 问题标记为 major→minor（仅影响极低概率的 CSP 环境，且已有 fallback）。
  - `queue_stats_cards.html` 语义错误（`avg_duration` 错用 `description`）标记为 major → 合理，因为直接导致用户看到错误文本。

### 完整性
- **充分理解了变更意图**：PR 目标是 UI + AI 输出双语，审查指出 AI 服务端使用 `output_language` 正确，但 UI 模板和 toast 遗漏严重。
- **缺少对“AI 输出本身翻译”的验证**：AI 返回的评论内容（如建议、问题描述）是否真的按 `output_language` 输出？审查未确认 prompt 是否传递了该配置。

## 2. 发现的模式

### 代码模式
- **重复工具函数散落各服务**：`_t()` 在 4 个服务中重复 → 暗示缺少共享工具层。
- **语言名字典重复**：`language_names` 在 4 处定义 → 提示应提取为常量。
- **toast 消息直接字符串拼接**：`toast_redirect` 函数中直接写英文 → 未抽象 i18n 分发逻辑。
- **Jinja2 模板中混用 `_()` 和硬编码**：部分模板完全国际化，部分完全未动 → 增量迁移不彻底。

### 架构观察
- **i18n 实现较成熟**：`i18n.py` 有 `_flatten`、`make_translation_func`、延迟加载，设计合理。
- **但集成不完整**：
  - WebUI 路由中 `render_template` 覆盖不全面（部分路由直接 `TemplateResponse`）。
  - 前端 JS 翻译依赖 `document.write`，脆弱。
- **配置分散**：`output_language` 存在于 `Settings`，`language` 存在于 `WebUIConfig`，两者关系模糊。

## 3. 规范完善建议

基于本次审查，建议新增或强化以下规则：

| 规则 | 严重度 | 说明 |
|------|--------|------|
| **国际化覆盖完整性检查** | major | PR 声明 i18n 时，必须扫描所有模板、路由 toast、JS 字符串、API 错误消息，确保无硬编码用户可见文本 |
| **重复工具函数出现 ≥2 次必须提取** | minor | `_t()` 类辅助方法在 4 个服务重复，应提取到 `shared/utils` |
| **常量字典重复 ≥2 次必须集中定义** | minor | `language_names` 重复定义 4 次 |
| **`document.write` 禁止用于动态内容注入** | major | 改为 `x-text`、`innerText` 或 `textContent` |
| **toast 消息必须使用 i18n 函数** | major | 所有 `toast_redirect` 调用处必须根据用户语言动态选择字符串 |
| **新增 i18n 键必须验证语义正确性** | minor | `common.description` 错用于“平均耗时”属语义错误 |
| **Jinja2 全局 `_` fallback 必须注释风险** | suggestion | `deps.py` 中 fallback 为中文可能误导开发者 |

## 4. 经验教训

### 值得在未来审查中关注的要点
- **i18n PR 的“覆盖度嗅探”**：快速扫描所有 `.html`、`.js`、路由中 `toast_`、`alert(` 调用，检查是否有中文字符串。
- **重复代码的“三处法则”**：发现第三处相同逻辑时，必须要求提取共享函数。
- **前端动态文本注入的可靠性**：避免 `document.write`，优先使用框架声明式绑定（Alpine `x-text`）。
- **翻译键的语义验证**：不能仅检查是否使用了 `_()`，还要验证键名与显示内容是否匹配。

### 对特定技术/模式的审查经验
- **Alpine.js + i18n**：需要检查 `x-text="_t('key')"` 是否有效，而不是依赖 `document.write`。
- **HTMX 片段模板**：容易被遗漏，因为不经过完整页面布局。审查时应单独列出所有 `_fragment.html` 文件。
- **延迟加载 i18n 的线程安全**：审查中发现 `_ensure_loaded` 未加锁，虽影响小但应建议用 `threading.Lock` 或预加载。

### 最终总结
这是一次**高质量的审查**，覆盖了 i18n PR 的典型陷阱：重复代码、硬编码遗漏、前端注入风险。主要改进空间在于补充 JS 端扫描和 API 错误消息检查。建议项目添加 CI 脚本自动扫描硬编码中文字符串（排除注释和已用 `_()` 包裹的）。
