## 2. 发现的模式

**代码模式**

*   **功能闭环的易碎性**：新增一个数据字段，极易出现解析→存储→展示某一环脱节。本次 `suggestion` 字段在解析层提取，在去重层合并，却消失在格式化层，是典型的“提取后忘记消费”。这提示此类多模块联动功能需要强制性的端到端检查。
*   **解析器职责膨胀**：`result_parser.py` 继续承担了越来越多的业务逻辑（去重、合并、清洗、格式转换）。审查者虽未显式指出，但在项目记忆的“代码高危区”已标记为“上帝类”风险。本次新增的清洗逻辑进一步加剧了这一问题，未来重构成本会很高。
*   **Python 异常处理的宽泛陷阱**：使用裸 `except Exception` 是普遍存在的反模式，它不仅掩盖预期外的错误，还常常吞掉 `KeyboardInterrupt` 等系统异常（在较旧 Python 版本中）。本项目两次出现此模式，是编码习惯上的弱点。

**架构观察**

*   **配置层存在事实源分散的顽疾**：`constants.py` 和 `config.py` 分别维护同一默认值，说明项目尚未建立严格的配置单一来源机制。这种分散在以往审查反思中已被指出，但至今仍以“注释同步”作为短期缓解，技术债积压明显。
*   **AI 输出契约管理薄弱**：系统依赖 AI 按特定格式输出，但 Prompt 模板与解析器之间的“合约”全靠隐式约定，没有类型化或显式的 schema 校验。当新增格式要求时，极易因 Prompt 未更新而失效。这暴露了将非结构化文本作为 API 时缺乏契约验证手段的架构弱点。

## 3. 规范完善建议

基于本次审查，建议在项目审查规则或开发规范中新增/强化以下条目：

1.  **新数据字段生命周期强制检查清单**：凡引入配置项、数据库列、API 参数或内部中间字段，审查者必须显式追踪其“产生→解析→验证→传递→存储→使用/展示”全链路，任一环节缺失则标记 `major` 并阻断。此规则已在项目记忆中提及，可进一步固化为 checklist 形式。
2.  **Prompt 模板与解析器同步更新规则**：当解析器增加对新输出格式的支持时，对应的 Prompt 模板（如 `prompt_builder.py` 中的示例）必须同步更新。缺少同步演示将导致功能退化，标记为 `major`（“配置假开关”风险的延伸）。
3.  **配置默认值单一事实源原则**：禁止在 `constants.py` 或其它模块中重复定义已在 Pydantic `Settings` 中声明的默认值。如需引用，应从 `Settings` 实例中推导或在模块作用域用 `Field.default` 动态获取。技术债应创建 Issue 跟踪，多次出现后升级为阻塞项。
4.  **日志语义一致性规则**：当函数行为发生语义转变（如从“去重丢弃”变为“去重合并”），对应的日志消息、变量名、注释必须同步修正。这可以作为“语义转换重构检查”的细化，纳入审查必检项。
5.  **异常捕获范围规范**：明确禁止在非最外层处理中使用裸 `except Exception`。需捕获的异常应显式列出，降级处理必须伴随 `warning` 级日志。这可以纳入代码风格或 lint 规则。

## 4. 经验教训

*   **“功能闭环审查”需以用户视角纵向切开系统**：不要满足于逐个文件的 diff 检查，应选取一个新增能力（如“用户在 PR 评论中看到修复建议”），模拟数据流从头走到尾。本次 `suggestion` 缺位正是横向文件审查容易忽略，纵向功能审查才能曝露的典型问题。
*   **AI 输出解析与 Prompt 的孪生关系**：任何针对 AI 输出的解析逻辑，都必须追问“AI 凭什么会按这个格式输出？”。如果 Prompt 中没有明确的指令和示例，解析器就是无源之水。这一点应作为审查任何 LLM 集成功能时的首要检查点。
*   **“配置假开关”不止于代码**：即使配置加载、数据库、解析全部就绪，如果上游（AI 模型）未被告知输出新格式，功能依然静默失效。这种失效比代码错误更难发现，因为它不报错，只是永远不走新分支。今后对类似调整应建立“端到端最低生效条件”检查表。
*   **微量格式瑕疵可降级避免噪音**：对于 `**建议**` 残留这种低影响问题，可以依照项目记忆的“纯可读性封顶 suggestion”原则大胆降级，避免 `major` 过多导致审查疲劳，让真正致命的问题被稀释。
