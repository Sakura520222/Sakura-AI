### 二、发现的模式

**代码模式**
1. **测试中重复定义辅助类**：两个独立测试函数内定义了完全相同的 `FixedDatetime`，违反 DRY 原则。
2. **Mock 参数忽略但不验证**：`now(tz=None)` 接受但不检查 `tz` 值，未来如果生产代码误传其他时区，测试无法捕获。

**架构观察**
- 项目使用依赖注入式的 mock（替换 `datetime` 模块），而非 `freezegun` 或 `pytest-freezer` 等成熟库，可能出于控制精度需求。
- 测试文件未使用 fixture 共享 mock 对象，导致重复定义。

### 三、规范完善建议

基于本次审查，建议**新增或强调**以下规则（融入项目记忆）：

| 建议规则 | 严重程度 | 理由 |
|---------|---------|------|
| **测试中的 mock 辅助类应提取为模块级 fixture 或 conftest.py 共享**，避免两个以上测试重复定义 | minor | 本次出现两处重复 |
| **Mock 方法若接收但忽略参数，应添加断言验证关键参数值**（如 `assert tz == timezone.utc`） | minor | 防止生产代码误传时测试仍通过 |
| **任何涉及 `datetime` API 迁移（如 utcnow → now(tz)）的 PR，必须扫描全仓库所有测试文件中的类似 mock**，输出扫描清单 | major | 避免遗漏其他测试中的 `utcnow` 调用 |
| **禁止在测试中直接替换内置类型（如 datetime）模块级属性**，除非有厂库无法满足的理由，且必须在 PR 描述中说明 | minor | 避免测试隔离性和并发问题 |

**项目特有规范强化**
- 当前“新增 DB 模型的 datetime 字段必须使用 `datetime.now(timezone.utc)`” 规则应扩展为：“**测试中的 mock datetime 必须显式验证时区参数传入**”。
- “重复逻辑跨文件检测”规则应降低阈值：同一文件内两处以上 >5 行相同逻辑，也应抽取。

### 四、经验教训

**未来审查关注要点**
1. **测试中的“假阳性容忍”**：当 mock 忽略关键参数时，测试可能绿但生产逻辑错误。应养成“mock 收参必断言”习惯。
2. **API 废弃迁移的全仓库覆盖**：`utcnow()` 废弃警告已经持续多个 Python 版本，此类 PR 应要求提供 `grep -r "utcnow" --include="*.py"` 扫描结果。
3. **增量审查的“债务碎片化”**：本次 PR 仅改了 2 处，但项目可能还有遗留 `utcnow`（包括非测试代码）。审查时不应只关注 diff，还应输出“本次未修复的同类问题”清单。

**对特定技术的审查经验**
- **`datetime` mock 的最佳实践**：推荐使用 `pytest-freezegun` 或 `time_machine` 库，避免手动替换类。如果必须手写，应封装为 fixture 并提供参数验证。
- **测试中重复定义类**：是“复制粘贴测试”的反模式信号，往往意味着测试需要重构为参数化或共享 fixture。
