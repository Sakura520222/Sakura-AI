## 6. 经验教训 & 未来改进要点

| 教训 | 对策 |
|------|------|
| **需求范围过大**导致一次性评审难度高 | 在 Issue 初稿阶段就 **拆分子需求**（如 “邮箱同步” 与 “公告 CRUD”），分别建立子 Issue，后续聚合到主 Feature。 |
| **标签推荐置信度不够**（如 `help wanted` 置信度仅 0.4） | 引入 **标签自动匹配模型**，结合项目历史标签分布进行校准，提升置信度阈值。 |
| **重复检测误报**（仅凭关键词匹配） | 采用 **语义相似度模型**（如 Sentence‑BERT）对 Issue 内容进行向量对比，降低误报率。 |
| **风险点列举不够细化**（未提及邮件模板渲染、SMTP 连接池） | 在可行性报告中加入 **技术细节清单**（依赖库、配置项、资源消耗），并提供 **原型实现方案**（代码片段或伪代码）。 |
| **优先级判断未充分考虑运营需求** | 与产品/运营团队同步，获取 **业务影响评分**（如用户触达率、运营成本），在评审时加入评分体系。 |
| **标题改写缺失** | 在 Issue 生成模板中加入 **标题审查检查**（是否包含关键动词、业务对象），自动提示是否需要改写。 |
| **文档/代码同步缺失** | 为每个新功能建立 **文档生成脚本**（如 MkDocs 自动从代码注释抽取），确保功能实现后文档自动更新。 |
