## 深度反思

### 1. 审查质量评估

**覆盖度：存在一个隐性盲区**

审查正确识别了变更意图（解决 AI 锚定大范围但只输出改动行导致 Apply suggestion 误删的问题），全仓残留扫描也执行到位。但遗漏了一个**提示词规则间的语义张力**：

- 规则要求"**SMALLEST** contiguous range"
- 同时要求"**ENTIRE** START_LINE..END_LINE 范围完整替换"

这两个目标在人类理解下不矛盾（选最小范围 → 然后完整输出该范围），但对 LLM 来说存在解读风险：模型可能理解为"为了最小范围而缩小选择"导致遗漏上下文，或"为了安全而扩大范围"导致不精确。审查未追问这个张力是否需要通过示例（few-shot）来消解。

**准确度：合理**

9/10 对于纯提示词文本变更是恰当的。没有代码逻辑错误，没有语法问题，评分不虚高。

**完整性：对设计决策的追问不足**

"non-contiguous edits → SUGGESTION = NONE"是一个**行为降级决策**——原本 AI 可能尝试给出不完美的建议，现在直接放弃。审查没有追问：
- 为什么不支持输出多个 SUGGESTION 块？
- 预期 NONE 率会上升多少？是否有监控？

这不算代码缺陷，但属于"变更影响的隐性维度"。

### 2. 发现的模式

**代码模式**：
- 提示词硬编码在 Python 多行字符串中，无外部模板机制——意味着每次提示词变更都走代码 PR 流程，变更是可追溯的
- 测试采用"关键短语存在性检查"——对提示词来说是务实选择，因为无法做语义断言

**架构观察**：
- 提示词演进路径：从模糊指令 → 累加具体规则。这种"打补丁"式演进长期会导致提示词臃肿，但目前规模下可接受

### 3. 规范完善建议

建议新增以下审查规则：

> **提示词多规则叠加的语义冲突检测**：当单次变更在提示词中新增 3 条以上规则时，应检查规则间是否存在目标张力或边界条件冲突，特别是"最小化"与"完整性"类目标的组合。

> **NONE/SKIP 门槛收紧的"溢出风险"评估**：将原本可以输出结果的场景重新归类为 NONE/SKIP 时，应评估对 AI 输出分布的影响，建议作者说明预期行为变化或提供 A/B 对比证据。

> **提示词测试的局限性显式声明**：关键短语存在性测试只能防止回退，不能验证语义正确性。审查摘要中应明确标注"测试仅覆盖文本完整性，不覆盖提示词效果"。

### 4. 经验教训

1. **"最小范围"与"完整替换"是提示词工程中的经典陷阱**——两个独立正确的约束组合后可能产生歧义，未来遇到类似场景应主动建议用 few-shot example 消解，而非仅靠文字描述

2. **提示词变更的"NONE 溢出"是隐性风险**——每次收紧输出约束，都应问一句"这会不会让 AI 从'给出不完美的建议'变成'直接放弃'"

3. **全仓残留扫描做对了**——这符合重构类变更的"零遗漏"标准，虽然是提示词文本而非代码模式，但旧措辞残留同样会导致 AI 行为不一致，验证方法正确

4. **设计决策 ≠ 代码缺陷，但值得记录**——"non-contiguous → NONE"可能是经过权衡的决策，审查者不一定要 block，但应该在评论中留痕，方便后续追溯为什么不做多 SUGGESTION 支持
