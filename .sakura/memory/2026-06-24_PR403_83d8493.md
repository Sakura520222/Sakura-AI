## 深度反思

### 1. 审查质量评估

**覆盖度：存在隐性盲区**

审查聚焦于提示词文本自身的自洽性，这做对了。但遗漏了一个关键交叉验证维度：**提示词约束与下游解析代码的对齐**。

提示词新增了"SUGGESTION 必须是完整范围逐行原文"的硬约束，那消费 `SUGGESTION = ...` 输出的解析逻辑（大概率在某个 `parse_review_response` 类函数中）是否依赖"只有改动行"的隐式假设？如果解析器会对 suggestion 内容做 diff 提取实际改动行，完整范围输入反而会导致语义错误。这个交叉验证在全量重审中应该做。

另一个盲区：新增了 `SUGGESTION = NONE` 的指导路径，下游是否正确处理了这个特殊值？是否会生成一条"空建议"展示给用户？

**准确度：评分合理但"无评论"是失职**

9/10 和 approve 决策本身没问题——纯提示词优化，无逻辑变更，无安全风险。但**"无评论"不可接受**。全量重审且无历史记录，至少应该有一条确认性评论，比如标注"已验证下游 parse 逻辑不依赖 suggestion 仅含改动行的假设"或"建议后续补充 SUGGESTION=NONE 的端到端测试"。零评论意味着审查者没有留下任何可供后续审查者追溯的推理痕迹。

**完整性：理解了"为什么"，未验证"连不连"**

审查摘要准确捕捉了变更动机（防止 Apply suggestion 后保留行被删除），这是好的。但"无逻辑或行为回归"的结论缺乏支撑——只看了提示词和测试，没看解析侧，这个结论是推断而非验证。

### 2. 发现的模式

- **提示词即接口契约**：这个项目通过 prompt 文本定义 AI 输出的接口规范，本质上是与一个"黑盒外部系统"的契约。修改契约时，消费方的适配验证不可省略。
- **"存在性测试"模式**：新增测试只验证关键短语在 prompt 字符串中存在/不存在。这是一种轻量护栏，能防止回退，但不能证明行为正确。

### 3. 规范完善建议

**新增规则：提示词契约变更的下游对齐验证**

> 当提示词新增/修改输出格式约束时，必须追踪下游解析/消费代码，验证是否存在与旧格式耦合的隐式假设。仅修改提示词而不验证消费方，至少标 minor。

**强化现有规则：测试深度要求补充**

在"测试'覆盖了函数'≠'覆盖了行为'"下增加子项：

> 针对提示词关键短语的"存在性测试"（assert "xxx" in prompt），其价值仅限于防回退。审查时不应将其等同于"行为验证"，评分时不应因此提高测试覆盖度得分。

### 4. 经验教训

- **"纯文本变更"不等于"零风险变更"**：提示词、配置文件、注释中的格式约定，如果被下游代码隐式依赖，修改它们和修改接口签名一样危险。审查时应问："有什么代码依赖这段文本的具体措辞或隐含语义？"
- **全量重审的"全量"应指影响面，而非文件数**：即使只改了两个文件，全量重审也应评估这两个文件在系统中的所有触达路径。
- **approve 不等于沉默**：高质量的 approve 评论是项目知识的沉淀。零评论的 approve 在审计追溯时等同于"未审查"。

### 5. 手动全量重审反思

本次标注为"首次审查"（无历史记录），因此不存在增量遗漏的修复问题。但从"全量重审"的应有标准看，本次审查实际上执行的是**变更文件级别的细审**，而非**系统影响面的全量评估**。差距在于：没有从 `prompt_builder.py` 出发，追踪 `build_prompt()` 的返回值被谁消费、SUGGESTION 段的输出经过哪些解析步骤、`NONE` 特殊值在整条链路中的传播路径。

**改进动作**：后续全量重审时，即使变更文件很少，也应强制执行一次"变更点的下游调用链扫描"，并在审查摘要中显式记录扫描结果。
