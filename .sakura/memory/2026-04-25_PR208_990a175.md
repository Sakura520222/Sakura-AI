# 审查质量反思

## 1. 审查质量评估

**覆盖度：中等偏上，但存在功能层盲区**
- 审查成功捕获了模板截断、`str.format`注入、异步丢失、重复代码、配置分组等**结构与规范类问题**，与项目记忆中的已知模式高度对齐。
- 但对 **Issue 反思功能的执行流与语义正确性** 覆盖不足。例如：
  - `reflect_issue()` 中状态更新与合并检查的逻辑是否与 `reflect()` 完全一致？是否存在因参数差异导致的潜在状态污染？
  - `issue_worker.py` 新增的调用点是否正确传递了所有必要参数？`asyncio.create_task` 的回调是否真的只 `discard`，能否在异常时给出回退行为？
  - 新增的 Issue Prompt 是否有长度或令牌限制检查？全量重审未验证 LLM 调用的边界安全。
- 相比之下，审查更专注“形式一致性”而非“功能正确性”，这使部分深层逻辑风险可能被遗漏。

**准确度：严重程度判定基本合理**
- 两个 `minor` 级 warning 符合项目记忆的“已知模式归档”规则，未错误升级为 `major`/`critical`。
- `suggestion` 区的重复代码、配置分组建议都属纯改善性，无越界标记。
- 但将 Jinja2 截断 + Markdown 渲染风险标为 `minor` 值得讨论：如果渲染错乱可能导致 XSS 或信息泄露，则应升级。审查未就该风险的安全后果做进一步论证，直接归档为“跨层边界”问题，略显机械。

**完整性：上下文利用充分，但功能意图未深度还原**
- 审查充分引用了项目记忆中的累积教训，对“str.format”“fire-and-forget”等模式进行了正确的模式匹配，审查语言与项目规范高度一致。
- 对 PR 描述的理解停留在“新增 Issue 反思”层面，但未进一步验证“反思内容如何影响后续 Issue 处理”这一业务闭环，缺少对端到端影响的分析。
- 审查未指出新增配置项 `sakura_use_summary_model` 在其他模块是否有配套调用，仅确认“三件套完整”，未验证其启用后的实际效果与契约。

## 2. 发现的模式

**代码层模式**
- **对称复制模式**：`reflect_issue()` 完全镜像 `reflect()` 的六步流程，开发者倾向于通过复制既有稳定流程再微调参数，而非抽象公共层。
- **配置即注册模板**：新增配置字段严格遵循 `descriptions → keys → short_name` 三处注册，项目中已形成强约定，任何新增配置都会自动通过该模式审查。
- **fire-and-forget + discard 回调**：异步任务失败时选择静默丢弃，避免主流程阻塞，这已从 `review_worker` 扩散到 `issue_worker`，成为“非关键业务”的惯用手法。

**审查行为模式**
- 审查者高度依赖“项目记忆库”，快速识别已知模式并归档，效率高但可能形成**模式匹配即通过**的惯性，忽视模式在新上下文中的适配性（如 `reflect_issue` 的 Issue Body 是否适合用 `str.format` 的已知应对方案）。
- 审查输出的结构严格遵循内部规范（问题、影响、建议），说明审查流程已标准化。

## 3. 规范完善建议

基于本次审查盲区，建议补充以下检查项：

1. **新增 LLM 调用的全链路验证**  
   Prompt 构建→参数注入→模型调用→输出解析→状态更新，任一环节的异常处理缺失或语义错误都应标出。尤其是当通过复制已有调用时，需强制比对参数类型、默认值、错误回退链。

2. **“已有模式复制”需显式评估内容适配性**  
   此条已存在于项目记忆（“嵌套新上下文时须追问‘内容是否适合该模式’”），但本次 `str.format` 问题仅归档而未追问适配性，应强化执行：若被复制模式原本处理的是**非用户输入**，新调用点输入为用户可控内容时，必须检查注入风险。

3. **跨层截断问题的严重性升级条件**  
   当前仅标 `warning`，建议增加“若渲染内容可能包含可执行脚本或泄露敏感数据，升级至 `major`”的补充判定树，避免公式化归档。

## 4. 经验教训

- **全量重审的“功能正确性”负债**：当变更增大（+250 行）且涉及新功能时，审查若停留在结构扫描和已知模式匹配，会遗漏业务流程级缺陷。需在策略上自动切换至**功能流审查**，至少提出一个功能路径的推演。
- **项目记忆的双刃剑效应**：标准化的教训库大幅提升了模式识别效率，但也带来了“用标签代替思考”的风险。本次 `str.format` 问题直接归档而缺少攻击场景分析，便是典型。
- **建议疲劳度控制**：`suggestion` 区关于重复代码和配置顺序的建议可能在第 2 轮仍不会被采纳，考虑到新功能急于上线，可考虑标注为“后续重构”以避免建议贬值。
