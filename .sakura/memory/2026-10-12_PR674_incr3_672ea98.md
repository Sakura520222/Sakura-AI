### 2. 发现的模式

- **代码模式**：
  - **平台分支假定二元对立（Windows vs POSIX）**：开发者通常习惯将系统划分为 `os.name == 'nt'` 和 POSIX。然而文件系统语义并非严格二元：**Windows（通常不敏感）/ Linux（通常敏感）/ macOS（POSIX 但默认不敏感）**。使用 `os.path.normcase` 作为“跨平台大小写归一化”手段容易产生虚假的安全感。
  - **测试驱动的安全证明**：通过 `os.path.samefile` 先验证“文件确实存在且指向同一目标”再断言拒绝，这种防御假阳性的测试编写模式非常严谨，值得在涉及别名/符号链接的安全测试中推广。
- **架构观察**：
  - 敏感上下文准入（`RepositoryContext`）采用的是**路径黑名单机制**（`.env*`、`_SECRET_NAMES` 等）。在多平台混合文件系统下，黑名单匹配极易因编码规范化（Unicode NFC/NFD）、大小写别名、8.3 短文件名等文件系统特性遭到绕过。

---

### 3. 规范完善建议

建议在《项目记忆》的**跨平台抽象与文件系统安全**部分追加以下准则：

1. **`os.path.normcase` 跨平台安全陷阱防线**：
   - 明确规则：`os.path.normcase` **仅在 Windows (nt) 下小写化，在 macOS/Linux 等 POSIX 平台恒等**。在涉及敏感文件/路径安全准入时，严禁假设 `normcase` 能处理所有大小写不敏感文件系统；若项目支持 macOS 宿主，须显式评估 APFS 大小写不敏感别名风险（按需使用 `str.casefold()` 配合 Fail-Closed 或进行底层文件 inode/stat 探查）。
2. **安全准入从“路径文本黑名单”向“真实标识比对/白名单”过渡**：
   - 依赖文件名的过滤器应提供路径规范化收敛层，在读取前对齐路径系统调用。

### 4. 经验教训

- **标准库契约的“非对称性”**：
  - Python 标准库中不少跨平台 API 存在平台行为差异（例如 `normcase`、`samefile`、锁语义等）。当看到代码使用 `normcase` 进行安全过滤时，应形成条件反射：**“这个系统的 POSIX 实现是否可能运行在大小写不敏感的文件系统上（如 macOS）？”**。
- **阻断边界的理性把控**：
  - 当发现潜在安全隐患，但该隐患属于跨平台历史包袱且 PR 目标明确限定为特定平台修复（如本次 `fix(windows)`）时，将其作为重要 Finding (minor/warning) 记录并阐明权衡，而不是直接拉闸阻断，既保证了主线迭代效率，又保障了安全上下文的传递。
