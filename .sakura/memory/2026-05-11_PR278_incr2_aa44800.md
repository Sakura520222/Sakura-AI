## 4. 经验教训

### 未来审查关注要点
- **重构中的“隐性删除”**：当代码从多行（类型转换 + 范围校验）简化为单行调用时，要逐行比对旧逻辑，不要只关注“是否更简洁”
- **配置类 PR 的对称性审查**：每看到一个 `get_dynamic_config(xxx)`，必须反查是否存在对应用户写入路径（WebUI/API），否则产生幽灵配置
- **“未在本 PR 范围”的技术债**：即使标注为 `minor` 或 `后续候选`，也应在 PR 描述或 issue 中创建追踪项，避免无限期搁置

### 对特定技术/模式的审查经验
- **`int(form.get(...))` 陷阱**：当 `form.get` 返回空字符串时，`int("")` 抛出 `ValueError`；本次用 `try/except` 解决，但**范围校验独立于类型转换**，容易在重构时被忽略
- **动态配置系统的演进策略**：推荐引入 `ConfigService.get_int(key, min=1, max=20, default=5)` 统一封装，避免每个调用方重复写 try/except + 范围校验
