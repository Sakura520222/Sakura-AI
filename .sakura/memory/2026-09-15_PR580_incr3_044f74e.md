## 2. 发现的模式  

### 代码模式  
1. **最小化权限声明**：在 GitHub Actions 中显式写 `permissions: {}`，体现了“Least Privilege”思路的贯彻。  
2. **测试契约化**：针对工作流对象属性编写专门断言，形成 **Workflow Contract Tests**，这种模式有助于防止未来工作流改动破坏安全假设。  
3. **增量提交频繁**：同一 PR 多轮小幅修改（f0c47ed2 → 044f74e6），每次只改动极少文件，适合 quick‑review，但也容易让审查者忽视全局依赖关系。  

### 架构观察  
- **CI 与业务代码耦合度低**：CI 工作流只依赖外部凭证和公开工具，未使用 repo‑token，说明项目在安全隔离上已有良好分层。  
- **依赖升级幅度大**：一次 PR 中涉及 70+ 文件、5668 行代码的依赖升级，暗示项目对 **uv.lock**、**pyproject.toml** 同步的治理仍不够自动化。  
- **系统服务层（systemd）与业务层混杂**：updater、daemon、systemd 脚本在同一仓库中，后续可能需要独立的部署子模块或 CI 镜像来降低相互影响。

## 3. 规范完善建议  

| 现有缺口 | 建议的审查规则或改进 |
|----------|-------------------|
| **依赖锁文件同步** | - **强制检查**：提交中若出现 `pyproject.toml`、`requirements.txt` 或 `uv.lock` 任意变动，审查工具必须自动比对两者是否保持一致；不一致直接标记 `error`。 |
| **跨文件安全契约** | - 为每个 GitHub Action 作业定义 **“权限契约”**（如 `permissions: {}`、`secrets` 使用限制），并在 CI 中运行合同测试；审查时检查是否新增或修改了合同测试。 |
| **递归/重入风险** | - **函数调用图检查**：对标记为 `public` 或 `service` 的函数执行一次全库搜索，若出现自调用或循环调用，自动标记 `major`。 |
| **增量审查的全局视角** | - **增量+全局双模**：quick‑review 只能覆盖本次改动；每当 PR 超过 **3 次增量** 或累计改动行数 > 1000，系统自动切换为 **full‑review**，要求审查全部关键文件。 |
| **文档/测试同步** | - **文档覆盖规则**：每当工作流文件或系统服务脚本被修改，必须同步更新对应的 **README / docs**，缺失时给出 `minor` 警告。 |
| **系统服务安全** | - **systemd unit 文件审查**：检查 `User=`、`Group=`、`CapabilityBoundingSet=` 等字段是否最小化；若缺失自动提示。 |

## 4. 经验教训  

1. **增量审查不能代替全局风险评估**  
   - 本次 PR 中的 “最小权限” 改动很安全，但之前的 **递归调用** 与 **锁文件漂移** 仍可能导致运行时错误或安全漏洞。审查流程应在每轮增量结束后，回顾是否已闭环所有历史标记的 `major` 项。  

2. **安全契约要配套测试**  
   - 通过在测试里断言 `permissions: {}`，把安全配置当成可验证的合约。以后对任何 “权限/凭证” 相关的改动，都应强制配套 **contract test**。  

3. **依赖升级必须自动化**  
   - 手动同步 `pyproject.toml` 与 `uv.lock` 极易出错。建议在 CI 中加入 `uv sync --locked` 步骤，或者在 PR 检查阶段运行 `uv lock --check`，不通过即阻断合并。  

4. **审查工具的“负向用例”**  
   - 高分审查仍需 **负向验证**（例如故意把 `permissions` 写错，确认审查能捕获）。在审查规则中加入 **“故障注入”** 检查，可提升误报率的容忍度。  

5. **文档与代码同步**  
   - 本轮审查没有检测到文档更新（如 systemd 服务说明），但实际 PR 中已经有对应的说明。建议在审查流程里加入 **doc‑diff** 检查，确保文档改动不被遗漏。

## 5. 增量审查反思  

| 问题 | 现状 | 风险/建议 |
|------|------|-----------|
| **是否解决了之前的 major 问题？** | 本次提交只涉及 CI 权限最小化，未触及 **依赖锁同步** 与 **递归调用**。这些问题仍未在 PR 中得到确认修复。 | 必须在后续提交或在当前 PR 的补丁中加入：<br>1. `uv.lock` 与 `pyproject.toml` 完全同步。<br>2. `updater_client.py` 的递归调用已改为循环或外部包装函数。 |
| **增量变更是否引入新风险？** | 新增 `permissions: {}` 本身是降风险的改动。唯一潜在风险是 **误删** 了后续可能需要的权限（如在未来的 workflow 中需要写 repo），但目前已通过测试验证。 | 建议在 CI 中保持 **permissions‑schema** 的版本化，防止未来误删导致工作流失效。 |
| **审查覆盖度因只看增量而下降？** | 是的。审查者只看到 4 行 YAML 的改动，未主动检查 PR 其余 70+ 文件的整体质量。 | 在每轮增量审查结束后，审查工具应自动弹出 **“全局待验证项”** 列表，提醒审查者回顾历史未闭环的问题。 |

**结论**：本轮增量审查在安全硬化方面做得很好，值得在项目中推广。但在 **全局风险闭环**、**依赖锁同步** 与 **递归调用** 这两大历史问题上仍有缺口。后续审查应结合 **增量+全局** 双模策略，确保每一次小改动都在更大的安全/功能视野下得到验证。
