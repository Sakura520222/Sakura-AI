# Issue #737 分析反思

## 1. 分类与优先级准确性

**分类：准确。** enhancement 判断正确——这是明确的输出观感改进请求，功能未损坏（非 bug），也无新能力（非 feature）。分析正确定位为"展示层改造而非功能缺陷"。

**优先级：medium 合理但可再斟酌。** 有一个反向论点值得记录：PR 审查评论是本产品（AI Code Review 机器人）的**核心交付物**，其观感直接决定用户对产品的第一印象和信任度，影响面覆盖所有审查路径（普通/行内/快速/标准/深度/降级）。从"产品门面"角度可论证偏 high。维持 medium 的合理性在于：无功能损失、无数据风险、可渐进实施。建议未来对"核心输出面整体观感"类 Issue，优先级判断时显式权衡"影响广度 vs 严重程度"两个轴。

## 2. 标签推荐质量

- **enhancement (0.9)**：合理。
- **configuration (0.55)**：贴切——模板双源（默认值 + DB 自定义合并）是本 Issue 最实质的工程难点，配置迁移兼容是硬需求。
- **test (0.55)**：勉强合理。test 通常用于纯测试建设类 Issue，此处测试只是改造的配套，作为次级标签可接受。
- **refactor (0.4)**：**语义上有问题**。Refactor 惯例指行为保持的代码结构调整，而本 Issue 是行为可见的输出变更（用户能看到的文案变了），且 Issue 明确约束"评分与决策逻辑零改动"。分析可行性部分自己也确认了逻辑零改动。0.4 置信度反映了犹豫，但更干净的做法是**直接不推荐**该标签，避免误导维护者预期代码结构调整。

**遗漏方向**：若仓库存在 `ui`/`ux` 类标签，比 refactor 更贴切。分析未核验仓库现有标签体系与建议标签的一致性——建议标签前应先比对仓库实际标签集，避免推荐不存在的标签。

## 3. 可行性判断质量

**整体质量高**，是本次分析的亮点：
- 模板双源与存量部署迁移风险（关键洞察——"仅改默认值不生效"）
- 四个格式化输出面的梳理及 `_format_comment` 死代码保留的谨慎提醒
- `parse_label_checkboxes` 正则耦合验证（展示与解析的隐性契约）
- `branding.py` 单一来源的涟漪效应 + 幂等判断基于精确字符串的脆弱性
- `{score}` 占位符 `format()` 缺参的具体陷阱

**三处可补充的遗漏**：

1. **现有测试断言的破坏面**：分析只提"补四类新用例"，但文案/模板改动几乎必然大面积击穿现有测试中的字符串断言（Emoji、评分格式、"AI审查决策"等措辞若被测试引用）。这通常是文案类改造工作量中被低估的最大项，应纳入估算。
2. **英文模板的写作风格验证**：`review_templates_en` 存在说明有多语言输出，但"专业、自然、克制"在英文语境下的措辞改造与验证未展开——两种语言的风格改造工作量并非简单翻倍，但也不是零。
3. **验收标准的主观性**："专业、自然"缺乏客观判据，建议实施时引入 golden example（改造前后对照样本）作为验收锚点，否则 PR review 阶段容易陷入主观拉锯。

## 4. 重复检测准确性

**判断准确且论证扎实。** 对 #321、#195 的"相关但不重复"区分展现了正确方法：
- #321：以"#737 保留复选框交互为前提"证明是增量而非重复
- #195：以"#737 不触及协议层"证明作用层不同

这种"按约束条件和作用层切分"的区分模式值得固化为标准方法。唯一潜在盲区：风格类改造常有**系列碎片 Issue**（如有人单独提过"去掉评分"或"页脚 AI 声明"），#737 可能是它们的超集。分析未报告是否搜索过此类局部重叠 Issue——若有存在，#737 应关联而非重复标记，这不影响本次结论但建议未来补这个搜索维度。

## 5. 标题改写适当性

**"无建议"是正确的克制。** 原标题已同时覆盖对象（PR 审查评论风格）、手段（去除 Emoji 和机器化模板）、目标（统一 Review 输出），信息密度适中、指向明确，且作为维护者自提的风格诉求，原标题承载了作者意图。"无建议"避免了为改而改。这为后续分析确立一个判据：**原标题已含"对象+动作+目标"三要素时不改写**。

## 6. 经验教训

可提炼为可复用模式：

1. **文案/风格类改造，风险重心在配置不在代码**：模板类内容一旦落 DB（用户可自定义），默认值修改只覆盖新部署，必须设计"旧默认值检测→安全升级 vs 用户自定义→保留并提示"的版本化迁移。凡涉及"默认模板/默认文案"的 Issue，此项应成为固定检查点。
2. **单一文案源的涟漪效应**：`branding.py` 这类"唯一来源"设计使任何文案修改都是跨输出面的变更，改动前必须枚举全部调用方并逐一决策"保留/同步"。
3. **字符串幂等判断是文案变更的隐形地雷**：基于精确字符串包含的幂等/去重逻辑（如 `append_review_signature`）在文案更新后失效，新旧混存期会产生重复内容——改文案必搜字符串比较点。
4. **展示格式可能与解析器存在隐性契约**：移除任何展示元素（百分比、Emoji）前，先验证解析正则的依赖边界。本次幸运的是正则只依赖 `**bold**` 结构，但这个验证步骤不可省略。
5. **行为可见的变更禁用 refactor 标签**，避免语义混淆。
6. **文案类改造的工作量估算公式**：N 个输出面 × 2 种语言 × （模板改写 + 现有断言修复 + 迁移用例），其中"现有断言修复"最易被低估。

**本仓库特有模式**：该项目存在"策略配置模板 > 代码默认值"的覆盖链和多条审查路径并存（含未被 worker 调用的库函数），任何输出面改造前必须先做调用链普查——这一前置步骤应写入此类 Issue 的实施建议首位。
