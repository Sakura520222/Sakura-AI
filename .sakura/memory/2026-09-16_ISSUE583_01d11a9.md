**六、经验教训 & 建议**

| 方向 | 关键要点 |
|------|----------|
| **冲突预防** | - 在 `main` 合并前，**先在 `develop` 上做一次前置合并**或 **rebase**，确保 `develop` 已包含 `main` 的最新改动。<br>- 为关键配置文件（`pyproject.toml`、CI YAML）设置 **冲突解决策略**（如 `ours/theirs`）或 **代码所有者**，提前指派解决人。 |
| **CI 设计** | - 将同步步骤拆分为 **“检查冲突”** 与 **“自动合并”** 两个 Job；若检测到冲突直接 **标记为失败**，并在 Issue 中附带冲突文件列表，减少手动排查时间。 |
| **自动化反馈** | - 在工作流失败后，自动 **在 Issue 中贴出 `git diff --name-only`**，帮助维护者快速定位冲突文件。 |
| **标签体系** | - 为分支管理类问题统一使用 `branch-management`、`merge-conflict`、`gitflow` 等标签，形成可搜索的闭环。 |
| **重复检测** | - 采用 **文本相似度 + 关键字段（分支、工作流名）** 双重判定，避免因标题相似但实际内容不同的误报。 |
| **文档** | - 在项目 `CONTRIBUTING.md` 中加入 **“Gitflow 同步流程”**，明确 **手动合并步骤**、**冲突处理约定**（保留哪一方），降低新贡献者的认知成本。 |
| **工作量评估** | - 为类似的分支同步冲突预设 **时间区间**（15‑45 min），在 Issue 模板中提供 **“预计耗时”** 字段，帮助团队更好地排期。 |
