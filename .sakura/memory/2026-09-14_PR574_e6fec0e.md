## 2️⃣ 发现的模式  

### 代码/依赖模式  
- **统一依赖声明**：项目同时维护 `pyproject.toml`（Poetry/PEP‑517）和 `requirements.txt`，且两者的版本号保持同步。说明团队倾向于兼容多种部署方式（poetry、pip‑freeze）。  
- **最低版本约束 (`>=`)**：采用宽松的 “最低版本” 方式，而非精确锁定。对安全更新友好，但需要配合 CI 检查兼容性。  

### 架构观察  
- **Python 3.14 为目标运行时**：`.python-version` 已指向 3.14，且依赖升级专门为此做兼容适配，说明项目在追踪最新语言特性（free‑threading）并准备在新环境中运行。  
- **缺少锁文件**：仓库未出现 `poetry.lock`、`uv.lock` 等锁定文件，依赖解析全交给 CI/运行时完成。此模式在 CI 环境下易出现瞬时兼容问题（如临时缺失的 wheel），需要 CI 中加入 **“pip install --prefer‑binary”** 或 **“poetry lock --no‑update”** 的检查。

## 4️⃣ 经验教训  

1. **即使是“一行版本号”也要完整审计**  
   - 通过全库搜索、Dockerfile 检查、锁文件比对等手段，确保没有遗漏的硬编码或脚本中隐式依赖。  
2. **CI 证据不可或缺**  
   - 把 CI 运行日志或成功构建链接视为审查结论的必备支撑，尤其在“无代码改动”场景下，更能提升信任度。  
3. **兼容新 Python 版本的依赖升级要提前验证**  
   - 对于像 Python 3.14 这种新特性，依赖的 cp314 wheel 是否可用直接决定部署成功率。建议在 CI 中加入 **“pip download --only‑binary :all: -r requirements.txt”** 的检查，以提前捕获缺失的二进制包。  
4. **文档同步不是可选项**  
   - 项目文档往往是新手或 CI 脚本的来源，若文档中出现旧的约束，会导致误导或脚本失效。审查时应把文档视为代码的“只读”入口，进行同步校验。  
5. **审查规则的层级化**  
   - 对“最简单变更”仍要执行 **Fail‑Closed**（宁可误报），但可以通过规则的优先级（如 “依赖同步” → “CI 证据” → “安全标签”）来降低噪音，保持审查效率。
