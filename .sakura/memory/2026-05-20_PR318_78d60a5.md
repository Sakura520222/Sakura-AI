## 深度反思

### 1. 审查质量评估
- **覆盖度**：基本覆盖核心逻辑，但遗漏了**跨文件影响检查**。变更新增 `suggested_title` 字段，虽下游使用安全，但未系统检查所有读取 `analysis_data` 的位置（如其他服务或任务队列），存在潜在遗漏风险。
- **准确度**：严重程度标记合理，反转义顺序问题确为 major，但未明确标注“阻断合并”级别（根据项目记忆，major 应阻断）。minor 问题标注准确，但“下游安全访问”结论略显仓促，应补充验证调用链。
- **完整性**：充分理解变更意图（降级增强），但未深入分析**正则提取的边界情况**（如字段值含引号或换行时的误匹配风险），上下文理解可更深入。

### 2. 发现的模式
- **代码模式**：项目倾向使用正则处理非结构化文本（如截断 JSON），但缺乏统一的转义处理函数，导致逻辑分散（如 labels/assignees 提取）。
- **架构观察**：服务层（`issue_analyzer.py`）与下游（`issue_service.py`、`issue_worker.py`）耦合较紧，变更需跨文件验证；动态配置体系未在此场景应用，但符合“复用优先”原则。

### 3. 规范完善建议
- **新增审查规则**：
  - **Major 级问题必须明确阻断**：根据项目记忆，major 问题应标“阻断合并”，本次未强调，需在审查模板中强制注明。
  - **跨文件变更强制全链路检查**：新增字段或逻辑时，必须列出所有相关读取/写入位置（如 `analysis_data` 的使用点），避免碎片化。
  - **正则提取 JSON 场景需补充边界测试用例**：建议在 PR 描述中要求提供截断 JSON 的测试示例（如含 `\\n` 的路径）。
- **项目特有规范**：
  - **反转义逻辑统一化**：强制要求提取共用 `_unescape_json_string` 函数，避免三处重复且不一致的代码（符合“辅助函数复用强制检查”）。

### 4. 经验教训
- **未来审查要点**：
  - **降级逻辑的兼容性验证**：新增字段时，必须检查所有下游消费者（包括非直接调用者，如任务队列或第三方集成）。
  - **正则模式的可维护性**：复杂正则（如 `(?:"|$)`）需在 docstring 中明确设计意图，避免维护者误改。
  - **类型注解完整性**：公共函数必须添加类型注解（如 `-> int | None`），这是项目质量基线。
- **技术模式经验**：
  - **JSON 截断处理**：正则提取虽灵活，但易出错；优先考虑 `json.loads` 部分解析或使用容错库（如 `json5`），而非手动正则。
  - **转义处理顺序**：始终先处理双字符转义（如 `\\`），再处理单字符（如 `\n`），这是字符串处理的黄金法则。
