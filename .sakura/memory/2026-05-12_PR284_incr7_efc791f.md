## 4. 经验教训

### 值得关注的要点
- **增量审查的“债务碎片化”陷阱**：同一个技术债（如配置范围校验缺失）跨越 4+ 轮 PR 仍未修复，审查结果中虽然列出但未触发升温机制 → 应严格执行“连续 3 轮未修复自动生成 issue”的规则。
- **“点状修复”的遗漏风险**：修复导入重复 → 仍留在 `database.py`；修复描述漂移 → 未检查 `fetch_url_tool` 同类漂移 → 单点修复容易遗漏同类债务。
- **评分乐观偏差**：当变更本身干净但架构问题仍在时，评分容易偏高。建议增加“–1 分 for 引入或延续架构异味”的微调规则。

### 对特定技术的审查经验
- **动态配置系统的三件套检查**：每看到一个新增配置读取，必须反查：
  1. 写入路径是否经过统一校验
  2. 更新后是否触发缓存失效
  3. 测试断言是否引用生产常量
- **Shell 工具语义漂移检查**：凡是 description 中包含“正则表达式/固定字符串/glob”等语义关键词的 LLM 工具，必须与实现逐词对照。
