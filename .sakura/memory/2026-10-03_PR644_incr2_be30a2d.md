### 2. 发现的模式与架构观察

*   **代码模式： Fail-Closed 防御性编程**
    *   项目在处理外部输入及配置校验时高度贯彻 Fail-Closed 原则。例如 `relation_analyzer.py` 对存量 DB 超限值的处理：在消费端捕获 `ValueError` 仅阻断关系分析阶段，避免主分析崩溃，且不触发非必要的外部 API 调用。
*   **架构观察： 锁生命周期与数据库方言兼容**
    *   **并发锁模式**：跨进程/异步任务的所有权交接（Handoff）极易在 `release` 与 `acquire` 的缝隙中发生锁状态分裂。通过将计数递增前置到等待 phase 并精细控制 `users == 0` 才删键，构建了确定性的并发所有权移交。
    *   **SQL 下推与 SQL 编译断言**：将 Python 内存扫描下推到数据库层面去重，同时使用 ORM AST 编译断言（支持 MySQL/PostgreSQL 方言），避免了 1093 错误及方言差异引起的动态 SQL 缺陷。

### 3. 规范完善建议

基于本次审查，建议在 `项目记忆` 中新增/强化以下两条规则：

1.  **并发所有权锁 (Ownership Lock) 生命周期规范**：
    *   *规则*：在实现基于 Users 计数或键值映射的锁/资源池时，**引用计数递增必须在进入 acquire 等待队列之前同步完成**；删除键/清理资源的条件必须严格约束为 `users == 0`，严禁“持有者 release 即删键”，以防交接期竞争造成分裂锁。
2.  **数据迁移 SQL 下推与编译防线**：
    *   *规则*：涉及大数据量去重/清理的迁移，严禁将全表拉入 Python 内存处理。必须下推至 DB，且必须包含方言编译测试（至少覆盖 MySQL 1093 派生表规避与 PG 兼容性），同时断言单次 SQL 执行上限。

### 4. 经验教训

*   **配置校验优先于早退 (Guard Before Early-Exit)**：
    *   *教训*：在编写“空数据/空候选早退”逻辑时（如 `if not items: return`），必须评估**坏配置是否会导致恶意或误操作绕过校验并静默生效**。配置合法性校验与安全边界检测必须物理置于任何逻辑早退分支之前。
*   **契约测试防老旧兼容接口破损**：
    *   当重构核心函数参数（如 `detect_duplicates` 将可选参数改为必填正整数）时，仅靠静态检索全库调用点是不够的，必须引入显式的**契约测试（Contract Tests）**断言非生产调用方及异常抛出行为。
