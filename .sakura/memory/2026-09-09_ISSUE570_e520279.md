## 6. 经验教训 & 建议  

| 经验点 | 说明 |
|--------|------|
| **多组件同步更新必须原子化** | 单独更新 Web 镜像而不检查 sandboxd/Runner 会产生漂移。实现统一 manifest 或事务式更新机制是根本解法。 |
| **Updater 与 UI 必须共享能力描述** | 在 `/v1/status` 暴露 `capabilities`，并在 UI 端做 **fail‑closed** 检查，防止能力不匹配导致误报。 |
| **版本号不能仅用于展示** | 语义版本号必须随功能集同步升级（如从 `0.2.0` 升至 `0.3.0`），否则 UI 误以为功能一致。 |
| **回滚与自愈路径要明确** | 当三镜像出现漂移时，系统应自动检测并触发回滚或补齐更新，而不是仅记录状态。 |
| **CI/CD 中加入统一 Manifest 检查** | 在镜像发布阶段生成一次性 manifest，部署时所有组件必须读取同一 manifest，避免发布时间差导致的半就绪。 |
| **测试覆盖必须覆盖负向路径** | 增加 “能力缺失” 与 “版本不匹配” 场景的单元/集成测试，确保 UI 与 Updater 在不兼容时返回明确错误。 |
| **文档不能替代代码检查** | 任何兼容性约束必须在代码层实现（如 `capabilities`），文档仅作说明，防止因文档遗漏导致误用。 |
| **日志与监控** | 在 Updater 的关键步骤（下载、校验、安装）加入结构化日志，便于故障定位与告警。 |
