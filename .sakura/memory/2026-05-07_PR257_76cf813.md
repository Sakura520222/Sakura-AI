## 四、经验教训

### 值得在未来审查中关注的要点

1. **新状态引入的全链路检查清单**  
   数据库枚举 → 后端逻辑 → API 返回 → WebUI 模板 → 过滤器下拉 → i18n → SSE 事件。建议形成固定检查模板。

2. **“技术上正确但看起来像 bug”的代码要格外谨慎评价**  
   `review_id=None` 时无法更新数据库不是问题，但在评论中列为主要条目会造成读者误解。建议改用 `info` 或 `note` 标记。

3. **返回值语义变化即使当前无害也要警示**  
   从 UUID 改为 task_key，当前调用方只用于日志，但未来可能有人用它做去重或追踪。应在 PR 中明确标注，或在代码中保留 UUID 作为内部标识。

4. **信号量排队场景下的共享取消信号是合理设计**  
   审查看似质疑“排队任务被一起取消”，但实际这正是设计意图。审查者需区分“设计缺陷”与“设计特性但缺少文档”。

### 对特定技术的审查经验

| 技术点 | 审查经验 |
|--------|----------|
| `asyncio.Event` 作为取消信号 | 需检查注册/注销配对、是否在 finally 中清理、多个等待者共享 event 时的行为是否符合预期 |
| SQLAlchemy 异步 session | 取消任务时若 DB 已无 record，不应强制更新；本 PR 正确处理了 `review_id=None` 的情况 |
| WebUI Jinja2 模板 | 新增枚举值必须搜索所有 `{% if status == ... %}` 和 `{% elif %}` 分支 |
