## 4. 经验教训

### 值得未来关注
1. **降级链路端到端验证**：不要只检查“是否触发了降级”，还要验证降级后是否真的能完成审查（如单文件 diff 仍超长）。
2. **异常类型映射的真实错误原因**：`BadRequestError` 的 `message` 字段应被解析，提取 `"maximum context length"` 等特征词后再决定是否降级。
3. **工具定义与业务模式的耦合**：`BASE_TOOLS` 作为“始终可用”工具集，不应包含条件性工具。建议引入 `CONDITIONAL_TOOLS` 字典，按需动态添加。

### 对特定技术的审查经验
- **OpenAI SDK 的异常层次**：`openai.BadRequestError` 继承自 `APIError`，但错误原因千差万别，务必检查 `e.body` 或 `e.message` 中的细分错误码。
- **工具循环的状态管理**：AI 多轮对话中 `messages` 是不断增长的引用型列表，在提取公共方法时务必注释清楚“该方法会修改传入的 messages 列表”。

### 本次审查的自我反思
- 标记为 `critical` 的两个问题（`KeyError` 风险、`BadRequestError` 误判）确实会影响生产稳定性。

- 缺少对“新增工具是否注册到 `TOOL_NAME_TO_DEFINITION`”这一点的验证——实际已注册，但审查未明确提及，属于轻微遗漏。
