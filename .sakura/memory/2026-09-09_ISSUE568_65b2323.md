**6️⃣ 经验教训 & 未来关注点**  

| 经验点 | 说明 | 行动建议 |
|--------|------|----------|
| **幂等性是补偿机制的核心** | 定时扫描必然会与实时 webhook 并发，若业务入口不具备幂等保护会产生重复分析任务。 | 在 `submit_*_task` 前加入唯一键检查或使用 **数据库唯一约束**；在调度器层实现 **分布式锁**（如 Redis lock）。 |
| **分页+速率限制** | 大仓库一次性拉取所有 open Issue/PR 可能触发 GitHub API 速率限制。 | 使用 `per_page=100` 分页，配合 **指数退避**；记录 `last_successful_page` 供下次增量扫描。 |
| **监控不可或缺** | 定时任务若因网络异常停摆，系统将长期缺失补偿。 | 在调度器内部捕获异常并上报至 **Prometheus/Alertmanager**，同时在 UI/仪表盘展示 “上次成功扫描时间”。 |
| **配置统一化** | 扫描间隔、是否启用开关等配置应集中在 `backend/core/config.py`，避免硬编码。 | 为新配置项提供 **环境变量** 与 **配置文件** 双入口，并在 CI 中校验默认值合法。 |
| **重复检测需语义层** | 仅靠标题关键字会产生误报/漏报。 | 引入 **文本相似度模型**（如 Sentence‑Transformers）或基于 **issue_body** 的相似度比对。 |
| **文档同步** | 新增调度器会影响部署手册、运维手册以及 CI 文档。 | 在 PR 中添加 **文档更新任务**（README、部署脚本、监控告警说明），并在 CI 加入 **文档 lint**。 |
| **测试覆盖** | 补偿扫描涉及外部 API 与 DB，单元测试需 **mock GitHubClient**、**使用 SQLite 内存库**，并验证 “已有记录不再触发”。 | 编写 **参数化测试**：① 正常触发；② 已有记录；③ 并发触发；④ API 失败回滚。 |
| **性能基准** | 评估全量扫描耗时，防止在高流量时段导致系统卡顿。 | 在本地/CI 中跑 **基准测试**，记录每 1000 条 Issue/PR 的处理时间，作为调度间隔的参考。 |
