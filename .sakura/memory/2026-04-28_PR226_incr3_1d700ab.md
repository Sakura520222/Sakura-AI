### 3. 规范完善建议

基于本次反思，建议新增或强化以下审查规则：

1.  **全局工作流串联检查规则（防“隧道视野”）**：
    ```markdown
    - **新功能闭环校验（major级别）**：对于引入新数据字段（配置、DB列、API参数等）的PR，审查必须追踪该字段的完整生命周期：
      - 产生 -> 解析 -> 验证 -> 存储 -> 使用/展示。
      - 若任一环节存在逻辑缺失，应标记为[major]，并指出体系不完整。例如，新增了控制开关，必须验证在所有相关分支中是否被正确检查。
    ```
2.  **日志一致性强制规则**：
    ```markdown
    - **日志语义与行为一致性**：代码的逻辑行为与日志消息描述必须完全一致。行为变更时，旧的日志消息必须同步更新。此规则作为硬性检查项，在quick审查中同样适用，发现即标为[minor]以上。
    - **关键路径日志级别可观测性**：对于AI生成值、外部输入等不可信数据，在其值被修正（如clamp）或因不合法而被丢弃时，必须使用`logger.warning`级别，以确保在默认日志级别下可见，便于监控和追踪。`logger.debug`在此场景下视为无效可观测性。
    ```
3.  **模式化解析脆弱性规则**：
    ```markdown
    - **LLM输出解析健壮性**：任何针对LLM输出的正则或字符串匹配，必须评估其对空白字符（空格、换行）、常见标点变体（中英文冒号）的容忍度。过于严格的模式应标记为[suggestion]，指出潜在的静默失败风险，并可在累积后升级为技术债。
    ```

### 4. 经验教训

-   **对AI输出解析要持“不信任”态度**：本次审查中的正则表达式问题是教科书级的案例。AI输出是非确定性的，任何强假设（如“恰好一个换行”）都是脆弱的。未来审查此类代码时，应**主动在脑中引入变异**（如多了空行、少了换行、冒号用中文格式等），并追问“解析逻辑会怎样？是报错、返回空、还是返回不完整数据？” 这应成为审查AI相关功能时的标准思维模型。

-   **“去重”变“合并”是重构高发错误区**：当一个既有功能（去重）的内涵发生根本性转变（合并）时，相关的元数据（日志、变量名、注释）极易被遗忘。未来审查此类“语义转换型”重构时，必须将对**元数据同步更新**的检查设为高优先级。

-   **警惕“高评分低决策”的信号**：评分 9/10 但决策是 `request_changes`，这个组合是内部一致的，但也是一个强烈的警示信号。它表明审查者认为代码质量已经很高，但仍然存在必须修改的问题（如那个误导性日志）。这提醒我们，不应被高分麻痹，而应仔细审视每个未闭环问题是否真的无关紧要。
