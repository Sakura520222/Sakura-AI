**六、经验教训与后续建议**

1. **动态模型信息的统一获取**  
   - 将模型名称（`context_model`）的解析抽象为公共函数或类属性，所有需要判断模型能力的地方统一调用，避免出现硬编码空字符串的情况。  
   - 在 `strategy_config` 中加入 `get_current_model()` 接口，返回实际服务模型名。

2. **能力判断的防御式写法**  
   - `is_model_supports_reasoning_content` 调用前先检查模型名是否为空，若为空则使用默认模型或抛出明确异常，防止静默失效。  
   - 示例：  
     ```python
     model_name = context_model or self._resolve_served_model()
     if not model_name:
         logger.warning("Model name unresolved, fallback to default.")
         model_name = DEFAULT_MODEL
     ```

3. **测试覆盖**  
   - 增加 **多模型切换** 场景的单元测试：① 使用 DeepSeek‑v4（支持），② 使用不支持的模型，③ 在工具链中途触发模型回退。确保 `reasoning_content` 在第① 场景被保留，其他场景按预期被丢弃。  
   - 用 **snapshot** 或 **parameterized** 测试确保历史消息结构始终包含 `reasoning_content`（当模型支持时）。

4. **日志与监控**  
   - 在工具循环结束后记录 `reasoning_content` 是否被写入的日志（debug 级别），便于快速定位类似回归。  
   - 若项目使用监控平台，可添加异常计数 `reasoning_content_missing`，在异常阈值触发告警。

5. **文档同步**  
   - 在项目的 “模型能力对照表” 文档中标注哪些模型支持 `reasoning_content`，并说明在代码中如何判断。这样新加入的模型或模型升级时，维护成本降低。

6. **代码审查检查点**  
   - 增加审查 checklist 项：*“调用模型能力判断函数时，确保传入的模型名是运行时解析得到的，而非硬编码或空值”。*  
   - 在 CI 中加入 **static analysis**（如 `ruff`、`pylint`）规则，检测 `is_model_supports_reasoning_content` 的调用是否使用了字面量空字符串。
