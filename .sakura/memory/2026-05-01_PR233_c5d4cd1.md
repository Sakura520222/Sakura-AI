### 2. 发现的模式

#### 代码模式
- **分散的版本管理**：版本号散落在 4+ 个位置（`main.py`、`auth.py`、`init.sql`、`__init__.py`、`database.py` fallback），存在**更新遗漏高风险**
- **Fallback 版本漂移**：`database.py` 使用 `"1.0.0"` 作为默认值，与最新版本差距过大，属于**技术债务累积模式**
- **PR 描述与变更脱节**：描述提及 CI 配置，但审查范围仅有版本更新，说明**审查未按 PR 实际内容执行**

#### 架构观察
- **Docker 与非 Docker 部署的两套初始化机制**：`init.sql`（Docker）与 SQLAlchemy fallback（非 Docker）可能导致**环境不一致**
- **多语言版本同步困难**：Python 代码（`main.py`、`__init__.py`）+ SQL 脚本（`init.sql`）混用，缺乏**单一真相源**

### 3. 规范完善建议

#### 新增审查规则

| 规则 | 严重度 | 触发条件 |
|------|--------|----------|
| **版本升级须验证构建/部署脚本** | major | 变更涉及版本号时，自动扫描 `Dockerfile`、`.github/workflows/*.yml`、`Makefile` 中是否引用版本标签 |
| **PR 描述与实际变更一致性检查** | major | PR 描述声明的改动（如"新增 CI"）在文件变更列表中找不到对应文件，须标记 |
| **数据库 fallback 默认值版本审查** | minor | 任何 `Column(default="x.x.x")` 类型的默认版本号与当前版本差异超过 1 个 major 版本时告警 |
| **版本号集中化强制检查** | suggestion | 发现 3 个以上独立版本号定义点时，建议改为从单一文件导入（如 `VERSION.txt`） |

#### 项目特有规范
- **版本升级 checklist 强制执行**：除了全仓库搜索 `version\s*=\s*["'][\d.]+["']`，还必须验证：
  1. 所有 `__version__` 引用点
  2. Docker 镜像标签
  3. Helm Chart values（如有）
  4. API 文档中的示例版本号

### 4. 经验教训

#### 未来审查关注点
- **禁止"双目标 PR"未拆分审查**：如果 PR 同时包含版本升级和功能新增（如 CI），必须要求拆分或明确审查两个维度的交叉影响
- **版本号升级必须附带 CHANGELOG**：即使是 patch 版本，也应在 PR 描述中说明修复内容，否则标记为 `suggestion` 并要求补充
- **多语言项目版本升级的自动化验证**：建议添加 CI 脚本自动检查所有版本号是否一致（如 `grep -r "version.*="`），防止人工遗漏

#### 对特定技术的审查经验
- **SQLAlchemy default 参数陷阱**：`default="1.0.0"` 在 ORM 创建对象时会作为 fallback，容易被忽略，审查时必须关注
- **GitHub Actions 与版本号的耦合**：如果 CI 中构建 Docker 镜像并打 `v2.9.1` 标签，必须验证版本号是否从代码中读取（避免硬编码）
- **semantic versioning 的误用模式**：无实际修复的版本升级属"空跳版"，应要求补充无效变更说明或降级为 build metadata

#### 本次审查的最大遗憾
**未完整执行项目记忆中的规范**：
- 项目记忆明确要求"版本升级须提交 CHANGELOG 草案（minor/major）"，本次审查仅建议但未强制
- "增量审查的风险升温检测"未应用到 CI 新增与版本升级的交叉验证
- "跨语言版本同步"已被标记为高危区，但审查未要求构建时注入方案

**改进方向**：下次遇到版本升级 PR，优先使用自动化工具（如 `grep` + `diff`）扫描全仓库所有版本号，再人工确认 fallback 和环境依赖。
