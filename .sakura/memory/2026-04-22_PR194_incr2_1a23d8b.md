## 2. 发现的模式

### 代码模式：防御性代码在重构中的"隐形流失"

```python
# 旧 mock 中的防御逻辑
if "/" in repo_name else ("", repo_name)

# 新实现中直接消失
_owner, _name = repo_name.split("/", 1)
```

这不是偶然遗漏，而是一种模式：**开发者在"用真实实现替换mock"时，倾向于认为真实数据源不会产生异常格式，从而丢弃防御层**。同理，mock 不需要路径安全验证（因为不读文件），替换为真实实现时安全验证没有被同步添加。

### 架构观察：双数据源的一致性裂缝

```
PyGithub API (主路径) ──→ 返回 ContentFile（含 sha、url 等元数据）
        ↓ fallback
LocalRepoAdapter ──→ 返回 _LocalContentFile（仅含内容，元数据缺失）
```

两条路径返回的对象结构不同，下游如果依赖元数据（如计算 diff 时需要 sha），会在 fallback 路径上产生难以排查的行为差异。

## 3. 规范完善建议

### 新增规则

| 规则 | 触发条件 | 检查要点 |
|------|---------|---------|
| **适配器接口契约验证** | 实现替换外部依赖的适配器类 | 必须列出被适配对象的所有公共方法/属性，逐一确认实现或显式抛 `NotImplementedError` |
| **重构防御性检查保留** | 替换/重写已有代码 | diff 中若删除了 `if/try/except` 等防御结构，必须确认新代码有等价保护或说明原因 |
| **双数据源返回类型一致性** | 存在主路径+fallback | 两条路径的返回类型必须共享同一基类或 Protocol，否则标记 major |

## 4. 经验教训

### "替换mock"类变更的系统性风险

替换 mock ≠ 简单实现接口。mock 隐含的简化假设（不需要安全验证、不需要参数语义、不需要元数据）在替换为真实实现时必须逐一重新审视。**审查此类变更时，应把"mock省略了什么"作为第一条检查线索。**

### 历史问题零修复的评分信号

第1轮 6/10 → 第2轮 5/10：3个严重问题全部未修复，评分下降体现了**问题积累惩罚**。这个策略是正确的——如果开发者对 critical 问题不响应就提交复审，评分应持续下降直至触发阻断机制，而非维持在原分。

### 静默失败的日志要求应升级

`_detect_default_branch` 静默回退到 `"main"` 被标记为 💡 suggestion，但考虑到这是扫描的**入口逻辑**，错误分支检测会导致整个扫描结果无意义。**入口处的静默失败应至少为 minor，建议升级判定标准。**

## 5. 增量审查反思

### 新增提交与历史问题的关系

本次提交 `1a23d8b` 的消息是 `fix(scan): replace mock repo with real PyGithub object or local adapter`——这本身就是**引入问题的提交**，而非修复提交。第1轮审查已经针对该提交给出了问题清单，第2轮发现零修复。这说明：

- 开发者可能将"重新触发审查"误解为"等审查者再看一遍"，而非"提交修复代码后触发"
- 审查系统应明确区分 **"复审"（re-review，针对修复提交）** 和 **"重复审查"（同一提交的二次审查）**，后者如果无变更应直接拒绝

### 覆盖度是否因增量视角下降

本次审查只关注了 2 个文件（+163/-0 和 +19/-8），没有回溯检查：
- `file_tool.py` 中调用 `get_contents(file_path, pr.head.sha)` 时，`pr` 为 `None` 的场景是否在其他地方也有处理？
- `search_files_tool.py` 的 `_search_via_api` 失败回退路径是否在所有调用场景下都正确？

但考虑到 quick 策略的定位，这种回溯可以接受。**真正的覆盖度风险在于：适配器实现了哪些方法、漏了哪些方法——这需要看适配器本身的完整性，而非回溯调用方。**

### 增量审查的正确做法

对于本轮审查，更高效的做法可能是：
1. 发现提交 hash 未变 → 直接输出"未检测到修复提交，历史问题全部未修复"，拒绝复审
2. 或要求开发者在 PR 中明确标注修复了哪些问题，审查时逐项核对

这样可以避免对同一份代码重复输出完整审查意见的浪费。
