**三、规范完善建议**

| 目标 | 建议的规则/检查点 | 说明 |
|------|-------------------|------|
| **分支命名统一** | - 在 CI 中强制 `gitflow-branch-policy.yml` 只接受 **feature/**、**fix/**、**refactor/**、**docs/**、**test/**、**chore/**、**perf/**、**ci/**、**dependabot/** 开头。<br>- 若出现非规范前缀，自动在 PR 评论中提醒并提供重命名指令（`git branch -m <new>`）。 | 本次 PR 因分支名不合规被阻断，说明规则已生效但缺少自动化提示。 |
| **外部调用统一超时** | - 为所有 Updater IPC/HTTP 调用统一封装 `request_with_timeout(path, timeout=DEFAULT_TIMEOUT)`，并在 **合约检查**（`/v1/check`、`/v1/preflight`、`/v1/update`）使用 **较长**（如 10 s）超时或 **重试** 机制。<br>- 禁止在同一方法内部递归调用 `self._request`，改为独立的 `get_status()` 方法。 | 防止递归导致的 2 s 短超时误报。 |
| **合约实现安全审查** | - **能力声明完整性**：每个能力必须在 `contract.py` 中显式列出 `required_capabilities`、`supported_versions`。<br>- **签名/校验**：合约文件在发布前必须经过 **SHA256** 与 **GPG** 双重签名，CI 中加入 `verify-contract-signature` 步骤。 |
| **脚本与入口文件安全** | - 所有 `*.sh` 脚本必须在文件头声明 `set -euo pipefail`，并对所有外部变量使用 `${VAR:-default}` 进行默认值处理。<br>- 对 `publish_development_deployment.py` 添加 **参数 schema**（如 `pydantic`），并在 CI 中运行 `python -m pyflakes` / `ruff` 检查未捕获异常。 |
| **幂等性与资源清理** | - CI 步骤（尤其是 Docker 镜像构建、发布）应在每次运行结束后执行 **资源回收**（`docker system prune -f`），防止残留容器导致后续运行误判。<br>- 合约事务回滚路径必须在单元测试中覆盖（已存在但建议在 `test_deployment_transaction_contract.py` 中加入 **故障注入** 场景）。 |
| **文档同步** | - 在 PR 检查链路中加入 **doc‑diff** 步骤，确保 `README*`、`docs/DEPLOYMENT.md` 中的版本号、能力列表与代码中 `contract.py` 保持一致。 |
| **异常脱敏** | - 所有后端异常返回必须走统一的 **ErrorResponse**，并对 **用户输入错误**（4xx）保留原始信息，对 **内部错误**（5xx）进行脱敏。<br>- 在 `backend/services/updater_client.py` 中加入 `except Exception as e: logger.exception(e); raise UpdaterUnavailableError`。 |

**四、经验教训 & 未来关注要点**

| 教训 | 具体表现 | 后续关注点 |
|------|----------|------------|
| **阻断项必须在审查摘要中突出** | 分支命名违规是阻断项，但只在“主要评论”里出现，若审查者快速浏览摘要可能错过。 | 在审查模板中加入 “**阻断项**” 小节，确保一眼可见。 |
| **递归调用的隐蔽风险** | `UpdaterClient._request` 递归导致短超时误判，且在大量并发请求时可能形成 **递归死锁**。 | 对所有内部调用进行 **调用图分析**（如使用 `pydeps`），发现并阻止同层递归。 |
| **合约/协议变更的全链路影响** | 引入三镜像合约后，涉及 **容器注册表、CI、前端、脚本** 多层面，任何一环不一致都会导致部署不完整。 | 在合约升级时执行 **端到端合约兼容性检查**：<br>1. 生成合约版本清单；<br>2. CI 中跑 **contract‑compatibility** 测试；<br>3. 发布前做 **灰度发布** 验证。 |
| **测试覆盖虽高，但缺少故障注入** | 3270 条通过的测试主要验证“成功路径”。 | 引入 **fault‑injection**（网络延迟、Updater 重启、镜像拉取失败）场景，确保回滚与自愈逻辑被覆盖。 |
| **文档与代码同步不自动化** | PR 中大量文档改动，但未检测文档是否真实反映代码实现。 | 在 CI 加入 **doc‑sync** 检查，使用脚本读取 `contract.py` 中的能力列表并对比文档章节。 |
| **CI 复杂度提升带来维护成本** | 多个工作流相互依赖，修改一次可能触发多处冲突。 | 将 CI 统一抽象为 **可组合的模板**（如 `reusable-workflows`），并在每次改动后自动跑 **workflow‑lint** 与 **dependency‑graph** 检查。 |

### 小结

本次审查成功捕获了两项关键阻断问题，展示了审查对 **流程合规** 与 **代码可靠性** 的价值。但在 **合约实现细节**、**异常处理**、**幂等性**、**文档同步** 等方面仍有盲区。建议在后续审查中：

1. **明确阻断项**，放在审查摘要显眼位置。  
2. **对递归/包装请求** 进行调用图审计，避免隐式超时。  
3. **为合约类变更引入端到端兼容性检查** 与 **故障注入测试**。  
4. **统一超时/重试策略** 与 **异常脱敏**，形成统一的错误处理规范。  
5. **CI 与文档同步检查** 自动化，降低手动漏检风险。

通过上述改进，可进一步提升审查的覆盖度、准确度与整体质量，为项目的长期可维护性奠定更坚实的基础。祝后续迭代顺利！
