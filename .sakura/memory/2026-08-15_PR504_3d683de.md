### 2. 发现的模式

*   **文档与代码的“衰减”模式**：开发者倾向于在 PR 描述或配置注释中记录“设计算式”（如 `pool_size + max_overflow`），但这种算式极易随代码重构而过时。本次发现的问题表明，注释中的逻辑往往不会随代码变动自动更新。
*   **资源调优的“黑盒”风险**：在进行数据库或中间件调优时，参数（如 `max-connections`）的选取往往依赖于开发者对应用侧配置的“认知”。当这种认知存在偏差（如记错 `max_overflow` 值）时，会导致生产环境的“虚假安全余量”。

### 3. 规范完善建议

*   **新增规则：数值计算的“源码溯源”**
    *   对于任何涉及资源配额（连接数、线程数、超时时间）的配置变更，**禁止直接采信 PR 描述或注释中的计算结果**。必须强制在代码库中定位实际定义处（如 `database.py` 中的 `create_engine` 或 `pool` 配置），进行现场反推计算。
    *   *示例*：若 PR 称连接上限为 20，必须搜索代码确认 `pool_size` 和 `max_overflow` 的实际值。
*   **完善检查项：镜像标签与参数版本的强绑定**
    *   在使用特定版本才支持的参数（如 `innodb-redo-log-capacity`）时，审查规则应增加一项：**检查 Docker 镜像标签是否显式固定**（如 `mysql:8.4` 而非 `mysql:latest` 或 `mysql:8`）。虽然本次审查确认了参数有效性，但未明确提及镜像标签的固定性，这是防止未来环境漂移的关键。

### 4. 经验教训

*   **警惕 PR 中的“算术题”**：PR 描述中包含的任何计算逻辑（如“余量约 20”、“内存降低 300MB”）都是高风险区。审查者应将其视为“未经测试的断言”，必须通过代码或配置进行独立验证。
*   **“安全余量”的双重验证**：在审查 `max-connections` 这类上限配置时，不能仅看“当前是否足够”，更要看“文档描述是否准确”。错误的余量描述（如文档称余量 20，实际仅 9）比“没有余量”更危险，因为它会诱导运维人员在后续扩容中做出错误的缩容决策。
*   **基础设施变更的“破坏性”隐蔽性**：关闭 `performance_schema` 虽然是优化手段，但也属于“破坏性变更”（移除了监控能力）。审查中确认了无代码依赖，这很好。未来的审查中，对于此类“减配”操作，应默认触发“依赖检查”，直到证明无消费方。
