### 6. 经验教训与后续建议  

1. **标签体系细化**  
   - 为分支冲突类 Issue 建立专属标签层级（`gitflow/merge-conflict`、`branch-sync`），避免使用笼统的 `other`。  
   - 将阻断性 Issue 标记为 `blocking`，便于在仪表盘中快速定位阻塞 CI 的根本原因。

2. **优先级评估标准化**  
   - 引入 **冲突影响度评分**：① 是否阻塞 CI（+2）② 受影响 PR 数量（+1）③ 是否涉及关键配置/锁文件（+1）。总分 ≥3 则设为 **high**。  
   - 将此评分写入 Issue 模板，自动化生成优先级。

3. **重复检测机制升级**  
   - 使用 **冲突文件指纹**（`git diff --name-only` 的哈希）+ **触发工作流 SHA** 进行匹配。  
   - 在检测脚本中加入 **方向判断**（main→develop vs develop→main）防止误报。

4. **冲突处理流程标准化**  
   - **步骤**：<br>① 在本地创建临时分支 `sync/main-to-develop-<date>`；<br>② 执行 `git merge --no-commit --no-ff origin/main`；<br>③ 解决冲突后运行 `uv sync --locked && pytest`；<br>④ push 到远程并创建 **draft PR**，让 CI 再次验证；<br>⑤ 通过审查后合并至 `develop`。  
   - 将此流程写入 `CONTRIBUTING.md` 或 `SYNC_GUIDE.md`，减少人工记忆成本。

5. **自动化工作流改进**  
   - 当检测到冲突时，**不要直接创建 Issue**，而是自动创建 **draft PR**（带冲突文件列表），并在 PR 描述中附上解决指引。这样可以在 PR 中直接完成冲突解决与 CI 验证，避免 Issue 产生后再手动同步。  
   - 在工作流中加入 **冲突文件输出**（`git diff --name-only`）并通过 `actions/create-issue` 或 `actions/create-pull-request` 进行自动化。

6. **文档与知识库同步**  
   - 对于 `.sakura/` 生成文件的冲突，建议在仓库根目录添加 **生成脚本**（如 `scripts/generate_sakura.sh`），并在 CI 中加入 **生成步骤**，确保每次合并后自动重新生成，降低手动冲突的概率。  
   - 将生成脚本的执行日志保存为 **artifact**，便于事后审计。

7. **沟通与指派**  
   - 建议在 Issue 中明确 **指派人** 与 **预计完成时间**，并在模板中提供 “@maintainer” 自动提醒。  
   - 对于重复 Issue，使用 **“related”** 而非 **“duplicate”**，除非确认两者完全相同。

- **分类**：细化为 `gitflow/merge-conflict` 更合适。  
- **优先级**：因阻塞 CI，建议提升至 **high**。  
- **标签**：保留核心标签，补充 `merge-conflict`、`blocking`，去除冗余 `automated`。  
- **可行性**：估算略乐观，需加入受保护分支、生成文件、CI 再验证的风险。  
- **重复检测**：当前仅凭标题判断不够，建议使用冲突文件指纹进行精确匹配。  
- **标题**：原标题已足够清晰，暂无必要改写。  

通过以上改进，可提升 Issue 处理效率、降低误报率，并让分支同步流程更自动化、可追溯。希望这些反思能帮助维护者快速闭环本次冲突并完善后续工作流。
