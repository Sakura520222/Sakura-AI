## 2. 发现的模式  

### 代码层面  
1. **手写 slug 化**：`backend/services/vector_store.py` 与 `backend/services/code_vector_store.py` 使用 `re.sub` + `hashlib.md5` 实现 collection name 的 slug 化，而不是直接依赖 `python‑slugify`。这说明项目对 slug 的行为有特定需求（如保持哈希），导致库被 **冗余声明**。  
2. **依赖声明与实际使用不匹配**：`python‑slugify` 在整个代码库中 **零调用**，但仍被列入 `pyproject.toml` 与 `requirements.txt`。这是一类常见的“遗留依赖”风险。  

### 架构与依赖管理  
1. **双清单（pyproject & requirements）同步**：项目坚持 `pyproject.toml` 与 `requirements.txt` 必须逐行镜像，这有助于 CI 与 Dockerfile 的统一，但也增加了 **手动同步的出错概率**。  
2. **uv.lock 纳入源码发行**：`uv.lock` 被视为发布产物，意味着锁文件的 **一致性** 对于可重复构建至关重要。当前审查发现锁文件未随依赖升级而更新，提示了在 **依赖升级流程** 中缺少一步自动化（如 PR 模板或 CI 检查）。  
3. **CI 对锁文件的容忍**：`.github/workflows/ci.yml` 直接 `pip install -r requirements.txt`，未使用 `uv sync --locked`，导致锁文件漂移不会导致 CI 直接报错。

- **全库搜索 + 语义搜索**：除了关键词匹配，还应使用语义相似度（如 LLM‑enhanced）捕获间接使用（如 `importlib.import_module('slugify')`）。

## 4. 经验教训  

1. **锁文件漂移是隐形风险**  
   - 即使 CI 不依赖锁文件，发布包仍会携带过时的锁文件，导致 downstream 环境出现不可预期的依赖冲突。审查时必须把 **锁文件同步** 视为 **必检项**，而非可选建议。  

2. **冗余依赖往往隐藏在“无调用”中**  
   - 项目在升级依赖前应先确认 **是否真的在代码中使用**。一次全库搜索即可发现 0 命中，随后可以决定是**移除**还是**保留**（如未来可能用到）。  

3. **双清单维护成本**  
   - 手动保持 `pyproject.toml` 与 `requirements.txt` 同步非常容易出错。推荐使用 **单一来源**（只保留 `pyproject.toml`），在 CI 中通过 `uv export -r > requirements.txt` 自动生成，或在 PR 中加入自动生成脚本。  

4. **审查要兼顾“当前风险”和“潜在风险”**  
   - 本次升级本身风险低，但如果以后引入 `slugify`，当前的 **unused‑dependency** 标记会变成 **breaking‑change**。审查应在建议中注明“**若未来使用，请重新评估兼容性**”。  

5. **审查工具的文件大小限制**  
   - `uv.lock` 超过搜索上限导致审查工具无法直接读取。建议在审查平台上配置 **分块读取** 或 **预先生成摘要**（如 `sha256`），以便在大文件情况下仍能提供验证依据。  

6. **CI 与发布流程的一致性**  
   - CI 使用 `pip install -r requirements.txt`，而发布包使用 `uv.lock`。两者不一致会导致 **“CI 通过、发布失败”** 的情形。统一构建链路（全部使用 `uv sync --locked`）可消除这类差异。
