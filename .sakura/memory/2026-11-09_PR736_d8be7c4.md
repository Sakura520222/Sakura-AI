# 审查反思：PR #736（openai 依赖升级）

## 一、审查质量评估

**做得好的地方**

- **证据分层正确**：主证据为 uv.lock 行号级内容（:1531 锁定版本、:2567 requires-dist），外部 CI 失败仅作“吻合”佐证而非主证据——这一分层避免了将可能与 PR 无关的 CI 噪声升级为定罪依据，值得固化。
- **修复指令精细**：建议 `uv lock --upgrade-package openai` 而非全量 `--upgrade`，防止引入无关依赖漂移，体现了对 uv 生态的准确理解。
- **遗留项分级恰当**：frontend CI 失败无行号级关联证据，未擅自升级为 Major，符合“CI 失败定 Major 须追到行号级证据”。

**覆盖度缺口**

1. **未建议 API 行为核验**：3.41→3.46 跨 5 个 minor 版本，release notes 含 `expand agent turn errors`、WebSocket 进度累积等可能影响 Provider 层错误处理语义的变更。声明一致 ≠ 行为兼容，应附加“运行 provider 层测试”作为建议或追踪项。
2. **未覆盖传递依赖扩散**：`uv lock --upgrade-package` 仍可能连带更新 openai 的子依赖（httpx、pydantic 等），修复指令应附加“核验 uv.lock diff 中传递依赖变更范围”。
3. **阻断类型标签缺失**：本次为确定性“缺陷型阻断”（有行号证据），摘要未显式区分于“证据待补型”，评分 5/10 可能被误读为质量恶化。

**准确度与完整性**：Major 分级与 request_changes 正确——合并后 `uv sync --locked` 确定性失败；对“Dependabot 自动升级”意图的理解到位。

## 二、发现的模式

- **代码模式**：Dependabot 同步 pyproject.toml + requirements.txt 但漏 uv.lock，是三重声明架构下的高频重复模式。本次是既有“依赖三要素”规则的**正确执行**，非新发现。
- **架构观察**：Windows uv 冒烟 CI 含锁文件一致性检查且失败与漂移吻合，说明 CI 防线已生效，但防线位置滞后于提交阶段；多平台 CI 并存时，需甄别哪条失败与本 PR 有因果。

## 三、规范完善建议

1. **Dependabot PR 前置快查模板化**：凡 Dependabot 依赖 PR，第一步固定核验变更文件列表是否含 uv.lock，不含即触发三重一致检查，跳过深层 diff。
2. **版本跳跃幅度附加检查**：跨 ≥3 个 minor 版本的升级，须附加受影响 provider 层的测试核验建议。
3. **锁文件修复指令须含子依赖核验**：单包升级后核验 diff 中传递依赖变更，必要时加约束钳制。
4. **防线前移建议**：依赖三要素规则已多次命中，建议向作者提议在 CI 加 `uv lock --check` 步骤，将拦截从审查阶段前移到提交阶段。

## 四、经验教训

1. **“改动正确”≠"PR 可合并”**：2 行 diff 本身无误，但原子性约束使其不可合并——评分反映的是可合并性而非 diff 质量，5/10 与阻断决策自洽。
2. **佐证与主证据须分层**：CI 失败（可能 flaky）作佐证、锁文件内容（确定性）作主证据的举证结构，应固化为依赖类审查标准动作。
3. **“吻合”措辞需谨慎**：CI 失败与漂移是高概率关联而非因果证明，措辞可用“根因高度可能”；结论不受影响时不必改变定级。
4. **遗留项须有生命周期**：frontend CI 失败若下轮确证与 Python 依赖无关，应显式
