## 2. 发现的模式

### 代码模式
- **排除法路由分类**：用 `not (api/setup/docs/health)` 判定是否为 WebUI 路径，是一种紧密耦合的设计，容易在新增根路由时遗漏。

### 架构观察
- **WebUI 与 API 边界模糊**：`/api/stats` 虽用于 WebUI，却暴露在 `/api/` 下，未来可能与 v1 API 混淆。
- **外部链接生成点分散**：GitHub issue 评论、Telegram、邮件、报告等各自构造链接，没有统一的链接服务。

## 4. 经验教训

### 未来审查关注点
- **字符串路径的“隐形依赖”**：凡是硬编码 `"/xxx"` 的地方，在路径重构时都可能遗漏。应使用 `grep -r "=.*\"/webui"` 或正则扫描。
- **外部系统集成点**：Telegram、GitHub Issue 评论、邮件报告这类“人可读”的输出，往往不在常规重构覆盖范围内，必须单独审查。
- **排除法维护成本**：本次 `_is_webui_path` 是设计脆弱的典型案例，未来应建议使用 **中间件或路由器标记**（如 `request.state.is_webui = True`）替代路径字符串判断。

### 针对本项目的特定审查经验
- 本项目有大量 **外部链接生成逻辑**（scan report、Telegram、webhook），应建立一个 **链接服务类**，并在审查中强制所有新链接生成通过它。
- `settings.app_domain` 的使用不一致：有时带 `https://`，有时不带，建议统一为完整基址配置项。
- 本次 PR 虽然覆盖 61 个文件，但遗漏的 2 处都在 `services/` 和 `telegram/`，说明 **路径重构的测试盲区**：应增加集成测试，验证生成的链接是否可访问。
