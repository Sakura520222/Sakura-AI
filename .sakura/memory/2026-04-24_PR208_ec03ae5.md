## 2. 发现的模式

### 代码模式
- **配置三层穿透**：`Settings` → `yaml_config` → 硬编码默认值，本次新增打破了第一层
- **fire-and-forget 标准范式**：`create_task` + `add_done_callback(discard)` + 实例级 set 持有引用
- **反思流程模板化**：init → read → prompt → LLM → commit → state → merge_check，六步固定

### 架构观察
- `SakuraMemoryService` 承担职责过重（配置、prompt、LLM、状态、文件），符合"错误处理策略分裂"高危区特征
- Worker 层是纯触发器，不持有反思逻辑——优点是解耦，缺点是异常边界完全依赖 Service 内部

## 3. 规范完善建议

### 新增规则

**R1: 纯可读性封顶规则**
> 不涉及功能、安全、数据完整性的可读性问题，严重程度封顶为 `suggestion`。包括但不限于：表达式嵌套、变量命名、局部导入位置。

**R2: 自评矛盾自动降级**
> 评论正文出现以下表述时，对应标签自动降级一级："非安全用途"、"影响极小"、"风险可控"、"理论上"、"虽然功能正确"。

**R3: 模式复制差异清单**
> 复制既有模式时，必须显式列出与原模式的**所有差异点**及各自理由。未列差异点视为遗漏。

### 修改规则

**"三问法强制绑定"强化**：当前规则要求内联三问答案，但未定义"答案不合格"的后果。建议增加：
> 三问中任一答案为"无"或"不涉及"时，该问题自动降级为 `minor`。

## 4. 经验教训

### L1: 评论去重执行失败
主评论区配置 fallback 和 f-string 各出现**两条重复 major 评论**，直接违反"同位置不同表述必须合并为一条评论"。根因：摘要生成与评论生成解耦不彻底，建议在输出模板层增加位置去重校验。

### L2: "已有模式"不等于"可接受"
shutdown 风险被降级为 minor 的理由是"与 reflect_pr 完全一致，属于已有模式"。但项目记忆明确警告"错误处理策略分裂——单PR无法根治须升级为技术债务决策"。正确做法：标为 warning 并归档为技术债务，而非降级为 minor 默默放过。

### L3: 防御代码复制须验证必要性
审查肯定了"防御性编程充分"，但未质疑：Issue 反思场景是否真的需要与 PR 反思同等强度的防御？如果 Issue 数据来源（GitHub API）比 PR 分析结果更结构化，部分 try/except 可能是防御过度。这属于"模式复制焦点转移"的适配性维度。

### L4: 增量审查的边界感
作为首次全量审查，对 fire-and-forget 的 shutdown 问题提出是合理的。但表述上应区分"本次引入的问题"和"本次暴露的已有问题"，避免给 PR 作者造成"只改这点却背所有锅"的错觉。
