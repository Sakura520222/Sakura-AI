## 6. 经验教训与后续关注点  

| 经验点 | 说明 |
|--------|------|
| **统一的取消机制** | 项目已经为 PR 实现了完整的取消链路，Issue 需要复用同一模式（`_cancel_events` + `finally` 清理）。后续若再引入新异步任务（如 `branch_worker`），应提前在 **抽象层**（如 `BaseWorker`）提供统一的取消注册/撤销接口，避免重复实现。 |
| **状态枚举同步** | 新增 `CANCELLED` 枚举后，必须在 **后端模型、前端模板、过滤器、i18n、SSE** 等多处同步。建议在添加枚举的同时，编写 **脚本** 自动搜索并更新对应文件，降低遗漏风险。 |
| **幂等与并发** | 同一 Issue 可能会有多个分析任务排队（不同版本、不同分支），取消时要决定是**全部取消**还是**仅当前执行的**。建议在任务注册表中记录 **唯一任务 ID**，并在 webhook 中使用 `repo#issue` 进行批量撤销，确保幂等。 |
| **资源浪费监控** | 该需求本质是防止 **无效 token 消耗**。实现后可在监控仪表盘（Prometheus / Grafana）加入 `issue_analysis_cancelled_total` 指标，帮助评估实际节省的配额。 |
| **测试覆盖** | 参考 `tests/test_review_worker_timeout.py` 与 `test_webhook_auto_review_toggle.py`，为 Issue 取消新增：<br>1. 正常关闭后任务被取消的单元测试。<br>2. 删除后任务被取消的集成测试。<br>3. 并发关闭/删除的竞争测试。 |
| **文档与用户指引** | 在项目文档的 **Issue 分析**章节加入 “关闭/删除会自动取消分析” 的说明，防止用户误以为需要手动取消。 |
| **错误处理** | 取消过程中若出现 `asyncio.CancelledError` 之外的异常，需要统一包装为 `IssueAnalysisError` 并记录日志，防止异常导致任务卡死。 |

- **分类**正确，**优先级**建议提升至 `high`。  
- **标签**需去除 `automated`，补充 `backend`、`cancellation`、`resource‑management`、`needs‑test`。  
- **可行性**评估总体准确，但工作量略低估，需细化任务拆分并考虑幂等性、资源清理风险。  
- **重复检测**可靠，暂无冲突。  
- **标题**可改写为更具描述性的形式。  
- **经验教训**强调统一取消机制、枚举同步、并发幂等、监控指标、完整测试以及文档同步。
