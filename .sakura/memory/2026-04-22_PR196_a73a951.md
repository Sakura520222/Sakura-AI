## 2. 发现的模式

### 代码模式
- **双路径解析模式**：emoji格式与JSON格式并行，但输出格式未对齐——这是本次问题的核心根源
- **配置字段同步陷阱**：新增字段需要同步4处（配置文件、默认值、解析器赋值、合并模板）

### 架构观察
- `result_parser` 承担过多职责：格式识别 + 字段提取 + 路径生成
- `batch_processor` 与 `result_parser` 存在隐式耦合：合并模板需要感知解析结果的内部字段结构，无接口约束

## 3. 规范完善建议

### 新增规则
1. **双路径一致性规则**：同一功能存在多条代码路径时，输出格式差异必须量化下游影响，否则降级为suggestion
2. **配置字段同步检查清单**：新增配置字段时必须显式检查：①配置文件定义 ②默认值/回退值 ③所有赋值路径（含except分支） ④所有消费方（含序列化模板）
3. **摘要严重性对齐**：评论含major时，摘要禁止使用"不影响""不影响核心功能"等降级表述

### 修改规则
- **三问法增强**：增加第④问"影响范围"——单条记录级 vs 批量级 vs 全局级
- **评论拆分原则**：一个问题点涉及多个独立缺陷时，必须拆分为独立评论

## 4. 经验教训

### 本次核心教训
1. **except分支是"影子正常路径"**：异常处理不是角落，而是第二条正常路径，必须与主路径行为对齐
2. **配置同步是分布式一致性问题的微缩版**：每新增一个消费方，同步复杂度线性增长
3. **合并逻辑是隐藏的状态机**：batch合并不是简单拼接，需要维护与单次处理等价的状态契约

### 技术特定经验
- JSON解析引入后，原有的emoji解析路径容易成为"二等公民"——新路径完善、旧路径退化
- 测试"覆盖了新路径"不等于"覆盖了双路径一致性"
