## 深度反思

### 1. 审查质量评估

**覆盖度：存在结构性盲区**

审查对 branch 参数的全链路传播和 per_file 路径的逻辑验证做得扎实，但存在明显盲区：

- **重构等价性未验证**：file_tool.py +223/-106、search_files_tool.py +153/-40 是大幅重构，审查几乎全部聚焦于 branch 新功能，未检验重构是否改变了已有路径的边界行为（如异常类型、返回值结构、错误消息）。这违反了项目记忆中"正确语义≠安全变更"的原则——重构可能改变某些调用方隐式依赖的"错误行为"。
- **constants.py 变更被跳过**：+22/-1 的配置扩展未逐项验证消费方，可能存在死常量。
- **`_ContentsFetchResult` 字段集一致性**：项目记忆明确要求"早返回路径字段集一致性：多早返回同构字典时主动对比字段集"，审查表扬了该封装但未执行字段集对比验证。

**准确度：评分偏高**

9/10 与实际检查深度不匹配。存在一个完全未测试的新方法（`_dispatch_search_round`）和一段核心检测逻辑（ref-inaccessible, lines 391-409）无覆盖，按项目记忆"高评分=穷尽检查点"的标准，8/10 更诚实。此外，项目记忆警告"suggestion vs major 锚定效应"——但反向锚定同样危险：高分削弱了 suggestion 的跟进紧迫感。

**完整性：功能视角完整，工程视角不足**

对 branch 功能的意图理解到位（非 PR 场景的 Issue 分析），但对"重构内部结构"这一 PR 描述的一半内容缺乏工程级审视。

### 2. 发现的模式

- **Result 元数据封装模式**：`_ContentsFetchResult` 将 requested/used/tried/error 打包，使上层无需重复判断分支状态——这是该项目的典型模式，值得作为后续审查的预期基线。
- **双路径搜索架构**：per_file 与 Search API 两条路径共存，测试仅覆盖一条，这是项目中持续存在的覆盖缺口风险点。
- **Fallback 链设计模式**：PR HEAD→base → 非PR branch→default → 全失败，每层有明确的触发条件和退出判断，设计合理但测试只覆盖了前两层。

### 3. 规范完善建议

**新增规则：**

1. **重构+功能混合 PR 的双轨检查强制化**：当 PR 同时包含重构和新功能时，摘要中必须分两个小节——"新功能验证"和"重构等价性验证"，后者须至少声明：(1) 已有测试是否全部通过 (2) 重构前后返回值结构是否一致 (3) 异常处理路径是否等价。缺少任一项标 minor。

2. **新增未测试方法/路径的评分硬上限**：新增的 public 方法或新增的分支路径如果零测试覆盖，评分上限 ≤8，无论其是否为主路径。当前"覆盖函数≠覆盖行为"是软性提醒，需升级为可执行的评分约束。

3. **constants 变更消费方验证**：constants 文件变更 ≥10 行时，须逐个新增常量 grep 验证存在至少一个消费方，未验证标 minor。

**修改规则：**

- 将"早返回路径字段集一致性"从代码质量建议提升为重构类变更的 **必检项**，缺少字段集对比声明即标 minor。

### 4. 经验教训

1. **"15 个测试"的数字欺骗性**：测试数量多 ≠ 路径覆盖广。本例 15 个测试全部走 `use_search_api: False`，实际只覆盖了一条代码路径。审查时应先画路径树，再标注每个测试落在哪个节点，而非被测试文件行数（+445）制造的安全感误导。

2. **grep 验证的"完成感陷阱"**：确认 branch 参数全路径传播后容易产生检查完成的满足感，但这只是参数传播一个维度。应将 grep 验证视为"入场券"而非"终点线"。

3. **PR 描述的权重应均分**：描述声称"重构内部结构、增强配置项、新增测试用例、适配调整"四件事，审查精力应大致按变更行数加权分配，而非全部倾斜到最"有趣"的功能点上。file_tool.py 的 223 行新增中有多少是纯重构？这部分的质量审查几乎空白。

4. **suggestion 的可追踪性不足**：指出"建议补充 Search API 路径测试"但未建议具体的追踪手段（如 TODO 注释、Issue 引用）。项目记忆明确要求"'未来风险'suggestion 须建议代码追踪手段"，本次审查未遵守。
