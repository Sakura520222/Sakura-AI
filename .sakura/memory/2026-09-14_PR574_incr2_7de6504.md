## 2. 发现的模式  

### 代码模式  

| 模式 | 体现 | 影响 |
|------|------|------|
| **单一来源派生 (Single‑Source of Truth)** | `systemd.py` 通过统一的 `UnitConfig` 生成 Exec、PIDFile、WorkingDirectory 等字段。 | 降低了硬编码风险，便于后续统一修改。 |
| **原子文件写入** | `daemon.py` 使用 `mkstemp` + `os.replace` + `_fsync_directory` 写入 PIDFile。 | 提升了系统断电恢复能力，符合系统级服务的可靠性要求。 |
| **幂等安装/卸载** | `install_service` / `uninstall_service` 对 unit 文件、链接、残留文件做了存在性检查与清理。 | 防止残留状态导致后续部署失败。 |
| **脚本模式切换** | `start.sh` 通过 `SAKURA_UPDATER_DEV` 环境变量区分 dev 与 prod，且在 prod 环境强制要求 systemd 可用。 | 明确了开发/生产行为差异，降低误用风险。 |
| **测试覆盖** | 新增 **系统级** 与 **边界** 测试（unit 渲染、fsync 异常、CLI 分发等）。 | 提升了回归安全网，尤其对系统服务的异常路径提供保障。 |

### 架构观察  

1. **模块化守护进程层**：`updater/src/sakura_ai_updater/` 将守护进程抽象为 `daemon`（文件写入、PID 管理）和 `systemd`（unit 生成、安装）两层，职责清晰。  
2. **文档/记忆同步**：项目通过 `.sakura/` 目录记录审查、经验、规则，形成了 **自我驱动的知识库**，有助于团队在迭代中保持一致。  
3. **依赖双清单**：`pyproject.toml` 与 `requirements.txt` 同步维护，体现了对 **多环境（pip/uv）** 的兼容需求。  
4. **CI 与部署脱钩**：虽然测试已覆盖新功能，但 CI 仍使用 `requirements.txt`，而发布可能走 `uv lock`，这在架构层面仍是潜在不一致点。

## 3. 规范完善建议  

| 现有规则 | 建议新增/修改 | 目的 |
|----------|--------------|------|
| **dependency_upgrade_review_enhancements.md**（已新增） | 增加 **“锁文件同步检查”**：在 PR 中强制运行 `uv lock --check` 或 `pip freeze > requirements.txt` 并对比差异。 | 防止依赖升级后锁文件漂移导致发布失败。 |
| **lockfile_dependency_rules.md** | 明确 **“CI vs Release 使用同一锁文件”**：CI 必须使用 `uv sync --locked`，且 CI 运行前检查 `requirements.txt` 与 `uv.lock` 是否一致。 | 保证 CI 与实际发布环境保持一致。 |
| **systemd integration**（暂无专门规则） | 新增 **“systemd unit 渲染安全规则”**：<br>1. ExecStart 参数必须经过 `shlex.quote` 或等价转义。<br>2. Unit 文件路径只能位于受信任目录（如 `/etc/systemd/system`、`/usr/lib/systemd/system`）。<br>3. 安装/卸载必须是幂等的，并在失败时回滚已创建的文件。 | 防止恶意路径注入、确保部署可恢复。 |
| **异常路径测试** | 要求每个新增功能至少提供 **一次异常路径的单元测试**（如 `os.replace` 抛异常、`systemctl daemon-reload` 失败等）。 | 提升系统级服务的容错能力。 |
| **文档同步检查** | 引入自动化脚本，检测 `README*`, `docs/*` 中的依赖约束是否与 `pyproject.toml` / `requirements.txt` 匹配。 | 防止文档与实际代码不一致导致使用者误导。 |

## 4. 经验教训  

1. **增量审查不等于安全审查**  
   - 本次 PR 通过增量审查快速获得 10 分，但若仅看增量（systemd 代码），容易忽视 **跨文件的全局一致性**（如锁文件、CI 配置）。建议在大幅增量时加入一次 **全库依赖一致性检查**。  

2. **系统服务改动必须验证恢复路径**  
   - PIDFile 的原子写入已实现，但 **systemd unit 安装失败后的清理** 仍需在测试中覆盖。未来审查应关注 “安装成功 → 卸载成功” 的完整闭环。  

3. **文档/记忆库的价值**  
   - 项目通过 `.sakura/` 记录审查反思，极大提升了团队知识沉淀。保持这种 **结构化记忆**，并将其纳入审查检查（例如要求每次关键改动必须更新对应记忆文件）。  

4. **安全转义不可忽视**  
   - `systemd.py` 直接拼接 Exec 参数，虽然当前路径校验较严，但若后续加入环境变量或用户输入，转义漏洞容易出现。审查时应明确要求使用安全拼接工具（`shlex.quote`、`subprocess.list2cmdline`）。  

5. **测试覆盖的层次化**  
   - 本次新增了 **unit、integration、lifecycle** 三层测试，验证了不同抽象层的行为。保持这种层次化的测试策略，可在以后功能重构时快速定位缺陷。

## 5. 增量审查反思  

| 增量提交 | 是否解决了前轮审查问题 | 是否引入新风险 | 审查覆盖度变化 |
|----------|----------------------|----------------|----------------|
| **依赖升级**（第1轮） | 已确认无锁文件漂移、无 Dockerfile/CI 冲突。 | 无新增风险。 | 仅针对两处文件，覆盖度高。 |
| **systemd 重构**（第2轮） | 解决了之前“守护进程仍使用手动 PIDFile” 的可维护性问题。 | 引入 **systemd 单元渲染与安装** 的新攻击面（路径注入、单元文件残留）。 | 增量审查重点转向 `updater/src/`，对 `tests/`、`docs/` 的覆盖也随之扩大，但对 **CI/锁文件同步** 的检查被削弱。 |

**总体反思**：  
- 增量审查在处理大规模结构性改动时，需要 **补充一次全局一致性审查**（依赖、CI、文档）。  
- 对于系统级改动，除了代码审查，还应加入 **运行时安全检查**（如在 CI 中启动临时 systemd 环境进行 smoke test）。  
- 通过本次经验，可以将 **“增量审查 + 全局一致性验证”** 设为标准流程，以兼顾效率与安全。

--- 

**总结**：本次审查在快速捕捉关键改动、确认兼容性与文档同步方面表现优秀，但在全局依赖锁文件、一致性验证以及系统服务安全细节上仍有提升空间。通过上述规则补充与审查流程优化，可在后续增量 PR 中保持高效且安全的审查质量。
