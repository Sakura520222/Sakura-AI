**4. 经验教训**  

1. **安全改动必须配合风险分级**：即便改动只有几行代码（如解析函数），其 **攻击面** 可能极大，审查时应主动提升风险等级。  
2. **增量审查不等于风险消除**：只看新增提交容易忽视 **历史遗留引用**，尤其是配置键或异常类的删除/重命名。全库搜索是必不可少的补充。  
3. **负向路径测试是安全审查的核心**：本次 PR 已加入异常/空值测试，值得在所有安全相关改动中强制要求。  
4. **双写一致性需要原子化**：单纯在成功后手动清理内存回退并不保证在并发环境下不留下残余，建议使用事务或锁。  
5. **CI 变更必须自检**：在 CI 中加入 **包装清单校验** 与 **性能基准**，可以在合并前捕获遗漏的资源或性能回退。

**5. 增量审查反思**  

| 关注点 | 本次增量是否满足 | 潜在风险 |
|--------|----------------|----------|
| **前轮提出的问题** | - ReDoS 风险已通过前向扫描解决。<br>- Token 失效漂移通过显式 `expires_at` 修复。 | - 未检查 **其他服务**（如 `announcement_service`）是否仍调用旧的图片解析函数。 |
| **新引入的风险** | - 新的解析代码在极端输入下的 **时间复杂度** 已有测试，但缺少 **性能基准**。<br>- `_FallbackBinding` 的清理逻辑在高并发下可能出现 **竞态**（两个线程同时删除同一 digest）。 | - 需要在 CI 中加入并发模拟或使用 Redis Lua 脚本保证原子性。 |
| **审查覆盖度** | 只审查了改动文件，未进行 **全库引用搜索**，导致潜在的 **KeyError**、**未更新的文档** 可能被忽略。 | - 建议在增量审查后立即跑一次全库搜索，尤其针对 `expires_at`、`telegram_bind_token_expire_seconds` 等配置。 |
| **回归验证** | 未在审查报告中提供 **全链路回归**（如公告、沙箱、身份）对应的 **集成测试** 结果。 | - 可能出现 **兼容性** 问题，导致旧数据/旧客户端在新版本中异常。 |

**总体反思**：本轮增量审查成功验证了核心安全改动，但因仅聚焦改动文件，导致 **全局影响** 与 **并发安全** 的检查略显不足。后续增量审查应在 **代码层** 与 **全局搜索** 两个维度同步进行，并在 **CI** 中加入 **性能基准** 与 **并发原子性** 检查，以实现真正的“安全‑可靠‑可回滚”闭环。
