### 4. 经验教训

**值得未来关注的要点**：
1. **SQLAlchemy 表达式的 truthy 陷阱**：不仅 `or_()`，`and_()`、`not_()` 同样可能触发 `__bool__` 警告。建议全项目扫描所有 `if` 条件中的 SQLAlchemy 核心表达式。
2. **历史债务的“降温”现象**：当同一个问题被标记多轮且未修复时，审查者可能无意识地降低其严重度感知。需强制在每次审查输出中高亮“债务存活轮数”。
3. **增量审查的“隧道视野”**：本次审查完全聚焦于 `build_review_search_filter`，但未检查 `issues.py` 中的内联 `if search:` 模式是否也应统一为 `is not None`（虽不属同一函数，但逻辑相似）。建议增加“相似模式嗅探”步骤。

**对特定技术/模式的审查经验**：
- **单例并发污染**：审查时若发现 `self.xxx = ...` 后在同一实例的多个方法中被读取，需确认实例是否被复用（如 FastAPI 依赖缓存）。最佳实践：使用 `Depends` 每次返回新实例，或使用 `contextvars`。
- **finally 清理路径**：当 try 块内有 `return`/`break`/`continue` 时，finally 总会执行。但若清理逻辑在 else 中，则异常/提前返回时不会执行。审查时需绘制控制流图。
