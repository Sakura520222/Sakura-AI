## 2. 发现的模式

### 代码模式
本仓库呈现出几个明显模式：

1. **以 GitHub Check Run 作为审查状态机核心载体**  
   状态流转、清理、并行控制都围绕 Check Run 展开，说明它不仅是展示层，还是流程控制层。

2. **用命名/标识区分逻辑分支**  
   例如 `webhook-incremental`、`review_job_id`、`external_id` 这类字段承担了关键路由职责。  
   这类设计优点是轻量，缺点是：**一旦标识约定不统一，就会出现误收敛、误取消、重复创建等问题**。

3. **测试偏向场景驱动**
   当前单测明显围绕“占位收敛”“并行保留”这类行为场景编写，说明项目更依赖行为回归测试而不是纯单元边界测试。

### 架构观察
从依赖图看，项目是典型的 **Webhook → Worker → Service → Check Run** 链路驱动架构：
- `webhook.py` 负责事件入口；
- `review_worker.py` 负责执行与状态推进；
- `github_app.py` 和 `check_run_service.py` 负责 GitHub 交互与状态收敛；
- 配置、数据库、CI failure 逻辑围绕这一主链路扩展。

这类架构的优点是职责分层清晰；  
但风险也很典型：
- **状态分散在多个节点**，任何一处“推断状态”的代码都可能与真实状态不一致；
- 并发和重试会放大边界问题；
- 需要特别关注“幂等性”“唯一标识”“状态收敛”三者的一致性。

## 3. 规范完善建议

### 建议新增/修改的审查规则
1. **Check Run 清理逻辑必须声明唯一匹配条件**
   - 例如：按名称、external_id、workflow/source 标签还是 metadata 组合匹配；
   - 审查时若仅凭单一字符串常量识别，需标记为“易回归边界”，至少列为 minor 观察项。

2. **并行执行类修复必须覆盖“保留对象”测试**
   - 不仅要测“该删的删掉”，还必须测“相似但不该删的必须保留”；
   - 对状态收敛类代码，建议形成固定测试模板。

3. **增量审查必须显式声明“非本次增量但相关的边界风险”**
   - 尤其当前一轮 major 已修复，本轮容易只看 diff；
   - 对“历史遗留风险是否已完全关闭”要有一句明确结论，避免隐性漏检。

4. **状态机类逻辑要求审查“逃脱路径”**
   - 检查：异常、重试、重复 webhook、并行执行、超时清理；
   - 这些路径一旦缺失，通常不是功能 bug，而是流程性 bug，更难发现。

### 项目特有的规范要点
- `review_job_id`、`external_id`、Check Run 名称之间的关系应形成文档化约定；
- 占位 Check 的命名与标识应避免仅靠人类可读字符串判断；
- 所有“清理 stale 状态”的函数都应具备幂等性说明；
- 对 webhook 场景建议保留“重复事件/乱序事件”回归测试集。

## 4. 经验教训

### 未来审查要关注的要点
- **代码越“像修复”，越要检查它有没有引入新的选择性副作用**；
- 对清理逻辑，必须反向思考：  
  “除了删错，还有没有删不掉、重复删、删后又被重新创建的问题？”
- 对并行流程，最危险的不是单点失败，而是**状态被错误归并**。

### 技术/模式审查经验
- 当一个修复从“广泛误伤”收敛到“只保留某个特定占位对象”时，应该立刻考虑：
  - 这个特定对象是否真的足够稳定；
  - 未来是否还有第二种占位对象；
  - 是否应该从“命名判断”升级为“显式类型/标签判断”。

这类经验在 GitHub App、CI、webhook 驱动系统里尤其重要。
