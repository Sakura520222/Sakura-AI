## 深度反思

### 1. 审查质量评估

**覆盖度：存在两个结构性盲区**

- **实例缓存的跨切面属性未审视**：`_check_run_ids` 作为实例级 dict，引入了隐式状态。审查覆盖了缓存命中/失效/终态清除的正常路径，但完全未评估：(1) 服务实例生命周期——若是长生命周期单例，缓存是否会无限增长；(2) 线程安全——多 worker 并发访问同一实例时 dict 的竞态风险。增量视角下这类"非 diff 可见"的架构副作用最易遗漏。
- **report_failed 修复的副作用未验证**：审查确认移除了 `error_message` 参数解决了泄露问题，但未追问：移除后 debug 日志现在记录什么？如果改为记录异常对象本身（`exc_info=True`），则修复有效；如果日志语句被整体删除或改为记录其他内容，则丧失了排查能力。这是"确认问题消失"但未"确认替代方案完备"的典型遗漏。

**准确度：合理**

两个 minor 判定准确。`finalize` 遗漏有自愈路径（update 失败 → 清缓存 → 回退），不会造成数据丢失或状态卡死，一次多余 API 调用确实是 minor 级别。README 残留引用属文档一致性，minor 合理。

**完整性：良好，有一处声明矛盾**

摘要声明"未重新验证前序 incr 中已通过的 prompt_builder 和 config 链路"，符合增量规范。但**历史审查上下文**中仍写着"report_failed 敏感信息泄露问题持续存在，至今未被处理"——与本轮摘要中"解决了上轮审查标记的敏感信息泄露风险"直接矛盾。说明历史上下文的生成时机或更新逻辑存在滞后，可能误导后续轮次。

### 2. 发现的模式

**代码模式：终态枚举不完整是高频陷阱**

`report_completed` 和 `report_failed` 正确传递了 `finalize=True`，但 `report_cancelled` 和 `report_skipped` 遗漏。模式清晰：开发者沿着"主路径"（成功/失败）添加优化参数时，容易遗漏"旁路终态"（取消/跳过）。这与状态机审查中"每个终态都需验证"的原则完全对应。

**架构观察：缓存的隐式生命周期契约**

`_check_run_ids` 缓存的有效范围隐含假设为"单次审查周期"，但这个契约没有在代码中显式表达（无注释、无生命周期钩子、无 TTL）。它完全依赖调用方按正确顺序调用 queued→progress→completed 来维持一致性。这是一种脆弱的隐式契约。

### 3. 规范完善建议

**新增规则：**

- **"布尔标志参数全路径传播验证"**：当为底层方法新增布尔控制参数（如 `finalize`）时，必须 grep 所有调用该底层方法的上层入口，逐个判定是否需要传递该标志。禁止仅验证"修改过的调用点"。
- **"实例缓存生命周期显式声明"**：引入实例级缓存时，审查须要求：(1) 缓存有效生命周期的显式声明（注释或文档）；(2) 与对象实际生命周期的匹配验证；(3) 长生命周期场景下的内存增长风险评估。
- **"软引用对称删除"**：删除文件时，除代码引用外，必须 grep README、CHANGELOG、文档索引等"编译器不报错的软引用"。

**修改现有规则：**

- 在"状态机逃脱路径"中补充：**缓存作为新增的状态层，同样需要逃脱路径验证**——包括 worker crash 后缓存丢失的恢复、服务重启后缓存空的冷启动行为。

### 4. 经验教训

- **"修复引入的参数传播是新的出错面"**：缓存机制本身的逻辑可以正确，但其控制信号（`finalize`）的传播是独立的问题面。审查优化类变更时，不能只看优化核心逻辑，必须把"优化控制参数的完整传播"作为单独的检查项。
- **"删除操作的引用追踪不能只看代码"**：代码引用有编译器/测试兜底，但 README 中的 markdown 链接没有。删除文件时"软引用"的遗漏率远高于"硬引用"，应作为固定检查步骤。
- **"确认问题消失 ≠ 确认修复完备"**：验证安全修复时，不能只确认"坏的被移除"，还要确认"好的替代方案到位"。移除 error_message 后，日志排查能力是否仍然存在？

**增量引入的新风险：**

实例缓存的线程安全和生命周期问题在本轮完全未被触及。如果 `CheckRunService` 是单例且多 worker 共享（常见于 async 框架），`_check_run_ids` 的并发读写存在数据竞争风险。这在全量审查中更容易被"服务实例化方式"这一上下文触发。

**覆盖度下降分析：**

增量视角导致审查聚焦于"缓存是否正确工作"，而忽略了"缓存在什么环境下工作"。实例缓存将状态从无状态服务变为有状态服务，这是一个架构级变更，但因为它只体现在几行代码中，增量审查容易将其视为"局部优化"而非"架构变更"。**判断标准应是：是否引入了跨请求的状态持久化，而非变更行数。**
