# 代码审查深度反思

## 1. 审查质量评估
- **覆盖度（严重不足）**：审查完全被限制在了 2 行文本的 diff 中，忽略了历史上下文中明确指出的两个**严重架构缺陷**（单例线程安全、多文件非原子提交）。在核心隐患未消除的情况下给出 `approve`，属于严重的覆盖度缺失。
- **准确度（极高）**：对这 2 行 Prompt 改动的定性非常精准。准确识别出了 LLM 容易将 `{}` 误解为字面量符的痛点，对 Prompt 工程细节的把控能力很强。
- **完整性（割裂）**：缺乏全局视角。本次审查将单次提交从整个 PR 中孤立了出来，没有意识到“一个完美的微调不能抵消底层架构的裂缝”。

## 2. 发现的模式
- **代码模式**：典型的 Prompt 防御性编码。通过将格式占位符 `{xxx}` 转化为自然语言指令“在此输出…”，消除 LLM 对元字符的歧义理解，这是处理复杂 Prompt 模板的优秀实践。
- **架构观察**：`sakura_memory_service.py` 是一个典型的“上帝服务”，承载了核心逻辑和 Prompt 模板管理。历史上下文表明，与之协同的 `github_write_service.py` 存在设计缺陷，导致两者组合使用时存在数据一致性风险。

## 3. 规范完善建议
- **新增规则：历史阻断机制**：在增量审查（尤其是 quick 模式）中，**必须强制加载历史审查上下文**。若历史上下文中存在未闭环的 `error` 或 `critical` 级别问题，无论当前增量改动多么微不足道或完美，决策必须锁定为 `request_changes` 或 `comment`，禁止 `approve`。
- **完善规范：大 PR 的拆分审查原则**：当一个 PR 包含大量基础架构变更（如本 PR 新增 735 行核心服务），后续追加的小修补（如本次的 Prompt 微调）不应作为放行整个 PR 的依据。

## 4. 经验教训
- **警惕增量审查的“隧道视野”**：只看 diff 是最危险的审查方式。Diff 只是局部切片，审查者必须在大脑中重构出完整模块的运行状态。
- **Prompt 审查经验沉淀**：在审查涉及 LLM 的代码时，需建立对 Prompt 中特殊符号（如 `{}`、`[]`、`<tag>`）的敏感度。Python 的 `.format()` 占位符与 LLM 的指令遵循之间存在天然的冲突，应作为常规检查项。

## 5. 增量审查反思
- **问题解决情况**：本次增量 **0% 解决** 历史问题。线程竞态和非原子提交这两个高危风险依然原封不动。
- **新风险引入**：无。纯文本描述修改，无逻辑变更，无新风险。
- **覆盖度下降表现**：审查质量出现了断崖式下降。从代码逻辑审查退化为语文层面的文本校对。**评分 9/10 和决策 approve 在此语境下是失真的**，它反映的是“这 2 行文本改得好”，而不是“这个 PR 可以合并”。这会导致项目带着技术债务上线。
