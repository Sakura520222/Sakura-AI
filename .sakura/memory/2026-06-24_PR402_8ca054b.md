# 深度反思：PR #402 增量审查队列机制

## 1. 审查质量评估

### 覆盖度：存在明显的"重心偏移"盲区

审查对增量队列、Worker、Reviewer 等"大块新增"覆盖充分，但对以下区域存在明显遗漏：

- **小变更文件集体失声**：`api_client.py`(+5/-1)、`pr_service.py`(+1/-7)、`pr_analyzer.py`(+7/-7)、`pr_dependency_graph.py`、`pr_summary.py`、`prompt_builder.py` 等共计 6 个文件、约 30 行变更，在 FINDINGS 中完全无体现。尤其是 `pr_service.py` 删除了 7 行——删除了什么行为？是否有调用方依赖？未做任何追溯。
- **新表索引缺失审查**：`PRReviewIncrementalQueue` 新增 37 行表定义，但审查未验证索引是否覆盖了队列服务中的查询模式（如 `find_active_review` 的 WHERE 条件）。无索引的队列表在生产负载下会直接退化。
- **数据库迁移策略未问**：新表如何创建？是否需要 migration？与现有部署流程的兼容性完全未提及。

### 准确度：webhook 异常兜底严重程度偏低

`webhook.py:398` 的 `enqueue_from_webhook` 无异常兜底被标为 `minor`，但实际影响是：**DB 故障时 synchronize 事件的增量更新静默丢失，既不入队也不触发新审查**。对于一个代码审查系统，"推送了新 commit 但审查不更新且无任何错误信号"属于核心价值链上的静默失败，应至少为 `major`。这里存在"代码改动小 → 严重程度低"的惯性误判。

### 完整性：PR 描述与实际变更的重大偏离未被捕获

PR 描述说的是"enhancing configuration options for AI service calls, optimizing performance, refining handling of tool calls"——给人一种小优化 PR 的印象。但实际变更是**引入完整的增量审查队列机制、僵尸检测、Webhook 集成重构、Worker 状态机扩展**，属于架构级变更。这直接违反了"PR 描述与 diff 一致性强制校验"原则，审查未标出此问题。

## 2. 发现的模式

### 代码模式

- **三层防御式规范化**：`_coerce_tool_call_to_dict` → `_normalize_tool_calls_inplace` → `_extract_tool_call_fields`，针对 SDK 对象/dict/字符串（checkpoint 损坏）逐层降级处理。这说明项目中 tool_call 的序列化/反序列化一直是痛点，历史上有过数据损坏。
- **提前创建消除竞态**：将 review record 创建移到代码索引之前，用"存在即锁定"替代"查询后创建"，是经典的竞态修复模式。
- **双分支异常收尾**：`Exception` 和 `CancelledError` 分别处理但都更新状态为 FAILED，说明之前有过僵尸 review 的生产事故。

### 架构观察

- **事件驱动链路**：Webhook → Queue → Worker → AI Reviewer，状态分散在 DB 表和内存中，状态一致性是核心风险点。
- **双模型架构**：存在 `summary_model` 和主 `model` 的区分，本次将 ContextCompressor 从 summary 切到主 model，这是一个成本维度的架构决策变更。
- **Activity Checkpoint 作为"会话持久化层"**：`load_messages`/`copy_messages_to_session` 表明 checkpoint service 承担了跨 review 实例的会话 continuity 职责，职责边界需要关注。

## 3. 规范完善建议

### 新增规则

**R1: "小变更文件批量审查"规则**
当 PR 中存在 ≥3 个变更量 ≤10 行的已有文件时，必须逐文件说明变更意图和影响，禁止在 FINDINGS 中集体忽略。删除行必须追溯被删除的行为及其调用方。

**R2: "静默失败路径升级"规则**
当失败路径满足以下条件时，基础严重程度至少为 `major`：
- 位于核心业务链路（非辅助/监控路径）
- 失败后无用户可见错误、无重试、无告警
- 导致数据静默丢失或状态不一致

**R3: "新增 DB 表必须审查索引"规则**
新增表定义时，必须对照同 PR 中的查询语句，验证是否有对应索引覆盖。无匹配索引时至少标 `major`。

**R4: "模型/成本切换显式论证"规则**
将 API 调用从低成本模型切换到高成本模型时，必须要求作者补充成本影响估算或性能必要性论证，至少标 `suggestion`。

### 现有规则强化

**"PR 描述与 diff 一致性"需要量化阈值**：当 PR 描述的语义范围（"优化配置"、"调整日志"）与实际变更的架构影响（新增队列、状态机扩展）存在量级差异时，应直接标 `major`，而非仅做文字对比。

## 4. 经验教训

### 值得未来关注的要点

1. **"文件列表≠审查范围"**：23 个文件列出不代表 23 个文件都被审查。审查者容易陷入"大文件深度看、小文件跳过"的模式，而小文件中的删除和参数变更往往隐藏着行为契约的变化。

2. **队列系统的"冷启动"与"降级"必须问**：引入新队列机制时，必须追问三个问题：表不存在时怎么办？队列入队失败时有没有降级路径？消费失败的消息去哪了？本次审查只问了第三个（异常状态收尾），前两个完全遗漏。

3. **"回调注入"模式需要生命周期验证**：`pending_user_message_callback` 被注入到 AIReviewer 中，审查应验证：回调是否在所有路径（正常完成、异常、取消、超时）下都恰好被调用一次？是否存在回调泄漏（持有了外部引用导致 GC 无法回收）？

4. **PR 描述的"降维"是危险信号**：将架构级变更描述为配置优化，可能是作者对变更影响认知不足，也可能是刻意降低审查预期。无论哪种情况，审查者的第一反应应该是"描述和 diff 不对等"而非"按描述方向审查"。

### 对队列+Worker 模式的专项经验

- **幂等性声明需验证**：审查摘要提到"入队幂等性"，但应追问：幂等键是什么？竞态窗口内两个相同请求同时到达时，数据库唯一约束是否能兜底？仅靠代码逻辑的 check-then-insert 在并发下不够。
- **`_drain_pending_incremental` 的"兜底"语义需警惕**：兜底逻辑往往意味着"正常路径不确定能不能覆盖"，这类方法容易成为 bug 藏身处，审查时应要求作者明确其触发条件和预期行为边界。
