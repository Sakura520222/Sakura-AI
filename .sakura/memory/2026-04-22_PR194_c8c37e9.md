## 2. 发现的模式

### 代码模式
- **防御递进失效**：修复 `os.path.join` → 引入 `resolve()` → 但 `resolve()` 在目录遍历子项和 `os.walk` 中未被应用。安全修复常因"点状修复"思维引入新漏洞
- **静默失败惯性**：`except OSError: pass`、弱 warning 措辞，说明开发者有"不让程序崩溃"的直觉，但缺乏"让调用方能感知异常"的意识

### 架构观察
- **适配器接口契约不完整**：`sha`/`url`/`html_url`/`git_url` 属性缺失，当前未崩溃仅因下游恰好未访问。这是"偶然正确"，不是"设计正确"
- **双数据源无收敛计划**：`git show` + 工作树回退是过渡方案，但无文档标注过渡期或收敛计划

## 4. 经验教训

### 核心教训
- **Symlink 是路径安全的第二道盲区**：`resolve()` 解决了 `../` 穿越问题，但 symlink 是"合法路径指向非法位置"，必须额外检查。审查路径安全代码时，脑中应自动追问："如果目录内有 symlink 指向外部会怎样？"
- **`os.walk` 的默认行为不应被信任**：虽然 `followlinks` 默认为 False，但依赖默认值是隐性知识，代码中必须显式声明。审查时看到 `os.walk` 无参数，应直接标记
- **安全修复的攻击者视角**：修复一个漏洞后，应从攻击者角度问"这条新防线有什么绕过方式？"而非满足于"原漏洞已修复"

### 审查流程教训
- **全量审查 ≠ 聚焦新增文件**：本次犯了这个错误，214 行新增文件吸引了全部注意力，29 行修改文件被忽视
- **历史遗留表的双刃剑**：维持了连续性，但也可能导致注意力被"之前已标记的问题"牵引，忽略新改动
