## 1) 审查质量评估

### 覆盖度
这次审查抓住了**最关键的阻塞问题**：为了清理 webhook 预创建的占位 Check，却把所有 `external_id` 不匹配的同名活跃 Check 都取消了，直接破坏并行执行隔离性。这个问题确实足以 `request_changes`。

但从覆盖度看，仍可能遗漏了几类重要风险：

- **占位 Check 与真实 Check 的接管关系是否完整闭环**
  - 现在只看到了“清理旧的/错误的”，但没充分验证：
    - 占位 Check 是否会被实际 worker 正确接管更新？
    - 接管失败时是否会残留“completed/cancelled”的假状态？
    - 重试路径是否会重复创建多个 Check？
- **回收逻辑的副作用**
  - 如果取消操作触发 webhook、状态同步或下游展示，可能引入连锁反应。
- **测试覆盖是否真正覆盖并发场景**
  - 当前新增测试有价值，但若没有并行 job / 重试 / 乱序更新的场景，仍可能只验证单路径。

### 准确度
这次 major 判定是合理的，而且严重程度不低。原因是：

- 这是**状态隔离错误**，不是简单的展示问题；
- 影响的是审查执行的“活跃任务”本身；
- 一旦误取消，后续状态更新会失真，属于**高影响、难恢复**的问题。

不过，建议对术语更精确一点：
- 不是“所有 external_id 不匹配的同名活跃 Check”都应该默认视为 stale；
- 只有**可证明属于 webhook 预创建占位物**的 Check 才能收敛。
  
也就是说，这里真正的错误不是“取消”本身，而是**取消条件过宽**。

### 完整性
审查对变更意图的理解是比较到位的：这是在修复 GitHub Check Run 的收敛与失败路径。

但仍有一个完整性风险：  
本次 PR 描述写的是“Analysis / Findings 配置能力增强”和“可观测性、严重性展示”，而增量代码重点却在 `github_app.py` 和 `review_worker.py` 的执行链路修复。审查虽然指出了关键 bug，但对**PR 叙述与实际改动范围的偏移**没有充分展开。  
这类“名义上是配置增强，实际上改了执行状态机”的变更，应更严格审视。

## 2) 发现的模式

### 代码模式
这次代码体现出典型的“**补丁式修复**”特征：

- 先有一个为了解决面板残留问题的修补动作；
- 再在原逻辑上追加清理路径；
- 但未充分建模“哪些 Check 可以被安全收敛”。

这类模式常见后果是：
- 逻辑越来越像“经验规则集合”；
- 条件判断逐渐扩大；
- 一旦缺少明确身份标识，就很容易误伤并发任务。

另一个明显模式是：
- **状态机逻辑与 webhook 生命周期耦合较深**
- 任务标识、Check Run 标识、external_id、head_sha 之间的关系没有被强约束  
  这会导致“看起来是同一个审查，但实际上是不同执行实例”的边界模糊。

### 架构观察
从依赖图看，这个项目的审查链路是一个多点耦合架构：

- webhook -> github_app -> review_worker -> reviewer / check_run_service
- 配置层、数据库层、服务层、GitHub App 层彼此交织

特点是：
- **状态流跨多个模块传递**
- GitHub Check Run 既是展示层，也是执行状态载体
- `external_id`、数据库记录、webhook 预创建之间存在隐含契约

这类架构最怕两件事：
1. 标识语义不统一；
2. 状态转换没有集中管理。

## 3) 规范完善建议

### 建议新增/修改的审查规则

#### 规则 1：状态收敛必须有“身份白名单”，不能仅用“不等于当前值”做删除条件
对于任何会影响执行实例的清理逻辑，必须确认：
- 该对象是否能被**明确识别为本次流程创建的临时对象**
- 是否存在并行/重试/乱序场景
- 是否可能误伤其他合法实例

可形成审查模板：
- “只允许收敛满足 X / Y / Z 条件的对象”
- “禁止用排除法清理活跃任务”

#### 规则 2：并发执行场景必须显式检查
如果变更涉及：
- Check Run
- webhook
- worker
- 重试/幂等
- 状态机

则必须至少问一遍：
- 并行 job 会怎样？
- 旧 job 未结束新 job 启动怎么办？
- webhook 重放怎么办？
- 失败后重试会不会重复创建状态？

#### 规则 3：PR 描述与实际 diff 的职责对齐
当 PR 描述是“配置增强/可观测性改进”，但 diff 涉及执行链路和状态机时，应强制提示：
- 这不是纯配置改动；
- 必须按流程正确性审查，而不是只看展示层。

### 项目特有规范要点
建议补充以下项目规则：

- `external_id` 的语义必须文档化：
  - 是执行实例 ID？
  - 是 webhook 占位标记？
  - 还是二者混用？
- 对 Check Run 生命周期建立统一约定：
  - 创建者、接管者、完成者、取消者分别是谁
- 所有状态转换应在服务层封装，避免散落在 webhook / worker 中各自实现
- 对“占位 Check”的清理必须使用**专门标记**，不要复用通用执行标识

## 4) 经验教训

### 未来审查应重点关注的点
- **不要把“清理脏状态”默认视为正向修复**
  - 清理动作往往最容易误伤正常执行
- **任何状态取消逻辑都要先问隔离性**
  - 是否会影响同 head、同 PR、同用户、同时间窗口内的其他任务
- **别只看当前执行路径**
  - 还要看重试、并发、超时、webhook 重放、手工触发等非主路径

### 对特定技术/模式的审查经验
对于 GitHub Check Run / webhook / worker 这一类系统：
- `external_id` 不应是“可随意解释”的字符串；
- 最好把它拆成明确字段：
  - `run_instance_id`
  - `placeholder_marker`
  - `source_type`
- 状态管理要尽量“单向”：
  - 只能由特定角色取消特定状态
  - 不能在清理流程里泛化操作活跃任务

## 5) 增量审查反思

### 新增提交是否解决了之前问题？
**没有彻底解决。**

前一轮问题是：
- 占位 Check 和实际 worker 使用不同执行标识，导致无法接管，留下悬挂状态。

这次试图修复这个问题，但方式是：
- 扩大清理范围，把所有不匹配 `external_id` 的同名活跃 Check 取消掉。

结果是：
- 原问题可能缓解了一部分；
- 但引入了更严重的新问题：**误杀并行/重试中的合法执行实例**。

所以这是“修复未闭环，且带来新回归”。

### 增量变更是否引入新的风险？
是的，而且风险很明确：

- 并发审查被互相取消
- 重试任务状态被污染
- Check 面板与真实执行脱钩
- 后续状态更新失真，导致排障困难

### 审查覆盖度是否因只看增量而下降？
有一定下降风险，尤其在这种“状态机连续修补”的场景里。

增量审查的天然盲点是：
- 容易只验证本次修复是否“看起来合理”
- 却忽略前后几轮之间的语义一致性

本例中最典型的点就是：
- 只看本次 diff，容易觉得“加清理逻辑是在修 bug”
- 但结合历史上下文，才能发现这是**把一个接管问题修成了隔离性问题**

因此，对于连续多轮围绕同一链路修补的 PR，应更强调：
- 历史问题是否真正关闭
- 新逻辑是否只是把 bug 转移到另一类场景
- 是否需要回到抽象层重新设计，而不是继续打补丁

---

## 结论

本次审查的主要优点是：**抓住了真实且高风险的并发隔离 bug**。  
主要不足是：对“修复意图”与“状态机语义”的系统性追问还可以更强，尤其要防止连续增量修补中出现“前一个洞补上，后一个洞更大”的情况。

### 本次最重要的审查经验
> 对于 Check Run / webhook / worker 这类状态系统，**收敛逻辑必须基于明确身份，而不是排除式条件**。  
> 一旦引入“取消不匹配项”的通用规则，就要优先怀疑并发误伤。
