## 2. 发现的模式

### 代码模式
- **“委托式重构”残留**：开发者倾向于用“调用新函数 + 保留旧方法”的方式降低修改风险，但遗留的 wrapper 会形成技术债务。
- **启发式判断过度使用**：`"." in message and " " not in message` 这种规则在通用逻辑中很脆弱，说明开发者对输入空间缺乏枚举。
- **模板标点硬编码惯性**：即使已经做了大量 i18n 替换，仍然容易在末尾遗漏句号、冒号等。

### 架构观察
- **分层清晰但边界仍模糊**：`deps.py` 作为 WebUI 依赖层，包含了 toast_redirect 这种偏业务逻辑的函数，导致它需要理解翻译键的格式。
- **i18n 基础设施已趋于成熟**：有 `output_text()`、`detect_language()`、`toast_redirect` 自动兜底，但缺乏编译时或静态检查来强制翻译键存在性。

## 4. 经验教训

### 未来审查关注要点
1. **重构残留检测**：当看到“新增模块级函数” + “类方法改为委托”时，必须检查是否删除了原方法。
2. **标点符号的本地化陷阱**：中文句号“。”与英文句号“.”虽然视觉相似，但必须纳入翻译值，否则未来语言（如阿拉伯语）会出错。
3. **启发式逻辑代码嗅探**：任何形如 `if condition and heuristic` 的分支，都应该要求注释说明“输入空间的边界条件”和“失败时的 fallback 行为”。
4. **增量审查的隧道视野修正**：即使某个问题不在变更文件内，但如果它被本次变更间接暴露（例如 billing.py 的异常现在会走新的 i18n 路径），应标记为 `major` 并要求补充修复。

### 对特定技术/模式的审查经验
- **i18n 重构 PR**：必须额外检查 `str(e)` 是否仍存在、`toast_redirect` 是否都传了 `lang`、模板中是否有孤儿标点。
- **委托模式移除**：建议使用 `grep -n "self\._t("` 确认所有调用点已替换，再删除定义。
