**6. 经验教训**  
| 经验点 | 说明 |
|---|---|
| **明确破坏性等级** | 数据库切换涉及持久化层，默认应标记为 *major* 或 *medium*，并在 PR 中提供完整的迁移/回滚步骤。 |
| **标签体系细化** | 对涉及底层技术的改动（数据库、缓存、消息队列）应统一使用专属标签，便于后续统计和搜索。 |
| **工作量估算要留余量** | 脚本、文档、CI 的改动往往比代码本身多，估算时应考虑 **测试+调试** 的时间。 |
| **重复检测要多维度** | 仅靠标题关键字可能漏掉已关闭的“内部实现” Issue，建议结合 **文件路径**（如 `docker-compose.prod.yml`）进行搜索。 |
| **迁移风险文档化** | 在 Issue 或 PR 描述中加入 **迁移矩阵**（MySQL → PostgreSQL）和 **回滚方案**，可显著降低审查阻断。 |
| **CI 配置同步** | 更换底层服务后，CI 中的 `services`、`env` 必须同步更新，防止因镜像缺失导致流水线报错。 |
| **保持原始动机** | Issue 中的 “镜像体积” 只是动机之一，仍需考虑 **性能、功能兼容** 等因素，避免因单一指标做出不适合的决策。 |
