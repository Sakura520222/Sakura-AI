## 2️⃣ 发现的模式  

### 代码层面  
| 模式 | 正面表现 | 潜在风险 |
|------|----------|----------|
| **统一的异常/日志函数**（`fail`、`log`）在 `start.sh` 中使用 | 统一错误输出，便于后期审计 | 在非交互式 CI 环境下，`fail` 仍会导致脚本退出但未返回明确的错误码，可能导致 CI 步骤误报 “success”。 |
| **大量 `@dataclass` / Pydantic‑like 结构**（`sandboxer/models.py`） | 可读性高，类型安全 | 未对 `__post_init__` 中的必填字段进行显式校验，若 `pyproject.toml` 生成的对象缺失字段会抛 `AttributeError`，破坏 **fail‑closed** 语义。 |
| **`docker compose` 通过变量渲染**（`docker-compose.yml`） | 环境可配置化 | 变量名与代码中硬编码的默认值不匹配时，部署会产生不可预期的镜像标签，缺少验证步骤。 |
| **“一次性导入”**（在 `backend/services/agent_team/*.py` 中大量 `from ... import *`） | 开发速度快 | 破坏了 **显式依赖**，审查时难以快速定位实际引用，易导致隐藏的循环依赖。 |
| **Shell 与 Python 双轨实现**（`start.sh` 与 `backend/services/...`） | 兼容不同运行环境 | 两套实现的错误处理策略不一致，可能出现 **错误码不对齐**（Shell 返回 1，Python 抛异常），导致 CI/监控误判。 |

### 架构层面  
- **沙箱层与业务层强解耦**：`sandbox_client` 通过 HTTP‑over‑UDS 与 `sandboxd` 通信，明确了信任边界。  
- **配置中心统一**：`backend/core/config.py` 负责所有运行时常量，新增的 `sandboxer/config.py` 仍保持独立，形成 **配置碎片**，后续需要统一入口。  
- **多镜像事务**：一次更新涉及 Web、sandboxd、runner 三个镜像，事务化管理在 CI 中实现，但缺少 **回滚日志** 与 **幂等性校验**（如同一 PR 多次触发时是否会产生重复镜像）。

## 3️⃣ 规范完善建议  

### 3.1 审查规则层面  
| 新增/修改的规则 | 适用范围 | 目的 |
|----------------|----------|------|
| **依赖文件缓存统一规则** | 所有 `setup-python` 步骤 | `cache-dependency-path` 必须指向项目根目录下的 `requirements.txt`、`pyproject.toml`（若使用 PEP‑517）或 `poetry.lock`，并在 CI 文档中注明对应的 `pip`/`poetry` 安装方式。 |
| **Shell 脚本错误码强制对齐** | 所有 `.sh` 脚本 | 脚本内部 `return`、`exit` 必须返回 0‑255 之间的明确错误码，且在 CI 步骤中使用 `set -e` 或自行捕获以防止 “silent success”。 |
| **新增服务层异常映射表** | `backend/services/**` | 每个对外抛出的异常必须在 `backend/api/errors.py` 中有对应的 HTTP 状态码与翻译条目，审查时检查是否同步更新。 |
| **全局配置键引用检查** | `backend/**/config.py`、`sandboxer/config.py` | 新增或删除配置键后，自动全库搜索引用（包括 Jinja、Docker‑compose、Shell）并确保不存在 `KeyError`。 |
| **大幅度功能引入的全链路兼容性审查** | 任意超过 500 行新增代码的 PR | 必须执行：① API 兼容性对比表；② 数据库迁移回滚脚本检查；③ 关键路径的单元/集成测试覆盖率 ≥ 90%。 |
| **日志/监控统一标签** | 所有新增 `log.info/debug/warn/error` 调用 | 必须包含 `component=<module>`、`event=<action>`，便于后期查询与告警。 |

### 3.2 项目特有的规范要点  
1. **沙箱镜像标签强绑定**：所有 `sandboxd`、`runner` 镜像必须使用 `sha256:<digest>` 或固定语义化版本号，禁止 `latest`。CI 中加入 `docker inspect` 校验标签一致性。  
2. **UDS 权限审计**：`sandbox_client` 调用的 Unix Domain Socket 必须在 `backend/core/config.py` 中声明 `SANDBOX_SOCKET_PATH`，并在部署文档里说明文件系统权限（`0600`）。审查时检查是否出现硬编码路径。  
3. **跨语言异常映射**：Shell 脚本的 `fail` 与 Python `raise SandboxError` 必须在 `docs/ERROR_MAP.md` 中保持一一对应。  
4. **文档-代码双向同步**：README/部署文档中出现的 CLI 参数（如 `SAKURA_SANDBOX_DOCKER_INTEGRATION`）必须在代码入口（`backend/core/config.py`）使用 `os.getenv` 并提供默认值，审查时检查是否遗漏。

## 4️⃣ 经验教训  

| 教训 | 说明 | 未来关注点 |
|------|------|------------|
| **阻断项必须与 CI 失效直接关联** | 本次阻断的 CI 缓存错误会导致依赖不一致，若未在 CI 中直接报错，合并后可能产生运行时故障。 | 在审查时立即验证 `actions/setup-python` 步骤是否在 **实际运行的 Job** 中被引用，并尝试手动触发一次缓存计算。 |
| **Shell 与 Python 错误处理不一致** | `docker pull` 失效在 Shell 中仅 `return 1`，而 Python 端可能捕获 `subprocess.CalledProcessError` 并记录不同信息，导致错误归因困难。 | 建议在审查中对 **跨语言错误路径** 建立统一的 “错误码/日志” 对照表。 |
| **大体量代码引入需分层审查** | 2000 行新增代码一次性审查导致对细节（如 `sandbox_client` 的超时、重试策略）未能深入。 | 将大 PR 拆分为 **功能分支**（如 “sandbox client”、 “sandbox execution”、 “CI workflow”），每个子 PR 完成后再合并主 PR。 |
| **文档改动不等同于实现改动** | 文档中提到的 “fail‑closed” 行为在实际代码里未必完全实现（例如 `sandbox_pull_or_build_images` 未输出错误信息）。 | 在审查时使用 **文档‑代码映射检查**：对每条关键文档说明，搜索对应实现并验证逻辑相符。 |
| **依赖声明与实际安装方式不匹配** | `pip install -e './sandboxer[dev]'` 使用 `pyproject.toml`，但 CI 缓存仍指向 `requirements.txt`，导致缓存失效。 | 审查时确保 **依赖声明层（pyproject/poetry）** 与 **CI 安装命令** 完全匹配，必要时在 CI 中显式运行 `pip freeze` 并对比缓存键。 |
| **安全模型需可验证** | PR 中的安全模型描述（如 “UID/GID 65532”）未在代码里有显式常量或测试验证。 | 为每条安全声明编写 **单元/集成测试**（如检查容器启动时的 `--user` 参数），并在审查报告中列出对应测试文件。 |

---

### 小结  

本次审查已经成功捕获了两项阻断/次要缺陷，并对整体架构给出了肯定。但面对 **大幅度功能引入**（OS 级沙箱、三镜像事务、跨语言交互），审查的 **深度** 与 **全链路兼容性** 仍有提升空间。通过补充上述审查规则、强化跨语言错误映射、以及在 PR 规模上进行分层审查，可进一步提升审查的安全性、可靠性和可维护性。
