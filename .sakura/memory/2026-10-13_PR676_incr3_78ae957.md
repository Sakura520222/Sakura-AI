# 审查反思：PR #676（增量第4轮，日志安全与可观测性）

## 一、审查质量评估

### 覆盖度
**做得好的**：
- 对 `log_sanitizer.py` 的正则语义（`_PAIR` 反向引用闭包 + DOTALL）和 `_percent_projection` 字节栈归约做了逐字符推演，覆盖了 ReDoS、畸形 Unicode、嵌套编码三条攻击面；
- 正确识别了“先截断后脱敏”的顺序漏洞并核验落库路径（`attempt_chain`）——这是很多审查会漏掉的持久化旁路。

**潜在盲区（本轮增量特有）**：
1. **`.sakura` 记忆文件的脱敏自洽性未被审查**。本次 18 个提交中约 15 个是 reflection/memory/consolidate 提交，其中 `2026-10-13_PR660_incr6_9ed0fef.md`（+68 行）等文件包含审查过程细节。本 PR 的主题恰是“凭据不落盘”——若反思文件中引用了真实日志片段、Settings 字段值或凭据前缀，等于在修复泄漏的同时制造新泄漏。审查摘要对此零着墨，这是增量审查被代码提交吸引注意力后的典型覆盖塌陷。
2. **6 次 `origin/main → develop` 反向合并未被质疑**。`deep` 策略下应确认增量 diff 基线是“相对 main 的最终合并 diff”而非“相对上轮审查点的提交列表”，否则 main 侧合入的变更可能逃逸审查视野。审查摘要未说明基线口径，属于可验证性缺口。

### 准确度
- 两个 suggestion 定级合理：均为性能问题，不改安全语义，不阻断——与本 PR “Fail-Closed 退化方向不变”的判断一致。
- **一处方法论瑕疵**：“无二次方 ReDoS 面”的结论来自**推演**而非实证。项目记忆明确规定“文档不可作验证依据”，同理，纯推理的正则复杂度结论也应配一个病态输入基准测试（如 1MB 含 `%` 与嵌套引号的文本 + 10 个 secret）落进 `test_logging_review_regressions.py`。推演可以支撑不阻断，但不能替代回归锚点。

### 完整性
- 审查准确捕捉到一个**规范性自反问题**：本 PR 向 `.sakura` 写入“Log Patcher Hot-Path Guard”硬规则，同时自己的 `_sanitize_record` 违反该规则。指出这种“规则与实现自相矛盾”是高质量信号。
- 遗漏：PR 描述明确承认“长时日志轮转压力测试未执行”，审查未将其转化为部署后观察项（如首个 500MiB 裁剪周期内的磁盘监控建议），可用一条非阻断提醒补全闭环。

## 二、发现的模式

**代码模式**：
- 纵深分层脱敏：明文 → 百分号编码 → JSON 转义嵌套 → 异常链（cause/context/ExceptionGroup），每层独立可测，是日志脱敏的成熟范式；
- **反复出现“热路径重复计算”**：`_configured_secrets()`（4 次/记录）、`_percent_projection`（k 次/消息）。模式根因相同——纯函数被放进循环而调用方未提取循环不变量。这类问题在 Python 日志管线中会系统性复发。

**架构观察**：
- `log_sanitizer` 被 40+ 文件消费（依赖图 N10 入度最高），单点故障即全局失效——这解释了为何该文件三轮都有实质修改，也应触发比普通文件更高的审查留存要求（如专门的红线测试套件）；
- ContextVar lane 隔离 + 显式 `secrets=` 参数传递，避免了“全局密钥注册表”的并发污染，设计方向正确。

## 三、规范完善建议

建议向项目记忆新增三条：

1. **AI 记忆文件脱敏红线**：`.sakura/` 下反思、记忆、总结文件提交前，须扫描其中引用的日志片段、配置示例、diff 摘要是否含明文凭据或可逆前缀——审查覆盖范围必须显式包含 AI 自身产物。
2. **重复 suggestion 的升级机制**：同一建议跨 ≥2 轮未处理时，不应原样重述，而应二选一：转为独立 tracked issue（从 PR 审查队列摘除），或升级为要求作者显式回应（接受/拒绝+理由）。避免“车轱辘建议”稀释审查信号——本轮建议 1 已是第三次出现。
3. **反向合并基线核验**：PR 分支合入 main ≥3 次时，增量审查必须声明并核验 diff 基线（最终 `main...HEAD` 三点 diff），防止合入内容逃逸审查。

## 四、经验教训

- **“性能建议非阻断”不等于“可无限期搁置”**：两个建议都落在作者自己刚立的硬规则射程内，规则-实现不一致比单纯性能问题更值得追踪，因为它侵蚀规则体系公信力。
- **loguru record dict 缓存的安全性依赖同步多 sink 语义**：`_log_secrets` 挂在 record 上能成立，前提是 record 生命周期严格限于单条记录且 sink 同步消费。若未来引入异步 sink 或 record 池化复用，该缓存会跨记录泄漏密钥——这是应该在代码注释中显式声明的隐含约束。
- **推演结论需要测试锚点**：正则/算法复杂度的审查结论应推动作者补病态输入基准测试，否则“无 ReDoS”只是本轮审查者的个人背书，后续重构无回归防线。
