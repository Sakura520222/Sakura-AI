### 2. 发现的模式

*   **代码/配置模式（假设驱动开发）**：
    *   开发者倾向于根据直觉或局部经验配置 GitHub Actions（如误认为 Dependabot 的 actor 是 `app/dependabot`），缺乏在真实 GitHub 权限模型下验证凭据（PAT/Secrets）可见性的意识。
*   **架构与自动化机制观察**：
    *   项目对 `uv.lock` 的严格一致性要求（`uv sync --locked`）与 Dependabot 的原生更新策略存在冲突。
    *   项目具备较强的自动化契约测试意识（如已存在 `tests/test_docker_channel_workflows.py`），但新新增工作流时容易遗漏同步编写 YAML 契约断言。

### 3. 规范完善建议

结合本次审查经验，建议在“项目记忆”中新增/优化以下 GitHub Actions 相关的审查规则：

#### 建议新增：GitHub Actions & Dependabot 自动化规范
1. **Dependabot 触发器与 Secrets 访问硬防线**：
   - 依赖机器人（Dependabot）触发的工作流若需要写入权限或访问全局 Secrets，**禁止使用** `pull_request` 事件（此模式下 `secrets` 恒为空），必须使用 `pull_request_target`。
   - 使用 `pull_request_target` 时，必须配置严格的 `if: github.event.pull_request.user.login == 'dependabot[bot]'` 身份门禁，且最小化 `permissions`，防止 Fork PR 提权攻击。
2. **Bot 身份标识一致性**：
   - 检查 PR 作者身份时，Dependabot 的 GitHub 登录名必须统一为 `dependabot[bot]`，不得误用 App ID 或名称（如 `app/dependabot`）。
3. **Workflow 凭据传递安全性**：
   - 严禁将 PAT / Token 直接拼入 `git push https://x-access-token:${PAT}@github.com/...` 格式的 URL 中（防止日志泄漏）。应统一采用 `actions/checkout` 的 `token:` 属性设置凭据后直接使用 `git push origin`。

---

### 4. 经验教训

1. **GitHub Actions 权限模型的“隐蔽坑点”**：
   - Dependabot 触发的 `pull_request` 在 GitHub 中被特殊对待（安全沙箱）。审查任何涉及 Bot 自动化的 Workflow 时，**第一反应必须检查 Secrets 的实际作用域与事件触发源**（`pull_request` vs `pull_request_target`）。
2. **警惕“看似合理的 PR 描述”**：
   - PR 描述中虽然写明了“作业级 `if` 限定 `app/dependabot` 本尊 (fork PR 拿不到 secret)”，但这完全是基于错误预设推导出的逻辑。审查必须以 **GitHub 平台机制真实行为** 为准，不能轻信 PR 描述中的安全假设。
3. ** Workflow 契约断言的防回退保障**：
   - GitHub Actions 的 YAML 往往缺乏 Linting 校验逻辑错误。将 Workflow 的关键配置（事件触发器、权限集、条件门禁）纳入 Python 自动化单测断言（YAML 解析测试），是保障 CI/CD 稳定性的极佳实践。
