**二、发现的模式**

| 类别 | 观察 |
|------|------|
| **代码模式** | 1. **Docker 参数硬编码**：`--mount type=bind,...` 直接写在代码里，缺少统一的参数生成函数，导致类似 `rw` 错误难以复用检测。<br>2. **测试与实现耦合**：单元/集成测试直接使用 `docker_runtime` 的内部实现细节（如 bind‑source 解析时机），一旦实现细节改动，需要同步更新多处测试，易产生 **TOCTOU** 失效。<br>3. **注释式“文档门禁”**：在 `test_docker_isolation.py` 中加入大量说明性 docstring，实际行为仍依赖代码实现，容易产生“文档即代码”误判。 |
| **架构观察** | 1. **sandboxer** 成为 **独立子服务**，但仍通过内部 import 与主业务代码耦合（如 `backend/services/agent_team/...` 直接引用 sandboxer 包），缺少明确的 **接口层**（API/DTO）进行边界划分。<br>2. **CI 工作流** 分散在多个 YAML（`sandbox-quality.yml`、`sandbox-publish.yml`），但 **gate 检查**（`sandboxer unit and runner isolation`）的结果未在 PR 描述或审查报告中自动关联，导致红灯信息被“孤立”。<br>3. **依赖图** 显示 `docker_runtime.py` 被多处核心模块间接引用，任何细微改动都具 **高传播风险**，但审查未执行全库引用搜索。 |

**三、规范完善建议**

1. **新增审查规则**  
   - **Docker 参数统一化**：所有 Docker `--mount`、`--network`、`--cap-drop` 等参数必须通过项目统一的生成函数或配置对象，审查时检查是否出现硬编码字符串。  
   - **跨模块引用安全检查**：对任何位于 `sandboxer/`（或其他新子服务）下的公共 API，必须在审查时执行 **全库引用搜索**，确保未出现未更新的旧调用或隐式依赖。  
   - **CI Gate 关联强制**：每次 PR 必须在审查报告中提供 **所有阻断 Gate 的 run 链接**，并在 PR 描述里注明“已验证对应 Gate 通过”。自动化脚本可检查 PR 是否缺失该信息。  
   - **测试-实现耦合度阈值**：若单元/集成测试直接检查实现细节（如内部变量名、函数调用顺序），审查应要求抽象为 **行为契约**（例如仅验证容器最终状态），并在代码中提供对应的 **契约抽象层**。  

2. **项目特有规范要点**  
   - **sandboxer 服务边界**：所有业务层调用 sandboxer 必须使用 `sandboxer.api`（或类似）包装层，避免直接 import `docker_runtime`。审查时检查是否有跨层直接引用。  
   - **文档-代码双向验证**：文档更新后必须运行 **文档测试脚本**（如 `pytest --doctest-glob='*.md'`）确保文档中的示例命令、参数与代码实现保持一致。  
   - **红灯阻断细化**：对于 `major` 级别的 CI 失败，审查报告必须提供 **根因定位建议**（如日志关键字、失败步骤），而不是仅标记 “仍红灯”。  

**四、经验教训**

| 经验点 | 具体建议 |
|--------|----------|
| **根因定位要闭环** | 修复代码后，审查者应主动 **拉取最新 CI run**，确认对应 Gate 已绿。如果仍红灯，需在审查报告中说明具体失败日志并列出可能的残留原因。 |
| **增量审查不等于全局审查** | 只看增量文件会遗漏 **全局影响**（如全局配置、共享常量）。在增量审查结束后，补充一次 **全库搜索**（`grep -R "rw"`、`grep -R "bind-propagation"`）确保没有遗漏的旧写法。 |
| **测试同步成本** | 对于涉及底层实现细节的测试，建议在代码层提供 **兼容层**（如 `DockerMountBuilder`），测试只验证该层的输出。这样即使底层实现改动，测试仍保持通过，降低维护成本。 |
| **CI 环境差异** | 本地 `docker` 与 CI 中的 Docker 环境（版本、守护进程配置）可能不同。审查时应检查 **Docker 版本约束** 是否在 `Dockerfile` 或 `workflow` 中明确声明，并在文档里提示 CI 环境要求。 |
| **文档门禁的误导** | 只在 docstring 中写 “此为文档门禁” 并不足以阻止错误使用，审查应要求 **代码层面的防御**（如 `assert`、异常）而不是仅靠说明。 |

**五、增量审查反思**

| 项目 | 结论 |
|------|------|
| **是否解决了历史问题** | ✅ 移除了 `rw` 字段，测试断言方向已与真实 Docker 行为对齐，基本解决了上一轮 “挂载参数不被支持” 的根因。<br>⚠️ 但 **sandboxer unit and runner isolation** 的红灯仍未消除，说明还有 **残余路径**（可能是其它 bind‑mount 或权限检查）未被覆盖。 |
| **是否引入新风险** | - **参数默认行为变化**：删除 `rw` 后依赖默认可写的假设在不同 Docker 版本上可能表现不一致，需要在文档注明最低 Docker 版本。<br>- **测试覆盖偏窄**：仅在两套测试中验证了 `workspace/task-git` 挂载写权限，未覆盖 **其他业务挂载**（如模型缓存、临时工作目录），潜在回归风险。 |
| **审查覆盖度下降** | 增量审查只关注了三个文件，导致 **未检查**：<br>1. `sandboxer/src/sakura_ai_sandboxer/config.py` 中是否还有旧的 `rw` 参数；<br>2. 业务层（`backend/services/agent_team/*`）对 `docker_runtime` 的调用是否仍假设可写；<br>3. CI 工作流中是否还有未更新的 `docker run` 参数。<br>因此覆盖度相对全局审查下降，建议在增量审查后加入 **快速全库引用检查**。 |

---

### 总结建议

1. **闭环验证**：在每次增量审查结束后，审查者必须拉取对应的 CI run，确认所有 **major** Gate 已绿，若仍红灯，提供具体日志定位点并要求作者再次修复。  
2. **全局影响快速检查**：增量审查完毕后运行一次 **全库搜索**（如 `git grep 'rw'`、`git grep '--mount'`），确保没有遗漏的旧写法。  
3. **抽象层建设**：为 Docker 参数构建统一的 Builder/Config 类，既降低硬编码风险，也让测试更聚焦行为而非实现细节。  
4. **文档‑代码同步**：引入文档测试或自动化检查，防止 “文档门禁” 仅停留在注释层面。  
5. **CI Gate 报告标准化**：在 PR 模板中加入 “CI Gate 链接” 字段，审查工具自动校验其存在性与通过状态，避免因信息缺失导致的阻断遗漏。

通过上述改进，可提升审查的 **覆盖度、准确度与闭环性**，降低因增量审查视野局限导致的遗漏风险，帮助 PR 更快进入合并。
