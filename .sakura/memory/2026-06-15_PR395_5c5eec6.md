## 深度反思

### 1. 审查质量评估

**覆盖度：存在盲区**

审查准确识别了两个核心修复和架构改进，但遗漏了几个值得追问的点：

- **`_get_graph_files_sync` 的大PR风险**：增量模式下调用 `pr.get_files()` 获取全PR文件列表，对于500+文件的PR是否触发GitHub API分页问题或超时？审查未评估这个新增的"全量获取"在边界场景下的表现。
- **`priority_paths` 溢出场景**：当优先路径文件数本身超过 `max_files` 时，`_trim_files` 的行为是什么？是全部保留还是截断？这个边界未被提及。
- **向后兼容性破坏**：`_build_prompts` 将三个参数从可选改为必填，如果有外部调用方或测试遗漏更新，会直接抛 `TypeError`。审查未做调用方扫描（项目记忆中明确要求"公共方法变更调用方扫描"）。
- **`frozenset` 的完备性**：只枚举了 `deleted` 和 `removed`，但 GitHub `File.status` 枚举还包括 `renamed`、`copied` 等。`renamed` 文件是否应参与依赖图构建？审查未追问这个语义问题。

**准确度：合理**

8/10 评分与 approve 决策匹配，suggestion 级别定位准确——测试缺口不影响正确性但影响信心。

**完整性：理解到位但深度不足**

审查正确理解了"修复两个Bug + 增量优化"的意图，但对变更引入的新风险面（全量获取性能、必填参数兼容性）缺乏"向前想"的意识。

### 2. 发现的模式

**代码模式：**
- 用 `frozenset` 替代多条件 `or` 做状态匹配，语义更清晰且性能微优
- "消除隐式回退"模式：将可选参数+不可达回退路径 → 必填参数+显式传值，这是一个好的防御性编程实践
- "获取分离"模式：将元信息获取（`_get_graph_files_sync`）与内容获取（`_select_content_files`）解耦，按需拉取

**架构观察：**
- 增量逻辑通过方法级条件分支实现，而非策略模式或独立类——在复杂度可控时这是合理选择，但若增量路径继续增长，应考虑抽离
- 依赖图服务的职责链清晰：元信息 → 内容 → 裁剪 → 提示词构建，每步可独立测试

### 3. 规范完善建议

**建议新增规则：**

1. **第三方API状态值匹配必须注释来源**：当代码匹配第三方API的枚举值时（如 GitHub `File.status`），应在常量定义处注释官方文档的完整枚举列表及选取依据。本次 `"deleted"` vs `"removed"` 的Bug根源就是缺乏这个约束。

2. **"恒定回退值"是强制阻断信号**：当可选参数的回退值在所有正常调用路径下都相同时（如恒为0），不得仅改为必填参数了事——必须同时追问"为什么之前的回退路径存在"以及"是否有其他调用方依赖旧签名"。

3. **集成测试参数必须触发关键分支**：集成测试中涉及阈值/裁剪类逻辑时，参数设置必须能触发裁剪分支。`max_files=50` 但测试数据只有几个文件，等于绕过了被测逻辑。应要求测试数据量 > 阈值或显式设置 `max_files` 小于数据量。

**建议强化现有规则：**

- 项目记忆中"公共/基类控制流变更调用方扫描"在本案中未被执行。`_build_prompts` 虽是内部方法（`_`前缀），但签名变更仍应扫描同模块内的所有调用点，确认参数传递正确。

### 4. 经验教训

**① 字面量匹配第三方值是高危反模式**

`"deleted"` vs `"removed"` 本质上是"凭记忆写状态值"而非"查文档写状态值"。未来审查中，凡是 `== "某个字符串"` 匹配外部系统状态的代码，都应主动核对官方文档，即使作者声称"已验证"。这类Bug的特征是：单元测试能通过（因为mock用了相同的字面量），但生产环境失败。

**② "回退值为0"应触发警觉而非跳过**

`len(pr_info.get("code_files", []))` 恒为0——这个模式在审查时应立即标记为 major 而非当作"次要改进"。因为"展示给用户的统计数字恒为0"直接影响可观测性和用户信任，严重程度应与功能Bug同级。

**③ 增量优化的"隐性代价"需显式评估**

`_get_graph_files_sync` 解决了"依赖图覆盖不完整"的问题，但引入了"每次增量审查都要全量拉文件列表"的代价。审查增量优化时，不能只看"解决了什么问题"，必须同时评估"引入了什么新代价"，特别是API调用次数和延迟。

**④ 测试"覆盖了函数"≠"覆盖了行为"**

7个测试用例覆盖了所有新方法，但集成测试因参数设置不当绕过了裁剪逻辑。这再次印证项目记忆中的原则——测试能通过和有意义地验证了新行为是两个层次。审查测试时，应先问"这个测试的参数/数据能触发哪条代码路径"，而非只看"是否调用了目标函数"。
