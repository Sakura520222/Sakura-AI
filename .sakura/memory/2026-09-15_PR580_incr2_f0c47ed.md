**三、规范完善建议**

1. **审查规则层面**  
   - **锁文件同步检查**：在任何涉及 `pyproject.toml`、`requirements.txt` 改动的 PR 中，必需自动比对 `uv.lock`（或 `poetry.lock`）是否同步，若不同步直接标记 **error**。可以在 CI 中加入 `uv lock --check` 步骤。  
   - **递归调用风险检测**：对 `*_client.py`、`*_service.py` 等网络请求封装层，强制使用 **显式超时、幂等包装**，并在审查规则中加入 “是否出现自调用/递归请求” 的关键字检测。  
   - **增量审查强制回溯**：当 PR 已经出现 **major** 级别未解决问题，后续增量审查必须 **重新评估这些未解决项**，否则自动阻断合并。  

2. **项目特有规范**  
   - **CI 输出约定**：所有业务脚本若要影响 CI，必须以 **统一的 JSON 输出**（如 `{"status":"superseded","advanced":false}`）为标准，避免仅返回字符串导致误判。  
   - **异常处理约定**：业务层不应直接抛出异常导致 CI 失败；统一使用 **返回值 + CI 捕获** 或 **自定义异常类** 并在 CI 中统一映射。  
   - **依赖升级流程**：依赖升级必须走 **“升级 → 本地测试 → CI → lock 文件同步 → 发布”** 的 5 步流水线，任何一步缺失均视为阻断。  

**四、经验教训**

| 教训 | 具体表现 | 对策 |
|------|----------|------|
| **审查盲点容易被高分掩盖** | 第 2 轮快速审查仅给出 8/10、approve，导致团队误以为所有风险已消除。 | 对于 **已有的 major 级别未解决问题**，即使增量改动本身无风险，也必须在审查报告中显式提醒并保持 **阻断状态**。 |
| **增量审查不等于全局审查** | 只看 `superseded` 逻辑，未检查 `uv.lock`、递归调用。 | 在增量审查前自动 **拉取 PR 的完整 diff**（包括历史提交），并在审查模板中加入 “**前置未解决问题**” 检查项。 |
| **CI 与业务代码耦合带来维护成本** | 业务脚本直接决定 CI 跳过，若脚本改动忘记同步 CI，可能出现 **“CI 仍执行旧逻辑”** 的隐患。 | 建议把 **CI 控制逻辑抽离到统一的库或配置文件**，业务脚本只输出状态，CI 统一解释。 |
| **锁文件漂移是常见隐患** | 第 1 轮已指出但未在后续提交中修复。 | 引入 **pre‑commit hook** 或 **CI lint** 检查 `pyproject.toml` 与 `uv.lock` 的一致性，强制提交前解决。 |
| **递归请求易导致不可预期的超时** | `updater_client.py` 的递归调用未被检测到。 | 在代码审查时使用 **AST 静态分析** 检测同文件内部函数的自调用，尤其是网络请求封装层。 |

**五、增量审查反思**

| 关注点 | 结论 |
|--------|------|
| **是否解决了之前审查提出的问题？** | **未解决**。本次增量只处理了 CI “superseded” 跳过逻辑，**依赖锁文件不同步** 与 **递归请求** 两个 major 风险仍旧存在，未在任何文件中出现修复痕迹。 |
| **增量变更是否引入了新的风险？** | **潜在风险**：<br>1. 返回 `None` 并在 CI 中捕获，若其他调用方忘记检查返回值，可能导致后续脚本误以为发布成功。<br>2. 新增的 `outputs.advanced` 变量在其他工作流中未统一使用，可能产生 **未定义行为**（如某些分支仍会执行 `sync-dockerhub`）。 |
| **审查覆盖度是否因只看增量而下降？** | **是**。审查仅聚焦于本次改动的文件，导致对 **历史未解决的重大缺陷**（锁文件、递归调用）失察。若采用 **“增量+全局回溯”** 的审查策略，可避免此类遗漏。 |

**总体建议**  
1. **在本 PR 中直接补齐锁文件**（运行 `uv lock && git add uv.lock`）并提交；<br>2. **重构 `updater_client.py`**，将递归调用拆分为独立函数或使用 **重试/幂等包装**，并补充相应单元测试。<br>3. **在 CI 中加入锁文件一致性检查** 与 **递归调用静态检测**，确保后续 PR 不再出现相同缺陷。<br>4. **在增量审查模板中强制列出“前置未解决问题”**，审查人员必须明确标记 “仍未解决 → 阻断合并”。  

通过上述改进，可提升审查的 **覆盖度、准确度与完整性**，防止高分掩盖潜在阻断风险。
