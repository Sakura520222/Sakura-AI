### 2. 发现的模式
* **依赖脱节模式（Dependabot 的原生局限）**：
  * Dependabot 针对 Python 生态更新依赖时，默认可能仅修改 `requirements.txt` / `pyproject.toml`，在未正确配置 GitHub Action 或 uv 支持时无法自动回写 `uv.lock`。
  * 导致机器人提交的 PR 天然伴随“CI `--locked` 必炸”的缺陷。
* **双配置维护模式**：
  * 项目同时维护 `pyproject.toml` 和 `requirements.txt`。修改版本必须双向对齐，且最终由 `uv.lock` 统一落地约束。

---

### 3. 规范完善建议
* **建议新增/固化规则：Dependabot 依赖升级自愈流水线**
  * *现状*：人工或 bot 每次修依赖都需额外一轮 review 来提醒跑 `uv lock`。
  * *建议*：在 CI 中为 Dependabot PR 增加自动化锁更新机制（如监听 Dependabot PR 并通过工作流运行 `uv lock --upgrade-package <pkg>` 后自动 push 回 PR 分支，结合项目记忆中已有的 `pull_request_target` 安全硬防线），从源头闭环此问题。
* **审查策略匹配度**：
  * 本次对于纯依赖升级采用 `quick` 策略是合适的；但规则中应明确：**即使是 `quick` 策略，一旦变更涉及依赖文件，必须强制勾稽 `uv.lock` 差异**。

---

### 4. 经验教训
* **警惕自动化 Bot PR 的虚假完整性**：
  * Bot PR 通常带有详尽的 Release Notes 和 Changelog，表面规范完整，最容易让人产生“无脑 Approve”的麻痹心理。
  * 依赖更新类 PR 的审查第 1 顺位永远是：**锁文件变了吗？CI 的 `--locked` 绿了吗？**
* **最小破坏锁更新**：
  * 提示指引时优先推荐 `--upgrade-package <pkg>` 而非无参 `uv lock`，避免无意带入其他间接依赖的大范围漂移，保持锁文件变更最小化与审查聚焦。
