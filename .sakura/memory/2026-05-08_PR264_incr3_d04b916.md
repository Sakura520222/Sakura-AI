## 3. 规范完善建议

### 新增/强化审查规则

| 规则 | 严重度 | 说明 |
|------|--------|------|
| **副作用函数命名必须明确** | Major | 若函数在特定参数下会修改状态（如数据库写），函数名或参数名必须显式提示，例如 `get_users(..., refresh=True)` 应改为 `fetch_users_with_refresh`。建议在 docstring 中用 `⚠️` 标注。 |
| **外部写入失败后须记录可恢复警告** | Major | 当 DB 已提交但外部文件（YAML、JSON、缓存）写入失败时，必须记录 `error` 级别日志并说明“DB 已更新，但外部文件未同步，重启后可能不一致”。 |
| **批量 SQL 查询膨胀必须评估上限** | Minor | 任何 SELECT+UPDATE 模式应注释说明最大循环次数（如 `len(reset_specs) <= 6`）和预估用户量，如果用户量 > 1k 则必须优化。 |
| **并发触发配额重置必须加锁或幂等** | Major | 多个请求同时调用 `reset_all_expired_quotas_atomic` 可能导致重复更新或死锁。建议要求显式使用分布式锁或数据库行锁 `SELECT ... FOR UPDATE`。 |

- **日志重复容忍度**：项目目前允许 Service 层和调用方都记录 info 日志。建议统一为：**Service 层只返回结果对象，调用方负责记录**。
- **测试重复模式**：新增的两个静态分析测试高度相似，应鼓励使用 `pytest.mark.parametrize` 以减少维护成本（当前仅作为 suggestion 合理）。

## 4. 经验教训

### 未来审查关注点
- **SQL 次数膨胀**：当重构引入额外的查询时，必须对比原实现（本 PR 从 6 条 UPDATE 变成 12 条 SQL）。审查应要求提供性能影响评估或用户量上限说明。
- **事务与外部依赖的顺序**：除了“先 DB 后文件”，还应检查 **如果外部写入失败，系统是否进入半一致状态**，以及是否有监控告警。
- **增量审查的盲区**：本次变更中 `quota_service.py` 新增的 `affected_user_ids` 追踪逻辑，审查者只关注了 SQL 次数，但未检查 **如果 SELECT 返回的 user_id 重复或包含无效值（如 NULL），`set` 是否安全**。

### 对特定技术的审查经验
- **SQLAlchemy 中的 `rowcount`**：`rowcount` 对于 RETURNING 语句在某些数据库（如 SQLite）可能不可靠。审查时需确认目标数据库（项目可能为 PostgreSQL 或 SQLite），若为 SQLite 则不应依赖 `rowcount` 去重。
- **frozen dataclass**：虽然不可变，但如果内部包含可变字段（如 `list`、`set`），则仍不安全。审查应检查 `QuotaResetResult` 是否包含可变类型（本例中没有）。
