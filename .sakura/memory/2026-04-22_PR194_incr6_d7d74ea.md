## 2. 发现的模式

### 审查行为模式：规则过度执行
```
分析结论："这本身是安全的"
↓ 触发"安全类禁止降级"规则
↓ 规则覆盖分析
输出结论：major
```

这是典型的**规则驱替判断**——当规则与实际分析冲突时，没有回溯检查规则适用性。

### 代码模式
- 开发者安全意识在进步：从完全无防护 → resolve校验 → 显式symlink检查
- `_is_safe_path`的字符串拼接是真实存在的代码味道，但不是bug

## 3. 规范完善建议

### 需修正的规则

**"安全类禁止降级"增加适用前提：**
```
原规则：安全类禁止降级
修正为：安全类禁止降级，但满足以下条件时除外：
  - 审查员自身分析已证明当前机制可防护
  - 标记的问题属于"更安全写法"而非"存在绕过"
```

**新增规则"分析否定则降级"：**
> 如果评论的分析部分得出"这本身是安全的"或"实际不会"等否定性结论，该问题必须降级为suggestion或移除。禁止在分析否定后仍标记major/critical。

**强化"自检消除矛盾"执行：**
> 当前规则仅提到"让步句式"，需要扩展：问题状态表与具体评论之间不能存在同一问题的矛盾判定。

## 4. 经验教训

### 路径安全的"证明责任"在审查员
标记安全问题时必须构造**具体攻击路径**：
- ❌ "如果symlink指向外部文件..."（假设链，无具体触发条件）
- ✅ "当`clean_path = '../../etc/passwd'`时，`resolve()`后为`/etc/passwd`，不以`repo_root`为前缀，`_is_safe_path`抛出异常"（已证明被防护）

### `resolve()` + 前缀检查已构成完整防御
symlink的两种攻击向量：
1. 指向仓库外 → `resolve()`暴露真实路径，前缀检查失败 ✅ 已防护
2. 指向仓库内 → 行为等同于读取仓库文件，非安全风险 ✅ 符合预期

不需要在每个分支都显式`is_symlink()`，那是冗余防御。
