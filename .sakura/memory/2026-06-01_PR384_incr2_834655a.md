## 代码审查反思报告

### 1. 审查质量评估

*   **覆盖度**：本轮审查覆盖面较广，涵盖了同步I/O、i18n、语义变更、命名约定等不同层面的问题，从代码质量到用户体验均有触及。未发现明显遗漏的重大逻辑缺陷或安全问题。但对新增 `candidate_service.py` 中“仓库级最新审查”匹配策略的**风险深度评估可能不足**。当前仅标注了“需确认”和建议文档化，但未进一步分析在具体业务场景下（如对一个新PR快速执行多次 `/agent`）可能产生的具体副作用（如引入无关历史上下文导致LLM幻觉），或评估是否有更稳妥的、兼顾“跨PR上下文复用”与“避免意外匹配”的折中方案。
*   **准确度**：问题定位准确，严重程度划分基本合理。对异步阻塞和i18n缺失标为 `major` 是恰当的，因为它们直接影响了系统性能和用户体验（虽然是admin页面）。将“语义变更”和“命名约定依赖”标为 `minor` 也符合其风险等级（逻辑可能不符预期，但通常不会导致崩溃）。
*   **完整性**：审查报告结构清晰，完整追踪了历史问题的状态，并区分了“重要问题”和“优化建议”。对变更的意图（如worktree管理、分支命名优化）有较好的理解。但在“优化建议”部分，对 `_update_pr_body` 异常处理契约的建议（第5点）和模板安全实践的建议（第6点），在完整报告中因聚焦主要问题而未展开，可能降低了给开发者的可操作指导。

### 2. 发现的模式

*   **代码模式**：
    *   **并发控制**：项目倾向于使用**乐观锁**（`UPDATE WHERE updated_at=...`）来解决并发状态更新问题，这是在Web场景下的合理选择。
    *   **代码复用**：积极使用**辅助方法提取**（`_accumulate_iteration_cost`, `_validate_max_files`等）来减少重复，表明团队有良好的重构意识。
    *   **防御性编程**：存在对潜在问题的**注释性防御**（如 `get_task_worktree_path` 的双重检查、`candidate_service` 的语义变更说明），这是一种平衡速度和安全的做法，但需警惕“注释代替解决方案”可能带来的维护债务。
*   **架构观察**：
    *   **异步/同步边界**：项目明确要求异步路由中的同步I/O必须用 `asyncio.to_thread()` 包装，这是一个**重要的架构规则**。本轮再次出现此问题，说明该规则的落实和自动化检查可能存在缺口。
    *   **模板与前端交互**：UI逻辑部分在Jinja模板中内联（`onclick`），这降低了可维护性。向 `data-*` 属性迁移的建议反映了更现代、更安全的前端实践趋势。
    *   **配置与状态管理**：`_repo_locks` 从无限增长到设置上限并FIFO淘汰，是处理进程内缓存状态的典型模式演进，体现了对长时间运行服务资源管理的重视。

### 3. 规范完善建议

*   **新增规则 - “语义变更审查”**：当代码修改了现有函数、查询或条件的**业务语义**（即使逻辑更简单、看似更合理），且影响范围不确定时，应要求：
    1.  在PR描述或代码注释中明确变更的**原始意图**。
    2.  评估对**现有调用方**的影响（是否所有调用场景都适用新语义？）。
    3.  考虑是否需要在**方法文档（docstring）** 中明确新契约。
    *   *本PR案例*：`candidate_service` 中移除 `pr_id` 过滤。
*   **强化规则 - “异步路径同步IO检查清单”**：在审查任何 `async def` 路由或函数时，应系统性检查其调用链中是否包含：
    *   文件系统操作（`open`, `stat`, `glob`, `rglob`）
    *   同步网络/HTTP请求
    *   同步数据库操作（非ORM的async方法）
    *   同步的CPU密集型计算
*   **项目特定规范 - “i18n键值同步验证”**：对于新增或修改的模板文件，审查时应将提取的 `_('key')` 列表与目标语言文件（如 `en.yaml`）进行**交叉验证**，可作为CI检查项。

### 4. 经验教训

*   **增量审查的“完整性幻觉”**：聚焦增量diff能高效发现新引入的问题，但可能弱化了对**变更在完整上下文中的意义**的思考。例如，只看到删除了 `pr_id` 过滤，但需主动思考：“这个修改是为了支持什么新用例？可能破坏什么现有用例？”
*   **“已修复”的验证责任**：标记历史问题“已修复”时，必须基于**当前diff的具体代码**进行确认。本审查中对历史问题的验证是扎实的（如给出了具体行号和模式）。这提醒我们，审查结论必须可追溯。
*   **工具生成结论的校准**：审查工具生成的结构化JSON（如 `SAKURA_REVIEW_JSON`）提供了良好骨架，但**决策理由（`decision_reason`）** 和**问题描述（`description`）** 的深度需要人工校准。例如，将i18n缺失描述为“不影响崩溃但影响体验”，就比单纯列出缺失键值更具指导性。
*   **防御性代码的注释必要性**：当代码中存在看起来冗余或反直觉的检查时（如 `get_task_worktree_path` 的二次路径检查），添加简短注释说明其**防御性目的**（“防止跨仓库路径穿越”）是极好的实践，能极大降低后续维护者的困惑。

### 5. 增量审查反思

*   **问题解决度**：新增的4个提交**确实解决**了上轮审查提出的核心历史问题（TOCTOU、内存增长、代码重复）。审查准确捕捉到了这一点，并给予了肯定。
*   **新风险引入**：增量变更**明显引入了新的风险点**，主要集中在：
    1.  **性能风险**：同步文件系统遍历（`rglob`）阻塞事件循环。
    2.  **功能风险**：i18n键缺失导致UI不可用。
    3.  **逻辑风险**：候选服务查询语义变更可能在特定场景下产生非预期行为。
*   **覆盖度平衡**：由于是增量审查，关注点自然聚焦于新增代码。但对**新增路由（`worktree_list_fragment`, `delete_worktree`）的认证/权限保护**未进行深入检查，这是潜在的覆盖盲点。项目记忆中的“WebUI/Dashboard API 认证链路”规则应在此类审查中主动应用。

**总结**：本轮审查质量良好，有效识别了增量代码中的关键改进和遗留问题。主要的反思点在于，对“语义变更”的影响评估可以更深入，并且在增量审查中需保持对新增端点安全属性的警惕。审查中提出的规范完善建议（特别是关于语义变更和异步IO检查的）若能融入团队流程，将有助于系统性地提升未来审查的效力和效率。
