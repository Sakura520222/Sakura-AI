### 3. 规范完善建议

建议在项目记忆或审查规则中新增/强化以下内容：

- **自动补丁验证规则**：任何由机器人自动提交的修复，审查时必须增加一步“补丁应用后文件语法完整性检查”，并输出 `compile()` 或 lint 结果；若检查失败，自动标记 `blocker`。
- **增量审查上下文扩展规则**：对于涉及 `try/if` 等块结构内修改的增量，审查要求必须获取变更块所在的完整函数/方法上下文，严禁只看 diff 片段来判断缩进。
- **“部分修复”高亮规则**：当变更行数中出现同一逻辑块（相同 if 条件、相同 except 头）同时存在于新增行与未删除旧行时，触发“可能为重复替换失败”的提示，自动升级为重点关注。
- **Python 项目特定**：缩进损坏直接导致 `IndentationError` 时，应一律标记为 `critical` 且决策 `request_changes`，无需讨论。

### 4. 经验教训

- **对自动修复的信任需要验证机制**：AI 生成的补丁在语义上意图正确，但物理形式可能完全错误。未来若开放自动修复功能，必须内建语法检查沙箱，验证通过后才能推送分支或提交。
- **增量审查不能仅依赖 diff**：这次审查者明确查看了 HEAD 分支的实际完整文件内容，才得以发现缩进错误和旧代码留存。这验证了一个好习惯：当 diff 涉及缩进敏感区域时，务必拉取完整上下文。
- **日志升级类修改的审查要点**：除了确认日志方法名更改，还需要确认新日志语句所处的控制流和缩进未被动到。这在 Python 中尤其重要。
- **重复结构的自动检测**：出现两个完全相同的 `if not (0.0 <= val <= 1.0):`、两个 `except (ValueError, TypeError):` 时，即使没有语法错误，也应作为“代码异味”提示，可能存在未完成的合并。
