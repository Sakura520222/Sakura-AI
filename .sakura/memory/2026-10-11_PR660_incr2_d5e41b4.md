### 2. 发现的模式与架构观察

- **代码模式**：
  - **幂等补救型并发控制**：项目采用“非锁定首读试探 → 唯一冲突回滚内层事务 (`begin_nested`) → `with_for_update` 锁定读赢家”的渐进加锁模式，既规避了高频场景下的 Next-Key Lock 互锁，又保障了单财务事实的一致性。
  - **防御性探测（Probe & Retain）**：在执行物理删除前，通过对全域财务模型依次加锁探测（`limit(1).with_for_update()`）实现软/硬删除的分流，展示了极强的合规与审计意识。
- **架构观察**：
  - **模块化依赖边界与配置层的张力**：`backend/core/config.py` 作为全系统基础设施，承担了配置解析与环境变量加载，但业务扩展引入可选支付网关（如 Paddle）时，容易因顶层静态导入或动态下拉框求值破坏配置层的低耦合性，形成架构“倒灌”。

### 3. 规范完善建议

基于本次审查暴露的模式，建议在项目记忆中补充/更新以下规则：

1. **探测锁防线 (Locking Probe on Indexed Columns Only)**：
   - 规则描述：任何在事务中执行 `SELECT ... FOR UPDATE` 或 `EXISTS(...) FOR UPDATE` 的探活/防删探测查询，其过滤列（如 `user_id`）**必须具备显式索引**。若关联模型外键无索引，禁止直接使用行级锁探测，须改用只读快照读探测或优先补齐索引迁移，防止扫描锁蔓延全表导致核心事务（如支付下单）受阻。
2. **多轮增量“遗留项生命周期”跟踪规范**：
   - 规则描述：当非阻断项（如 Core Config Isolation 违规）连续累积超过 2 轮审查未闭环时，即便单轮增量代码质量极高，也应在 PR 最终合入前强制建立跟踪 Issue 或在 PR Description 显著位置打上 `Tech-Debt` 标记，避免技术债随 PR 完结而遗忘。

### 4. 经验教训

- **注意“只读探测”与“行级写锁”的本质差异**：
  - 在设计防删/存在性校验逻辑时，开发者习惯直接加上 `.with_for_update()` 以防并发删除，但在无索引列上这等同于全表锁定。在未来审查 ORM 数据流时，只要看到 `for_update()`，必须立即交叉检查对应数据模型的 `index=True` 声明。
- **Fail-Closed 原则在计费迁移中的落地**：
  - 本次 PR 在“退款元数据解析损坏”和“多订单模糊匹配”时，严格回滚并抛出专用异常而不产生财务效果，是 Fail-Closed 的标准范式。未来审查金融类改动应持续将其作为金标准。
