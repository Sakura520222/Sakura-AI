## 2. 发现的模式

### 代码模式

本项目存在一个值得长期关注的模式：

- 多处定义相似的 duration 格式化函数；
- 函数名相似或相同，例如 `_format_duration`、`_formatDuration`；
- 但格式化语义并不完全一致：
  - `backend/main.py`：一位小数秒；
  - `dashboard.html`：一位小数秒；
  - `queue.py` / `deps.py`：整数截断秒。

这种模式容易导致审查和维护时出现误解：

- “后端格式化函数”这个说法过于宽泛；
- 不同文件中的同名私有函数可能服务于不同业务上下文；
- 单纯基于函数名判断一致性风险较高。

### 架构观察

当前架构有如下特点：

1. **后端存在公共信息聚合函数**
   - 历史审查中已经将系统信息逻辑抽取到 `backend/main.py:get_system_info_dict()`。
   - 这说明项目倾向于将 dashboard / API / WebUI 共用信息集中在 `main.py` 或公共模块中。

2. **WebUI 前端仍有部分展示逻辑**
   - `dashboard.html` 中包含 JS 格式化逻辑。
   - 这会带来前后端展示语义同步问题。

3. **不同上下文下的 duration 语义可能不同**
   - 启动耗时展示追求更精确，一位小数合理；
   - 队列平均耗时或其他统计场景可能故意使用整数秒；
   - 因此不应机械要求全仓所有 duration 都一致，应该先确认业务上下文。

## 3. 规范完善建议

### 建议新增审查规则：同名私有工具函数需按上下文核对

当项目中存在多个同名或近似同名的私有工具函数时，审查不能只根据函数名判断一致性，应核对：

- 所在模块；
- 调用方；
- 展示场景；
- 输出是否进入同一个 UI / API 契约；
- 是否存在用户可见的不一致。

建议规则：

> 对 `_format_duration`、`format_xxx` 等展示格式化函数进行审查时，应先确认调用上下文。只有同一业务对象、同一展示位置或同一 API 契约下的格式差异才应标为问题；跨场景差异应作为可维护性建议，而非默认阻断。

### 建议新增审查规则：注释类 PR 的审查重点

对于只修改注释的 PR，应重点检查：

1. 注释是否与代码事实一致；
2. 注释是否引用了易变实现细节；
3. 注释是否可能误导未来维护者；
4. 是否掩盖了未解决的真实行为差异；
5. 是否需要改代码而不是加注释。

本次注释是事实正确的，但引用 `backend/main.py._format_duration` 这种私有函数路径，未来如果函数迁移或重命名，注释可能过期。可作为轻微维护性关注。

### 建议修改结构化评论规则

本次“总结”被列入主要评论不太合适。建议强化：

> 只有可定位、可操作的问题或建议才生成 review comment；总结、评分、整体结论不应作为单独评论提交。

## 4. 经验教训

### 经验一：历史审查结论要重新定位对象

历史问题中提到“后端 `int(seconds)` 与前端 `toFixed(1)` 不一致”，但本轮发现：

- 如果对比对象是 `backend/main.py`，则不存在不一致；
- 如果对比对象是 `queue.py` / `deps.py`，确实存在格式差异，但可能不是同一展示链路。

因此未来审查中，看到“前后端不一致”这类历史结论时，要重新确认：

- 具体是哪一个前端函数；
- 具体是哪一个后端函数；
- 两者是否服务于同一数据路径；
- 是否真实出现在同一个用户界面或 API 返回中。

### 经验二：注释可以澄清问题，但不能替代行为统一

本轮注释有效澄清了：

```js
// 注意：格式与 backend/main.py._format_duration 保持一致（一位小数）
```

这能减少未来审查误判。

但如果项目未来希望全局统一 duration 格式，仍应考虑：

- 抽取公共格式化约定；
- 明确不同场景的格式标准；
- 在 API schema 或文档中注明；
- 避免多个私有函数各自演化。

### 经验三：小 diff 也要检查元信息一致性

虽然本轮只有一行注释，但 PR 描述仍是完整功能需求。审查时需要明确：

- 本轮增量是否只是补充说明；
- 完整功能是否已经在之前提交实现；
- 当前 approve 是针对增量，还是针对整个 PR 当前状态。

这可以防止“小变更 approve”被误读成“整个功能链路已重新完整验证”。

## 5. 增量审查反思

### 新增提交是否解决了之前审查提出的问题？

部分解决，或者更准确地说：**澄清了之前问题中的对比对象**。

> 前端 `toFixed(1)` 与后端 `int(seconds)` 可能不一致。

本轮注释说明前端实际上是与 `backend/main.py._format_duration` 对齐，而该函数确实是一位小数。因此：

- 如果历史问题目标是 dashboard 启动耗时展示与 `main.py` 一致，那么本轮已经解决疑义；
- 如果历史问题目标是全仓 duration 格式统一，那么本轮没有解决，只是补充说明。

审查报告中对此区分得比较好，但可以再明确一句：

> 本轮不要求统一 `queue.py` / `deps.py`，因为它们不属于当前启动耗时展示链路。

### 增量变更是否引入了新的风险？

风险很低。

新增的是注释，不改变运行时行为。

潜在轻微风险是：

- 注释绑定了私有函数路径 `backend/main.py._format_duration`；
- 未来如果该函数改名、迁移或语义变化，注释可能过期；
- 但这属于维护性风险，不构成阻断。

### 审查覆盖度是否因只看增量部分而下降？

有一定下降，但在本轮场景下可以接受。

由于这是增量审查，审查重点放在新增注释是合理的。不过仍应在报告中显式说明：

- 未重新验证完整启动耗时记录链路；
- 未重新验证 API / WebUI / 测试整体一致性；
- 仅验证本次新增注释与当前相关实现一致。

这类声明可以提升审查边界的透明度。
