## 3. 规范完善建议

### 新增/强化审查规则

| 规则 | 严重度 | 说明 |
|------|--------|------|
| **重复逻辑 ≥2 次但未抽取** | minor | 当前规则是“≥2 次抽取”，但可增加例外说明：若逻辑极简（1-2 行）且未来扩展性低，允许不抽取，但须注释。 |
| **全局导入与局部导入冲突审计** | major | 若某符号已在模块顶层导入，函数体内不得再延迟导入，除非有明确的循环引用注释。 |

### 项目特有规范要点
- **异步测试强制要求**：当新增异步函数（如 `fetch_provider_models`）或装饰器（如 `@limiter.limit`）时，必须同步提供异步测试用例，否则阻断合并。
- **XSS 防护统一函数**：建议在前端提供 `escapeHtml(message)` 工具函数，所有 toast 调用统一使用。

## 4. 经验教训

### 值得在未来审查中关注的要点
- **限流+超时的成对检查**：每当你看到一个 `@limiter.limit`，必须同时检查该接口内部所有外部 IO（HTTP、DB、Redis）是否设置了显式超时。
- **重复代码的“隐性重复”**：`startswith("/") + 切片` 虽然只出现 2 次，但出现在两个不同层次（`_build_base_url` 内外），应优先消灭在更底层。
- **测试覆盖的“假阳性”**：新增 59 行测试 ≠ 覆盖了关键分支，必须检查边界用例（如 `/models` 带或不带斜杠）。

### 对特定技术/模式的审查经验
- **Jinja2 模板中的 JS 安全**：不要只看是否用了 `{{ }}`，还要看 JS 中是否将服务端变量赋值给 DOM 属性（如 `innerHTML`）。
- **`alert()` 替换为 toast**：是好实践，但必须验证 `showToastMsg` 内部是否安全（本案例中发现了 `innerHTML` 问题）。
