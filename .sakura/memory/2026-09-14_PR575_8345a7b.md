## 2. 发现的模式  

### 代码模式  
1. **统一依赖声明**：项目在 `pyproject.toml` 与 `requirements.txt` 中保持 1:1 镜像，遵循 “代码即配置” 的原则。  
2. **子项目独立**：`sandboxer`、`updater` 各自拥有独立的 `pyproject.toml`，而不是使用根项目的 `[tool.poetry]` 继承，这导致 **版本漂移** 成为潜在风险。  
3. **依赖约束宽松**：所有 pydantic 约束均使用 `>=`，未锁定上限，旨在兼容未来的次要/补丁升级。  

### 架构观察  
- **单体 + 多子包**：根项目提供核心服务，子项目 (`sandboxer`, `updater`) 以独立包形式存在，且在运行时会相互调用（如协议模型共享）。这种结构在 CI 中需要 **多套 lock**，否则易出现 **锁文件不一致** 的问题。  
- **UV 作为主要包管理工具**：但 CI 仍使用 `pip -r requirements.txt`，形成 **双轨依赖解析**（uv vs pip），导致锁文件失效时仍能通过 CI，降低了锁文件的实际约束力。

## 3. 规范完善建议  

| 现有缺口 | 建议的审查规则或改进 |
|----------|--------------------|
| **锁文件同步** | - 新增规则：**每次修改 `pyproject.toml`、`requirements.txt`、或任何 `*_lock` 文件时，必须在同一 PR 中提交对应的锁文件更新。** <br> - 自动化检查：CI 中加入 `uv lock --check`（或 `uv sync --locked`）步骤，若锁文件过期即失败。 |
| **子项目依赖一致性** | - 规则：**所有子项目的关键依赖（如 pydantic、fastapi）版本下限必须与根项目保持一致**，除非在 PR 描述中明确说明不同步的原因。 <br> - 实现方式：在审查脚本中使用 `rg "pydantic" --glob "**/pyproject.toml"` 并比对版本号。 |
| **文档/示例同步** | - 规则：**README、AGENTS.md、CI 示例等出现的依赖约束必须与实际 `pyproject.toml` 保持同步**。 <br> - 检查点：搜索 `pydantic>=` 关键字，确认无硬编码旧版本。 |
| **升级后兼容性回归** | - 规则：**每次提升关键库的下限（尤其是大型库如 pydantic、fastapi）后，必须运行项目的完整单元/集成测试并确保通过**。 <br> - 可在 CI 中加入 `pytest -m "pydantic"` 之类的标签化测试，确保覆盖模型序列化、校验路径。 |
| **依赖约束风格** | - 建议统一使用 **`pydantic>=2.13.5,<3`**（或上限锁定）以防止未来的破坏性大版本升级意外进入。<br> - 若坚持宽松约束，需在审查中明确评估 “上游大版本破坏性改动” 的风险。 |

## 4. 经验教训  

1. **锁文件不是可选项**  
   - 即使 CI 采用 `pip`，项目文档与开发者仍依赖 `uv lock`，锁文件失效会导致本地与 CI 环境不一致，影响可复现性。审查时必须把锁文件的同步视作 **阻断项**（error/major），而非 minor。  

2. **子项目的依赖一致性**  
   - 多子包结构下，单独维护依赖会产生“版本漂移”。在升级根项目关键依赖时，审查应主动检查 **所有子项目**，并在 PR 描述中要求同步或给出充分解释。  

3. **文档与代码的双向校验**  
   - 项目文档（README、AGENTS.md）中出现的安装指令往往是使用者的第一手参考。审查应把这些文档列入 **代码一致性检查范围**，防止文档落后导致用户在本地遇到锁文件或版本冲突。  

4. **升级后兼容性验证不可省**  
   - 对于像 pydantic 这类 **API 频繁演进** 的库，仅靠“语义兼容（>=）”并不足以保证运行时不出错。应在审查流程中加入 **兼容性回归**（运行所有模型相关的测试），并在审查报告里明确验证结果。  

5. **审查策略要匹配变更风险**  
   - 本次使用 **quick** 策略对仅两行依赖变更进行审查，虽然风险相对低，但因为涉及锁文件和子项目同步，仍建议提升为 **full** 或 **medium** 检查，以确保不会遗漏隐藏的兼容性问题。

### 小结  

本次审查在捕获关键风险（锁文件失效、子项目版本漂移）方面表现优秀，标记的严重程度也恰当。但仍有提升空间：  
- 将锁文件同步提升为阻断项；  
- 加入对所有子项目依赖的一致性检查；  
- 扩展兼容性回归测试覆盖；  
- 确保文档与实际依赖保持同步。  

通过在审查规则中加入上述检查点，可显著提升项目的可复现性、维护一致性以及对依赖升级的安全性。祝后续 PR 顺利合并 🚀。
