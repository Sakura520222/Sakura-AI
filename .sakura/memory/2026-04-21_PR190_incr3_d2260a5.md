# 审查反思报告

## 1. 审查质量评估

### 覆盖度：严重不足
本次审查犯了增量审查最典型的错误——**隧道视野**。只盯着 +16 行 diff 说"干净、聚焦"，却完全无视了历史上下文中明确标注的两个重大遗留问题：
- 多文件提交非原子性（`github_write_service.py:76`）
- 单例线程安全问题（`github_write_service.py:28-31`）

`decision: approve` 是 PR 级别的结论，但审查过程完全没有验证这两个 block 级问题是否已修复。这在逻辑上是断裂的——"本次提交没问题"≠"这个 PR 可以合并"。

### 准确度：评分失真
在存在未关闭重大问题的上下文中给出 9/10 高分，评分体系失去了区分度。如果历史问题仍然存在，这个 PR 的整体质量上限应该是 7 分左右；如果问题已修复，审查应该**明确确认**这一点并说明理由，而非直接跳过。

### 完整性：上下文利用率为零
历史上下文提供了精确到行号的问题定位和演变脉络，但本次审查没有任何引用或回应。这等同于丢弃了前 5 轮审查积累的知识价值。

## 2. 发现的模式

**代码模式**：本次提交本身质量不错——聚焦单一职责（历史上下文传递）、最小化改动、通过日志增强可观测性而非侵入式重构。这是渐进式开发的良好实践。

**架构观察**：变更路径 `review_worker.py → sakura_memory_service.py` 符合已有的 worker→service 分层，没有引入新的依赖方向。但这恰恰说明本次变更是"安全区"操作，审查应该把精力放在"非安全区"（即历史问题涉及的文件）。

## 3. 规范完善建议

### 新增审查规则

**规则：增量审查的历史问题回溯**
> 当审查上下文中存在 severity ≥ `warning` 的未关闭问题时，增量审查的决策和评分必须显式处理这些问题的状态。可选处理方式：
> - 确认已修复（需简要说明修复依据）
> - 确认仍未修复（需在评论中重新标记，评分不得高于 7 分）
> - 明确标注"仅评估增量，未验证历史问题"（此时 decision 不应为 approve）

**规则：评分与决策的解耦**
> 评分可以反映增量变更的质量（如本次 9 分合理），但 `decision` 必须反映 PR 整体可合并性。当存在未解决的重大问题时，即使增量评分很高，decision 也应降级为 `request_changes` 或至少 `comment`。

## 4. 经验教训

**核心教训：quick 策略不等于放弃全局判断**

quick 策略的设计初衷是减少对单个提交的审查深度，但不应因此跳过 PR 级别的质量门禁。正确的做法是：
- diff 分析可以用 quick 模式（不逐行深挖）
- 但决策环节必须执行一个轻量级的 checklist，其中"历史问题状态验证"应是必选项

**对热点文件的警惕**：`github_write_service.py` 在 5 轮中 4 轮被标记，属于系统性问题高发区。即使本轮未修改该文件，在做出 approve 决策前也应确认其当前状态。
