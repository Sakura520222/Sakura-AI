# 审查反思：PR #190 提交 7dd4a7c

## 1. 审查质量评估

**覆盖度：局部精准，全局失守。**
对 +37/-12 的增量代码审查非常到位——正则 lookahead 边界遗漏、大小写不一致、重复结构三个发现都是真实且有价值的。但这是一个本末倒置的精准：在仍有未闭环 PR 级严重问题的前提下（线程安全竞态、非原子提交），对一处解析优化给出 approve，等于在着火的房子里表扬窗帘的颜色。

**准确度：严重程度判定合理，但决策矛盾。**
三个发现分别标为建议/优化，技术判断正确——正则边界问题确实是低概率边缘场景，不属于 error 级别。**问题在于决策逻辑**：项目记忆明文规定"存在未闭环 critical 问题时，decision 必须降级为 comment 或 request_changes"，本次审查直接 approve，违反了自己建立的规范。

**完整性：上下文利用到位但结论割裂。**
历史问题追踪表做得很好，显式标注了第5轮问题的修复状态。但追踪表中**缺失了两个持续未解决的 critical 问题**（`github_write_service.py` 线程安全、非原子提交），这要么是遗忘，要么是有意回避。

## 2. 发现的模式

**代码模式：LLM 输出解析的防御性分层**
三层回退（精确标记 → 宽松标记 → 标题分割）是处理非结构化 LLM 输出的经典模式，设计合理。但正则解析天然脆弱，每一层的边界条件（lookahead 终止符、大小写敏感）都是潜在漏洞点。本次发现的两个问题本质相同：**防御逻辑在不同层之间的一致性缺失**——check 用 `lower()`，split 用原串；`sakura_md` 的 lookahead 考虑了 `MEMORY_MD_START`，`memory_md` 却没有对称地考虑 `SAKURA_MD_START`。

**架构观察：`sakura_memory_service.py` 持续膨胀**
项目记忆已标记该文件为"上帝服务"前兆（超800行），本次又增加解析逻辑。解析 LLM 响应本质上是独立的关注点，应考虑抽离为独立的 parser 模块，而非在 service 中不断追加。

## 3. 规范完善建议

**新增规则：PR 级阻断表必须强制出现在每次增量审查输出中**
当前的历史追踪表由审查者自由决定包含哪些问题，导致本轮直接遗漏了两个 critical。应规定：项目记忆中标记为"遗留关注点"的问题，必须在每次审查的追踪表中出现，状态只能从"遗留"变为"已修复"或"确认仍遗留"，**禁止不出现**。

**新增规则：quick 策略的 approve 必须经过阻断检查清单**
quick 策略可以减少评论深度，但 approve 决策前必须显式回答：PR 级遗留 critical 是否为 0？如果不是，decision 自动降级为 comment。

## 4. 经验教训

**防御性代码的"镜像一致性"原则**
当为 A/B 两个对称结构编写防御逻辑时，A 考虑的边界条件必须镜像检查 B 是否也覆盖。本次 `sakura_md` 和 `memory_md` 的 lookahead 不对称就是典型违反。审查时看到对称代码结构，应主动做差异对比。

**大小写归一化的"贯穿性"原则**
`lower()` 用于判断但原串用于操作，是防御性编程中极常见的漏洞模式。一旦在某处引入归一化，必须追踪该变量后续所有使用点是否也归一化，否则防御形同虚设。

## 5. 增量审查反思

**新增提交的价值：确实解决了第5轮提出的防御性不一致问题**
三层提取策略是对之前零散防御代码的系统化重构，方向正确。但本轮发现的大小写问题和 lookahead 不对称说明"系统化"做得还不够彻底。

**引入的新风险：低**
变更范围小且集中在解析逻辑内部，不涉及 IO、并发、权限，引入新 bug 的概率低。

**覆盖度下降：典型表现**
增量审查只看 +37/-12，完全忽略了这些代码所处的 PR 上下文（+1875/-34，包含安全敏感的写服务）。结果是：对一片树叶的纹理分析得很细，但没注意到树根在腐烂。**这恰好印证了项目记忆中记录的"隧道视野"陷阱——本次审查中了招。**

---

**一句话总结**：这是一次高质量的局部代码审查，但作为 PR 级别的质量守门，它因遵守增量边界而放弃了全局责任，违反了自身建立的阻断机制，决策应为 `comment` 而非 `approve`。
