### 2. 发现的模式与架构观察

*   **业务层“两段式准入/补偿”模式**：`prepare_admission` + `admit_reanalysis_operation`。在外部调度（如 Worker/队列）可能失联的情况下，使用 `submission_acknowledged=False` + `pending_reconciliation` 状态机，兼顾了可用性与记账防漏，属于成熟的分布式事务补偿模式。
*   **架构风险：全局配置（`config.py`）与业务领域能力（Payment SDK）倒置依赖**：
    *   `config.py` 直接导入具体的 `paddle_capabilities` 并在顶层求值 `DYNAMIC_CONFIG_SELECT_OPTIONS`。
    *   **架构反模式**：核心配置中心应是无状态、最轻量的基础层，过早引入外部重型 SDK 会导致全应用级启动脆弱性（如任何导入级副作用都会使无关子系统瘫痪）。

### 3. 规范完善建议（拟增入项目记忆）

1.  **全局配置层懒加载与依赖隔离原则（Core Config Isolation）**：
    *   `backend/core/config.py` 禁止在模块顶层静态导入具有外部三方依赖或可选组件的 domain/services 模块；
    *   动态选择器（如下拉币种/模型列表）须采用**函数化惰性加载（Lazy/Callable Provider）**或在运行时首次请求时解析，防止三方 SDK 缺失引发全系统启动崩溃。
2.  **端点级多语言解析契约统一（Endpoint i18n Consistency）**：
    *   同一 API/路由端点内，所有显式异常抛出分支（如校验阶段 409、入场阶段 402/429）必须统一解析语言（`lang=user_lang`），避免前置校验用系统默认语言、后置逻辑用用户首选语言的双重体验割裂。

### 4. 经验教训

*   **区分“理论设计降级”与“物理运行依赖”**：
    *   在底层写了 `try ... except ImportError` 优雅降级，但在上层模块（如配置或工厂）被无保护地顶层 `import`，是常见的降级假象。审查带有“降级分支”的改动时，必须全局搜索该 SDK 是否在其他公共入口被硬引用。
*   **金融/计费准入的“零信任输入”**：
    *   客户端传参不能作为账单主体（Payer），必须由服务端上下文强行覆盖。本次审查对 `trigger_user_id` 与 `billing_user_id` 鉴权覆盖的核查非常具有样板意义。
