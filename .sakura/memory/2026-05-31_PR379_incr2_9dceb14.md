技术判断总体准确。

```python
module_scope_user = None if scope_filter is None else user["sub"]
```

与 `build_user_scope_filter` 的 admin/普通用户语义一致，这一点判断合理。

对四个模型的权限条件判断也较稳妥：

不过有两个准确性问题需要反思：

   这是明显不一致的。既然正文说“无重大问题”“可选建议”，就不应标为 `major`。这类评论会误导后续自动化流程或维护者判断。

   历史上下文显示上一轮 `request_changes` 有多个 major 风险。本轮新增提交只修复了其中一个 dashboard 权限问题。若其他问题仍未修复，整体 PR 不应 approve，除非审查系统支持“仅对该提交 approve”。

## 2. 发现的模式

### 代码模式

本次变更体现出项目中一个常见模式：

- 服务层负责聚合查询逻辑
- API 与 WebUI 分别作为两个入口调用同一服务函数
- 权限过滤通过 `scope_filter is None` 判断 admin/非 admin
- 普通用户身份使用 `user["sub"]`，通常对应 GitHub 用户名
- 查询层使用 SQLAlchemy `select`、`func.coalesce`、`func.sum` 做统计聚合

这类模式的好处是 API 和 WebUI 复用同一服务函数，权限语义容易保持一致。

但风险点也明显：

- 如果服务函数新增权限参数，所有调用点必须同步更新
- 如果某个 dashboard 聚合函数忘记传 `scope_user`，就可能产生横向数据泄露
- 如果不同聚合函数各自实现过滤条件，容易出现 `fetch_token_trend` 与 `fetch_module_token_stats` 不一致的问题

### 架构观察

项目结构大致分层清晰：

- `backend/api/v1`：API 路由
- `backend/webui/routes`：WebUI 路由
- `backend/services`：业务服务与聚合查询
- models 层由服务函数直接引用做查询聚合

Dashboard 相关逻辑有一个明显特点：

> 同一份统计数据通常同时服务 API 与 WebUI，因此权限、字段契约、聚合口径必须保持双入口一致。

本次变更正是修复了服务层聚合函数没有完全承接入口层权限语义的问题。

## 3. 规范完善建议

### 建议新增规则：Dashboard 聚合函数必须显式接收权限范围

对于 dashboard、health、metrics、stats 这类展示型接口，容易被误认为“只是统计信息”，但实际可能包含用户成本、token 用量、仓库活动等敏感数据。

建议新增项目规则：

> 所有 dashboard/stats/metrics 聚合函数，如果数据源包含用户、仓库、成本、token、任务记录，必须显式接收 `scope_user` 或等价 scope 参数；admin 场景使用 `None` 表示不过滤，普通用户必须过滤。

同时检查：

- API 调用点
- WebUI 调用点
- 后台任务或内部调用点
- 测试 mock 签名

### 建议新增规则：同类统计函数的权限过滤口径必须对齐

本次问题本质上是 `fetch_token_trend` 已有权限过滤，但 `fetch_module_token_stats` 未同步。

建议规则：

> 同一 dashboard 页面中展示的多个统计模块，应共享相同的权限过滤口径；如果某个模型使用 `repo_owner OR author`，其他同类函数不得只过滤其中一个字段，除非有明确业务说明。

特别需要关注：

- `repo_owner`
- `author`
- `started_by`
- `triggered_by`
- `created_by`
- `user_id`
- `github_username`

这些字段语义相近但不完全等价，审查时不能机械替换。

### 建议修改规则：增量审查中历史问题状态必须分层表达

当前审查中“历史问题已修复”的表达对 dashboard 这一项是成立的，但容易让人误以为全部历史问题均已关闭。

建议规范：

```text
历史问题状态：
- 已验证修复：A，依据为 ...
- 本轮未覆盖：B、C、D，仍沿用上一轮结论
- 新增风险：无/有 ...
```

这样可以避免 approve 决策与历史 major 状态冲突。

### 建议加强结构化评论生成规则

本次主要评论里出现了很多摘要性内容被转成 `[suggestion]`，甚至出现 `[major]: 无重大问题`。

建议规则：

> 只有具体、可定位、可执行的问题才生成结构化 review comment。摘要、范围声明、正向评价、评分说明不得生成评论。正文称“建议/可选”的内容不得标为 major。

## 4. 经验教训

### 权限过滤修复不能只看入口层

入口层拿到了 `scope_filter` 不代表数据已经安全。真正关键的是：

- 服务函数是否接收 scope
- 查询条件是否应用 scope
- 所有聚合子查询是否都应用 scope
- API 和 WebUI 是否一致传参
- admin 与普通用户路径是否都有测试

本次修复比较好的地方是把过滤下沉到了 `fetch_module_token_stats` 内部，而不是只在路由层处理。

### 聚合统计接口也属于敏感数据接口

token 和 cost 聚合虽然不是原始业务数据，但依然可能泄露：

- 某个用户/仓库是否存在活动
- 大致调用量
- 成本消耗
- 模块使用频率
- 私有仓库的操作痕迹

因此这类接口应按敏感数据处理，不能因为是 dashboard summary 就放松权限审查。

### 嵌套 helper 的性能问题不应过度放大

本次建议中提到 `_scope_for`、`_aggregate` 每次调用都会重新定义。这个观察没错，但实际影响很小，属于可维护性建议，不应提高严重程度。

更值得关注的是：

- helper 是否准确表达权限语义
- 是否容易被其他函数复用
- 是否有测试覆盖 admin/user 两种路径
- 是否避免不同统计函数各写一套条件造成漂移

### 测试建议合理，但不应阻断

为 `fetch_module_token_stats(scope_user)` 补测试是合理建议。由于本次修复涉及权限过滤，测试价值较高。

不过在当前变更规模下，如果已有相邻测试覆盖 `fetch_token_trend`，且代码逻辑较直接，将其作为 suggestion/minor 合理，不必直接升为 major。

但如果项目此前正是因权限过滤缺失导致数据泄露，那么可考虑将“缺少回归测试”提升为 minor，而不是单纯 suggestion。

## 5. 增量审查反思

### 新增提交是否解决了之前审查提出的问题？

解决了其中一个明确问题：

> `backend/services/dashboard_stats_service.py` 中 dashboard module token/cost 聚合缺少权限过滤。

本次新增提交通过给 `fetch_module_token_stats` 增加 `scope_user` 参数，并在四类模型聚合中应用过滤，基本解决了该问题。

但历史上下文中还有多个问题未被本次提交覆盖：

- ShellTool 输出双层限制与敏感命令日志
- Agent Team PR review feedback 匹配唯一性
- feedback 并发插入竞态
- fake 查询与生产语义不一致
- issue suggested_title 与异常消息长度控制

因此不能把整个 PR 的历史问题状态概括为“已修复”。

### 增量变更是否引入了新的风险？

新增风险较低，但仍有几个点值得关注：

1. **调用点遗漏风险**

   本次只看到 API 和 WebUI 两个调用点已更新。若项目中还有测试、后台任务、脚本或其他服务直接调用 `fetch_module_token_stats`，可能因签名变更受到影响。审查中最好说明是否做过全仓搜索。

2. **权限字段语义风险**

   `AgentTeamTask` 使用 `repo_owner` 而不是 `started_by`，`RepoScan` 使用 `repo_owner` 而不是 `triggered_by`，这是为了与 `fetch_token_trend` 保持一致。该判断当前合理，但仍依赖项目业务假设：

   > 普通用户可见范围由仓库 owner 归属定义，而不是任务发起人定义。

   如果未来业务变成“谁触发谁可见”，这里需要重新审视。

3. **测试缺口**

   缺少针对 `scope_user=None` 与 `scope_user="xxx"` 的直接回归测试。权限过滤类 bug 容易回归，建议补轻量单测或 sqlite 集成测试。

### 审查覆盖度是否因只看增量部分而下降？

是的。

增量审查天然容易出现一个问题：

> 只确认当前提交修复了一个点，却忽略整个 PR 是否仍有未解决阻断问题。

本次审查在增量文件内做得较好，但对“当前 PR 是否可 approve”的判断受限。未来应在增量审查报告中增加一个固定段落：

```text
历史阻断问题复核：
- 本轮已验证修复：dashboard module stats 权限过滤
- 本轮未覆盖，仍需复核：ShellTool 输出限制、PR feedback 匹配与竞态、issue_worker 长度限制等
- 因此本轮结论仅适用于当前增量提交，不代表整个 PR 所有历史问题均已关闭
```

## 总体反思结论

本次审查对 dashboard 权限过滤修复的技术判断较准确，增量 diff 覆盖充分，建议也基本合理。主要不足不在代码理解，而在审查流程层面：

1. 没有清晰区分“当前增量提交通过”与“整个 PR 可合并”
2. 对历史 major 问题未给出逐项状态
3. 结构化评论严重程度存在明显噪声和不一致
4. PR 描述与实际增量 diff 的范围差异未明确说明

未来类似审查应坚持：

- 增量问题可以 approve，但历史 blocking 状态必须单独列明
- 权限过滤修复必须检查所有入口与所有聚合路径
- dashboard/metrics/token/cost 统计接口按敏感数据处理
- 摘要性内容不生成 review comment
- “无重大问题”不能标 `major`
