# 深度反思：PR #417 增量审查（incr2）

## 1. 审查质量评估

### 覆盖度：存在可疑的"零发现"

9 个文件、+252/-18 行变更，涵盖 webhook 去重、状态机新状态、repr 反序列化、搜索回退逻辑——审查结果为 **0 个新问题**，全部归入"正确修复"。这在统计上不正常：

- **search_files_tool.py 回退路径无性能边界**：非默认分支零匹配时逐文件搜索，若 PR 涉及 500+ 文件，将触发大量 API 调用。审查未追问速率限制或文件数量上限。
- **delivery_id 去重记录无清理机制**：`find_by_delivery_id` 查全状态记录，但无 TTL 或定期清理，属于"映射表清理对称性"原则的遗漏——只建不清理。
- **`skipped` 新状态的横向传播**：新增终态 `skipped` 后，审查未 grep 验证现有状态分支（switch/if-else）是否全部覆盖该状态，存在状态机逃脱路径遗漏风险。

### 准确度：严重度判定合理但偏保守

8 项"正确修复"的定性准确，终态缓存一致性、去重时序、untrusted 边界移动均有规则依据。但 **ReDoS 跨两轮增量未修复仍标 minor**，与"历史 major 阻断评分上限 ≤8"无直接冲突，却与安全修复的时效性原则矛盾——两轮未触碰的高危正则，应考虑升级阻断力度或至少在决策中明确附条件。

### 完整性：主要评论截断是严重缺陷

主要评论在 `(1) external_ci_` 处截断。这直接违反了"决策完整性声明"原则——comment 决策下存在未解决的 suggestion，但声明本身不完整，读者无法判断审查者的完整意图。

## 2. 发现的模式

### 代码模式
- **终态驱动缓存清除**：`finalize=True` 作为终态方法的语义标记，统一清除 `_check_run_ids` 缓存。模式一致但依赖命名约定而非类型系统。
- **Best-effort 反序列化 + 静默降级**：tool_call repr 解析失败回退空 id，与项目记忆中"恒定回退值/静默失败路径→标 major"存在张力。审查将其判定为"降级合理"，但未验证下游对空 id 的容忍度。
- **防御性去重前置于副作用**：delivery_id 去重在配额扣费之前，时序正确，属于成熟的 webhook 处理模式。

### 架构观察
- **状态机扩展方式**：通过新增 `skipped` 状态区分"PR 关闭取消"和"drain 跳过"，语义清晰。但状态枚举分散在 ORM 模型和业务逻辑中，缺乏集中定义。
- **Untrusted 边界作为安全架构原语**：`=== END UNTRUSTED ISSUE EVIDENCE ===` 标记线成为项目级的 prompt injection 防护约定，本次将 `.sakura/` 知识移入边界内是正确的架构对齐。

## 3. 规范完善建议

### 新增规则

**R1: 审查输出完整性校验**——提交前必须验证：(1) 主要评论无截断；(2) 所有引用的编号在问题表中可追溯；(3) 决策声明与问题表状态一致。本次截断是流程缺陷而非能力缺陷。

**R2: 新增状态机状态须全仓 grep 验证消费方**——现有"布尔标志参数全路径传播"规则应扩展为"状态枚举变更全路径传播"，覆盖 switch/if-else、状态断言、日志打印等所有消费点。

**R3: Best-effort 反序列化的下游容忍度必须显式验证**——不能仅因"降级合理"就通过，须追踪空值/默认值在下游是否触发异常或静默错误。与现有"恒定回退值标 major"规则对齐。

### 修改规则

**"映射表清理对称性"需增加时序维度**——现有规则关注" A 清理须同步清理 A→B 映射"，但未覆盖"新建映射而无清理计划"的场景。delivery_id 去重记录即属此类。

## 4. 经验教训

**"正确修复清单"≠"免检通行证"**：本次审查将 8 项变更逐一描述为"正确修复"，实质上是在复述 diff 而非审查 diff。正面评价越多越先做负面检查——这条原则被违反了。每个"正确"背后都应追问：边界条件？性能影响？横向一致性？

**跨增量持续存在的 minor 安全问题需要升级策略**：ReDoS 两轮未修复，审查仅重复"建议后续增量加输入长度限制"。对于安全类问题，应设定"N 轮未修复则升级严重度或改变决策"的 escalation 策略，否则 minor 永远是 minor。

**增量审查的"不在本轮变更行"不应成为免检理由**：对于前序 suggestion（external_ci_failures untrusted 包裹），虽然本轮未触及该文件，但本轮新增了 `.sakura/` 知识移入 untrusted 边界的修复——这说明开发者正在系统性处理 untrusted 边界问题。审查应主动关联："既然本轮修了 issue_analyzer 的 untrusted 边界，external_ci_failures 的同类问题是否应同步修复？"这比机械标注"延续存在-不阻断"更有价值。

## 5. 增量审查反思

### 前序问题解决情况
- 5 项前序问题中 2 项已修复（init.sql DDL、默认模板），修复质量经逐行验证，信任链完整。

- search_files_tool 的回退路径引入了非默认分支下的 O(files) API 调用，这是增量引入的性能风险，被遗漏。

### 覆盖度下降证据
本轮审查的"抬头步骤"执行良好（PR 描述校验、前序问题勾选），但"回头看"步骤缺失——完成 diff 分析后未回头问"这些修复放在一起是否引入了系统性问题"。增量审查的覆盖度下降不是发生在"看 diff"阶段，而是发生在"看完整度"阶段。
