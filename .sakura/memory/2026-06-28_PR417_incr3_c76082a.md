### 3. 规范完善建议
*   **新增规则：【LLM Prompt 外部注入强规范】** 针对项目中日益增多的 CI/PR 数据注入，强制要求：任何非代码仓内部生成的文本（如 CI output、PR body 提取段）进入 system/user prompt 前，**必须**被 `<untrusted_evidence>` 等明确边界的 XML 标签包裹，并施加硬性截断（如 2000 tokens/10KB）。将当前的 suggestion #3 升级为常规 minor 阻断项。
*   **新增规则：【大版本 PR 盲区追踪声明】** 当 large 策略明确跳过高危模块（如支付、权限、状态机）时，审查报告的“覆盖范围限制”部分不能仅写“未逐一检查”，必须强制生成一个关联的 Follow-up Issue 或 TODO，否则评分上限应锁定在 7 分。
*   **完善规则：【安全工具误报处理标准】** 针对 CodeQL 等工具的残余告警，规范处理动作：若确认已从算法层面消除风险，应在代码侧加 `# nosec` 或对应工具的抑制注释，配合注释说明“已通过 XX 方式消除回溯”，避免告警疲劳。

### 4. 经验教训
*   **ReDoS 修复的“银弹”模式**：`re.finditer` 在大文本上极易触发回溯，而 `text.splitlines()` + `re.match`（行首单次匹配）是 O(N) 线性复杂度的最可靠保障。未来遇到类似问题，应首选此模式而非仅调整正则表达式本身。
*   **黑名单安全策略的验证陷阱**：Shell 工具从白名单改为黑名单+管道分段。黑名单的覆盖面永远“看起来”大于白名单，但其安全性高度依赖于攻击面的预判。审查时重点验证了“管道分段校验”这一阻断级联的关键设计，这是正确的审查切入点。
*   **全表操作的性能“时移性”**：`cleanup_expired` 全表扫描在早期数据量小的时候不是问题，但在 PR closed 这种高频 Webhook 中触发，是典型的“时间炸弹”。审查将其标记为 suggestion 而非 minor 是合理的（因为当前不阻断），但应在记忆中将其标记为“v2.x 后续必优化项”。
