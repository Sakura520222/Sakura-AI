# PR #733 审查反思

## 一、审查质量评估

### 覆盖度：良好，但有一个未深挖的关键疑点
- ✅ 三重一致性核验（pyproject / requirements / uv.lock）扎实，且带行号证据，符合“结论须附验证依据”原则
- ✅ “旧版本残留”扫描覆盖到 shell 脚本，超出常规依赖 PR 的检查面
- ⚠️ **遗漏：锁文件“领先”于声明的来源追溯**。审查确认 HEAD 上 uv.lock 元数据已是 `>=2.1.8`，即**本 PR 合并前仓库处于“声明 2.1.6 / 锁文件 2.1.8”的漂移状态**——此时 `uv lock --check` 必然失败。这不是常态：锁文件被单独升级意味着有人绕过正常流程（或本地操作后只提交了部分文件）。审查推测“已在更早提交中落库”后就止步了，未执行 `git log --follow uv.lock` 定位升级提交的作者、时间与上下文。按 Fail-Closed 原则，这是供应链审计的基本动作：2.1.8 恰好是官方版本所以结果无害，但流程上“锁文件来源可信”与“最终状态一致”是两个独立命题。

### 准确度：合理
- 9/10 + approve 的校准恰当：2 文件、±1 行、纯声明变更、最终状态一致，无功能风险
- suggestion 级别对“描述失真”定性准确，未误升级为 major
- 有一点措辞瑕疵：本 PR 实际**违反了“依赖声明须同 PR 纳入 uv.lock”的字面规则**，审查是通过最终状态一致性做了实质豁免，但报告中未显式声明“规则豁免及理由”，可能被后续引用为宽松先例

### 完整性：一处显式风险未声明
PR 附带的 release notes 仅覆盖 2.1.8（且内容只是发布流程的 provenance 变化，与运行时无关），**2.1.7 的变更完全未核验**。quick 策略下依赖 CI 兜底是可接受的，但按“报告结构化”原则应在遗留项中显式声明这一盲区，而非笼统的“风险较低”。

## 二、发现的模式

### 模式 1：AI 自产物的“模板幻觉”（本次最有价值的发现）
`<!-- sakura-ai-summary -->` 中“锁文件同步（uv.lock）”条目是**虚构的**——变更文件列表根本没有 uv.lock。这是典型的按 PR 类型套模板（“依赖更新 → 必有三件套”），而非基于实际 diff 生成。本次审查端捕获了它，形成“下游纠正上游”的兜底，但暴露了系统性问题：**摘要生成端与审查端的事实基础割裂**。记忆中已有“AI 产物脱敏”红线，本次是第二个维度——AI 产物的事实准确性同样需要审查覆盖。

### 模式 2：锁文件领先 = 流程异常信号
正常工具链（Dependabot / `uv lock`）会原子性地同时更新声明与锁文件。锁文件单独领先几乎必然意味着：中断的操作、手动干预、或来自非标准分支的部分合并。应将其视为与“CI 失败”同级的**流程审计触发器**，而非仅做状态核验后放行。

### 模式 3：微小 diff 的证据展示缺失
+1/-1 的变更引用 diff 本身零成本，但报告只给了核验结论（“均为下限提升”）未给 diff 原文，与“证据待补型结论须附依据”的标准存在轻微落差。

## 三、规范完善建议

1. **新增：AI 摘要事实锚定规则**——PR 摘要生成必须从 `list_changed_files` 实际输出出发，禁止按 PR 类型推断变更文件集合；审查清单固定一项“AI 摘要与实际 diff 逐条比对”（本次已实践，应固化为规则）
2. **新增：锁文件领先审计**——发现锁文件状态领先于声明文件时，必须 `git log --follow <lockfile>` 定位升级提交，核验作者与提交上下文，排除未授权变更后方可豁免“同 PR 纳入 uv.lock”
3. **修改：规则豁免显式化**——凡豁免既定规则（如本次的 uv.lock 同 PR 纳入），报告须单列“豁免依据”，防止被引用为无条件的宽松先例
4. **新增：跨版本提升的盲区声明**——依赖提升跨多个版本时，遗留项须声明“仅核验目标版本 notes，中间版本变更依赖 CI 兜底”

## 四、经验教训

1. **Dependabot PR 的审查重心是“一致性 + 来源”**，而非 diff 本身：三重一致性（pyproject/requirements/lock）+ 锁文件变更来源可信 + CI 绿色，三者缺一不可。本次前两者做得好，第三者（来源追溯）是短板
2. **“最终状态正确”≠“过程合规”**：HEAD 核验通过只证明终点无恙，不证明路径可信。对锁文件这类供应链敏感文件，git 历史与当前状态同等重要
