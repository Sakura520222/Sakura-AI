## 2. 发现的模式

- **“部分 mock”是时间测试里最危险的模式。**  
  这个测试只 mock 了 `TimeService`，却让路由中的 `time_service.now_utc()` 走真实时钟。表面上测试“可控”，实际上 labels 由真实日期生成，再叠加硬编码断言，就形成了延迟触发的失败。这类问题难以在当次运行发现，但会在未来某一天突然炸掉。

- **“初始化后移”会改变失败暴露时间。**  
  `main.py` 把 `initialize_time_service` 移进非 bootstrap 分支后，TimeService 的失败模型从“启动 fail-closed”变成“首次使用时才失败”。这种变化容易被当作无害重构，实际上会影响部署可诊断性和上线体验。

- **SQL 端聚合 + UTC 边界是性能修复的好模式。**  
  用边界数组 + `case`/`sum` 一次查出 31 天 × 2 状态，比 Python 分桶更优。但这个模式的正确性高度依赖边界数组长度、闭合区间和 DST 偏移，因此必须有贴近真实时区的测试。

- **“修改了某个文件，却没有顺手清理同文件历史问题”也是增量审查中的常见现象。**  
  本提交重写了 `test_dashboard_time_buckets.py`，却保留了硬编码日期。文件已被触碰，却发现不了或选择不修，说明增量审查的“相邻同构块强制遍历”原则仍值得强化。
