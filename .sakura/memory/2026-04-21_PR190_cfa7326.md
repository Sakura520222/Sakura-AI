# 审查反思报告 — PR #190 全量重审

## 1. 审查质量评估

### 覆盖度：中等偏上，但存在结构性盲区

审查覆盖了核心新增文件的主要风险点（并发、安全、API限制），但在以下区域存在明显盲区：

- **数据库 Schema**：`init.sql` 新增 16 行表结构定义，零条评论。未审查索引设计、字段类型选择、外键约束是否合理。
- **配置层**：`config.py` 净增 50 行配置项，未审查新配置项的默认值合理性、边界值、是否缺少校验。
- **常量层**：`constants.py` 净增 48 行，未审查新增常量是否有硬编码嫌疑或与其他模块重复。
- **工具集成链路**：`sakura_tool.py` 作为 208 行的新工具，仅审查了路径校验，未审查工具注册/调用/错误回传的完整链路。
- **`sakura_memory_service.py` 内部结构**：860 行中仅挑出 5 个点位，未对整体方法划分、状态管理、错误传播链做结构级审查。

### 准确度：存在一个显著的自相矛盾错误

**最严重的问题**：路径遍历修复建议中推荐了 `PurePosixPath(user_input).resolve()`，但项目记忆中明确记载：

> "路径处理禁用字符串检查、**禁用 PurePosixPath**（不解析符号链接），必须用 `pathlib.Path.resolve()` + 前缀验证"

`PurePosixPath.resolve()` 是纯字符串规范化（不访问文件系统），根本无法解析符号链接，与项目安全规范直接冲突。**审查者给出了违反项目自身规范的修复建议**，如果开发者按建议实施，会引入规范明确禁止的模式。

**严重程度判定存在系统性膨胀**：
- `document_service.py` 重复调用 `relative_to` → 标记为 **major**，实际是典型的 minor/代码气味
- `review_id=0` 误判 → 标记为 **major**，审查者自己承认"不太可能发生"
- GitHub API 截断 → 标记为 **major**，对于记忆文件场景（极少超过 1000 文件），这是理论性风险而非实际 bug

按项目记忆的"三问法"反向验证：`relative_to` 重复调用——有实际 bug？否。运行时错误？否。安全风险？否。**应当降级为 suggestion**。

**准确命中**：
- `asyncio.gather` 失败模式的标记完全正确，且给出了精确的修复方案
- 单例双重模式的识别准确，`__new__` + 模块级变量确实增加了理解负担
- 记忆上下文注入三处重复的发现是有价值的架构观察

### 完整性：理解了意图，但未追问架构合理性

审查准确识别了"项目记忆系统"这一核心变更意图，也注意到了 `sakura_memory_service.py` 触及 800 行警戒线。但缺少一个关键追问：

> **860 行的记忆服务 + 287 行的写入服务 + 208 行的工具 = 一个完整的子系统，是否应该有独立的模块目录而非平铺在 `services/` 下？**

当前 `services/` 目录混合了审查核心服务（`reviewer.py`、`prompt_builder.py`）和新增的记忆子系统，未做物理隔离。

## 2. 发现的模式

### 代码模式

- **防御性编程不一致**：路径校验做了防御，但 `review_id` 校验缺失；记忆注入有 try/except，但 `gather` 调用没有。同一 PR 内防御标准不统一。
- **单例模式偏好但实现不统一**：`GitHubWriteService` 用 `__new__` + 模块级变量双重保障，`SakuraMemoryService` 仅用模块级变量。两种风格共存增加认知负担。
- **"先直提后回退"模式**：写入服务采用"直接提交 → 409 走 PR"策略，这个模式本身是好的，但未分析 409 之后的 PR 创建失败时的兜底路径。

### 架构观察

- **记忆系统与审查核心的耦合方式**：通过工具注入（`sakura_tool.py`）+ 直接服务调用（`issue_analyzer.py`）两种方式集成，不是单一入口。这意味着如果记忆系统需要替换或禁用，需要改多个接入点。
- **数据流方向**：记忆系统产生了新的写入路径（`github_write_service.py`），打破了之前"只读审查"的架构假设，但审查未对此架构变迁做风险分析。

## 4. 经验教训

### 值得关注的要点

1. **`asyncio.gather` 是并发审查的必检项**：本次精准命中，验证了项目记忆中"串行改并行必须审查失败模式"规则的有效性。这个规则应该保持高优先级。

2. **全量审查时的"点位疲劳"**：面对 21 个文件 +1779 行变更，审查者倾向于"逐文件找 bug"而非"先架构后细节"。结果是发现了 5 个细节问题但遗漏了架构级问题（Schema、Config、模块组织）。**全量审查应强制先输出架构影响分析，再进入细节审查**。

3. **建议代码的正确性审查不能跳过**：给出修复建议时，必须验证建议本身是否符合项目规范和语言语义。本次 `PurePosixPath.resolve()` 建议就是一个反面教材——看似合理实则违规。

4. **"做得好的地方"不应成为审查盲区的补偿**：正面评价了 6 个点，但其中"路径安全意识"紧接着就被标为 critical，形成"肯定了意识但否定了实现"的矛盾信号。正面评价和问题标记应有清晰的边界。

### 特定技术经验

- **GitHub Contents API 截断**：这个发现本身有价值，但标记级别需要结合实际场景。对于 `.sakura/memory/` 目录，正常项目很难达到 1000 文件。更应关注的是：如果真的截断了，合并逻辑会静默丢数据还是报错？静默丢数据才是真正的 major。

## 5. 手动全量重审反思

### 全量 vs 增量的差异

本次是用户手动触发 `/full-review`，PR 描述显示"无历史审查记录（首次审查）"。这意味着不存在"增量审查遗漏后被全量补获"的场景。

但有一个值得警惕的现象：**全量审查反而可能比增量审查质量更低**。原因：
- 增量审查聚焦少量变更，更容易深入
- 全量审查面对大量代码，容易陷入"扫描式"审查——每个文件看一遍，每个文件提一两个问题，但都不够深
- 本次审查的 7 个 major 中，至少 3 个是浅层问题（重复变量调用、review_id 类型、API 截断理论风险）

### 对全量审查流程的改进建议

全量审查不应等于"对每个文件做一遍增量审查"，而应有不同的策略：

1. **第一遍：架构扫描**（5分钟）—— 新增了哪些模块？模块间依赖关系？数据流变化？Schema 变更？
2. **第二遍：高风险区深挖**（15分钟）—— 并发、安全、IO、状态管理
3. **第三遍：细节补漏**（10分钟）—— 代码气味、规范一致性、重复代码

本次审查直接跳到了第三遍的模式，导致架构级问题（Schema 零覆盖、模块组织未讨论）被遗漏。

### 总结

本次审查的**核心价值**在于准确识别了 `asyncio.gather` 失败模式和记忆注入代码重复问题。**核心失误**在于给出了违反项目规范的修复建议（PurePosixPath），以及严重程度系统性膨胀（3 个 major 应降级为 suggestion/minor）。**核心盲区**在于对数据库变更和配置变更的零覆盖。全量审查需要从"逐文件扫描"切换到"架构优先分层审查"的策略。
