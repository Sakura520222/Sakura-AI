#### 2. 发现的模式

**代码模式**：
- **渐进式迁移不彻底**：同一个 `issue_worker.py` 中，部分配置已迁移至 `get_dynamic_config()`，部分仍用旧 DB 直读，说明缺少全量扫描工具或 checklist。
- **异常处理“外层兜底”依赖**：多处依赖外层 `try/except` 捕获内层类型转换异常，但未提供上下文友好的错误消息。

**架构观察**：
- **双源配置（DB + YAML）** 是合理设计，但审查指出“认知负担”确实存在。项目未提供统一的配置抽象层（如 `ConfigService` 聚合两者），导致开发者需记住哪些 key 在 DB 动态配置、哪些在 YAML。
- **`get_dynamic_config()` 内存缓存** 对热路径友好，但缺少显式的缓存失效钩子，配置更新时需全局 `invalidate`，容易遗漏。

#### 3. 规范完善建议

基于本次审查，建议**新增或强化**以下审查规则：

1. **【major】配置迁移 PR 必须包含全量调用方扫描清单**  
   当将静态配置改为动态配置时，审查者必须输出所有读取该配置的位置（grep 扫描），并逐一确认已替换为 `get_dynamic_config()`。  
   *理由*：本次遗漏了两处，人工容易漏。

2. **【minor】动态配置读取必须显式声明默认值或处理 `None`**  
   所有 `await get_dynamic_config("key")` 调用后，必须紧跟 `or default_value` 或断言非空，避免因 DB 无记录导致 `None` 穿透业务逻辑。  
   *理由*：审查中未验证回退行为，属于常见隐患。

3. **【major】配置更新操作必须触发缓存失效验证**  
   任何通过 WebUI/API 保存动态配置的路径，审查时需确认是否调用了统一缓存清除函数，并检查后台 worker 能否在下次读取时获得新值。  
   *理由*：内存缓存易导致“保存成功但 worker 仍用旧值”问题。

4. **【suggestion】双源配置页面需增加跨页导航提示**  
   当配置分散在通用动态配置页和策略 YAML 页时，应在 UI 上相互提供链接或说明，降低用户困惑。  
   *理由*：观察点1未闭环。

#### 4. 经验教训

**值得未来关注的要点**：
- **配置迁移类 PR 的审查 checklist**：
  1. 全局搜索旧配置 key 的所有出现位置（不仅是当前 PR 变更文件）。
  2. 确认新 `get_dynamic_config()` 调用处都有合理的默认值 / 回退。
  3. 验证配置保存后是否有缓存失效或刷新机制。
  4. 若配置分为 DB 和 YAML 两处，检查 UI 是否清晰引导用户。
- **`int()` 转换用户输入**：永远不要依赖外层裸 `except ValueError` 返回不友好信息，应当在捕获后转换为业务可读消息。

**对特定技术的审查经验**：
- **动态配置系统**：在享受运行时变更便利的同时，必须付出“缓存一致性”和“配置源可观测性”的代价。审查时应重点关注：
  - 冷启动时的默认值加载顺序。
  - 热更新期间的原子性和可见性。
  - 配置错误时不影响服务可用性（降级到安全默认值）。

**本次审查的亮点**：  
审查者注意到了 `innerHTML` 的安全性并建议注释，尽管非紧急，但体现了对 XSS 预防规范的坚持。同时 `DYNAMIC_CONFIG_RANGES` 的完整性检查（如 0.0-1.0 阈值）也很细致。

**可改进点**：  
未要求对 `issue_worker.py` 的迁移补充单元测试（模拟 `get_dynamic_config` 返回不同值），这属于“增量审查必须输出未直接测试但依赖的调用链”规则的应用不足。
