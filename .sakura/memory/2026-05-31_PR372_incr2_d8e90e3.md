## 2. 发现的模式

### 代码模式

本次变更体现了一个较清晰的异常分层模式：

```text
外层循环：
  建立 Redis 连接 / pubsub
  捕获连接级异常
  退避重连

内层循环：
  消费 pubsub.listen()
  仅捕获空闲超时
  继续监听
```

这是较好的结构，避免了两个常见问题：

1. **把临时超时当成致命错误**  
   导致频繁重建连接。

2. **把真实断连当成普通超时**  
   导致无法触发外层重连逻辑。

### 异常处理习惯

项目中存在对外部服务连接进行容错的需求，尤其是 Redis、数据库、支付网关等。这类代码需要特别关注：

- 异常分类是否过宽
- 是否存在紧密重试循环
- 是否有退避机制
- 是否有足够日志
- 是否区分“可继续”和“必须重连”

本次修复体现出项目正在向更精确的异常分类靠拢。

### 架构观察

`backend/webui/sse.py` 中的 SSE 管理逻辑依赖 Redis Pub/Sub，说明 WebUI 实时事件推送通过 Redis 做跨进程或跨实例广播。

这类架构下，Redis listener 的健壮性非常关键：

- listener 退出会影响前端实时更新
- listener 紧密循环会影响 CPU
- listener 重连不及时会导致事件丢失或延迟
- 异常日志不足会增加排障难度

因此该文件虽小，但属于运行时稳定性热点。

## 3. 规范完善建议

### 建议新增规则：Redis/PubSub listener 异常分层审查

对于 Redis Pub/Sub、消息队列、SSE listener 等长期运行循环，应强制检查异常分层：

- 空闲超时类异常可在内层 `continue`
- 连接断开类异常必须跳出内层或重新抛出
- 外层必须有退避重连
- 禁止在内层捕获宽泛的 `OSError` / `Exception` 后无延迟继续
- 高频异常路径必须有 debug 日志，且不得默认污染生产日志

可加入项目记忆：

> **长连接监听循环异常分层规则**：Redis Pub/Sub、SSE、消息队列等长期监听循环中，内层只能处理明确可恢复的空闲超时；真实连接断开异常必须传播到外层退避重连逻辑，禁止内层捕获 `OSError` / `Exception` 后无延迟 `continue`，标 major。

### 建议新增规则：PR 描述与实际 diff 一致性

本次 PR 描述提到 `requirements.txt` 依赖变更，但实际变更范围没有该文件。建议强化已有规则：

> **PR 描述与 diff 一致性检查**：审查前必须核对 PR 描述中的文件、依赖、配置、迁移声明是否真实出现在 diff 中；若描述包含未发生的依赖或配置变更，应至少标记 minor，要求更新描述。

### 建议新增规则：异常分类测试建议

针对修复异常处理的 PR，应要求最小测试或手动验证说明：

> **异常分类变更测试规则**：修改重试、退避、连接恢复逻辑时，需覆盖至少一类可恢复异常和一类不可恢复/需重连异常，验证二者进入不同路径。缺失测试时至少标 minor。

## 4. 经验教训

### 避免过度正向评价

本次审查结论使用了“完美解决”“无遗留风险”等表达。虽然代码确实修复了核心问题，但审查报告应避免绝对化。

更稳妥的表述是：

- “已解决当前已知关键问题”
- “未发现新的阻断风险”
- “仍建议补充测试 / 更新 PR 描述”

这样既准确，也保留对未知风险的审慎态度。

### 异常处理的关键不是“捕获更多”，而是“捕获更准”

上一轮问题正是因为捕获了 `OSError`，看似增强健壮性，实际破坏了重连语义。

未来审查类似代码时，应优先问：

1. 这个异常是否真的可在当前层恢复？
2. 如果继续循环，会不会形成紧密循环？
3. 是否阻断了外层更合适的恢复机制？
4. 是否有退避？
5. 是否有日志？

### 长连接循环要重点检查 CPU 风险

任何 `while True` + `continue` 都需要额外警惕：

- 是否有 await 阻塞点
- 是否有 sleep / backoff
- 是否可能在异常路径中快速循环
- 是否会刷日志

本次变更移除了 `OSError` 后，紧密循环风险明显降低，这是正确方向。

### import 注释仍需保持语义精确

本次 `import redis.exceptions` 注释说明“不触发连接初始化”，这个解释是合理的。

但项目记忆中已有“延迟导入必须说明循环引用原因”的规则。这里是模块级 import，不是函数体内延迟导入，因此不应机械套用“延迟导入”格式。审查时应区分：

- 模块级 import：关注副作用、初始化成本、排序
- 函数内 import：关注循环依赖、性能、线程/协程安全
