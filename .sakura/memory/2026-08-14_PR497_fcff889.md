基于对 PR #497 及其审查结果的深度分析，以下是对本次审查的反思：

### 1. 审查质量评估

*   **覆盖度：优秀**
    *   审查者敏锐地捕捉到了本次变更的核心风险点——**Digest 数据源的切换**（从 `steps.build` 到 `steps.materialize`）。这不仅仅是变量名的改变，而是“构建产物”与“发布产物”概念的解耦。审查者验证了这一变更对下游 `sync-dockerhub` 和 `latest` 标签更新的影响，确保了全链路的一致性。
    *   对新增的正则校验（`^sha256:[0-9a-f]{64}$`）给予了关注，这在防止注入攻击和脏数据处理上至关重要。
    *   对测试覆盖度的验证（特别是旧字符串移除断言）确保了逻辑分支的彻底切换，没有遗留代码。

*   **准确度：优秀**
    *   评分 9/10 是合理的。该 PR 逻辑清晰，测试完备，且解决了明确的痛点（Stable 渠道重试机制）。未发现误判。
    *   对于“无评论”的处理，审查者在摘要中详细罗列了验证要点，将“无评论”转化为了一种高质量的“通过验证”。

*   **完整性：良好，但有细微提升空间**
    *   审查者充分理解了“复用 Digest”的意图。
    *   **潜在遗漏点（影响 1/10 的扣分项）**：
        *   **资源清理**：在 Stable 渠道复用旧 Digest 并跳过 `crane copy` 时，本次构建产生的新 Digest（未打标签的悬空镜像）将如何处理？GitHub Actions 的默认清理策略可能会在保留时间后删除它，但在高频构建场景下是否会导致 Storage 快速膨胀？虽然这不影响功能正确性，但属于运维成本层面的考虑。
        *   **并发竞态**：虽然审查者考虑了 digest 校验，但未明确提及极端并发场景：如果两个并发的 Workflow 同时检测到“旧 Digest 存在”并决定复用，后续的 `crane tag` 操作是否幂等？（`crane tag` 通常支持幂等，但这是值得确认的 implicit knowledge）。

### 2. 发现的模式

*   **代码模式：防御性校验模式**
    *   在 CI 脚本中引入严格的正则校验（`^sha256:[0-9a-f]{64}$`）来验证外部命令（`crane digest`）的输出，表明项目对“不可信输入”的防御意识已经下沉到基础设施层。

*   **架构观察：单一事实来源转移**
    *   架构上确立了 `materialize` 步骤作为“发布状态”的单一事实来源，而非 `build` 步骤。这种“构建归构建，发布归发布”的解耦设计是 CI/CD 成熟的表现，使得发布流程可以独立于构建流程进行重试和回滚。

### 3. 规范完善建议

*   **新增审查规则：Digest 来源追踪**
    *   对于涉及 Docker 镜像发布的 CI 变更，必须强制审查 `outputs.digest` 的来源。任何从“构建 ID”向“发布 ID”的切换，必须验证下游所有消费者（同步、通知、部署）是否已兼容新 ID 格式或含义。
*   **新增审查规则：外部命令输出校验**
    *   要求所有将外部 CLI 工具（如 `crane`, `gh`, `kubectl`）输出赋值给关键环境变量的操作，后必须紧跟校验逻辑（如正则匹配或非空检查），防止工具错误导致灾难性后果（如将错误信息赋值给镜像 Tag）。
*   **新增审查规则：不可变资源的幂等性**
    *   涉及“不可变标签”的操作，必须验证其在幂等场景下的行为（即重复执行不应失败且结果一致）。

### 4. 经验教训

*   **警惕“逻辑短路”的风险**：在代码中复用 Digest（`PUBLISHED_DIGEST="$existing"`）虽然高效，但意味着跳过了 `crane copy`。在未来审查中，如果发现类似的“捷径”，必须确认跳过的步骤是否包含副作用（如 Manifest 的跨 Registry 传播、额外的元数据注入），确保这些副作用在复用场景下是不需要的或已被其他方式满足。
*   **测试断言的“排他性”验证**：本次审查中提到的“旧字符串移除的断言”是一个极佳的实践。它提醒我们，在逻辑分支变更时，不仅要验证“新逻辑存在”，还要验证“旧逻辑彻底消失”，防止代码中出现“死逻辑”或隐藏的默认回退分支。
*   **关于 9/10 分的反思**：高评分 PR 往往容易让人忽略“资源管理”问题。对于此类高完成度的 PR，审查者应主动从“功能性”转向“经济性/运维性”思考（如：未使用的镜像如何清理？），这是从 Code Review 迈向 Architecture Review 的关键一步。
