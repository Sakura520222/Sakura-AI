**四、经验教训**

1. **工具容错要显式**：当自动审查因格式或解析错误中断，报告本身应呈现错误信息，而不是空白。否则会误导审查者认为代码无风险。  
2. **大幅依赖升级不可轻视**：一次性升级多个第三方库会产生连锁兼容问题，必须在 PR 描述中列出每个库的 **Breaking Changes**，并在 CI 中加入对应的兼容性测试。  
3. **重复改动是潜在冲突源**：同一功能在不同提交中多次修改（如 `review_timeout`），容易导致 **合并冲突** 与 **逻辑不一致**，审查时应主动发现并建议统一。  
4. **增量审查不等于风险降低**：虽然只看增量提交可以提升效率，但在本例中增量涉及 **核心业务、配置、错误处理**，若只审查增量会遗漏历史代码对新改动的影响。需要 **全局影响分析**（搜索所有引用、测试覆盖）。  
5. **UI 改动需配套后端校验**：从自由文本到下拉框的改动会限制前端可输入的值，后端必须加入 **Enum 验证**，否则旧版前端仍可能发送非法值。
