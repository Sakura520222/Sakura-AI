# 深度反思：PR #400 增量审查队列机制

## 1. 审查质量评估

### 覆盖度：有亮点但有明显盲区

**做得好的：**
- 准确穿透了 PR 描述的表层（"优化配置选项"），抓住了实际核心变更（增量审查队列机制），符合"PR 描述与 diff 一致性强制校验"原则
- 两个 major 之间有因果关联——major 1（会话恢复导致旧 prompt 残留）和 major 2（删除数据源但保留消费方）都指向同一个设计决策："用恢复完整历史会话替代历史摘要注入"，审查者识别了该决策的两个不同维度的副作用

**遗漏的：**
- **测试文件质量未评估**：5 个新增测试文件共 1100+ 行，完全未提及。按"测试与代码的同源偏差"原则，应至少抽查关键测试是否覆盖了 major 1/2 的场景，还是只测了 happy path
- **`context_compressor.py` 32 行变更零覆盖**：上下文压缩是增量审查的核心组件，其变更逻辑是否正确完全未触及
- **`review_worker.py` 200 行新增只标了 1 个 major**：状态机变更（pending → reviewing → completed）的并发安全、乱序事件处理、重复消费防护均未提及
- **`webhook.py` 56 行新增零覆盖**：事件入口的幂等性、重复事件处理未检查

### 准确度：基本合理，一处值得商榷

- major 1、major 2 判定准确，确实是功能性缺陷
- **minor 2（pending 永久卡住）严重程度可能偏低**：如果 `compare` 因网络/权限问题持续失败，队列项永远 pending，可能导致增量审查机制实质性瘫痪。在"事件驱动闭环审查"原则下，这应至少是 major 级别——状态机无逃脱路径是架构缺陷而非小问题

### 完整性：理解了设计意图但未穷尽副作用

审查者正确理解了三层设计（持久化 → 动态注入 → 兜底消费），也识别了 tool_calls 多形态兼容和僵尸 review 检测的价值。但对"会话恢复"这一核心架构决策的副作用分析不够系统——只发现了 prompt 和死代码两个问题，未追问：恢复的会话中是否还有其他"过期状态"（如 tool 定义、temperature 等运行时参数）？

## 2. 发现的模式

### 代码模式
- **"替代式重构"的不完整清理**：用机制 A 替代机制 B 时，A 的实现可能正确，但 B 的消费方被遗漏。这是本次 major 2 的根因模式
- **LLM 集成的多形态兼容**：`_coerce_tool_call_to_dict` / `_extract_tool_call_fields` 反映了不同模型返回 tool_calls 格式不一致的现实，这类"适配层"在 LLM 集成中是刚需
- **辅助任务 token 预算粗放管理**：直接从 1000 涨到 16000 而非基于实际输出分布设定，说明缺乏对辅助任务输出长度的度量

### 架构观察
- 增量审查采用 **"会话快照恢复"** 模式而非 **"摘要传递"** 模式，这个选择带来了 prompt 刷新的天然困难
- webhook → queue → worker 的异步链路中，queue 层（`pr_review_incremental_queue.py`）作为新增的中间层，其状态机健壮性是整个链路的单点

## 3. 规范完善建议

### 建议新增的审查规则

**R1: "数据源-消费方"联动删除强制验证**
> 删除任何数据源（section、字段、配置项、API 响应字段）时，必须 grep 全仓引用，逐项确认消费方已同步清理或适配。仅删除生产者而遗留消费者 = major。

**R2: "会话恢复"模式的配置刷新检查清单**
> 当系统采用恢复历史会话（而非重建会话）时，必须逐项验证：system prompt、tool 定义、运行时参数（temperature/max_tokens）、角色设定等在恢复后是否被当前配置覆盖。遗漏任何一项 = major。

**R3: 状态机中间状态的逃脱路径强制检查**
> 任何状态机实现（queue、workflow、review 状态）必须为每个中间状态（pending/processing/reviewing）提供超时或异常逃脱路径。无逃脱路径的中间状态 = major。

**R4: 大面积新增测试文件的抽样审查**
> 单 PR 新增超过 3 个测试文件时，必须至少抽查 1 个关键路径测试，验证其是否覆盖了异常分支和边界条件，而非仅覆盖 happy path。

### 建议强化的现有规则

在"事件驱动闭环审查"中补充：**队列化中间层的状态机完备性**是必查项，特别是异常路径下的状态归宿。

## 4. 经验教训

### L1: "替代式重构"的副作用必须正向验证，不能仅靠"没报错"
本次 major 2 的本质是：删除了 section 6.3 的注入代码，但没验证 `prompt_builder` 中依赖该字段的分支。教训：**重构删除后，应 grep 被删除数据的所有引用，验证消费方行为**，而非假设"删了生产者就完了"。

### L2: "会话恢复"是 LLM 集成中的高危模式
与无状态 API 调用不同，LLM 会话恢复携带了完整的对话历史，包括 system prompt。选择此模式时必须在设计阶段就明确：**哪些会话元素需要被"当前配置"覆盖**，并在实现中强制执行。本次 major 1 就是设计时未考虑、实现时未处理。

### L3: 队列 pending 状态的"静默失败"比"显式报错"更危险
`compare` 失败返回 None → 队列项保持 pending → 无告警无日志无重试。这种"静默卡住"在生产环境中极难发现。教训：**异步队列的每个状态转换必须有可观测性（日志/指标），异常路径必须有明确的失败状态或重试机制**。

### L4: 审查精力分配应跟随风险分布
本次审查对新文件（`pr_review_incremental_queue.py` 419 行）和大改动文件（`review_worker.py` +200 行）的覆盖不足，而这两个文件正是增量审查链路的核心风险点。教训：**审查时间应按"变更行数 × 架构关键度"分配，而非按"问题明显度"分配**。新文件和大改动文件应分配更多精力，即使初步扫描未发现明显问题。
