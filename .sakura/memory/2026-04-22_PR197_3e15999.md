## 2. 发现的模式

### 代码模式
- **防御性守卫的双重语义**：`isinstance` 检查在此处不仅是类型过滤，更是**隐式接口契约验证**。移除它等于移除了运行时的接口合规性断言
- **动态类型反模式**：`type('Repo', (), {...})()` 绕过所有静态检查，是 Python 中最危险的 mock 方式之一

### 架构观察
- **接口契约无文档化**：所有工具依赖 repo 对象的哪些属性/方法，没有集中定义。这导致删除实现时无法系统性验证影响范围
- **适配器生命周期混乱**：从引入 local_repo_adapter（6轮补丁未完善）→ 直接删除 → 引入更差的轻量 mock，反映了对接口抽象的反复摇摆

## 3. 规范完善建议

### 新增规则

**回滚 PR 真实性验证**：
> 回滚 PR 必须对比目标 commit 与当前 diff，确认是状态恢复而非引入新实现。若回滚中混入新代码，按普通变更审查，且"意图与实际不符"本身标记 major。

**接口实现删除检查清单**：
> 删除实现某接口的类时，必须：(1) 列出该接口所有消费者；(2) 逐一确认替换实现的接口完备性；(3) 无法确认时按 critical 标记。禁止"先删再看"。

**类型守卫移除评估**：
> 移除 `isinstance`/`hasattr` 等运行时类型检查时，必须评估其是否承担接口契约验证职责。若承担，移除等同移除防御，按"防御代码隐形流失"规则处理。

### 规则修订

建议扩展为：

## 4. 经验教训

### 回滚陷阱
回滚常被视为"安全操作"，但**破坏性回滚比破坏性新增更危险**——因为审查者预期它无害，容易放松警惕。本次的"假回滚"就是典型：声称恢复，实际退化。

### 适配器热点的终局
`local_repo_adapter.py` 连续 6 轮补边缘而契约未补齐，最终被删除。这验证了项目记忆中"适配器热点衰减"规则的正确性，但也暴露了**衰减规则的盲区**：删除后引入更差替代品，问题没有消失而是降级。

### 接口契约的隐性债务
项目中没有 repo 对象的接口定义（Protocol/ABC/文档），所有工具通过鸭子类型隐式依赖。这种"无契约依赖"使得：
- 删除实现无法静态发现影响
- 替换实现无法验证完备性
- 重构成本随消费者数量指数增长

**建议**：将此作为技术债务记录，在 `sakura_memory_service.py` 全量审查时同步评估引入 repo 接口定义的可行性。
