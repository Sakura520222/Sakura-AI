## 深度反思

### 1. 审查质量评估

**覆盖度**：核心遗漏点抓得准，但有盲区。`_handle_label_checkbox_toggle_inner` 的遗漏是本 PR 最关键的完整性缺陷——PR 描述列出 3 个处理点，实际存在 4 个调用点，这是"PR 描述与 diff 一致性"原则的典型应用场景，审查者正确触发了该检查。但审查未验证**测试是否也遗漏了该路径**——新增的 3 个测试文件分别覆盖 `/full-review`、`/revoke`、`/agent`，恰好与 PR 描述的 3 个点一一对应，说明测试同样存在盲点，这应当被指出。

**准确度**：`request_changes` + 5/10 对于"核心目标完成度 75%（4 个调用点漏 1 个）"是合理的。这不是边缘 case，而是 PR 声明目标的直接缺失。严重程度判定准确。

**完整性**：对变更意图理解到位——从 `"none"` 到 `"unknown"` 的语义迁移，本质是区分"确实无权限"和"无法判断权限"。但未追问一个架构层面的问题：**字符串枚举模式是否应在此契机迁移为 Enum**？每次新增状态值都需全仓扫描调用点，这是"stringly-typed"的固有风险。

### 2. 发现的模式

- **字符串状态机模式**：`check_collaborator_permission` 返回 `"none"` / `"unknown"` / （推测）`"admin"` / `"write"` / `"read"` 等，属于典型的字符串枚举反模式。新增状态值的传播完全依赖人工审查。
- **PR 描述作为"变更清单"的陷阱**：作者按感知列出修改点，但遗漏了第 4 个调用点。PR 描述的完整性不可信，必须以代码静态分析为准。
- **辅助函数提取时机**：`_permission_check_unavailable_response` 的提取是正确的，但在提取后未反向验证所有原调用点是否都已迁移到新函数。

### 3. 规范完善建议

**新增规则——"返回值枚举扩展的全调用点扫描"**：
> 当 PR 修改函数的返回值集合（新增/修改枚举值、异常类型、错误码）时，必须列出该函数的**所有调用点**，并逐个确认是否适配了新返回值。仅检查 PR 描述中提到的调用点不够，必须通过 IDE/Grep 独立验证。

**强化现有规则——"PR 描述与 diff 一致性"的量化验证**：
> 当 PR 描述以列表形式声明"修改了 X、Y、Z"时，审查者应显式计数并对比实际 diff 中的修改点数量。数量不匹配时必须标 major。

**新增规则——"测试覆盖与 PR 描述的镜像偏差"**：
> 当新增测试文件/用例的数量与 PR 描述的修改点数量精确一致时，应警惕测试是否仅覆盖了作者"想到的"路径，而非"实际存在的"路径。

### 4. 经验教训

- **"quick"策略不等于"跳过调用方扫描"**：即使是 quick 审查，契约变更（返回值、异常、签名）的调用方扫描是不可缩减的硬性步骤。本次审查在 quick 模式下仍然抓住了遗漏，说明该原则已内化，值得保持。
- **PR 描述的列表是"风险信号"而非"完成清单"**：作者列出 3 个点，恰好漏了 1 个。规律是：**显式列出的点通常就是作者实际修改的点**，所以列表本身是发现遗漏的最佳线索——对比列表与全仓调用点。
- **测试与代码的同源偏差**：测试和代码通常由同一作者编写，会共享相同的认知盲点。审查者不能因为"测试覆盖全面"就放松对代码路径完整性的独立验证。
- **语义迁移 PR 的"零遗漏"标准**：当 PR 目标是"将 A 统一迁移为 B"时，完成度不是"大部分迁移了"，而是"零遗漏"。任何残留的 A 都是 blocking 级别问题，因为残留点会产生与已迁移点不一致的用户体验。
