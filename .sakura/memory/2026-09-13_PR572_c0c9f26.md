**二、发现的模式**

| 模式 | 说明 |
|------|------|
| **代码风格不统一** | 项目大部分代码已采用 Python 3 的异常捕获写法（`except (A, B):`），但仍残留若干旧式写法。出现位置分散在多个子模块，说明在一次大幅重构（systemd 相关）时，旧文件未同步升级。 |
| **异常捕获倾向“一口气捕多类”** | 多数 `except` 同时捕获 3‑5 种异常，且往往直接把异常当作普通错误处理而不记录上下文。虽然功能上可行，但可读性与后期排查成本较高。 |

| **文档驱动实现** | PR 中大量文档（README、DEPLOYMENT.md）与代码实现保持高度一致，审查者能够通过文档验证实现细节，体现了“文档即规范”的良好实践。 |
| **测试覆盖率提升** | 新增 7 套测试（unit + integration），覆盖 systemd 单元生成、启动/卸载、镜像事务恢复等关键路径，显示出对新功能的 **测试驱动** 开发思路。 |

**三、规范完善建议**

1. **统一异常捕获风格**  
   - **规则**：所有 `except` 必须使用括号形式捕获多个异常，且每个 `except` 块必须显式命名异常对象（`as e`），便于日志记录。  
   - **实现**：在 CI 中加入 `flake8` / `ruff` 的 `E722`（不捕获裸异常）和自定义规则 `EXC001`（禁止 `except A, B:`）的检查。  
   - **补充**：提供项目内部的 **异常处理指南**，约定异常层级（业务异常 → 系统异常 → 意外异常）以及统一的日志记录方式。

2. **关键模块导入安全**  
   - **规则**：对 **入口模块**（如 `__main__`, `systemd.py`）的 **顶层 import** 进行白名单审查，确保任何导入错误都会在单元测试阶段被捕获。  
   - **实现**：在 CI 中加入 `python -m py_compile $(git ls-files '*.py')` 步骤，确保所有文件均能成功编译。若已有该步骤，可将其设为 “必选” 并在 PR 检查中显示。  

3. **异常捕获粒度审查**  
   - **规则**：每个 `except` 块应捕获 **不超过 3 种**异常，超过则需拆分或使用基类异常捕获后在内部细分处理。  
   - **目的**：提升代码可读性，防止“一锅端”式错误屏蔽。  

4. **文档-实现一致性检查**  
   - **规则**：新增或修改的文档章节必须对应至少一条单元/集成测试。审查时检查文档中提及的命令/选项是否在代码中实际实现。  
   - **实现**：使用脚本解析 Markdown 中的代码块或 `--` 参数，交叉匹配代码定义。  

5. **脚本幂等性 & 回退路径**  
   - **规则**：所有新增的 shell 脚本（如 `start.sh`）必须提供 **幂等** 说明及 **非 systemd 环境** 的回退路径。审查时检查关键函数（install、uninstall、status）是否在非 systemd 环境下保持原有行为。  

**四、经验教训**

| 教训 | 说明 |
|------|------|
| **语法层面错误会导致全链路失效** | 本次 PR 中的 9 处 `except A, B:` 语法错误直接让整个包在 import 阶段崩溃，所有业务功能、测试、构建均不可用。**教训**：在大规模功能改动前，务必加入 **全库编译检查**（`python -m py_compile`）以及 **静态代码检查**，防止此类低级错误进入 CI。 |
| **审查时要兼顾“负面”与“正面”** | 虽然审查对 systemd 实现的正向评价非常细致，但对新增脚本的安全性、回退路径缺乏评估。以后审查应 **均衡** 正面亮点与潜在风险，确保每个新增文件都有对应的风险点检查。 |
| **跨文件异常风格统一需要组织层面的推动** | 单文件的风格统一可以通过 lint 自动完成，但跨模块的老旧代码往往需要 **集中迁移**（如一次性运行 `git grep -R "except .*,"` 并统一修复）。项目可以设立 **代码风格迁移里程碑**，在每次大改动前完成一次全库迁移。 |
| **文档与实现相互验证是高效的审查手段** | 本次审查利用了文档与实现的一致性来快速定位功能正确性，这说明 **文档即测试** 的思路非常有效。建议在审查清单中加入 “文档-实现对应检查” 步骤。 |
| **CI 需要覆盖“导入阶段”** | 仅跑单元测试不足以捕获 import‑time SyntaxError，必须在 CI 中显式执行一次 **全库编译** 或 **import‑all** 检查。 |
| **异常捕获的业务语义要清晰** | 多异常捕获往往是为了统一错误处理，但若不记录原始异常信息，会丢失调试线索。建议在捕获块中使用 `logger.exception(...)` 或 `raise ... from e` 进行链式抛出。 |

**结论**  
本次审查在发现阻断性语法错误、评估功能实现方面表现出色，覆盖面广、定位精准。但仍可在 **正向风险评估**、**脚本幂等性**、**全库编译检查** 等方面进一步完善。通过引入统一的异常处理规范、全库编译 CI 步骤以及文档‑实现对应检查，可在后续 PR 中提前拦截类似问题，提升代码质量与合并效率。
