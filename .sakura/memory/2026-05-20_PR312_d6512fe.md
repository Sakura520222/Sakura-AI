## 发现的模式

**代码模式**：
- **同步阻塞**：在 async 路由中直接调用 ChromaDB 同步 API 是常见反模式，项目中可能存在类似问题，需全局扫描。
- **i18n 键缺失**：新增 UI 功能时翻译键未同步更新是重复问题，需强化流程检查。
- **CSRF 策略分化**：JSON API 使用 header CSRF，表单使用 form CSRF，设计合理但缺乏文档说明。

**架构观察**：
- 项目采用 FastAPI + Alpine.js + Jinja2 模板，前后端耦合较紧。
- 依赖注入（如 `get_user_preferences`）使用良好，但部分路由未统一注入，导致参数传递不一致。
- ChromaDB 作为向量存储，同步操作与异步路由的冲突是架构级挑战。

## 规范完善建议

1. **新增审查规则**：
   - **异步路由中的同步I/O**：强制要求使用 `asyncio.to_thread()` 或 `run_in_executor()` 包装同步调用，否则标记为 **major**。
   - **i18n 键完整性**：新增 UI 元素必须同步更新翻译文件，缺失则阻断合并。
   - **CSRF 策略文档化**：JSON API 与表单 CSRF 差异需在代码注释或文档中说明，避免混淆。

2. **项目特有规范**：
   - **ChromaDB 操作封装**：将同步 I/O 抽取为独立线程池服务，统一管理事件循环阻塞风险。
   - **Alpine.js 作用域安全**：模板中动态数据绑定需使用 `@submit.prevent` 或数据属性，避免原生 JS 与响应式数据冲突。
