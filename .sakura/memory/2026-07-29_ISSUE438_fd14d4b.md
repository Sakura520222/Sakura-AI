## 6. 经验教训与改进建议

1. **对极短 Issue 应优先做语义和状态判断，而不是展开无关代码分析。**  
   先判断是否属于测试、误发、空白、占位或恶意内容，再决定是否需要代码检索。

2. **“无可修复内容”不等于“低优先级”。**  
   应区分：
   - `low`：有明确问题，但影响较小；
   - `invalid`：不构成有效 Issue；
   - `wontfix/closed`：确认不处理；
   - `needs-info`：可能有真实意图，但信息不足。

3. **重复检测必须提供可审计证据。**  
   对 `#144` 应输出对比摘要；无法访问或无法确认时，降低置信度并标记待验证。

4. **标签、指派人和标题应基于仓库事实。**  
   需要检查现有标签名称、维护者规则和标题规范，不能仅凭常识推荐 `invalid`、`test` 或自动指派仓库所有者。

5. **测试类 Issue 应引导其转化为可执行任务。**  
   若作者确实在测试 Issue 分析链路，建议要求补充：
   - 测试目的；
   - 预期分类、标签和输出协议；
   - 是否需要保留该 Issue；
   - 测试完成后的清理方式。

6. **建议的最终处理结论应更明确：**  
   “当前内容不足以构成缺陷或需求；若无额外测试目的，建议标记 `invalid`/`test` 后关闭。与 #144 的重复关系在补充对比证据前不应确认。”
