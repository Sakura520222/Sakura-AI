# 深度反思 — PR #202 (e0bcbcc)

## 1. 审查质量评估

### 覆盖度：修复验证停留在"是否修改"层面
审查验证了 `base_branch` 参数"加了"，但没有验证**调用链是否完整传递**。`_find_open_sakura_branch` 新增参数后，`_commit_via_pr` 的调用处是否正确传入了 `base_branch`？这个关键执行流验证缺失。

### 准确度：三个硬规则违反

| 违反规则 | 具体表现 |
|---------|---------|
| **三问法强制绑定** | 两个 major 均无内联三问答案 |
| **自评矛盾检测** | 摘要明确写"风险可控 — 极少超过30条"，却标 major，应自动降级 |
| **评论去重** | 148行与152行描述完全相同的问题，重复标记 major |

### 完整性：修复正确性未推演
`base_branch` 校验标记为"已修复"，但没问：当所有 open sakura PR 的 base 都不匹配时，函数返回 `None`，`_commit_via_pr` 是否正确 fallback 到创建新分支？**"部分修复比未修复更危险"**——这里"已修复"的判定可能过于乐观。

## 2. 发现的模式

**审查行为模式**：历史遗留问题陷入"标记-不修-再标记"循环。分页问题连续3轮标 major，开发者连续3轮不修，说明**严重程度判定与开发者认知不匹配**，审查侧需要反思而不是重复。

**代码模式**：错误处理策略分裂（同服务内抛异常 vs 静默降级共存）是项目级问题，单次 PR 内无法根治，但审查没有将此从"代码问题"升级为"技术债务决策"。

## 3. 规范完善建议

**强化两条已有规则的执行约束**：

1. **suggestion疲劳归档的触发条件明确化**：当前规则写"连续≥3轮未修复标归档"，但实际执行时仍重复标 major。建议改为：**第2轮未修复即降级为 suggestion，第3轮强制归档并从主评论移除**。分页问题在第1轮就应该评估实际影响，第2轮就该归档。

2. **quick策略下历史问题的处理协议**：quick审查应区分"本轮阻断项"和"历史追踪项"。历史追踪项在 quick 模式下**只进摘要表格，不生成独立评论**，避免评论膨胀。

**新增规则**：
- **修复验证须含调用链**：标记"已修复"时，必须验证修改点的上游调用和下游消费是否一致，否则标"待验证"
- **同问题合并评论**：同一代码位置的不同表述必须合并为一条评论，禁止拆分

## 4. 经验教训

1. **"风险可控"是降级信号**：审查者自己在摘要中给出了降级理由，却在评论中维持原级，这是知行分离。应该在写摘要时就触发自检。

2. **quick下≤27行变更的审查颗粒度失配**：用了 quick 策略，但对两个历史问题各写了长段分析和建议，实际产出与策略定位不符。按"微小增量精简"规则，这次报告应≤200字。

3. **类型注解问题不该在quick中提出**：`Optional[tuple]` → `Optional[tuple[str, str]]` 是纯改善性建议，在 quick 策略下属于噪声，消耗了审查者和开发者的注意力。

## 5. 增量审查反思

**修复验证的深度不足**：本轮核心变更是修复"返回值为空"和"分支查找缺陷"，但审查对修复代码本身的正确性（而非"是否修改了"）缺乏推演。增量审查容易陷入**对照清单打勾**的陷阱——看到改了就打✅，而不验证改得对不对。

**未引入新风险**：+27/-7 的变更范围小，且修复逻辑相对独立，未观察到新风险引入。

**覆盖度未明显下降**：因为变更本身范围小且集中在历史问题修复，聚焦验证是合理的。问题不在于"遗漏了什么"，而在于"验证了什么但验证得不够深"。

---

**一句话总结**：本次审查的核心失误是**规则执行形式化**——有规则但不触发自检（三问法、矛盾检测、归档），导致评论膨胀、严重程度失准、修复判定过于乐观。quick策略的价值在于精简，但产出却是"quick的速度 + deep的格式"。
