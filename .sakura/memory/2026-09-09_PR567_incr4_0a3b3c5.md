## 2. 发现的模式  

### 代码模式  
1. **环境变量注入在包入口**：项目倾向在 `backend/__init__.py` 统一设置运行时开关，这种做法易导致 **隐式全局副作用**。  
2. **使用 `os.environ.setdefault`**：保证已有外部传参优先，这是一种良好习惯，但需要配套的 **文档与 CI 检查**，确保所有入口（Docker, helm, systemd）都显式声明。  
3. **测试模式**：新增的单元测试直接 import `RetryAfter` 并检查返回类型，体现了 **“最小可行测试”** 的思路，但缺少 **端到端** 场景验证。  

### 架构观察  
- **依赖图密集**：`backend/__init__.py` 位于根节点，几乎所有子模块在 import 时都会触发其副作用，说明 **初始化层** 对全局状态的控制力度很大。  
- **Telegram 相关功能** 与 **通知服务**、**身份服务** 紧耦合，任何全局配置的变动都会在多条业务链路上传播。

## 4. 经验教训  

1. **全局副作用必须全链路审查**  
   - 环境变量、单例、全局缓存等改动往往在增量审查中“看不见”。审查时应主动 **搜索全局引用**，并考虑 **运行时顺序**。  

2. **配置变更的文档闭环**  
   - 仅在代码里写 `os.environ.setdefault` 不足，必须同步更新 **部署文档**、**helm values**、**Dockerfile**，并在 CI 中验证变量是否被正确注入。  

3. **测试覆盖的层次**  
   - 单元测试验证返回类型是必要的，但 **业务层兼容性** 更关键。针对每个受影响的业务入口（如 `send_notification`、`handle_retry`）补充回归测试，可提前捕获类型不匹配导致的运行时异常。  

4. **审查结论的可追溯性**  
   - “评分 10/10、approve” 需要背后有 **可验证的依据**（搜索、CI 链接），否则审查可信度下降。  

5. **增量审查不等于全局审查**  
   - 本次 PR 只改了两文件，却涉及全局环境变量，审查不能仅停留在增量代码行数。必须 **提升视角**，审查全局影响。
