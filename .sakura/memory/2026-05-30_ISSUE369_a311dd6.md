## 1. 分类与优先级准确性

### 分类

将其分类为 `bug` 可以接受，因为用户反馈“无法安装访问”，属于运行异常或部署失败类问题。

但更准确的候选分类可能包括：

- `bug`
- `installation`
- `deployment`
- `configuration`
- `environment`

如果仓库标签体系中存在 `install`、`deployment`、`setup`、`docker` 等标签，应优先考虑这些，而不是直接锁定到模板渲染兼容性问题。

### 优先级

标记为 `critical` 的依据不足。

“无法安装访问”从用户影响上看可能严重，但原始日志只显示：

```text
Config file '{env_file}' not found.
GitHubAppClient单例初始化完成
LabelService单例初始化完成
```

这些日志本身并不能证明应用完全不可用，也不能证明是全局性阻断问题。尤其是 `Config file not found` 可能只是缺少 `.env` 导致的配置警告，应用仍可能继续启动。

更稳妥的优先级应为：

- `high`：如果用户确实无法访问核心页面；
- `medium`：如果只是安装配置问题、缺少环境变量或文档不清；
- `critical`：只有在确认最新版本默认安装必现、所有用户无法启动/访问时才适合。

### 关键词误判风险

标题“无法安装访问”容易触发高优先级判断，但不能仅靠标题定为 `critical`。需要结合：

- 是否有完整错误栈；
- 是否可复现；
- 是否影响默认安装路径；
- 是否影响所有部署方式还是个别环境；
- 是否是配置缺失、依赖冲突、Docker 构建还是文档问题。

## 5. 标题改写适当性

### 当前建议标题

> [bug][critical] Starlette 1.0.0 breaking change 导致 TemplateResponse 签名不兼容，应用完全无法访问

这个标题技术上很具体，但问题是：**它超出了原始 Issue 能支持的信息范围**。

如果没有完整 traceback 或依赖版本证据，这属于过度改写。标题应该先反映用户真实问题，而不是提前锁定根因。

### 更合适的标题

在证据不足时，可以建议：

> [bug] 安装后无法访问，启动日志提示配置文件未找到

或：

> [deployment] 安装/启动后无法访问，疑似缺少环境配置文件

如果后续确认是依赖问题，再改为：

> [bug] Starlette 1.0.0 TemplateResponse 签名变更导致 WebUI 模板渲染失败

### 标题改写原则

- 保留用户核心现象：无法安装/无法访问；
- 引入已知日志线索：配置文件缺失；
- 避免在证据不足时写死根因；
- 避免直接标 `critical`，除非确认全局阻断。

## 6. 经验教训

### 经验一：Issue 分析要区分“症状”和“根因”

“无法访问”只是症状。可能原因包括：

- `.env` 缺失；
- 配置项缺失；
- GitHub App 凭据错误；
- 数据库连接失败；
- 端口映射错误；
- Docker 构建失败；
- 前端静态资源缺失；
- 模板渲染失败；
- 第三方依赖 breaking change。

不能因为仓库历史上出现过 Starlette 问题，就直接套用到当前 Issue。

### 经验二：日志中的直接信号应优先分析

当前最直接的信号是：

```text
Config file '{env_file}' not found.
```

未来遇到类似 Issue，应优先检查：

1. `.env` 是否要求必须存在；
2. 示例配置文件是否完整；
3. 缺失配置时是否应该 fail-fast；
4. 日志是否正确打印实际路径；
5. 安装文档是否明确说明创建配置文件；
6. Docker/Compose 是否正确挂载环境变量。

### 经验三：依赖兼容性问题需要版本证据

如果判断为依赖 breaking change，应至少具备以下证据之一：

- `pip freeze`；
- `requirements.txt`；
- Docker 构建日志；
- 完整 traceback；
- 可复现命令；
- 代码调用点；
- 官方 release note 链接。

否则应标注为“可能原因”，而不是直接作为确定结论。

### 经验四：重复检测不能只看症状

“无法访问”“启动失败”“安装失败”这类 Issue 很容易误判重复。重复检测应基于：

- 相同错误栈；
- 相同依赖版本；
- 相同复现步骤；
- 相同修复方式；
- 相同影响模块。

如果只是表象相同，应标为“可能相关”而非“重复”。

### 经验五：建议增加 `needs-info` 流程

对于这类信息不足的 Issue，分析结果中应主动生成追问清单，例如：

```text
请补充：
1. 安装方式：源码 / Docker / Docker Compose？
2. Python、FastAPI、Starlette、Jinja2 版本。
3. 完整启动日志和访问时报错栈。
4. 是否创建了 .env 文件，是否基于 .env.example。
5. 访问的具体 URL、HTTP 状态码。
6. 是否使用默认配置。
```

这比直接给出具体修复方案更可靠。
