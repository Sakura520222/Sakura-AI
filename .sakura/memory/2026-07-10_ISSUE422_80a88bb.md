## 6) 经验教训

### 这类 Issue 分析要特别注意的点

#### 1. “重写/统一”不等于纯重构
- 这种描述常常伴随：
  - 新协议支持
  - 新 UI
  - 新数据结构
  - 兼容旧配置
- 所以必须同时检查“架构影响”和“功能扩展”，不能按纯重构处理。

#### 2. 配置类 Issue 要看“配置源”和“配置流”
要问清楚：
- 配置是写入 DB、env 还是文件？
- 运行时读取来源是什么？
- 是否存在多源冲突？
- 是否需要迁移和回退？

这类问题的风险不在 UI，而在**一致性和兼容性**。

#### 3. AI Provider 支持不能只看接口名
不同厂商之间最容易踩坑的是：
- 模型列表接口是否一致
- 消息格式是否一致
- 推理参数是否能统一
- 错误码、鉴权、streaming 是否一致

所以“兼容 OpenAI”这句话不能直接等价成“能复用同一请求路径”。

#### 4. Setup Wizard 是高影响入口
一旦涉及 Wizard：
- 初始体验
- 引导逻辑
- 回退路径
- 默认值
- 失败提示
都要一起看。
这类改动通常比表面上“只是加个表单”更重。

### 仓库特有建议
- 该仓库明显围绕 AI Reviewer 和 provider 配置，**provider 抽象层是核心模块**
- 以后遇到类似 Issue，建议优先检查：
  1. provider 注册方式
  2. 模型发现机制
  3. 配置持久化来源
  4. Wizard 初始化流程
  5. 多语言/文案同步
- 若涉及“内置最新模型”，还要警惕：这会不会变成长期维护负担，而不是一次性开发。
