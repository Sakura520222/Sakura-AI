### 二、发现的模式

#### 🔁 代码模式

**1. “快照式”副作用设计**
- `apply_labels_to_pr` 仅依赖初始 `existing_labels` 快照，忽略执行中的状态变化
- **暴露问题**：服务层设计未考虑“批量操作中间状态”的可观测性
- **类似风险扫描**：同文件中是否有其他方法（如 `remove_label_from_pr`）也存在“基于旧状态判断”的逻辑？

**2. “静默降级优先”的异常处理**
```python
# label_service.py:377
existing_labels = self.get_pr_existing_labels(...) or []  # 失败变空列表
```
- **模式本质**：为简化调用方逻辑，牺牲异常可区分性
- **项目记忆关联**：符合“日志静默传染”高危模式，审查已发现但仍需在规范中强化“失败必须返回 None 或抛异常”。

**3. “字符串解析即信任”**
```python
blocked_raw.replace(",", " ").split()  # 过度切分
```
- **深渊模式**：直接基于用户输入做空白切分，未考虑标签名保留原始空格的需求
- **类似风险**：WebUI 中其他配置输入（如 `exclude_labels`、`auto_approve_patterns`）是否也存在同名问题？

#### 🏗️ 架构观察

**1. 分层边界模糊**
- `LabelService` 既负责配置加载，又负责冲突检测，还负责 GitHub API 调用（`get_pr_existing_labels`）
- **建议**：参照项目记忆中的 `comment_service` 单一职责教训，未来可抽取 `LabelConflictEngine` 独立。

**2. 配置双入口不一致**
- WebUI 支持 `conflict_rules`，但 API (`api/v1/config.py`) 返回值未包含该字段
- **根因**：增量开发时仅实现前端入口，未同步 API 契约 → 触发“增量审查陷阱”中的“全生命周期扫描”要求。

**3. AI Prompt 注入的“半接入”模式**
- `build_label_recommendation_message(new_existing_labels=True)` 但调用方未传参
- **模式**：新增参数时，开发者容易忽略所有调用位置（`LabelRecommender` 有多处调用？）

### 三、规范完善建议

#### 📜 建议新增/修改的审查规则

**规则 1（major）：批量操作状态追踪规则**
> 当服务层方法执行“循环应用标签/评论/文件”等批量操作时，若依赖“已有状态”做判断，则必须在循环内维护 `effective_entities` 集合并实时更新，禁止仅使用初始快照。

**规则 2（major）：配置解析禁止破坏标签名**
> 解析 GitHub 标签列表或用户输入的冲突规则时，必须保留标签名的原始空格（如 `good first issue`）。仅允许按 `,` 或 `\n` 分隔，禁止按普通空格 `split()`。

**规则 3（major）：外部依赖失败必须显式降级**
> 获取 GitHub 标签/文件/评论等外部资源失败时，禁止返回空列表/空字典替代“未知状态”。必须返回 `None` 或抛异常，调用方需显式处理（如跳过自动操作、记录 warning）。

**规则 4（suggestion）：REST API 与 WebUI 配置同步检查**
> 新增 WebUI 配置字段时，必须在同一 PR 中同步更新 `api/v1/config.py` 的 GET/PUT 端点，否则触发 major 级别的“增量审查陷阱”标记。

**规则 5（suggestion）：新增参数必须追踪所有调用方**
> 修改公共函数签名（新增参数）时，PR 描述中必须列出所有调用位置并确认已接入，否则审查自动标记 suggestion。

#### 📌 项目特有规范要点（更新到项目记忆）

- **标签冲突检测规范**：
  - 自动应用标签时，必须维护 `effective_existing_labels` 集合（初始 PR 标签 + 本次已成功应用的标签）
  - 批量推荐标签应先做批内冲突预检（互斥标签同时出现时直接拒绝全部）
  - `get_pr_existing_labels` 失败必须返回 `None`，上层遇到 `None` 时禁止自动应用，仅输出 `suggested` 状态

- **配置解析红线**：
  - 禁止使用 `.replace(',', ' ').split()` 模式解析标签列表
  - 统一使用 `[item.strip() for item in raw.split(',') if item.strip()]`

- **异常降级策略**：
  - 外部 API 失败时，默认行为应为“拒绝高风险操作”（如自动打标签），而非“静默继续”

### 四、经验教训

#### 🧠 值得在未来审查中关注的要点

1. **“批量操作”审查清单**：
   - [ ] 循环内是否依赖外部状态？
   - [ ] 状态是否在循环内实时更新？
   - [ ] 是否有“批内预检”机制？

2. **配置解析审查清单**：
   - [ ] 是否使用了 `split()` 不带参数？
   - [ ] 是否处理了空格、逗号、换行混合输入？
   - [ ] 是否保留标签名内部空格？

3. **异常处理审查清单**：
   - [ ] 外部调用失败后返回的是“空值”还是“None”？
   - [ ] 调用方能区分“无数据”和“获取失败”吗？
   - [ ] 失败时是否有 warning 级别日志？

4. **增量参数审查**：
   - [ ] 新增参数是否在所有调用位置实际传入了值？
   - [ ] 是否有“参数已存在但 caller 未使用”的死路径？

#### 🔍 特定技术/模式的审查经验

**模式：单例服务 + 热加载配置**
- **风险点**：配置更新时是否有锁保护？读取时是否可能读到半更新状态？
- **检查方法**：扫描 `update_config` 方法，确认是否使用 `asyncio.Lock` 或原子替换整体字典。

**模式：AI Prompt 动态注入上下文**
- **风险点**：新增上下文信息（如 `existing_labels`）是否在调用链中完整传递？
- **检查方法**：从 prompt builder 的参数反向追踪到最外层调用（如 `review_worker`），确认每个环节都透传。

**模式：WebUI 表单 + API 双配置入口**
- **风险点**：两个入口的校验逻辑、默认值、序列化格式是否一致？
- **检查方法**：对比 WebUI 保存时的 JSON payload 与 API PUT 的期望格式。
