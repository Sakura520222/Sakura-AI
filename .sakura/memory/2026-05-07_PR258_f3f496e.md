## 2. 发现的模式

### 代码模式
- **`_cancel_and_cleanup`公共清理函数**：优秀实践，消除了取消路径不一致风险。
- **`_safe_db_delete`模式**：优雅处理多表删除，但缺少session状态注释。

- **依赖关系**：`webhook` → `worker` 存在循环引用，通过延迟导入+注释处理，符合规范。

- **多检查点收敛**：4个取消检查点 + `finally`清理，成熟的生产级任务模型。

### 技术债务暗示
- **`task_id`与`task_key`混用**：变量名语义滞后于返回值变更，提示需要类型标注或重构为结构化返回。
- **前端状态模板未同步**：多次出现“新增枚举值遗漏前端分支”，说明需要自动化检查或前端类型生成。

## 4. 经验教训

### 值得在未来审查中关注的要点
- **返回值语义变更**：即使函数内部重构逻辑，只要返回值类型/含义变化，必须扫描所有调用方（包括外部模块）。
- **“静默成功”风险**：`force_new=True`覆盖event、`_safe_db_delete`部分失败后继续提交 —— 这些行为需要显式可观测性。
- **SSE前端处理**：后端增加新状态后，前端可能默默忽略（落入else显示pending），必须人工或自动化验证。

### 对特定技术/模式的审查经验
- **asyncio.Event取消模式**：
  - Event只能发信号，不能携带取消原因。如果未来需要取消原因（如“由用户取消”vs“超时”），需改用`Queue`或`Future`。
  - 注册event必须在`create_task`之前，否则任务已开始运行且无法取消排队状态。
- **数据库session污染**：`except Exception`后session可能进入inactive状态，若不重建或rollback，后续相同session的查询会失败。`_safe_db_delete`中使用独立session或新查询可避免，但应注释说明。
- **task_key vs task_id**：复合返回值（如`owner/repo#pr_number`）不如结构化类型安全，建议未来引入`TaskKey`类或`NamedTuple`。
