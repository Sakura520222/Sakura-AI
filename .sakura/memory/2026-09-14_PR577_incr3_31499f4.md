## 2. 发现的模式  

### 代码模式  
- **依赖声明统一**：项目坚持 `pyproject.toml ↔ requirements.txt` 双清单镜像，且已有自动化测试 `test_pyproject_dependencies_mirror_requirements_txt` 进行行对行校验。  
- **零调用依赖**：`python‑slugify`、`alembic`、`watchfiles` 等在代码库中几乎没有直接 import，说明这些库主要在 **外部脚本、CI、迁移工具** 中使用，或是历史遗留。  
- **大量 merge commit**：增量 PR 中多次 `merge remote-tracking branch 'origin/main' into develop`，导致提交历史噪声，审查时需要过滤掉这些合并提交。  

### 架构观察  
- **层次清晰的后端/向量存储**：`vector_store.py` 与 `code_vector_store.py` 负责向量命名，手写正则实现而非依赖 `slugify`，体现了对 **可控性** 的追求。  
- **热重载机制**：`backend/core/hot_reload.py` 使用 `watchfiles`，并显式传入 `stop_event`、`ignore_permission_denied`，表明对 **跨平台文件权限** 有细致处理。  
- **依赖锁定流程**：项目在 CI 中使用 `uv lock --check`，但在 PR 流程中缺少强制更新锁文件的检查点，导致 **锁文件漂移** 成为潜在风险点。

## 3. 规范完善建议  

| 建议 | 目标 | 具体实现 |
|------|------|----------|
| **强制锁文件同步** | 防止发布包与源码锁文件不一致 | - 在 CI 中加入 `uv lock --check` 并把返回码设为 **error**；<br>- 在 PR 模板或合并保护规则中要求 **`uv.lock` 必须随依赖变更一起提交**； |
| **依赖使用审计** | 清理零调用依赖、降低维护成本 | - 定期运行 `pipdeptree --warn silence` + 项目全局搜索，生成 **未被 import** 的依赖列表；<br>- 对列表中的依赖发起 **“可移除”** 议题，或在 README 中注明仅供外部脚本使用。 |
| **升级后行为回归测试** | 捕获默认行为变更导致的业务回归问题 | - 为 `python‑slugify` 添加 **snapshot test**（对比升级前后相同输入的 slug 结果）；<br>- 在 `watchfiles` 升级后验证 **热重载** 在不同 OS 权限下的表现。 |
| **合并提交清理** | 降低审查噪声、提升历史可读性 | - 在开发分支使用 **rebase** 或 **squash**，避免大量 “merge remote‑tracking branch” 提交进入主线；<br>- 在 CI 中检测合并提交数量，超过阈值给出警告。 |
| **审查规则细化** | 提升 quick 策略的覆盖度 | - **依赖升级**：① 检查 `pyproject.toml` 与 `uv.lock` 同步；② 检查 **API 兼容性**（通过 changelog、type‑stub）并要求最少一条运行时测试覆盖该库的关键路径； |
| **文档同步** | 防止 README/CI 示例与实际依赖不符 | - 在 CI 中加入脚本比对 `README.md` 中的示例安装指令（如 `pip install "python‑slugify>=9"`）与 `pyproject.toml` 中的约束。 |

## 4. 经验教训  

1. **锁文件是不可或缺的审查点**  
   - 即使双清单已经同步，锁文件漂移仍会导致发布环境使用旧的依赖版本。审查时必须把 **锁文件更新** 设为阻断项。  

2. **零调用依赖不等于“安全”**  
   - 依赖可能在 **CI、Dockerfile、迁移脚本** 中被间接使用。仅凭代码搜索判断可删除会误删，需结合全局构建链路审查。  

3. **升级后默认行为的隐蔽影响**  
   - `python‑slugify 9.0` 将默认算法从 “legacy” 改为仍是 “legacy”，但引入了 **opt‑in modern**，如果业务误用了新参数或依赖了旧行为的细节（如字符截断），可能出现意外。  
   - 建议在升级前阅读 **migration guide**，并在 **单元测试** 中加入关键输入的期望输出。  

4. **增量审查的盲点**  
   - 只看增量提交会忽略 **历史遗留问题**（如锁文件未更新的旧提交），导致审查结论偏乐观。  
   - 在增量审查前，先跑一次 **全库依赖一致性检查**（包括锁文件），再针对增量做细化评估。  

5. **审查策略与实际风险匹配**  
   - “quick” 适合小幅度、低风险改动；但本次一次性升级了四个库，风险累积，建议升级到 **medium** 或 **full**，以确保每个库的兼容性都得到充分验证。

### 小结  

- 本次审查质量符合 quick 预期，但在锁文件同步与升级后行为回归方面仍有提升空间。
