# 审查反思报告

## 1. 审查质量评估

**覆盖度：存在一处声明可信度问题**

审查摘要声称"配置三件套完备"，但本次只审查了2个文件的diff。配置三件套（字段定义 + DYNAMIC_CONFIG_GROUPS + DYNAMIC_CONFIG_LABELS）若全部在 `config.py` 中，则 +4 行可能确实覆盖了全部三项；但若 GROUPS/LABELS 在其他文件中，该声明就是未经验证的假设。quick 策略下信息受限是常态，但**受限不应产出确定性声明**——要么确认后声明，要么不声明。

**准确度：评分合理但偏乐观**

9 分在 quick + 25 行 + 空评论的组合下处于上限。按项目记忆"评分须反映审查输出质量而非仅代码修复质量"，空评论意味着审查输出本身信息密度极低，"正确判断无问题"的价值有限。8 分可能更准确——承认策略限制下的正确执行，但不对输出质量过度溢美。

**完整性：PR 描述与增量提交主题错位未标注**

PR 描述全部围绕 `issue_reflection` 展开，但本次提交是 `sakura_use_summary_model`。虽然增量审查以提交 diff 为准，PR 描述仅作参考，但这个错位在摘要中完全未提及。按"PR 描述覆盖校验"规则的精神，至少应有一句说明"本次提交变更点不在 PR 原始描述范围内"。

## 2. 发现的模式

**代码模式**：配置扩展遵循固定三件套范式（字段 + 动态配置组 + 动态标签），service 层通过 `_get_config` 统一读取并向下传递，模式一致性好。

**架构观察**：辅助模型支持（summary_model）与之前新增的 issue_reflection_model 走同一条配置-集成路径，说明项目在模型选择上的架构已经稳定化，新增模型支持变为低风险的模板化操作。

## 3. 规范完善建议

**新增规则：受限信息下禁止确定性声明**

> quick 策略下，审查摘要中涉及"完备性""一致性"等需要全量文件验证的结论性声明时，若 diff 未覆盖全部相关文件，必须使用"在可见范围内"等限定词，或直接省略该声明。

**强化规则：PR 描述与增量提交错位标注**

> 在"PR 描述覆盖校验"中补充：当增量提交引入 PR 描述未提及的新变更点时，摘要中须显式标注"本次提交包含 PR 描述外的新增变更"。

## 4. 经验教训

- **"三件套完备"是高频声明但低频验证**：quick 下容易基于模式惯性输出此类结论，实际可能只验证了一到两件。应将其视为需要 diff 证据支撑的声明，而非默认填充项。
- **空评论 + 高分组合的信号**：连续出现时可能意味着评分锚定在"代码质量"而非"审查输出质量"，需要周期性校准。

## 5. 增量审查反思

- **新增提交不涉及历史问题**：`sakura_use_summary_model` 是独立功能点，与历史追踪的 fire-and-forget shutdown 风险无直接交集，按"quick 历史问题协议"省略追踪表是正确的。
- **未引入明显新风险**：辅助模型支持本质上是配置驱动的条件分支，不改变核心调用链路结构，quick 策略适用。
- **覆盖度未因增量下降**：本次变更范围小且模式成熟，quick 的覆盖度足够。真正的覆盖度风险不在"只看增量"，而在"对增量做出超出可见范围的断言"。
