## 2. 发现的模式

### 代码模式
- **防御代码边界粗糙**：新增的 `_dedup_inline_comments` 是典型防御性编程，但 key 设计和默认值处理体现了一种常见反模式——「有防御意识但防御粒度不够」，导致防御本身引入新问题（默认值 0 导致误去重、key 维度不足导致误丢弃）。
- **双路径对称性忽视**：JSON 路径与 emoji fallback 路径在历史上多次出现不对称处理（去重、提取逻辑等），开发者倾向于只修主路径。

### 架构观察
- `result_parser.py` 作为核心解析器，持续是热点文件（10+次标记），其双路径（JSON/emoji）架构的复杂性是问题滋生根源。每条路径的独立修改容易破坏对称性。

## 3. 规范完善建议

### 新增规则
- **标签跨区一致性硬校验**：「主要评论」中的 `[major]/[critical]` 必须与正文分区标签严格对应。若正文放🟡/💡分区，摘要中禁止使用 major/critical。建议在输出流程中增加校验步骤：提取摘要中所有 major/critical → 反查正文分区 → 不一致则阻断或降级。
- **同位置问题合并规则**：同一文件同一行号的多个观察点（如 :395 的去重 key 和默认值问题）应合并为单条评论，避免碎片化。
- **历史闭环记忆联动**：`[遗留确认] ✅已修复` 的条目必须同步触发项目记忆中对应条目的状态更新或移除。

### 修改规则
- **quick策略下防御性建议的级别锚定**：审查者自述「不太可能产生」「概率极低」的问题，在 quick 策略下应直接定级 suggestion，禁止升级。

## 4. 经验教训

- **去重逻辑是高频陷阱**：key 设计需三问——①默认值是否会产生虚假碰撞？②唯一性维度是否覆盖实际区分需求？③丢弃时是否有可观测性（日志）？本次两个 suggestion 全部命中此陷阱。
- **防御代码的「不可能路径」仍需对称处理**：即使当前不会触发，不对称的防御结构在未来重构时极易成为隐患。这不是过度工程，是架构卫生。
- **小 diff 不等于无执行流影响**：+16 行修复了一个被多处调用的函数，影响范围由调用方决定而非 diff 大小决定。
