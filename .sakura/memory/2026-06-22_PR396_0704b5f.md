# 审查反思：PR #396

## 1. 审查质量评估

### 覆盖度：存在明显盲区

**遗漏的关键问题：**

- **协议过度容错的误解析风险**：审查正面评价了容错设计，但未追问反面——增强容错是否会让**真正的格式错误**被静默吞掉？应要求补充"故意错误的输入不应被解析为有效结果"的负面测试用例。这直接违反了项目记忆中"测试覆盖了函数≠覆盖了行为"的原则。

- **Score clamping 的具体实现与边界**：从 `raise` 改为 `clamp` 是行为契约变更，但审查未追问：clamp 范围是什么？分数为 0 或负数时行为？超过 10 时行为？这是"小控制流变更也是契约变更"的典型场景。

- **`_realign_suggestion_indentation` 的降级路径**：当 diff 中找不到对应行缩进映射时（重命名文件、二进制文件、空 diff），函数行为未审查。基于 diff 解析的功能必须评估边界。

- **Markdown 注入风险**：suggestion 内容如果包含 ` ``` `，渲染到 GitHub comment 时会导致 markdown 块提前闭合。审查完全未提及。

- **pr_analyzer → comment_service 的隐式数据流**：缩进映射从 diff 提取后在 comment_service 消费，但这个跨模块数据流没有接口层面的契约定义。

### 准确度：基本合理，但有低估

- minor/suggestion 的分级准确，四条发现都定位精确
- **可能低估**：协议解析重构的回归风险和 markdown 注入应至少标 minor
- **可能高估**：对"测试覆盖全面"的正面评价，根据"测试与代码的同源偏差"原则，同作者新增 394 行测试恰好覆盖 394 行改动，这本身是警告信号而非正面信号

### 完整性：意图理解到位，上下文深度不足

审查准确理解了"增强 AI 输出格式化能力"的主线，但对管道架构中跨模块数据流（缩进映射）的完整性验证不足。

## 2. 发现的模式

**代码模式：**
- **渐进容错**：在现有解析器上叠加兼容层而非重写，风险可控但复杂度递增
- **防御性编程不一致**：缩进补齐做了防御，文件转储没做防御——同一 PR 内防御标准不统一
- **延迟导入无规范**：标准库模块也用延迟导入，说明项目可能存在启动性能焦虑，但缺少统一规范

**架构观察：**
- `pr_analyzer`（数据提取）→ `review_protocol`（解析）→ `comment_service`（渲染）的管道中，缩进映射是**跨层直通数据**，绕过了中间层的接口定义，形成隐式耦合

## 3. 规范完善建议

建议新增以下审查规则：

| 规则名称 | 核心要求 |
|---------|---------|
| **AI 输出容错的负面验证** | 增强容错性时，必须补充"错误输入不应被解析为有效"的负面测试 |
| **诊断转储的生产就绪标准** | 新增文件转储功能必须包含：数量上限、单文件大小上限、清理机制、async 上下文适配 |
| **移除安全网替代验证** | 移除截断/限制等隐式安全网时，必须提供显式替代或论证不再需要的依据 |
| **Diff 解析边界强制评估** | 基于 diff 的功能必须覆盖：空 diff、二进制文件、重命名、大文件 |
| **Markdown 嵌入注入检查** | 将外部内容嵌入 GitHub markdown 时，必须评估 ``` 等语法元素的干扰 |

## 4. 经验教训

1. **容错性增强是双刃剑，审查必须看两面**：不能只验证"正确的输入能被容忍"，必须验证"错误的输入不会被误判为正确"。本次审查只看了正面。

2. **"测试量大的 PR"应触发同源偏差警报**：新增测试行数与改动行数高度匹配时，审查者应主动寻找"作者没想到的路径"而非确认"覆盖全面"。

3. **跨模块数据流是管道架构的脆弱点**：当数据从 A 模块提取、跳过 B 模块、在 C 模块消费时，B 模块的接口变更不会触发 C 模块的适配检查。审查时应将此类直通数据流标为关注点。

4. **移除限制比新增限制更值得深挖**：`decision_engine` 移除截断时，审查只标记了"缺少上限保护"，但更深层的问题是：GitHub comment 有 65536 字符硬限制，这个隐式约束是否在架构中有任何层的保障？应追问而非仅建议。
