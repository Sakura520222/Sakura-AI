## 深度反思：PR #220 审查

### 1. 审查质量评估
- **覆盖度**：未发现遗漏。变更精准，且确认了“全仓库无残留 `rerank/` 模式”，排除了同类模式扩散。

- **完整性**：充分理解了问题根因（`base_url` 携带路径细节 + `post("/")` 拼接逻辑）与修复方案。审查基于 `config.py` 中 `rerank_base_url` 的实际情况做出了正确推断。

### 2. 发现的模式
- **配置与调用耦合的反模式**：`config.py:179` 中 `rerank_base_url` 包含了 `/v1/rerank` 的完整路径，而不是纯主机/端口。这迫使使用者（`embedding_service.py`）必须意识到其尾部已带路径，从而只能传空字符串，是一种隐式契约。
- **HTTP 客户端透明性不足**：`AsyncOpenAI` 封装显然不会自动跟随重定向或记录 3xx 状态，导致 307 变成一个静默失败，依赖下游调用者自行排查。这与项目记忆中“**HTTP客户端应全局启用重定向跟随或显式告警3xx非透明失败**”的教训完全吻合。
- **微小增量精确扫描**：这次审查确实践行了“全仓库无残留”的扫描，避免了同类问题在其他服务中潜伏。

### 3. 规范完善建议
基于本次案例，应强化以下规则：

- **配置拆分规则（新增）**：
  > `base_url` 等配置项**禁止**包含 API 路径段（如 `/v1/rerank`），应拆分为 `base_url`（`scheme://host:port`）与 `api_path`，由调用方显式拼接。若历史遗留已含路径，必须添加注释声明禁止追加额外路径，并将该债务归档。
- **HTTP客户端健壮性检查项（强化）**：
  > 任何需要依赖外部 API 调用的代码，审查时必须确认底层 HTTP 客户端是否启用了**重定向跟随**（如 `follow_redirects=True`）或至少对非 2xx 响应有**显式日志告警**。缺失时至少标记 `suggestion`，若可能造成静默功能退化则升级为 `major`。
- **修补后同类调用扫描模式固化**：
  > 当修复涉及字符串拼接（如 URL、SQL 片段）时，强制全文检索相同客户端/工具类的其他调用点，检查是否存在同类模式，即使当前未报错也应列入潜在风险注释。

### 4. 经验教训
- **API URL 拼接陷阱的每一次修复都只是“救火”**：真正的根因是隐含契约和透明性缺失。未来在任何项目中，一旦发现 `base_url` 内嵌路径，应将其视为**技术债 Issue**，推动配置重构，而非满足于逐次修补。
- **重定向非透明失败是系统性弱点**：硅基流动的 307 本可以是临时性问题，但客户端未跟随重定向则变成了永久故障。今后审查任何 HTTP 集成时，必须假设“服务端随时可能返回 3xx”，并评估客户端是否有能力处理，否则就是脆弱设计。
- **微小变更不意味着低风险**：两行改动修好一个功能，但背后暴露的配置/客户端设计问题需要单独记录，否则会在后续迭代中被遗忘。本次审查虽已 approve，但反思后可建议创建技术债 Issue（如“抽象 rerank 客户端，剥离 base_url 中的路径细节”），避免下一人误踩。
