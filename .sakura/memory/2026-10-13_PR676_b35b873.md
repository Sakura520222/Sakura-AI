### 2. 发现的模式

- **代码模式**：
  - **基于 ContextVar 的分层与不可变状态传递**：通过 `traced_operation` 与 `task_logging`，在异步流式输出、后台任务与跨线程调度间维持严格隔离与血缘追踪。
  - **异常附带元数据（Escaping Exception Metadata）**：在 Exception 实例上动态挂载 `_log_correlation` 和 `_log_redaction_secrets`，使得错误在穿越调用栈被顶层捕获时，依然具备精确的脱敏和溯源能力。
  - **防御性文件交接**：放弃常规环境变量/标准输出打印敏感 Token，采用 POSIX `0600` mkstemp + `os.replace` 原子替换，兼顾平台 ACL 与进程间一次性交接。
- **架构观察**：
  - **横切日志桥接架构（Logging Bridge & Loguru Sink）**：系统处于 stdlib `logging` 与 `Loguru` 的双轨/桥接期。任何挂载在桥接层上的全局过滤器或 patcher，都位于整个应用的最内层热路径（甚至截获第三方依赖的全部 DEBUG 日志），计算复杂度放大效应极强。

### 3. 规范完善建议

建议在《项目记忆》的**“异步并发与 Agent Harness”**或**“架构隔离与业务设计”**中新增以下审查规则：

1. **日志拦截与热路径开销防线（Log Patcher Hot-Path Guard）**：
   - 挂载在 Loguru 全局 patcher、`logging` Handler/Filter 上的脱敏或字段提取逻辑，严禁在单条日志内重复执行昂贵操作（如无缓存的正规化扫描、遍历大对象 `__dict__`、扫 `os.environ`）。
   - 若需动态感知配置，脱敏规则须在 Module/Process 级别做带版本/哈希的缓存，或挂载在单次记录生命周期（Record Local Cache）内，避免乘以 sink 数量与高频 DEBUG 吞吐量。
2. **敏感凭据文件交接生命周期（Handoff File Safety）**：
   - 凡涉及引导凭据（Bootstrap/Setup Token）的文件交接，必须保证：原子写（`mkstemp` + `replace`）、最小权限（POSIX `0600` / Windows ACL）、启动轮换（Startup Rotation）以及消费即焚（Consume & Delete）。

### 4. 经验教训

- **框架级生命周期对复杂度的隐式放大**：
  - 在类似 Loguru 的系统中，一条 LogRecord 从发起到落地，会依次流经：Logger 本地 patcher → 全局 patcher → 各 Sink Filter → Formatter。
  - 在审查类似“全局脱敏/格式化”中间件时，必须在脑中模拟其**被调用频次公式**：$N_{\text{calls}} \approx N_{\text{patchers}} + N_{\text{sinks}}$。在 `DEBUG` 级别全开时，这种微秒级的无缓存全量正则/字典遍历会演变为毫秒级的性能劣化。
- **安全与性能的平衡（Fail-Closed 缓存）**：
  - 提供性能优化建议时，切忌破坏“动态生效”与“脱敏闭环”。建议采用的“单条 Record 生命周期缓存”技巧极为漂亮：既消除了单条日志在跨 Filter 时的重复计算，又保证了下一条日志能实时感知动态配置更新，且不会导致 Token 在内存常驻泄漏。
