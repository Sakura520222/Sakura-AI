## 深度反思

### 1. 审查质量评估

**覆盖度：存在结构性盲区**

本轮对 diff 内的 6 个变更点逐一验证，逻辑正确性覆盖充分。但存在两个盲区：

- **状态不可逆性未质疑**：stale repo 清理设 `is_displayed=False` 是单向操作，如果 owner 恢复可见性或仓库 rename-back，当前没有"重新发现"机制。审查验证了"隐藏正确性"，未验证"恢复可达性"——这直接违反了"状态机逃脱路径"原则，但本轮未触发。
- **权限层级一致性未检查**：`refresh_summary_route` 的鉴权加在路由层。如果同一 service 方法存在其他调用入口（worker、内部函数），该鉴权被绕过。审查只验证了"这个路由有了鉴权"，未验证"这个 service 方法是否需要鉴权"。

**准确度：判断合理，无误判**

两个 minor 标记精准：测试声明缺失确实导致 pytest 不收集该用例（功能性缺陷，非风格问题）；硬编码中文 + `str(exc)` 泄漏违反了"内部错误信息禁止泄漏至用户界面"的硬规则。严重程度恰当，未高估也未低估。

**完整性：微观充分，宏观不足**

PR 描述与 diff 的逐项勾选完成度好，前序问题状态表清晰。但"未重新验证"部分仅列了模块名，缺少一句关键判断：**本轮 service 层同步逻辑的变更是否改变了 worker 调用时的前置假设？** 如果 `refresh_available_repositories` 过去返回空列表时 worker 有特定行为，现在返回隐藏仓库后行为是否一致？这是增量审查最易遗漏的"隐式契约破坏"。

### 2. 发现的模式

**代码模式：**
- **软删除偏好**：stale repo 和 banned member 仓库都用 `is_displayed=False`，项目倾向于保留数据而非物理删除。这带来累积风险——缺少定期清理机制。
- **防御性逐步加固**：第1轮缺鉴权→第2轮补鉴权，第1轮缺状态检查→第2轮补检查。初始实现偏乐观，靠审查驱动加固。这本身不是问题，但意味着**首轮审查的"安全边界"检查权重应提高**。
- **`full_name` 作为历史兼容层**：`repo_id` 优先 + `full_name` 兜底，说明存在仅按 full_name 存储的迁移期数据。这种双键查找模式在 rename 场景下正确，但如果两个 repo 先后占用同一个 full_name（delete→recreate），可能产生误匹配——虽然概率极低，但未在审查中讨论。

**架构观察：**
- **权限检查在路由层而非服务层**：这意味着权限与业务逻辑分离不彻底。如果后续新增 API 端点复用同一 service 方法，鉴权容易遗漏。
- **token 刷新与业务操作耦合**：`join_plan` 内调用 `get_effective_access_token` 触发刷新，失败会阻断加入操作。这个副作用链路没有独立的降级策略。

### 3. 规范完善建议

**建议新增的审查规则：**

1. **"软删除累积风险"检查**：当变更引入新的 `is_displayed=False` / `is_deleted=True` 标记时，须追问：(a) 数据累积速率 (b) 是否有定期清理任务 (c) 恢复路径是否存在。无恢复路径且无清理机制时标 minor。
2. **"权限检查层级一致性"规则**：同一 service 方法被 ≥2 个路由调用时，权限检查应在 service 层；若仅在 route 层，须声明"单入口，无内部调用"。
3. **"前序问题连续追踪升级"机制**：同一 minor 问题连续 ≥2 轮未修复且不在 diff 范围内时，第 3 轮须升级为"建议拆分独立 PR 修复"或标记为合并阻断条件，避免无限顺延。
4. **"邻接区域连带审查"正式化**：新增代码行号 ±30 范围内的已知问题，即使不在 diff 中，也须作为 suggestion 提出（本轮已实践，应固化为规则）。

**项目特有规范：**
- i18n key 已存在但代码仍用硬编码的情况，应作为自动 lint 检查项（grep f-string 中文字面量 → 交叉验证 yaml key 是否存在）。

### 4. 经验教训

1. **"可接受"需要失败路径证据**：本轮对 `get_effective_access_token` 的副作用判定为"可接受"，但未验证 token 刷新失败时的异常传播路径。"可接受"的标准应是"已验证失败场景行为合理"，而非"没看到明显问题"。
2. **正向验证密集时强制执行负面检查**：6 个变更点全部 ✅，这是隧道视野的高危信号。应在流程中强制插入"回头问"步骤：看完 diff 后，不看描述，只看代码，问自己"这些改动可能破坏什么"。
3. **增量评分的双轨声明缺失**：quick 策略要求区分"增量质量分"与"PR 整体可合并评估"，本轮只给了 8/10，未显式声明 PR 整体评估结论（如"增量质量 8/10，PR 整体因 3 个未解决 minor 暂不建议合并"）。
4. **"不在 diff 范围内"不等于"不需要关注"**：两个前序 minor 都因"不在本轮 diff 中"而维持 suggestion，但本轮修改了同文件的相邻区域（test 文件 314 行起新增，问题在 283 行），这创造了"顺带修复"的零成本窗口，审查应更强烈地建议利用这个窗口。

### 5. 增量审查反思

**前序问题解决：部分有效**
- 鉴权修复质量好，逻辑清晰，是本轮最有价值的改进。
- 测试声明和硬编码中文连续两轮未修复，形成了"审查疲劳"模式——每轮都标记，每轮都有合理借口（不在 diff 中），但问题实质上没有向解决方向移动。需要打破这个循环。

**新增风险：中等**
- `ban_member` 仓库隐藏引入的状态管理复杂度被低估：banned → unbanned 后，仓库的 `is_displayed` 不会自动恢复，unban 流程是否处理了这个？diff 中未体现，审查未追问。
- stale repo 清理的单向性与 rename-back 场景存在潜在冲突，虽然 `repo_id` 优先查找缓解了大部分情况，但 `is_displayed=False` 不会被自动翻转。

**覆盖度下降：可控但需警惕**
- 未重新验证的模块（加密服务、OAuth、调度器 worker）本轮确实不涉及，声明充分。但遗漏了"service 层变更对 worker 的隐式影响"这一交叉维度——这不属于"重新验证已审模块"，而属于"验证变更的下游影响"，是增量审查的本职范围。
