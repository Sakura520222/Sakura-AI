## 2. 发现的模式  

### 代码模式  

| 观察点 | 具体表现 | 潜在风险/建议 |
|--------|----------|----------------|
| **Mock 与实现 API 不对齐** | `os.chown/chmod` → `os.fchown/fchmod` | 易导致非 root 环境下隐藏权限错误。建议在测试库层统一提供 **“POSIX descriptor mock”**，并在 CI 中强制使用。 |
| **跨平台分支写死** | `if sys.platform.startswith("linux"):` 中硬编码路径 | 难以维护，建议抽象为 **平台适配层**（`platform_utils.py`），统一入口。 |
| **大量文件改动集中在单次提交** | 单个 commit 改动 20+ 文件、+22k 行 | 代码审查效率下降，易遗漏细节。推荐 **拆分为功能/模块粒度的多个 PR**。 |
| **硬编码 UID/GID** | `65532:65532` 直接写在代码/Dockerfile | 若后续需要变更，需要同步多处。建议抽取为 **配置常量**，并在 `config.py` 中统一管理。 |
| **异常捕获宽泛** | `except Exception:` 在 `sandbox_client.py` 中出现 | 容易掩盖真实错误，建议捕获具体异常并记录上下文。 |
| **文档 → 代码不对称** | 文档中描述 “sandboxd 只能访问 Docker socket”，但代码里缺少显式的 `socket_path` 检查 | 需要 **文档‑代码双向验证**，防止文档误导。 |

### 架构观察  

| 特点 | 说明 |
|------|------|
| **服务拆分明确** | `backend/services/agent_team/*` 与 `sandboxer/*` 形成 **清晰的边界**，通过 HTTP‑over‑UDS 进行交互，符合最小特权原则。 |
| **依赖图高度集中** | `backend/core/config.py` 为多模块的根配置点，几乎所有服务层都直接引用，形成 **单点故障**。若配置变更未同步到所有使用方，容易产生 `KeyError`。 |
| **CI 工作流耦合度提升** | 多个 workflow 相互依赖（`gitflow-sync`, `sandbox-publish`, `sandbox-quality`），但 **权限声明未统一**，可能导致某些 job 在分支保护下被阻断。 |
| **网络策略模块新加入** | `network_policy.py` 与 `sandbox_client` 形成 **双向依赖**（client 读取策略、策略依赖 client 状态），需要注意循环依赖和初始化顺序。 |
| **跨语言/跨容器交互** | `sandboxer` 包含 CLI (`__main__.py`) 与 Docker‑runtime (`docker_runtime.py`)，但 **入口点文档不完整**，导致使用者可能误用非 sandbox 入口。 |

## 3. 规范完善建议  

### ① 新增/修改审查规则  

| 规则 | 目的 | 适用范围 |
|------|------|----------|
| **CI 红灯阻断规则** | 任意 **GitHub Actions** 失败的检查必须标记为 `error`，且在 PR 合并前必须提供 **全绿 run 链接**。 | 所有 PR，尤其涉及构建/安全改动的 PR。 |
| **POSIX 描述符统一 Mock** | 对 `os.fchown/fchmod`、`os.fchmodat` 等低层 API 的 mock 必须与生产实现保持 **一一对应**。 | 单元测试、fixture 编写。 |
| **配置项消费点追踪** | 新增或删除的配置键必须在 **全库搜索**（包括动态字典、翻译文件）后确认无遗漏引用。 | `backend/core/config.py` 及任何 `*.yaml/json` 配置文件。 |
| **异常捕获粒度** | 禁止在生产代码中出现 `except Exception:`，必须捕获 **具体异常类** 并给出 **错误标签注释**（`# USER_INPUT_ERROR` / `# INTERNAL_ERROR`）。 | 所有 `backend/services/*`、`sandboxer/*`。 |
| **跨平台分支抽象** | 所有平台相关判定应封装为 **平台适配层**（如 `platform_utils.py`），避免在业务代码中出现硬编码 `if sys.platform == "win32"`。 | 新增的 OS‑sandbox 代码路径。 |
| **文档‑代码同步检查** | 文档中提到的安全模型、环境变量、网络策略必须在代码中 **有对应的实现或校验**，否则审查标记为 `error`。 | `docs/**` 与 `backend/**`、`sandboxer/**`。 |
| **增量审查全库引用** | 对 **配置键删除**、**API 接口变更**、**异常类新增** 必须执行 **全仓库引用搜索**，确保无遗漏使用。 | 本次 PR 中的 `network_policy.py`、`sandbox_client.py`、`backend/core/config.py` 变更。 |

### ② 项目特有的规范要点  

| 要点 | 说明 |
|------|------|
| **Sandbox 镜像标签必须固定** | Docker 镜像引用应使用 **`<repo>:<major.minor.patch>`**，禁止 `latest` 或 `dev`。 |
| **UDS 权限声明** | 所有通过 Unix Domain Socket 交互的服务必须在 `permissions` 中声明 `read-all` 或 `write-all`，并在 workflow 中显式 **`permissions: write-all`**。 |
| **网络策略 JSON Schema** | `network_policy.py` 输出的策略文件应遵循 **JSON Schema**，CI 中加入 schema 校验步骤。 |
| **双向安全审计日志** | 对每一次 sandbox 创建/销毁、权限检查、标签校验都应记录 **结构化审计日志**（JSON），并在 `sandboxer` 中提供统一的日志输出函数。 |
| **跨语言部署文档** | 由于本次引入了 `sandboxd`、`sandboxer` 两个容器，部署文档必须明确 **容器编排顺序** 与 **健康检查**，并在 CI 中加入 **`docker compose config --quiet`** 校验。 |

## 4. 经验教训  

1. **CI 失败即阻断**  
   - 本次 PR 中外部检查仍是红灯，却已在审查中给出 `minor` 级别建议，导致决策与项目规则不一致。以后必须把 **CI 失败** 直接映射为 **阻断错误**，并在审查报告中强制要求提供复跑证据。  

2. **增量审查需配合全局搜索**  
   - 只看增量提交容易遗漏 **跨文件/跨模块的连锁影响**（如 `config.py` 中新增字段被其他模块引用）。在每次增量审查后，务必执行 **全库引用搜索**，尤其针对配置键、异常类、公共 API。  

3. **Mock 与生产代码同步**  
   - 第一次审查发现 `os.chown/chmod` 与 `os.fchown/fchmod` 不匹配，说明测试团队对底层系统调用的抽象不统一。建议在项目级别提供 **统一的系统调用 wrapper**，所有代码和测试统一使用该 wrapper，避免类似不一致。  

4. **文档与实现必须双向验证**  
   - 本 PR 更新了大量安全模型文档，但审查未检查文档中声明的安全约束是否在代码里实现（如 “Web 容器永不接触 Docker socket”）。以后审查时应把 **文档‑代码对应检查** 设为必检项。  

5. **大幅度单次提交的风险**  
   - 本次 PR 包含 30+ 文件、22k 行改动，审查人员难以在有限时间内完成深度审查。建议 **拆分 PR**，每次只改动一个子系统（如 sandboxd、network_policy、CI workflow），并在合并前进行 **集成回归测试**。  

6. **异常处理统一标签**  
   - 项目已有 “错误文案透传” 规范，但实际代码中缺少对应标签。审查时应检查 **每个 except 块是否有 `# USER_INPUT_ERROR` 或 `# INTERNAL_ERROR` 注释**，并在 CI 中加入 lint 检查。

### 小结  

本次审查在 **功能层面**（mock、CI、测试）表现出色，成功定位并修复了关键阻断点。但在 **安全/异常、配置、文档同步** 等全局维度仍有不足，尤其是对 **新增 sandbox 子系统** 的深度安全审查不够。建议在后续审查中：

1. 将 **CI 红灯** 直接标记为阻断错误并强制提供复跑证据。  
2. 对所有 **新增/删除配置项**、**异常捕获** 进行 **全库引用/标签检查**。  
3. 引入 **统一系统调用 wrapper** 与 **平台适配层**，降低跨平台差异导致的隐蔽错误。  
4. 将大规模变更拆分为 **功能粒度的多个 PR**，并在每个 PR 中加入 **文档‑代码双向验证**。

通过上述改进，可进一步提升审查的覆盖度、准确度与整体可靠性。祝后续 CI 复跑顺利，PR 能顺利合入主线。
