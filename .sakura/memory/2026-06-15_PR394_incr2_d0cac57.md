## 深度反思

### 1. 审查质量评估

**覆盖度**：合格但存在盲区。审查准确验证了历史 major 问题（`_handle_label_checkbox_toggle_inner` 遗漏 `unknown` 处理）的修复，并发现了新的 minor 问题（处理方式不一致）。但未追问一个关键问题：其他函数对 `unknown` 的处理方式是什么？如果它们返回 403 或抛异常，那这种不一致到底是"遗漏"还是"有意设计"？评论给出了现象但缺少对根因的判断，导致可操作性打折。

**准确度**：minor 标记合理。不一致本身不构成阻断，但确实是维护隐患。approve 决策与无 major 问题的结论一致，符合规范。

**完整性**：对增量意图理解到位——修复遗漏分支。但对 PR 整体完成度的评估偏被动，仅声明"历史问题未覆盖"，未主动判断这些未覆盖问题是否构成 PR 合并的阻断条件。

### 2. 发现的模式

**代码模式**：典型的"引入集中处理函数但未完成全量迁移"模式。`_permission_check_unavailable_response` 作为辅助函数被创建，但调用方各自为政——有的调用它，有的自行处理。这种半迁移状态是技术债的高发区。

**架构观察**：权限校验是一个分布式判断逻辑，分散在多个 webhook handler 中，没有统一的中间件或装饰器层。这导致每次新增权限状态（如 `unknown`）都需要逐一排查所有 handler，容易遗漏。本次 PR 的两轮审查恰好印证了这一点。

### 3. 规范完善建议

建议新增规则：

> **辅助函数迁移完整性校验**：当 PR 新增辅助/公共函数以统一某类处理逻辑时，必须列出所有应使用该函数的调用点，并逐项说明已迁移或未迁移的原因。未完成迁移的调用点至少标 minor。

这条规则可以直接捕获本次审查中发现的 minor 问题，并将其从事后发现提升为事前检查项。

### 4. 经验教训

- **新状态引入 = 全量路径扫描**：`"unknown"` 作为新的权限枚举值，其影响范围不限于"新增代码"，而是所有 `permission` 判断分支。首轮审查遗漏 `_handle_label_checkbox_toggle_inner` 就是因未做全量扫描。未来遇到枚举值扩展，应强制执行全仓 `grep` 级验证。
- **不一致评论需给出方向**：指出"处理方式不一致"时，应明确建议"应统一为 X 方式"或"需补充注释说明差异原因"，否则作者可能不知如何处理。
- **503 语义需谨慎**：503 表示"服务不可用，可重试"。如果其他函数对 `unknown` 返回 403（表示"禁止访问"），语义上差异很大——一个是临时故障，一个是永久拒绝。这种不一致可能影响客户端重试策略，值得在评论中点明。

### 5. 增量审查反思

**问题解决**：新增提交完整修复了历史 major 问题，包括代码逻辑（返回 503）和测试覆盖（+48 行测试），修复质量可接受。

**新风险**：引入了一个轻微的架构不一致风险——不同 handler 对同一异常状态的反应不同。这不阻断合并，但会增加后续维护者的认知负担。

**覆盖度下降**：本轮审查严格聚焦于增量 diff，对"其他函数如何处理 `unknown`"的判断仅基于历史记忆而非重新验证。根据项目记忆中"核心问题必须在当前 diff 中重新验证修复证据"的原则，这里存在轻微的宽松——虽然不是核心问题，但既然提到了不一致，就应给出具体代码位置作为证据。
