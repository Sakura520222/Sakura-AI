## 2. 发现的模式  

### 代码模式  
1. **依赖同步**：几乎所有依赖的声明都在 `pyproject.toml` 与 `requirements.txt` 中保持逐行镜像，配合 `test_pyproject_dependencies_mirror_requirements_txt` 自动校验。  
2. **增量反思归档**：每一次增量 PR 都会在 `.sakura/memory/` 下生成对应的 Markdown 记忆文件，形成“审查即记忆”的闭环。  
3. **频繁 Merge from `main`**：在增量 PR 中多次出现 `Merge remote-tracking branch 'origin/main' into develop`，说明分支同步频繁，可能导致冲突隐蔽。  

### 架构观察  
- **单体根项目 + 多子项目**：根目录有 `pyproject.toml`、`requirements.txt`、`uv.lock`，而 `sandboxer/` 与 `updater/` 各自维护独立的 `pyproject.toml`。根项目的依赖约束提升后，子项目未同步，形成潜在的 **版本漂移**。  
- **依赖锁文件单点**：项目仅使用根目录的 `uv.lock`，子项目不生成独立锁文件，导致子项目的依赖漂移难以自动检测。  
- **反思驱动的知识库**：`.sakura/memory/` 目录被当作内部知识库，所有 PR 都会写入，形成可追溯的经验沉淀，但目前缺少统一的元数据（如关联 PR、作者、风险等级），不便于后续检索。

## 4. 经验教训  

1. **锁文件的“漂移”是阻断级别**  
   - 即使只是依赖下限提升，锁文件若未重新生成，会在 CI `uv sync --locked` 时直接报错。审查时应把这类问题视为 **阻断**，而不是 **minor**。  
2. **子项目的依赖版本必须被显式审查**  
   - 单独的 `pyproject.toml` 容易被忽视，导致根项目与子项目之间出现不兼容的依赖版本。审查时要把子项目纳入依赖一致性检查的范围。  
3. **反思文档虽好，但需结构化**  
   - 目前每篇 Markdown 都是自由书写，缺少统一标签和元信息，检索成本高。结构化后可以直接在审查工具中关联到对应 PR。  
4. **增量审查不能放松**  
   - 只看增量提交会导致对历史未解决问题（如锁文件漂移）产生盲区。审查时需要回溯最近几轮的 “未闭环” 项，确保增量变更真正解决了旧问题。  
5. **兼容性验证要留痕**  
   - 对 `pydantic`、`watchfiles` 等大库的升级，审查中只写了“未命中破坏性改动点”。最好附带 **搜索命令**（如 `grep -R "pydantic." src/`）或 **CI 兼容性测试** 链接，形成可验证的证据。
