## 2. 发现的模式

**代码模式**：
- **防御性冗余编程**：同一验证逻辑在多个方法中重复实现（`_normalize_review_result_for_diff` 和 `_check_cancelled`）。这是一种常见的健壮性保障手段，但也增加了维护成本。
- **增量式重构**：项目正处于从 JSON 解析到标签化协议的迁移过程中，代码变更呈现明显的阶段性特征（逐步替换、逐步测试）。

**架构观察**：
- **Worker 与服务分离**：`review_worker.py` 作为工作流编排层，`prompt_builder.py` 作为业务逻辑层，职责划分清晰。
- **测试驱动开发**：新增功能均伴随测试用例，测试覆盖意识较强，但测试质量（如 mock 真实性）有待深入评估。
- **审查历史累积**：项目已有 415 次反思记录，形成了丰富的审查规范库，但规范应用的一致性（如历史问题跟踪）需要加强。

## 3. 规范完善建议

**新增审查规则建议**：
1. **防御性冗余代码审查要点**：
   > 当同一验证逻辑出现在多个位置时，必须评估：(1) 是否应提取为公共函数；(2) 重复实现是否在长期维护中可能产生不一致；(3) 性能影响是否可接受。

2. **历史问题长期未修复升级机制**：
   > 对于跨越 3 轮及以上审查仍未修复的建议级问题，应在审查报告中明确标注为“技术债”，并建议创建 Issue 跟踪，而不仅仅是提醒。

3. **防御性代码的测试覆盖验证**：
   > 新增防御性过滤/验证逻辑时，必须测试其“被过滤/验证对象为空”的边界情况。

**项目特有规范要点**：
- **增量审查的“完整性声明”**：在 approve 决策时，若存在未覆盖的历史问题，必须声明：“本次增量审查未验证历史问题 [问题描述]，但基于当前 diff 未发现新的阻断风险。”
- **性能影响预评估**：新增逐条验证逻辑时，应简要说明预期数据规模及性能影响评估。

## 4. 经验教训

**审查要点**：
1. **高分 PR 的隐性问题**：9/10 的评分不应掩盖长期未修复的技术债。审查者需平衡“当前变更质量”与“代码库整体健康度”的评估。
2. **防御性代码的双面性**：提高健壮性的同时，可能引入复杂性和性能开销。审查时需评估“收益 vs 成本”。
3. **增量审查的“向前看”**：不仅验证当前变更，还需评估其对后续维护的影响（如重复逻辑可能导致未来修改遗漏）。

**技术审查经验**：
- **验证逻辑一致性审查**：当多个方法执行相似验证时，应检查：
  1. 验证规则是否一致（如“有效评论”的定义是否相同）。
  2. 错误处理策略是否一致（过滤后是否统一标记为 issues）。
  3. 是否存在优化机会（如共享验证函数）。
- **测试有效性深度评估**：测试“能通过”只是基础，还需验证测试是否真正覆盖了生产环境的关键场景（如大数据量、复杂结构）。

## 5. 增量审查反思

**历史问题解决情况**：
- ❌ `int()` 冗余调用未修复：本轮未触及，但审查者正确识别并保留了历史状态。
- ✅ 新增提交增强了健壮性：评论过滤逻辑和提示词上下文改进符合 PR 目标。

**新风险识别**：
1. **性能风险**：`_normalize_review_result_for_diff` 逐条验证可能在处理大规模 review 结果时产生延迟。
2. **逻辑一致性风险**：重复验证可能在未来修改时遗漏其中一个位置，导致行为不一致。
3. **过滤策略风险**：过滤逻辑可能过于严格，导致有效评论被误过滤（需更多边界测试验证）。

**审查覆盖度反思**：
- **覆盖度下降的体现**：
  1. 未评估新增方法的错误处理路径（如验证过程中的异常如何传播）。
  2. 未审查新方法与现有工作流的集成点（如 `_make_and_submit_decision` 调用前的完整数据流）。
  3. 对测试用例的 mock 设计审查不足（是否模拟了生产环境的真实 diff 结构）。
- **改进建议**：增量审查应增加“集成点检查”清单，确保新增逻辑与现有流程无缝衔接。
