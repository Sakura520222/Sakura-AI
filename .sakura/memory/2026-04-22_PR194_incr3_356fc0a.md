## 2. 发现的模式

### 代码模式
- **渐进式补洞**：本次修复了路径遍历和 ref 忽略，但输入校验始终"差一步"——修了 path 漏了 ref
- **静默降级偏好**：多处 fallback 无日志，与项目规范「入口静默失败升级为 minor」持续冲突

### 架构观察
- **适配器契约残缺**：`LocalRepoAdapter` 作为 `Repository` 替代品，但 `search_files_tool` 仍假设 GitHub 特有属性（`_requester`），说明适配器边界未显式定义
- **双数据源风险持续**：PyGithub 主路径 + LocalRepo 回退路径的行为差异（如 ref 失败时静默切换）是数据不一致的隐患

## 3. 规范完善建议

### 新增规则
1. **输出前自检机制**：若问题描述中包含"虽然有...但..."的让步句式，必须重新评估严重程度，让步内容若否定了核心风险则必须降级
2. **分区与标签解耦**：禁止"建议（可选）"分区出现 major/critical 标签，如需标记为 major 则必须放入对应严重程度分区
3. **变更文件零遗漏**：quick 策略下，对变更文件的覆盖度应有硬性校验——输出前对照文件列表逐项确认

### 修正现有规则
- **增量审查边界**需细化：同一文件中，仅对 **新增/修改的代码行** 输出完整意见；未修改的历史代码如需提及，仅允许在"历史遗留阻断"分区中简述，禁止输出完整建议代码块

## 4. 经验教训

1. **try/except 不等于安全**：`_search_via_api` 的容错机制让审查者产生了"有保护所以可以标critical"的矛盾心理——正确做法是：有容错 = 运行时不崩溃 = 不可能是 critical（除非有资源耗尽等次生风险）

2. **git 命令的安全边界**：`git show` 确实有沙箱限制，不能与直接文件系统操作等同看待。对 git 命令的输入校验应基于实际可利用的攻击面，而非套用通用注入检测模板

3. **问题状态追踪表的价值**：本次审查中，追踪表清晰展示了"3个核心问题已修复、2个未修复、1个部分修复"，这比纯文字描述有效得多，应作为多轮审查的标配
