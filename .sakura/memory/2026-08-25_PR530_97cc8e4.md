**三、规范完善建议**

1. **新增/修改审查规则**  
   - **规则 1：配置变更审查**  
     - 对所有新增或修改的配置项（如 `REASONING_CONTENT_ENABLED`）必须检查：<br>① 是否在 `README/部署文档` 中说明默认值与作用；<br>② 是否在代码中提供 **类型/范围校验**（如 `assert isinstance(value, bool)`）。  
   - **规则 2：异常捕获粒度**  
     - 禁止在业务代码中使用裸 `except Exception`，必须捕获具体异常（如 `KeyError`, `ImportError`），并在注释中标明处理意图。  
   - **规则 3：能力声明一致性**  
     - 当功能依赖 **模型能力声明**（如 reasoning_content）时，审查必须验证 **所有调用方**（包括异步任务、CLI、Webhook）均使用同一判断函数，防止出现“半边支持”情形。  
   - **规则 4：回归行为验证**  
     - 对涉及 **功能开关** 的改动，必须提供 **两套测试**：<br>① 开关开启时的正向路径；<br>② 开关关闭时的负向路径（保持旧行为或安全降级）。  

2. **项目特有的规范要点**  
   - **模型注册文件（builtin_models.json）** 必须在 **CI** 中加入 **JSON Schema 校验**，防止手动编辑导致键名错误。  
   - **单元测试命名规范**：新增的测试文件命名应统一以 `test_` 开头，且每个模型的子案例使用 `@pytest.mark.parametrize`，便于覆盖矩阵化。  
   - **配置默认值声明**：所有 `config` 模块的公开函数应在 docstring 中明确标出 **默认值来源**（环境变量 / .env / 硬编码），并在代码里使用 `os.getenv(..., default)` 统一读取。  

**四、经验教训**

| 教训 | 具体表现 | 对策 |
|------|----------|------|
| **1. “空字符串”导致功能沉默** | 之前 `is_model_supports_reasoning_content('')` 返回 `False`，进而丢弃 `reasoning_content`。 | - 在能力判断函数中加入 **非空检查**，并在异常路径记录日志。 |
| **2. 动态模型名称获取的可靠性** | `context_model` 取值依赖 API 响应的 `metadata.model`，若该字段缺失或命名变化，功能会失效。 | - 为 `metadata` 加入 **结构化校验**（pydantic/attrs），并在缺失时回退到 `fallback_model`。 |
| **3. 测试覆盖不等于风险消除** | 单元测试覆盖了多模型组合，但未模拟 **网络异常、模型服务超时** 场景。 | - 增加 **异常路径测试**（mock `requests.exceptions.Timeout`），确保在异常时 `reasoning_content` 仍保持一致或安全降级。 |
| **4. 配置开关的文档同步** | 新增的 `REASONING_CONTENT_ENABLED` 没有在项目文档里出现，运维可能不知情。 | - 在 PR 中强制要求 **文档改动**（README、部署脚本）同步更新；审查时检查对应文档是否已修改。 |
| **5. 过宽异常捕获的隐蔽风险** | `reviewer.py` 使用 `except Exception as e:` 捕获所有错误，可能掩盖模型加载失败导致的业务中断。 | - 将异常捕获细化为 `except (KeyError, ImportError) as e:`，并在捕获后 **重新抛出或记录**，防止误判为正常流程。 |
