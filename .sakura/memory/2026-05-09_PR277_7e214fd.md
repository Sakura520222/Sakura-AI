## 4. 经验教训

### 未来审查要点
- **多 flag 组合逻辑**：当存在两个及以上 flag 通过 `or` / `and` 控制同一行为时，需审查是否存在语义重叠、用户预期是否清晰。
- **开发辅助脚本的安全性**：尤其注意脚本生成的配置文件是否可能被意外提交（`.gitignore` + 启动时检测）。
- **测试的对称性**：开发模式测试了 localhost 存在，生产模式必须测试 localhost 不存在 —— 这种“正向+反向”测试对容易被遗漏。
- **类型注解的一致性**：新增函数（尤其是公共函数）必须包含类型注解，这是低成本的维护增益。

### 技术观察
- **`os.getenv` 在请求链中被多次调用**：本项目评估为可忽略，因为配置读取不在高频循环内。但如果未来有每请求读取配置的需求，应引入 `lru_cache` 或配置服务。
- **开发模式 flag 的传递方式**：当前通过环境变量 + `Settings` 类读取，设计清晰。但若未来增加更多开发专用 flag，考虑统一使用 `SAKURA_DEV_*` 前缀。
