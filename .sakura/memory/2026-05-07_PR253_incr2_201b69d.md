### 二、发现的模式

**代码模式**
1. **渐进式债务偿还**：重构时只提取重复逻辑，不改变外围事务模式（受限于外部调用链），这是务实的安全做法
2. **幂等性标注习惯形成**：docstring 中新增 `幂等: 是` 和 `非原子操作`，符合项目规范
3. **日志-返回对偶模式**：`_safe_db_delete` 在异常时 `logger.warning` 并返回0，调用方通过 `v == 0` 推断失败 — 但这种隐式约定容易混淆“真失败”和“无记录”

**架构观察**
- 事务管理分散：session 生命周期在 webhook 层（async with），commit 却在 service 层内部，导致双重提交风险长期未解
- 静态方法用于 DB 操作：`_safe_db_delete` 标记为 `@staticmethod`，说明该 service 类更接近于“函数命名空间”而非真正的领域对象

### 四、经验教训

1. **假阳性的累积成本**：`v == 0` 导致的 warning 误报，每次幂等重试都会触发，最终会让真实失败淹没在噪音中。未来遇到类似“用特殊值表示两种不同语义”的模式时应提前打 major 而非 suggestion。

2. **重构保留隐式依赖**：`zip(db_filters, result_keys)` 依赖顺序对应，这是隐含的脆弱性。虽然本轮未改，但应在审查中标记 `💡 未来风险提示`，建议在 PR 评论中提醒作者增加断言检查长度。

3. **事务双重提交的债务接受判断**：本轮评分 8/10 且 approve 合理，因为：
   - 历史问题中3个已修复，重构质量高
   - 双重提交问题需要修改外部调用方（webhook.py 的 session 管理），超出本重构范围
   - 文档已标注 `非原子操作`，给了调用方知情权

4. **增量审查的盲区**：审查员未检查 `_safe_db_delete` 的异常消息是否包含敏感信息（如 `str(e)` 可能打印 SQLAlchemy 的完整错误，内含表名、字段、部分 SQL）。这是增量审查只看“新增行数”时的典型遗漏 — 新增方法体内部调用了 `logger.warning(str(e))`，应扫描该模式。
