### 4. 经验教训

*   **版本兼容性的“木桶效应”**：
    *   在脚本中引入了针对旧版本的回退逻辑（`compose_pull_with_native_progress` 的 fallback），容易让人产生“已处理兼容性”的错觉。教训是：**兼容性检查必须覆盖所有新增的外部调用**，而不仅仅是显式处理过的那部分。`up -d --pull never` 虽然不是 pull 命令，但同样是 Compose 调用，且引入了新参数，必须纳入同一兼容性策略考量。
*   **环境变量驱动的逻辑分支是隐蔽的 Bug 源**：
    *   Dev 模式通常通过环境变量控制，容易被主逻辑路径忽略（如 `stop_verified_updater` 中的 `elif` 链条漏掉了 Dev 场景）。审查此类代码时，应**强制演练**所有环境变量组合下的执行流。
*   **文档即代码的验证深度**：
    *   当 PR 描述提到“更新部署文档以提及...”时，审查不能止步于“文档更新了”。必须验证文档中的**行为描述**（如“原生动态进度渲染器”）在代码中是否有对应的实参支撑（`--progress tty`），避免文档承诺了代码未提供的能力。
*   **评分与决策的一致性**：
    *   8/10 的评分通常意味着“优秀”，但本次留下了兼容性回归和 CI 失败的问题。这提示在未来的审查中，若发现阻断性或严重的技术债，应更果断地调低评分或严格标记 `Request Changes`，以避免“高分通过”带来的虚假安全感。
