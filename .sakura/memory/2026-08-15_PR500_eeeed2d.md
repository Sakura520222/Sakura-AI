    *   审查者准确识别出 PR 的核心意图是“恢复开发频道更新”和“加固更新链路”，并据此验证了修改是否彻底（例如指出虽然修了 digest 校验，但如果路径解析错误，dev 模式仍会在运行期失败，这与加固链路的目标相悖）。

### 2. 发现的模式

*   **代码模式：Fail-Closed 防御性编程**
    *   无论是 `_select_registry_digest` 对非法 digest 的拒绝，还是 `daemon.py` 对孤儿 socket 的拒绝拉起，都体现了“宁愿不可用也不可用错”的强防御模式。
*   **架构观察：状态外置与进程隔离**
    *   前端倾向于将状态（如 Job ID）持久化到 `sessionStorage` 以应对刷新，但随之引入了“状态恢复时的数据完整性”问题（仅有 ID 无验证信息）。
    *   后端守护进程（`daemon.py`）正在走向严格的隔离（`cwd=/`, abspath），这说明项目正在极力规避宿主机环境（如当前工作目录变更、文件被删除）对后台服务的干扰。
*   **错误处理：结构化优先**
    *   明显的趋势是从通用的 HTTP 500/502 错误转向具体的、结构化的检查结果（如 `current_image_identity_valid`），这有助于前端做出更精准的用户反馈。

### 3. 规范完善建议

*   **新增规则：前端恢复状态的最小可用性验证**
    *   针对前端轮询机制，建议增加规范要求：**若利用持久化存储恢复异步任务状态，必须同时存储用于验证任务最终结果的“核心断言数据”（如目标版本、目标 Hash），而非仅存储任务 ID。** 防止因服务端不可用导致无法验证任务结果时，误判任务失败。
*   **新增规则：脚本入口的路径一致性契约**
    *   涉及调用子进程的 Shell 脚本，若采用 `BASH_SOURCE` 锚定项目根目录，**所有**传递给子进程的文件参数（包括配置文件、Compose 文件）必须统一基于该根目录解析。禁止混合使用“绝对路径（状态）”和“相对路径（配置）”。
*   **新增规则：外部依赖行为的假设验证**
    *   对于依赖外部运行时（如 Docker）元数据（`RepoTags`）的逻辑，必须在测试用例中覆盖**“最小元数据集”**场景（如 Docker 清理 tag 后仅保留 digest 的情况），不得假设运行时总是保留完整的原始信息。

### 4. 经验教训

*   **Docker 元数据的不可靠性**：
    *   Docker 的 `RepoTags` 是可变的且可能被垃圾回收，核心身份识别应始终依赖 `RepoDigests`（内容寻址）。审查中确认的根因修复再次印证了这一点：不要依赖 UI 友好但不可靠的 Tag 来做核心逻辑判断。
*   **守护进程的 CWD 陷阱**：
    *   长期运行的后台进程（Daemon）如果继承启动时的 CWD，在目录被删除或移动时会遭遇莫名的文件解析错误。将 Daemon 的 CWD 强制设为 `/` 是一个极其稳健的最佳实践。
*   **“瞬时错误”处理的复杂性**：
    *   在前端轮询中，区分“服务端瞬时故障（5xx）”和“任务本身失败”需要额外的健康检查机制。单纯依赖服务端接口的恢复是不够的，必须具备独立于主 API 链路的最终状态验证手段（如直接对新容器进行 `/health` 检查）。
*   **路径解析的隐形杀手**：
    *   在混合使用 Python（后端）和 Bash（脚本）的项目中，`os.path.abspath` 的行为依赖于进程启动时的 CWD。当脚本通过 `cd` 或锚定路径改变了执行上下文，若参数未同步转为绝对路径，会导致极其隐蔽的“文件未找到”或“运行时配置错误”。这类错误往往在非标准调用路径（如从非根目录启动脚本）下才暴露。
