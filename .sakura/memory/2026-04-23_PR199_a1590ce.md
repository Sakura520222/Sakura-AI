## 深度反思报告

### 1. 审查质量评估
- **覆盖度（优）**：审查没有局限于 diff 本身，而是主动交叉验证了 `review_worker.py` 和 `issue_analyzer.py`，确认了防御代码（索引 `messages[1]`、`.get()` 默认值、非空检查）的模式一致性。对 `scan_worker.py` 的 `try/except` 边界审计非常完整。
- **准确度（优）**：严重程度判定精准。将“AI 可能盲目尝试不可用工具”判定为 `suggestion` 而非 `major`，符合“三问法”（非实际 bug、非运行时错误、非安全风险），避免了过度拔高。
- **完整性（良）**：精准捕捉了变更的**隐性意图**（提示词分类不仅是重组，更是引入了状态不确定性），并指出了对应的处置逻辑缺失。
- **扣分项（评分锚定风险）**：给出 9/10 偏高。本次变更本质是“成熟模式的横向复制 + 提示词微调”，创新度和复杂度有限。根据记忆中“评分锚定风险”规则，此类高质量但无突破的变更 8/10 更为严谨，9 分容易拉高整体基线导致后续真正的高难度变更无处可升。

### 2. 发现的模式
- **代码模式（防御性记忆注入范式成型）**：`try(import) -> try(获取上下文) -> check(非空) -> inject(messages[1])` 已在三个 Worker 中稳定复用，这标志着该项目的一个核心跨切面逻辑已经固化。
- **架构观察（提示词与运行时的状态割裂）**：`scan_prompt_builder.py` 将工具分为“始终可用”与“按条件可用”，引入了**运行时状态**。但提示词是静态的，这种分类实际上是在提示词层面建立了一个“没有降级出口的状态机”。这是典型的 AI Agent 架构痛点：Prompt 描述理想态，Runtime 面对异常态。

### 3. 规范完善建议
- **新增规则：【提示词条件分支须含降级指引】**：在系统提示词中引入“按条件/可选/有时不可用”等状态描述时，必须同步审查是否提供了失败后的兜底策略（如跳过、重试、降级），否则应标记为 suggestion。
- **固化规则：【模式复制的审查焦点转移】**：当变更明确声明“遵循 XXX 模式”且交叉验证一致时，审查重心应从“验证模式正确性”转移到“验证模式适配性”（例如：`messages[1]` 在 scan_worker 中是否和 review_worker 一样肯定是 user message？审查者做对了这一步）。

### 4. 经验教训
- **审查 LLM 提示词要像审查状态机**：不能仅做文本通顺度审查，必须画状态转移图。本次发现的“按条件可用工具无失败指引”本质上就是状态机缺失了 Error State 的转移边。
- **“正确的静默吞错”需要底线声明**：`scan_worker.py:516` 的 `except ImportError` 是合理的降级，审查者准确指出了“不应中断扫描主流程”。这强化了一个认知：**在核心业务链路中，非核心依赖的静默降级是允许的，但必须在注释或日志中明确表达“此处的预期就是失败”**，否则未来维护者可能误将其当作 bug 修复。
- **diff 小但语境深**：本次总变更量仅 +45/-3 行，但牵涉到 Prompt Engineering 和 Worker 上下文注入两个核心域。印证了“小diff≠无执行流影响”，quick 策略在此类高内聚模块中依然产出了高质量的深度分析。
