## 2. 发现的模式

### 代码模式

本次变更体现出几个项目内常见模式：

1. **SQLAlchemy 条件过滤通过列表组装表达式**
   `scope_user` 被用于生成可选过滤条件，形如：

   ```python
   condition if scope_user is not None else None
   ```

   这种模式的关键风险是 `None` 与 falsy 值的语义区别。对于权限过滤、租户隔离、用户范围限制，必须避免用 `if value` 代替 `if value is not None`。

2. **服务层集中做 dashboard 聚合**
   `dashboard_stats_service.py` 承担跨模块统计职责，可能会聚合 Issue、Agent Team、Repo Scan 等多个业务表。  
   这种服务天然容易出现：
   - 权限过滤不一致；
   - 时间范围口径不一致；
   - fake session 测试与真实 SQLAlchemy 查询行为不一致；
   - 不同模块字段命名或状态枚举不一致。

3. **项目正在迁移 timezone-aware datetime**
   从 `datetime.utcnow()` 迁移到 `datetime.now(timezone.utc)` 是项目持续性技术债。后续审查中应注意 naive/aware 混用问题，而不是只机械检查替换是否完成。

### 架构观察

1. **Dashboard 是跨模块聚合层**
   Dashboard 统计依赖多个业务模块，因此它不是简单展示层，而是一个横向聚合入口。审查时应把它视作权限、数据口径和性能敏感模块。

2. **WebUI route 与 service 分层较清晰**
   本次涉及：
   - `backend/webui/routes/dashboard.py`
   - `backend/services/dashboard_stats_service.py`

   route 层负责请求入口和时间/参数处理，service 层负责统计查询。这个分层方向合理，但也要求审查时同时检查：
   - route 是否正确传递用户范围；
   - service 是否强制应用过滤；
   - 前端/模板是否对字段格式有假设。

3. **历史问题分布不均**
   Dashboard 相关问题逐步收敛，但 shell、agent team、worker 等模块仍有高风险遗留项。增量审查不能因为当前 dashboard diff 质量高，就暗示整个 PR/release 风险很低。

## 3. 规范完善建议

### 建议新增或强化的审查规则

1. **Release PR 描述与实际 diff 强制核对**
   如果 PR 描述是 release note、changelog 或包含多个历史 PR/Issue，但当前 diff 只覆盖少量文件，审查必须明确说明：

   - 当前审查是否只覆盖新增提交；
   - release note 中列出的内容是否已经在历史提交中审过；
   - 是否存在描述过期、夸大或未同步风险。

   建议规则：

   > Release/changelog 型 PR 中，若描述列出功能集合但当前增量 diff 未体现，应至少标记为 suggestion/minor，要求确认描述来源或说明本轮仅审查增量。

2. **权限过滤中禁止 truthiness 判断**
   对用户、租户、组织、仓库、项目范围等 scope 字段，建议形成项目规范：

   ```python
   if scope_user is not None:
       ...
   ```

   禁止：

   ```python
   if scope_user:
       ...
   ```

   原因是空字符串、0、空集合等值可能具有业务意义，不能被隐式跳过。

3. **timezone-aware datetime 替换需检查下游兼容**
   不能只检查 `utcnow()` 是否被替换，还要检查：
   - 是否与 naive datetime 混算；
   - DB 字段是否 timezone-aware；
   - JSON/template 输出是否稳定；
   - 测试 mock 是否同步。

4. **结构化评论生成规则需要收紧**
   本次“主要评论”把大量摘要内容转成 suggestion，这是明显噪声。建议规则：

   > 只有具体代码位置、明确问题、可执行建议才能生成 review comment。审查摘要、评分、历史状态表、无问题声明不得进入 comment 列表。

5. **Dashboard 统计类变更建议有轻量测试**
   对 dashboard metrics、趋势、统计口径、权限过滤，应至少考虑：
   - 字段存在；
   - 类型稳定；
   - 空数据降级；
   - 权限过滤；
   - 时间范围边界。

   无测试不一定阻断，但应作为低风险建议记录。

### 项目特有规范要点

- Dashboard service 中所有跨模块统计必须统一应用 `scope_user` / 当前用户过滤；
- 统计查询中的 `None` 表示“不限制”，空字符串不应等同于“不限制”；
- WebUI routes 下新增或修改 dashboard API 时，需要确认认证链路和数据敏感度；
- 时间展示、启动时间、运行时信息应优先使用 timezone-aware datetime 或项目统一时间工具；
- 统计/展示接口不应泄露跨用户、跨仓库或跨组织数据。

## 4. 经验教训

1. **小 diff 也可能是权限修复**
   本次 `scope_user` 的三处改动看似只是风格调整，但实际关系到数据隔离。对于权限、scope、tenant、user filter 相关代码，不应按普通 refactor 看待。

2. **`if value` 与 `if value is not None` 在安全语境下差异很大**
   在权限过滤中，truthiness 判断可能导致空字符串、0、空列表等边界值绕过过滤。未来看到类似字段名：
   - `user_id`
   - `scope_user`
   - `tenant_id`
   - `org_id`
   - `repo_id`
   - `owner`
   
   都应优先检查是否误用 truthiness。

3. **timezone API 迁移不是纯机械替换**
   naive datetime 到 aware datetime 是语义变化。虽然迁移方向正确，但审查时仍应检查下游契约，尤其是：
   - ORM 字段；
   - 序列化；
   - 测试断言；
   - 与旧值比较的地方。

4. **历史问题“已修复”需要边界清晰**
   本次说 dashboard 相关历史问题已修复是合理的，因为给出了具体 diff 位置。但对 shell、worker、agent team 等未触及问题，只能说“本轮未涉及/未验证”，不能暗示整体已解决。

5. **评论输出质量和代码判断同样重要**
   审查本身的代码判断较好，但结构化评论噪声较多。未来需要避免把审查报告正文拆成一堆 suggestion comment，这会降低 PR 作者的处理效率。

## 5. 增量审查反思

### 新增提交是否解决了之前审查提出的问题？

是，至少解决了 dashboard 相关的一个明确历史问题：

- 第2轮提出的 `scope_user` truthiness 与 `is not None` 风格不一致问题，本次在 `fetch_token_trend` 的多个模块 scope 条件中修复；

这些都是正向改进。

### 增量变更是否引入了新的风险？

风险较低，但不是完全没有：

1. **aware datetime 兼容性风险**
   `datetime.now(timezone.utc)` 返回 aware datetime，可能影响下游 naive datetime 比较或序列化。需要确认具体上下文。

2. **空字符串过滤的业务语义**
   `scope_user=""` 现在会被当作有效过滤值。安全角度通常更合理，因为不会绕过过滤；但业务上也要确认空字符串是否可能来自异常输入。如果可能，应在更上游做参数规范化或校验。

3. **模块级导入 `or_` 基本无风险**
   这是正常清理。除非该模块存在特殊导入循环，但 `sqlalchemy.or_` 不涉及项目内部依赖，风险很低。

### 审查覆盖度是否因只看增量部分而下降？

是，有一定下降，主要体现在：

- 没有验证 PR 描述中列出的 release 内容；
- 没有复核历史高风险文件，如 `shell_tool.py`、`pr_review_feedback.py`、`issue_worker.py`；
- 没有确认 dashboard 统计整体调用链和测试现状；
- 没有全仓扫描其他 `datetime.utcnow()` 的迁移状态，只是作为建议提及。

不过这符合“增量审查”的边界，只要报告明确声明“仅审查本次新增提交”即可。问题在于本次审查虽然有声明增量范围，但最终给出 9/10 和 approve 时，仍应更明确地区分：

> 本次新增提交质量高，可以 approve；但不代表 PR 描述中的所有 release 内容均已在本轮重新验证。

未来类似小型增量 PR，应保持当前对细节修复的敏感度，同时加强三点：  
**核对 PR 元信息、控制评论噪声、明确增量审查边界。**
