- **原子化封装 + 局部复用**：`_parse_positive_int_config` 仅在同一模块内复用，未提升到 utils，符合“先局部、后抽象”的谨慎重构模式。

## 4. 经验教训

### 值得未来关注的要點
- **消费方隐式上限的验证**：当配置值无业务上限时，审查应主动扫读消费方代码，确认是否存在物理上限（如 `asyncio.Semaphore(100)` 硬编码）。
- **日志缺失的累积风险**：配置解析函数广泛复用后，若某些路径无日志，将导致可观测性盲区。建议要求所有配置封装函数在非法输入时至少 debug 级别日志。
- **配置迁移的“对称性三件套”**：写入路径、缓存失效、**默认值对比**——本次缺了第三件。

### 对特定技术/模式的审查经验
- **`int(str(raw).strip())` 防御链**：`None` → `"None"` → `ValueError` → 被捕获 → 用户友好错误。但 `str(None).strip()` 得到 `"None"` 并非预期行为，更好的做法是 `if raw is None: raise ValueError`。审查未指出这一点，属于深度边界检查遗漏。
- **frozenset 常量与消费方一致性**：本次新增 `BASIC_CONFIG_KEYS` 包含新的 review 配置，审查确认了导入替换，但未检查 `get_all_db_config_keys` 的迭代逻辑是否与 `BASIC_CONFIG_KEYS` 语义对齐（应同时包含 core + basic，已做对）。
