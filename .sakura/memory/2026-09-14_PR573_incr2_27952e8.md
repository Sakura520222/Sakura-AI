## 2. 发现的模式  

### 代码模式  
1. **单一来源参数化**：`backend_cli_flags` 统一生成 CLI 参数，避免配置漂移。  
2. **原子文件写入 + fsync**：在生成 systemd unit 时使用 `mkstemp` → `os.replace` → `_fsync_directory`，体现对电源故障的防护意识。  
3. **层级权限校验**：`DaemonBackend._ensure_private_directory` 通过逐级 `lstat` 检查目录所有者与权限，防止 symlink 攻击。  
4. **开发/生产模式分支**：`SAKURA_UPDATER_DEV` 环境变量控制行为，保持 CI 与本地调试的分离。  

### 架构观察  
- **系统守护层与业务层解耦**：`systemd.py` 负责 service 单元生成，`daemon.py` 负责业务守护，二者通过 CLI 标志对齐。  
- **依赖管理多入口**：项目同时维护 `pyproject.toml`、`requirements.txt`、`uv.lock`（未在 PR 中出现但在规则中被要求），形成潜在的同步风险。  
- **文档驱动**：大量 `.sakura` 目录下的经验、规则、记忆文件，说明团队采用“审查+文档+反思”闭环流程。

## 3. 规范完善建议  

| 现有缺口 | 建议规则 | 预期收益 |

## 4. 经验教训  

1. **依赖升级不等于功能变更**：虽然 alembic 版本提升对业务代码几乎没有直接调用，但仍需要 **“是否真的需要”** 的业务层确认。  
2. **增量审查容易忽略全局约束**：本次 PR 大量新增文件，但唯一的全局风险点（alembic 依赖）在增量文件中未直接出现，导致审查遗漏。以后应在增量审查之外加入 **全局关键点清单** 检查。  
3. **原子写入与目录 fsync 是高可靠性系统的标配**：审查时对这些细节的肯定说明，建议将其提炼为项目内部的 *安全写入规范*，供新模块参考。  
4. **脚本安全分支（dev vs prod）**：使用环境变量区分行为的做法值得在项目规范中固化，防止以后出现 “在容器里误报 systemd 可用” 的情况。  
5. **文档与代码的双向追踪**：大量 `.sakura` 记忆文件虽有价值，但如果不与代码变更关联（如在 PR 描述中引用），审查人员可能忽视其中的潜在风险建议。建议在 PR 模板中加入 **“关联记忆/经验文件”** 字段。

## 5. 增量审查反思  

| 问题 | 现象 | 评估 |
|------|------|------|
| **之前提出的 alembic 依赖疑问是否得到解决？** | PR 中仅更新了版本号，未给出删除或保留的明确说明。 | **未闭环**，仍是潜在风险。后续需要作者在评论中说明或在后续 PR 中处理。 |
| **增量变更是否引入新风险？** | 新增 `systemd.py`、`start.sh` 大幅改动，已通过单元/集成测试覆盖，且审查指出了安全设计（PIDFile、权限检查），未发现明显回归风险。 | **风险已被有效缓解**，但仍建议在 CI 中跑一次完整的 systemd‑service 启动模拟（如 `systemd-run`）以验证真实环境行为。 |
| **审查覆盖度因只看增量而下降？** | 增量审查聚焦在新文件与改动的实现细节，导致对全局依赖使用情况（alembic）缺乏关注。 | **是**，需要在增量审查之外加入 **全局依赖检查** 步骤。 |

**结论**：本轮增量审查在实现细节层面做得非常细致，但在全局依赖治理上仍有盲区。后续审查流程应加入 **全局关键点（依赖、锁文件、文档）复核**，并确保所有 **reviewer‑suggestion** 能得到明确的处理结论（接受、拒绝或后续计划），以避免悬而未决的技术债务。
