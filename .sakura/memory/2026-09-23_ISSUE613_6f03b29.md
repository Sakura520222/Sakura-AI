## 6. 经验教训与后续关注点  

1. **配置权威来源必须明确**  
   - 在多模型、多业务场景下，**模型级配置**应始终是唯一的 **Source of Truth**。全局配置只能作为默认值，且在代码层面需要强制覆盖或警告。  
   - 建议在 `Settings` 中加入 **配置来源标记**（如 `source: "model"`），并在调用前进行校验。

2. **默认值设计要慎重**  
   - 将 `temperature` 默认改为 `None` 而非硬编码 `0.7`，可以让业务显式决定是否使用默认。类似的 **默认预算**、**默认模型** 也应采用 “显式声明或无默认” 的策略，以防隐式覆盖。

3. **错误分类与重试策略分离**  
   - `BAD_REQUEST`、`REFUSAL` 绝不应进入可重试集合，防止对非法请求的指数退避导致资源浪费。建议抽象为 **RetryPolicy**，并在每个错误类别上附带 **retryable** 标记，统一由底层统一判断。

4. **统一预算计算（EffectiveRequestPolicy）**  
   - 将 `maybe_compress` 与 `UnifiedRequest` 的预算计算合并，避免 **“预检预算 ≠ 实际发送预算”** 的不一致。实现时可提供 **单元测试** 对比 `effective_max_output_tokens` 前后是否保持一致。

5. **迁移与清理的分阶段策略**  
   - **阶段 1**：在代码中加入 **兼容层**（保留旧字段但抛警告），确保现有业务不立即失效。  
   - **阶段 2**：在 CI 中加入 **配置使用率检测**（未被引用的 Settings 字段报错），逐步淘汰旧字段。  
   - **阶段 3**：彻底删除旧字段并同步文档。

6. **测试覆盖与回归守卫**  
   - 对每个改动点（`call_with_retry`、`stream_with_retry`、`UnifiedRequest`、错误分类）都应新增 **正向 + 负向** 测试。  
   - 引入 **contract test**（协议层请求/响应对比）以及 **load test**（高并发下的重试行为）来确保改动不引入性能回退。

7. **文档同步**  
   - 所有配置字段的变更必须同步到 **README / developer guide**，并在 CI 中加入 **文档检查**（如 `mkdocs` 自动生成的 API 文档与代码保持一致）。

8. **跨模块影响评估**  
   - 统一请求参数的改动会波及 **star_aid_summary_service**, **history_context_service**, **issue_analyzer**, **scan_worker**, **reviewer** 等多个服务。建议在 PR 中提供 **影响矩阵**，列出每个服务受影响的具体文件与函数。
