## 2. 发现的模式

### 代码模式
- **配置访问模式**：频繁出现 `(value if value is not None else get_settings().xxx)`，说明项目缺少统一的配置解析抽象层。
- **延迟导入**：`_read_user_config_from_db` 中使用延迟导入但未注释，说明**延迟导入必须注释原因**这一规则多次被违反（项目记忆已记录）。
- **版本号多源硬编码**：历史遗留问题，虽已记录但仍未解决，说明“单一真实源”规范落地难。

### 架构观察
- **配置穿透链路**：`UserConfig → AppConfig → Settings` 降级链设计清晰，但实现中 `get_user_dynamic_config` 同时承担“读取用户配置”和“降级”职责，**单一职责原则**有待提升。
- **WebUI 直接操作数据库**：`settings.py` 中直接使用 SQLAlchemy ORM 查询，虽被认定为“轻量可接受”，但违反“路由层禁止直接操作数据库”规则，说明紧耦合已被容忍。

## 3. 规范完善建议

### 新增/修改审查规则

1. **新增规则**：**新增用户级配置项时，必须扫描所有调用 `get_user_dynamic_config` 或 `get_dynamic_config` 的热路径，评估性能影响**（标 major）。
   - 理由：本次 `output_language` 在评论格式化时调用，若 PR 有 100 条评论，会触发 100 次缓存查询（虽有 LRU，仍需评估）。

2. **修改规则**：**`init.sql` 缺失表定义** 降级为 **minor**（如果 `create_all` 已覆盖且非手动 SQL 部署为主）。
   - 理由：Docker 部署依赖 `init.sql` 但 `create_all` 能补建，实际不影响运行，不应阻断合并。

3. **新增规则**：**用户级配置接入点扫描**：新增用户配置项时，必须列出所有可能获取 `user_id` 的入口（webhook、定时任务、WebUI、API、bot），确保无遗漏（标 major）。

### 项目特有规范要点

- **配置服务抽象**：建议引入 `ConfigService` 类，统一封装 `get_effective_output_language(user_id)`，避免重复判断逻辑。
- **版本号单一真实源**：强制执行 `backend/__version__` + `pyproject.toml` 动态读取，其他位置通过导入获取。

## 4. 经验教训

### 值得关注的未来审查要点

1. **配置热更新的并发安全性**：当前使用进程级 `OrderedDict` + TTL，在 **多 worker + 内存共享** 场景下，不同 worker 缓存不一致问题未讨论。若未来引入 Redis 或分布式缓存，需更新审查规则。

2. **`user_id` 降级路径的日志缺失**：`get_user_dynamic_config` 在 `pr_info` 无 `user_id` 时静默降级，未记录 `warning` 日志。建议新增规则：**配置降级必须记录日志**（标 minor）。

3. **Foreign Key 缺失的长期影响**：`UserConfig.user_id` 无 FK，虽与 `AppConfig` 一致，但会导致孤儿记录。若未来引入用户删除功能，需额外清理。建议在 **PR 描述** 或 **设计文档** 中明确说明“Phase 1 暂不加 FK，Phase 2 会重构”。

4. **异步 session 异常处理**：项目记忆已强调 `async with session.begin()` 模式，但本次变更中没有显式使用该模式（`user_config.py` 中手动 `commit/rollback`），建议在“需特别关注的领域”中强化该模式。

## 总结

本次审查**质量较高**，覆盖了核心设计、调用方扫描、缓存策略、i18n 完整性等关键点，但存在**轻微过标**（将非阻断项标为 major）和**少数遗漏**（性能评估、非 webhook 入口）。项目记忆中的“延迟导入必须注释”“版本号单一源”等规则反复被违反，说明需要**自动化检测**（如 pre-commit hook）或**更严格的代码评审流程**。

**改进方向**：引入配置服务的统一抽象层，减少重复判断逻辑；强制要求 PR 中包含“配置接入点扫描清单”；对历史遗留问题（如版本号硬编码）建立技术债跟踪机制。
