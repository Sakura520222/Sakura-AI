## 📐 发现的模式

### 代码模式

1. **防御式导入**：API v1 模块从 `webui.deps` 导入依赖，暗示项目早期未做清晰分层，后续持续“带病运行”。

2. **异常处理分层焦虑**：`main.py` 中 `401→redirect`、`/webui→HTML`、`else→JSON` 三层判断，反映项目同时服务浏览器和 API 客户端的设计压力。

3. **测试中的隐式全局状态**：测试不显式 mock 配置读取，依赖 `conftest.py` 或全局 fixture，增加维护成本。

### 架构观察

- **WebUI 与 API 共享依赖层**：`deps.py` 既是 WebUI 的依赖注入容器，也作为 API 的“工具袋”。长期会导致：
  - 循环依赖风险
  - 部署单元无法解耦
- **支付服务的状态管理**：`payment_service.py` 集中了订阅、配额、降级逻辑，但缺少**状态机**抽象，导致“超出配额”无补偿处理。
- **错误页的脆弱性**：`error_page(user=user)` 在多数调用点传入用户，但在全局异常处理器中无法获取，暴露了 **request 与认证状态的解耦不足**。

## 📜 规范完善建议

基于本次审查，建议新增或强化以下规则：

| 规则 | 严重度 | 说明 |
|------|--------|------|
| **跨层导入必须注释理由** | minor | API 模块从 WebUI 层导入时，需注释说明为何无法定义在本层 |
| **全局异常处理器不得引用业务依赖** | major | 异常处理器应只处理格式转换，不解析 token、不查数据库 |
| **重复代码提取必须与性能权衡** | suggestion | 6 次独立日志调用可考虑批量聚合，避免高频 I/O |
| **测试中禁止依赖隐式全局 mock** | minor | 所有外部依赖（配置、数据库、API）必须显式 mock 或注入 |
| **新增降级日志必须评估监控影响** | suggestion | 若日志格式变更，需通知运维或修改告警规则 |

**项目特有规范补充：**
- `webui/deps.py` 只应包含**通用基础设施依赖**（如 `get_db`），业务依赖应放在各自模块的 `deps.py` 或 `core/dependencies.py`
- 新增 `HTTPException` 拦截器时，必须测试 **401 是否能优先重定向到登录页**

## 🧠 经验教训

### 未来审查关注点

1. **导入路径的“反模式”信号**  
   当 API 模块从 `webui.xxx` 导入时，立即检查是否涉及业务逻辑 → 可能预示分层腐化。

2. **异常处理器的顺序敏感性**  
   多个 `@app.exception_handler` 注册顺序决定优先级，应要求显式注释顺序依赖关系。

3. **“已修复”问题的回归验证**  
   本轮修复了装饰器重复，但未检查是否还有其他模块同样定义了相同函数 → 应要求全局搜索。

4. **配置驱动的降级策略**  
   遇到“无法自动重置配额”的模型限制时，应当提议配置化（如 `auto_reset_on_expire`），而非仅记录日志。

### 特定技术模式审查经验

- **FastAPI 依赖注入滥用**：当 `Depends` 函数被多个路由共享时，检查它的副作用（是否修改全局状态、是否访问同一数据库连接）。
- **Telegram Bot 的 Update 对象**：`update.message`、`update.callback_query` 等多态字段，所有访问前必须 None 检查（本次已做，但需养成良好的全局习惯）。
