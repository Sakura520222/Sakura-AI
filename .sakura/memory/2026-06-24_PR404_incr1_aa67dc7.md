## 深度反思

### 1. 审查质量评估

**覆盖度：微观优秀，宏观有缺口**

本轮对增量 diff 的微观审查质量很高——提示词契约追踪（`prompt_builder` → `review_protocol._parse_finding()` → `to_review_result()`）完整验证了下游不受影响，`_STAGE_TITLE` 的 fallback 等价性验证也到位。但存在一个明确遗漏：

**未声明历史遗留问题状态。** 历史上下文记录了 3 个未解决的 minor/suggestion 级问题（死代码 `find_check_run_for_sha`、debug 日志敏感信息泄露风险、`cleanup_stale_check_runs` 冗余调用），本轮审查摘要对此完全未提及。虽然这三项均非 major，但作为持续存在的已知问题，approve 决策时应至少有一句状态声明（如"历史 3 项 minor/suggestion 延续存在，不构成合并阻断"）。这属于"决策完整性声明"原则的执行缺口。

**准确度：无误判**

对 SUGGESTION 提示词变更的风险定级准确——识别出解析器仅做哨兵检测和标签保留，不做结构验证，因此提示词措辞变更确实不构成接口断裂。对 `_STAGE_TITLE` 新增的"低风险"判断也合理。

**完整性：PR 描述-增量差异声明缺失**

按规范"摘要中必须声明本轮增量范围与 PR 描述的差异"，本轮增量（prompt 重构 + stage title 增强）与 PR 描述（cleanup_stale_check_runs 新增与调用切换）属于不同关注点，但摘要未显式声明这一差异。读者可能产生"PR 描述提到的变更是否已全部审查过"的困惑。

**评分修正意见：** 9 分偏高。在"高评分应意味着穷尽检查点"的标准下，遗漏历史问题状态声明和 PR-增量差异声明，应为 **8 分**。

### 2. 发现的模式

**代码模式：**
- **"宽松解析 + 强提示"范式**：`review_protocol.py` 对 SUGGESTION 内容不做结构验证（不检查是否完整替换、不检查 unchanged lines 是否原样），而是通过提示词强约束 AI 输出质量。这降低了层间耦合，但也将正确性完全押注在 AI 遵从度上——如果 AI 忽略提示词规则，解析器不会拦截。
- **阶段元数据平行 dict 模式**：`_STAGE_TITLE` 与 `_STAGE_DESC` 键集必须手动保持同步，无编译期或测试期保障。

**架构观察：**
- 提示词构建器与协议解析器之间通过纯文本格式传递数据，而非结构化对象（如 JSON Schema），这是 LLM 工具链的常见妥协——文本格式对 LLM 更友好，但对维护者而言契约是隐式的。

### 3. 规范完善建议

**建议修改的审查规则：**

1. **扩展"决策完整性声明"适用范围**：当前规则仅要求"历史 major 未覆盖须说明"，建议扩展为"approve 时若存在任何未解决的已知问题（≥minor），须在摘要中逐项声明状态（已修复/延续存在-不阻断/延续存在-建议合并前处理）"。本轮遗漏的根因是 3 个 minor 不触发规则。

2. **新增"阶段元数据键集同步"检查项**：当新增与既有 dict 键集必须平行的 dict 时（如 `_STAGE_TITLE` 对应 `_STAGE_DESC`），建议至少在测试中加一个断言 `assert set(_STAGE_TITLE.keys()) == set(_STAGE_DESC.keys())`，或在审查中要求说明同步保障机制。

**项目特有规范要点：**
- 对于本项目，"提示词变更 = 接口变更"已作为核心原则落地，执行效果好。可以进一步细化：当提示词变更属于**约束收紧**（如本轮"必须完整替换"）时，除了验证下游不断裂，还应评估"旧有宽松输出是否会在过渡期出现"——如果有缓存或并发的旧输出，解析器能否安全处理。

### 4. 经验教训

1. **高评分下的"声明性遗漏"比"技术性遗漏"更危险**：本轮没有漏看任何代码问题，但遗漏了过程性声明（历史问题状态、PR-增量差异）。这类遗漏不会导致错误合并，但会损害审查记录的可追溯性，且难以通过技术手段检测。建议在审查清单中加入"声明性检查点"作为最终放行前的硬性步骤。

2. **"宽松解析"的隐性代价需要被显式记录**：本轮验证了"提示词变更不打破解析器"，但反过来——解析器对 SUGGESTION 的宽松态度意味着它也无法防御 AI 输出不符合提示词要求的情况。这不是本轮的问题，但作为架构特征值得在项目记忆中标记，以便未来评估是否需要增加校验层。

3. **热点文件的任何新增都值得一句开销说明**：`check_run_service.py` 已被标记为性能热点（每次审查调用 5-6 次 cleanup），本轮在其中新增了 `_STAGE_TITLE.get()` 调用。虽然 dict 查找开销可忽略，但对已知热点文件的任何变更，审查中一笔带过"开销可忽略"比完全沉默更好——体现对历史上下文的持续感知。

### 5. 增量审查反思

**历史问题解决情况：**
- 第一轮核心问题（SUGGESTION 语义模糊）在本轮通过独立的新提交修复，但审查摘要未将其定位为"对第一轮问题的响应"，而是作为独立变更描述。这弱化了审查的闭环感。
- 3 项 minor/suggestion 延续存在，未处理。

**新增风险：**
- `_STAGE_TITLE` 新增本身无风险，但缺乏键集一致性测试是一个小的技术债——未来新增阶段时容易忘记同步。

**覆盖度下降分析：**
- 本轮覆盖度下降主要体现在"声明性维度"而非"技术维度"。对 4 个变更文件的 diff 审查是充分的，但对 PR 全局状态的感知（历史问题、PR 描述对齐）因增量视角而弱化。这是增量审查的固有风险——审查者容易"进入增量隧道"，只关注眼前 diff 而忘记抬头看 PR 全局。建议在增量审查流程中增加一个"抬头步骤"：在开始看 diff 前，先读一遍 PR 描述 + 历史问题清单，形成"全局清单"，最后在摘要中逐项勾选。
