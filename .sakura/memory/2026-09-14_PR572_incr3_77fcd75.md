## 2. 发现的模式  

### 2.1 代码模式  
| 模式 | 描述 | 影响 |
|------|------|------|
| **文件/目录安全检查重复实现** | `ensure_runtime_tmp` 与新实现 `ensure_run_dir` 在 “trust‑chain” 校验上采用相似逻辑。 | 说明项目已形成成熟的安全防护模式，可抽象为公共工具函数以减少重复。 |
| **系统调用后缺少错误回滚** | `systemd.py` 卸载后 `fsync` 失败时抛 `ServiceError`，但未在调用方做回滚。 | 在极端异常（如磁盘 I/O 错误）下可能留下半残的 unit 文件。 |
| **Shell 脚本中业务路径硬编码** | `start.sh` 直接引用 `$UPDATER_STATE_DIR/sakura-ai-updater`，缺少 `realpath` 处理。 | 在符号链接或相对路径环境下可能产生不一致的二进制路径。 |
| **测试依赖真实二进制** | `tests/test_start_sh_updater_lifecycle.py` 通过子进程调用实际 `updater` binary。 | 对 CI 环境的构建依赖提升，若二进制编译失败，所有测试失效。 |

### 2.2 架构观察  
- **后端/前端分层明确**：`daemon.py`（后端守护进程） → `systemd.py`（systemd 适配层） → `start.sh`（用户入口）形成清晰的三层结构。  
- **依赖链路紧密**：`__main__.py` 直接导入 `daemon` 与 `systemd`，因此 **任何低层语法错误会直接导致入口不可用**。
- **测试覆盖点分布**：单元测试、集成测试、以及 Bash 脚本层面测试共同构成了多层验证，但 **所有层面的入口都依赖于库的成功 import**，所以 import‑层面的错误会一次性失效所有测试。

## 3. 规范完善建议  

### 3.1 审查规则（通用）  
1. **语法错误全库检查**  
   - 在每轮审查前强制执行 `python -m compileall -q <src_dir>`，任何 SyntaxError 必须在审查报告中列为 **critical** 并阻止继续。  
2. **跨平台 API 使用检测**  
   - 对 `os.O_DIRECTORY`、`fcntl`、`select.epoll` 等 POSIX‑only 接口，审查时自动检查是否有 `@pytest.mark.skipif(sys.platform != "linux")` 或等价 `skipif`。  
3. **依赖链路完整性验证**  
   - 对每个 **入口模块**（如 `__main__.py`、`start.sh`）执行 **import‑graph** 探测，若上层依赖的子模块存在未修复的 SyntaxError/ImportError，必须在审查报告中标记为 **blocking**。  
4. **测试‑二进制耦合度评估**  
   - 若测试直接调用项目生成的二进制，审查时应确认 **构建产物** 已在 CI 中成功生成；若未生成，要求添加 `skipif` 或改为 mock。  

### 3.2 项目特有规范要点  
| 规范 | 说明 | 适用范围 |
|------|------|----------|
| **受信目录创建策略** | 所有涉及文件系统写入的函数必须遵循 **fail‑closed** 合约，统一使用 `_check_trusted_directory_chain`。 | `daemon.py`、`systemd.py`、任何新增文件操作模块 |
| **Shell 脚本参数透传约定** | `start.sh` 中所有 `updater` 子命令的参数必须通过 `"$@"` 直接转发，避免手动拼接导致遗漏。 | `start.sh`、未来的包装脚本 |
| **CI 编译门禁** | 在 `.github/workflows/ci.yml` 中加入 `python -m compileall` 步骤并把结果设为 **required**。 | CI 全局 |
| **POSIX/Windows 兼容标签** | 对每个使用平台限定 API 的测试文件在文件顶部统一加入 `# pytestmark = pytest.mark.skipif(sys.platform != "linux", reason="POSIX only")`。 | 所有跨平台测试 |

## 4. 经验教训  

1. **历史技术债务的阻断效应**  
   - 即使增量实现本身质量高，若 **库层面的语法错误** 未清除，整个 PR 将因 **无法运行 CI** 而失效。审查时必须把 **全局可运行性** 置于首位。  

2. **增量审查不等于局部审查**  
   - 在 quick 策略下，仅看增量代码容易忽略 **跨文件的编译门禁**。推荐在每次增量审查前执行一次 **全库语法/导入检查**，即使改动不触及相关文件。  

3. **测试依赖的脆弱性**  
   - 测试直接调用真实二进制是高价值的行为验证手段，但也会把 **构建链路** 变成单点故障。建议在单元层使用 mock，在集成层保留真实二进制验证。  

4. **文档/实现同步审查**
   - 本次 PR 同时更新了大量文档，审查时应检查 **文档中的使用示例** 是否与实现匹配（如 `systemctl` 参数、路径约定），防止文档误导。

### 改进建议  
1. **在每轮增量审查前执行全库编译/导入检查**，把结果作为阻断条件。  
2. **将经验证的历史缺陷列入待办清单**，在 PR 合并前必须全量通过 `python -m compileall`，否则直接 `request_changes`。
3. **为 Bash 测试引入二进制构建成功的前置条件**（如在 CI 中先跑 `make build-updater && echo OK`），确保测试不会因二进制缺失而误报。  
4. **将 `updater_stop_daemon` 的建议实现合并到同一 PR**，或单独开一个小 PR 解决该行为偏差，防止在后续合并时遗漏。
