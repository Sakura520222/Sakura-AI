## 4. 经验教训

### 值得关注的要点
- **“点状修复”的陷阱**：只改断言不改来源（如生成断言的辅助函数）可能导致未来再次漂移。
- **配置系统的“对称性审查”必须成对出现**：  
  `范围定义` ↔ `测试断言` ↔ `路由校验` ↔ `写入路径校验` 四者必须一致。
- **历史问题升温 ≠ 自动解决**：必须配套 **issue 创建 + 阻塞合并** 才能驱动修复。

### 对特定技术的审查经验
- **Pydantic / 动态配置**：  
  避免同时存在 `DYNAMIC_CONFIG_RANGES` 和内联 `if not (min <= val <= max)`。推荐统一为 `ConfigService.validate_range()`。
- **测试的“脆弱断言”**：  
  断言值直接硬编码范围而非引用常量 → 容易过时。建议改为：
  ```python
  assert ranges["web_search_max_results"] == (1, 100)
  ```
