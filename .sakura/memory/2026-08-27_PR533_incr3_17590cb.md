## 1. 审查质量评估  

### 覆盖度  
- **代码层面**：本轮审查只聚焦在 `sandboxer/tests/integration/test_docker_isolation.py` 的增量改动（+137/-17），对新增的 `sandboxd` 控制平面、网络策略、Docker 运行时等核心模块未进行全局扫描。由于这些模块直接影响生产安全（容器隔离、能力降权、凭证清洗），仅凭增量文件的检查难以保证没有遗漏的安全或兼容性缺陷。  
- **CI/部署层面**：对新增的 GitHub Actions 工作流（`sandbox-quality.yml`、`sandbox-publish.yml`）以及 `start.sh`、Compose 配置的改动未做系统化的权限、环境变量、缓存策略审查，容易导致运行时红灯。  

### 准确度  
- **严重程度标记**：审查将 “sandboxer unit and runner isolation” CI 红灯标记为 **major / error**，这符合项目硬规则（任何 CI 失败即阻断），且对业务安全影响极大，判定合理。  
- **误判风险**：审查将本次提交的脱敏实现视为“无新缺陷”，但未验证脱敏后异常类型、返回码是否仍保持与生产代码一致（如 `DockerAdapterError` 是否被错误包装），存在潜在误判。  

### 完整性  
- **变更意图**：PR 描述涉及 **沙箱化、权限最小化、全链路安全**，审查对这些宏观目标的理解基本到位，尤其对脱敏顺序与界限做了肯定。  
- **上下文缺失**：未检查 **旧版沙箱实现** 与 **新实现** 的兼容性（是否仍保留向后兼容入口），也未评估 **Windows/macOS** 分支的行为是否仍符合安全模型。

## 2. 发现的模式  

### 代码模式  
| 模式 | 说明 | 潜在风险 |
|------|------|----------|
| **统一脱敏流水线** (`_redact_docker_stderr`) | 多层次替换 → 长度截断，保持日志可读性。 | 脱敏顺序硬编码，若后续新增敏感字段（如 token）需手动维护，易遗漏。 |
| **测试侧挂接 adapter** | 通过 `adapter._run_command` 替换实现诊断。 | 只能在测试环境生效，生产代码仍可能抛出未脱敏的原始异常。 |
| **异步隔离用例全部改写为诊断执行器** | 将 `await sandbox.run()` 包装为 `await sandbox.run_with_diagnostics()`。 | 若诊断路径未覆盖所有异常分支，某些错误仍会泄露。 |
| **“skip on Windows”** | 集成测试在 Windows 主机上被显式跳过。 | 可能导致跨平台回归盲区，尤其是文件系统路径脱敏在 Windows 上表现不同。 |
| **大量文件改动（+22k 行）** | 一次性引入大量新模块与文档。 | 代码审查难以一次性覆盖全部风险，建议分拆 PR。 |

### 架构观察  
- **沙箱服务独立化**：`sandboxer/` 成为独立子项目，提供 `docker_runtime`, `service`, `app` 等入口，且通过 HTTP‑over‑UDS 与后端交互，形成 **双层防护**（Web → sandboxd → Docker）。  
- **依赖图高度交叉**：`backend/services/agent_team/*` 多次依赖 `sandbox_client`、`network_policy`，形成 **环形依赖**（如 `execution.py` → `network_policy` → `sandbox_client` → `execution.py`），若不加以约束，未来模块解耦会很困难。  
- **配置中心单点** (`backend/core/config.py`) 被多个子系统共享，导致 **配置变更传播风险**，尤其是安全相关的阈值（CPU、内存、PID）需要统一校验。

## 3. 规范完善建议  

### 新增/修改审查规则  

| 规则 | 适用范围 | 说明 |
|------|----------|------|
| **全局脱敏规则审查** | 所有涉及日志、异常信息的代码 | 确认脱敏函数统一调用、顺序可配置、并在 CI 中加入脱敏覆盖率检查。 |
| **跨平台测试完整性** | `tests/**/*.py` | 对所有标记为 `skipif(os.name=="nt")` 的集成测试，要求提供 **Linux‑only** 运行报告链接，且必须在 PR 描述中明确说明跳过原因。 |
| **环形依赖检测** | `backend/services/**` | 自动检测模块间的循环依赖，若出现 >2 层循环，必须提供抽象层或接口拆分方案。 |
| **CI 关键工作流阻断规则** | `.github/workflows/*.yml` | 任意 **job** 失败必须标记为 `error/major`，且 PR 必须附带 **全绿** run 链接方可通过。 |
| **增量审查全库引用搜索** | 任意删除/改动公共 API、配置键、异常类 | 必须在审查报告中列出全库搜索结果，确保没有遗漏引用导致运行时 `KeyError` 或未捕获异常。 |
| **安全异常分类强制** | `except` 块 | 禁止裸 `except Exception`，要求显式捕获 `DockerAdapterError`, `SandboxError` 等并在注释中标注错误级别 (`# INTERNAL_ERROR`). |
| **文档‑代码双向校验** | `README*`, `docs/**`, `CONFIGURATION.md` | 文档中出现的配置项、命令行参数必须在代码中有对应常量或解析路径，缺失即标记为 `error`. |

### 项目特有规范要点  

1. **沙箱入口统一化**：所有对外执行入口（`backend/services/agent_team/execution.py`、`sandbox_client.py`）必须通过统一的 `SandboxExecutor` 接口调用，避免散落的 `docker run` 命令。  
2. **凭证清洗原则**：Git URL 中的凭证只能在 **askpass** 阶段注入，任何硬编码 `token=`、`username:` 必须在 CI 中报错。  
3. **容器资源限制声明**：每个容器镜像的 `cpu`, `memory`, `pids`, `nofile`, `ulimit` 必须在 `docker-compose.yaml` 中显式声明，且在代码层有对应常量校验。  
4. **安全审计日志**：所有沙箱创建、启动、销毁操作必须记录 **审计级别** 日志，且日志字段需经过脱敏函数。

## 4. 经验教训  

| 教训 | 具体表现 | 建议的改进措施 |
|------|----------|----------------|
| **增量审查易忽视全局安全链路** | 本轮仅检查了测试文件，未审查 `sandboxd` 控制平面的权限配置。 | 在大型功能引入（沙箱、网络策略）时，强制执行 **全库安全审查**，即使是增量 PR 也要打开全局视图。 |
| **CI 红灯的阻断意义被低估** | “sandboxer unit and runner isolation” 红灯被标记为阻断，但审查未要求立即提供全绿 run 链接。 | 将 CI 失败的**链接收集**设为审查必填项，审查报告中自动检查是否已附带。 |
| **脱敏实现的“黑盒”误判** | 认为脱敏逻辑已完备，未检查异常类型保持一致性。 | 在审查时执行 **异常类型映射对比**（原始 vs 脱敏后），确保 API 合约不被破坏。 |
| **跨平台跳过导致回归盲区** | Windows 上的集成测试被跳过，导致潜在路径/权限差异未被捕获。 | 引入 **平台矩阵 CI**（Linux/Windows/macOS），即使测试被跳过，也要求提供 **模拟或手工验证报告**。 |
| **一次性大体量提交降低审查效率** | 本次 PR 变更 22 k 行、101 文件，审查人员难以全盘把握。 | 推行 **功能拆分 PR**（每个子系统单独 PR），并在合并前进行 **集成回归**。 |

| **配置/权限** | ❌ 未审查 `sandboxd` 容器的 `cap_drop`、`no-new-privileges` 等安全配置是否在 Dockerfile 中实际生效。 | ⚠️ 若配置失效，容器可能获得过高权限，导致安全突破。 | 📉 因增量审查范围受限，未覆盖这些关键安全配置文件。 |

### 综合结论  
- **增量审查**在本次 PR 中对 **脱敏实现** 的质量给予了肯定，但 **未能捕获全局安全链路**（沙箱控制平面、CI 工作流、跨平台测试）以及 **新引入的风险**。  
- 为提升审查质量，建议在 **大幅功能引入** 时，**强制全库审查**（或至少一次完整的安全审计），并在审查工具中加入 **CI 运行状态检查**、**跨平台测试覆盖度**、**异常类型保持性** 等自动化检测。
