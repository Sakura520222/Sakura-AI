## 审查质量评估

总体评分 7/10 基本合理：本次变更范围小、引用点完整、兼容性核对有实际依据，且没有被 PR 描述带偏。但作为一次针对 CI 依赖升级的审查，仍有两点明显盲区：

### 1. 未区分 `setup-crane` 版本与实际安装的 `crane` CLI 版本

- `imjasonh/setup-crane` 的 v0.7 并不等价于 `crane` CLI 的 v0.7。该 action 的作用是“安装最新版 crane CLI”，因此 action 版本从 v0.4 升到 v0.7，实际安装的 crane 版本也可能跟着变。
- 审查结论写了“v0.7 下 `crane copy` / `crane tag` / `crane digest` / `crane auth login` 语义与参数完全一致”，但依据主要是 setup-crane 的 release notes，没有去核对 crane 自身发布历史或 go-containerregistry 的变更。
- 虽然直觉上这些命令很稳定，但“未发现 Breaking Changes”这句话需要更严谨的验证链：**action 版本 → action 安装的 crane 版本范围 → 工作流中实际使用的子命令参数**。

### 2. 未提及 GitHub Actions 的 SHA 固定问题

- 本次将 `imjasonh/setup-crane` 固定到 `v0.4` 改为 `v0.7`，仍然是可变 tag。
- 对于第三方 action，尤其是需要访问镜像仓库凭据的工作流，最佳实践是固定到完整 commit SHA，而不是 tag。v0.6/v0.7 的 release notes 本身就包含“防止脚本注入”“修复 shell 变量引用”等安全修复，说明 action 代码在有实际变化。
- 审查中没有提出“建议固定到 commit SHA”，这是供应链安全角度的遗漏。至少应作为 minor 或 suggestion 给出。

### 3. 外部 CI 失败的分级可以更明确

- 审查把 Gitflow 分支规则失败标为 minor，虽然能解释“不是本 diff 引入”，但它同时是“确定性、阻塞合并”的。对于实际合并流程而言，这更像一个需要维护者行动的阻断项。
- 如果是人工审查，`comment` 可接受；但如果作为自动化审查机器人，建议这种情况下直接给 `changes_requested`，并显式说明“diff 本身无问题，但该 PR 当前无法通过分支保护”。

## 发现的模式

### 代码 / 工作流模式

- 项目将 crane 相关调用集中收敛在 `docker-publish.yml` 和 `docker-reconcile.yml` 两个工作流中，且 `docker-reconcile.yml` 的 backfill job 复用 `docker-publish.yml`，这是比较好的工作流复用模式。
- 三处 `setup-crane` 都是裸 `uses:`、无输入参数，说明升级时的兼容面很小。审查能快速通过主要依赖这一点，这是合理的。

### 架构 / 仓库策略观察

- 仓库采用 Gitflow 风格分支保护，但 dependabot 自动生成的分支名是 `dependabot/github_actions/...`，与允许的前缀规则冲突。这是一个**自动化策略与基础设施之间的结构性冲突**，不是单次 PR 的偶发问题。
- 这提示项目可能存在一种常见的“策略漂移”：分支规则保护了手工分支，却没有为自动化机器人开白名单，导致 dependabot 创建的 PR 几乎必然失败。

## 规范完善建议

建议在项目审查规则中新增/强化以下条目：

### 1. GitHub Actions 升级专用检查项

- 必须确认 action 引用是否存在可变 tag，若存在，建议固定到 commit SHA。
- 对 0.x 版本升级要特别谨慎，0.x 的 minor 版本也可能包含破坏性变更，不能只看 semver 组名。
- 对“安装型 action”（如 setup-crane、setup-buildx、setup-qemu）要区分 **action 版本** 和 **安装工具版本**，并核对实际使用命令在目标工具版本下的兼容性。

### 2. Dependabot 分支策略

- 在 `gitflow-branch-policy.yml` 中显式增加 `dependabot/` 前缀白名单，或允许 `dependabot/**` 进入 develop。
- 将“dependabot PR 到 develop 会触发分支策略失败”记入项目记忆，后续同类 PR 可直接复用该结论，不必每次重新拉取外部 CI 日志。

### 3. 工作流变更的验证方式

- 建议在 CI 中增加 `actionlint` 或类似工具，对 `.github/workflows/` 下的 YAML 做结构校验。
- 对工作流升级类 PR，除了 grep 引用点，还应检查是否存在其他文件通过 `workflow_call` 或手工复制方式引用同一 action。

## 经验教训

### 1. “最简单变更”最容易忽略供应链问题

本次只是 `v0.4` → `v0.7` 的字符串替换，但背后的安全语义并不简单：

- action 代码可能被重新打 tag；
- action 内部可能安装不同版本的 CLI；
- action 可能获得工作流的 `GITHUB_TOKEN` 或镜像仓库凭据。

今后遇到“版本号替换”类 PR，除了看 release notes，还应至少看一遍 action 的 `action.yml` 和核心脚本，确认它到底做了什么、能否访问敏感信息。
