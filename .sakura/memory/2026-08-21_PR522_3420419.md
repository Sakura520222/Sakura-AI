# 代码审查反思报告

## 1. 审查质量评估

*   **覆盖度：极高**
    *   **核心路径验证充分**：审查不仅覆盖了配置系统的重构链路（默认值、DB 覆盖、迁移幂等性），还深入到了运行时最危险的 Worker 循环逻辑。
    *   **隐患挖掘彻底**：精准捕捉到了 `while True` 移除轮次限制和预算检查后的严重后果（资源耗尽、并发饥饿）。
    *   **潜在盲区**：PR 描述提及 "Update dependencies"，审查摘要中虽提及 Python 3.14 和 Dockerfile 更新，但未详细展开对具体第三方库（如 FastAPI/Pydantic/SQLAlchemy）版本升级的 Breaking Changes 核对。若此次包含 Major 版本依赖升级，此处存在轻微覆盖缺口。

*   **准确度：精准**
    *   **定级合理**：将 `issue_analyzer` 和 `scan_worker` 的无界循环定为 `major` 完全符合项目 "LLM 应用的无限循环风险" 核心原则。这不仅是代码缺陷，更是生产环境的运维灾难。
    *   **误判控制**：对 Python 3.14 新语法的合法性判断准确，避免了对非标准写法的误报；对热重载中私有属性的操作定为 `suggestion` 而非 `error`，准确区分了开发体验与生产稳定性。

*   **完整性：深刻**
    *   充分理解了 PR "配置统一存储" 的重构意图，并验证了数据完整性（Unique 约束、迁移脚本）。
    *   识别了 "删除即变更" 的本质，对被删配置键做了全仓引用验证，防止了悬挂引用。

## 2. 发现的模式

*   **代码模式：安全护栏的隐性剥离**
    *   本次 PR 呈现了一种典型的危险模式：以 "简化代码" 或 "信任模型" 为由，删除了原本存在的物理硬约束（`max_iterations`, `budget`）。这种清理往往容易被误认为是优化，实则移除了防止 LLM 幻觉导致死锁的最后一道防线。

*   **架构模式：Worker 安全标准的不对等**
    *   审查揭示了 `Review Worker` 与 `Issue/Scan Worker` 在安全设计上的割裂。前者保留了 `_run_review_task_with_timeout`，而后者在本次变更中失去了保护。这表明项目中缺乏统一的 "Worker 执行生命周期基类" 或强制混入（Mixin）来标准化超时与取消逻辑。

*   **架构模式：配置系统的 "去中心化消费"**
    *   配置重构采用了 "中心化注册 + 去中心化消费" 的模式。虽然架构清晰，但极大增加了 "死配置" 风险。审查中发现对被删键的清理验证难度较大，侧面印证了这种模式对静态分析的不友好。

## 3. 规范完善建议

*   **新增规则：[LLM 循环双重约束强制]**
    *   **内容**：凡涉及 LLM Tool 调用的 `while` 循环，必须强制同时具备 **外部约束**（`asyncio.wait_for` / `timeout`）和 **内部约束**（`max_iterations` / `step_limit`）。
    *   **理由**：单一约束失效（如协议层超时未生效）时，另一约束必须兜底。禁止仅依赖模型 "自然停止"。

*   **强化规则：[配置删除的全量回溯验证]**
    *   **内容**：删除配置键（Settings/Dynamic Config）必须不仅搜索代码引用，还必须强制检查：
        1.  CI/CD Workflow 环境变量注入。
        2.  `docker-compose.yml` / `Dockerfile`。
        3.  任何包含 `config` 关键字的 Markdown 文档或初始化脚本。
    *   **理由**：配置往往是隐式传递的，代码无引用不代表运行时不使用。

*   **细化规则：[私有属性访问的防御性编程]**
    *   **内容**：在访问第三方库（如 FastAPI）的 `_private` 属性前，强制要求 `hasattr` 检查或 `try-except AttributeError` 包裹，并附带注释说明 "Hack for version X.Y"。
    *   **理由**：防止上游库版本微调导致开发环境崩溃，且难以排查。

## 4. 经验教训

*   **历史记忆是最佳防线**：
    *   本次审查中引用了 `.sakura/memory` (PR505) 的教训，成功阻止了同类错误的复发。这证明在 Agent 类项目中，维护一份 "反模式黑名单" 比通用的 Code Review 规则更有效。

*   **警惕 "信任模型" 的陷阱**：
    *   当开发者倾向于 "相信模型会正确停止" 时，往往意味着系统鲁棒性的倒退。代码审查必须始终假设模型是非理性的、恶意的或故障的，所有与模型交互的控制流必须有 "熔断机制"。

*   **重构需保留 "运维逃生通道"**：
    *   删除 `max_iterations` 这种可配置项，意味着当模型行为异常时，运维无法通过调整配置止损，必须重新部署代码。审查时应警惕任何 "硬编码化" 或 "不可配置化" 的重构倾向。
