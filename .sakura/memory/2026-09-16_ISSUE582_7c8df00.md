## 6. 经验教训 & 后续建议  

| 关键点 | 说明 |
|--------|------|
| **自动化同步策略** | 自动把 `main` 合并到 `develop` 的工作流虽提升同步频率，但在 **活跃的 `develop`** 上容易产生冲突。建议：<br>1. **仅在 `main` 稳定后**（如发布 Tag）触发同步；<br>2. 使用 **rebase** 而非 merge，保持线性历史，降低冲突概率。 |
| **冲突预警** | 在合并前加入 **冲突检查** 步骤（`git merge --no-commit --no-ff origin/main`），若检测到冲突即 **自动创建 Issue 并标记 `ci-blocking`**，避免 CI 直接失败。 |
| **CI 失效反馈** | 当前工作流在冲突时直接报错并创建 Issue，缺少 **通知渠道**（如 @team、Slack）。建议在 workflow 中加入 `actions/github-script` 发送通知。 |
| **冲突文件定位** | `.sakura/` 目录常包含 **自动生成的知识库**，其冲突往往需要 **重新跑抽取脚本** 而非手动编辑。可以在工作流中检测该目录冲突后，自动触发 **重新生成** 脚本作为后置步骤。 |
| **标签体系统一** | 为避免标签碎片化，建议在仓库根目录维护 **`LABELS.md`**，列出官方标签、含义及使用场景，供 AI 与人工审查统一参考。 |
| **重复 Issue 管理** | 引入 **“related”** 与 **“duplicate”** 的明确区分流程：<br>1. 自动比对冲突 SHA；<br>2. 若相同则直接关闭新 Issue；<br>3. 若不同但相似，添加 `related` 并在对应 Issue 中记录链接。 |
| **文档同步** | 将分支同步策略写入 **CONTRIBUTING.md**，明确说明：<br>- `main` → `develop` 合并频率<br>- 冲突处理流程（谁负责、何时执行）<br>- CI 阻断的升级路径 |
