### 2. 发现的模式
- **代码模式**：
  - **支付网关辅助函数**：新增 `_to_minor_units`/`_from_minor_units` 采用 `Decimal` 精确计算，符合金融场景最佳实践，但缺少直接测试覆盖。
  - **验证逻辑宽松化**：金额验证在 `paid_amount_cents is None` 时直接返回，货币不匹配时仅警告，体现了“容错优先”的设计倾向，但缺乏安全阈值或 ADR 文档。
- **架构观察**：
  - **支付服务集中化**：`payment_service.py` 承载核心业务逻辑，但成为历史问题热点（多轮审查均标记问题），建议拆分或引入策略模式。
  - **配置硬编码**：`CURRENCY_DECIMALS` 字典缺少来源注释，反映配置管理未完全中心化。

### 3. 规范完善建议
- **新增审查规则**：
  1. **支付事务原子性检查**：任何支付状态变更（如 `confirm_payment`）必须评估与关联操作（如服务发放）的事务一致性，标 major。
  2. **辅助函数直接测试强制规则**：独立纯函数（如 `_to_minor_units`）必须有直接单元测试，覆盖边界情况（None、负数、无效输入），标 major。
  3. **设计决策文档化要求**：对持续多轮未根治的安全降级行为（如金额验证绕过），强制要求记录 ADR 或代码注释，否则升温为 critical。
- **项目特有规范**：
  - **货币转换配置溯源**：`CURRENCY_DECIMALS` 等常量必须标注 ISO 4217 等权威来源。
  - **支付日志 Bypassing 标识**：已实践的 `BYPASSING` 日志标识应推广为支付网关日志标准。

### 4. 经验教训
- **增量审查局限性**：本次仅审查新增提交，但支付服务是历史热点，需主动关联扫描（如 `webhook.py` 调用链）。未来对核心文件变更，即使“quick”策略也应执行跳跃式全量扫描。
- **支付安全持续关注**：金额验证绕过、货币不匹配等历史问题虽标记为设计决策，但需定期复审（如每季度），防止技术债累积。
- **测试覆盖深度**：集成测试可覆盖调用链，但纯函数边界情况需直接单元测试，避免依赖间接覆盖。
