## 1. 审查质量评估

### 覆盖度

本次审查总体覆盖了主要增量：`reviewer.py`、`issue_analyzer.py` 新增 `event_callback`，以及两个 worker 侧接入回调。核心问题——`except Exception: pass` 静默吞异常——被正确识别，且与项目记忆中的“禁止静默吞没异常”规则一致。

但仍有一些可能遗漏的点：

1. **缺少对事件契约一致性的检查**
   - 本次变更引入了新的事件类型与数据结构，例如 thinking、tool_call、tool_result、tool_error 等。
   - 审查没有明确检查这些 `event_type` 是否与前端 SSE 消费端、`ActivityEventService`、数据库事件类型约束保持一致。
   - 如果前端依赖固定字段，例如 `tool_name`、`message`、`status`，字段不一致可能导致 UI 无法正确展示。

2. **缺少测试覆盖要求**
   - 本次 PR 新增了一个跨服务、worker、SSE 链路的实时事件能力，但审查报告没有将“缺少测试”作为重要问题提出。
   - 至少应建议覆盖：
     - `event_callback=None` 时不影响原有流程；
     - callback 正常执行时事件被记录；
     - callback 抛异常时主流程不中断且有日志；
     - 工具调用失败时是否发送失败事件。

3. **未充分评估 callback 阻塞风险**
   - `event_callback` 是异步回调，并且在工具循环中被 `await`。
   - 如果 `_log_activity` 或 SSE 发布链路变慢，会直接拖慢 AI 工具调用流程。
   - 当前设计可能是有意保证事件顺序，但审查应至少指出：这是同步等待式事件上报，需确认性能和失败隔离是否符合预期。

4. **未检查事件数据序列化边界**
   - 审查提到了 `json.dumps(result, ensure_ascii=False)[:200]` 的截断，但没有进一步检查：
     - `result` 是否一定 JSON 可序列化；
     - callback 传入的 `data` 是否满足 `ActivityEventService.log_event` 的存储格式；
     - 截断后的字符串是否可能破坏 JSON 语义。
   - 如果只是用于展示，截断字符串可接受；如果前端当 JSON 解析，则存在隐患。

5. **未关注重复实现**
   - `reviewer.py` 与 `issue_analyzer.py` 中可能出现相似的事件发送逻辑。
   - 本次审查没有指出是否可以抽出统一 helper，例如 `_safe_emit_event`，以减少未来不同模块行为不一致。

### 准确度

严重程度基本合理，但有细节可优化。

1. **`except Exception: pass` 标为 major 是可以接受的**
   - 因项目有硬规则“禁止静默吞没异常”，即使该异常只影响活动上报，也应至少标为 major。
   - 不过从业务风险看，它不会直接导致审查失败、数据损坏或安全问题，因此不宜标 critical。当前没有标 critical 是正确的。

2. **“参数构造、序列化等异常会被完全吞没”的表述需更精确**
   - 如果参数构造位于 `try` 内，确实会被吞掉。
   - 但如果回调闭包 `_log_activity` 内部也已有日志，那么部分异常其实已被记录。
   - 更准确的说法应是：`event_callback` 调用外层的异常兜底没有日志，导致 callback 入口之前或 callback 未自行记录的异常不可观测。

3. **对 `_log_activity` 缺 `exc_info=True` 的降级判断合理**
   - 当前是 debug 日志，不属于强制 `logger.error(..., exc_info=True)` 的场景。
   - 作为历史遗留问题继续追踪即可，不应在本次增量中阻断。

4. **主评论质量存在格式问题**
   - “主要评论”中出现多条 `[suggestion]` 承载摘要、清单、表格残片，说明结构化评论抽取不够干净。
   - 这会降低审查报告可读性，也可能污染 GitHub review comments。
   - 后续应避免把整段报告、表格、历史追踪内容误作为行级 suggestion。

### 完整性

本次审查基本理解了 PR 意图：为 AI Reviewer 和 Issue Analyzer 增加实时进度事件回调，并由 worker 转发到活动日志/SSE。

但对上下文的理解仍有不足：

- PR 描述提到“统一实时活动监控界面”，而本次增量只是接入 worker 到服务层的事件回调。审查应更明确地区分：
  - 已实现：工具执行过程事件上报；
  - 依赖已有：SSE、ActivityEventService、前端展示；
  - 未验证：前端是否能消费新增事件。
- 本次变更和历史问题中的 activity 权限、公共服务测试覆盖有关联，但审查只做了历史追踪，没有主动检查当前新增事件是否会暴露敏感数据。

## 2. 发现的模式

### 代码模式

1. **可选异步回调模式**
   - 服务层通过 `event_callback: Optional[Callable[..., Coroutine]] = None` 接收上层注入。
   - worker 层构造闭包，将具体事件写入活动服务。
   - 这种模式解耦较好：核心 AI 流程不直接依赖 ActivityEventService。

2. **容错优先模式**
   - callback 失败不影响主流程，这是合理的。
   - 但当前实现用 `except Exception: pass`，体现出项目中仍存在“为了不影响主流程而静默忽略”的习惯。
   - 正确模式应是：失败隔离 + debug 日志。

3. **延迟导入模式**
   - worker 中 `_log_activity` 使用延迟导入避免依赖链过早加载。
   - 项目已形成相关规范：延迟导入必须说明循环依赖或依赖链原因。

4. **事件数据截断模式**
   - 工具参数、工具结果进行 `[:200]` 截断，说明开发者有意识控制前端实时日志体积。
   - 但目前截断策略分散，缺少统一常量或 helper。

### 架构观察

1. **服务层与 worker 层职责较清晰**
   - `reviewer.py`、`issue_analyzer.py` 负责业务执行；
   - `review_worker.py`、`issue_worker.py` 负责记录任务活动；
   - `ActivityEventService` 负责持久化与 SSE 发布。

2. **Activity/SSE 已成为横切能力**
   - 它横跨 PR review、issue analysis、repository scan。
   - 因此事件类型、权限、数据结构、测试覆盖应逐步规范化，否则后续每个 worker 都会各自实现一套类似逻辑。

3. **异步链路存在背压风险**
   - 当前事件记录在主流程中 `await` 执行。
   - 如果活动服务或 SSE 变慢，可能影响 AI 工具循环。
   - 未来可以考虑将非关键活动事件投递到后台队列，或提供 fire-and-forget 但带日志的安全封装。

## 3. 规范完善建议

### 建议新增审查规则

1. **可选回调异常处理规则**
   - 对非关键 callback、hook、observer 的异常必须隔离主流程，但禁止静默吞没。
   - 推荐模式：
     ```python
     try:
         await event_callback(event_type, data)
     except Exception as exc:
         logger.debug("event_callback failed: {}", exc, exc_info=True)
     ```

2. **实时事件契约检查规则**
   - 新增或修改 SSE/activity 事件时，必须检查：
     - 事件类型是否有统一定义；
     - 前端是否支持该事件类型；
     - 字段名是否稳定；
     - 是否包含敏感信息；
     - 是否有最小测试覆盖。

3. **活动事件敏感信息审查规则**
   - 工具参数、模型输出、Issue/PR 内容片段推送到前端前，应检查是否可能包含 token、secret、private repo 信息。
   - 对工具参数和结果建议统一脱敏或白名单字段。

4. **事件上报不得显著阻塞主流程**
   - 对高频或长链路中的事件上报，应评估是否同步等待。
   - 如果同步等待，应说明原因，例如保证顺序。
   - 如果异步投递，应保证异常可观测。

5. **重复事件发送逻辑抽象规则**
   - 多个服务中重复出现 `if event_callback: try await ... except ...` 时，应考虑抽出 `_safe_emit_event`，统一日志、截断、脱敏、异常处理。

### 项目特有规范要点

- `ActivityEventService` 相关变更应强制检查权限、事件 schema、前端消费、SSE 发布路径。
- worker 中 `_log_activity` 失败不能影响主任务，但必须保留足够日志。
- 延迟导入必须继续保留原因注释。
- 新增活动事件字段应避免把完整工具参数或完整模型结果直接传给前端。

## 4. 经验教训

1. **“不影响主流程”不等于“可以静默失败”**
   - 对 telemetry、activity、SSE 这类辅助能力，失败隔离是正确的；
   - 但完全 `pass` 会让问题难以定位。
   - 最佳实践是 debug 级日志 + 主流程继续。

2. **实时活动功能要审事件契约，而不只是审调用点**
   - 这类 PR 的风险不只在 Python 代码是否能运行；
   - 更在于前后端是否理解同一套事件类型和字段。

3. **跨 worker 的横切逻辑容易复制粘贴**
   - `review_worker`、`issue_worker`、`scan_worker` 已经有相似活动日志逻辑。
   - 后续应特别关注这些模块之间的行为是否一致。

4. **增量变更中新增的“可选参数”也要检查全量调用点**
   - 虽然参数有默认值，不会破坏旧调用；
   - 但仍应检查所有核心调用路径是否有必要接入 callback，避免功能只在部分任务类型生效。

5. **审查输出本身需要结构化质量控制**
   - 本次报告主体较完整，但“主要评论”部分出现重复、截断、表格残片。
   - 未来应区分：
     - 行级评论：只放具体代码问题；
     - 总结性内容：放在 review body；
     - 历史追踪：避免生成 GitHub 行级 suggestion。

## 5. 增量审查反思

### 新增提交是否解决了之前问题？

本次提交主要是功能增强：为 AI Reviewer 和 Issue Analyzer 增加实时事件上报。它没有直接修复历史中的主要遗留问题：

- `activity_access.py` 权限模式不一致：未涉及。
- `_log_activity` 异常日志缺少 `exc_info=True`：未修复，但本次新增 callback 进一步扩大了活动日志链路的重要性。
- 公共服务/路由测试覆盖不足：未见新增测试。

不过本次提交确实延续并利用了此前的 Activity/SSE 基础设施，说明项目正在围绕实时活动监控继续扩展。

### 增量变更引入的新风险

1. **新增静默异常点**
   - 6 处 `except Exception: pass` 是明确新增风险。
   - 虽然不影响主流程，但违反项目日志规范。

2. **事件链路耦合增强**
   - AI 工具循环现在会等待 activity callback。
   - 这使 activity 体系的性能和稳定性间接影响 AI 任务执行耗时。

3. **事件内容可能泄露上下文**
   - 工具参数和工具结果被推送到活动流。
   - 即使截断到 200 字符，也要确认其中不含敏感信息。

4. **事件类型/字段可能与前端不匹配**
   - 若前端没有处理新增事件类型，用户可能看不到预期进度，或者 UI 展示异常。

### 审查覆盖度是否因只看增量下降？

有一定下降。

本次是 quick + 增量审查，重点集中在 4 个变更文件，对以下关联面覆盖不足：

- 前端 activity 页面是否消费新增事件；
- ActivityEventService 是否对新增数据结构有约束；
- 权限控制是否保证用户只能看到自己的任务事件；
- 测试是否覆盖新链路；
- SSE 性能和背压风险。

未来遇到 Activity/SSE/worker 这类横切能力，即使是小增量，也应执行轻量关联扫描：

1. 服务层事件生产点；
2. worker 记录点；
3. ActivityEventService 存储/发布；
4. activity access 权限；
5. 前端展示；
6. 最小测试覆盖。

## 总结

本次审查抓住了最明确、最符合项目硬规则的问题：新增 `event_callback` 调用中静默吞异常。评分 7/10 和 request_changes 基本合理。

主要不足是审查偏局部，未充分检查实时事件功能的完整契约、测试覆盖、敏感信息、性能背压和前端消费兼容性。后续应把 Activity/SSE 视为项目级横切能力，新增事件时不只看调用是否成功，还要检查“谁能看到、看到什么、是否安全、是否稳定、是否有测试”。
