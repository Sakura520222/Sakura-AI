## 2. 发现的模式

### 代码模式
- **"接收但忽略"反模式**：`ref`、`sha` 参数被接收后完全丢弃，无日志、无警告、无异常。这是本次最危险的编码习惯——调用方产生"我传了参数所以行为正确"的错误假设。
- **空实现存根**：`get_topics()` 等返回空值，且无 TODO 标记，容易成为永久的技术债。

### 架构观察
- **双数据源静默切换**：PyGithub API vs 本地文件系统，但切换条件不透明。两种数据源的"时间一致性"问题（API 可能看到最新 commit，本地可能是 clone 时的快照）未被讨论。
- **适配器不适配**：名义上是适配器模式，实际是"鸭子类型硬凑"——只要不报 AttributeError 就算成功。

## 3. 规范完善建议

### 新增规则

**规则：参数静默忽略禁止**
> 当方法签名包含参数但实现中完全忽略时，必须满足以下之一：
> - 抛出 `NotImplementedError` 并说明替代方案
> - 记录 warning 日志
> - 在文档字符串中用 `.. note::` 明确标注
> 
> 违反级别：major（quick 策略不免责）

**规则：适配器接口契约审查**
> 实现适配器/代理模式时，必须验证：
> 1. 返回值类型是否与被适配对象一致（不只是"能用"，要"兼容"）
> 2. 下游代码依赖的属性/方法是否全部实现
> 
> 违反级别：major（若下游会因此报错）

**规则：双数据源一致性声明**
> 当同一抽象存在两种实现（如 API + 本地），PR 描述或代码注释必须明确：
> 1. 何时选择哪种实现
> 2. 两种实现的数据一致性保证（或明确声明"无保证"）

### 修改现有规则
- **三问法补充**：在"全否则降级"后追加 → *但"接口契约违反（调用方会因类型不匹配报错）"例外，保持 major*

## 4. 经验教训

### 值得关注
1. **"替换 mock"类 PR 的陷阱**：mock 通常只实现了被测场景需要的最小接口，替换成真实实现时，未覆盖的接口会成为隐性炸弹。审查时应主动拉取下游调用链，验证接口完整性。
2. **安全漏洞的"低垂果实"**：本次 critical 是教科书式的路径遍历，说明 `os.path.join + 外部输入` 的组合仍然是高频漏洞点，P1 规则应继续保持。

### 审查策略反思
- **quick 策略下 major 通胀**：本次将 3 个功能缺失标为 major，违反了"优化建议≠major"的判定原则。功能缺失（尤其是 fallback 路径）本质是 suggestion，除非会导致运行时错误。
- **应先问"是否有调用方实际依赖"**：如果 `ref=pr.head.sha` 在本地适配器路径下根本不会被触发（因为选择逻辑已排除），则问题严重性应降级。

### 技术经验
- 本地适配器若要支持 `ref` 读取，`git show {ref}:{path}` 是正确方案，但需注意：如果 ref 不存在或 path 在该 ref 中不存在，要有清晰的错误处理，不能返回空或静默失败。
