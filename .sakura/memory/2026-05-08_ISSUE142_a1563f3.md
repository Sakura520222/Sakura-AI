## 6. 经验教训（可供未来类似 Issue 分析参考）

### 针对“多厂商接入 + 配置重构”类 Issue 的必查清单

- [ ] 当前配置的真实源是 DB 还是 YAML？本次是否引入双写？
- [ ] 主模型 API Key 是否会被 RAG/重排序模型隐式复用？解耦点在哪里？
- [ ] 厂商的模型列表 API 是否有统一的降级策略（如失败回退到静态预定义表）？
- [ ] Setup Wizard 的取消/返回/切换厂商是否调用了公共清理函数？
- [ ] 是否设计只读的`/api/ai-providers/{provider}/models`接口（不应写入配置）？
- [ ] 模型上下文自动获取失败时，是否记录 warning 并回退到 `PREDEFINED_MODELS` 静态值？

### 仓库特有的高风险模式（本次 Issue 触发）

- **配置穿透多层**：`Settings → yaml_config → 硬编码默认值` 全链路修改易遗漏。必须增量审查所有调用 `_ENV_TO_SETTINGS_KEY` 的地方。
- **惰性重置遗漏读取路径**：新增厂商后，`ModelContextManager` 的 `auto_fetch_model_context` 若为 True，所有读取模型上下文窗口的路径必须调用自动获取函数，否则仍读静态映射。

### 对分析流程的建议

- 当 Issue 涉及 **4 个以上配置域** 时，应输出一张 **状态变更全链路清单**（DB ENUM → 模型枚举 → API 序列化 → WebUI 模板 → i18n → SSE 事件 → 状态转换矩阵），即使当前分析未要求。
- 重复检测应给出至少一句解释（如标题关键词重叠、范围包含等），避免黑盒判断。
