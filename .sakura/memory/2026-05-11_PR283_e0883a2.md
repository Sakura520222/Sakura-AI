## 2. 发现的模式

### 代码模式
- **共性的防御模式**：在函数顶部对可能未赋值的变量统一初始化（`None`），与已有 `review_obj` 风格一致。
- **测试结构**：新增测试覆盖了正向（合法值）、反向（非法值）、优先级（用户值优先）和回退（全局默认），但缺乏集成测试验证真实缓存失效和并发场景。

### 架构观察
- **配置系统依赖动态读取 + 缓存失效**：用户配置通过 `get_user_dynamic_config` 读取，并配有 `invalidate_user_dynamic_config_cache`，但测试中仅在 assert 后调用失效，可能掩盖“未失效时后续测试仍读到旧值”的 bug。
- **异步测试的清理陷阱**：使用 `monkeypatch` 虽然自动恢复环境变量，但缓存失效是应用层状态，pytest 无法自动清理，这在该仓库中已是第二次出现的模式漏洞。

## 4. 经验教训

### 值得未来审查关注的要点
- **异步测试中的副作用隔离**：凡是在异步测试中直接调用 `invalidate_xxx_cache` 且不在 `finally` 中执行，一律视为高风险。即使 pytest 隔离了模块，但 `lru_cache` 或模块级 `dict` 会跨测试污染。
- **用户级配置的隐性影响范围**：新增用户偏好（如语言、时区、分页大小）时，审查者应主动 `grep` 扫描该配置 key 在 `templates/`、`sse/`、`logs/`、`emails/` 中的使用，不能只看后端服务。
- **“防御性初始化”不等于“防御性使用”**：在 worker 顶部初始化 `output_language = None` 只是避免 `NameError`，但如果后续调用 `get_user_dynamic_config` 失败返回 `None` 且没有降级，仍然会引发 `TypeError`。审查时应要求显式降级逻辑。

### 对特定技术/模式的审查经验
- **`monkeypatch` + 异步缓存模式**：该仓库已出现至少两次（本次 + 历史记忆中的动态配置测试），建议团队统一封装 `pytest.fixture(scope="function")` 自动清理所有用户配置缓存，避免每个测试手动调用 `invalidate`。
- **`output_language` 的全局影响**：该字段可能被用于构建 prompt、解析 review 结果、翻译 UI 消息。任何一处未支持用户值都会导致体验割裂。建议后续重构为 `LanguageContext` 中间件，而非逐函数传递。
