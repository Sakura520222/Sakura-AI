- **配置系统的三层结构**：`UserConfigValue` → `user_config.py`（业务逻辑）→ `schemas.py`（API 契约），对称性良好。

## 4. 经验教训

### 值得关注的要点
- **版本检测与运行时 fallback 的脱节**：这是本次最值得记录的经验。仅仅检测并记录警告不够，应设计一个统一的能力矩阵（如 `supports_getdel` 返回 bool，`getdel_with_fallback` 封装），由调用方根据标志位选择路径。
- **增量审查中“历史未解决问题”的升温机制**：本轮的 `datetime.utcnow` 已经连续多轮标记为未处理，按规范应升级为阻断或自动生成 issue。审查未执行升温，是个流程疏漏。
- **测试重复代码识别**：`FakeLogger` 重复定义在同一个文件的两个测试函数中，说明审查者对 DRY 原则敏感，但提取为 fixture 会更好。

### 对特定技术的审查经验
- **Redis 命令兼容性**：类似 GETDEL 这类低版本不支持的命令，应要求：
  1. 版本检测（本 PR ✅）
  2. 运行时 fallback 路径（本 PR ❌ 缺失）
  3. 集成测试覆盖低版本环境（本 PR ❌ 缺失，仅单元测试）
- **联合类型与空值语义**：`UserConfigValue = str | int | bool | None` 中，`None` 表示“删除覆盖”，需确保所有读取该配置的代码将 `None` 等价于“使用全局默认值”。本次审查检查了 `user_config.py` 的 `if raw_value is None`，但未扫描所有调用 `get_user_config` 的地方。
