# 深度反思 — PR #415 增量审查 (1deb347)

## 1. 审查质量评估

**覆盖度：基本充分，但存在规则自违反的盲区。**

源码仅 +9/-6，测试新增 5 个用例覆盖了截断优先级、空输入、无边缘、OMITTED 污染、HTML 实体还原——对 `_parse_previous_graph` 的边界场景覆盖合理。等价性验证也正确指出了旧代码遍历 edge 对天然只触达端点、新代码用 `endpoints` 集合显式表达同一语义。

**但有一个明显的规则违反未被发现：**

项目记忆明确规定了 **"quick 策略评分上限 8/10，除非显式执行完整检查点并声明"**。本次审查策略为 `quick`，给出了 **9/10**，而审查摘要中 **没有** "显式执行完整检查点" 的声明。这是一个审查输出自身的合规性缺陷——审查者在评估代码是否遵守规则时，忽略了审查输出本身是否遵守项目记忆规则。

**准确度：合理。** 前序两个问题（minor + suggestion）严重程度标注恰当，修复确认无误。

**完整性：有一个模糊点。** PR 描述中还提到"增加历史记录保留功能，确保依赖图的变更轨迹得以完整保存"，但本次增量 diff 并未体现该功能。审查摘要中"PR 描述-增量一致性"仅校验了与本次 diff 直接匹配的两条声明（+9/-6 和 +68 行测试），对第三条声明未做任何说明。作为增量审查这可以理解为"非本次提交范围"，但应在摘要中显式标注"剩余 PR 描述项不在本次增量范围内"以保持完整性。

## 2. 发现的模式

- **确定性重构模式**：将无序容器（`set`）替换为有序容器（`dict.values()`）以稳定截断行为，同时用显式过滤（`endpoints`）替代隐式语义（遍历 edge 对天然只触达端点）——这是提升代码可读性和确定性的典型手法。
- **测试驱动修复模式**：两个前序问题均通过补充测试用例修复，而非仅改源码，符合"测试先行验证"的良好实践。
- **边界条件系统化覆盖**：5 个测试用例分别对应空输入、无边缘、OMITTED 标记、HTML 实体、截断优先级——呈现了按"解析器可能遇到的异常输入"系统化枚举测试场景的模式。

## 3. 规范完善建议

**新增规则：审查输出自身合规性自检**
> 审查输出生成后，须回扫项目记忆中的硬性约束（如策略评分上限、决策与严重程度绑定等），确认输出本身未违反。建议在审查流程末尾增加一个"输出合规性检查"步骤。

**修改规则：增量审查中 PR 描述一致性校验须声明范围边界**
> 当前规则"PR 描述与 diff 一致性强制校验"在增量审查场景下需要补充：若 PR 描述包含不属于本次增量的声明项，须在摘要中显式列出并标注"不在本次增量范围内，待后续提交覆盖"，不能静默跳过。

## 4. 经验教训

- **规则自违反是最高优先级的反思项。** 审查系统的元规则（评分上限、决策绑定）比被审查代码的规则更难被自身检测到，因为审查注意力集中在代码而非输出格式上。未来应在反思阶段首先回扫"本次审查输出是否违反了项目记忆中的硬约束"。
- **"无评论"不等于"无遗漏"。** 本次主要评论为空，结合 9 分高分，容易产生"完美通过"的错觉。实际上存在评分违规和描述一致性边界未声明两个问题——高评分场景下更应警惕"正面评价越多越先做负面检查"这一已有原则的执行力度。
- **等价性验证应标注验证方式。** 本次声明了"行为一致"，但未说明是仅通过代码逻辑推导还是也运行了对比测试。对于确定性相关的重构，建议在审查中标注验证方式（静态推导 / 测试对比 / 两者兼有）。
