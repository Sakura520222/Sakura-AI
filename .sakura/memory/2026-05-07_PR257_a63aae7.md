## 2. 发现的模式

### 代码模式
- **防御性检查点扩散**：在多阶段任务中多次调用 `_check_cancelled`，但清理逻辑未复用，导致重复代码。应抽取 `_handle_cancellation` 方法统一处理。
- **静态方法用于工具函数**：`_make_task_key` 为静态方法但在多处被外部调用，暗示应提升为模块级函数。
- **延迟导入无注释**：项目中已有规范要求注释循环引用原因，但仍有遗漏，说明自动化检查（lint）缺失。

### 架构观察
- **Webhook + Worker 分离**：webhook 做轻量去重和快速响应，Worker 做重量级任务 —— 符合“前置+兜底”模式（项目记忆已记录）。
- **取消信号设计**：使用 `asyncio.Event` + 任务注册表，是典型的手动取消模式，但缺少超时自动取消机制。
- **单例 Worker 生命周期**：在模块加载时初始化，与 FastAPI 应用生命周期绑定，缺乏优雅关闭时的任务等待逻辑。

## 3. 规范完善建议

### 新增/修改审查规则

| 规则 | 建议 |
|------|------|
| **取消路径资源清理一致性** | 凡有多处取消检查点，必须抽取公共清理函数，避免部分路径遗留状态。标 major |
| **状态枚举变更的兼容性审查** | 新增枚举值必须检查：① 数据库列类型（ENUM/VARCHAR）② 历史数据回填 ③ API/前端过滤器更新。标 major |
| **并发模型注释强制** | 实例级可变状态用于 async 单例时，必须注释“依赖 asyncio 单线程事件循环，无竞态条件”或“需加锁”。标 minor |
| **延迟导入注释自动化** | 提交前检查脚本应扫描 `import` 语句是否出现在函数体内且无注释，阻断合并。标 suggestion |

### 项目特有规范补充
- **取消操作用户可见性**：PR 关闭自动取消审查时，应在数据库记录 `cancelled_by = "system"` 或 `cancelled_reason` 字段。
- **幂等性日志分级**：高频取消（如重复 close 事件）应使用 debug 级别，避免日志洪水。

## 4. 经验教训

### 未来审查关注要点
- **状态机的完整性**：当引入新状态（CANCELLED），必须审查所有状态转换路径（created → running → cancelled/failed/success）是否覆盖，以及状态回退是否允许。
- **多检查点的行为收敛**：对于多阶段长任务，建议统一使用装饰器或上下文管理器自动处理取消检查及清理。
- **Event loop 绑定风险**：任何存储 `asyncio.Event` 的单例，若可能跨越不同的 event loop（如测试框架重置 loop），需重建 Event。

### 对特定技术的审查经验
- **asyncio 取消模式**：`Event` 适合“信号通知”，但不支持“等待并附带额外数据”（如取消原因）。若需传递信息，改用 `asyncio.Queue` 或 `Future`。
- **SQLAlchemy 异步 session**：在取消路径中更新数据库状态前，应检查当前 session 是否已因异常而无效，必要时关闭重建。
