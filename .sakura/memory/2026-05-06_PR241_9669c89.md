## 2. 发现的模式

### 代码模式
- **Tailwind 工具类硬编码 CSS 覆盖**：在 `base.html` 中使用基于 Tailwind 类名的复杂选择器（如 `.bg-white.dark\:bg-gray-800`）是**脆弱的临时方案**，项目记忆中也强调过类似模式（注释引用存在性、脆弱选择器）。
- **Jinja2 模板中的逻辑重复**：侧边栏激活类名重复 14 次，符合“两处可容忍，第三处须提取”的经验阈值。
- **无障碍渐进增强**：添加 `prefers-reduced-motion` 和 `aria-hidden`，说明开发者有一定无障碍意识，但 `register.html` 遗漏暴露出**同步维护隐患**。

### 架构观察
- **前后端样式职责模糊**：`login.html` 和 `register.html` 不继承 `base.html` 却复制了完整主题 CSS，说明缺乏**轻量级基础模板**或 **CSS 片段复用机制**。
- **全局样式覆盖的过渡策略**：使用 `main > div > .bg-white...` 覆盖旧卡片，表明项目处于**渐进式重构阶段**，尚未完成全量组件化。这种模式在项目记忆中被标记为“死代码保留须注释”的反例。

## 4. 经验教训

### 未来审查中值得关注的要点
1. **验证 PR 描述中的每一条声明**：特别是“添加樱花飘落动画”这类可见特性，必须确认动画 DOM 元素存在、CSS 类已定义、无拼写错误。
2. **主动检查无障碍一致性的传播**：如果一个页面有 `prefers-reduced-motion`，同类型页面（如 login/register）必须同步检查。
3. **动画性能的快速评估**：大量绝对定位 + `animation: fall 线性无限循环` 可能导致 GPU 图层暴涨，建议未来标注“若页面滚动掉帧，需优化”。
4. **色彩语义的一致性审计**：危险操作用红色、成功用绿色、警告用黄色是跨文化通用预期，偏离时需要强理由。

### 对特定技术的审查经验
- **Tailwind + 自定义 CSS 覆盖**：优先推荐使用 `@apply` 在 CSS 中组合工具类，而不是写基于类名的选择器覆盖。后者在 Tree-shaking 或类名变更时极易失效。
- **Jinja2 模板中的样式共享**：对于 login/register 这种不继承 base 的独立页面，建议统一使用 `{% include "partials/_theme_styles.html" %}`，避免三处冗余。
- **`backdrop-filter` 的渐进增强**：应同时提供 `background-color` 回退 + `@supports (backdrop-filter: blur())` 条件增强，而不是仅靠浏览器自然回退。
