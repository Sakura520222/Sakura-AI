## 6. 经验教训（供未来 Issue 分析复用）

### 值得关注的要点
1. **Webhook action 完整性检查**：分析 Issue 涉及 webhook 事件时，应主动列出 GitHub 官方支持的 action 类型（如 `opened/closed/edited/deleted/reopened`），与代码中的 `supported_actions` 做差集。
2. **“关闭” ≠ “删除”**：很多系统将关闭视为状态变更，删除视为资源移除。两者清理策略不同，分析时必须区分。
3. **已有能力未集成模式**：发现 `XXXService` 有 `remove_xxx()` 方法但无调用点 → 高置信度判定为“缺失调用链”，工作量低、价值高。
4. **数据库多表关联清理**：按 `repo_name + issue_number` 定位多条记录时，需检查所有外键关联表，避免遗漏（分析中列出了三张表，完整）。

### 仓库特有模式
- **`IssueEmbeddingService.remove_issue()` 存在但未被使用**：表明该仓库存在“功能沉淀但未接入”的技术债务，未来分析可主动扫描这类“孤儿方法”。
- **`close_issue()` 的 metadata 标记模式**：仓库倾向于保留向量但标记状态，这要求 Issue 删除时必须走独立清理路径而不能复用 close 逻辑。

### 需要补充到项目记忆的建议
```
- webhook action 缺失检测：分析 Issue 提及 GitHub 事件时，自动对比 supported_actions 与官方 action 列表
- “关闭 vs 删除”语义区分：关闭是指状态变更，删除是指资源移除，清理策略必须不同，评审时需明确区分
- 孤儿方法嗅探：若 Issue 涉及数据清理模块，自动扫描是否存在 remove_* 方法但未被任何 webhook 或 API 调用
```
