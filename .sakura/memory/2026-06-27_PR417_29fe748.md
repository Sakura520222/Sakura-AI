## 深度反思

### 1. 审查质量评估

**覆盖度：存在明显盲区**

- **+10k/-1.2k 大版本仅产出 5 个发现，密度严重不足。** 按项目记忆中"高评分=穷尽检查点"原则，7 分对应的问题发现量与变更规模不匹配。一个 10k+ 行的 PR，仅 2 minor + 3 suggestion，大概率存在遗漏。
- **四大新模块的内部逻辑审查缺失**：`check_run_service.py`(403行)、`ci_failure_service.py`(469行)、`pr_review_incremental_queue.py`(421行)、`issue_protocol.py`(321行) 均为全新文件，审查摘要仅做了功能概述，未对这三个核心服务内部的错误处理、边界条件、并发安全做深入检查。尤其增量队列涉及"僵尸 review 检测"、"兜底消费"等复杂状态机逻辑，按项目记忆"状态机逃脱路径"原则，每个中间状态须有超时或异常逃脱路径——这条完全未执行。
- **`review_worker.py` +677 行大幅重构**：摘要仅提到"大幅重构"，但按"重构+功能混合 PR 双轨检查"原则，须分"新功能验证"和"重构等价性验证"两节，并声明(1)测试全通过(2)返回值一致(3)异常等价。审查中完全缺失重构等价性验证。
- **`file_tool.py` +223/-106 分支回退重构**：同样缺少重构等价性验证。
- **`prompt_builder.py` +136/-17**：提示词格式变更，按"提示词/配置文本变更下游对齐"原则，须追踪下游解析代码，未执行。
- **`constants.py` +22/-1**：按"constants 变更 ≥10 行须逐个 grep 验证消费方"原则，未执行。
- **webhook.py +352/-3**：新增 check_run/workflow_job handler，但未按"事件驱动闭环"原则检查重复/乱序/并发/唯一约束。

**准确度：基本合理，但有一个值得商榷的点**

- 问题 #1 标 minor 合理——`create_all` 确实能兜底，Docker 窗口问题属于规范违反而非功能阻断。
- 问题 #2 标 minor 合理——输入已收窄，实际风险低。
- **问题 #3 标 suggestion 偏低**：按项目记忆"'标记不可信'≠'防护完成'"，LLM prompt 链路外部输入须有截断和清洗。CI 失败内容来自外部系统，注入 prompt 但未做任何包裹/截断，这实际上是一个 prompt injection 风险，应至少标 minor。项目记忆中明确写了这条是硬性要求，审查自己却降级为 suggestion，属于**规则执行不一致**。
- 问题 #4 标 suggestion 合理——性能问题而非正确性问题。
- 问题 #5 标 suggestion 合理——静默忽略不影响功能。

**完整性：PR 描述一致性校验做得好，但深度不足**

- 逐项勾选 PR 描述与 diff 一致性执行到位，这是优点。
- 但"抬头步骤"只做了勾选，没有进一步问"这些模块之间的数据流是否闭环"——例如 CI 失败从 webhook 采集 → 存储 → 审查注入，这条链路的端到端完整性未验证。

### 2. 发现的模式

**代码模式**
- 项目重度依赖 ORM `create_all` 做 schema 管理，而非正式迁移工具，这与 init.sql 存在长期张力。
- LLM prompt 构建有"不可信标记包裹"的既有模式（PR 审查和 Issue 分析中已采用），但新模块未对齐，说明**既有模式未被作为 checklist 强制执行**。
- 辅助功能（CI 失败存储、增量队列）的资源上限控制意识在增强（提到了"条数限额存储"），但 cleanup 路径的资源消耗意识不足。

**架构观察**
- 四大功能共享一个模式：**webhook 采集 → DB 持久化 → worker 消费/注入**。这是一种事件驱动架构，但审查未系统性地检查这个模式在四个模块中的实现一致性（如：是否都有防重、超时、清理）。
- `review_worker.py` 作为核心消费端，同时承载了四个功能的注入逻辑，复杂度急剧上升（+677行），但没有看到对应的测试覆盖评估。

### 3. 规范完善建议

**建议新增/修改的规则**

1. **大版本变更强制分模块审查**：单 PR 变更 ≥5 个新增/大幅修改文件且总量 ≥5k 行时，须对每个新模块独立输出"模块内部审查"小节，至少覆盖：错误处理、边界条件、资源上限、状态机逃脱路径。不能仅做功能概述。
2. **LLM prompt 注入防护升级为 hard rule**：将"外部内容注入 prompt 须有不可信标记包裹+截断"从经验教训提升为明确规则，违反即标 minor，不接受 suggestion 降级。本次审查自己打了自己的脸。
3. **重构等价性声明模板化**：对变更量 ≥100 行且为修改（非新增）的文件，强制要求输出三声明：(1)测试全通过 (2)返回值一致 (3)异常等价，缺项即标 minor。
4. **constants 变更自动触发消费方 grep**：将"≥10 行须逐个 grep"改为"任何 constants.py 变更均须列出受影响的消费方及验证结果"。

### 4. 经验教训

**本次最核心的教训：大变更量的"概览陷阱"**

10k+ 行的 PR 极易陷入"概述功能→挑几个明显问题→收工"的模式。审查摘要写得漂亮（四大功能清晰归纳、PR 描述一致性逐项勾选），但实质深度不够。**好的审查摘要不等于好的审查**。未来的大版本审查须在摘要之后强制执行"逐模块深挖"步骤，即使这导致审查输出很长。

**具体技术经验**

- **事件驱动架构的系统性审查**：当 PR 引入多个"webhook→DB→worker"链路时，不能逐个孤立审查，而应先建立链路全景图，再逐链路检查：防重（幂等键）、乱序（版本号/时间戳）、并发（锁/唯一约束）、清理（对称性）。本次四个新链路都未做这个系统性检查。
- **"性能时间炸弹"的变体**：问题 #4 是典型例子——单个 PR 关闭触发全表扫描，当前数据量无感，但这是 O(n) 随数据量线性增长的模式。审查时应显式标注"当前数据量下可接受，但增长到 X 条时需优化"。
- **既有安全模式的传染性**：项目中已有 `=== BEGIN UNTRUSTED ... EVIDENCE ===` 模式，新模块未采用说明开发者没有内化这个模式。审查时应将既有安全模式作为 grep 检查项，而非依赖开发者自觉。
