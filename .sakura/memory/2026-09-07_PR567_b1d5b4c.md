## 1. 审查质量评估  

### 覆盖度  
- **安全层面**：审查已指出 sandbox 套接字的符号链接检查、公告 HTML 的全量转义、日志脱敏等关键防护，基本覆盖了新引入的攻击面。  
- **并发可靠性**：对 CAS Claim 租约、心跳机制以及多 DB 方言的阅读状态适配都有关注，覆盖了高并发场景。  
- **配置/依赖**：对 `.venv/local` 与 `.venv/sandbox` 的隔离、uv.lock 的使用以及 Docker 镜像标签的固定都有检查，基本覆盖了环境一致性风险。  
- **遗漏点**：  
  1. **跨服务 API 兼容性**：新增的 `announcements`、`identity`、`sandbox_client` 等 API 与旧版客户端的兼容性未做显式验证（如旧版前端调用是否会因字段缺失报 500）。  
  2. **异常链路**：虽然提到了脱敏，但未检查所有 `except Exception` 的捕获位置，仍可能出现黑盒异常泄露。  
  3. **CI 质量**：新增的两个 workflow（sandbox‑publish、sandbox‑quality）未验证是否存在 **checkout** 步骤、是否对 `permissions` 做最小化声明。  

### 准确度  
- **严重程度标记**：审查把所有新功能归为“无评论”，直接给 10/10 的最高分，显得过于宽容。按照核心审查原则，**全量重审** 中即便没有明显缺陷，也应给出 **“建议‑minor”**（如文档同步、兼容性测试）以提示后续关注。  
- **误判风险**：对 “无评论” 的结论缺少验证依据（如搜索关键字、运行 CI 链路），违反了“无评论须附验证说明”的原则，存在误判的潜在风险。  

### 完整性  
- **变更意图**：审查对功能点（公告中心、沙箱 runner、依赖 venv、身份统一）都有概括性描述，基本把握了 PR 的宏观目标。  
- **上下文缺失**：未检查 **迁移脚本**（如 `telegram_users` 数据迁移）的幂等性、回滚机制，也未验证 **旧数据** 在新结构下的兼容路径。  
- **全局影响**：未对 **数据库 schema** 的变更（新增字段、唯一约束）进行全库引用搜索，可能导致未捕获的 `KeyError` 或冲突。

## 2. 发现的模式  

### 代码模式  
| 模式 | 说明 | 潜在风险 |
|------|------|----------|
| **统一 Upsert + CAS** | 多处使用原子 Upsert（如公告投递）配合 CAS Claim 租约 | 若租约失效未及时回收，可能导致“僵尸租约”导致资源泄漏 |
| **多渠道投递抽象** | 通过统一的 `NotificationEndpoint` 抽象 Telegram、SMTP、WebUI | 各渠道实现细节（SMTP 认证、Telegram Bot token）如果未统一脱敏，日志中仍可能泄露敏感信息 |
| **Unix Domain Socket (UDS) 交互** | `sandboxd` 使用独立 UDS 进行进程间通信 | 若 UDS 文件权限设置不当，可能被本地非特权用户劫持 |
| **双向 venv 隔离** | `.venv/local` 与 `.venv/sandbox` 分离，防止依赖泄漏 | 依赖同步脚本若未对两端版本锁定，可能出现 “依赖漂移” 导致运行时错误 |
| **大量 workflow 复用** | 多个 CI workflow 采用相同模板，修改频繁 | 任何模板错误会在所有 workflow 中传播，需对模板本身进行独立审查 |

### 架构观察  
- **模块解耦**：`identity`、`announcement`、`sandbox` 各自拥有独立的 API、模型、服务层，契约清晰。  
- **依赖链深**：从 `backend/services/agent_team/execution.py` 到 `sandboxer/src/...` 再到 CI workflow，形成 **跨语言（Python、Node、Go、Rust）** 的执行链路，调试难度大。  
- **配置中心**：大量配置（网络策略、邮件 SMTP、Telegram）集中在 `backend/core/config.py`，但缺少 **层级校验**（如 `offline` 与 `full_access` 的互斥检查）。  
- **日志桥接**：`backend/core/logging_bridge.py` 负责统一日志，但未看到对 **结构化日志**（JSON）强制输出的约束，影响后续监控和审计。

## 3. 规范完善建议  

### 新增/修改审查规则  

| 规则 | 适用范围 | 关键检查点 |
|------|----------|------------|
| **全量审查必须提供验证依据** | 手动全量重审 | 每一条 “无问题” 结论后需附上搜索命令、CI 链路或运行时验证截图 |
| **新增 API 必须提供兼容性测试** | API 增删改 | 检查 `tests/` 中是否有旧版客户端调用的回归测试；若没有，标记为 `minor` |
| **跨语言进程通信安全检查** | UDS、Docker、OCI | 验证 socket 文件权限、容器用户映射、`--cap-drop` 参数是否在 workflow 中声明 |
| **配置键删除全库引用搜索** | 配置变更 | 自动运行 `grep -R "CONFIG_KEY" -n .` 并列出所有引用，确保无遗漏 |
| **异常捕获粒度强制** | 代码质量 | 禁止 `except Exception`，若出现必须在审查报告中标记为 `error` |
| **Workflow 权限最小化** | CI/CD | 每个 job 必须显式声明 `permissions: read-all` 或更细粒度，且不能使用 `write-all` 除非必要 |
| **文档-实现双向校验** | 文档更新 | 对每一段功能描述，审查员需在代码中定位对应实现（函数/类），否则标记为 `suggestion` |
| **迁移脚本幂等性检查** | 数据迁移 | 检查迁移脚本是否包含 `IF NOT EXISTS` 或唯一约束判断，防止二次运行导致冲突 |
| **多渠道通知脱敏审计** | 安全 | 确认所有邮件/Telegram 发送日志在 `logging_bridge` 中已经脱敏，若未脱敏标记 `error` |
| **CI 质量 Gate 强制阻断** | CI | 任意 `failure`（包括 `warning`）必须在 PR 中提供对应 run 链接并标记为 `error`，否则阻断合并 |

### 项目特有的规范要点  

1. **Announcement 生命周期状态**：必须在数据库 schema 中为每个状态（draft/published/archived/withdrawn）添加 **唯一索引**，防止状态冲突。审查时检查对应迁移文件。  
2. **Sandbox 镜像 digest 锁定**：所有 `docker pull` 必须使用 `@sha256:` 固定 digest，且在 `sandbox-publish.yml` 中做 **digest 校验** 步骤。  
3. **双向 venv 清理**：在 `backend/core/setup_service.py` 中加入 **post‑shutdown hook**，确保 `.venv/sandbox` 在容器退出时被彻底删除。  
4. **网络策略互斥**：`offline`、`web_tools`、`full_access` 三种策略必须在 `config.py` 中实现 **互斥校验**（如 `assert not (offline and full_access)`），审查时检查是否存在此类校验。

## 4. 经验教训  

| 教训 | 说明 | 后续关注点 |
|------|------|------------|
| **“无评论”不等于“无风险”** | 本次审查直接给出 10/10，缺乏验证依据。 | 任何全量审查必须留下 **审查痕迹**（搜索、运行日志）。 |
| **增量审查的盲点** | 只看增量会忽略全局依赖（如全局配置键、数据库迁移）。 | 在每次增量审查后自动触发 **全库搜索** 检查。 |
| **跨语言安全链路易被遗漏** | 沙箱 runner 涉及多语言容器，安全检查集中在 Python 端。 | 引入 **跨语言安全审计清单**（容器用户、文件系统挂载、网络隔离）。 |
| **CI 工作流的权限泄露** | 新增 workflow 未明确 `permissions`，可能导致 token 泄露。 | 在代码审查阶段使用 **lint‑action‑permissions** 检查所有 workflow。 |
| **文档更新的同步成本** | 大幅度 README/AGENTS 更新，若忘记同步到 `docs/` 目录会产生不一致。 | 建立 **文档同步检查脚本**，在 CI 中对比 `README*` 与 `docs/` 内容。 |
| **异常脱敏不够细粒** | 只提到“日志脱敏”，未检查具体实现。 | 强制在每个 `except` 块中使用统一的 **sanitize_error** 函数，并在审查时搜索 `sanitize_error(`。 |

## 5. 手动全量重审反思  

- **增量审查遗漏**：此前的增量审查主要关注 **代码行数** 与 **单文件 lint**，未触及 **跨模块依赖**（如 `identity` 与 `announcement` 的外键关系）和 **数据库迁移** 的幂等性。全量审查首次捕捉到这些潜在风险。  
- **全量审查价值**：通过一次性审视 **所有工作流、配置、模型**，能够发现 **全局安全策略**（如 UDS 权限、Docker 镜像 digest）未在增量审查中出现的缺口。  
- **改进方向**：在每次大版本发布前，强制执行 **全量审查**，并在审查报告中明确列出 **“本次全量审查新发现的风险点”**，与增量审查报告形成对照，确保历史遗漏得到闭环。

### 小结  

本次全量重审整体把握了宏观功能创新，但在 **细节验证、异常脱敏、CI 权限、跨版本兼容性** 等方面仍有提升空间。通过引入上述审查规则、加强验证依据、强化跨语言安全检查，可显著提升审查的 **覆盖度、准确度和可追溯性**，降低后续回滚与安全事故的风险。
