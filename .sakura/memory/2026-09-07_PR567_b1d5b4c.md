## 2️⃣ 发现的模式  

### 代码层面  
| 观察点 | 具体表现 | 潜在风险 |

| **模块化拆分** | 多个 `backend/api/v1/*` 按功能拆分（`announcements`, `auth`, `users`, `webhook`），但 **`__init__.py`** 里仅做了空导入，缺少统一导出列表。 | 可能导致 **循环依赖** 或 **未显式暴露的内部实现** 被误用。 |

| **热重载** | `backend/core/hot_reload.py` 大幅改动，加入了异常捕获并尝试 **重启进程**。 | 若重启策略不够保守，可能引起 **无限重启循环**。 |

### 架构层面  
- **工作流驱动的发布链**：`release-on-pr-merge.yml`、`docker-edge.yml` 等工作流相互调用，形成 **可复用工作流图**。但 **权限声明**（`permissions`）未统一，容易出现 **最小权限原则** 被破坏。  
- **Agent 沙箱与主服务解耦**：沙箱运行器抽离为独立镜像，业务层通过 `sandbox_client.py` 进行 RPC 调用。此设计提升安全性，但也引入 **跨容器网络、卷挂载** 的新攻击面，需要 **网络策略**、**文件系统只读** 的硬化措施。  
- **配置中心统一**：大量配置集中在 `backend/core/config.py`，但 **新增配置**（如 sandbox 相关）未在 **文档** 中声明默认值与可选范围。

## 3️⃣ 规范完善建议  

### 规则层面（可加入审查系统）  
1. **解析失败强制阻断**  
   - 当 AI/工具返回 “非 SAKURA_REVIEW envelope” 或解析错误时，自动标记 PR 为 **`error`**，并阻止合并，要求人工复核。  
2. **新增/删除工作流必须审查 `permissions`**  
   - 检查是否出现 **权限降级**（如 `contents: read` → `none`）或 **权限提升**（未在 repo‑level 保护中声明），并强制提供 **权限变更说明**。  
3. **依赖升级兼容性检查**  
   - 对所有 `requirements` 中的 **major/minor** 版本升级，自动拉取对应 **CHANGELOG**，生成 **Breaking‑Changes checklist**，必须全部勾选通过。  
4. **配置键全库引用搜索**  
   - 每次 `config.py` 中新增或删除键，审查工具需执行全仓库 `grep -R "KEY_NAME"`，列出所有引用并标记 **是否受影响**。  
5. **异常捕获粒度强制**  
   - 禁止 `except Exception`，要求显式捕获 `ValueError、KeyError、HTTPException` 等，并在每个 `except` 块添加 **错误分类注释**（`# USER_INPUT_ERROR` / `# INTERNAL_ERROR`）。  
6. **日志脱敏规则**  
   - 检测 `logging.*` 调用中是否直接打印变量名为 `token、secret、password`，若检测到则标记为 **`minor`** 并要求使用 **脱敏函数**。  
7. **镜像标签固定化**  
   - 所有 `docker build`、`docker pull` 步骤必须使用 **完整标签**（如 `python:3.12.4-slim`），禁止 `latest`、`<branch>`。  
8. **沙箱安全检查**  
   - 对任何涉及 `docker run` 的工作流，必须检测以下参数是否显式配置：`--cap-drop ALL`、`--read-only`、`--network none`（或受控网络），并强制提供 **安全评审报告**。  

### 项目特有的规范要点  
- **公告中心 API**：在 `backend/api/v1/announcements.py` 中新增的 CRUD 接口必须在 **`schemas.py`** 中定义 **完整的 Pydantic 验证**，并在 **`tests/`** 中提供 **权限校验**、**分页**、**软删** 场景的测试。  
- **多模态图像压缩**：涉及 `pillow`、`opencv` 的压缩逻辑必须在 **`tests/`** 中加入 **大文件、异常文件**（如损坏的 JPEG）路径，确保 **fail‑closed**。  
- **Agent 沙箱 Runner**：所有调用 `sakura-ai-agent-runner` 的代码必须使用 **统一的 `SandboxClient`**，并在该类中实现 **超时、返回码校验、日志捕获**，审查时确保 **每个调用都有对应的单元测试**。  
- **热重载**：`hot_reload.py` 中的重启逻辑必须提供 **幂等性保证**（如使用文件锁），并在 **CI** 中加入 **重启失败的模拟** 测试。

## 4️⃣ 经验教训  

| 教训 | 说明 | 后续行动 |
|------|------|----------|
| **工具失效不能等同于“无风险”** | 本次审查因为 envelope 解析错误直接返回空结果，导致严重漏报。 | 在审查管线中加入 **“解析失败 → 自动阻断”** 的安全阈值；同时在 PR 页面显式提示 “AI 审查失败，请人工复核”。 |
| **大规模改动必须配套全库影响分析** | 53 k 行改动涉及 API、CI、依赖、配置，单纯增量审查无法发现隐藏的跨模块引用。 | 为 **每一次大版本发布**（如 `v3.2.0`）强制执行 **全库引用图谱**（使用 `pydeps`、`grep`、`git grep`）并输出报告。 |
| **文档/代码同步是必检点** | `README` 中的升级说明与实际代码（`__version__`）保持一致，但未检查 **迁移脚本** 与 **数据库 schema** 是否同步。 | 引入 **文档-代码双向验证** 检查：文档中出现的关键字段、API 路径必须在代码中有对应实现或测试。 |
| **依赖升级是安全风险的高发点** | 本次升级了 `starlette`、`asyncmy`、`stripe` 等，未见兼容层或回退方案。 | 在每次 **依赖升级 PR** 中加入 **兼容性测试矩阵**（多 Python 版本、不同 OS），并在审查报告中列出 **已验证的破坏性变更**。 |
| **异常处理与错误分类必须可追溯** | 多处使用宽泛捕获，导致错误日志难以定位。 | 统一 **错误码体系**，在每个 `except` 中使用 **自定义异常类**，并在响应层统一映射到 HTTP 状态码与错误文案。 |
| **CI 工作流的最小权限原则** | 新增工作流未明确 `permissions`，可能导致 **令牌泄露**。 | 为每个工作流模板提供 **权限清单**，审查时强制检查 **是否只授予所需的 `contents`, `packages`, `id-token`**。 |
| **沙箱安全硬化是多层防御** | 迁移到独立镜像后，仍需检查 **文件系统、网络、capabilities** 的完整硬化。 | 在 `sandbox_client` 与 `docker-runtime` 中实现 **安全审计日志**，并在 CI 中跑 **安全基线扫描**（如 `trivy`、`docker bench security`）。 |

### 小结  

本次审查的最大问题是 **“未提供任何实际审查信息”**，这本身已经是一次严重的安全失误。通过上述反思，我们明确了在大幅度功能、架构与依赖升级时，必须：

1. **把工具解析失败当作阻断**，强制人工复核。  
2. **全链路、全库影响分析**，尤其是配置、API、工作流权限。  
3. **细化异常、日志、权限、依赖升级的审查规则**，并在 CI 中自动验证。  
4. **保持文档‑代码同步**，并在审查报告中提供对应的验证证据。  

落实这些改进后，后续的 PR 审查将能够更好地发现风险、避免漏报，并提升项目整体的安全与可维护性。祝审查工作顺利！ 🚀
