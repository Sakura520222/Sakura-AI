### 4. 经验教训与未来关注

1.  **大规模删除 PR 的验证范式**：
    *   删减代码比新增代码更需要警惕 **“暗藏依赖”**（如文档、部署配置、动态反射调用、i18n 资源等）。审查删减类 PR 时，全库静态符号匹配是必选操作，验证思路可固化为：`代码层引用` -> `配置层声明` -> `UI/模板层渲染` -> `i18n 翻译文件` -> `CI/部署环境变量`。
2.  **行为变更（Breaking Change）的判定边界**：
    *   当删除了某项底层功能（如 Telegram MFA 通知）且未直接提供等效替代时，只要文档同步更新 + 新契约测试覆盖 + 符合既定重构蓝图，即可判定为“有意的架构收敛”，无需阻断。
