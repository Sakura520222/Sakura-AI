## 1) 审查质量评估

### 覆盖度
本次只命中了一个 **major**：增量 webhook 预创建 Check Run 与 worker 实际接管的执行标识不一致，导致 GitHub Checks 面板悬挂检查。这个问题抓得比较准，且属于**链路级一致性问题**，不是局部代码瑕疵，确实有阻断合并的理由。

但从变更范围看，这次 PR 影响面非常大：

- `check_run_service.py` 大幅重构
- `review_worker.py` 重构并扩展
- `github_app.py` / `webhook.py` / `database.py` 相关链路变化
- 配置项新增
- 测试大改

因此只发现 1 个 major，**覆盖度上仍偏保守**。尤其这种“重构 + 功能扩展 + 状态机链路调整”的组合，通常还应重点检查：

1. **状态迁移是否完整**
   - queued / in_progress / completed / cancelled 是否都有闭环
2. **并发与幂等**
   - webhook 重复触发、worker 重入、增量 head 切换是否会重复建 run
3. **失败路径**
   - worker 异常退出、check run 创建失败、GitHub API 失败后的回收
4. **测试是否覆盖了新增配置的默认值与边界值**

这些点从审查摘要里看，似乎没有被充分展开。

### 准确度
这个 major 的定性是合理的，原因有两点：

- 它不是“展示问题”，而是**GitHub Checks 状态残留**，会直接影响用户判断 PR 状态
- 问题具有**持续性**：不是一次性误报，而是会留一个挂起检查，造成长期污染

不过可以再更精确一点：  
这个问题更像是 **流程一致性 bug / 资源生命周期管理 bug**，而不是单纯“执行标识不一致”。它的本质是：

> 预创建资源和实际消费资源没有共享同一生命周期归属，导致预创建对象失去被后续路径清理/接管的能力。

这类问题在审查里最好明确归类为 **状态机/资源所有权错误**，便于后续建立通用审查规则。

### 完整性
从审查意见看，已经理解了主链路：  
webhook 预创建 queued Check → worker 处理增量 → worker 用新 id 找不到旧 Check → 重新创建 → 旧 Check 残留。

这说明对上下游关系有一定把握。  
但完整性上仍有两个疑问：

1. **是否确认了所有增量路径都走同样逻辑？**
   - 例如普通 review、增量 review、超时重试是否一致
2. **是否确认了“取消旧 Check”是否存在副作用？**
   - 如果 GitHub API 取消失败，是否有兜底策略
   - worker 接管时是否需要保证同 head 唯一 active Check

也就是说，这次审查指出了“现象”和“修复方向”，但对“全链路一致性约束”还没有完全闭环。

## 2) 发现的模式

### 代码模式
这次 PR 暴露出几个明显模式：

#### 1. 执行标识与业务实体分离，但缺少稳定绑定
`review_job_id`、`PRReview.id`、`ReviewRunKey` 这些对象看似都在表达“同一次审查”，但实际可能不是同一生命周期标识。  
这是典型的“**语义相近但身份不统一**”问题。

建议后续审查重点关注：

- 是否存在多个“看起来像主键”的字段并行使用
- 预创建与实际执行是否使用同一个外部可持久化 ID
- 查找逻辑是否依赖临时 ID，导致跨阶段不可接管

#### 2. 重构后引入“隐式状态转换”
从修改文件看，`check_run_service` 和 `review_worker` 都进行了大幅改动。  
这种改动容易出现：

- 状态切换点变多
- 旧逻辑被拆散
- 某些 cleanup、cancel、finalize 路径被遗漏

这次挂起 Check 就是典型“**创建和完成不是同一路径，回收丢了**”问题。

#### 3. 测试替换幅度很大，但可能存在覆盖断层
`tests/test_check_run_service.py` 改动接近重写，说明测试被大幅调整。  
这种情况下要特别警惕：

- 原有边界测试是否被删掉
- 新增测试是否只验证 happy path
- 是否覆盖 webhook → worker → GitHub Check 的完整链路

---

### 架构观察
这个项目明显是一个 **事件驱动 + 任务 worker + GitHub Checks 状态机** 的架构，核心链路跨越：

- Webhook 接入
- DB 记录
- GitHub App Check Run 创建/更新
- Worker 异步处理
- WebUI 配置影响行为

架构特点是：

1. **跨层状态传递多**
   - 配置、数据库、GitHub 外部状态、worker 内状态都要一致
2. **副作用强**
   - 一次错误可能直接污染 GitHub Checks 面板
3. **链路长**
   - 很容易出现“前面创建了，后面接不上”的问题

所以这类仓库的审查，不能只看单文件逻辑，必须做 **链路级审查** 和 **资源生命周期审查**。

## 3) 规范完善建议

### 建议新增/强化的审查规则

#### 1. 预创建资源必须有接管协议
凡是“先创建、后异步接管”的对象，都必须明确：

- 由谁创建
- 由谁接管
- 用什么稳定 ID 接管
- 接管失败如何清理

可形成规则：

> 预创建的外部资源（Check Run / Job / Ticket）若会被异步 worker 接管，必须使用同一持久化标识，或显式设计 cancel + recreate 回收路径。

#### 2. 状态机必须做全路径审查
对于 `queued → in_progress → completed → cancelled/failed` 这类状态机，审查时应强制检查：

- 每个中间态是否有出口
- 异常分支是否能回收
- 重试是否会留下孤儿状态

#### 3. 重构类 PR 强制查“等价性破坏”
本次属于“重构 + 功能增强”，建议规则中明确：

- 如果重构改变了对象身份、查找键、生命周期归属，必须视为功能性变更审查
- 不能仅以“逻辑重组”为由降低风险

#### 4. 增量审查必须核对“同一 head”的唯一性
对于增量 review，建议增加规则：

> 同一 PR head 上是否可能存在多个 active Sakura Check？若存在，必须有明确的回收或覆盖策略。

这条规则能直接命中本次问题。

---

### 项目特有规范建议

1. **Check Run 外部 ID 统一约束**
   - 建议在项目内明确：`external_id`、`review_job_id`、`ReviewRunKey` 之间的映射规则
   - 最好文档化，避免各层各用各的

2. **GitHub Checks 资源生命周期文档化**
   - 哪些 check 允许并行
   - 哪些 check 必须单活跃
   - 哪些场景必须 cancel 旧 check

3. **增量模式必须有回滚/重试测试**
   - webhook 预创建成功，但 worker 启动失败
   - worker 切 head 后旧 check 未取消
   - GitHub API 返回错误时的残留行为

4. **配置项变更要补默认值测试**
   - 新增 Analysis / Findings 配置应验证默认关闭/开启行为
   - 配置页字段变化要验证后端 schema 和前端展示一致

## 4) 经验教训

### 未来审查中要特别关注
1. **“创建”和“完成”是否由同一身份体系贯穿**
   - 这是这类异步系统最容易漏的点

2. **“看似只是重构”时更要查状态机**
   - 状态转移、cleanup、取消逻辑最容易被拆散

3. **外部系统资源要看“遗留物”**
   - GitHub Checks、队列任务、DB 记录都可能残留
   - 不能只看主流程成功

4. **测试改动大时，要反向怀疑覆盖缩水**
   - 测试文件大量替换，不等于覆盖质量提高

### 针对本次 PR 的直接经验
- 这类 PR 最危险的不是业务逻辑本身，而是 **身份、状态、回收** 三者脱节
- 当代码同时动了 webhook、worker、service、模型、配置、测试时，审查应优先做“链路一致性”而不是“局部语法正确性”
- 如果发现一个外部可见 major，通常还应继续追问：  
  **是否还有第二个同类残留？是否所有分支都共享同一接管协议？**

---

## 总结
本次审查对核心问题的识别是准确的，尤其抓到了一个会直接污染 GitHub Checks 面板的链路级 major。  
但从变更规模和重构深度看，审查整体仍偏保守，后续应更主动地检查：

- 状态机闭环
- 外部资源生命周期
- 异步接管的一致性
- 测试是否覆盖失败和重试路径

如果要把这类 PR 审得更稳，下一步最值得补强的不是“更多局部 bug”，而是建立一套 **资源接管/回收/唯一性** 的审查模板。
