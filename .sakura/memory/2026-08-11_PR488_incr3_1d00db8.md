## 深度反思

### 1. 审查质量评估

**覆盖度：存在结构性盲区**

审查摘要声明"29个文件、115处`exc_info=True`主要分布在内部服务/workers中，不直接返回外部响应"，但这个结论缺乏验证链路。内部服务的日志同样可能通过以下路径泄露到外部：
- Worker 的 stderr 被日志收集器（如 Loki/ELK）捕获后，错误信息通过 WebUI 的日志查看面板展示
- 内部服务间的错误响应被上游 API 透传

仅凭"不直接面向客户端"就判定安全，违反了全链路思维。

**准确度：9分存在确认偏误**

触发项目记忆中的明确警告——"高评分PR确认偏误警惕"。本轮完美修复了 major 问题，但第1轮提出的 minor 可用性问题（`ValueError` 路径将安全的用户校验提示如"output_language 仅允许为空、zh-CN 或 en"过度脱敏为通用消息）在本轮**完全未被提及**。修复一个问题的同时沉默地放过另一个问题，9分无法自洽。

**完整性："无评论"的风险未充分对冲**

审查摘要对"无评论"做了范围声明，但缺少一个关键动作：对持续存在的 minor 问题应至少留一条评论标记其状态（如"已知问题，建议作为独立跟进项"），否则等于从审查记录中抹除了该问题的存在。

### 2. 发现的模式

**代码模式：loguru 迁移残留**
项目从标准库 `logging` 迁移到 `loguru` 时，`exc_info=True` 的写法被大量保留。这是典型的"API 表面兼容但语义不同"的陷阱——标准库中 `exc_info=True` 是布尔参数，loguru 中它被解析为格式化字符串的一部分，行为静默退化而非报错。

**架构观察：测试文件责任集中化**
`test_stack_trace_exposure.py` 作为跨端点的集中安全测试文件，三轮中持续膨胀。当前模式可行，但随着覆盖端点增加，维护成本和测试隔离性会恶化。趋势上应考虑各模块自带安全回归测试。

**错误处理分层模糊**
项目缺少明确的错误分类体系：用户输入校验错误（可返回具体提示）、业务逻辑错误（返回业务语义消息）、内部系统错误（必须脱敏）。当前修复将后两类混为一谈，导致可用性牺牲。

### 3. 规范完善建议

**新增规则：**
- **loguru 强制写法**：禁止 `exc_info=True`，统一使用 `logger.exception()`（except 块内）或 `logger.opt(exception=True).error()`（非 except 上下文），纳入 lint 规则
- **脱敏分级强制声明**：每个 `except` 块的对外响应必须注释标注错误类别（`# USER_INPUT_ERROR` / `# INTERNAL_ERROR`），`USER_INPUT_ERROR` 类别禁止使用通用脱敏消息
- **同类问题追踪规则**：当识别出 N 处同类问题时，修复 1 处的增量 PR 必须在 PR 描述或评论中列出剩余 N-1 处的处理计划或明确说明不处理的理由

### 4. 经验教训

- **"修复正确问题"不等于"审查完成"**：本轮精准修复了 major 问题，但审查的职责还包括跟踪之前标记的未解决问题。建议审查时强制回看上一轮的 issue list
- **宽泛 `except Exception` 是精细化错误处理的天然敌人**：一旦用宽泛捕获，后续想对 `ValueError`（用户输入）和 `RuntimeError`（系统错误）做差异化响应就需要额外的 `isinstance` 判断，增加了出错概率。长远应推动在入口层做参数校验，将 `ValueError` 消灭在进入业务逻辑之前
- **测试用例的分支隔离技巧值得复用**：用 `RuntimeError` 而非 `ValueError` 来精确触发 `except Exception` 分支、用合法值 `"en"` 避免误触校验逻辑——这种"精准构造"思维应作为测试编写的标准要求

### 5. 增量审查反思

**问题解决：部分解决**
- ✅ major（`except Exception` 日志替换）：彻底修复，含回归测试
- ❌ minor（`ValueError` 过度脱敏）：未被提及、未被追踪，实质上从审查视野中丢失

**新风险：无**
新增代码逻辑清晰，测试构造精准，未引入新风险。

**覆盖度下降：确认发生**
增量审查导致审查者的注意力锚定在"这个提交是否正确修复了上轮 major 问题"上，产生了隧道视野。上一轮 minor 问题因为不在增量 diff 中，被自动过滤掉。**这是增量审查最典型的失败模式——只验证"改得对不对"，不验证"还差什么"。** 建议：增量审查的 checklist 中必须包含"上轮未解决问题状态确认"这一项。
