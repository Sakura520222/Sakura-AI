## 1. 审查质量评估

### 覆盖度（高，但有遗漏）
- **已覆盖关键点**：MFA 锁定、Passkey 流程、内存回退大小限制、限流配置硬编码、CSRF 缺失、WebAuthn 用户验证不一致、死代码（通知服务未调用）。
- **遗漏的重要问题**：
  - **事务一致性问题**：`finish_authentication` 中 `session.commit()` 失败时，`reset_mfa_failures`（Redis 操作）已执行，会导致“认证失败但 MFA 失败计数被清空”的不一致。报告中虽在“未直接测试但依赖的调用链”表格中列出，但**没有作为 major 问题提出修复建议**，只作为风险观察。这违反项目记忆“事务与外部写入顺序检查”原则。
  - **原子消费的遗留风险**：WebAuthn challenge 虽已原子 pop，但 `finish_authentication` 中异常（如签名验证失败）后没有重新生成 challenge，重试请求会收到已使用的 challenge。应在异常时显式清除客户端存储的 challenge 或返回新 challenge。
  - **限流超时未成对检查**：见下方案例。

### 准确度（基本合理，轻微过严）
- **合理**：`except Exception` 未区分 `AccountLockedError` → major 正确；内存回退无大小限制 → major 正确（符合项目记忆）。
- **轻微过严**：`/passkey/verify-discover` 无 CSRF → 标记为 major，但登录端点在未认证状态下确实无法携带 CSRF token，且与 GitHub OAuth callback 一致。应降为 minor + 强制注释，而非 major 阻断意图。

### 完整性（充分理解意图，但缺少集成风险提示）
- 正确识别了“死代码”问题（通知服务未调用）。
- 但未评估 **Passkey discoverable flow 与现有用户合并/冲突风险**：若用户已在系统中存在，通过 passkey 直接登录是否应要求绑定现有账户？当前实现似乎允许直接登录并创建新会话，未检查账户是否已绑定其他凭据，可能导致账户混淆。

## 2. 发现的模式

### 代码模式
- **“惰性清理 + 无上限”重复出现**：内存回退字典、`_USER_PREFS_CACHE` 等类似结构多次出现无大小限制。反映项目未形成统一的“带上限的 TTL 缓存”工具类。
- **双路径不一致**：API 与 WebUI 限流配置一个硬编码一个读配置，WebUI 新增端点无 CSRF 但原端点有——缺少“新增端点自动套用基类或装饰器”的强制模式。
- **异常后状态的乐观假设**：多处“Redis 操作 → DB 操作”顺序，假设 DB 一定成功，没有补偿逻辑。

### 架构观察
- **配置穿透良好**：新配置都定义在 `config.py`，Pydantic Field 带范围校验。
- **服务层封装较干净**：Redis key 构建、锁逻辑均下沉到 `mfa_lockout_service`。
- **但存在服务间隐式依赖**：`mfa_notification_service` 定义后无人调用，说明缺少“功能启用即调用”的设计评审。

## 3. 规范完善建议

### 新增/强化规则（基于本次审查）

| 规则 | 严重程度 | 说明 |
|------|----------|------|
| **事务外的外部写入必须支持补偿或异步** | major | 先外部存储（Redis）后 DB commit 失败时，必须有补偿回滚或记录异常供重试。 |
| **新增公共功能模块必须至少有一处调用路径（除工具类外）** | major | 防止死代码进入主干。单元测试可 mock，但生产入口必须存在。 |
| **WebAuthn challenge 消费失败后必须失效并重新生成** | major | 避免重放攻击或客户端重试使用过期 challenge。 |
| **所有“公开登录/注册端点”的 CSRF 豁免必须注释安全边界** | minor → major（连续2次） | 已多次要求注释，仍未落实时升级。 |
| **双路径（API/WebUI）新增功能必须对比现有端点的限流/CSRF/错误处理** | major | 本次 API 与 WebUI 的限流不一致。 |

### 项目特有规范点
- **内存降级结构统一工具化**：建议提供 `TTLLRUCache(maxsize=1000, ttl=300)` 类，替换各处手写的 `_lock_fallback`。
- **Passkey 登录账户绑定检查**：discoverable credential 返回的用户 ID 必须与当前会话（如有）或已有账户冲突时提示合并。

## 4. 经验教训

### 未来审查要点
- **“操作顺序”审查优先级提高**：凡修改外部存储（Redis）+ DB，必须画出顺序图，若 DB 可能失败则检查是否有补偿。
- **死代码检测**：新增服务文件时，强制要求 grep 其公开函数在 PR 内是否被调用。本次 `notify_mfa_event` 未被调用本应在首次审查就被阻断。
- **限流 + 超时成对检查**：每个 `@limiter.limit` 处，必须检查该端点内所有外部 I/O（数据库、HTTP、Redis）是否设置了 `timeout` 或 `asyncio.wait_for`。

### 技术/模式审查经验
- **WebAuthn 的安全假设不可信**：`require_user_verification=False` 与 `REQUIRED` 不一致是安全漏洞，但容易被忽略，因为代码分散在 `begin` 和 `finish`。未来应强制要求 `begin` 和 `finish` 的验证要求参数从同一个配置/常量派生。
- **“状态在 options 和 verify 之间变化”的问题通用化**：不限于 MFA 锁定，所有两步验证流程（TOTP、WebAuthn）都应检查中间状态（账户禁用、锁定、凭据删除）并重新抛出对应异常，而不是落入通用 `except Exception`。

## 总结

本次审查质量较高，覆盖了主要安全与规范问题，但在**事务一致性**和**死代码检测**上存在遗漏。审查准确度基本合理，仅 CSRF 标记可降级。基于此，建议补充以下 **major 级别问题**到原审查中：

1. `finish_authentication` 中 DB commit 失败时 Redis 失败计数已被清空 → 需补偿或改为先 DB 后 Redis。
2. `mfa_notification_service` 无调用路径 → 必须添加调用或标记为预留并创建 issue。
3. `/passkey/verify-discover` 应添加 CSRF 豁免注释（安全边界）。

这些未在原始报告中作为 major 提出，应在反思后补充。
