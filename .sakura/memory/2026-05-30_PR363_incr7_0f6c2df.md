## 2. 发现的模式

### 代码模式

本次变更体现了几个项目内常见模式：

1. **使用 loguru，占位符风格为项目规范**

   项目倾向于：

   ```python
   logger.info("message: {}", value)
   ```

   而不是：

   ```python
   logger.info(f"message: {value}")
   ```

   这有利于延迟格式化和日志风格统一。

2. **存在持续清理 lint 问题的提交习惯**

   本次两个提交都偏维护型：

   - 删除 unused import
   - 删除 unused variable
   - 统一日志格式

   说明项目正在逐步响应前轮审查或静态检查反馈。

3. **`event_callback` 异常处理是高频模式**

   历史上下文显示，`reviewer.py` 和 `issue_analyzer.py` 多处存在类似：

   ```python
   try:
       ...
   except Exception:
       ...
   ```

   这类模式容易出现静默吞异常、日志不完整、重复代码等问题。

### 架构观察

1. **后端服务层较厚**

   热点文件包括：

   - `reviewer.py`
   - `issue_analyzer.py`
   - `activity_checkpoint_service.py`
   - `activity.py`

   说明业务逻辑集中在 service 和 route 层，部分文件承担职责较重。

2. **活动监控 / SSE / review / issue analysis 之间耦合较强**

   历史问题中反复出现：

   - activity stream
   - checkpoint
   - event callback
   - tool_calls
   - reviewer / issue analyzer worker

   说明这组模块构成一个跨层链路，增量审查时不能只看单文件。

3. **项目对日志规范有明确偏好，但执行不完全一致**

   本次修复 f-string 日志说明此前已有风格漂移。后续应通过 lint 或自定义规则自动化约束。

## 3. 规范完善建议

### 建议新增审查规则

#### 规则 1：审查决策必须与问题严重程度一致

如果报告中没有 `critical` 或 `major` 问题，默认不得 `request_changes`。

建议规则：

> 当最终决策为 `request_changes` 时，审查报告必须至少包含一个明确、可执行、与本 PR 相关的 blocking/major 问题，并说明阻断原因。

否则应使用：

- `approve`
- `comment`
- `request_changes` 仅用于必须修改的问题

#### 规则 2：PR 描述与实际 diff 严重不一致时必须指出

本次 PR 描述是大型功能，但 diff 是小型清理。

建议规则：

> 审查前必须校验 PR 描述、提交信息、文件变更范围是否一致。若 PR 描述明显描述了不存在的功能，应标记为 minor/major，并要求更新 PR 描述或确认是否提交缺失。

#### 规则 3：历史问题状态更新必须有证据

报告中不能仅凭印象将历史问题标为“已修复”。

建议规则：

> 对历史问题状态标记为“已修复”时，必须提供修复提交、文件位置或重新扫描依据；否则应标为“未在本次增量中验证”。

#### 规则 4：报告摘要不得转化为 review comments

本次“主要评论”中包含大量摘要片段，影响质量。

建议规则：

> 只有具体、可操作、定位明确的问题才能作为 review comment；报告性内容不得拆成 suggestion 评论。

#### 规则 5：loguru 日志格式应纳入自动检查

项目已形成规范：

```python
logger.info("xxx {}", value)
```

建议加入静态检查规则：

- 禁止 `logger.info(f"...")`
- 禁止 `logger.warning(f"...")`
- 禁止 `logger.error(f"...")`
- 允许极少数经过注释说明的例外

## 4. 经验教训

### 经验 1：小 PR 也要检查元信息一致性

即使代码 diff 很小，也不能忽略：

- PR 描述
- commit message
- 关联 issue
- 实际文件变更

本次最大的问题不是代码，而是元信息不一致和审查决策不一致。

### 经验 2：历史遗留问题不能模糊处理

历史问题应分三类：

1. **本次已修复**
2. **本次未涉及**
3. **仍阻断本 PR**

不能把“之前可能修了”直接写成“已修复”。  
也不能把“不在本次范围”同时作为阻断依据，除非该 PR 明确目标就是修复这些问题。

### 经验 3：`request_changes` 是强信号，必须慎用

`request_changes` 会阻塞合并。  
如果审查正文没有明确阻断问题，使用它会降低审查可信度。

本次更合理的决策可能是：

- 若只看增量代码：`approve`
- 若要求修正 PR 描述：`comment` 或 `request_changes`，但必须明确说明“PR 描述与实际变更不一致，需要修正”

### 经验 4：日志风格修复应继续系统化

本次修复了两处 f-string 日志，但类似问题可能仍存在。  
未来应通过 grep 或 lint 全仓扫描，例如：

```bash
grep -R "logger\..*f\"" backend/
```

避免只修局部。

- 决策与实际风险不匹配

## 总结

本次审查对实际代码变更的判断基本正确：三个变更都安全、合理、低风险。

但审查质量存在几个关键问题：

1. **最终 `request_changes` 与正文“无问题”矛盾。**
2. **PR 描述与实际 diff 严重不一致未被指出。**
3. **历史问题状态更新缺少证据，尤其是 `event_callback`。**
4. **主要评论生成质量较差，把报告摘要拆成了 suggestion。**
5. **严重程度体系使用不严谨，`critical: 无` 不应作为评论。**

未来应强化三条规则：

- 决策必须与严重程度一致。
- 历史问题状态必须有代码证据。
- 审查前必须校验 PR 描述、提交和实际 diff 是否一致。
