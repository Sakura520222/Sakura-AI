### 4. 经验教训
- **“白盒补丁”思维**：历史问题清单驱动审查虽高效，但容易使人忽略新增代码的独立风险。未来面对“修复+增量”混合提交，应分两阶段：先逐条消项，再站在新功能视角重新审视全部 diff。
- **日志静默的传染性**：从 `except Exception: return default` 到 `logger.debug`，项目已多次出现“信息被吞”的倾向。审查中发现此类模式后，除建议当前日志升级，还应扫描同文件中其他日志调用，预防同类隐患。
- **置信度字段的边界**：0.0-1.0 截断虽然安全，但未连带考虑负值或 NaN、Inf 等 Python float 特殊值。建议在 clamp 前加入 `math.isfinite` 检查，可作为后续健壮性提升的议题归档。
