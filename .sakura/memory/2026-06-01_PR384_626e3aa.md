### 2. 发现的模式

**代码模式：**
1.  **基于 `asyncio.Lock` 的资源串行化**：项目大量使用模块级或类级 `asyncio.Lock`（如 `_repo_locks`）来保护共享资源（Git 仓库操作）。这是一种常见模式，但审查精准地指出了其**无清理机制的副作用**，这是在异步/长时运行服务中的典型陷阱。
2.  **状态机驱动的任务流程**：任务状态（`WAITING_HUMAN`, `ITERATING` 等）是核心控制信号。代码中显式检查状态并进行转换。这带来了清晰度，但也引入了如 `TOCTOU` 这类状态检查与使用不一致的经典并发问题。
3.  **前端驱动 UI 逻辑后端化**：将 `can_send_prompt` 等判断逻辑从前端硬编码移至后端计算，是增强可控性和准确性的良好模式。审查正确识别并赞扬了这一点。
4.  **防御性路径校验**：`ensure_within_base` + `relative_to` 的双重检查体现了对路径安全的谨慎，虽然审查认为第二重是冗余的，但这反映了**防御性编程**的习惯。

**架构观察：**
1.  **清晰的分层与隔离**：`git_workspace_service`（底层 Git 操作）-> `workspace_service`（工作区路径逻辑）-> `agent_team_worker`（任务编排）-> `routes`（Web 入口），职责划分清晰。多 worktree 设计成功实现了任务间代码隔离。
2.  **“模块级缓存 + 锁” 作为服务组件**：Git 仓库的 clone (`base`) 和锁 (`_repo_locks`) 被设计为模块级单例，服务于所有任务。这提高了效率，但也带来了状态管理（清理）和潜在瓶颈（锁粒度）的长期挑战。
3.  **同步 I/O 与异步框架的融合**：在异步 FastAPI 路由和异步 worker 中，需要处理同步的 Git 命令执行。代码中使用了 `asyncio.to_thread` 包装，符合规范。
4.  **DB 与应用代码的同步演进**：新增 `pr_head_sha` 列和 `PR_REVIEW` 枚举，在模型、`init.sql` 和业务代码中同步更新，体现了良好的变更管理习惯。

### 3. 规范完善建议

基于本次审查，建议考虑以下规范的新增或强调：

1.  **并发安全审查规则**：在审查涉及 **状态机转换、共享内存缓存（如 `_repo_locks`）、或“读取-检查-执行”操作**的变更时，应强制进行并发场景分析。明确要求说明如何保证操作的原子性或幂等性。
2.  **资源生命周期管理规则**：为使用模块级缓存（如 `dict` 存 Lock、对象池）的代码建立规范，要求必须有明确的**清理策略、容量上限说明或使用弱引用**，并在代码注释或审查清单中体现。
3.  **数据库查询效率审查规则**：对于新增或修改的 ORM 查询，特别是涉及 `WHERE` 条件、`JOIN` 或聚合操作时，要求评估是否利用了合适索引，并在必要时建议添加。
4.  **枚举存储策略规范**：明确项目对枚举类型的存储偏好。例如，对于值可能动态增加或需要频繁 `GROUP BY` 的枚举，优先使用 `String` 列而非数据库 `ENUM` 类型，并在项目文档中说明此约定。
5.  **重构建议的标准化输出**：对于识别出的代码重复（如 `process_human_followup_iteration`），建议在审查模板中增加一个“重构建议”字段，明确指出可抽取的公共逻辑和预期收益，便于后续跟进。
