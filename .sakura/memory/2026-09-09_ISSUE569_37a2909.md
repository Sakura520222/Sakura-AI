## 6️⃣ 经验教训 & 后续建议

| 方向 | 关键经验 | 对策 |
|------|----------|------|
| **审查质量 vs 评分** | 高分并不等于低风险，评分模型容易产生“确认偏误”。 | 在评分模型前加入 **风险覆盖检查**（例如必检文件列表、关键路径验证），并对 **9‑10 分** 设置 **强制审查项**。 |
| **跨文件/跨模块推理** | 依赖图是实现跨文件审查的关键，但需要 **增量计算** 防止大 PR 卡顿。 | 使用 **增量缓存**（上一次 PR 的图）+ **拓扑跳数阈值**，仅在变更子图上执行深度搜索。 |
| **高风险场景抽象** | “部署链、双写、回退、并发、状态机” 这些概念在提示词里必须 **结构化**，否则 LLM 可能忽略。 | 为每类场景预定义 **关键词库** 与 **检查清单**，在 Prompt 中以 **列表形式** 注入。 |
| **反证（adversarial pass）成本** | 额外的 LLM 调用会显著提升 token 消耗。 | 将反证设为 **可选**，仅在 **高风险文件**（如 `Dockerfile*、*.yml、*_handler.py`）触发；或采用 **本地规则引擎**（正则/AST）先筛选。 |
| **可观测性** | 新增的审查步骤若不记录，后期难以评估改进效果。 | 在 `activity_observability` 中统一埋点：**调用次数、耗时、覆盖文件数、检测到的风险类别**，并在仪表盘展示趋势。 |
| **回归测试** | 仅靠人工案例难以保证长期有效。 | 基于历史 PR（如 #567）生成 **自动化审查回归套件**，在 CI 中运行审查模型并比对预期评分/标记。 |
| **标签体系统一** | 过多自定义标签会导致检索噪声。 | 维护 **标签字典**（仓库根目录 `LABELS.md`），每次新增标签需在字典中登记并说明使用场景。 |
| **重复检测** | 纯关键字匹配容易漏掉语义相似的 Issue。 | 引入 **向量化相似度**（如 OpenAI embeddings）进行批量比对，阈值可根据历史误报率调优。 |
| **标题规范** | “feat(review): …” 已符合 Conventional Commits，但缺少 **优先级** 信息。 | 若团队采用 **priority‑tag**（如 `[high]`），可在标题中加入，便于看板排序。 |
