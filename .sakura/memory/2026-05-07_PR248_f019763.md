## 深度反思报告

### 一、审查质量评估

**覆盖度：较好，但有遗漏**

本次审查识别了 8 个问题（5 个 major，3 个 minor/suggestion），覆盖了：
- 并发安全（diff_tool 单例）
- 异常健壮性（空值保护、AttributeError）
- 降级策略完整性（files 为空、finally 路径）
- 估算准确性（中文 token）

**遗漏的关键问题：**

1. **`_run_tool_loop` 中的 `messages` 可变性副作用**  
   该方法接收 `messages` 列表并在循环中追加 assistant/tool 消息，调用方（`review_pr_with_tools` 和 `compact` 分支）均依赖此副作用。但若未来引入重试或缓存，可能导致消息列表意外膨胀。  
   **应标记为 major**（符合项目记忆：“工具循环复用中的副作用注释”）。

2. **`PromptTooLongError` 的 `user_message` 未本地化**  
   项目记忆要求“异常类必须提供 user-facing message 属性且支持 i18n”，但本次新增的异常直接使用英文字符串，未接入 i18n 框架。  
   **实际应为 major，审查中未提及**。

3. **`compact_messages` 构建后未验证工具定义是否完整**  
   精简模式移除了 `BASE_TOOLS` 中的 diff 工具，但若后续工具调用需要 diff 数据，会静默失败。  
   **应为 minor**。

**严重度误判：**
- `api_client.py:207-215` 的 token 估算问题标记为 **major 合理**（影响降级决策）。
- `reviewer.py:537-538` 的 finally 路径问题标记为 **major 合理**（可能导致数据残留）。
- `reviewer.py:496` 的 files 为空检查标记为 **major 略高**，因为空 files 时精简模式不变长但增加一次无用调用，不会导致错误，应为 **minor**。

### 二、发现的模式

#### 正面模式
1. **降级梯度设计清晰**：首次超长 → 精简模式（移除 diff + 按需工具）；多轮超长 → 压缩历史，两级降级边界明确。
2. **BadRequestError 关键词识别**：避免将所有 API 错误误判为超长，设计谨慎。
3. **工具定义与业务解耦**：`COMPACT_TOOLS` 独立定义，符合“CONDITIONAL_TOOLS 按需动态添加”的规范建议。

#### 负面模式
1. **可变单例并发污染反复出现**：本次 `diff_tool` 问题与项目记忆中“可变单例并发安全”的教训完全一致，说明团队未形成强制使用上下文管理器的习惯。
2. **异常处理中的用户消息本地化缺失**：多个自定义异常（包括历史中的 `ValidationError`、`AuthError`）均未内置 i18n，是系统性问题。
3. **增量审查中的历史债务忽略**：本次为首次全量审查，但项目记忆中有 124 次反思，其中多次强调“同一模块不得同时提供类方法和模块级函数”——`reviewer.py` 中 `review_pr`（实例方法）和 `review_pr_with_tools`（实例方法）并存但未标记废弃，应清理。

### 三、规范完善建议

| 现有规则 | 建议补充 |
|---------|---------|
| 实例级可变状态用于请求级数据时必须使用上下文管理器 | **增加检查点**：审查时扫描 `__init__` 中的单例 + `set_*` 方法，强制要求实现 `__enter__/__exit__` 或改为每次新建 |
| 异常类必须提供 user-facing message 属性 | **细化**：user_message 必须调用 i18n 函数（如 `_()`），禁止硬编码字符串；审查时抽查新增异常类 |
| 工具循环中的副作用必须注释 | **升级为 major**：若公共方法修改传入的列表/字典参数，必须在 docstring 中用 `⚠️ 副作用：会修改 messages 列表` 明确标注 |
| 降级路径必须有单元测试验证 | **补充场景**：测试必须覆盖“files 为空时的精简模式行为”以及“多轮超长时 finally 清理路径” |

**新增规则建议：**
- **major**：`except Exception` 块中若重新抛出，必须在 `raise` 前记录原始异常堆栈（使用 `logger.exception`），否则标 major。
- **minor**：新增的 `compact_*` 函数必须与原始函数保持相同的参数顺序和默认值，方便后续替换。

### 四、经验教训

#### 值得未来关注的要点
1. **工具调用的幂等性**：当前的 `_run_tool_loop` 不支持重试（若某次 API 调用超时，messages 已被追加，无法回滚）。建议未来引入“快照-重放”机制。
2. **中文环境的 token 估算**：本次使用 `len(content)//4` 是已知缺陷，建议引入 `tiktoken` 并缓存编码器，避免每次调用都重新加载。
3. **并发测试缺失**：项目中没有针对 `AIReviewer` 多实例共享 `diff_tool` 的并发测试，建议添加 `pytest-timeout` + `threading` 模拟交叉污染。

#### 对特定技术的审查经验
- **OpenAI 兼容 API 的健壮性**：不同提供商返回的 `tool_calls` 结构差异大（有的用 `function`，有的用 `function_call`），必须使用 `getattr` + 类型守卫。
- **loguru 占位符迁移陷阱**：本次多处混合 f-string 和 `{}`，审查时应统一扫描文件中的 `logger.` 调用，用正则 `logger\.(debug|info|warning|error)\(f"` 检出遗漏。
- **finally 块的路径覆盖**：在存在 `try-except-else-finally` 时，画出执行路径图（包括异常重抛、return、break），检查每个分支是否都能到达清理代码。
