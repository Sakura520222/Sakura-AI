## 深度反思

### 1. 审查质量评估

**覆盖度：存在一处语义疑点未深挖**

审查摘要称 `omitted_records` 从 `len(rows)` 改为 `len(deduped)` 是"正确反映去重后实际被省略的记录数"——但 `len(deduped)` 语义上是"去重后**保留**的记录数"，而非"被省略的记录数"。如果变量名 `omitted_records` 在此项目上下文中本就指"从全量中筛出用于处理的记录"（即 omitted from full set），那表述没问题；但如果它实际被下游消费为"被丢弃的记录数"，则存在语义错配。**审查在此处接受了表面合理性，未追溯变量名的下游消费语义。**

此外，去重逻辑隐式依赖 SQL 的 `ORDER BY created_at DESC`——如果未来有人将排序改为 ASC，`set` 首次出现保留会悄悄变成"保留最旧记录"。代码中未见注释锚定此耦合关系。

**准确度：合理**
9/10 对应 +15/-6 的小变更、逻辑正确、测试覆盖主路径+边界场景，评分恰当。

**完整性：充分**
正确识别了 PR 描述与增量的范围差异、跨 source 不去重的业务意图、历史问题的延续状态。

### 2. 发现的模式

- **Python 端去重偏好**：本项目倾向于在应用层用 `set` 做去重，而非 SQL 端 `ROW_NUMBER() OVER(PARTITION BY ...)`。对小规模数据合理，但隐含了排序耦合风险。
- **测试命名高描述性**：`test_fetch_dedupes_same_name_keep_latest` 这类命名直接编码了"输入条件+预期行为"，值得肯定。

### 3. 规范完善建议

**新增规则建议：隐式排序-去重耦合须显式注释**

> 当 Python 端去重/取首条逻辑的行为正确性依赖于 SQL 查询的排序顺序时，必须在代码中添加显式注释说明此依赖关系（如 `# 依赖上方 ORDER BY created_at DESC，set 保留首次出现即最新记录`），缺失则标 suggestion。

**补充检查点：变量赋值变更时的语义一致性**

> 当已有变量的赋值来源改变时（如 `omitted_records` 从 `len(rows)` → `len(deduped)`），须快速验证变量名与新赋值的语义是否仍然匹配，或至少确认下游消费方不会因语义漂移而产生误判。

### 4. 经验教训

- **"简单去重"不简单**：`set` + 排序依赖的组合看似 trivial，但排序方向与"保留哪条"的隐式映射是最容易在后续维护中出错的点。审查小变更时不能因"逻辑显而易见"就跳过耦合分析。
- **高分 ≠ 穷尽**：9 分的变更仍有可标注的 suggestion（排序耦合注释、变量语义一致性），高分应该意味着检查点穷尽，而非"没看到大问题就给高分"。

### 5. 增量审查反思

- **前序修复未回验**：`cleanup_expired` 全表扫描在 incr2 声称已修复，本轮标记"未重新验证"。符合增量规则，但存在**信任链累积风险**——如果 incr2 的修复本身有瑕疵，后续增量不会发现。对于 major 级修复，建议在终审时做一次快速回扫。
