**二、发现的模式**

| 类别 | 观察到的模式 |
|------|--------------|
| **代码习惯** | 1. **依赖注入式写法**：在 `deps.py` 中通过 `Depends` 直接返回 `Response`，随后在中间件里统一处理续期，避免在业务路由里显式写 `set_cookie`。<br>2. **统一常量**：`SESSION_MAX_AGE`、`WEBUI_TOKEN_COOKIE_NAME` 等常量集中在 `deps.py`，便于全局修改。<br>3. **防御式返回**：对无效/失效的 Cookie 统一返回 401 并在异常处理器里删除，形成“一处删除，多处防御”。 |
| **架构特征** | 1. **层级化认证链**：`require_auth → enforce_mfa_enrollment → queue_webui_token_renewal`，形成 **MFA → 会话续期** 的硬性顺序。<br>2. **中间件 + 依赖双保险**：即使业务路由忘记调用 `queue_webui_token_renewal`，中间件仍会在响应阶段检查并写入 Cookie，提升鲁棒性。<br>3. **数据库权威 Claims**：所有续期前重新查询 `TelegramUser`，确保角色、用户名、激活状态即时同步，这是一种 **“权威源+缓存”** 的防止陈旧 JWT 的典型做法。 |
| **测试策略** | 1. **端到端+单元混合**：大量使用 `TestClient` 对完整请求链路（包括重定向、模板响应）进行验证，覆盖了 Cookie 写入的所有分支。<br>2. **负向用例**：专门验证 MFA 未完成、账号被禁用、旧 token 不续期等路径，体现了 **Fail‑Closed** 思路。 |

**三、规范完善建议**

1. **新增审查规则**  
   - **中间件写 Cookie 时序检查**：要求审查时确认 `Set-Cookie` 在 `http.response.start` 之前写入，防止在 `RedirectResponse`、`StreamingResponse` 等特殊响应里被覆盖。  
   - **并发续期幂等性**：若同一次请求因多层依赖（如 `require_auth` 与 `require_api_auth`）都触发 `queue_webui_token_renewal`，必须保证只产生一次写入。审查时检查是否有 `has_webui_cookie` 或类似 guard。  
   - **MFA 前置标记完整性**：所有进入 `require_auth` 的路径必须显式依赖 `enforce_mfa_enrollment`，防止遗漏导致未完成 MFA 的会话被续期。  
   - **旧 token 兼容测试**：在引入滑动会话时，必须新增对 “旧 token 在下次完整授权后被升级” 的回归测试。  

2. **项目特有规范要点**  
   - **统一 Cookie 操作入口**：所有对 `webui_token` 的写/删操作只能通过 `WebUITokenRenewalMiddleware` 或 `queue_webui_token_renewal`，禁止在业务路由里直接 `response.set_cookie`。  
   - **Claims 同步约定**：续期前必须调用 `refresh_login_claims`（或等价函数）获取数据库最新的 `github_username、role、email、email_verified、active`，代码审查时检查是否遗漏。  
   - **异常处理统一**：401/428 等状态码的返回必须在 `backend/main.py` 中统一处理，并在对应异常处理器里执行 Cookie 删除，以防散落的手写 `Response(status_code=401)` 漏掉清理。  

**四、经验教训**

| 教训 | 对策 |
|------|------|
| **“侵入式依赖改动”易导致链路破裂**（第1轮） | 采用 **中间件+依赖注入** 的双层防护后，代码更稳健。以后新增全局行为（如审计、限流）时，优先考虑 **ASGI 中间件**，仅在必要时才改动业务依赖签名。 |
| **管理员 API 绕过 MFA 隐患** | 将权限校验统一委托给 `require_api_auth`，形成 **单一入口**，审查时应检查是否存在类似的 “特权路径直接跳过公共校验” 的情况。 |
| **登录重定向死循环** | 在 401 处理器里显式删除 Cookie，防止旧 token 触发循环。以后涉及 **自动跳转** 的错误处理，都要检查是否需要清理会话凭证。 |
| **测试覆盖不足的负向场景** | 本次通过新增大量负向单测（MFA 未完成、账号禁用、旧 token）弥补。建议在每次功能性改动后，**至少增加一个负向用例**，确保 Fail‑Closed 行为。 |
| **增量审查对全局安全链路的盲点** | 虽然本轮只看增量文件，但审查者仍回顾了整个认证链路，避免仅关注局部改动导致的遗漏。以后增量审查前应 **执行一次全局依赖/安全链路抽查**（如搜索 `queue_webui_token_renewal` 的所有调用点）。 |

### 综合建议

1. **在 CI 中加入 “Cookie 写入时序” 检查**：使用 `httpx` 或 `starlette.testclient` 发起包含 `RedirectResponse` 的请求，断言响应头里包含 `Set-Cookie`。  
2. **为 `queue_webui_token_renewal` 添加幂等单测**：模拟同一请求在不同依赖层多次调用，确保最终响应只写入一次 Cookie。  
3. **持续维护 “单入口校验” 规范**：所有特权或安全相关的入口（如 `require_api_admin`）必须通过公共校验函数，否则在代码审查时标记为 **阻断（error）**。  
4. **每轮增量审查前执行一次全局安全链路抽查**：自动化脚本列出所有涉及 `webui_token`、MFA、Claims 刷新的路径，确保没有遗漏。  

通过上述反思与改进，可进一步提升审查的 **防漏** 与 **防误** 能力，确保安全关键路径在未来的迭代中保持稳健。
