## 2. 发现的模式

### 代码模式
1. **DRY 倾向明显**：`quota_checks` 列表 + 循环的写法值得推广，但未进一步提取为可复用函数。
2. **递增式降级补偿缺失**：多轮审查中“超额后仅记录日志”反复出现，表明团队倾向于先保证功能上线，再补充补偿逻辑，但缺乏自动补偿的统一模式或装饰器。
3. **缓存单例隐式状态共享**：`get_settings()` + `@lru_cache` + `setattr` 原地修改的模式，在项目中被多处使用，但缺少显式的“可变单例”注释。

### 架构观察
- **异常处理器与业务逻辑耦合风险再次出现**：第 3 轮审查已明确“全局异常处理器不得引用业务依赖”，本轮又出现 token 解析。说明该规范执行不彻底，或缺少自动化检测（如 lint 规则）。
- **测试隔离依赖注入不彻底**：测试中直接使用 `get_templates()` 单例，而非通过依赖注入或 fixture 重置，表明测试框架对全局状态的隔离意识较弱。
- **API 与 WebUI 边界仍然模糊**：`require_payment_enabled` 定义在 `webui/deps.py` 但被 API 模块引用，虽被接受，但暗示认证/授权层未完全分离。

## 3. 规范完善建议

### 新增 / 强化规则

| 规则 | 严重度 | 说明 |
|------|--------|------|
| **全局异常处理器内禁止任何可能与配置/秘钥交互的调用** | `major` | 不仅禁止查数据库和解析 token，还应禁止调用依赖 `get_settings()` 的任何函数，因为配置本身可能抛出异常 |
| **可变单例必须显式注释并发安全策略** | `minor` | 若 `@lru_cache` 单例会被 `setattr` 修改，必须在类或函数处标注：是否线程安全、是否需要锁 |
| **测试中禁止依赖未隔离的全局缓存单例** | `minor` | 若必须使用全局 `@lru_cache`，应在 `setUp` / `fixture` 中清理缓存（如 `func.cache_clear()`） |
| **配额降级补偿应作为统一的后台任务而非内联逻辑** | `suggestion` | 避免每轮增量审查都重复提醒同一问题，推动团队建立“配额溢出自动平滑”的标准实现 |

### 项目特有要点
- 支付配置的全链路（API、WebUI、Telegram、定时任务、配额检查）必须纳入 PR 强制检查清单。
- 任何新增 `@lru_cache` 返回的对象，如果会被写操作修改，必须触发 `major` 级别的审查复核。

## 4. 经验教训

### 值得在未来审查中关注的要点
- **单例 + 可变对象 = 高风险**：尤其在被异步框架和多线程环境使用时，必须审查是否加锁。
- **异常处理器是最后的兜底，其依赖链必须为 ∅**：任何可能失败的调用（包括配置、JWT 库、环境变量）都应被 `try/except` 包裹并降级。
- **“修复”的验证不能只看逻辑，要看路径**：本例中 `settings.payment_enabled` 和 `is_payment_enabled()` 虽然逻辑上同步，但一个读内存单例，一个读 DB + TTL 缓存，存在短暂不一致窗口（虽然影响不大）。

### 对特定技术/模式的审查经验
- **`@lru_cache` + `setattr` 模式**：审查时必须验证：
  - 所有修改点是否都通过同一单例？
  - 是否存在任何路径绕过 `setattr`（如直接写 DB）？
  - 并发修改是否安全？
- **Jinja2 全局变量绑定**：若绑定的是可变对象，模板看到的是最新引用，而不是快照 —— 这是一个“特性”，但必须明确文档化。
