## 2. 发现的模式

### 代码模式
- **安全降级癖好**：多处使用 `except Exception` 捕获 Redis 错误并回退到内存（如 GETDEL → 内存路径）。做法本身合理，但缺少：

  - 降级时是否记录 warning 日志（已有 `logger.warning`，✅符合规范）
- **懒加载模式滥用风险**：`_render_settings_page` 中的条件查询本意是优化，但增加了分支复杂度。如果将来调用方传入的 `overrides` 意外缺少字段，会导致意外查询。

### 架构观察
- **Redis 依赖硬编码**：所有 fallback 逻辑依赖全局 `_totp_setup_fallback` 字典。若未来需要支持多进程/多实例，该字典会失效，但没有注释说明“当前仅支持单进程”。
- **配置读取在装饰器中**：`@limiter.limit(lambda: get_settings().xxx)` 每次请求都会调用 `get_settings()`，可能成为热路径瓶颈。建议注入配置或使用缓存。

### 技术经验
- **`GETDEL` 与回退**：fallback 到内存路径后，原 Redis 中的 key 可能残留。长期运行会导致 Redis 中存在已使用但未删除的 key（因为 `GETDEL` 失败时未执行 Redis 删除）。这不是本次变更的 bug，但值得后续优化。
- **`_cleanup_totp_setup_fallback` 与 Redis TTL 一致性**：内存 TTL 基于 `two_factor_pending_token_expire_minutes` 计算，Redis 端用 `setex`。两者保持一致 ✅。但清理函数仅在每次写入时调用，不提供后台清理线程，高并发下可能短暂超额（可接受）。
