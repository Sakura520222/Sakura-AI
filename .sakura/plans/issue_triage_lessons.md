# Issue 分析与 triage 规范

## 分类与优先级
- 简短 Issue 不应过度推断；必须区分事实、推测、待确认。
- 优先级应基于影响范围：是否默认配置、是否核心流程、是否阻塞开发、是否影响生产。
- "记录耗时"属于 observability/monitoring，不等同于性能优化。
- Gitflow `main -> develop` 同步失败通常是 maintenance/ci/merge-conflict。

## 功能提议三阶过滤
1. **定位过滤**：是否契合项目核心定位？偏离→wontfix/out-of-scope
2. **合规过滤**：是否合规/ToS可行？风险→wontfix/needs-decision
3. **优先级排序**：通过前两阶后才评估优先级
- 产品契合度应是第一道过滤，技术复杂度是第二理由

## 标签建议
优先使用仓库已有标签。避免为了单个 Issue 创建过细标签。
- `security`标签仅用于当前已存在的安全漏洞，不用于假设性风险
- `help wanted`须评估实际贡献门槛，核心链路任务通常不适合
- UI行为异常应优先考虑bug分类而非enhancement

## 重复检测硬规则
重复检测输出必须包含四要素：
`{被引Issue标题}` + `{相似点}` + `{差异点}` + `{判断结论}`
- 无法获取被引Issue信息时应标注"信息不足，无法判断"，不给模糊结论
- 仅凭异常类名/关键词匹配判定重复是危险的，须附带触发场景比对
- 主分析链路失败时输出的重复检测结果可信度接近零

## 标题改写
标题应保留需求边界，不擅自扩大范围。不在标题放 `[priority]`，用标签/字段表达。

## 可行性建议
- 给出分层工作量：最小实现、API暴露、WebUI/i18n/测试、架构重构
- "允许AI指定X"类需求须验证信息可用性：AI如何获知X的可选值？无信息来源=不可行
- 集成类Issue的降级策略是必问项
- 可行性须含"可验证性"维度：改进类Issue仅评估"能不能做"不够
- 需求模糊时优先级应带条件标注（如"medium（需求澄清后确认）"）
- 工作量估算须与分析中识别的风险自洽

## 安全异常定性
区分"防线击穿"（真漏洞）vs"防线误伤"（False Positive）：
- 两者的标签和优先级应有明显区分
- 安全校验类Bug修复最容易犯"一刀切放开导致真漏洞"

## 元分析/自引用Issue
- 须具备递归深度检测或自引用识别能力
- 置信度在边界场景应主动乘以0.7衰减因子
- 评估类Issue应拆解为可验证改进任务
- 回退默认值须显式标记"分析失败"状态，禁止伪装成正常分析结果
- **`automated` 标签须明确语义**：区分"用户手动提交"与"自动化流程"，避免误用（ISSUE #431）
- **降级输出附带唯一错误码**：禁止硬编码静态字符串，所有 fallback 路径须有唯一错误码标识（ISSUE #432）

## 配置/部署类 Issue 分类
- 部署/配置类 Issue 应优先归类为 `configuration` 而非 `other`（ISSUE #429）
- 须提供阶梯式排查清单，按概率排序，首项为最可能根因
- 高优先级须附加"预期用户可自行修复"标记，避免开发者过度介入
- 必须检查：GitHub App 安装权限、Webhook Secret 配置、仓库特有注册依赖（如 Telegram）

## 并发竞态分类
- 并发正确性问题应使用 `concurrency`/`race-condition` 标签，非 `performance`（ISSUE #430）
- 单例模式在 asyncio 并发中的状态污染是核心风险
- webhook 重试与 Issue edited 频繁触发导致级联竞态，须建议去重或限流

## 大范围 Enhancement 分类
- 不能粗分为 `other`，应按 `enhancement` + `configuration` + `refactor` 复合分类（ISSUE #422）
- 须拆解：配置源、配置流、协议差异、默认值、兼容性、回退与迁移风险
- "重写/统一"不等于纯重构：须同步检查新协议支持、UI、数据结构、分阶段落地可行性
- 重复检测须保守：主题相似不足以直接判重复，须区分"同主题"、"同目标"、"同实现范围"

## 标签推荐增强
- **标签不可为空输出**：至少给出最贴近的候选标签，保留与仓库现有标签体系的一致性（ISSUE #422）
- **`duplicate` 标签须附证据链**：{被引Issue标题} + {相似点} + {差异点} + {判断结论}，缺一不可（ISSUE #432）
- **标题改写不可缺失**：单次标题（如"bug"、"报错"）须强制改写（ISSUE #431）
- **保留核心卖点**：对配置类/Provider 类 Issue，标题应保留"一键配置/模型内置/Provider 统一"等核心信息（ISSUE #422）

## 可行性评估分层
- 复杂 Issue 应将"高复杂度"拆成可交付阶段，而非只给总体判断（ISSUE #422）
- 建议拆分为：Provider 协议抽象 → 原生适配 → 模型发现/元数据统一 → 参数映射 → Wizard 联动 → 故障转移 → 配置迁移与兼容
- 每阶段须含：工作量估算、风险识别、技术依赖评估
