# Issue 分析与 triage 规范

## 分类与优先级
- 简短 Issue 不应过度推断；必须区分事实、推测、待确认。
- 优先级应基于影响范围：是否默认配置、是否核心流程、是否阻塞开发、是否影响生产。
- "记录耗时"属于 observability/monitoring，不等同于性能优化。
- Gitflow `main -> develop` 同步失败通常是 maintenance/ci/merge-conflict。

## 功能提议三阶过滤
1. **定位过滤**：是否契合项目核心定位？偏离→wontfix/out-of-scope
2. **合规过滤**：是否合规/ToS可行？风险→wontfix/needs-decision
3. **优先级排序**：通过前两阶后才评估优先级
- 产品契合度应是第一道过滤，技术复杂度是第二理由

## 标签建议
优先使用仓库已有标签。避免为了单个 Issue 创建过细标签。
- `security`标签仅用于当前已存在的安全漏洞，不用于假设性风险
- `help wanted`须评估实际贡献门槛，核心链路任务通常不适合
- UI行为异常应优先考虑bug分类而非enhancement

## 重复检测硬规则
重复检测输出必须包含四要素：
`{被引Issue标题}` + `{相似点}` + `{差异点}` + `{判断结论}`
- 无法获取被引Issue信息时应标注"信息不足，无法判断"，不给模糊结论
- 仅凭异常类名/关键词匹配判定重复是危险的，须附带触发场景比对
- 主分析链路失败时输出的重复检测结果可信度接近零

## 标题改写
标题应保留需求边界，不擅自扩大范围。不在标题放 `[priority]`，用标签/字段表达。

## 可行性建议
- 给出分层工作量：最小实现、API暴露、WebUI/i18n/测试、架构重构
- "允许AI指定X"类需求须验证信息可用性：AI如何获知X的可选值？无信息来源=不可行
- 集成类Issue的降级策略是必问项
- 可行性须含"可验证性"维度：改进类Issue仅评估"能不能做"不够
- 需求模糊时优先级应带条件标注（如"medium（需求澄清后确认）"）
- 工作量估算须与分析中识别的风险自洽

## 安全异常定性
区分"防线击穿"（真漏洞）vs"防线误伤"（False Positive）：
- 两者的标签和优先级应有明显区分
- 安全校验类Bug修复最容易犯"一刀切放开导致真漏洞"

## 元分析/自引用Issue
- 须具备递归深度检测或自引用识别能力
- 置信度在边界场景应主动乘以0.7衰减因子
- 评估类Issue应拆解为可验证改进任务
- 回退默认值须显式标记"分析失败"状态，禁止伪装成正常分析结果
