# 近期审查经验：高风险模式与行动清单

## 1. 平台级配置需求的分析方式

“统一 AI Provider 配置、支持 Anthropic/OpenAI、模型内置、推理参数、Setup Wizard、故障转移”等表述不是普通 `other` 需求，而是配置体系与接入链路的复合增强。

分析时按以下工作包拆解：
- Provider 协议、认证和 streaming/错误语义；
- 模型发现、内置模型元数据和套餐/权限差异；
- 推理参数的厂商私有映射；
- Settings、env、DB、API、Wizard 的配置流与迁移；
- fallback/路由策略、旧配置兼容和测试。

优先级应同时考虑核心用户路径（特别是首次设置）和实际阻塞性；“high impact enhancement”不等于紧急故障。重复检测只能在比较具体范围后下结论，主题相似时应称“相关，待人工确认是否重复/拆分”。

## 2. 异步资源清理的反模式

**反模式：用排除条件清理活跃资源。** 例如取消所有 external_id 不等于当前任务的同名 Check。这会将“修复占位资源残留”转化为“误杀并行任务”。

行动：先定义可被回收对象的正向身份白名单；为并行、重试、乱序、重复 webhook 增加保留性测试（不仅测试“该删的删掉”，也测试“相似对象不能删”）。

## 3. 隐式接口与文本同步

- `/health` 的 `service`、`version` 等监控字段是对外契约；即使代码库 grep 无引用，也需评估仪表盘、告警和外部消费者兼容性。
- 后端校验/错误文案变动必须搜索对应 i18n 键和全部语言文件；核心逻辑先更新、翻译滞后是重复出现的模式。
- 提示词、配置文本和 PR 评论 marker 也属于下游解析契约。格式演进应检查解析兼容与降级，而非只改生成端。

## 4. 审查执行失效模式

近期复盘反复暴露的不是局部代码误判，而是流程漏检：
- 高评分/“标准重构”导致确认偏误；
- 只看增量导致历史问题被无证据地关闭；
- PR 描述与 diff、统计数字未交叉验证；
- 将功能扩展隐藏在“重构”叙事中；
- 未输出重构等价性声明和 quick 自检。

### 每轮行动清单

1. 先列 PR 描述承诺，再读 diff；
2. 先做负面检查，再写正面评价；
3. 对历史发现逐条附证据更新状态；
4. 对公共函数、状态机、配置与外部接口做调用链扫描；
5. 输出时区分“当前增量通过”与“PR 整体可合并”。

## 5. 依赖更新审查的系统性失误（PR441-PR456）

近期8个依赖更新PR（441-456）暴露了反复出现的审查失误：

- **"一行变更"陷阱**：qrcode v7→v8、alembic 1.13→1.18等major升级仅改一行，但审查工具两次完全失效（PR454、PR456），未产出任何有效输出
- **评分违规**：PR448给出10/10、PR444给出9/10，均违反quick策略8/10硬性上限
- **证据链缺失**：声明"项目未使用废弃API"时未附grep命令和结果
- **自动化工具盲区**：Dependabot分支命名与Gitflow冲突是结构性问题（PR442、PR453、PR455），须在仓库配置层面解决

**核心教训**：审查工具自身的可靠性是审查质量的前提。当工具失效时必须有降级输出。代码越简单，流程越不能省。

## 6. Issue分析的分类精炼（ISSUE438-451）

- 测试/占位Issue不应标为enhancement，应优先使用test/meta标签
- 重复检测必须提供{被引标题}+{相似点}+{差异点}+{结论}四要素证据链
- 极短Issue先做语义判断（测试/误发/空白），再决定是否需要代码检索
- 标题改写不可将分析元数据（如[other][low]）直接写入Issue标题

## 7. 异步上下文与生命周期风险（PR#479）

`ContextVar` 在 ASGI 环境中的传播边界比开发者预期更微妙。当后台任务通过 `get_runtime_supervisor()` 获取 supervisor 时，lifespan 上下文与独立 HTTP 请求任务的 ContextVar 可能不同，导致：
- 后台任务绕过"清库守护者" supervisor，关键操作（如 DROP TABLE）执行时任务未被停止
- **"停止"比"启动"更难**：关闭时的错误可能导致数据损坏，后果比启动失败更严重
- 架构意图（"受控的重置流程"）必须映射到代码的显式控制结构上

## 8. 增量审查的全局视野缺失（PR#478）

增量审查容易产生"隧道视野"——只看到当前 diff，忽略 PR 中仍存在的历史阻断问题。核心教训：
- **审查的"边界"必须是决策时的"输入"，不是思考的"围墙"**
- 存在未解决阻断问题时，approve 决策必须附带风险声明
- 评分与决策需与上下文对齐——技术上正确的增量审查在包含阻断问题的 PR 中缺乏实际意义

## 9. 基础语法正确性不容忽视（PR#477）

两个 `except` 逗号语法（Python 2）的 critical 错误，阻断了核心模块导入：
- **基础模块的语法错误产生放射性影响**，审查应对核心抽象层给予最高优先级
- 大规模变更中，不轻信"通过了 pytest"——语法错误可能导致测试本身无法运行
- **"最简单"变更的"最严格"审查**原则再次验证

## 10. 后续改进建议

- 在 PR 模板加入 `i18n Impact`、外部契约影响和描述统计来源；
- 为 Check Run 建立显式身份字段及状态转移测试矩阵；
- 为审查输出模板加入固定占位：描述-diff勾选、重构三轨、历史问题证据、quick自检；
- 将连续三轮未处理的 suggestion 显式登记为技术债，并评估升温或创建 Issue；
- **为Dependabot PR配置分支保护规则例外**，从根本上解决Gitflow冲突；
- **审查工具须增加降级输出机制**，确保工具失效时不产出空结果；
- **依赖更新审查增加自检步骤**：评分上限校验、证据链完整性、CHANGELOG逐项核对。
