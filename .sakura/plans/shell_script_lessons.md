# Shell 脚本审查经验教训

## 1. 版本兼容性的"木桶效应"
- **兼容性检查必须全覆盖**：在脚本中引入了针对旧版本的回退逻辑，容易让人产生"已处理兼容性"的错觉。教训是：**兼容性检查必须覆盖所有新增的外部调用**，而不仅仅是显式处理过的那部分
- **典型案例**：`up -d --pull never` 虽然不是 pull 命令，但同样是 Compose 调用，且引入了新参数，必须纳入同一兼容性策略考量

## 2. 环境变量驱动的逻辑分支是隐蔽的 Bug 源
- **容易忽略**：Dev 模式通常通过环境变量控制，容易被主逻辑路径忽略
- **强制演练**：审查此类代码时，应**强制演练**所有环境变量组合下的执行流
- **典型案例**：`stop_verified_updater` 中的 `elif` 链条漏掉了 Dev 场景

## 3. 文档即代码的验证深度
- **行为描述验证**：当 PR 描述提到"更新部署文档以提及..."时，审查不能止步于"文档更新了"。必须验证文档中的**行为描述**（如"原生动态进度渲染器"）在代码中是否有对应的实参支撑（`--progress tty`）
- **避免虚假承诺**：避免文档承诺了代码未提供的能力

## 4. 空Body的陷阱
- **{} vs 无操作**：在 REST API 设计中，发送 `{}` 往往被服务端解释为"使用默认值"，而非"无操作"或"智能推断"
- **必须查阅服务端代码**：在脚本审查中，遇到 `curl --data '{}'` 这种写法时，必须第一时间查阅服务端代码，确认每一个省略字段的默认值是否会与脚本当前的上下文变量（如 `$CURRENT_CHANNEL`）发生冲突

## 5. 跨组件逻辑验证的必要性
- **不能只看 Diff**：当 PR 仅修改了客户端（`start.sh`）但依赖服务端（`updater`）的特定行为时，审查者不能只看 Diff
- **必须跳转验证**：必须像本次审查一样，跳转到服务端代码验证其处理逻辑，否则极易漏掉这种"客户端以为发送了 A，服务端理解成了 B"的逻辑鸿沟

## 6. UX 细节决定成败
- **区分失败和无需操作**：对于 CLI 工具，区分"失败"和"无需操作"是用户体验的关键
- **以用户视角处理错误**：将 422 错误笼统地打印为 JSON 原文是典型的"以开发者视角而非用户视角"处理错误的方式
- **未来审查重点**：未来的审查应更关注错误信息是否对操作者具有可读性和指导性
