# 大规模工具链更新经验教训

## 常见陷阱

### 确认偏误
- **现象**：9/10 评分 + 全部通过测试 → 忽略配置合理性
- **根因**：高评分易引发"一切顺利"的幻觉
- **影响**：工具配置问题被遗漏，长期影响代码质量

### 工具盲区
- **现象**：只验证规则执行，不验证规则选择
- **根因**：过度信任工具输出，缺乏人工校准
- **影响**：不合理规则长期存在

### 兼容性遗漏
- **现象**：CI 通过不代表所有依赖已支持新版本
- **根因**：仅检查构建成功，未验证依赖官方支持状态
- **影响**：生产环境运行时异常

## 审查要点

### 配置合理性审计
- **规则白名单**：忽略的规则是否与项目架构匹配
- **规则冲突**：与 mypy、black 等工具是否存在冲突
- **设计文档对齐**：配置须逐项验证与文档一致

### 变更等价性验证
- **非纯格式化**：引入 `asyncio.to_thread()` 等变更须提供行为不变证明
- **禁止仅依赖测试**："测试通过"不等于语义等价

### 依赖兼容性
- **Python 版本**：跳跃升级须验证所有核心依赖官方支持
- **工具大版本**：须逐条核对 Breaking Changes
- **CI 依赖**：验证废弃参数未被使用

## 最佳实践

1. **审查分层**：配置层 → 变更层 → 影响层
2. **人工校准**：工具验证合规性，人工校准合理性
3. **小步迭代**：避免一次性升级多个工具或跨越多个大版本
4. **文档同步**：变更说明须同步更新开发文档

## 经验总结

- **"维护性变更"是规范建设契机**：强迫团队明确代码底线和规则选择
- **审查者须扮演"架构与规范守护者"**：将审查重点从代码片段提升到配置决策
- **自动化服务于项目，而非相反**：工具配置必须符合项目长期演化方向
