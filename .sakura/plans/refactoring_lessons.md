# 重构审查经验教训

## 1. 信任但要验证
- **注释撒谎的现象**：即使 PR 描述和代码注释声称有"兜底机制"，审查者必须保持怀疑
- **比逻辑错误更难排查**：注释声称有超时，实际上却不存在，这种"注释撒谎"的现象比逻辑错误更难排查

## 2. LLM 应用的无限循环风险
- **极度危险**：在 LLM 应用中，`while True` 配合模型自决退出是极度危险的
- **不可控的后果**：模型可能会产生幻觉或陷入死循环，导致不可控的 API 成本和资源占用
- **必须保留物理硬约束**：必须在代码层面强制保留物理硬约束

## 3. 重构不仅仅是清理
- **副作用是破坏了安全边界**：本次 PR 的目标是"简化配置"，但副作用是破坏了安全边界
- **审查者需要警惕**：那些打着"简化/重构"旗号移除关键安全检查的变更

## 4. 手动全量重审的价值
- **发现系统性风险**：全量审查能够发现增量审查极易忽略的系统性风险
- **跨文件关联性验证**：通过全量视角，能够发现如 `agent_team_max_runtime_minutes` 这一配置在全局范围内的"孤儿状态"（只定义不使用）
- **对增量审查的启示**：对于涉及"核心控制流变更"或"配置项删除"的 PR，即使是在增量审查中，也应触发**全量验证模式**

## 5. 测试覆盖的局限性
- **测试只能证明"被测函数"行为正确**：无法证明"未测函数"（如实际 AI 调用链路）不受影响
- **测试通过不等于 Bug 修复闭环**：这是重要的认识

## 6. 全链路 grep 验证
- **关键手段**：使用"全仓 grep"来验证配置项的消费方，而非仅阅读单个文件
- **发现关键问题**：这是发现"死配置"和"循环边界缺失"的关键手段

## 7. 删除完整性验证
- **必须验证所有被删除公共符号**：在非测试代码中已无引用
- **配置同步清理**：验证相关配置（如 UI、i18n 键）已同步清理
- **死代码扫描**：重构 PR 合并前必须通过工具扫描确保未引入新死代码

## 8. 重构后"残留"审查
- **从"新增了什么"转向"删除得是否干净"**：这是重构审查的重要视角转变

## 9. 重构+功能混合 PR 审查
- **双轨检查**：摘要分"新功能验证"和"重构等价性验证"两节
- **已有测试通过确认**：重构后所有已有测试是否通过
- **返回值结构一致性**：重构前后返回值结构是否等价
