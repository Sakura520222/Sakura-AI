# PR567~PR577 系列经验教训（16 次反思提炼）

> 覆盖：PR567 全量+incr2/3/4、ISSUE568-571、PR572+incr2、PR573-PR577 依赖管理系列。

## 1. 审查证据与纪律
- "无评论/无问题"结论必须附验证依据：rg 命令、CI run 链接。全量重审给 10/10 却无证据 = 确认偏误（PR567）。
- 阻断缺陷先于功能审查：9 处 Python2 `except A,B:` 语法错误让整个包 import 崩溃，功能评审失去意义；CI 必须有全库 py_compile/import-all 防线（PR572）。
- 历史阻断未修复时 PR 实际不可合并；语法阻断应设为 merge-gate，语法修复与功能变更分离提交。

## 2. 全局副作用审查
- 包入口 `__init__.py` 注入环境变量（PTB_TIMEDELTA）影响全进程时间语义：须全库搜索读取点、检查配置加载顺序、补业务层回归测试、同步 Dockerfile/helm 文档（PR567 incr4）。
- 增量 ≠ 全局：配置键/异常类/缓存结构改动后必须跑全库引用搜索，防 KeyError 与隐式引用遗漏。

## 3. 资源与性能防线
- 图片处理：解码内存预算 + JPEG draft 降采样 + 原位 EXIF 转置 + DecompressionBomb 防护；负向路径（超限直接丢弃）必须有测试（PR567 incr2/incr3）。
- ReDoS 防护用前向扫描替代回溯正则；解析类改动要求微基准。
- Redis+内存双写清理需原子化（Lua/pipeline），防并发竞态残留。

## 4. 通知与补偿机制
- 删除旧通知链路（ISSUE571）：全链路引用审计（含动态 import/字符串拼接）、配置项安全删除、灰度/feature flag、回滚方案、端到端测试；分类为 refactor 但优先级应考虑合规影响升 high。
- 定时补偿扫描（ISSUE568）：与 webhook 并发需唯一约束/分布式锁保证幂等；分页+指数退避应对 GitHub API 限流；必须上报"上次成功扫描时间"防静默停摆。

## 5. 深度审查能力建设（ISSUE569）
- 依赖图驱动跨文件推理：增量缓存 + 拓扑跳数阈值，防止大 PR 卡顿。
- adversarial pass 成本高：仅高风险文件（Dockerfile/*.yml/*_handler.py）触发，先用规则引擎筛选。
- 用历史缺陷 PR（如 #567）构建审查回归套件；统一埋点调用次数/耗时/覆盖文件数。
- 高风险场景（部署链/双写/回退/并发/状态机）提示词结构化为清单注入。

## 6. 跨语言与部署安全
- UDS 权限、容器用户映射、`--cap-drop`、镜像 digest 锁定（@sha256:）纳入跨语言安全清单；workflow 强制最小 permissions（PR567）。
- Shell 是一等公民：fail-closed、ERR_ 前缀错误码、标签一致性断言；热区文件（连续大改）触发额外全链路回归。
- 平台特定 API（os.O_DIRECTORY）测试须 skipif；模块级直接 import 关键模块形成单点故障，考虑延迟导入。

## 7. 元教训
- 审查工具对超大文件（uv.lock）有读取上限：分块处理，不得以"读不了"跳过验证。
- 基础语法问题要在增量审查前拦截；"通过了 pytest"不等于语法正确（测试可能根本无法运行）。
