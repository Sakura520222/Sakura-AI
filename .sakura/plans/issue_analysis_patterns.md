# Issue 分析模式与规则

## 1. 分类与优先级通用规则
- 简短 Issue 不应过度推断；必须区分事实、推测、待确认
- UI行为异常优先考虑bug分类（"某事不该发生"），除非仓库明确不使用bug标签
- 优先级不应固化到标题前缀中，用标签/字段单独承载
- good first issue置信度须反映隐性门槛，分析自身已识别"需注意X"时该注意就是门槛

## 2. 功能提议过滤三阶模型
1. **定位过滤**：是否契合项目核心定位？偏离→wontfix/out-of-scope
2. **合规过滤**：ToS/合规风险→wontfix/needs-decision，不得用low掩盖合规问题
3. **优先级排序**：通过前两阶后才评估。核心能力自改进→影响范围全局→优先级上浮

## 3. 可行性分析深度要求
- **信息可用性前置检查**："允许AI指定X"→AI如何获知X？无信息来源=不可行
- **降级策略是集成类必问项**：API调用失败是否阻断核心流程？须有显式降级
- **可验证性维度**：改进类Issue须回答"做了怎么验证"，无基准指标则改进无法验证
- **工作量须与风险自洽**：识别了复杂分支却不反映在估算中=自相矛盾
- **权限前置依赖**：读取GitHub新端点须检查App现有权限是否覆盖
- **需求模糊时优先级保守**：含"动态""下一次"等时序模糊词时带条件标注

## 4. 重复检测四要素硬规则
输出必须包含：`{被引Issue标题} + {相似点} + {差异点} + {判断结论}`
- 无法获取被引Issue信息→标注"信息不足，无法判断"
- 禁止仅凭异常类名/关键词匹配下结论，须附带触发场景比对
- 主链路失败时输出的重复检测结果可信度≈零，不应作为有效结论呈现

## 5. 安全异常定性规则
- 首要步骤：鉴别是"防线击穿"（真漏洞）vs"防线误伤"（False Positive）
- 两者标签和优先级截然不同：SecurityError可能是误杀而非漏洞
- 修复安全校验类Bug时最易犯"一刀切放开导致真漏洞"
- `security`标签仅用于当前已存在的漏洞，不用于假设实现某功能会引入的问题

## 6. 元分析/自引用Issue规则
- 须具备递归深度检测或自引用识别能力，否则存在无限循环风险
- 所有分类/标签/优先级置信度自动乘以0.7衰减因子
- 应拆解为可验证改进任务，而非仅做概括性描述
- 仓库标签体系应考虑`meta`/`self-evaluation`专属标签

## 7. 格式契约故障处理
- AI输出格式与解析器强耦合时，单标签缺失→整条链路崩溃
- 各模块须独立解析、独立降级，禁止级联失败
- 回退默认值须显式标记"分析失败"状态，禁止伪装成正常结果
- 内部错误信息不得泄漏到用户界面

## 8. 提示词即接口契约
- 提示词新增/修改输出格式约束=修改接口契约
- 须追踪下游解析代码验证隐式假设耦合
- 仅修改提示词不验证消费方至少标minor
- "纯文本变更"≠零风险——被代码隐式依赖的文本格式约定修改与接口变更同级

## 9. 配置/部署类 Issue 分析模式
- **阶梯式排查清单**：提供按概率排序的排查步骤，首项为最可能根因
- **"最快验证命令"**：在分析结果中附一条用户可立即执行的验证命令
- **高优先级不意味代码缺陷**：high 须附加"预期用户可自行修复"标记，避免开发者过度介入
- **GitHub App 权限检查**：检查 App 是否安装到目标仓库且有 Issues 读写权限
- **Webhook Secret 配置检查**：未设置 Secret 可能导致拒绝
- **分析输出格式化**：输出应使用"请按顺序检查：1... 2... 3..." 的分步格式
- **仓库特有模式优先**：若仓库依赖外部注册（如 Telegram），将注册检查放在首位

## 10. 并发竞态分析模式
- **单例模式陷阱**：在 asyncio 并发场景下，优先检查共享可变对象生命周期与任务隔离
- **webhook 级联竞态**：webhook 重试与 Issue edited 频繁触发可能导致级联竞态，须建议去重或限流
- **缓存并发安全**：无锁访问缓存须用 `asyncio.Lock` 或改用线程安全的数据结构
- **标签准确性**：并发正确性问题应推荐 `concurrency`/`race-condition` 标签，非 `performance`
- **任务隔离 vs 资源复用**：推荐每次分析创建独立实例或深拷贝工具处理器，注意资源开销

## 11. 元分析/自引用增强规则
- **递归深度限制**：分析工具自身 Issue 时，设置全局递归深度计数器（即使看似不可能触发）
- **置信度衰减**：自引用场景下，所有分类/标签/优先级置信度自动乘以 0.7 衰减因子
- **降级输出显式标记**：`category: "analysis_failed"`，`feasibility: "分析失败"`，禁止伪装正常
- **内部错误脱敏**：所有 fallback 路径输出的静态字符串须审查，泄漏内部错误标 major
- **日志截断升级**：当前仅保存 80 字符前后缀，应升级为完整载荷保存
- **标题强制改写**：单次标题（如"bug"、"报错"）须强制改写，不可缺失

## 12. AI 输出不稳定容错模式
- **指数退避重试**：解析失败增加指数退避重试（至少 2 次），保存完整载荷用于离线调优
- **协议解析器严格性/容错性平衡**：对特定字段做内容净化而非直接拒绝，可推广到所有单行字段
- **消费方兼容性验证**：修复降级输出后，须验证所有消费方（前端展示、通知）对新状态标记的处理
- **多文件协同修复测试**：涉及多个文件时，须编写集成测试验证整个链路

## 13. 认证/API Key 问题分析模式
- **不可重试异常**：API 认证错误（401/403/AuthenticationError）应在重试逻辑中立即捕获并给出明确提示
- **配置问题 vs 代码缺陷**：准确区分根因（用户配置）和代码可优化点（重试策略）
- **最小信息泄露**：request id 等内部标识符应记录在日志而非返回前端
- **多 Key 字段混淆**：检查 `.env` 文件中是否有多个 Key 字段（如 OPENAI_API_KEY 和 openai_api_key）优先级不清
- **标签推荐**：认证类问题优先推荐 `authentication`、`configuration` 标签，避免 `question` 掩盖代码改进需求
