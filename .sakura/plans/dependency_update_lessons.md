# 依赖更新审查经验教训

## 1. "小变更"需要"大警惕"
- **影响面可能极广**：依赖版本号的一行修改，其影响可能横跨整个应用
- **不能因 diff 小而降低审查严谨度**：简单的依赖更新背后，可能隐藏着需要严肃对待的兼容性风险

## 2. 规则执行优先于业务判断
- **流程铁律**："quick 策略上限" 是流程铁律，必须无条件遵守
- **评分超出限制是更严重的错误**：评分超出限制是比漏报代码问题更严重的审查输出错误

## 3. 证据链比结论重要
- **所有正面的结论都必须伴随可验证的证据**：审查摘要中 "检查了使用情况" 的结论，如果没有附上 grep 命令和结果，就是无效的
- **禁止无证据断言**：所有关于"无影响"、"未使用"、"兼容"的结论，都必须附上 grep 搜索命令和结果作为证据

## 4. 自动化工具发起的变更更需警惕
- **可能绕过人工评估**：自动化更新可能绕过人工评估
- **假设开发者可能未充分测试**：审查时需要假设"开发者可能未充分测试"

## 5. 跨越大版本的升级需要更充分的验证
- **至少提供**：依赖锁定文件验证、核心功能冒烟测试
- **建议提供**：版本跳跃路径（如 3.11→3.12→3.13→3.14）作为降级方案

## 6. 依赖升级的全方位检查
- **优先检查**：受影响的依赖锁文件（`requirements.txt`、`poetry.lock`）
- **验证**：CI 配置中是否包含该 Python 版本的测试
- **检查**：容器镜像构建的下游消费方（如 Kubernetes 部署清单）

## 7. Python 大版本升级风险点
- **C 扩展库兼容性**：如 `cryptography`、`numpy`
- **标准库行为变更**：如 `asyncio`、`typing`
- **类型检查工具适配**：如 mypy 版本需跟进
- **构建依赖变化**：如 `pyproject.toml` 中的构建后端

## 8. "精简变更"需"深度检查"
- **1 行变更的连锁反应**：审查时应扩展到"1 行变更的连锁反应"
- **建议增加检查项**：
  - `git log --oneline -5 docker/Dockerfile` 查看历史变更频率
  - `docker history <image>` 对比新旧镜像差异

## 9. 对于 Dependabot 生成的 PR
- **审查重点**："依赖图的受影响范围"，而不仅仅是"版本号是否最新"
- **项目记忆的主动调用**：在审查开始时，应主动检查项目记忆中是否有与当前变更类型（依赖升级、容器配置）相关的特别规则或历史教训

## 10. 自动化依赖更新的验证清单
- **建议**：在项目规范中新增"自动化依赖升级的验证清单"模板，简化未来类似审查
