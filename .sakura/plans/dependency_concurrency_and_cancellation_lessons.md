# 依赖升级、并发状态机与异步调度经验教训

## 一、自动化依赖更新 (Dependabot) 审查教训

### 1.1 警惕 Bot PR 的“虚假完整性”
- **教训现象**：Dependabot 提交的 PR 通常附带详尽的 Changelog 和语义版本说明，给人一种“规范、安全、无害”的心理错觉。
- **审查死穴**：在现代 Modern Python 生态中，Dependabot 往往只修改明文清单（`pyproject.toml` 或 `requirements.txt`），完全遗漏 `uv.lock`，导致 CI 中开启的 `uv sync --locked` 100% 报错阻断。
- **行动准则**：依赖类 PR 审查的第 1 顺位永远是：**锁文件变了吗？CI 的 `--locked` 绿了吗？**
- **修复指引原则**：优先推荐单包最小升级（`uv lock --upgrade-package <pkg>`），避免盲目运行无参 `uv lock` 引发全量依赖漂移；同时指导维护者检查 GitHub Actions 自动补锁流水线（如 `MY_RELEASE_PAT` 配置）。

## 二、并发状态机与紧急修复中的反模式

### 2.1 紧急修 Bug 时的“就地重写”陷阱
- **教训现象**：在处理线上或高优先级缺陷时，开发者为了求快，往往倾向于在当前调用点直接内联手写过滤逻辑（如 `state != "released"`），即使底层已经有封装好的白名单判定工具。
- **潜在危害**：黑名单否定条件在系统后续拓展新状态（如 `cancelled`, `timed_out`）时极易被静默击穿；此外重复的内联实现会导致业务逻辑分散，形成语义漂移。
- **行动准则**：代码审查必须对负向条件（`!=`）保持高度警惕，强制要求复用底层模块的显式白名单工具与单一真值源。

## 三、异步任务与取消排空观测性教训

### 3.1 区分协程取消语义与故障诊断证据
- **教训现象**：在使用 `asyncio.shield` 进行取消排空时，为了确保 `CancelledError` 能被准确重新抛出，开发者往往用简单的 `try...finally` 或吞掉子任务异常。
- **潜在危害**：若底层子任务是因为真实的业务 Crash、连接超时或死锁中断，吞掉异常会导致系统完全丧失排查现场的依据。
- **行动准则**：在取消排空中，捕获底层异常后务必记录调试或警告日志，再安全退出并重新抛出 `CancelledError`。
