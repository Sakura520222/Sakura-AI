# 队列与 Worker 模式经验教训

## 1. "小变更文件批量审查"
- **不要忽略小文件**：23 个文件列出不代表 23 个文件都被审查。审查者容易陷入"大文件深度看、小文件跳过"的模式
- **小文件中的关键变更**：小文件中的删除和参数变更往往隐藏着行为契约的变化

## 2. 静默失败路径升级
- **升级条件**：当失败路径满足以下条件时，基础严重程度至少为 `major`：
  - 位于核心业务链路（非辅助/监控路径）
  - 失败后无用户可见错误、无重试、无告警
  - 导致数据静默丢失或状态不一致
- **典型案例**：webhook.py:398 的 `enqueue_from_webhook` 无异常兜底，DB 故障时增量更新静默丢失

## 3. 新增 DB 表必须审查索引
- **对照查询验证**：新增表定义时，必须对照同 PR 中的查询语句，验证是否有对应索引覆盖
- **无匹配索引至少标 major**：无索引的队列表在生产负载下会直接退化

## 4. PR 描述与 diff 一致性强制校验
- **量级差异应标 major**：当 PR 描述的语义范围（"优化配置"、"调整日志"）与实际变更的架构影响（新增队列、状态机扩展）存在量级差异时，应直接标 `major`

## 5. 队列系统的"冷启动"与"降级"必须问
- **三个必须追问的问题**：
  1. 表不存在时怎么办？
  2. 队列入队失败时有没有降级路径？
  3. 消费失败的消息去哪了？

## 6. "回调注入"模式需要生命周期验证
- **必须验证**：回调是否在所有路径（正常完成、异常、取消、超时）下都恰好被调用一次？
- **防止回调泄漏**：是否存在回调泄漏（持有了外部引用导致 GC 无法回收）？

## 7. PR 描述的"降维"是危险信号
- **两种可能**：将架构级变更描述为配置优化，可能是作者对变更影响认知不足，也可能是刻意降低审查预期
- **第一反应**：无论哪种情况，审查者的第一反应应该是"描述和 diff 不对等"而非"按描述方向审查"

## 8. 幂等性声明需验证
- **必须追问**：幂等键是什么？竞态窗口内两个相同请求同时到达时，数据库唯一约束是否能兜底？
- **代码逻辑不足**：仅靠代码逻辑的 check-then-insert 在并发下不够

## 9. "兜底"逻辑需警惕
- **往往意味着不确定**：兜底逻辑往往意味着"正常路径不确定能不能覆盖"
- **容易成为 bug 藏身处**：这类方法容易成为 bug 藏身处，审查时应要求作者明确其触发条件和预期行为边界

## 10. 事件驱动链路的状态一致性是核心风险
- **Webhook → Queue → Worker → AI Reviewer**：状态分散在 DB 表和内存中
- **状态同步延迟**：是异步架构的固有挑战
- **审查重点**：状态一致性是核心风险点

## 11. 模型/成本切换显式论证
- **将 API 调用从低成本模型切换到高成本模型时**：必须要求作者补充成本影响估算或性能必要性论证，至少标 `suggestion`
