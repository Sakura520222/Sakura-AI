# 依赖链审查经验（PR#473-PR#476教训）

## 核心教训

### "一行变更"认知陷阱
- 主版本号升级仅改一行 `requirements.txt` 时，审查者倾向于降低严谨性
- **代码越简单，流程越不能省**：一行版本号的变更恰恰需要最严格、最全面的审查
- 它牵涉面广（影响所有运行环境）、风险隐蔽（潜在运行时错误）

### 依赖链"由点及链"验证路径
1. **框架自身破坏性列表**：逐条核对 Changelog Breaking Changes
2. **项目直接代码调用点**：用 grep 搜索被移除/重命名的 API，确认现有配置兼容
3. **插件/扩展生态兼容性**：验证所有直接依赖的插件（如 pytest-asyncio）的兼容性版本要求
4. **同类工作流文件一致性**：检查仓库内所有同类文件是否需统一版本

### 默认值是隐藏的 API
- 服务器组件（如 Uvicorn）的配置默认值变更等同于 API 行为变更
- 即使项目未配置该项，新默认值也可能改变运行时行为（如 HTTP 头信任策略）
- 安全和调试场景下尤为重要

## 自动化依赖 PR 审查要点

### 流程合规性优先检查
- **分支命名兼容性**：检查 Dependabot/Renovate 分支是否符合 Gitflow 策略
- **配置修改建议**：不符合时须同时附带 `.github/dependabot.yml` 的 `prefix`/`target-branch` 修改建议
- **PR 描述信息完整性**：验证自动化 PR 是否提供足够的变更日志和影响说明

### 安全影响验证
- 即使 PR 描述为"安全更新"，也必须通过代码搜索验证漏洞功能是否在项目中实际使用
- **"无影响"结论的权威性来源**：不等于"我看了觉得没事"，而是"我已执行`[具体命令]`，其`[具体输出]`证明无影响"

### 技术栈耦合意识
- 项目紧密依赖 FastAPI 生态（FastAPI → Starlette → Uvicorn → Pydantic）
- 升级其中一个须联动检查整个链条
- 版本约束精确性：`requirements.txt` 中的版本下界应反映项目测试和确认可用的最低版本

## 工具链集成闭环
引入或更新自动化工具（如 Dependabot）时：
1. 配置工具
2. 验证其产出物符合项目规范
3. 必要时修改项目规范以接纳新工具
- 这个闭环是 CI 绿灯的前提

## 自确认偏误防御
- **高评分负面检查优先**：评分 ≥7 时须先输出负面检查结果再写优点
- "安全"配置（如 `cancel-in-progress: true`）并非无害，审查需默认其"可能中断下游任务"
