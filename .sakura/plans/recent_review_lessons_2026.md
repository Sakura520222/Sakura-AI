# 最新审查经验教训与常见问题模式 (2026)

## 一、依赖更新与自动化 Bot 提交教训

### 1.1 “变更越小，越容易放松警惕”
- **现象**：Dependabot 或自动化机器人提交的依赖升级 PR 往往只有 `pyproject.toml` 的 2 行修改，极易让人误以为无风险而快速 Approve。
- **教训**：在开启 `uv sync --locked` 的 CI 体系中，未更新 `uv.lock` 会导致 CI 100% 失败。必须时刻保持 Fail-Closed 意识，对构建与锁定状态进行严格的链条追溯。

---

## 二、架构设计与用户感知/日志治理教训

### 2.1 “设计即如此”与“用户体验/日志噪音”的平衡
- **现象**：系统关闭某些功能后，底层 APScheduler 定时器仍保持运行（用于多副本观察 DB 变化），导致日志持续输出心跳信息（每天约 960 行）。
- **教训**：即使底层机制是“有意为之的架构设计”，其过程日志也必须被严格收敛。如果不收敛，会引发日志污染并对运维产生“功能仍在运行”的误导。必须在 `logging_bridge` 中收敛 INFO 级心跳日志。

## 三、代码契约与状态判断教训

### 3.1 状态与异常混淆的反模式防范
- **现象**：在检查资格/状态的辅助函数中，将“业务不符合资格（明确拒绝）”与“系统/网络异常（检查失败）”混淆并统一返回 `False`。
- **教训**：这种“三态归一”是典型的反模式，会导致 Fail-Closed 逻辑把临时网络抖动等可重试错误误判为永久失败。设计状态返回值时必须显式区分业务拒绝与异常失败。

### 3.2 元组契约变更的解包风险
- **现象**：辅助函数异常分支返回 `False`，而主路径返回 `(status, data, err)` 三元组，调用方无条件解包触发 `TypeError: cannot unpack non-iterable bool object`。
- **教训**：修改返回类型或异常分支时，必须建立“返回值-解包签名” pairs 的全面排查，确保调用方解包契约一致。

## 四、前端交互与恢复路径教训

### 4.1 UI 修改遗漏恢复路径 (Restore Path)
- **现象**：修复前端文本格式化或渲染逻辑时，仅重构了用户主动点击/交互的回调，忽视了页面刷新后的恢复函数（如 `restoreProgressTarget()`）。
- **教训**：前端 UI 修改不仅要核验实时渲染路径，还必须追踪 DOMContentLoaded 或页面中断恢复时的二次渲染逻辑，确保格式化逻辑完全统一。
