# 经验与改进计划

## 流程改进

- 对大型 PR 采用“架构优先分层审查”：先架构扫描（模块/依赖/数据流/Schema）再高风险区深挖，最后细节补漏。
- quick 策略的文件过滤逻辑需排查，避免 21→2 这类严重覆盖失败。
- 为 unknown 决策加兜底（如自动降级为 request_changes），并要求给出明确结论。

## 质量门禁

- 添加 PR 规模与策略校验与提示；对增量审查标记主体是否已全量审查。
- 强制评论数量与评分的关联校验，避免无评论高评分。

## 技术实践

- Linter：建议引入 mypy 或启用 pyright 严格模式，提前暴露类型契约错误。
- 建议代码的正确性校验：给出修复建议时需验证是否与规范与语言语义一致。

## 代码审查习惯

- 溯源思维：处理属性/键值报错时应溯源到数据构造点，确认数据模型真面目。
- 警惕“点状修复”：Bug 常指向设计缺陷，应排查同类模式的全局泛滥情况。
- 避免点位疲劳：先输出架构影响分析再进入细节审查，防止架构级盲区。
- 检查 asyncio.gather 失败模式与错误传播。

## 防御与一致性

- 同一 PR 内防御性编程与校验策略应保持一致。
- 新增大文件时要求输出结构概览，避免对 800+ 行服务仅点位审查。
