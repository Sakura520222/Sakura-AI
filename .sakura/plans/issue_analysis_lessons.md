# Issue 分析经验教训

## 1. 区分"症状"和"根因"
- **症状≠根因**："无法访问"只是症状，可能原因包括配置缺失、依赖冲突、数据库连接失败、端口映射错误等
- **不能直接套用历史问题**：不能因为仓库历史上出现过 Starlette 问题，就直接套用到当前 Issue

## 2. 日志中的直接信号应优先分析
- **最直接的信号**：如 `Config file '{env_file}' not found.`
- **未来检查清单**：
  - `.env` 是否要求必须存在
  - 示例配置文件是否完整
  - 缺失配置时是否应该 fail-fast
  - 日志是否正确打印实际路径
  - 安装文档是否明确说明创建配置文件
  - Docker/Compose 是否正确挂载环境变量

## 3. 依赖兼容性问题需要版本证据
- **至少具备以下证据之一**：
  - `pip freeze`
  - `requirements.txt`
  - Docker 构建日志
  - 完整 traceback
  - 可复现命令
  - 代码调用点
  - 官方 release note 链接
- **否则标注为"可能原因"**：不能直接作为确定结论

## 4. 重复检测不能只看症状
- **"无法访问"类 Issue 容易误判重复**：重复检测应基于：
  - 相同错误栈
  - 相同依赖版本
  - 相同复现步骤
  - 相同修复方式
  - 相同影响模块
- **如果只是表象相同**：应标为"可能相关"而非"重复"

## 5. 建议增加 `needs-info` 流程
- **对于信息不足的 Issue**：分析结果中应主动生成追问清单
- **示例追问**：
  - 安装方式：源码 / Docker / Docker Compose？
  - Python、FastAPI、Starlette、Jinja2 版本
  - 完整启动日志和访问时报错栈
  - 是否创建了 .env 文件，是否基于 .env.example
  - 访问的具体 URL、HTTP 状态码
  - 是否使用默认配置

## 6. 过度确定是高风险
- **标题锁定根因需谨慎**：如果没有完整 traceback 或依赖版本证据，将问题过度锁定为某个根因是高风险的
- **标题应反映用户真实问题**：在证据不足时，标题应先反映用户真实问题，而不是提前锁定根因

## 7. 元 bug 的特殊性
- **自动打上 `self-referential` 标签**：当系统分析自身 Issue 时，应自动打上 `self-referential` 标签
- **启用额外安全检查**：如截断 recursion depth
- **降级输出必须显式标记状态**：所有降级输出必须附带唯一错误码，并通过日志记录原始错误详情

## 8. 硬编码错误信息的危险
- **违反原则**：三个降级路径都返回了静态字符串"无法评估"，导致用户无法区分是"系统故障"还是"Issue 本身不可评估"
- **违反核心原则**：这违反了"内部错误信息禁止泄漏至用户界面"原则
