# Sakura AI Reviewer 项目概述

## 1. 项目简介与技术栈
Sakura AI Reviewer 是一款基于大语言模型的智能 GitHub 代码审查与 Issue 分析机器人。

- **后端语言**：Python 3.11+
- **Web 框架**：FastAPI
- **前端界面**：HTML（自包含 WebUI）
- **数据库**：MySQL、Redis
- **AI 与检索**：LLM API、RAG 向量检索
- **基础设施**：Docker、Docker Compose
- **代码规范**：Ruff
- **集成渠道**：GitHub App、Telegram Bot

## 2. 架构设计与关键决策
- **分层架构**：API 层、服务层、数据访问层分离
- **服务层职责边界**：`comment_service` 为行内评论渲染唯一入口
- **集中式结果解析器**：AI 输出清洗收敛于 `result_parser.py`
- **配置三层穿透**：Settings → yaml_config → 硬编码默认值
- **降级标志传递模式**：布尔标志沿调用链传递失败语义
- **fallback 链路统一**：空字符串 → settings → yaml → 硬编码
- **fire-and-forget 范式**：`create_task` + `add_done_callback(discard)`
- **工具插件化架构**：统一工具注册与调用
- **全局异常处理器不得引用业务依赖**：不解析 token、不查数据库
- **版本号多源硬编码**：main.py、auth.py、init.sql 三处独立，无双向同步
- **配置全链路模式**：新增配置字段须在各层（Settings → SQL → UI 分组 → 文案）同步添加
- **服务层薄化演进**：逐步移除配置读取逻辑，将决策提交上移到 worker 层
- **i18n 延迟加载线程安全**：`_ensure_loaded` 须加锁或预加载
- **模板碎片化债务**：共用样式须提取为独立 CSS 文件，禁止双源维护

## 3. 已知问题和注意事项
- **错误处理不统一**：新代码应倾向显式错误传播
- **静默降级缺乏可见性**：降级路径须产生 warning 日志
- **`except Exception` 无日志视为静默失败**：违反可观测性规范
- **轮询缺少强制失败出口**：启动循环须超时检查 + exit≠0
- **外部依赖失败必须显式降级**：返回 None 或抛异常，禁止空列表
- **配置解析红线**：禁止 `.replace().split()` 解析标签列表
- **配置假值陷阱**：须用 `is not None` 而非 Truthy 检查
- **增量审查全局意图保护**：聚焦局部 diff 易忽略整体意图
- **双重格式化陷阱**：下游再次调用 format 会破坏结构
- **测试隐式全局状态**：不依赖隐式全局 fixture，须显式 mock
- **版本号漂移风险**：Python + SQL 多语言硬编码，无中心化管理
- **CHANGELOG 文化缺失**：minor/major 升级建议强制起草条目
- **历史问题风险升温**：新功能上线须重新评估既有问题影响范围
- **可变单例并发安全**：`@lru_cache` + `setattr` 修改须加锁或注释策略
- **配置开关与既有数据库兼容性**：新增字段后旧记录的默认行为（NULL vs 默认值）须显式处理
- **双重降级检查路径的隐式风险**：同一开关在多处独立检查可能导致维护不一致
- **降级标志分散检查**：缺乏统一的门面函数，各服务独立实现相同逻辑
- **死代码保留无注释**：未调用的条件分支须注释预期调用者或未来用途
- **注释维护成本**：硬编码方法名或路径的注释，连续 3 轮未修复应升级为 minor
- **跨模块导入删除风险**：删除导入前必须全仓库引用搜索，避免 `from module import *` 破坏
- **动画性能风险**：大量绝对定位飘落花瓣可能导致低端设备重绘/重排问题
- **无障碍一致性传播遗漏**：`prefers-reduced-motion` 等增强须同步所有同类页面
- **毛玻璃深色模式对比度风险**：`bg-white/70` 在深色模式下文字对比度可能不足
- **响应式窄屏布局溢出**：新增大内边距/圆角/阴影可能导致横向滚动
- **PR 描述与变更内容严重不符**：须作为 critical 级别问题阻断合并
- **i18n 前端注入脆弱性**：`document.write` 禁止用于动态内容注入，须用 `x-text` 或 `innerText`
- **toast 消息硬编码**：所有用户可见消息必须使用 i18n 函数
- **翻译键语义验证缺失**：键名与显示内容必须匹配，禁止错用（如 `description` 用于耗时）
- **JS 端 i18n 集成遗漏**：HTMX 回调、Alpine 组件中的文本须统一使用 `window._t`
- **API 错误消息未国际化**：`/api` 端点返回的 JSON 错误须按用户语言输出

## 4. 审查中发现的重要模式
- **微小变更审查价值**：行数少 ≠ 风险低
- **增量隧道视野**：对新增字段完整生命周期缺乏追踪
- **suggestion 疲劳归档机制**：第 2 轮未修复降级，第 3 轮强制归档
- **增量审查两重责任**：追踪历史修复 + 覆盖本次意图
- **“删除优于修复”模式**：冗余功能删除比修补安全
- **幽灵 PR 模式**：描述与提交内容严重不符须阻塞
- **LLM 输出解析的不信任原则**：主动引入变异追问
- **增量审查全文检索原则**：数行变更也须检索全仓库同名函数
- **批量操作状态追踪规则**：维护实时更新的集合
- **防御式导入反模式**：API 从 webui 层导入预示分层腐化
- **异常处理器顺序敏感性**：注册顺序决定优先级
- **修复 + 新功能混合 PR 风险**：新代码单独列清单审查
- **属性注入倾向**：`**kwargs + setattr` 须强制白名单
- **审查遗漏语义版本验证**：版本号变动须与 PR 描述功能幅度对齐
- **配置三重归属模式**：字段定义、UI分组、UI标签三者易不同步
- **消费点散落**：同一配置开关在多条路径中分别检查，缺乏注册中心
- **配置热更新未验证**：动态配置字段是否支持运行时修改常被遗漏
- **增量审查与PR描述脱节**：描述提及 SQL/UI 但提交仅含代码时未标记风险
- **渐进式代码清理**：多次“删除未使用导入”的小步提交，保持 import 整洁
- **Tailwind 硬编码覆盖脆弱模式**：基于工具类名的选择器极易失效，须标注临时过渡
- **Jinja2 样式重复阈值**：两处相同样式允许，第三处必须提取为宏或 include
- **PR 描述视觉特性必须验证存在性**：动画、飘落效果等须确认 DOM 元素和 CSS 类正确挂载
- **重复工具函数散落模式**：`_t()`、`language_names` 出现 ≥2 次必须提取到共享模块
- **i18n 覆盖度嗅探**：扫描所有 `.html`、`.js`、路由中 `toast_`、`alert(` 检查硬编码字符串
- **注释债务标注模式**：TODO 必须包含 issue 关联和预期移除版本，否则连续 3 轮升级严重度
- **副本同步标记强制包含源位置行号**：复制代码注释必须标注源文件路径+行号范围

## 5. 团队约定和规范

### 审查硬规则
- **三问法**：major 须内联“用户影响/利用条件/现有缓解”
- **纯可读性封顶**：最多 suggestion
- **自评矛盾降级**：出现“风险可控”降一级
- **根因修复验证**：须回溯核心要求
- **配置默认值变更强制风险评估**：覆盖面、成本、兼容性
- **生命周期方法调用验证**：无调用标记 major
- **新功能闭环校验（major）**：新增字段须追踪完整生命周期
- **格式化/转换函数重复调用检查（critical）**：扫描全路径
- **日志可观测性三件套**：语义一致、不可信用 warning、扫描同类隐患
- **布尔标志控制流完整性检查**：验证无路径绕过
- **外部依赖失败显式降级（major）**：禁止返回空列表/空字典
- **配置解析红线（major）**：禁止 `replace().split()` 解析标签
- **批量操作状态追踪（major）**：维护实时更新集合
- **全局异常处理器不得引用业务依赖（major）**：只做格式转换
- **`except Exception` 必须记录日志（major）**：除非顶级循环
- **全局异常处理器禁止调用可能抛异常的函数（major）**：应重构而非掩盖
- **版本号升级检查清单（major）**：全仓库搜索 `version\s*=\s*["'][\d.]+["']`，并验证 CHANGELOG 草案
- **新增 SQL 字段须检查迁移脚本（major）**：`init.sql` 仅适用于新库，现有库需提供 `ALTER` 语句
- **降级标志必须单一事实来源（major）**：应抽取到共享模块
- **配置热更新验证（major）**：新增动态配置字段必须说明是否支持运行时热更新
- **降级标志全生命周期追踪（major）**：覆盖 UI、API、worker、migration、SQL、settings、log 七个消费点
- **PR 描述与变更内容一致性检查（critical）**：若描述中的功能/文件范围与提交差异超过20%或完全不符，须标记 critical 并要求修正
- **PR 描述视觉特性验证（critical）**：动画、飘落等可见特性必须确认 DOM 元素和 CSS 类真实存在且正确挂载
- **新增纯视觉动画性能评估（major）**：飘落、bounce 等动画须评估低端设备、长页面的重绘/重排风险
- **深色模式毛玻璃对比度验证（major）**：`bg-white/70` 等半透明背景必须验证文字对比度 ≥ 4.5:1
- **删除导入前全仓库引用搜索（minor）**：即使文件内无引用，须确认无跨模块导入
- **语义版本验证（suggestion）**：检查变动幅度与版本号一致
- **跨语言版本漂移标注（suggestion）**：Python + SQL 须标注风险
- **测试必须验证异常路径被真正触发（minor）**：Mock 具体异常类型
- **可变单例须注释并发安全策略（minor）**：是否加锁
- **死代码须加注释或移除（minor）**：保留未调用的条件分支时必须注释预期调用者
- **配置与注释分组一致性（minor）**：字段声明的注释分组须与 UI 分组实际归属一致
- **开关类配置的测试覆盖（minor）**：新增布尔开关至少有一个测试用例验证关闭时行为
- **配置开关可观测性强制检查（minor）**：关键路径必须记录 info 日志（含开关状态）
- **注释引用跨模块私有方法（minor）**：私有方法属于模块内部，注释须改为公开接口或功能描述
- **UI 配置变更须端到端验证（suggestion）**：确认配置项在界面可见、可保存、重启后不丢失
- **注释风格一致性规则（suggestion）**：同级配置块应强制使用相同分隔符格式
- **SQL 初始化脚本的可重入性（suggestion）**：使用 `INSERT IGNORE` 或 `ON DUPLICATE KEY UPDATE`
- **响应式窄屏布局检查（minor）**：新增大内边距/圆角/阴影不应导致布局溢出或横向滚动
- **样式重复提取阈值（minor）**：两处相同样式允许，第三处必须提取为 Jinja2 宏或 `{% include %}`
- **Tailwind 类名选择器须标注脆弱性（minor）**：基于工具类名的 CSS 覆盖选择器必须注释“脆弱，仅临时过渡”
- **国际化覆盖完整性检查（major）**：PR 声明 i18n 时，必须扫描所有模板、路由 toast、JS 字符串、API 错误消息
- **重复工具函数提取规则（minor）**：相同逻辑出现 ≥2 次必须提取到共享模块
- **常量字典集中定义规则（minor）**：`language_names` 等字典重复 ≥2 次必须集中定义
- **`document.write` 禁止规则（major）**：禁止用于动态内容注入，改用 `x-text` 或 `textContent`
- **toast 消息强制 i18n（major）**：所有 `toast_redirect` 调用处必须使用 i18n 函数
- **连续 3 轮未根治问题自动升级（major）**：历史存在 3 轮的相同问题，即使有注释，也从 suggestion 升为 major
- **PR 评分趋势分析（suggestion）**：若连续多轮评分相同，审查应说明“为何未进步”或“债务被接受”
- **副本同步完整性验证（minor）**：注释声称“复制自 xxx”时，必须 diff 验证内容一致性
- **临时选择器必须标注预期移除版本（minor）**：脆弱选择器除 TODO 外，必须注明“计划于 vX.X 移除”

### suggestion 疲劳归档协议
- 第 1 轮未修复：评估降级
- 第 2 轮未修复：强制降级
- 第 3 轮未修复：强制归档并从主评论移除

### 版本管理补充规范
- 版本号变更须搜索正则 `version\s*=\s*["'][\d.]+["']` 防止动态拼接遗漏
- PR 描述功能与版本号语义对齐验证（新增付费系统应确认为 minor）
- 增量审查须评估历史问题在新功能上线后的风险等级变化（升温/降温）
- 版本号升级 PR 必须验证 `__version__` 单一真实源是否存在
- 版本号升级 PR 必须附带 CHANGELOG 草案
- 数据库默认值变更必须评估已有数据迁移并提供 UPDATE 语句

### 增量审查补充规范
- 增量审查必须扫描 PR 描述中的所有提及文件（即使提交列表不含某文件）
- 多文件变更的原子提交要求：PR 描述涉及 SQL/UI 但提交仅含 config 时须标记并要求拆分或补充
- 增量审查必须自动执行 `grep` 扫描 PR 描述中提到的所有配置字段名，覆盖 Python + SQL + 前端配置映射
- 增量审查中注释引用的任何符号须确认存在性，私有成员须标注稳定性风险
- 任何 import 删除必须触发全仓库引用扫描
- 连续 3 轮相同评分须触发架构讨论：是否安排专门 PR 彻底重构债务
