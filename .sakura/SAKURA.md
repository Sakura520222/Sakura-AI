## 3. 审查核心原则
- 审查须核对 PR 描述、提交信息(type/scope 须与文件匹配)、文件清单与 diff 一致性；**描述中可枚举功能点须逐项勾选表，未勾选直接标 minor**；描述与diff数字差异>10% 须标 minor。
- 增量审查须声明范围+双轨评分(增量质量+PR 整体评估)；历史 major 未清零评分上限 8；quick 上限 8。
- approve 须逐项声明未解决已知问题(>=minor)状态；request_changes 须对应明确 major/blocking。
- 正面评价越多越先做负面检查(隧道视野防范)；**高评分场景须强制先输出负面检查结果再写优点**。
- quick 策略须强制输出自检清单：决策完整性、上限、负面检查，**未全勾不允许输出**。
- 结构化评论只发布具体可操作问题；摘要/评分不得转 review comment。

## 4. 硬规则
1. async 路由同步 I/O 须 asyncio.to_thread()。
2. 延迟导入须注释；配置废弃须全链路清理。
3. DB 枚举/状态新增须检查迁移+状态转移矩阵+超时逃脱。
4. DB schema 变更须检查 nullable/default/事务/并发。
5. LLM prompt 外部输入须有截断+清洗/包裹；移除截断须验证等效控制否则 major。
6. 终态方法缓存须验证清理(finalize=True)，遗漏=major。
7. 布尔/状态枚举新增须 grep 所有消费点。
8. 重复检测须含证据链(标题+相似+差异+结论)。
9. 大 PR(>=5k行)须逐模块审查；重构>=100行须声明测试/返回值/异常等价。
10. constants 变更须列消费方；软删除引入须追问累积/清理/恢复。
11. 安全相关须区分漏洞 vs 误杀(三角验证)。
12. 支付/计费变更须输出兼容性/回滚检查。
13. 新增 worker 须验证防重/重试/超时；映射表须有清理计划。
14. 重构(提取/统一)类变更须强制双轨声明：测试全通过+返回值一致+异常等价。
15. 等量替换文件(+N/-N, N<=30)须逐变更点列出before->after并声明等价性。
16. 可观测性端点(`/health`等)字段值变更须视为接口变更。
17. 前序问题标记"已修复"须有依据：当前diff含相关文件 或 显式引用历史增量编号。
18. 同一suggestion连续>=3轮未处理须标注"长期搁置"并评估是否降级关闭。
19. GitHub Check Run / webhook / worker 类状态修复必须先检查身份、状态、回收三者是否统一。
20. 预创建资源若由异步 worker 接管，必须核对接管协议：创建者、接管者、稳定 ID、失败清理。
21. 重构 + 功能扩展的组合 PR，不能按纯重构降级。
22. 配置/Provider/Wizard 类 Issue 不能粗分为 other；必须拆解配置源、配置流、协议差异。
23. Issue 分类与标签不得空输出：至少给出最贴近的候选标签。
24. 对"看似只是重写/统一"的需求，必须同步检查是否包含新协议支持。
25. 依赖更新须对照上游Changelog逐项确认破坏性变更影响；核心库升级即使approve也须附风险提示。
26. quick策略输出前须强制声明`[x] quick 上限 (8/10)`校验。
27. GitHub Actions大版本升级须逐条核对Breaking Changes。
28. 自动化工具(Dependabot等)生成的PR，描述覆盖度以最终合并后主diff为准。
29. 模糊治理类Issue应先建议`needs-information`标签并要求提供具体清单。

## 5. Agent/Worker/Webhook
- Agent 基类变更须列调用方检查返回值/异常/状态语义。
- Shell 白名单!=安全须检查 $()反引号;&&|&等；输出须双层限额。
- 长连接/worker 禁止 except:continue 无日志无退避。
- webhook 须检查签名/幂等/乱序/重复；成本是安全新维度。

## 6. FastAPI/WebUI
- CSRF/认证不得依赖必填校验；新路由须确认认证链路。
- /health 字段变更须检查同步与监控兼容；新字段须检查 i18n。

## 7. 测试与报告
- 安全解析须单测边界；fake 须贴近生产；审查输出须合规性自检。

## 9. 最新反思(PR #441-456)关键教训
- **Quick策略元规则执行**：评分超限(>8/10)属于元规则违反，严重程度高于漏报代码问题；高评分须触发负面检查优先
- **依赖更新深度审查**：Major升级须逐条核对Changelog Breaking Changes+grep项目代码确认调用点；证据链标准化（即使"无影响"也须附grep验证摘要）
- **GitHub Actions大版本升级**：v5→v7等跨大版本升级须逐条核对废弃参数，在所有工作流文件中搜索确认兼容
- **核心运行时升级**：Python 3.11→3.14等跳跃须列举核心依赖、查证兼容性、要求完整构建日志和冒烟测试
- **Dependabot/Gitflow冲突**：自动化工具分支命名须与Gitflow策略兼容，CI失败须附工具配置修改建议
- **审查工具鲁棒性**：工具失效时须降级输出带错误码的COMMENT，规则执行>规则制定
- **Issue分析质量**：重复检测必须带证据链；短Issue先语义判断再代码分析；标签推荐须匹配仓库标签体系
