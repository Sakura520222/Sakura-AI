# Sakura AI Reviewer 项目概述

## 1. 项目简介与技术栈
Sakura AI Reviewer 是一款基于大语言模型的智能 GitHub 代码审查与 Issue 分析机器人，具备主动探索代码库、跨文件依赖理解和全仓库扫描能力，旨在自动化提升代码质量管理与日常协作效率。

- **后端语言**：Python 3.11+
- **Web 框架**：FastAPI
- **前端界面**：HTML（自包含 WebUI）
- **数据库**：MySQL（关系型存储）、Redis（Pub/Sub 实时通信与缓存）
- **AI 与检索**：LLM API 对接、RAG 向量语义检索、DuckDuckGo/Tavily Web 搜索
- **基础设施**：Docker、Docker Compose
- **代码规范**：Ruff（Linter 与 Formatter）
- **集成渠道**：GitHub App（Webhook/OAuth）、Telegram Bot

## 2. 架构设计与关键决策
- **分层架构**：API 层、服务层、数据访问层分离
- **错误处理策略**：当前存在分裂（同服务内抛异常与静默降级共存），属于已知技术债务，单次 PR 内不根治，需作为项目级决策统一

## 3. 已知问题和注意事项
- **错误处理不统一**：部分场景抛异常、部分场景静默降级，缺乏一致策略，新代码应倾向显式错误传播
- **分支查找 fallback 路径**：`_find_open_sakura_branch` 返回 `None` 时，下游 `_commit_via_pr` 必须正确 fallback 到创建新分支，此处为历史易错点
- **"部分修复比未修复更危险"**：标记"已修复"时若验证不充分，容易掩盖残留问题

## 4. 审查中发现的重要模式
- **"标记-不修-再标记"循环**：连续多轮标记同一问题但开发者不修复，说明严重程度判定与开发者认知不匹配，审查侧应反思判定标准而非重复标记
- **修复验证停留在"是否修改"层面**：增量审查易陷入对照清单打勾陷阱——看到改了就打✅，不验证改得对不对、调用链是否完整
- **quick 策略颗粒度失配**：quick 审查产出应精简（≤200字），但实际易出现"quick的速度 + deep的格式"，导致评论膨胀
- **知行分离模式**：摘要中写出降级理由（如"风险可控"），却在评论中维持原严重级别，说明写摘要时未触发自检

## 5. 团队约定和规范

### 审查硬规则（强制执行）

**三问法强制绑定**：所有 major 级别评论必须内联三问答案，无答案则不得标 major。

**自评矛盾检测**：摘要中出现"风险可控""影响有限"等降级表述时，必须自动将相关评论降级，禁止摘要与评论严重程度矛盾。

**评论去重与合并**：同一代码位置的不同表述必须合并为一条评论，禁止拆分标记。

**修复验证须含调用链**：标记"已修复"时，必须验证修改点的上游调用和下游消费是否一致传递，否则只能标"待验证"。

### suggestion 疲劳归档协议
- 第 1 轮未修复：评估实际影响，考虑是否直接降级
- 第 2 轮未修复：强制降级为 suggestion
- 第 3 轮未修复：强制归档并从主评论移除，仅保留在摘要追踪表格中

### quick 策略执行约束
- 历史追踪项在 quick 模式下**只进摘要表格，不生成独立评论**
- 纯改善性建议（如类型注解补全）在 quick 模式下属于噪声，不应提出
- ≤27 行变更的 quick 审查报告应≤200 字

### 降级信号词清单
以下表述出现在摘要中时，自动触发对应评论降级自检：风险可控、影响有限、极少出现、边缘场景、可接受
