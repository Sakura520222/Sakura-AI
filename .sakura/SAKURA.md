# Sakura AI Reviewer 项目概述

## 1. 项目简介
基于大语言模型的智能 GitHub 代码审查与 Issue 分析机器人。

**技术栈**：Python 3.11+、FastAPI、MySQL、Redis、Docker、GitHub App、Telegram Bot

## 2. 架构设计
- 分层架构：API 层、服务层、数据访问层分离
- 配置三层穿透：Settings → yaml_config → 硬编码默认值
- 动态配置系统：统一接口处理 None/非法值降级并记录 warn
- 工具插件化架构：统一工具注册与调用

## 3. 审查核心模式
- **微小变更审查价值**：行数少 ≠ 风险低
- **"删除优于修复"模式**：冗余功能删除比修补安全
- **连续 3 轮未根治问题自动升温**：升级为 major→critical
- **增量审查必须检查关联文件**：避免功能碎片化
- **异常日志级别统一规范**：`except Exception` 后必须使用正确日志级别
- **测试文件深度验证**：强制检查测试用例与新增逻辑的匹配度
- **跨流程数据一致性验证**：涉及多流程变更必须检查核心数据一致性

## 4. 审查硬规则（major/critical）
1. **未修复历史问题必须关联 issue 号**
2. **延迟导入必须注释原因**：函数体内 import 若无注释说明循环引用原因，阻断合并
3. **异步路由同步调用包装强制化**：所有 async 路由中的同步 I/O 必须使用 asyncio.to_thread() 包装
4. **配置废弃全链路清理**：配置字段废弃时必须从代码、UI配置页面、动态配置键列表中全链路清理
5. **SSE 异常日志强制记录**：所有 SSE 发布必须记录异常日志，禁止静默失败
6. **工具安全边界审查**：新增工具必须检查命令链绕过风险，标记为 major
7. **新增状态枚举的全链路审查**：新增枚举值必须检查 DB ENUM/迁移、历史数据回填、API返回、WebUI 模板/i18n/过滤器、SSE 事件发送与前端接收
8. **测试函数命名规范强制检查**：所有测试函数必须以 `test_` 前缀命名，增量审查中强制验证测试文件结构
9. **异常日志级别统一规范**：`except Exception` 后必须使用正确日志级别
10. **增量审查全链路检查**：高频修改文件必须强制检查关联文件，避免功能碎片化
11. **全局状态并发安全规则**：标记模块级单例变量为major风险，要求评估热更新场景下的重置逻辑
12. **数据库迁移完整性检查表**：强制PR输出迁移脚本覆盖范围，包括已有部署的ALTER TABLE语句
13. **大文件拆分规范**：单文件超过1000行时强制建议拆分，提升可维护性
14. **测试数据完整性检查**：增量审查中必须验证测试payload是否同步补全对应字段
15. **权限跳过逻辑的强制注释规范**：要求所有权限跳过场景必须在注释中明确说明原因和安全影响
16. **Webhook事件字段校验**：强制检查GitHub Webhook事件类型与关键字段的匹配性

## 6. 最新审查模式（PR #334 增量审查）
- **常量派生审查**：强制检查常量自动化派生函数的测试覆盖度和边界防护
- **调用方验证**：新增/修改工具函数必须强制检查所有调用点，避免功能碎片化
- **阻断性风险标识**：可导致服务启动失败的错误必须标记为阻断（critical/major）
- **增量审查覆盖度保障**：强制检查关联文件，避免因只看增量部分而下降覆盖度
- **新增审查规则**：
  - **常量派生函数强制测试**：任何从源数据派生常量的私有函数必须附带单元测试（标 major）
  - **配额消费顺序规范**：强制要求"验证 → 扣费"顺序，对任何资源消费操作标记为 major 风险
  - **表单路由一致性检查**：前端模板新增表单时必须同步检查后端路由是否存在（标 major）
  - **统计查询数据隔离**：所有统计类查询必须验证 owner 过滤，防止数据泄露
