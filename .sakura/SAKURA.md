# Sakura AI Reviewer 项目概述

## 1. 项目简介与技术栈

Sakura AI Reviewer 是一款基于大语言模型的智能 GitHub 代码审查与 Issue 分析机器人。

- **后端语言**：Python 3.11+
- **Web 框架**：FastAPI
- **前端界面**：HTML（自包含 WebUI）、Alpine.js、HTMX
- **数据库**：MySQL、Redis
- **AI 与检索**：LLM API、RAG 向量检索
- **基础设施**：Docker、Docker Compose
- **代码规范**：Ruff
- **集成渠道**：GitHub App、Telegram Bot

## 2. 架构设计与关键决策

- **分层架构**：API 层、服务层、数据访问层分离，路由层禁止直接操作数据库
- **集中式结果解析器**：AI 输出清洗收敛于 `result_parser.py`
- **配置三层穿透**：Settings → yaml_config → 硬编码默认值
- **动态配置系统**：`get_dynamic_config` 统一接口，处理 None/非法值降级并记录 warn
- **工具插件化架构**：统一工具注册与调用
- **全局异常处理器不得引用业务依赖**
- **i18n 门面模式**：`render_template` 统一注入 `_()` 和 `lang`
- **服务层自治事务模式**：服务方法内部自行 commit
- **幂等共享信号模式**：取消任务时多排队任务共享 asyncio.Event
- **批量操作 savepoint 模式**：循环中使用 `begin_nested()` 替代全局 rollback
- **权限策略单一真实源**：所有角色判断调用策略函数
- **内存回退字典必须实现大小/TTL 限制**
- **安全操作必须记录审计日志**

## 3. 已知问题和注意事项

- **错误处理不统一**：新代码应倾向显式错误传播
- **`except Exception` 无日志视为静默失败**（major）
- **配置假值陷阱**：须用 `is not None` 而非 Truthy 检查
- **版本号多源硬编码**：main.py、auth.py、init.sql 三处独立
- **i18n 翻译覆盖不完整**：toast 消息、API 错误响应易硬编码
- **中文 Token 估算缺陷**：`len(content)//4` 是近似值
- **字符串前缀移除禁止使用 `lstrip`**：必须使用 `removeprefix`
- **整数配置必须同时校验类型 + 范围**（major）
- **动态配置读取调用方须处理 None/非法值并记录 warning**（major）
- **配置迁移必须输出“迁移完整性检查表”**
- **禁止路由层裸写 `int(request.form.get(...))`**：必须统一封装并记录 warn
- **配置默认值必须唯一声明于 `config.py`**（major）
- **Shell 命令白名单匹配禁止使用前缀匹配**（major）
- **BackgroundTasks 不适合长时间运行任务**（major）
- **事务外的外部写入必须支持补偿或异步**（major）
- **新增公共功能模块必须至少有一处调用路径**（major）
- **WebAuthn challenge 消费失败后必须失效并重新生成**（major）
- **测试中的 mock datetime 必须显式验证时区参数**（minor）
- **延迟导入必须注释原因**（major）
- **同步函数中使用 `get_running_loop().create_task` 时，无法创建任务必须记录 warning**（major）
- **`asyncio.create_task` 后台任务需评估服务 shutdown 时的丢失风险**（major）

## 4. 审查中发现的重要模式

- **微小变更审查价值**：行数少 ≠ 风险低
- **增量隧道视野**：对新增字段完整生命周期缺乏追踪
- **“删除优于修复”模式**：冗余功能删除比修补安全
- **连续 3 轮未根治问题自动升温**：升级为 major→critical，第 4 轮自动生成 issue
- **配置与消费的对称性审查**：每看到一个新增配置字段，强制扫描其唯一读取位置
- **CSRF + JSON API 组合**：成为固定审查项
- **配置迁移中的“隐性删除”**：重构简化时须逐行比对旧逻辑的边界条件
- **就地修改 + 别名引用陷阱**：名字暗示快照但实际不是的变量须警惕
- **“双防线”依赖惯性**：前后端同时校验易在重构中被部分删除
- **配置解析函数必须记录 warning 日志**（配置降级时）
- **测试中修改全局缓存必须使用 fixture 或 finally 确保清理**（major）
- **“惰性清理 + 无上限”重复出现**：应统一 TTL LRU 缓存工具类
- **双路径不一致**：API 与 WebUI 新增功能必须对比限流/CSRF/错误处理
- **操作顺序审查优先级提高**：Redis + DB 操作必须检查补偿逻辑
- **异步调用方式必须统一**：同一模块内 fire-and-forget 全部使用 `create_task` 或全部使用 `await`，禁止混合
- **函数副作用必须在 docstring 中用 `⚠️` 标注**
- **UI 变更必须检查 JS 事件绑定是否依赖精确 DOM 结构**
- **模板中内联 SVG 装饰图标必须添加 `aria-hidden="true"`**

## 5. 团队约定和规范

### 审查硬规则（major/critical）
- 三问法：major 须内联“用户影响/利用条件/现有缓解”
- `except Exception` 必须记录日志
- i18n 扫描完整性：全覆盖，禁止硬编码
- 所有用户输入验证端点必须有速率限制
- 所有 JSON API 端点（除公开只读）必须显式使用 CSRF
- 整数配置必须同时校验类型 + 范围
- 动态配置读取调用方须处理 None/非法值并记录 warn
- 类型转换与范围校验必须原子化
- Shell 命令白名单精确匹配
- BackgroundTasks 长任务风险评估
- 测试缓存清理必须异常安全
- 未修复历史问题必须关联 issue 号（TODO(issue-xxx)）
- 公开登录端点 CSRF 豁免必须注释安全边界
- PR 描述与变更文件必须一致

### suggestion 疲劳归档协议
第 1 轮未修复：评估降级 | 第 2 轮未修复：强制降级 | 第 3 轮未修复：强制归档

### 增量审查补充规范
- 必须输出“已检查的规则清单”（最少 10 条）
- 必须输出“历史未解决问题清单并升温”
- 必须输出“未直接测试但依赖的调用链”
- 配置迁移 PR 必须输出“迁移完整性检查表”
- 观察点必须有后续行动：不得仅列出不创建 issue
- 新增配置字段检查表：唯一性、默认值兼容性、所有读取路径的 None 处理、写入路径与缓存失效成对
- 测试断言必须引用生产常量，禁止硬编码
- 变更模板文件时，必须输出该模板被哪些路由/端点使用的清单

### 常量与配置规范
- 常量定义位置与语义保持一致
- 配置更新操作必须触发缓存失效验证
- 工具函数必须位于约定公共模块（utils/、core/）

### 日志与可观测性
- 新增异常处理器必须记录 warn 级别日志
- 配置降级路径必须有 warning 日志
