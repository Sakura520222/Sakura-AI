# Sakura AI Reviewer 项目概述

## 1. 项目简介与技术栈
基于大语言模型的智能 GitHub 代码审查与 Issue 分析机器人，具备跨文件依赖理解、全仓库扫描和项目记忆能力。
- **技术栈**：Python 3.11+ / FastAPI / MySQL & Redis / LLM & RAG / Docker / GitHub App & Telegram Bot

## 2. 架构设计与关键决策
采用后端分层架构，前后端同仓：
- `backend/api/`：路由；`core/`：配置与依赖注入；`models/`：数据结构
- `backend/services/`：核心业务（AI审查、记忆系统、RAG等）
- `backend/workers/`：异步任务；`telegram/`：Bot交互；`webui/`：前端
- **关键决策**：业务规则 YAML 外部化热更新；耗时任务 Worker 隔离；容器化交付。

## 3. 已知问题与注意事项
### PR194 遗留缺陷（未闭环）
- **`local_repo_adapter.py` 路径遍历**：`os.path.join` 拼接外部输入且无 `.resolve()`，critical 级安全漏洞
- **`_LocalContentFile` 属性缺失**：未实现 `size`、`sha`、`url`、`html_url`、`git_url`，下游访问会静默失败或抛异常
- **`get_contents` 多态语义未保持**：PyGithub 对目录返回 `list[ContentFile]`，对文件返回单个对象，本地实现未保持此行为
- **适配器方法覆盖不全**：`get_branches()`、`get_pull()` 等方法可能缺失，扫描工具链可能不止用到 `get_contents`
- **ref/sha 参数静默忽略**：无日志、无警告、无异常，调用方产生错误假设
- **`_detect_default_branch` 静默回退 "main"**：入口处静默失败会导致整个扫描结果无意义
- **`repo_name.split("/", 1)` 无防御**：webhook 数据理论上可控但缺少防御层
- **AST 路径安全检查未生效**：`local_repo_adapter.py` 无 `.resolve()` 仍进入审查流程，需确认检查是否已实现

### PR190 遗留缺陷（未闭环）
- **`github_write_service.py:76`**：多文件提交非原子性，与 memory_service 并行化部分成功叠加可致数据不一致
- **`github_write_service.py:28-31`**：单例实现线程安全问题
- **`result["commit"]` KeyError**：PR 描述第5轮遗留，尚未确认是否已修复
- **`sakura_memory_service.py`**：800+行"上帝服务"，双数据源过渡态（dict回退+DB直查）、格式化逻辑分散、无重试回滚、并行化失败模式退化。需周期性全量审视
- **截断长度不一致**：同实体出现 `[:150]`、`[:200]`、`MAX_COMMENT_CONTENT_LENGTH=200` 三处不统一
- **`_fetch_comments_from_db`**：缺少 `review_id` 空字符串/无效格式防御校验

### 安全敏感点
- 路径处理禁用字符串检查、禁用 `PurePosixPath`，必须用 `Path.resolve()` + 前缀验证，需升级为 AST 硬性拦截
- 写操作服务必须审查权限边界与异常链路，安全/并发相关问题禁止降级

## 4. 审查发现的重要模式
- **"替换mock"系统性风险**：mock 隐含简化假设（不需要安全验证、参数语义、元数据），替换时必须逐一重新审视，"mock省略了什么"是第一条检查线索
- **防御性代码"隐形流失"**：用真实实现替换 mock/旧代码时，倾向认为真实数据源不会异常而丢弃防御层
- **"接收但忽略"反模式**：参数被接收后完全丢弃，比抛异常更危险——调用方产生"传了参数所以行为正确"的错误假设
- **适配器不适配**：名义上适配器模式，实际鸭子类型硬凑——只要不报 AttributeError 就算成功
- **双数据源一致性裂缝**：主路径与 fallback 返回对象结构不同，下游依赖元数据时产生难以排查的行为差异
- **空实现存根**：返回空值且无 TODO 标记，成为永久技术债
- **数据契约不严格**：跨模块混用 dict 与对象，缺类型注解
- **防御性编程表面化**：用高级 API 但不理解底层，产生虚假安全感
- **LLM 信任钟摆**：在"不信任"与"过度信任"间摆动
- **净减代码蜜糖效应**：需区分减少的是业务逻辑（好）还是防御代码（危险）
- **双服务脆弱性叠加**：上游部分成功+下游非原子提交=数据不一致最短路径
- **`asyncio.gather` 暗礁**：默认任一异常取消全部，重构为并行时必须审查失败模式
- **微小 Diff 欺骗性**：增量高质量≠PR可合并
- **增量审查陷阱**：隧道视野、零评论高分走过场、找问题凑数拔高严重度

## 5. 团队约定与规范
### 代码规范
- 跨模块复杂数据禁止裸 `dict`，必须用 `Pydantic`/`dataclass`/`TypedDict`
- 文件路径操作必须使用 `pathlib`，安全场景严格禁止 `Pure` 系列路径
- 魔法数字≥2次必须提取为常量（`constants.py`）
- 延迟导入：确认无循环导入风险且无性能优化意图时才可标记为问题
- 双数据源必须标注过渡期和收敛计划，返回类型须共享基类或 Protocol
- 移除防御性代码必须有等价替代或显式风险声明（`# SAFETY: ...`）

### 审查规则（按优先级）
| 规则 | 级别 | 触发条件 |
|------|------|----------|
| PR级阻断表强制 | P0 | 遗留 critical 每次必须出现，状态只可更新不可删除 |
| quick approve 检查 | P0 | approve 前必须确认遗留 critical 为 0，否则自动降级 |
| 历史阻断机制 | P0 | 未闭环 error/critical 时增量审查禁止 approve |
| 强制拦截词 | P0 | PR 含高危词时锁定 approve 权限 |
| 遗留降级禁令 | P0 | 禁止 Critical/Error 降级为 Suggestion |
| 评分评论支撑 | P0 | 评分必须有评论，9分以上需说明优点 |
| PR规模策略校验 | P0 | 文件>10 禁止 quick 策略 |
| 严重度三问法 | P1 | 标记 major 前：①实际bug？②运行时错误？③安全风险？全否降级；但接口契约违反（调用方会因类型不匹配报错）例外，保持 major |
| 并行化失败审查 | P1 | 串行改 gather 必须检查 return_exceptions、部分成功处理 |
| 防御代码移除审查 | P1 | diff 中删除 if/try/except 必须确认新代码有等价保护 |
| 跨服务链路推演 | P1 | 变更输出是已知问题服务输入时必须端到端推演 |
| 路径安全硬拦截 | P1 | 涉及路径拼接且无 .resolve() 直接 error，AST 拦截必须实现 |
| 适配器接口契约验证 | P1 | 必须列出被适配对象所有公共方法/属性，逐一确认实现或显式抛 NotImplementedError |
| 参数静默忽略禁止 | P1 | 方法签名含参数但实现完全忽略，必须抛 NotImplementedError / 记录 warning / 文档标注 |
| 双数据源类型一致 | P1 | 主路径+fallback 返回类型必须共享基类或 Protocol，否则 major |
| 入口静默失败升级 | P1 | 扫描入口处的静默回退至少为 minor，不可标 suggestion |
| 增量上下文引用 | P1 | 含历史上下文时必须输出问题状态更新表 |
| 评论结构隔离 | P1 | 区分[新增]/[历史遗留]/[确认修复]，禁止未修改文件混入行间评论 |
| 膨胀模块全量审视 | P1 | 持续增长模块需周期性全量审查 |
| 同提交重复审查拒绝 | P1 | 复审时提交 hash 未变应直接拒绝，区分"复审"与"重复审查" |
| 零修复评分下降 | P1 | 开发者对 critical 不响应就提交复审，评分持续下降直至触发阻断 |
