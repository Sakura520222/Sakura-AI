# Sakura AI Reviewer 项目概述

## 1. 项目简介与技术栈
Sakura AI Reviewer 是一款基于大语言模型的智能 GitHub 代码审查与 Issue 分析机器人，具备主动探索代码库、跨文件依赖理解和全仓库扫描能力，旨在自动化提升代码质量管理与日常协作效率。

- **后端语言**：Python 3.11+
- **Web 框架**：FastAPI
- **前端界面**：HTML（自包含 WebUI）
- **数据库**：MySQL、Redis（Pub/Sub 实时通信与缓存）
- **AI 与检索**：LLM API、RAG 向量语义检索、DuckDuckGo/Tavily Web 搜索
- **基础设施**：Docker、Docker Compose
- **代码规范**：Ruff
- **集成渠道**：GitHub App（Webhook/OAuth）、Telegram Bot

## 2. 架构设计与关键决策
- **分层架构**：API 层、服务层、数据访问层分离
- **服务层职责边界**：`comment_service` 为行内评论渲染的唯一权威入口；禁止上游预渲染 body 字段
- **集中式结果解析器**：AI 输出清洗、提取、格式化收敛于 `result_parser.py`
- **错误处理策略分裂**：同服务内抛异常与静默降级共存，属已知技术债务
- **配置三层穿透**：`Settings` → `yaml_config` → 硬编码默认值；新增配置须同步注册
- **配置与逻辑断层风险**：配置项、数据库字段和业务逻辑分布多处，易出现“假开关”
- **降级标志传递模式**：使用布尔标志沿调用链传递失败语义，替代空列表歧义
- **动态冲突检测模式**：批量操作时使用逐步更新的集合检测元素间冲突
- **fallback 链路统一**：空字符串 → settings → yaml → 硬编码默认值
- **fire-and-forget 范式**：`create_task` + `add_done_callback(discard)` + 实例级 set 持有引用
- **工具插件化架构**：统一工具注册与调用
- **防御式转义范式**：花括号转义为标配，但缺乏公共工具层
- **API 客户端 URL 拼接规范**：禁止 base_url 尾部带路径细节
- **跨层导入**：API 从 webui 层导入依赖时须注释理由，防止分层腐化
- **WebUI 与 API 共享依赖层**：`deps.py` 同时服务两端，存在循环依赖和部署解耦风险
- **异常处理分层焦虑**：全局异常处理器不得引用业务依赖（不解析 token、不查数据库）

## 3. 已知问题和注意事项
- **错误处理不统一**：新代码应倾向显式错误传播
- **静默降级缺乏可见性**：降级路径须产生 warning 日志，否则视为 silent-failure
- **日志级别可观测性**：对不可信数据修正/丢弃时须用 warning，debug 视为无效
- **轮询缺少强制失败出口**：启动等待循环须具备超时检查和 exit≠0
- **假修复与假闭环**：验证须推演完整执行流，安全问题不可仅文档化关闭
- **跨层截断风险**：模板截断 + Markdown 解析破坏语法
- **外部依赖失败必须显式降级**：失败禁止返回空列表/空字典，须返回 None 或抛异常
- **配置解析红线**：禁止使用 `.replace(',', ' ').split()` 解析标签列表
- **配置假值陷阱**：配置加载须用 `is not None` 而非 Truthy 检查
- **异步执行取消/超时风险**：`run_in_executor` 缺少 shield 或超时处理可能任务泄漏
- **幽灵变更与隧道视野**：PR 描述提及但审查遗漏的文件须强制核对
- **增量审查全局意图保护**：聚焦局部 diff 而忽略整体意图属经典陷阱
- **置信度降级的假兜底风险**：置信度强制置零须连带检查下游消费者的条件判断
- **双重格式化陷阱**：看到 `obj["body"] = format(...)` 应立即追踪下游是否也调用 format
- **401→login 与异常拦截器顺序冲突**：多个 `@app.exception_handler` 的注册顺序影响认证重定向逻辑
- **重复代码提取与性能权衡**：高频场景多次独立日志调用应考虑聚合或采样
- **降级日志的监控影响**：日志格式变更需通知运维或修改告警规则
- **测试中的隐式全局状态**：测试应显式 mock 配置、数据库、API，不依赖隐式全局 fixture

## 4. 审查中发现的重要模式
- **微小变更审查价值**：行数少 ≠ 风险低，能发掘深层洞见
- **打勾陷阱**：注意力绑定历史问题而忽略新风险
- **增量隧道视野**：聚焦局部深度足够但缺乏全局广度，对新增字段完整生命周期缺乏追踪
- **配置默认值变更的连锁阻塞**：未附风险评估的变更会卡住后续提交
- **suggestion 疲劳归档机制**：第 2 轮未修复降级，第 3 轮强制归档
- **增量审查两重责任**：追踪历史问题修复 + 覆盖本次提交整体意图
- **“删除优于修复”模式**：功能冗余时删除比修补更安全
- **幽灵 PR 模式**：描述与提交内容严重不符时必须阻塞
- **LLM 输出解析的不信任原则**：主动引入变异追问解析逻辑行为
- **增量审查全文检索原则**：即使仅数行变更，也应检索同名函数全仓库调用位置
- **批量操作状态追踪规则**：循环依赖“已有状态”判断时，必须维护实时更新的集合
- **防御式导入反模式**：API 模块从 webui 层导入业务依赖，预示分层腐化
- **异常处理器顺序敏感性**：多个 `@app.exception_handler` 注册顺序决定优先级
- **修复 + 新功能混合 PR 风险**：新引入代码需单独列清单独立审查
- **属性注入倾向**：`**kwargs + setattr` 多次出现，应强制白名单模式

## 5. 团队约定和规范

### 审查硬规则
- **三问法**：所有 major 须内联“用户影响/利用条件/现有缓解”；任一答案为“无”自动降级
- **纯可读性封顶**：封顶为 suggestion
- **自评矛盾降级**：出现“风险可控”等信号词自动降一级
- **根因修复验证**：引用高危区标签须回溯核心要求
- **修复验证须含调用链**：验证上游调用和下游消费一致性
- **配置默认值变更强制风险评估**：涵盖攻击面、资源成本、兼容性
- **AI 系统 prompt 变更审查**：高敏感，评估提示注入、语义漂移和工具滥用
- **生命周期方法调用验证**：无调用标记 major
- **容器/服务就绪轮询模式**：须含超时检查和失败退出
- **新功能闭环校验（major）**：新增数据字段须追踪完整生命周期
- **格式化/转换函数重复调用检查（critical/major）**：扫描数据全路径上的所有同名调用
- **服务层格式化唯一权威规则（critical）**：行内评论渲染仅允许在 `comment_service` 层执行
- **日志可观测性三件套**：①语义与行为一致；②不可信数据用 warning；③扫描同文件同类隐患
- **布尔标志控制流完整性检查**：引入布尔标志须验证无路径绕过
- **外部依赖失败显式降级规则（major）**：失败禁止返回空列表/空字典
- **配置解析红线规则（major）**：禁止 `replace().split()` 解析标签
- **批量操作状态追踪规则（major）**：循环依赖状态判断时须维护实时更新集合
- **PyGithub 返回类型守卫规则（major）**：使用 `get_contents()` 必须检查 type 属性
- **跨层导入注释规则（minor）**：API 从 webui 导入须注释理由
- **全局异常处理器不得引用业务依赖（major）**：只做格式转换
- **重复代码提取性能权衡（suggestion）**：高频日志调用考虑聚合

### suggestion 疲劳归档协议
- 第 1 轮未修复：评估实际影响考虑降级
- 第 2 轮未修复：强制降级为 suggestion
- 第 3 轮未修复：强制归档并从主评论移除
