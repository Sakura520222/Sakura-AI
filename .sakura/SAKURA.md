# Sakura AI Reviewer 项目概述

## 1. 项目简介与技术栈

Sakura AI Reviewer 是一款基于大语言模型的智能 GitHub 代码审查与 Issue 分析机器人。

- **后端语言**：Python 3.11+
- **Web 框架**：FastAPI
- **前端界面**：HTML（自包含 WebUI）、Alpine.js、HTMX
- **数据库**：MySQL、Redis
- **AI 与检索**：LLM API、RAG 向量检索
- **基础设施**：Docker、Docker Compose
- **代码规范**：Ruff
- **集成渠道**：GitHub App、Telegram Bot

## 2. 架构设计与关键决策

- **分层架构**：API 层、服务层、数据访问层分离
- **配置三层穿透**：Settings → yaml_config → 硬编码默认值
- **动态配置系统**：统一接口处理 None/非法值降级并记录 warn
- **工具插件化架构**：统一工具注册与调用
- **i18n 门面模式**：统一注入 `_()` 和 `lang`
- **服务层自治事务模式**：服务方法内部自行 commit
- **权限策略单一真实源**：所有角色判断调用策略函数
- **安全操作必须记录审计日志**
- **外部可见链接必须通过统一链接服务生成**（major）

## 3. 已知问题和注意事项

- **错误处理不统一**：新代码应倾向显式错误传播
- **`except Exception` 无日志视为静默失败**（major）
- **配置假值陷阱**：须用 `is not None` 而非 Truthy 检查
- **整数配置必须同时校验类型 + 范围**（major）
- **动态配置读取调用方须处理 None/非法值并记录 warning**（major）
- **Shell 命令白名单精确匹配**（major）
- **BackgroundTasks 长任务风险评估**（major）
- **未修复历史问题必须关联 issue 号**

## 4. 审查中发现的重要模式

- **微小变更审查价值**：行数少 ≠ 风险低
- **"删除优于修复"模式**：冗余功能删除比修补安全
- **连续 3 轮未根治问题自动升温**：升级为 major→critical，第 4 轮自动生成 issue
- **包装函数调用一致性检查**：若模块定义了包装函数用于测试替换，生产代码必须通过该包装函数调用
- **配置解析函数日志策略一致性**：所有 `resolve_*_config` 函数必须对降级路径记录 `logger.warning`
- **重构行为变更检查表**：抽取内联逻辑时，必须对比旧代码的所有边界条件和语义
- **历史问题追踪强制关联**：审查中发现的历史未修复问题，必须在PR描述中关联具体issue编号
- **异步路由中的同步I/O阻塞**：在 async 路由中直接调用同步 API 是常见反模式，必须使用 `asyncio.to_thread()` 包装
- **i18n 键完整性**：新增 UI 元素必须同步更新翻译文件
- **全量重审价值**：功能重构后全量审查能发现增量审查可能遗漏的系统性、跨文件问题
- **增量审查必须检查关联文件**：变更涉及公共函数时，需列出并验证所有调用点是否同步更新，避免功能碎片化
- **配置迁移完整性检查**：对于配置体系变更 PR，强制输出"迁移完整性检查表"，验证所有读取/写入位置对齐
- **动态配置降级处理**：新增配置读取必须检查 `get_dynamic_config` 返回 None 或类型不匹配，并提供降级逻辑（标 major）
- **公共端点依赖风险评估**：依赖第三方公开API/端点的变更必须添加注释说明稳定性假设及降级方案
- **业务逻辑函数必须说明取舍**：对于fallback或妥协性设计，强制在docstring中说明原因及未覆盖范围
- **JSON解析安全规范**：明确解析不完整JSON时的容错策略（如截断位置、反转义范围）
- **Major级问题必须明确阻断**：major问题应标"阻断合并"，在审查模板中强制注明
- **配置字段复用强制检查**：新增配置必须优先使用动态配置体系，硬编码需说明原因并标major
- **异常隔离原则**：独立功能检查应使用独立try/except，避免被上游逻辑异常阻断
- **参数边界值测试**：新增数值参数必须检查负数、零值、极大值场景，并在PR描述中说明处理逻辑
- **JSON解析回退路径注释规范**：当回退逻辑存在已知局限时，必须在代码中添加注释说明，标为minor
- **公共函数调用点全量检查**：增量审查中，若变更涉及公共函数，必须列出并验证所有调用点，避免功能碎片化，标为major

## 5. 团队约定和规范

### 审查硬规则（major/critical）
- **未修复历史问题必须关联 issue 号**
- **配置保存端点必须原子化**（major）
- **认证流程一致性**：Passkey与OAuth在头像获取、token构建等环节必须统一模式
- **新增状态枚举的全链路审查**：新增枚举值必须检查DB ENUM/迁移、历史数据回填、API返回、WebUI模板/i18n/过滤器、SSE事件发送与前端接收，标major
- **延迟导入必须注释原因**：函数体内import若无注释说明循环引用原因，阻断合并，标major
- **增量变更上下文影响检查**：增量审查需检查变更是否影响已缺失的 i18n 键或其他依赖项，标major
- **GitHub头像URL规范**：统一使用重定向端点（`avatars.githubusercontent.com/{username}`）而非API端点，以减少认证依赖和延迟
