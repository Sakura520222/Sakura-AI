# Sakura AI Reviewer 项目概述

## 1. 项目简介与技术栈
Sakura AI Reviewer 是一款基于大语言模型的智能 GitHub 代码审查与 Issue 分析机器人，具备主动探索代码库、跨文件依赖理解和全仓库扫描能力，旨在自动化提升代码质量管理与日常协作效率。

- **后端语言**：Python 3.11+
- **Web 框架**：FastAPI
- **前端界面**：HTML（自包含 WebUI）
- **数据库**：MySQL（关系型存储）、Redis（Pub/Sub 实时通信与缓存）
- **AI 与检索**：LLM API 对接、RAG 向量语义检索、DuckDuckGo/Tavily Web 搜索
- **基础设施**：Docker、Docker Compose
- **代码规范**：Ruff（Linter 与 Formatter）
- **集成渠道**：GitHub App（Webhook/OAuth）、Telegram Bot

## 2. 架构设计与关键决策
- **分层架构**：API 路由 → 服务层 → 数据层，业务逻辑内聚于 `services/`
- **配置与代码分离**：标签策略、审查模式通过 `config/` 下 YAML 外部化
- **异步任务隔离**：耗时任务（仓库扫描、AI 推理）由 `workers/` 独立处理
- **降级链路设计**：真实 GitHub API → 本地适配器降级，遵循渐进增强原则
- **前后端一体仓**：WebUI 存放于 `backend/webui/`，由 FastAPI 托管静态资源
- **容器化交付**：Docker Compose 编排环境依赖与数据库初始化

## 3. 已知问题和注意事项
- **repo 对象无接口定义**：缺少 Protocol/ABC/文档定义，所有工具通过鸭子类型隐式依赖。删除实现无法静态发现影响，替换实现无法验证完备性。在 `sakura_memory_service.py` 全量审查时应评估引入接口定义的可行性。
- **适配器契约债务**：`local_repo_adapter.py` 曾连续 6 轮补边缘而 sha/url 契约未补齐，经历删除→引入更差替代品→重新引入的循环，契约完整性仍未验证。
- **result_parser 双路径架构热点**：`result_parser.py` 作为核心解析器持续是热点文件（10+次标记），JSON/emoji 双路径架构的复杂性是问题滋生根源，每条路径的独立修改容易破坏对称性。
- **parse_review_result.py 遗留状态**：parse_source except分支已修复（第6轮确认）；emoji去重已修复；line_number类型防御已修复；剩余关注：去重key维度不足(suggestion)、emoji路径未调用去重(suggestion)。
- **result_parser 与 decision_engine 隐式耦合**：解析结果结构直接影响决策引擎分支逻辑，`parse_source` 字段引入了多态解析路径标记，下游需感知此维度。
- **降级链状态污染风险**：JSON 解析失败降级到 emoji 解析时，中间变量可能未正确重置。
- **"确认式疲劳"**：遗留问题连续多轮标记未修复后信息增量归零，退化为"打勾仪式"，需机制将信号从审查标记转化为流程阻断。

## 4. 审查中发现的重要模式
- **标签跨区矛盾**：正文放在「建议（可选）」分区使用🟡标签，但摘要却标记 `[major]`，直接违反"分区标签解耦"规范，暴露标签生成缺乏一致性校验
- **去重逻辑高频陷阱**：key 设计须三问——①默认值是否产生虚假碰撞？②唯一性维度是否覆盖实际区分需求？③丢弃时是否有可观测性（日志）？
- **防御代码边界粗糙**：有防御意识但防御粒度不够，防御本身引入新问题（默认值导致误去重、key维度不足导致误丢弃）
- **双路径对称性忽视**：JSON 路径与 emoji fallback 路径历史上多次出现不对称处理（去重、提取逻辑等），开发者倾向只修主路径
- **小 diff 不等于无执行流影响**：修复被多处调用的函数时，影响范围由调用方决定而非 diff 大小决定；增量审查天然弱点——只看 diff 无法验证完整调用链
- **适配器选择性实现**：只实现搜索用到的接口而非全面契约，首次全量审查须逐一校验公共方法实现状态
- **异常语义混用**：用 NotImplementedError 表达"不支持"的降级意图，与 Python 原生语义冲突
- **防御性守卫的双重语义**：`isinstance` 检查可能同时承担隐式接口契约验证职责，移除时须评估防御流失
- **"假回滚"模式**：声称 revert 但混入新实现，破坏性回滚比破坏性新增更危险
- **动态类型反模式**：`type('Repo', (), {...})()` 绕过所有静态检查，是危险的 mock 方式
- **try/except 边界审计**：审查解析代码须标记所有可能抛异常的表达式，确认异常点在预期范围内
- **防御性切片隐含假设**：AI 生成代码常正确实现但缺少对前置假设的显式声明
- **首次审查与 quick 策略的结构性矛盾**：契约敏感型变更的首次全量审查与 quick 浅层扫描需求冲突
- **str.find() 返回 -1 的切片陷阱**：须显式验证而非一笔带过
- **记忆"存而不查"是假记忆**：缺少"变更文件↔遗留关注点"的主动匹配，记录等于无效
- **"不可能路径"仍需对称处理**：即使当前不触发，不对称防御结构在未来重构时极易成隐患，是架构卫生而非过度工程

## 5. 团队约定和规范
- **代码风格**：Ruff 作为唯一检查和格式化工具，通过 `run_ruff.py` 统一执行
- **结构化数据防御**：处理外部 JSON 时每个字段的类型假设须有显式校验或独立 try/except 隔离
- **类型假设显式化**：对复合类型须先 `isinstance` 校验再操作，禁止隐式假设
- **常量集中治理**：枚举值统一收归 `constants.py`，禁止散落硬编码
- **测试覆盖底线**：新增测试文件须扫描负面用例、边界值用例，用例命名体现场景而非实现细节
- **评分决策解耦**：增量质量高≠可合并，未闭环 critical 时 decision 必须降级为 request_changes
- **major 判定三问法**：判定 actual bug 时须三问——①实际 bug？②运行时错误？③安全风险？不满足②③不应升级为 major
- **标签跨区一致性硬校验**：「主要评论」中 `[major]/[critical]` 须与正文分区标签严格对应；正文放🟡/💡分区则摘要禁止使用 major/critical；输出流程须增加校验：提取摘要中 major/critical → 反查正文分区 → 不一致则阻断或降级
- **同位置问题合并**：同一文件同一行号的多个观察点应合并为单条评论，避免碎片化
- **遗留关注点必须触发**：变更文件命中遗留关注点时须显式确认状态（`[遗留确认] 文件名: 问题状态`），禁止静默跳过；命中遗留关注点的问题严重程度不因策略降级
- **历史闭环记忆联动**：`[遗留确认] ✅已修复` 的条目必须同步触发项目记忆中对应条目的状态更新或移除
- **遗留问题累积升级**：同一 suggestion 连续 3 轮未修复须标注 `[累积遗留-3轮]`，连续 5 轮评分上限 -1
- **Revert PR 真实性与追溯**：须对比目标 commit 与当前 diff 确认是状态恢复而非混入新实现（"假回滚"本身标记 major）；须追溯原 PR 被回滚原因确认根因已解决，未追溯时评分上限 7
- **适配器首次审查契约校验**：新增适配器类首次审查须列出目标接口所有公共方法/属性并逐一标注实现状态，未完成校验时评分上限 6
- **接口实现删除检查**：删除实现某接口的类时须列出所有消费者、逐一确认替换完备性，无法确认时按 critical 标记
- **类型守卫移除评估**：移除 `isinstance`/`hasattr` 等运行时检查时须评估是否承担接口契约验证职责
- **方法命名与实现语义一致**：方法名暗示的操作与实际实现语义偏差须标记 suggestion
- **quick 策略分层**：纯风格偏好、纯可读性建议（如 `type()` 写法）在 quick 模式下省略；防御缺口保留；审查者自述"不太可能产生""概率极低"的问题直接定级 suggestion 禁止升级
- **文档双语化**：面向开源社区提供中英文双语 README 及详细文档
