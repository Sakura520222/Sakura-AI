# Sakura AI Reviewer 项目概述

## 1. 项目简介与技术栈
Sakura AI Reviewer 是一款基于大语言模型的智能 GitHub 代码审查与 Issue 分析机器人，具备主动探索代码库、跨文件依赖理解和全仓库扫描能力，旨在自动化提升代码质量管理与日常协作效率。

- **后端语言**：Python 3.11+
- **Web 框架**：FastAPI
- **前端界面**：HTML（自包含 WebUI）
- **数据库**：MySQL（关系型存储）、Redis（Pub/Sub 实时通信与缓存）
- **AI 与检索**：LLM API 对接、RAG 向量语义检索、DuckDuckGo/Tavily Web 搜索
- **基础设施**：Docker、Docker Compose
- **代码规范**：Ruff（Linter 与 Formatter）
- **集成渠道**：GitHub App（Webhook/OAuth）、Telegram Bot

## 2. 架构设计与关键决策
- **分层架构**：API 层、服务层、数据访问层分离
- **错误处理策略**：当前存在分裂（同服务内抛异常与静默降级共存），属于已知技术债务，单次 PR 内不根治，需作为项目级决策统一
- **配置三层穿透**：`Settings` → `yaml_config` → 硬编码默认值，新增配置必须遵循此链路
- **配置三件套范式**：新增字段必须同步注册描述、字段列表、摘要三处，为项目强约定
- **fallback 链路统一化**：空字符串 → settings → yaml → 硬编码默认值，reflection/consolidation/issue_reflection 三处已对齐
- **模型选择架构稳定化**：新增模型支持走同一条配置-集成路径，service 层通过 `_get_config` 统一读取，已变为低风险的模板化操作
- **fire-and-forget 标准范式**：`create_task` + `add_done_callback(discard)` + 实例级 set 持有引用，但存在 shutdown 丢失风险（已归档为技术债务）
- **反思流程模板化**：init → read → prompt → LLM → commit → state → merge_check，六步固定
- **SakuraMemoryService 职责过重**：承担配置、prompt、LLM、状态、文件，符合"错误处理策略分裂"高危区特征；Worker 层为纯触发器，异常边界完全依赖 Service 内部
- **声明式渲染模式**：HTML 元素附加 `data-markdown` 属性，依赖客户端 Markdown 解析器统一处理，扩散成本低。`base.html` 集中管理排版插件（typography、hljs 暗色主题），任何模板的 Markdown 渲染都强依赖这些全局配置的加载顺序和存在性
- **跨层边界风险**：Jinja2 模板截断 + 客户端 Markdown 解析构成典型跨层边界，截断行为与服务端/客户端各自对完整性的假设冲突，容易产生"罕见输入才暴露"的长期风险
- **降级渲染安全策略**：当 Markdown 解析与截断组合存在语法破坏风险时，移除 `data-markdown` 属性从解析降为纯文本渲染，体现"有风险则舍弃特性"的保守策略
- **防御性转义模式**：花括号转义是 `str.format()` 与用户输入共存的标配防护，项目已形成"先转义再格式化"的固定模式

## 3. 已知问题和注意事项
- **错误处理不统一**：部分场景抛异常、部分场景静默降级，缺乏一致策略，新代码应倾向显式错误传播
- **分支查找 fallback 路径**：`_find_open_sakura_branch` 返回 `None` 时，下游 `_commit_via_pr` 必须正确 fallback 到创建新分支，此处为历史易错点
- **"部分修复比未修复更危险"**：标记"已修复"时若验证不充分，容易掩盖残留问题；复合问题只修一半却整体标"已修复"是典型假闭环
- **fire-and-forget shutdown 丢失**：进程退出时异步任务可能未完成写入，已归档为技术债务，新代码复制此模式时不得静默通过
- **"已有模式"≠"可接受"**：与既有代码一致不能作为降级理由，应标为 warning 并归档
- **"假实现"陷阱**：代码已使用某功能的相关类/属性但效果缺失时，须回溯检查配置层（如插件加载、CSS/JS 引入），而非直接认定"未实现"
- **跨层截断风险**：服务端模板截断（Jinja2 slice）+ 客户端 Markdown 解析的组合会破坏语法结构，典型实例如 `scan.error_message[:500]` + `data-markdown`，涉及 Markdown 的可行性评估须作为标准检查项
- **渲染兼容性风险**：为原有纯文本区域添加 Markdown/HTML 解析时，历史值中可能含 `#`、`*`、`_`、`>`、数字后跟点号等敏感字符，被意外解析会造成展示错乱，须检查并转义或显式禁用解析
- **"三件套完备"是高频声明低频验证**：quick 下易基于模式惯性输出此类结论，应视为需要 diff 证据支撑的声明而非默认填充项
- **空评论+高分组合的信号**：连续出现时意味着评分锚定在"代码质量"而非"审查输出质量"，需周期性校准
- **防御性转义缺乏公共工具层**：`_escape_braces` 等转义函数存在同模块内重复定义，若修改一处遗漏另一处将导致行为不一致，长期维护风险需归档跟踪
- **微小变更仍有横向扫描义务**：即使 diff 仅 20 行，涉及 `str.format()` 或 Markdown 解析等敏感 API 时，须对同文件内同类调用做全文关键字符扫描

## 4. 审查中发现的重要模式
- **"标记-不修-再标记"循环**：连续多轮标记同一问题但开发者不修复，说明严重程度判定与开发者认知不匹配，审查侧应反思判定标准
- **修复验证停留在"是否修改"层面**：增量审查易陷入对照清单打勾陷阱——看到改了就打✅，不验证改得对不对、调用链是否完整
- **打勾陷阱的边界**：当变更攻击面集合为空（如纯版本号替换）时，空评论=正确输出而非偷懒
- **quick 策略颗粒度失配**：quick 应产出精简（≤200字），但实际易出现"quick速度+deep格式"的评论膨胀
- **知行分离模式**：摘要中写出降级理由，却在评论中维持原严重级别，说明写摘要时未触发自检
- **状态标签与实际状态脱节**：已修复的 critical 仍以原标签出现在主评论中，造成开发者困惑
- **归档 ≠ 阻塞**：技术债务归档意味"已知且接受"，不应继续影响当前决策；但需警惕归档后遗忘
- **填充倾向对抗规则**：生成时倾向于用已有内容填充空白区域，需通过输出模板的结构性约束解决
- **规则执行防形式化失败**：规则写明"从模板层面阻断"但实际仍依赖模型判断，需在输出模板层面取消主评论输出区域作为默认路径
- **验证性内容 ≠ suggestion**：修复确认不应放入 suggestion 槽位，标签误用导致归档逻辑混乱
- **严重程度回归"问题存在感"**：脱离用户影响判定严重程度，major 前未执行三问
- **防御代码复制须验证必要性**：复制既有防御模式时应评估新场景是否需要同等强度
- **问题描述粒度决定闭环质量**：多条子问题写成一条评论，开发者只修了明显部分，审查者看到部分修复就整体打勾；拆分是避免假闭环的最直接手段
- **PR 描述截断/错位未察觉**：PR 描述截断或与增量提交主题错位时审查无感知
- **受限信息产出确定性声明的惯性**：quick 下信息受限是常态，受限不应产出"完备""一致"等确定性声明
- **模式复制的一致性陷阱**：聚焦于"模式一致"时易忽略模式在新上下文的适配性，必须显式列出与原模式的差异点
- **知识性 Issue 快速闭环**：纯事实查询型 Issue 无需修代码，直接给出代码引用与逻辑链即可高效关闭；追踪路径从功能类初始化反查参数来源
- **增量审查隧道视野**：仅观察新增/修改行的属性，未横向检查受影响的公共依赖（如 Markdown 解析器配置、CSS 排版类是否启用），也未检查相同字段在非变更模板中的兼容性隐患
- **审查输出机械化填充**：quick 报告倾向填充所有模板区域，主评论区易出现摘要表格的碎片化粘贴，反映生成惯性而非内容需求
- **修复验证须含"使用面"检查**：验证转义函数不仅看函数逻辑，还需确认所有出现用户内容处均已调用该函数，遗漏的调用点构成验证缺口

## 5. 团队约定和规范

### 审查硬规则（强制执行）

**三问法强制绑定**：所有 major 级别评论必须内联三问答案。三问中任一答案为"无"或"不涉及"时，该问题自动降级为 `minor`。无答案则不得标 major。

**纯可读性封顶规则**：不涉及功能、安全、数据完整性的可读性问题，严重程度封顶为 `suggestion`。

**自评矛盾自动降级**：评论正文出现"非安全用途""影响极小""风险可控""理论上""虽然功能正确"等表述时，对应标签自动降级一级。

**评论去重与合并**：同一代码位置的不同表述必须合并为一条评论，禁止拆分标记。

**复合问题拆分约束**：一条评论包含多个独立子问题时，必须编号枚举。修复验证须逐项勾选，部分修复标"部分修复"而非"已修复"。

**根因修复验证**：问题描述引用高危区标签时，修复验证必须回溯到高危区描述的核心要求，而非仅验证表面修复。

**历史问题消失检测**：每轮审查须显式清点上一轮所有 open 项的去向——已修复/归档/降级，禁止无痕消失。

**模式复制差异清单**：复制既有模式时，必须显式列出与原模式的所有差异点及各自理由。未列差异点视为遗漏。

**修复验证须含调用链**：标记"已修复"时，必须验证修改点的上游调用和下游消费是否一致传递，否则只能标"待验证"。

**修复即清除标签**：增量提交修复了某问题后，该问题从主评论移除，仅保留在已修复追踪表中。禁止以原严重程度标签重复输出。

**决策状态同步**：当所有 critical/major 均已修复或归档且无新增阻塞项时，decision 必须升级为 `approve` 或 `comment`。

**PR 描述一致性校验**：PR 描述与实际 diff 方向矛盾时须注明。增量提交引入 PR 描述未提及的新变更点时，摘要须显式标注"本次提交包含 PR 描述外的新增变更"。

**受限信息禁止确定性声明**：quick 策略下涉及"完备性""一致性"等需全量验证的结论性声明时，若 diff 未覆盖全部相关文件，须使用"在可见范围内"等限定词或直接省略。

**低置信度标签过滤**：Issue 分析中标签置信度 < 0.5 且与分析正文无语义交集时，直接丢弃不输出。

**增量审查边界感**：区分"本次引入的问题"和"本次暴露的已有问题"，避免给 PR 作者造成误判。

**"已有模式"标签强制升级**：任何被识别为"与现有代码行为一致"的缺陷，必须标为 `warning` 并归档，禁止以 `[minor]` 呈现或混入 `suggestion` 区域。

**引入渲染增强须评估内容兼容性**：若为原有纯文本区域添加 Markdown/HTML 解析，须检查历史值是否含 `#`、`*`、`_`、`>`、数字后跟点号等敏感字符。未转义且未禁用解析时应标 `warning`。

**suggestion 槽位内容约束**：suggestion 槽位只能包含可行动的前瞻建议，禁止粘贴变更评估表格、摘要片段或修复确认类内容。若出现评估表格或摘要片段，直接判定审查无效，需重新生成。

**重复检测须附上下文**：Issue 分析中标注"可能是 #X 的重复"时，须附带简短相似度说明（如"均询问同一功能的后端模型选择"），提升可复核性。

**转义函数复用检查**：审查发现新增或修改转义/清理逻辑时，必须横向扫描同模块内相似上下文是否存在同一函数的多处定义或调用缺失，结果用一句话声明（如"未见其他 `format` 调用"或"另有 N 处未转义，已另开 issue"）。

**微小增量横向扫描**：即使 diff ≤ 30 行，若涉及 `format(`、Markdown 解析、渲染配置等敏感 API，须执行同文件全文关键字符扫描，结果在摘要中一句话声明。

### suggestion 疲劳归档协议
- 第 1 轮未修复：评估实际影响，考虑是否直接降级
- 第 2 轮未修复：强制降级为 suggestion
- 第 3 轮未修复：强制归档并从主评论移除，仅保留在摘要追踪表格中

### quick 策略执行约束
- 历史追踪项在 quick 模式下只进摘要表格，不生成独立评论。当增量变更与追踪项所在模块/逻辑完全无交集时（如纯版本号、纯文案），可省略追踪表
- 纯改善性建议在 quick 模式下属于噪声，不应提出
- ≤27 行变更的 quick 审查报告应≤200 字，且必须包含决策依据
- 无新增评论时主评论区强制为空：quick 策略下若无新增问题，主评论输出单一占位符或留空。必须在输出模板层面取消主评论输出区域作为默认路径
- 微小增量审查输出需坚持"不牺牲必要风险提示"：精简不应以遗漏兼容性风险、归档标记等实质性提示为代价
- quick 模式下生成前须清空 suggestion 区的表格类内容，仅保留纯文本建议，防止填充惯性导致格式违规
- 微小增量不豁免横向验证：即使 diff 极小，仍须对敏感 API 做全文扫描，防止"精简不允许遗漏实质性风险"

### 降级信号词清单
风险可控、影响有限、极少出现、边缘场景、可接受
