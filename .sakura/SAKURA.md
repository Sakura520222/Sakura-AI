# Sakura AI Reviewer 项目概述

## 1. 项目简介与技术栈
Sakura AI Reviewer 是一款基于大语言模型的智能 GitHub 代码审查与 Issue 分析机器人，具备主动探索代码库、跨文件依赖理解和全仓库扫描能力，旨在自动化提升代码质量管理与日常协作效率。

- **后端语言**：Python 3.11+
- **Web 框架**：FastAPI
- **前端界面**：HTML（自包含 WebUI）
- **数据库**：MySQL、Redis（Pub/Sub 实时通信与缓存）
- **AI 与检索**：LLM API、RAG 向量语义检索、DuckDuckGo/Tavily Web 搜索
- **基础设施**：Docker、Docker Compose
- **代码规范**：Ruff
- **集成渠道**：GitHub App（Webhook/OAuth）、Telegram Bot

## 2. 架构设计与关键决策
- **分层架构**：API 层、服务层、数据访问层分离
- **服务层职责边界**：`comment_service` 为行内评论渲染的**唯一权威入口**，任何期望调整渲染的行为必须在 service 层统一实现；禁止在上游 worker 或 parser 中预渲染 `body` 字段，违反此原则应标 `critical`
- **集中式结果解析器**：AI Reviewer 原始输出的清洗、提取和格式化收敛于 `result_parser.py`，职责包含解析、去重、合并与字段清洗，存在“上帝类”倾向，需关注其可观测性和测试复杂度
- **错误处理策略分裂**：同服务内抛异常与静默降级共存，属于已知技术债务
- **配置三层穿透**：`Settings` → `yaml_config` → 硬编码默认值；新增配置须同步注册描述、字段列表、摘要（三件套范式），且 `config.py` 与 `database.py` 双源同步
- **配置与逻辑断层风险**：配置项、数据库字段和业务逻辑分布在 `config.py`、`comment_service.py`、`result_parser.py` 等文件中，易出现“添加配置但逻辑未调用”的假开关问题
- **fallback 链路统一**：空字符串 → settings → yaml → 硬编码默认值
- **fire-and-forget 范式**：`create_task` + `add_done_callback(discard)` + 实例级 set 持有引用，存在 shutdown 丢失风险（已归档）
- **工具插件化架构**：统一工具注册与调用，但分类逻辑存在语义混淆
- **声明式渲染与跨层边界**：HTML 附加 `data-markdown` 依赖客户端解析；模板截断+客户端解析构成跨层语法破坏风险
- **防御性转义范式**：花括号转义为 `str.format()` 与用户输入共存的标配，但缺乏公共工具层
- **API 客户端 URL 拼接规范**：禁止 base_url 尾部带路径细节；外部 API 推荐完整 URL；配置层应统一对 URL 做规范化处理
- **版本号管理**：分散在多个文件，应逐步统一从 `__version__.py` 导入
- **AI 输出解析的防御式后处理模式**：在解析层增加清洗逻辑以应对上游模型输出格式不可控，此为可接受的快速修复，但应注释清洗目标以便未来移除
- **格式化调用链重复的脆弱设计**：`review_worker` 和 `comment_service` 均直接调用同一格式化函数且原地修改 `body`，形成“先加工再传入仍会被二次加工”的陷阱
- **标签冲突检测架构**：现有标签自动应用缺乏冲突检测机制，需建设结构化标签冲突规则引擎，防止“追加标签不考虑已有上下文”导致误打标签或下游自动化误触发

## 3. 已知问题和注意事项
- **错误处理不统一**：新代码应倾向显式错误传播
- **静默降级缺乏可见性**：降级路径须产生告警（日志 warning 或指标），否则视为 silent-failure；Issue 分析时应自动标记 silent-failure 并建议 regression 标签
- **日志语义与行为一致性**：行为变更时旧日志消息须同步更新；“去重”变“合并”等语义转换型重构极易遗忘元数据同步
- **日志级别可观测性**：对 AI 生成值、外部输入等不可信数据，在其值被修正或丢弃时须用 `logger.warning`，确保默认级别可见；`logger.debug` 在此场景视为无效可观测性；同类场景日志级别应保持一致
- **安全防护场景日志级别强化**：防止误导性自动应用的降级操作（如置信度强制置零），即使防护已执行，仍应使用 `warning` 级别确保可观测性，`info` 仅适用于纯信息性事件
- **轮询缺少强制失败出口**：任何启动等待循环须具备超时检查和 `exit≠0`
- **假修复与假闭环**：复合问题只修一半标“已修复”、仅通过注释关闭安全问题、验证停留在“是否修改”而非完整调用链，均为假闭环；修复验证须推演完整执行流，安全问题不可仅文档化关闭
- **假实现陷阱**：生命周期方法（`reset_*` 等）全仓库无调用，属功能未完整实现
- **跨层截断风险**：模板截断+Markdown 解析破坏语法，须作为标准检查项
- **防御性转义重复定义**：同模块内多次定义需归档跟踪
- **配置假值陷阱**：配置加载须用 `is not None` 而非 Truthy 检查
- **异步执行取消/超时风险**：`run_in_executor` 缺少 `shield` 或超时处理可能任务泄漏
- **幽灵变更与隧道视野**：PR 描述提及但审查遗漏的文件须强制核对；增量审查易陷入“对照清单打勾”而忽略新引入的重大风险
- **增量审查隧道视野——全局意图保护**：AI 审查聚焦增量 diff 而忽略 PR 整体意图（如 meta 信息、已有标签、标题描述摘要），属经典认知陷阱；分析增量审查类 Issue 时应将此作为固定思维模板，评估是否需注入“全局意图保护”到 prompt 中
- **置信度降级的假兜底风险**：校验降级时将置信度强制置零，若下游渲染、API 推送或数据库写入存在 `confidence > 0` 门槛判断，可能无意中完全隐藏修复建议，形成“可观测性静默”；任何 `confidence` 写入审查须连带检查下游消费者对该字段的条件判断
- **httpx 重定向非透明失败**：须确认 `follow_redirects` 设置，3xx bug 优先检查重定向配置而非仅修 URL
- **LLM 输出解析健壮性**：针对 LLM 输出的正则或字符串匹配须评估对空白、标点变体的容忍度；严格依赖换行等强假设应标记为 suggestion 并指出静默失败风险
- **双重格式化陷阱**：对数据字段的格式增强若在多层级执行，极易因信息保留不全导致重复；审查时看到 `obj["body"] = format(obj["body"], ...)` 模式应立即追踪下游消费者是否也调用 `format`
- **安全默认值泄露与 Setup 免认证**：高危模式须强制检测
- **配置默认值变更影响深远**：涉及外部可见行为或安全策略的默认值变更须包含 major 风险评估，不能以单一 provider 假设断言成本可控
- **AI 系统 prompt 变更**：视为高敏感，须评估提示注入、语义漂移和工具滥用
- **警告级别误设**：`logger.warning` 被误用于非警告场景会造成日志噪声，应审查 warning 调用是否确实表示需人工关注的异常条件
- **反模式解析**：正则 `\\*\\*.*\\*\\*` 等过度匹配模式可能吞掉正文中 Markdown 加粗文本而非仅匹配标题

## 4. 审查中发现的重要模式
- **微小变更审查价值**：即使微小变更也能发掘深层洞见，远非草率审核可比
- **打勾陷阱**：增量审查最危险的形态——注意力绑定在历史问题上而忽略新风险；零评论高分是审查陷阱典型信号
- **增量隧道视野新形态**：聚焦局部代码深度足够但缺乏全局广度，对新增字段的完整生命周期（产生→解析→验证→存储→使用）缺乏追踪
- **增量审查的全局意图保护**：此模式完美印证“增量审查陷阱——隧道视野致配置假开关、数据流断裂”；AI 只聚焦增量 diff 却忽略 PR 整体意图（标题、已有标签、描述摘要），正是隧道视野；今后分析类似 Issue 时应直接关联该教训并建议在 prompt 中注入 PR meta 信息传递
- **校验降级后的安全熔断模式**：用布尔标志记录输入校验失败导致的降级事实，并在高风险操作前主动将置信度归零，强制切换至低风险渲染路径；可提炼为“当输入验证降级可能破坏后续建议的上下文准确性时，必须对关联可执行动作进行能力降级，避免误导性自动应用”
- **配置默认值变更的连锁阻塞**：未附风险评估的 major 默认值变更会卡住后续所有提交
- **归档≠阻塞**：技术债务归档意味已知且接受，但归档项被后续变更放大风险时应重新激活
- **suggestion 疲劳归档机制**：第 2 轮未修复降级，第 3 轮强制归档，是优秀的长尾管理模式
- **增量审查两重责任**：追踪历史问题修复 + 覆盖本次提交整体意图，防止宏观风险感知失败
- **“删除优于修复”模式**：功能冗余时删除相关代码比修补更安全；重复格式化问题的最优解是删除上游预格式化而非修补下游
- **幽灵PR模式**：描述与提交内容严重不符时必须阻塞
- **对假闭环的警惕**：关联 Issue 的修复审查应声明“可见范围内无法验证是否完全解决”或“已验证完全解决”
- **LLM 输出解析的不信任原则**：审查时应主动引入变异（多余空行、缺失换行、标点变体）追问解析逻辑行为
- **修复建议代码错误**：审查建议中给出的代码示例可能含逻辑死块，须在反思环节指出并要求正确的 diff
- **增量审查全文检索原则**：即使仅数行变更，也应检索同名函数在全仓库的调用位置以发现重复调用；审查时至少确认一句“检查下游使用无负面影响”以符合回归评估要求
- **标签冲突规则的工程化需求**：现有自动标签缺乏冲突检测，未来分析任何“标签自动应用”相关 Issue 时，都应审查是否存在同类“追加标签不考虑已有上下文”的问题，可沉淀为检查项

## 5. 团队约定和规范

### 审查硬规则
- **三问法**：所有 major 评论须内联“用户影响/利用条件/现有缓解”；任一答案为“无”或“不涉及”自动降级为 minor
- **纯可读性封顶**：封顶为 suggestion
- **自评矛盾降级**：出现“风险可控”“影响极小”等信号词自动降一级
- **复合问题拆分**：编号枚举，修复验证逐项勾选
- **根因修复验证**：引用高危区标签须回溯核心要求
- **历史问题消失检测**：每轮显式清点上一轮全部 open 项去向
- **修复验证须含调用链**：验证上游调用和下游消费一致性；安全问题仅文档化关闭标记为“未修复”或归档；当变更引入置信度强制修正时，须追踪该字段在所有消费者中的条件判断
- **修复即清除标签**：增量提交修复后该问题从主评论移除
- **决策状态同步**：所有阻塞项已修复或归档且无新增时，decision 升级为 approve 或 comment
- **PR 描述与审查覆盖一致性校验**：审查前核对 PR 描述 Changes、实际 diff 和审查覆盖列表一致，不一致须 critical 告警
- **强制一致性校验（major）**：比对 PR 描述与提交 diff 实际内容，类型不符阻塞审查
- **配置默认值变更强制风险评估**：涵盖攻击面、资源成本、兼容性
- **AI 系统 prompt 变更审查**：高敏感，评估提示注入、语义漂移和工具滥用
- **生命周期方法调用验证**：无调用标记 major
- **硬规则 major 多轮未闭环阻塞**：连续两轮未修复（跨 PR 有效），decision 降级为 request changes 或 comment
- **历史阻塞项强制关联**：即使无文件交集也须反映仍开放的阻塞项
- **容器/服务就绪轮询模式**：须含超时检查和失败退出
- **连续未闭环风险转技术债**：连续 3 轮未修复须创建正式技术债 Issue
- **suggestion 槽位内容约束**：仅可行动的前瞻建议
- **“已有模式”标签强制升级**：标为 warning 并归档
- **微小增量横向扫描**：涉及敏感 API 时须同文件全文关键字符扫描
- **安全扫描 Issue 强制风险列表**：产出结构化风险列表，密钥泄露自动标记 major
- **Issue 重复检测实证要求**：必须输出候选 Issue 标题与语义相似度分值；仅声明“可能是 #X 的重复”而不含标题/相似度视为不合格
- **URL 拼接检查清单**：base_url 禁止尾部带路径；修复须确认 `follow_redirects` 并评估全局启用
- **PR 引用 Issue 强制声明**：须声明“可见范围内能否完全解决”，缺失时评分≤8
- **标签规则记忆闭环**：静默降级映射 silent-failure，先前修复未生效推荐 regression
- **版本升级专项检查**：确认 `pyproject.toml` 版本同步和 `CHANGELOG.md` 更新
- **PR描述过时检测**：描述含未在本提交出现的代码变更时强制要求更新
- **新功能闭环校验（major）**：对引入新数据字段的变更，须追踪字段完整生命周期（产生→解析→验证→存储→使用/展示）；任一环节缺失标记 major
- **格式化/转换函数重复调用检查（critical/major）**：发现多处调用同一格式化函数且传入同一原始数据时标记为 major；若造成功能退化则标 critical；审查时须扫描数据从生产到落地的全路径上所有同名格式化调用
- **服务层格式化唯一权威规则（critical）**：行内评论渲染仅允许在 `comment_service` 层执行，上游预渲染 `body` 字段违反此原则
- **历史问题闭环验证规则**：当提交声称解决长期未修复问题时，须要求说明中列出受影响调用位置及冲突逻辑消除证据，缺失触发 `missing-statement` 降级
- **日志可观测性三件套**：①语义与行为一致性（行为变更时旧日志须同步更新）；②不可信数据修正/丢弃时须用 `warning`，`debug` 视为无效可观测性；③发现日志问题后须扫描同文件同类隐患
- **增量审查回归评估强化**：在“回归评估”条目下显式要求“扫描受改动字段影响的下游模块（即使不在diff范围内）”，防止隧道视野
- **布尔标志控制流完整性检查**：微小布尔标志引入会改变控制流，须沿该标志所有使用点验证状态一致性，检查是否有代码路径意外重置标志或绕过检查

### suggestion 疲劳归档协议
- 第 1 轮未修复：评估实际影响考虑降级
- 第 2 轮未修复：强制降级为 suggestion
- 第 3 轮未修复：强制归档并从主评论移除

### quick 策略执行约束
- 历史追踪项只进摘要表格；存在未闭环阻塞项时摘要须显式列出
- 纯改善性建议属噪声不应提出
- ≤27 行变更报告≤200 字且含决策依据
- 无新增问题时主评论区强制为空
- 受限信息下禁止产出“完备性”“一致性”等确定性声明，须用“在可见范围内”或省略
- 无法查看 PR 引用 Issue 内容时摘要须注明“无法核对是否完全解决”
- 低置信度不直接相关的标签视为噪声
- 不能跳过描述-代码一致性检查
