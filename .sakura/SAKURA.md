# Sakura AI Reviewer 项目概述

## 1. 项目简介与技术栈
Sakura AI Reviewer 是一款基于大语言模型的智能 GitHub 代码审查与 Issue 分析机器人，具备主动探索代码库、跨文件依赖理解和全仓库扫描能力，旨在自动化提升代码质量管理与日常协作效率。

- **后端语言**：Python 3.11+
- **Web 框架**：FastAPI
- **前端界面**：HTML（自包含 WebUI）
- **数据库**：MySQL、Redis（Pub/Sub 实时通信与缓存）
- **AI 与检索**：LLM API、RAG 向量语义检索、DuckDuckGo/Tavily Web 搜索
- **基础设施**：Docker、Docker Compose
- **代码规范**：Ruff
- **集成渠道**：GitHub App（Webhook/OAuth）、Telegram Bot

## 2. 架构设计与关键决策
- **分层架构**：API 层、服务层、数据访问层分离
- **服务层职责边界**：`comment_service` 为行内评论渲染的**唯一权威入口**；禁止上游预渲染 `body` 字段，违反标 `critical`
- **集中式结果解析器**：AI 输出清洗、提取、格式化收敛于 `result_parser.py`，存在“上帝类”倾向
- **错误处理策略分裂**：同服务内抛异常与静默降级共存，属已知技术债务
- **配置三层穿透**：`Settings` → `yaml_config` → 硬编码默认值；新增配置须同步注册三件套范式
- **配置与逻辑断层风险**：配置项、数据库字段和业务逻辑分布多处，易出现“假开关”
- **降级标志传递模式**：使用布尔标志（如 `labels_fetch_failed`）沿调用链传递失败语义，替代空列表歧义
- **动态冲突检测模式**：批量操作时使用逐步更新的集合（如 `effective_labels`）检测元素间冲突，比静态快照更可靠
- **fallback 链路统一**：空字符串 → settings → yaml → 硬编码默认值
- **fire-and-forget 范式**：`create_task` + `add_done_callback(discard)` + 实例级 set 持有引用
- **工具插件化架构**：统一工具注册与调用，但分类逻辑存在语义混淆
- **声明式渲染与跨层边界**：HTML 附加 `data-markdown` 依赖客户端解析
- **防御性转义范式**：花括号转义为标配，但缺乏公共工具层
- **API 客户端 URL 拼接规范**：禁止 base_url 尾部带路径细节
- **版本号管理**：应逐步统一从 `__version__.py` 导入
- **AI 输出解析的防御式后处理模式**：增加清洗逻辑应对模型输出不可控，应注释清洗目标
- **格式化调用链重复的脆弱设计**：多处调用同一格式化函数且原地修改，形成二次加工陷阱
- **标签冲突检测架构**：需建设结构化标签冲突规则引擎，防止误打标签

## 3. 已知问题和注意事项
- **错误处理不统一**：新代码应倾向显式错误传播
- **静默降级缺乏可见性**：降级路径须产生 warning 日志，否则视为 silent-failure
- **日志语义与行为一致性**：行为变更时旧日志消息须同步更新
- **日志级别可观测性**：对不可信数据修正/丢弃时须用 `warning`，`debug` 视为无效
- **安全防护场景日志强化**：降级操作（如置信度强制置零）须用 `warning`，`info` 仅适用于纯信息事件
- **轮询缺少强制失败出口**：启动等待循环须具备超时检查和 `exit≠0`
- **假修复与假闭环**：验证须推演完整执行流，安全问题不可仅文档化关闭
- **假实现陷阱**：生命周期方法全仓库无调用，属功能未完整实现
- **跨层截断风险**：模板截断+Markdown 解析破坏语法
- **防御性转义重复定义**：同模块内多次定义需归档
- **外部依赖失败必须显式降级**：获取 GitHub 资源失败禁止返回空列表/空字典，须返回 `None` 或抛异常
- **配置解析红线**：禁止使用 `.replace(',', ' ').split()` 解析标签列表，统一使用逗号分隔 + strip
- **配置假值陷阱**：配置加载须用 `is not None` 而非 Truthy 检查
- **异步执行取消/超时风险**：`run_in_executor` 缺少 `shield` 或超时处理可能任务泄漏
- **幽灵变更与隧道视野**：PR 描述提及但审查遗漏的文件须强制核对
- **增量审查全局意图保护**：AI 聚焦增量 diff 而忽略整体意图（标题、已有标签、描述摘要）属经典陷阱
- **置信度降级的假兜底风险**：置信度强制置零须连带检查下游消费者对该字段的条件判断
- **httpx 重定向非透明失败**：须确认 `follow_redirects` 设置
- **LLM 输出解析健壮性**：对空白、标点变体的容忍度须评估
- **双重格式化陷阱**：看到 `obj["body"] = format(...)` 应立即追踪下游是否也调用 `format`
- **安全默认值泄露与 Setup 免认证**：高危模式须强制检测
- **配置默认值变更影响深远**：涉及外部可见行为或安全策略的变更须含 major 风险评估
- **AI 系统 prompt 变更**：视为高敏感，须评估提示注入、语义漂移和工具滥用
- **警告级别误设**：`logger.warning` 误用于非警告场景会造成日志噪声
- **反模式解析**：正则 `\\*\\*.*\\*\\*` 等过度匹配可能吞掉正文 Markdown 加粗
- **PyGithub get_contents 多态返回**：须检查 `type` 属性（`file`/`dir`/`submodule`/`symlink`），而非仅 `isinstance(list)`

## 4. 审查中发现的重要模式
- **微小变更审查价值**：行数少 ≠ 风险低，能发掘深层洞见
- **打勾陷阱**：注意力绑定历史问题而忽略新风险；零评论高分是典型信号
- **增量隧道视野**：聚焦局部深度足够但缺乏全局广度，对新增字段完整生命周期缺乏追踪
- **校验降级后的安全熔断模式**：用布尔标志记录降级事实，在高风险操作前主动归零置信度
- **配置默认值变更的连锁阻塞**：未附风险评估的变更会卡住后续提交
- **归档≠阻塞**：归档项被后续变更放大风险时应重新激活
- **suggestion 疲劳归档机制**：第 2 轮未修复降级，第 3 轮强制归档
- **增量审查两重责任**：追踪历史问题修复 + 覆盖本次提交整体意图
- **“删除优于修复”模式**：功能冗余时删除比修补更安全
- **幽灵PR模式**：描述与提交内容严重不符时必须阻塞
- **对假闭环的警惕**：须声明“可见范围内能否完全解决”
- **LLM 输出解析的不信任原则**：主动引入变异追问解析逻辑行为
- **增量审查全文检索原则**：即使仅数行变更，也应检索同名函数全仓库调用位置
- **批量操作状态追踪规则**：循环内依赖“已有状态”做判断时，必须维护 `effective_entities` 集合并实时更新
- **标签冲突规则的工程化需求**：任何“标签自动应用”相关 Issue，都应审查是否存在同类“追加标签不考虑已有上下文”问题

## 5. 团队约定和规范

### 审查硬规则
- **三问法**：所有 major 须内联“用户影响/利用条件/现有缓解”；任一答案为“无”自动降级
- **纯可读性封顶**：封顶为 suggestion
- **自评矛盾降级**：出现“风险可控”等信号词自动降一级
- **复合问题拆分**：编号枚举，修复验证逐项勾选
- **根因修复验证**：引用高危区标签须回溯核心要求
- **历史问题消失检测**：每轮显式清点上一轮全部 open 项去向
- **修复验证须含调用链**：验证上游调用和下游消费一致性
- **修复即清除标签**：增量提交修复后该问题从主评论移除
- **决策状态同步**：所有阻塞项已修复或归档且无新增时，decision 升级为 approve
- **PR 描述与审查覆盖一致性校验**：不一致须 critical 告警
- **强制一致性校验（major）**：类型不符阻塞审查
- **配置默认值变更强制风险评估**：涵盖攻击面、资源成本、兼容性
- **AI 系统 prompt 变更审查**：高敏感，评估提示注入、语义漂移和工具滥用
- **生命周期方法调用验证**：无调用标记 major
- **硬规则 major 多轮未闭环阻塞**：连续两轮未修复，decision 降级为 request changes
- **历史阻塞项强制关联**：即使无文件交集也须反映仍开放的阻塞项
- **容器/服务就绪轮询模式**：须含超时检查和失败退出
- **连续未闭环风险转技术债**：连续 3 轮未修复须创建正式技术债 Issue
- **suggestion 槽位内容约束**：仅可行动的前瞻建议
- **“已有模式”标签强制升级**：标为 warning 并归档
- **微小增量横向扫描**：涉及敏感 API 时须同文件全文关键字符扫描
- **安全扫描 Issue 强制风险列表**：产出结构化风险列表
- **Issue 重复检测实证要求**：必须输出候选 Issue 标题与语义相似度分值
- **URL 拼接检查清单**：base_url 禁止尾部带路径；修复须确认 `follow_redirects`
- **PR 引用 Issue 强制声明**：须声明“可见范围内能否完全解决”，缺失时评分≤8
- **标签规则记忆闭环**：静默降级映射 silent-failure，先前修复未生效推荐 regression
- **版本升级专项检查**：确认 `pyproject.toml` 版本同步和 `CHANGELOG.md` 更新
- **PR描述过时检测**：描述含未在本提交出现的代码变更时强制要求更新
- **新功能闭环校验（major）**：新增数据字段须追踪完整生命周期（产生→解析→验证→存储→使用/展示）
- **格式化/转换函数重复调用检查（critical/major）**：扫描数据从生产到落地的全路径上所有同名格式化调用
- **服务层格式化唯一权威规则（critical）**：行内评论渲染仅允许在 `comment_service` 层执行
- **历史问题闭环验证规则**：修复须列出受影响调用位置及冲突逻辑消除证据
- **日志可观测性三件套**：①语义与行为一致性；②不可信数据修正/丢弃时须用 `warning`；③扫描同文件同类隐患
- **增量审查回归评估强化**：显式要求“扫描受改动字段影响的下游模块（即使不在 diff 范围内）”
- **布尔标志控制流完整性检查**：引入布尔标志须沿所有使用点验证状态一致性，检查无路径绕过
- **外部依赖失败显式降级规则（major）**：失败禁止返回空列表/空字典，须返回 `None` 或抛异常
- **配置解析红线规则（major）**：禁止 `replace(',', ' ').split()` 解析标签，统一使用逗号分隔 + strip
- **批量操作状态追踪规则（major）**：循环依赖状态判断时必须维护实时更新的集合
- **PyGithub 返回类型守卫规则（major）**：使用 `get_contents()` 必须检查返回对象的 `type` 属性
- **错误路径上游追踪规则（major）**：函数改变失败模式（抛异常→返回错误字符串）必须审查所有调用方

### suggestion 疲劳归档协议
- 第 1 轮未修复：评估实际影响考虑降级
- 第 2 轮未修复：强制降级为 suggestion
- 第 3 轮未修复：强制归档并从主评论移除

### quick 策略执行约束
- 历史追踪项只进摘要表格；存在未闭环阻塞项时摘要须显式列出
- 纯改善性建议属噪声不应提出
- ≤27 行变更报告≤200 字且含决策依据
- 无新增问题时主评论区强制为空
- 受限信息下禁止产出“完备性”“一致性”等确定性声明
- 无法查看 PR 引用 Issue 内容时摘要须注明“无法核对是否完全解决”
- 低置信度不直接相关的标签视为噪声
- 不能跳过描述-代码一致性检查
