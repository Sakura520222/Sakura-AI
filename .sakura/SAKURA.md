# Sakura AI Reviewer 项目概述

## 1. 项目简介与技术栈
Sakura AI Reviewer 是一款基于大语言模型的智能 GitHub 代码审查与 Issue 分析机器人，具备主动探索代码库、跨文件依赖理解和全仓库扫描能力，旨在自动化提升代码质量管理与日常协作效率。

- **后端语言**：Python 3.11+
- **Web 框架**：FastAPI
- **前端界面**：HTML（自包含 WebUI）
- **数据库**：MySQL（关系型存储）、Redis（Pub/Sub 实时通信与缓存）
- **AI 与检索**：LLM API 对接、RAG 向量语义检索、DuckDuckGo/Tavily Web 搜索
- **基础设施**：Docker、Docker Compose
- **代码规范**：Ruff（Linter 与 Formatter）
- **集成渠道**：GitHub App（Webhook/OAuth）、Telegram Bot

## 2. 架构设计与关键决策
- **分层架构**：API 层、服务层、数据访问层分离
- **错误处理策略分裂**：同服务内抛异常与静默降级共存，属于已知技术债务，单次 PR 不根治
- **配置三层穿透**：`Settings` → `yaml_config` → 硬编码默认值；新增配置必须同步注册描述、字段列表、摘要（三件套范式），且 `config.py` 与 `database.py` 双源同步，保证默认语义一致
- **fallback 链路统一**：空字符串 → settings → yaml → 硬编码默认值，reflection/consolidation/issue_reflection 三处已对齐
- **模型选择路径稳定**：新增模型支持为低风险模板化操作，统一走 `_get_config`
- **fire-and-forget 标准范式**：`create_task` + `add_done_callback(discard)` + 实例级 set 持有引用，存在 shutdown 任务丢失风险（已归档）
- **反思流程模板化**：init → read → prompt → LLM → commit → state → merge_check
- **工具插件化架构**：统一工具注册与调用，但工具分类逻辑（搜索 vs. 内容获取）存在语义混淆，需关注分组边界
- **声明式渲染与跨层边界**：HTML 附加 `data-markdown`，依赖客户端 Markdown 解析器；Jinja2 截断+客户端解析构成跨层语法破坏风险，降级为纯文本渲染是保守安全策略
- **防御性转义模式**：花括号转义是 `str.format()` 与用户输入共存的标配，“先转义再格式化”已成固定模式，但缺乏公共工具层，存在维护风险
- **一次配置变更可影响深远**：`web_search_enabled` 从 `False` 改为 `True` 这类默认值变更，可同时改变攻击面（SSRF）、资源成本（API 费用）和用户体验
- **部署兼容性演进**：启动脚本消除 `cd docker/..` 反模式，引入 `docker compose` 自适应检测，项目正从工具集合向可交付部署演进，配置中心化一致性权重升高
- **API 客户端 URL 拼接规范**：httpx 的 `base_url` + `url` 拼接易因斜杠产生意外，禁止在 base_url 尾部带路径细节，路径统一在请求方法参数中指定；外部 API 调用推荐使用完整 URL 消除拼接歧义；配置层应统一对 URL 做规范化处理（去尾斜杠、确保 scheme），降低各模块自行处理的风险
- **版本号管理**：分散在 backend/main.py、auth.py、init.sql 三个文件，缺少单一来源管理，应逐步统一从 `__version__.py` 导入

## 3. 已知问题和注意事项
- **错误处理不统一**：部分场景抛异常、部分静默降级，新代码应倾向显式错误传播
- **分支查找 fallback**：`_find_open_sakura_branch` 返回 `None` 时下游必须正确创建新分支
- **轮询缺失强制失败出口**：容器/服务就绪轮询若无超时检查和 `exit≠0`，会污染后续故障诊断，是反复出现的模式缺陷；任何启动等待循环都必须具备超时失败分支
- **“部分修复比未修复更危险”**：复合问题只修一半却整体标“已修复”是典型假闭环；修复验证必须推演完整调用链
- **“假修复”识别**：仅通过注释或文档声明“已知可接受风险”而关闭的安全问题（如 TOCTOU、竞态条件）不能标记为“已修复”，须标记为“未修复（已知风险已文档化）”或归档
- **fire-and-forget shutdown 丢失**：进程退出时异步任务可能未完成写入，已归档，新代码不得静默复制
- **“假实现”陷阱**：生命周期方法（`reset_*`、`init_*`）定义为公共方法但全仓库无调用，属于功能未完整实现；代码“引用了相关类/属性但效果缺失”时须回溯配置层
- **跨层截断风险**：模板截断（如 `[:500]`）+ Markdown 解析会破坏语法，任何涉及 Markdown 的可行性评估须作为标准检查项
- **渲染兼容性**：为纯文本区域添加 Markdown/HTML 解析时，历史值中的 `#`、`*` 等敏感字符可能被意外解析，必须检查并转义或禁用
- **防御性转义重复定义**：`_escape_braces` 等同模块内多次定义，修改一处时另一处可能遗漏，需归档跟踪
- **配置“假值”陷阱**：Python Truthy 检查（`if value:`）会将数值 0、空字符串等合法值误判为假，配置加载必须使用 `is not None`
- **默认免费非成本豁免**：配置默认值变更涉及可替换外部依赖时，不能以“默认 provider 免费”断言成本可控，必须条件化风险陈述
- **异步执行取消/超时风险**：`run_in_executor` 无法感知 asyncio 取消，缺少 `shield` 或超时处理可能导致任务泄漏，应作为审查重点扫描项
- **“幽灵变更”与隧道视野**：PR 描述提及但审查完全遗漏的文件（常见于配置默认值变更被“修复”主题掩盖），必须在审查启动时强制核对文件覆盖一致性
- **httpx 重定向非透明失败**：httpx 默认不跟随重定向，3xx 响应直接被视为错误而开发者未感知；涉及 HTTP 客户端 URL 拼接修复时必须确认 `follow_redirects` 设置，审查须显式判断当前重定向行为是否为预期；3xx 相关 bug 须优先检查重定向跟随配置，而非仅修触发重定向的 URL
- **静默降级缺乏可见性**：降级兜底虽避免崩溃但掩盖功能缺失；任何降级路径必须产生可见性告警（日志警告或指标），否则视为 silent-failure 模式；Issue 分析识别到静默降级时应自动标记 silent-failure 并优先建议 regression 标签
- **安全默认值泄露**：JWT/CSRF 同一 secret_key 默认值、API token 在 query 参数传输等属于高危模式，必须强制检测并标记 major 以上
- **Setup 免认证接口风险**：仅靠前端守卫的免认证接口是反模式，必须强制网络层隔离或二次认证
- **文档重组织与代码过滤逻辑冲突**：新增子目录可能被 `document_service.py` 中跳过逻辑误判，任何文件位置变动须检查 DAO 层过滤规则
- **异步懒加载并发安全**：异步上下文中懒加载单例模式若无锁保护（如 `asyncio.Lock`），多协程并发时可能重复初始化，须评估竞态条件
- **关键路径外部依赖缺少错误隔离**：直接影响核心操作（如提交流程）的第三方调用，即使有默认兜底，也须捕获所有异常并记录日志，避免异常穿透导致功能中断

## 4. 审查中发现的重要模式
- **“标记-不修-再标记”循环**：严重程度判定与开发者认知不匹配时，审查侧应反思判定标准
- **打勾陷阱**：增量审查易陷入对照清单打勾——看到改了就打✅，不验证改得对不对、调用链是否完整；最危险的形态是“幽灵变更”，注意力被绑定在历史问题上而忽略新引入的重大风险；零评论高分是审查陷阱的典型信号，quick 审查即使 approve 也应留下“LGTM + 已知未验证项”的极简评论
- **配置默认值变更的连锁阻塞**：一个未附风险评估的 major 默认值变更会卡住后续所有提交（包括版本号 bump），突显功能开发阶段安全/兼容性评估前置的重要性；此类问题需尽早创建技术债 Issue 并标注阻塞原因
- **增量隧道视野新形态**：审查者错误认为“无交集即可不追踪历史阻塞项”，导致局部高质量但全局不安全；跨 PR 未闭环 major 必须作为前置检查，无论本次变更是否涉及
- **微小增量不失焦**：即使仅版本号 bump，也必须恪守阻塞规则，防止假安全网；微小变更不意味低风险，两行改动修复功能背后暴露的配置/客户端设计问题需单独记录
- **归档 ≠ 阻塞**：技术债务归档意味“已知且接受”，不应继续影响决策；但归档项被后续变更放大风险时（如 Web 搜索描述守卫移除 + 默认启用），应重新激活或升级
- **假闭环与验证缺失**：仅凭文档化关闭安全问题、验证停留在“是否修改”而非执行流，均导致假闭环；复合问题拆分枚举是避免假闭环的最直接手段
- **防御代码复制须验证必要性**：复制既有防御模式时应评估新场景是否需要同等强度
- **受限信息产出确定性声明的惯性**：quick 下信息受限是常态，不应产出“完备”“一致”等声明
- **技术债务的可接受性判定需要显式流程**：低优长期问题建立“第 2 轮未修复降级，第 3 轮归档”的处理流程，是优秀的长尾管理模式；修复的局限性应归档为技术债务，无法推动全局清理时当场建议创建工程债务 Issue
- **增量审查的两重责任**：增量审查不仅追踪历史问题的修复，也必须覆盖本次提交的整体变更意图，防止宏观风险感知失败
- **静默降级须声明注释**：任何降级兜底若无日志/指标可观测，视为静默失败；编码时须显式注释“已知降级：无告警”，Issue 分析时自动评估降级路径可见性
- **重复检测需实证**：Issue 重复判定不能仅凭直觉标记“可能重复”，必须输出候选 Issue 标题、核心描述并量化相似度，禁止“可能”式模糊表述导致假闭环
- **安全类 Issue 自动风险列表**：主动扫描请求应产出结构化风险列表（认证、授权、注入、SSRF、配置），强制推荐 security 标签并评估是否触发 bug 分类
- **文档重组织的强制检查项**：任何涉及文件新建或位置变动的 Issue，`document_service.py` 过滤逻辑和 RAG 索引机制必须列为强制检查项
- **API URL 拼接陷阱的根因是隐含契约**：base_url 内嵌路径构成隐式契约，修复应推动配置重构而非逐次修补；发现 base_url 包含路径段应视为技术债 Issue
- **重定向非透明失败是系统性弱点**：任何 HTTP 集成必须假设服务端随时可能返回 3xx，评估客户端处理能力
- **“删除优于修复”模式**：当功能冗余或引发一致性问题时，完全删除相关代码并委托给底层实现，往往比修补更安全，可避免后续连锁维护成本
- **幽灵PR模式**：PR描述与提交内容严重不符（如描述功能重构但提交仅为版本升级），审查必须识别此冲突并阻塞

## 5. 团队约定和规范

### 审查硬规则（强制执行）
- **三问法**：所有 major 评论必须内联“用户影响/利用条件/现有缓解”三问答案，任一答案为“无”或“不涉及”时自动降级为 minor
- **纯可读性封顶**：不涉及功能、安全、数据完整性的问题，严重程度封顶为 suggestion
- **自评矛盾降级**：评论正文出现“风险可控”“影响极小”“理论上”等降级信号词时，对应标签自动降一级
- **复合问题拆分**：一条评论包含多个独立子问题时须编号枚举，修复验证逐项勾选，部分修复标“部分修复”
- **根因修复验证**：问题描述引用高危区标签时，修复验证须回溯到高危区核心要求
- **历史问题消失检测**：每轮审查须显式清点上一轮所有 open 项的去向，禁止无痕消失
- **修复验证须含调用链**：标记“已修复”时必须验证修改点的上游调用和下游消费是否一致传递；安全问题仅通过注释“已文档化”关闭的，强制标记为“未修复”或归档
- **修复即清除标签**：增量提交修复某问题后，该问题从主评论移除，仅保留在已修复追踪表中
- **决策状态同步**：所有 critical/major 均已修复或归档且无新增阻塞项时，decision 须升级为 approve 或 comment
- **PR 描述与审查覆盖一致性校验**：审查开始前必须核对 PR 描述 Changes 列表、实际变更文件列表和审查覆盖列表三者一致；PR 描述提及但未覆盖的文件必须发出 critical 告警；全量审查须显式列出所有改动文件并标注审阅状态
- **强制一致性校验（major级别）**：审查前必须比对PR描述中的变更类型与提交diff的实际内容；若类型不符（如描述“重构”但提交“chore”），标记`[major]`并阻塞审查；若描述范围超出提交，要求澄清
- **配置默认值变更的强制风险评估**：任何更改外部可见行为或安全策略默认值的配置项，必须包含 major 级别以上风险评估，涵盖攻击面、资源成本、兼容性；以单一 provider 假设作为“影响可控”依据时须显式注明边界条件
- **AI 系统 prompt 变更审查**：审查对象为 AI 系统自己的工具描述或 prompt 时，视为高敏感变更，须进行提示注入、语义漂移和工具滥用评估，优先级不低于 warning
- **生命周期方法调用验证**：定义为 `reset_*`、`init_*`、`close_*` 等生命周期语义的公共方法，必须搜索全仓库调用点；若无调用，标记为 major 并视为功能未完整实现
- **硬规则 major 多轮未闭环阻塞**：项目记忆中明确标注“强制风险评估”且影响力为 major 的安全/架构类问题，若连续两轮未修复（跨 PR 同样生效），审查决策须降级为 request changes 或 comment 并说明阻塞理由；不得直接 approve
- **历史阻塞项强制关联**：即使当前增量与历史未闭环 major 无文件交集，审查决策也必须反映仍开放的阻塞项，不得以“无交集”为由忽略；quick 策略下摘要必须显式列出“仍开放的阻塞项”
- **容器/服务就绪轮询模式**：任何依赖轮询等待的启动或健康检查阶段，必须包含明确的超时检查和失败退出（exit≠0），缺其一视为 major 问题
- **连续未闭环风险转技术债**：连续 3 轮未修复的 major 风险，必须创建正式技术债 Issue 并标注阻塞原因，防止审查线程无限挂起
- **suggestion 槽位内容约束**：只能包含可行动的前瞻建议，禁止粘贴变更评估表格、摘要片段或修复确认类内容
- **“已有模式”标签强制升级**：任何被识别为“与现有代码行为一致”的缺陷，必须标为 warning 并归档
- **微小增量横向扫描**：diff ≤ 30 行但涉及 `format(`、Markdown 解析、URL 拼接等敏感 API 时，须执行同文件全文关键字符扫描；涉及字符串拼接构成 API 路径时必须 `git grep` 扫描同类字面量
- **安全扫描 Issue 强制风险列表**：主动安全扫描/审计类 Issue 须产出结构化风险列表，强制推荐 security 标签，默认密钥泄露类问题须自动标记 major 以上
- **Issue 重复检测实证要求**：判定重复时须输出候选 Issue 标题与核心描述并量化相似度，禁止仅凭“可能”式模糊结论；分析中须区分 Issue 状态，已关闭但问题重现应标为回归而非简单重复
- **URL 拼接检查清单**：所有 API 调用配置段禁止在 base_url 尾部带路径细节，外部 API 推荐使用完整 URL；修复 URL 拼接问题必须确认 `follow_redirects` 设置并评估全局启用
- **PR 引用 Issue 强制声明**：当 PR 描述出现 `Fixes #xxx` 时，审查摘要须包含“可见范围内该修改是否完全解决所引 Issue 尚存不确定性”或“已验证完全解决”；缺少此声明评分不得高于 8/10，需标记 missing-statement
- **标签规则记忆闭环**：分析识别到静默降级时须主动映射 silent-failure 标签；识别到先前修复未生效时须优先推荐 regression 标签
- **版本升级专项检查**：必须确认`pyproject.toml`/`setup.py`中的版本同步（若存在），检查是否有`CHANGELOG.md`更新需求；patch版本升级需说明修复了哪个具体问题
- **PR描述过时检测**：当PR描述包含未在本次提交中出现的代码变更时，强制要求更新描述或拆分PR，禁止“描述沿用上一轮PR内容”

### suggestion 疲劳归档协议
- 第 1 轮未修复：评估实际影响，考虑直接降级
- 第 2 轮未修复：强制降级为 suggestion
- 第 3 轮未修复：强制归档并从主评论移除，仅保留在摘要追踪表中

### quick 策略执行约束
