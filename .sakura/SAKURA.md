## 3. 审查核心原则
- 审查须核对 PR 描述、提交信息、文件清单与 diff 一致性；描述中可枚举功能点须逐项勾选，未勾选标 minor；描述与diff数字差异>10%须标 minor。
- 增量审查须声明范围+双轨评分(增量质量+PR整体评估)；历史 major 未清零评分上限 8；quick 上限 8。
- approve 须逐项声明未解决已知问题状态；request_changes 须对应明确 major/blocking。
- 高评分场景须强制先输出负面检查结果再写优点（隧道视野防范）。
- quick 策略须强制输出自检清单：决策完整性、上限、负面检查，未全勾不允许输出。
- **审查输出完整性前置检查**：审查生成前须校验输出格式合规性，校验失败须生成标准化元评论（含错误码）并中止内容性评论，杜绝静默失败。
- **"无发现"须输出正式结论**：审查完毕确认无风险时，须输出具体验证证据（grep命令+结果摘要），而非空结论或不输出。
- **增量审查全局风险关联**：存在未解决阻断性问题时，任何增量 approve 须声明"本审查未覆盖历史阻断问题#XXX，该风险仍为阻断项"。
- **"最简单"变更最严格审查**：一行版本号/配置变更须从安全、兼容性、CI流程、工具链配置多维度审查，提供完整证据链。

## 4. 硬规则
1. async 路由同步 I/O 须 asyncio.to_thread()。
2. 延迟导入须注释；配置废弃须全链路清理。
3. DB 枚举/状态新增须检查迁移+状态转移矩阵+超时逃脱。
4. DB schema 变更须检查 nullable/default/事务/并发。
5. LLM prompt 外部输入须有截断+清洗/包裹。
6. 终态方法缓存须验证清理(finalize=True)，遗漏=major。
7. 布尔/状态枚举新增须 grep 所有消费点。
8. 重复检测须含证据链(标题+相似+差异+结论)。
9. 大 PR(>=5k行)须逐模块审查；重构>=100行须声明测试/返回值/异常等价。
10. constants 变更须列消费方；软删除引入须追问累积/清理/恢复。
11. 安全相关须区分漏洞 vs 误杀(三角验证)。
12. 支付/计费变更须输出兼容性/回滚检查。
13. 新增 worker 须验证防重/重试/超时；映射表须有清理计划。
14. 重构类变更须强制双轨声明：测试全通过+返回值一致+异常等价。
15. 等量替换文件须逐变更点列出before->after并声明等价性。
16. 可观测性端点字段值变更须视为接口变更。
17. 前序问题标记"已修复"须有依据。
18. 同一suggestion连续>=3轮未处理须标注"长期搁置"。
19. Check Run/webhook/worker类状态修复须检查身份、状态、回收三者统一。
20. 预创建资源由worker接管须核对接管协议。
21. 重构+功能扩展组合PR不能按纯重构降级。
22. 配置/Provider类Issue须拆解配置源、配置流、协议差异。
23. Issue分类与标签不得空输出。
24. "看似重写"的需求须同步检查新协议支持。
25. **依赖更新须逐条核对Changelog Breaking Changes**；Major升级须摘要关键Bug修复（安全/数据一致性），即使"无影响"也须附grep验证摘要。
26. quick策略输出前须强制声明`[x] quick 上限 (8/10)`校验。
27. GitHub Actions大版本升级须逐条核对Breaking Changes。
28. 自动化工具PR描述覆盖度以最终合并后主diff为准。
29. 模糊治理类Issue应先建议`needs-information`标签。
30. **工具链配置变更专项清单**：CI/linting配置变更须评估规则影响范围、CI兼容性、是否附needs-ci-run标签。
31. **大规模格式化PR差异化策略**：修改文件>20的自动化格式化PR，重点审查工具配置合理性与unsafe-fixes抽样复查，简化逐行diff。
32. **Major依赖升级验收清单**：须增加"已评估核心库升级风险并附明确验证要求"项，风险提示须转化为可执行合并后行动项。
33. **外部依赖声明检查**：涉及新增外部服务依赖的PR，审查时应强制要求声明用途、必要性和回退方案。
34. **CI工作流破坏性变更声明规范**：修改CI/CD核心逻辑的PR，描述必须说明变更前/后行为及目的。
35. **工具配置忽略规则决策记录**：被加入ignore列表的linting规则须在PR描述中附理由。
36. **大规模工具链更新审查清单**：工具配置重大变更须含配置合理性审计、影响范围评估、与设计文档对齐验证。
37. **自动化依赖更新审查专项**：Dependabot/Renovate PR须强制检查：①分支命名符合Gitflow；②Changelog Breaking Changes逐条核对+grep验证调用点；③同类工作流文件依赖版本一致性；④插件/扩展生态兼容性。
38. **基础模块导入链验证**：定义被广泛依赖的基类/抽象层的PR，须验证基础模块及关键上层模块能否正常导入，防止阻断性语法错误扩散。
39. **Python版本一致性检查**：Python代码变更须扫描废弃Python 2语法（except逗号语法、print语句等），尤其新引入代码。
40. **复杂逻辑表达式可读性**：and/or/not混合超过两级时必须使用括号明确运算分组，即使优先级正确。
41. **ContextVar/隐式上下文一致性**：使用ContextVar传递服务依赖的代码，须审查所有执行上下文（lifespan、HTTP请求、后台任务），验证依赖来源一致性。
42. **关键操作排他性**：涉及数据一致性/服务关闭/状态重置的操作，须确保所有并发访问路径统一管理（同一supervisor或注册表）。
43. **后台任务显式管理**：后台任务创建须显式传入supervisor/管理者参数，禁止关键路径依赖隐式ContextVar传播。
44. **"停止"路径审查**：资源清理/关闭路径须额外关注，确保所有任务在关键操作（如删表）前被正确停止。
45. **简化变更审慎审查**：删除校验或限制时须确认：①是否有下游依赖该限制；②是否为向后兼容；③是否在全局重构中风险受控。

## 5. Agent/Worker/Webhook
- Agent 基类变更须列调用方检查返回值/异常/状态语义。
- Shell 白名单!=安全须检查 $()反引号;&&|&等；输出须双层限额。
- 长连接/worker 禁止 except:continue 无日志无退避。
- webhook 须检查签名/幂等/乱序/重复。

## 6. 知识库维护
- .sakura/更新须遵循**增量追加或精确修改**原则，禁止覆盖式重写。
- 元数据(版本号、次数、日期)修改须提供计算依据。
- .sakura/核心文件重大修改须视为与代码变更同等重要的审查项。
- 工具链同步闭环：引入新工具须完成 配置→验证产出物→必要时修改项目规范 的完整闭环。
