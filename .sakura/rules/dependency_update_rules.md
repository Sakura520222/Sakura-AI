# 依赖更新审查规则（扩展版）

## 1. 依赖更新深度审查规则
- **Major 升级专项检查**：主版本号升级须逐条核对上游 Changelog Breaking Changes，用 grep 搜索被移除/重命名的输入参数，确认现有配置兼容
- **Breaking Change 逐项确认**：对于主版本号（major）或包含破坏性变更（如放弃旧版Python支持、弃用API）的依赖升级，即使只改一行代码，也必须：
  - 评估项目中实际调用点
  - 对照上游 Changelog 的破坏性列表，逐项确认本项目是否受影响
  - 必要时要求添加测试或版本兼容性说明
- **证据链标准化**：即使结论是"无影响"，也须附 grep 验证摘要（如"经 `grep -rn 'xxx' .` 确认项目代码中未调用此函数"）

## 2. Quick 策略执行校验规则
- **评分硬上限**：quick 策略评分上限 8/10，违反此上限属于元规则违反，严重程度高于漏报代码问题
- **自检声明要求**：在输出决策和评分前，强制进行自我校验声明，例如：`[x] quick 上限 (8/10)`。未包含此声明则不允许输出最终审查结果
- **高评分负面检查优先**：评分 ≥7 时须先输出负面检查结果再写优点，防止确认偏误
- **元规则自反性**：审查者不仅用规则审查代码，更须用规则审视自己的输出，评分上限/清单勾选等元规则具有最高优先级

## 3. 大版本语言运行时升级专项审查规则
- **Major 标记要求**：Python/Node.js 等语言大版本升级（如 3.x→3.y, y≥2）须标记为 major
- **兼容性验证计划**：必须包含依赖兼容性验证计划（至少包含：依赖锁定文件验证、核心功能冒烟测试）
- **版本跳跃路径**：建议提供版本跳跃路径（如 3.11→3.12→3.13→3.14）作为降级方案
- **额外检查项**：
  - `pyproject.toml` 或 `setup.cfg` 中的 `python_requires` 约束是否需要同步更新
  - CI/CD 流水线的 Python 版本矩阵是否覆盖新版
  - 容器镜像大小变化对部署成本的影响
  - 项目文档或 README 中的 Python 版本声明是否需要更新

## 4. 自动化依赖更新的审查增强规则
- **Dependabot/Renovate PR 专项检查**：
  - 版本跳跃幅度（minor/major）
  - 依赖在新版中的 breaking changes 文档
  - CI 矩阵是否覆盖新版
  - 分支命名是否符合 Gitflow 策略
- **PR 描述覆盖度**：以最终合并后主 diff 为准，而非初始提交
- **工具链同步规则**：自动化工具 PR 触发 CI 失败且为配置未覆盖时，须同时附带工具配置修改建议
- **验收清单**：即使经 CHANGELOG 确认无破坏性变更，也须增加 `[x] 已评估核心库升级风险并附明确验证要求`

## 5. "小变更"需要"大警惕"
- **影响面分析**：依赖版本号的一行修改，其影响可能横跨整个应用。不能因其 diff 小而降低审查严谨度
- **证据链优先**：审查摘要中 "检查了使用情况" 的结论，如果没有附上 grep 命令和结果，就是无效的。所有正面的结论都必须伴随可验证的证据
- **全量扫描清单**：全量审查时应增加：
  - `git diff --stat` 与 PR 描述的交叉验证
  - 依赖图分析（`pipdeptree` 或 `poetry show --tree`）以评估影响范围
  - 容器镜像扫描报告的调取（如 Trivy、Snyk 扫描结果）

## 6. CI 失败归属声明
- **禁止黑箱结论**：断言 "CI 失败与本次变更无关" 时须简述判断依据（如查看 CI 日志步骤）
- **CI 分支规则**：在严格的 Gitflow 或主分支保护规则下，CI 失败通常应视为 `blocker` 或至少是 `must-fix` 的 `minor`，禁止降级为 `suggestion`

## 7. GitHub Actions 大版本升级
- **Breaking Changes 核对**：升级主版本号时强制核对 Breaking Changes，搜索所有工作流文件确认废弃参数未被使用
- **配置合理性审计**：忽略的规则必须与项目架构匹配，与设计文档对齐

## 8. 证据链比结论重要
- **grep 结果必须附上**：所有关于"无影响"、"未使用"、"兼容"的结论，都必须附上 grep 搜索命令和结果作为证据
- **禁止无证据断言**：审查中不能只有结论而没有验证过程
