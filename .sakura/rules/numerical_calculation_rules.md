# 数值计算审查规则

## 1. 数值计算的"源码溯源"
- **禁止采信描述或注释**：对于任何涉及资源配额（连接数、线程数、超时时间）的配置变更，**禁止直接采信 PR 描述或注释中的计算结果**
- **现场反推计算**：必须强制在代码库中定位实际定义处（如 `database.py` 中的 `create_engine` 或 `pool` 配置），进行现场反推计算
- **示例流程**：若 PR 称连接上限为 20，必须搜索代码确认 `pool_size` 和 `max_overflow` 的实际值，验证计算是否正确

## 2. 警惕 PR 中的"算术题"
- **视为"未经测试的断言"**：PR 描述中包含的任何计算逻辑（如"余量约 20"、"内存降低 300MB"）都是高风险区，审查者应将其视为"未经测试的断言"，必须通过代码或配置进行独立验证

## 3. "安全余量"的双重验证
- **文档描述准确性检查**：在审查 `max-connections` 这类上限配置时，不能仅看"当前是否足够"，更要看"文档描述是否准确"
- **错误的余量描述更危险**：错误的余量描述（如文档称余量 20，实际仅 9）比"没有余量"更危险，因为它会诱导运维人员在后续扩容中做出错误的缩容决策

## 4. 文档与代码的"衰减"模式
- **算式易过时**：开发者倾向于在 PR 描述或配置注释中记录"设计算式"（如 `pool_size + max_overflow`），但这种算式极易随代码重构而过时
- **审查要求**：本次发现的问题表明，注释中的逻辑往往不会随代码变动自动更新，必须与代码实际值进行比对验证

## 5. 资源调优的"黑盒"风险
- **认知偏差风险**：在进行数据库或中间件调优时，参数（如 `max-connections`）的选取往往依赖于开发者对应用侧配置的"认知"
- **验证要求**：当这种认知存在偏差（如记错 `max_overflow` 值）时，会导致生产环境的"虚假安全余量"，必须通过代码追溯验证
