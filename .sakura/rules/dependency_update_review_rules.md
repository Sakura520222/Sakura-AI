# 依赖更新审查规则

> 来源：PR447-PR456 审查反思，2026年7-8月

## 一、变更规模与审查深度脱钩

1. **"一行变更"陷阱**：`requirements.txt`中一行版本号变更可能涉及核心库破坏性升级。**行数少 ≠ 风险低**，必须按依赖影响面而非diff行数确定审查深度。
2. **核心库升级强制清单**：数据库驱动（asyncmy/asyncpg）、安全库（webauthn/Jinja2）、模板引擎、认证库等核心依赖的任何版本升级，即使decision为approve，也必须附带风险提示和合并后验证要求。

## 二、证据链标准化

3. **"无影响"结论须附grep证据**：声明"项目未使用废弃API"时，必须输出验证命令及结果，如：
   ```
   grep -rn "废弃函数名" backend/ → 无输出，确认安全
   ```
4. **CHANGELOG逐项核对**：主版本号(major)升级必须对照上游Changelog的Breaking Changes列表，逐条确认项目是否受影响，不可仅凭"看了文档"跳过。
5. **证据链比结论重要**：即使最终结论是"无问题"，也必须输出"检查了什么→看到了什么→为何判断为安全"的完整推理过程。

## 三、版本升级分级审查

6. **Major版本升级**：必须执行完整审查——CHANGELOG分析 + 项目调用点grep + 兼容性评估 + 建议端到端验证。
7. **Patch版本升级到核心库**：仍需快速浏览Changelog确认无行为变更，不可因版本号"只差一点"而跳过。
8. **Python/Node.js运行时升级**：属于最高层级依赖变更，必须验证核心依赖（如chromadb）在新运行时下的兼容性，要求构建日志 + 冒烟测试证据。

## 四、Quick策略下的评分铁律

9. **评分上限8/10不可违反**：quick策略下评分必须≤8/10。给出9/10或10/10是比漏报代码问题更严重的审查输出错误（PR448, PR444教训）。
10. **自反性检查**：审查者输出前必须用规则审视自己的输出——评分是否超限、决策是否与风险等级匹配、是否存在确认偏误。

## 五、审查工具失效应急

11. **降级输出强制规范**：当审查工具因格式校验等原因无法产出有效输出时，必须生成降级结果——包含错误码"REVIEW_FAILED"和"需人工复核"声明（PR454, PR456教训）。
12. **工具自身可观测性**：审查系统的输出验证失败（如`expected <FINDINGS>`）是关键运维信号，必须被监控和修复。
