# CI/CD 审查规则

## 1. CI/CD 工作流变更专项评估
- **权限最小化原则**：新增或修改 `.github/workflows` 文件时，需评估权限范围是否符合最小化原则
- **构建缓存策略**：检查缓存策略是否合理，避免缓存失效或缓存污染
- **构建产物安全性**：评估是否需要 SBOM（Software Bill of Materials）等安全清单
- **维护成本评估**：新增发布路径的维护复杂性

## 2. CI 结果的严重性分级
- **CI 失败默认为 error/minor**：明确"CI 检查失败"在代码审查中的默认严重性等级（应为 `error` 或 `minor`），禁止标记为 `suggestion`，除非有明确的豁免理由
- **Gitflow 分支规范作为第一道防线**：CI 的分支命名校验虽然属于流程规范，但其失败直接反映了代码未经过标准的开发流程，应尽早发现并纠正

## 3. 高评分 PR 二次审查
- **触发条件**：对于获得极高评分（如 9/10、10/10）的大型 PR，建议触发一个简短的"二次审查"流程
- **审查重点**：专门由不同审查者或更高级策略，重点检查自动化工具可能遗漏的**架构合理性、配置风险及非功能性需求**

## 4. 自动化工具 PR 流程检查
- **Gitflow 兼容性**：Dependabot/Renovate PR 的源分支和目标分支须符合仓库 Gitflow 策略
- **PR 描述与最终 diff 一致**：多依赖升级合并后，描述须覆盖最终变更
- **工具链同步修复**：CI 失败原因为配置未覆盖时须附工具配置修改建议

## 5. 测试隔离性审查
- **状态共享检查**：审查测试代码时，需检查测试用例之间是否存在通过类变量、全局状态等不当方式共享状态
- **并行化风险**：这类共享状态在未来的测试并行化中会成为关键缺陷
- **推荐做法**：应鼓励使用实例变量或 pytest fixtures
