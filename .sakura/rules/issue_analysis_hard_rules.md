# Issue 分析硬规则

基于 ISSUE #422~#432 反思提炼，所有 Issue 分析必须遵守。

## 1. 分类规则

### 1.1 配置/部署类
- 不得粗分为 `other`，优先归类 `configuration`
- 须提供阶梯式排查清单（按概率排序），首项为最可能根因
- 必须检查：GitHub App 安装权限、Webhook Secret、仓库特有注册依赖

### 1.2 并发竞态类
- 正确性问题用 `concurrency`/`race-condition`，非 `performance`
- 单例模式在 asyncio 并发中的状态污染须检查共享可变对象生命周期
- webhook 重试与事件频繁触发导致级联竞态，须建议去重或限流

### 1.3 大范围 Enhancement
- 不能标 `other`，应按 `enhancement` + `configuration` + `refactor` 多标签
- "重写/统一"不等于纯重构：须检查新协议支持、UI、数据结构、兼容旧配置
- 须拆解：配置源、配置流、协议差异、默认值、兼容性、回退与迁移风险

### 1.4 元分析/自引用
- 系统分析自身 Issue 时须启用递归深度限制（全局计数器）
- 所有分类/标签/优先级置信度自动乘以 0.7 衰减因子
- 应考虑 `meta`/`self-evaluation` 专属标签

## 2. 标签规则

- **标签不可为空输出**：至少给出最贴近的候选标签，保留与仓库标签体系一致
- **`duplicate` 须附完整证据链**：`{被引Issue标题} + {相似点} + {差异点} + {判断结论}`
- **`automated` 须明确语义**：区分"用户手动提交" vs "自动化流程"
- **`help wanted` 置信度保守**：核心链路任务通常不适合对外招募
- **`security` 仅用于已存在漏洞**，不用于假设性风险

## 3. 标题改写规则

- **不可缺失**：单次标题（如 "bug"、"报错"、"问题"）须强制改写
- **保留核心卖点**：配置/Provider 类保留"一键配置/模型内置/Provider 统一"等关键词
- **避免过度归纳**：不擅自扩大范围，保留需求边界
- **`[type][priority]` 前缀一致性**：若仓库使用则须保持

## 4. 可行性评估规则

- 复杂 Issue 须将"高复杂度"拆成可交付阶段
- 建议拆分维度：协议抽象 → 适配 → 元数据统一 → 参数映射 → UI 联动 → 故障转移 → 迁移兼容
- 每阶段须含：工作量估算、风险识别、技术依赖
- 必须评估"配置源"和"配置流"（写入来源、读取路径、多源冲突、回退机制）

## 5. 降级输出规则

- 所有降级输出须附带唯一错误码
- 禁止硬编码静态字符串伪装正常结果
- 须显式标记失败状态（`category: analysis_failed`）
- 内部错误信息禁止泄漏至用户界面
- 修复后须验证所有消费方对新状态标记的兼容性

## 6. AI 输出容错规则

- 解析失败须指数退避重试（至少 2 次）
- 保存完整载荷用于离线调优（而非仅 80 字符前后缀）
- 协议解析器须平衡严格性与容错性：特定字段做内容净化而非直接拒绝
- 多文件协同修复须编写集成测试验证整个链路

## 7. 部署/配置类排查模板

```
排查步骤（按概率排序）：
1. [最快验证] 检查 XXX（用户可立即执行）
2. 检查 GitHub App 安装权限
3. 检查 Webhook Secret 配置
4. 检查仓库特有注册依赖（如 Telegram 注册）
5. 检查网络连通性/AI API Key 有效性
...
```

## 8. 并发竞态排查清单

- [ ] 共享可变对象是否有生命周期声明？
- [ ] 单例模式在 asyncio 下是否有状态污染风险？
- [ ] webhook 是否有去重或幂等处理？
- [ ] 缓存是否有锁保护（asyncio.Lock）？
- [ ] 是否区分"性能问题"与"正确性问题"？
