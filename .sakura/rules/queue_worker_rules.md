# 队列与Worker架构审查规则

## 1. 入队阶段
- **幂等性声明须验证**：幂等键是什么？并发下check-then-insert不够，须有唯一约束兜底
- **冷启动容错**：队列表不存在时怎么办？须有迁移/自动建表说明
- **入队失败降级**：入队失败须有降级路径（如回退到完整审查），禁止静默丢弃
- **触发场景完整**：webhook各事件类型（push/synchronize/force_push）是否均入队？

## 2. 消费阶段
- **消息确认/重试机制**：消费失败时消息如何处理？重试次数、退避策略
- **死信队列**：多次重试失败的消息去哪？有无告警？
- **消费并发控制**：同一PR的多个增量审查是否串行处理？
- **幂等消费**：重复消息能否安全重复消费？

## 3. 状态管理
- **状态转移矩阵**：queued→in_progress→completed/failed/cancelled，每个转移的触发条件和退出条件
- **逃脱路径**：每个中间状态是否有超时/异常逃脱路径？无逃脱=major
- **终态资源清理**：_cancel_events、_background_tasks等资源字典在early return/finally时须检查清理
- **僵尸检测**：是否有定期扫描stale状态的机制？

## 4. 积压监控
- 队列长度监控指标是否暴露？
- 积压阈值告警是否配置？
- 消费延迟对用户体验的影响是否评估？

## 5. 事件顺序
- 乱序事件（如旧commit事件晚于新commit到达）如何处理？
- 重复事件（GitHub webhook重试投递）幂等性保障
- 事件丢失后的补偿机制
