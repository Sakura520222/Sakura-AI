# 审查元数据与输出质量规则

## PR/Issue 描述一致性
- 审查开始前必须比对：标题、描述、提交信息、实际 diff 文件。
- 若描述声称包含 health API、文档、迁移、依赖、release notes、多个 Issue/PR，但 diff 未体现，应至少标 `minor` 要求确认。
- Release/changelog 型 PR 若描述范围大于当前增量，应说明“本轮仅审查增量”，不能暗示全部 release 内容已验证。
- 自动生成或复用的描述若已过期，会误导发布记录和审查范围，应作为流程风险指出。

## 严重程度与决策一致
- `request_changes` 必须对应明确阻断项、major/critical 或必须修改的硬规则。
- 若正文写“无严重/重要问题、仅建议、评分高”，决策应为 `approve` 或 `comment`。
- 若存在 major 但仍 approve，必须解释不阻断原因：默认关闭、业务约束、已有保护、风险可接受等。
- 可观测性、测试 fake、docstring 等质量问题通常不应轻易标 major。

## 结构化评论降噪
只允许生成具体、可定位、可执行的 review comment。禁止把以下内容转为评论：
- 摘要、评分、结论、表格、规则清单；
- “做得好”“无问题”“已检查”；
- 无文件/行号的泛泛建议；
- 同一根因的重复评论。

评论应包含：文件位置、问题、影响、修复建议。正向结论不得带 `critical/major/minor` 标签。

## 增量审查边界
- 对历史问题只能说“本轮未涉及/未验证”或“基于历史记录已修复”，不要绝对确认。
- 核心基类、公共函数、配置、DB schema、权限过滤变更，即使 diff 小，也要做调用方/关联扫描。
