# 工具链变更审查规则（PR#459/#460教训）

## 大规模工具链更新审查清单
当 `ruff.toml`、`.pre-commit-config.yaml`、CI 工作流等工具配置发生重大变更时：

- **配置合理性审计**：新增/忽略的规则是否与项目架构、技术栈匹配？是否经过团队讨论？
- **影响范围评估**：列出受影响的主要规则类别，评估其对项目代码风格的实际影响
- **忽略规则决策记录**：任何被加入 `ignore` 列表的规则，必须在 PR 描述中附带简短理由
- **依赖兼容性核查**：目标 Python 版本变更时，必须核查所有核心依赖是否已正式支持新版本

## 非等价性变更验证要求
对于非纯格式化的改动（如引入 `asyncio.to_thread`、修改异常处理、调整控制流）：
- 不应仅满足于"测试通过"
- 必须说明修改的**目的**（如"防止事件循环阻塞"）
- 必须说明如何**验证**修改未改变外部可观测行为

## 审查工具自身失效的应对
- **降级输出强制规范**：审查工具格式验证失败时，必须生成带唯一错误码的 COMMENT，标记 REVIEW_FAILED
- **"无评论"≠"无问题"**：自动化审查场景下，"无评论"可能源于工具故障，审查者必须对"空结果"保持高度警惕
- **工具链故障直接导致审查质量归零**：维护审查工具的稳定性与维护项目代码同等重要

## CI 工作流变更专项评估
- **权限最小化**：审查工作流权限范围
- **构建缓存策略**：评估缓存策略合理性
- **外部依赖声明**：新增外部服务依赖（如 API、密钥）必须声明用途、必要性和回退方案
- **`cancel-in-progress` 风险**：评估该配置对下游任务的潜在中断影响
- **工作流依赖链连续性**：引入作业间 `needs` 依赖或条件跳过时，分析对整个工作流依赖链的潜在中断

## 大型格式化 PR 差异化审查
对文件数 >20 的自动化格式化/重构 PR：
1. **信任工具但验证边界**：重点审查工具配置的合理性，以及 `--unsafe-fixes` 部分的抽样人工复查
2. **聚焦变更描述**：严格审查 PR 描述的完整性和准确性
3. **简化代码级审查，强化元数据审查**：从逐行 diff 转向确认变更分类、版本号、文档同步性

## 高评分 PR 二次审查
对于获得极高评分（9/10、10/10）的大型 PR，建议触发简短的"二次审查"流程，重点检查自动化工具可能遗漏的架构合理性、配置风险及非功能性需求。
