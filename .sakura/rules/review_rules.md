# 审查规则

## PR 规模与策略

| 规则ID | 规则内容 | 优先级 |
|--------|----------|--------|
| PR-SIZE-001 | 文件数 >10 时，禁止使用 quick 策略 | P0 |
| PR-SCOPE-001 | 单 PR 不应同时包含：新子系统 + 配置变更 + 版本升级 | P1 |
| LARGE-FILE-001 | 新增文件 >200 行，必须包含结构概览评论 | P1 |

## 输出与决策

| 规则ID | 规则内容 | 优先级 |
|--------|----------|--------|
| REVIEW-OUTPUT-001 | 评分必须有评论支撑，否则降级为 incomplete | P0 |
| REVIEW-DECISION-001 | 禁止输出 unknown 决策，必须给出明确结论；对无足够依据的 unknown 建议兜底为 request_changes | P0 |

## Schema 与配置

| 规则ID | 规则内容 | 优先级 |
|--------|----------|--------|
| SCHEMA-CHANGE-001 | 数据库 Schema 变更必须被审查（索引、外键、字段类型与约束） | P1 |
| CONFIG-CHANGE-001 | 配置项净增 >20 行必须审查（默认值、边界、校验） | P1 |

## 建议与校验

| 规则ID | 规则内容 | 优先级 |
|--------|----------|--------|
| REVIEW-SUGGESTION-001 | 修复建议必须回查项目记忆与规范，避免与规范冲突 | P1 |
| REVIEW-SEVERITY-001 | major 标记应通过“三问法”反向验证：是否实际 bug、运行时错误、安全风险 | P1 |
| TYPE-SAFETY-001 | 跨函数/模块传递复杂数据禁止使用裸 dict，应使用 Pydantic/TypedDict/dataclass | P1 |

## 并发与失败模式

| 规则ID | 规则内容 | 优先级 |
|--------|----------|--------|
| CONCURRENT-GATHER-001 | 使用 asyncio.gather 时必须审查失败模式与错误传播 | P1 |

## 增量审查注意事项

- 对“大功能 PR + 后续小修”的增量审查，应在决策中提示“需确认主体变更是否已通过审查”，否则触发全量审查
