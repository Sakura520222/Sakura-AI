# 敏感数据处理审查规则

## 1. 敏感数据入口规范化原则
- **源头治理优于末端治理**：对于 API Key、Token 等外部输入的敏感凭证，**必须在第一次进入系统的边界（如 API 接收层、DTO 解析层）进行规范化（strip/trim）和校验**
- **禁止末端补丁**：禁止在业务逻辑层或适配器层通过"临时清洗"来处理脏数据，以避免脏数据落库或在不同业务路径间产生不一致行为
- **全路径一致性**：所有读取该敏感字段的代码路径必须使用相同的数据处理规范

## 2. 全链路影响分析
- **消费方检索要求**：当修改核心数据结构（如 `Account.api_key`）的处理逻辑时，审查清单必须包含：**"检索所有读取该字段的代码路径，并确认是否需要同步修改"**
- **工具要求**：必须利用 IDE 的"Find Usages"功能进行全仓库检索，防止漏网之鱼
- **读写分离验证**：探测（读/校验）与实际业务（写/执行）使用不同数据访问路径时，需验证修复是否能覆盖全场景

## 3. 防御性编程分布不均风险
- **统一输入层**：代码库中存在多处处理 `api_key` 的逻辑时，缺乏统一的输入清洗层是高风险点
- **使用点防御不足**：开发者倾向于在"使用点"做防御（如 `probe_account`），而不是在"入口点"做规范，应优先推动入口点治理

## 4. 错误处理同构性检查
- **逻辑同步更新**：相似功能的错误处理逻辑应保持一致。如 `setup_service.test_ai_api` 与 `account_probe` 在处理认证失败时逻辑相似（均为 401），但错误文案和处理逻辑未同步更新，会导致用户体验割裂

## 5. 测试覆盖局限性认识
- **测试不等于闭环**：虽然 PR 添加了针对某个函数的回归测试，且测试通过了，但这并不意味着系统整体功能正常。测试只能证明"被测函数"行为正确，无法证明"未测函数"（如实际 AI 调用链路）不受脏数据影响
- **测试通过≠Bug 修复闭环**

## 6. 适配器模式下沉风险
- **依赖脆弱性**：`build_headers` 等逻辑封装在适配器层，导致上层业务逻辑（如 `role_config`）可能直接传递原始数据，依赖下层适配器或探测逻辑来处理脏数据，这是一种脆弱的依赖关系
