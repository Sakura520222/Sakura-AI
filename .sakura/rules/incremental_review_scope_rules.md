# 增量审查范围管理规则（PR#478教训）

## 核心原则：边界是输入，不是围墙
审查的"策略边界"（如 quick 策略的范围限制）必须是决策时的"输入"，而不是思考的"围墙"。任何审查结论都必须在项目整体健康状况的背景下进行校准。

## 历史阻断问题的强制声明
- **approve 决策的前置条件**：当仓库存在被标记为"未解决的阻断性问题"的历史审查上下文时，任何增量审查的结论（尤其是 approve）都必须首先声明：
  > "本审查未覆盖/未验证历史阻断问题#XXX，该风险仍为当前 PR 的阻断项"
- **决策选项扩展**：建议策略的决策选项增加 `"approve_with_known_risks"`，明确区分"本增量无问题"和"本 PR 整体风险可接受"

## 简化逻辑变更审查清单
- 当删除校验或限制时，需额外确认：
  1. 是否有文档、接口契约或下游系统依赖该限制？
  2. 更改是向后兼容的，还是属于破坏性变更？
- **"简化"不等于"安全"**：移除校验看似降低复杂度，但可能扩大系统行为空间，或与整体架构的某处隐式约定冲突

## 评分与决策的上下文对齐
- 一个"技术上正确"的增量审查，如果发生在包含阻断性问题的 PR 中，其 approve 评分缺乏实际意义
- 审查系统的评分和决策机制需要包含"问题解决状态"这一维度
- **隧道视野防御**：增量审查或自动化工具容易让审查者"只见树木不见森林"，必须主动跳出变更文件本身，利用项目记忆、历史上下文和依赖图来评估变更的真实影响

## 来源
- PR#478（config.py 重构，quick 策略）：增量审查正确识别了变更本身的低风险，但忽略了 PR 中仍存在的 Python 2 语法阻断问题，给出了不安全的 approve 信号
- 核心教训：审查边界限制不能掩盖全局风险判断
