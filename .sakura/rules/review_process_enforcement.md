# 审查流程与输出执行规则

> 来源：近期 Issue #422、PR #419–#421 的复盘。与既有硬规则互补，强调可审计的执行方式。

## 描述、范围与数字

1. 审查前将 PR/Issue 标题、描述、提交说明和实际 diff 逐项对照。
2. 描述中可枚举的功能点必须在审查摘要逐项标记：已在 diff 验证、未包含于本轮、或未找到实现。描述声称而 diff 未体现的功能，至少标 `minor` 要求澄清。
3. 若描述的文件数或增删行数与 `git diff --stat` 偏差明显（建议阈值 10%），标记描述质量风险；文件列表截断时不得据此确认数字正确。
4. 重命名/重构 PR 中每个非重命名行为改动都须有独立动机和风险说明。

## 重构与小变更

1. 提取公共函数、内联替换、统一逻辑等重构，必须显式给出三项结论：
   - 测试是否通过；
   - 返回值/副作用是否等价；
   - 异常与边界行为是否等价。
2. 标题称“重构/统一”但实际放宽验证、扩大支持范围或改变默认行为时，将扩展部分作为功能变更独立审查。
3. 小型等量替换（尤其 +N/-N 且 N≤30）仍须逐点说明 before/after，不得以行数相等推定等价。
4. 微小修复也要执行负面检查：搜索同函数/调用链内同类用法、检查拼写/格式、确认无未覆盖的分支。

## 增量审查的证据要求

1. 历史问题只能基于当前 diff 证据，或明确引用已验证的历史增量，标为“已修复”；否则只能说“本轮未涉及/未验证”。
2. 标记历史问题关闭时，必须写明对应文件、提交/增量编号或测试证据；禁止无依据关闭。
3. 对循环中更新的共享变量（时间、状态、标识等），应搜索函数内全部消费点，不能只检查本次改动的两个分支。
4. `quick` 审查可缩小范围，但不免除：历史问题状态、关联调用链、描述-增量一致性和输出自检。

## 输出自检

提交结论前必须明确：
- 决策与严重程度一致；
- 增量质量与 PR 整体可合并性分开陈述；
- 已声明未修复的历史问题及其阻断性；
- 已完成负面检查；
- quick 策略时评分不高于约定上限。

正面评价或高评分不能替代上述检查；代码越简单、越像“标准重构”，越应先完成负面清单。
