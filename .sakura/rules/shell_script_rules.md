# Shell 脚本审查规则

## 1. API 调用中的"隐式默认值"审查
- **禁止假设服务端默认行为**：当 Shell 脚本通过 HTTP API 与服务端交互时，若请求体为空或省略了关键参数，必须强制审查服务端的默认值是否符合当前上下文
- **空 Body 陷阱**：遇到 `curl --data '{}'` 或类似写法时，必须第一时间查阅服务端代码，确认每一个省略字段的默认值是否会与脚本当前上下文变量（如 `$CURRENT_CHANNEL`）发生冲突
- **适用场景**：REST API 调用、Daemon/IPC 通信、配置更新接口

## 2. 多路径失败语义一致性
- **主路径与回退路径一致性审查**：对于存在"主路径"和"回退路径"的关键操作，必须强制审查两条路径在以下场景下的表现是否一致：
  - 无需更新时
  - 网络不可达时
  - 权限不足时
- **统一错误提示**：除非设计上明确允许差异，否则应向用户呈现统一的错误提示或状态码
- **典型案例**：优先使用高级组件（如 Daemon），失败时降级为原生工具（如 Docker Compose）的策略

## 3. 守护进程交互的幂等性
- **重复调用安全性**：涉及 Daemon/IPC 调用的脚本变更，必须验证重复调用（如用户连续按回车）是否会导致服务端状态紊乱或产生竞态条件（如多个 Job 同时运行）
- **状态同步验证**：确保脚本中的状态检查与守护进程的实际状态保持同步
- **适用场景**：Updater 守护进程、后台任务管理、IPC 通信

## 4. 外部 CLI 依赖版本特性清单
- **最低版本号标注**：在使用 Docker、Compose 或其他外部工具的特定参数（如 `--pull never`, `--progress tty`）时，必须在代码注释或依赖文档中显式标注要求的最低版本号
- **兼容性全覆盖**：引入新参数时，必须验证所有使用该工具的调用点都经过兼容性检查，不能仅覆盖显式处理过的部分
- **版本检查建议**：在脚本头部维护 `REQUIRES_DOCKER_COMPOSE_VERSION="2.22.0"` 等常量，并在初始化阶段进行检查

## 5. Dev 模式对等性验证
- **双模式逻辑等价性**：对于涉及进程生命周期管理的函数（start/stop/restart），必须审查其 Dev 模式（通常通过环境变量 `*_DEV=1` 触发）与生产模式的逻辑等价性
- **禁止空分支**：要求开发人员在实现生产逻辑时，必须同步实现 Dev 模式的对应路径，不得留空
- **强制演练**：审查此类代码时，应强制演练所有环境变量组合下的执行流

## 6. 状态驱动的菜单交互审查
- **状态准确性要求**：菜单逻辑高度依赖于动态状态（部署模式、当前频道、后台任务状态），这种状态机式的交互设计要求代码中对状态的读取和同步必须极其准确
- **状态变更追踪**：必须追踪所有可能导致状态变更的路径，确保菜单逻辑能正确响应

## 7. 双轨制回退架构审查
- **语义一致性维护**：项目采用"优先使用高级组件，失败时降级为原生工具"策略时，必须在两个不同执行环境（Daemon 环境vs 本地 Docker 环境）中维护语义的一致性
- **示例场景**："已是最新"的语义差异、成功/失败状态码、超时处理

## 8. 脚本健壮性检查
- **原子写入权限**：检查文件原子写入权限（如 0600）的设置是否合理
- **子 Shell 隔离**：验证子 Shell 是否正确隔离，避免变量污染
- **临时文件清理**：审查脚本异常中断（如用户 Ctrl+C）时，临时文件（`.tmp`）的清理机制是否完善
- **路径安全校验**：拒绝符号链接/越界的路径安全校验
