# 工具链更新模式

## 大规模更新的本质

工具链驱动的维护性更新不是简单的"格式调整"，而是项目规范的重要演进过程。

## 常见场景

### Ruff 版本升级
- **影响范围**：全局代码风格检查、自动化修复
- **风险点**：规则变更、新增默认规则、破坏性变更
- **审查重点**：ruff.toml 配置合理性、忽略规则理由、与设计文档对齐

### Python 版本升级
- **影响范围**：语言特性、标准库、第三方依赖兼容性
- **风险点**：3.11 → 3.14 等跳跃升级可能导致依赖不兼容
- **审查重点**：核心依赖（SQLAlchemy、FastAPI、Pydantic）官方支持状态

### GitHub Actions 升级
- **影响范围**：CI/CD 流程、构建环境
- **风险点**：废弃参数、行为变更
- **审查重点**：所有工作流文件的废弃参数使用检查

## 变更类型分类

### 纯格式化变更
- **特征**：仅涉及空格、换行、导入顺序
- **风险**：低
- **验证**：工具检查 + 抽样审查

### 非等价性变更
- **特征**：引入新函数、修改控制流、异步行为改变
- **风险**：中高
- **验证**：必须提供行为不变证明，不止依赖测试

### 配置决策变更
- **特征**：启用/禁用规则、修改阈值
- **风险**：长期影响代码质量
- **验证**：需要团队讨论和文档记录

## 审查层次

1. **配置层**：工具配置是否正确、合理
2. **变更层**：批量修复是否引入语义改变
3. **影响层**：依赖兼容性、开发环境、文档

## 最佳实践

- **小步迭代**：避免一次性升级多个工具或跨越多个大版本
- **文档同步**：变更说明须同步更新开发文档
- **回滚计划**：重大升级须制定回滚方案
- **监控告警**：升级后密切监控 CI 失败率和构建时间
