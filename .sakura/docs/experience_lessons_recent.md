# 近期审查经验教训（2026‑09）

本章节汇总了 2026‑09‑07 至 2026‑09‑14 期间 15 份审查反思中提炼出的关键经验教训，供团队在后续审查、PR 评估以及流程改进时参考。

## 1. 依赖升级审查
- **锁文件同步是阻断项**：`uv.lock` 未随 `pyproject.toml` / `requirements.txt` 更新会导致发布产物与 CI 环境不一致。必须在审查规则中将锁文件同步检查设为 **error**（见 `rules/dependency_upgrade_review_enhancements.md`）。
- **双清单一致性**：项目同时维护 `pyproject.toml` 与 `requirements.txt`，手动同步易出错。建议使用统一生成脚本 `scripts/verify_requirements_sync.py`，在 CI 中强制校验。
- **未使用依赖检测**：如 `python‑slugify` 在代码库中零调用，属于冗余依赖。引入全库 `import‑checker`，自动给出 **suggestion** “可移除”。
- **CI 证据必须附带**：所有 “无问题” 结论必须提供 CI 运行链接或搜索命令输出，防止审查结论缺乏可追溯性。
- **大版本升级需兼容性回归**：跨 major/minor 的依赖升级必须抓取上游 Release Notes，列出 Breaking Changes，并提供相应的回归测试或迁移代码。

## 2. 代码质量与安全审查
- **Python 2 语法禁用**：`except A, B:` 仍在多个模块中出现，导致 `SyntaxError` 阻断全库导入。已在 `rules/python_syntax_rules.md` 中明确为 **Critical**。
- **全局配置变更审查**：对 `backend/__init__.py` 中的环境变量注入必须进行全库搜索，防止隐式副作用（如 `PTB_TIMEDELTA`）。
- **异常捕获统一**：所有 `except` 必须使用 `as` 语法并记录异常对象，避免信息丢失。
- **跨模块影响评估**：增量审查需配合全库引用搜索，尤其在修改配置键、缓存结构或异常类时。

## 3. 架构与流程
- **单点故障防护**：`systemd.py` 对 `daemon.py` 的直接导入导致单点故障。建议使用延迟导入或 `try/except` 包装。
- **文档‑实现同步**：文档改动必须与代码实现保持一致，审查时应检查文档中的版本约束是否同步。
- **幂等性与原子化**：双写（Redis + 内存）结构需使用事务或 Lua 脚本保证原子性，防止并发回退。
- **灰度发布与 Feature Flag**：对影响外部渠道的改动（如通知服务）应使用 feature flag 或灰度发布，以便快速回滚。

## 4. 测试与可观测性
- **负向路径测试必不可少**：安全相关改动必须加入异常/空值的负向测试。
- **性能基准**：对解析类、全量扫描等关键路径加入 `pytest‑benchmark`，设定时延阈值（如 ≤ 5 ms）。
- **监控告警**：所有关键任务（如补偿扫描、锁文件同步）必须在 Prometheus/Alertmanager 中上报状态，防止任务失效而不自知。

## 5. 重复检测与标题规范
- **语义相似度检测**：仅靠关键字匹配会产生误报/漏报。建议结合 LLM/向量相似度进行二次比对。
- **标题结构**：遵循 `type(scope): description` 规范，保持信息完整；如无必要可保持原样。
