# 架构设计与关键决策

## 1. 分层架构
- **API层**：处理HTTP请求、参数验证、CSRF检查
- **服务层**：业务逻辑处理、事务管理、缓存操作
- **数据访问层**：数据库操作、ORM模型管理
- **路由层禁止直接操作数据库**：所有数据库操作必须通过服务层

## 2. 配置管理
- **配置三层穿透**：Settings → yaml_config → 硬编码默认值
- **动态配置系统**：`get_dynamic_config`统一接口，处理None/非法值降级并记录warn
- **配置默认值必须唯一声明于`config.py`**：禁止双源默认值

## 3. AI与检索
- **集中式结果解析器**：AI输出清洗收敛于`result_parser.py`
- **LLM API集成**：支持多种大语言模型API
- **RAG向量检索**：基于向量相似度的检索系统

## 4. 数据存储
- **MySQL**：主数据库，存储用户数据、配置、历史记录
- **Redis**：缓存、会话、限流、任务队列
- **内存回退字典**：实现大小/TTL限制，作为Redis降级方案

## 5. 前端架构
- **自包含WebUI**：HTML模板内嵌所有资源
- **Alpine.js**：轻量级前端框架
- **HTMX**：HTML增强，实现无JavaScript的AJAX交互
- **Tailwind CSS**：样式框架，支持暗色模式

## 6. 工具插件化架构
- **统一工具注册与调用**：所有工具通过统一接口注册
- **工具插件化**：支持动态加载和卸载工具

## 7. i18n国际化
- **i18n门面模式**：`render_template`统一注入`_()`和`lang`
- **翻译覆盖完整性**：所有用户可见字符串必须使用翻译键

## 8. 事务与并发
- **服务层自治事务模式**：服务方法内部自行commit
- **幂等共享信号模式**：取消任务时多排队任务共享asyncio.Event
- **批量操作savepoint模式**：循环中使用`begin_nested()`替代全局rollback

## 9. 权限与安全
- **权限策略单一真实源**：所有角色判断调用策略函数
- **安全操作必须记录审计日志**
- **外部可见链接必须通过统一链接服务生成**

## 10. 前端架构决策
- **显式标记优于路径推断**：使用`mark_webui_request` + `request.state.is_webui`替代排除法分类
- **延迟初始化模式必须全文件一致性检查**
- **模板JS插件安全规范**：强制使用`|tojson`进行JS上下文转义

## 11. 热点文件管理
- **热点文件复杂度管理**：承载过多业务逻辑的文件（如webhook.py）需特别关注跨逻辑审查
- **核心文件关联扫描**：对webhook.py等热点文件，即使"quick"策略也需跳跃式全量扫描
- **增量审查关联扫描清单**：为核心业务文件建立变更关联检查清单，自动检查任务创建、配额检查等关联逻辑

## 12. 事务边界架构
- **事务边界模糊审查**：配额检查与任务创建在不同事务中时，需评估数据最终一致性挑战
- **服务层事务边界规范**：强制要求服务层函数不执行commit，仅flush；路由层统一commit
- **批量操作事务一致性**：检查部分失败时是否回滚或记录补偿日志

## 13. Agent架构（基于 PR #399-#404 审查）
- **Agent基类核心控制流变更须列所有调用方**：检查返回值、异常传播、循环结束、副作用语义
- **Agent conversation推荐[system, user]起始消息**：仅靠system prompt启动须说明
- **LLM失败/空响应/最大迭代的日志语义属于可观测性契约**
- **工作区三层嵌套**：base_workspace ⊂ repo_root ⊂ worktree，安全校验基于路径包含关系

## 14. Check Run与审查状态同步（基于 PR #404）
- **head_sha在异步链路中漂移**：须验证初始化→传递→消费→异常→终态→反向影响全部路径
- **实例缓存将无状态变有状态**：判断标准是"是否引入跨请求的状态持久化"而非变更行数
- **双模型架构**：summary_model与主model的区分，ContextCompressor的模型归属是成本维度决策

## 15. 审查工具鲁棒性架构（基于 PR#454/#456）
- **审查输出验证管道**：AI审查输出须经格式验证→内容完整性检查→降级输出兜底，任何环节失败都须生成带错误码的COMMENT
- **降级输出架构**：主审查路径失败时，降级路径必须生成：唯一错误码、REVIEW_FAILED状态标记、人工复核提示，禁止静默丢弃
- **规则执行引擎**：审查规则的100%执行需要执行验证机制（工具单元测试），而不仅仅是规则文档
- **审查输出自检链**：quick上限校验→负面检查校验→证据链完整性→决策完整性声明，任一失败须拦截输出

## 16. 自动化工具集成架构（基于 PR#452-#456）
- **Dependabot/Gitflow共存协议**：自动化工具分支命名须与项目Gitflow策略兼容，要么在策略文件中添加例外，要么配置工具生成符合策略的分支前缀
- **CI分支策略作为策略执行者**：外部Check Run执行分支策略校验是健壮设计，将策略与实现解耦
- **工具链同步机制**：自动化工具PR触发CI失败且为配置未覆盖时，须同时附带工具配置修改建议
- **依赖升级验证清单模板**：标准化的验证流程包括Changelog核对、项目影响评估、CI状态归属、破坏性变更确认

## 15. 队列与事件驱动链路（基于 PR #402）
- **事件驱动链路**：Webhook → Queue → Worker → AI Reviewer，状态分散在DB表和内存中
- **状态一致性是核心风险点**：状态同步延迟是异步架构的固有挑战
- **Activity Checkpoint作为"会话持久化层"**：checkpoint service承担跨实例的会话continuity
- **降级决策前置到同步层**：webhook层作为入口承担降级决策职责

## 16. 提示词-解析器架构
- **"宽松解析+强提示"范式**：解析器不做结构验证，通过提示词约束AI输出质量
- **纯文本格式传递数据**：提示词构建器与协议解析器间非结构化对象，契约是隐式的
- **存在性测试≠行为验证**：assert "xxx" in prompt 仅防回退，不证明行为正确
