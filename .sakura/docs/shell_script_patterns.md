# Shell 脚本模式与架构

## 1. Shell 脚本 "Client化" 趋势
- **HTTP 客户端能力**：`start.sh` 不再仅仅是 Docker Compose 的包装器，正在演变为具备复杂逻辑的 HTTP 客户端
- **REST API 交互**：通过 REST API (`/v1/update`) 与后台守护进程通信，处理 JSON 响应，并根据业务状态（如 `requires_confirmation`）进行逻辑分支
- **状态驱动**：菜单逻辑高度依赖于动态状态（部署模式、当前频道、后台任务状态）

## 2. 双轨制回退架构
- **优先高级组件，降级原生工具**：项目采用"优先使用高级组件，失败时降级为原生工具"的策略
- **复杂度增加**：这种模式增加了代码的复杂度，因为必须在两个不同的执行环境（Daemon 环境 vs 本地 Docker 环境）中维护语义的一致性
- **典型场景**：本次发现的"已是最新"的语义差异

## 3. 双层守护/升级架构
- **外层编排器 + 内层守护进程**：`start.sh` 作为外层编排器，`updater` 作为内层守护进程
- **状态同步复杂性**：stop 操作需要穿透两层逻辑（Shell 命令 → Socket → Daemon），这种架构在状态同步上存在复杂性
- **状态机式交互**：要求代码中对状态的读取和同步必须极其准确

## 4. Shell 脚本复杂度管理
- **Python 测试驱动**：通过引入 Python 测试（`test_start_sh_lifecycle.py`）来为 Shell 脚本建立"行为契约"
- **工程化模式**：这是一种将复杂 Shell 脚本工程化的有效模式

## 5. 防御性编程增强
- **路径安全校验**：代码中大量出现路径安全校验（拒绝符号链接/越界）
- **二进制安全校验**：`updater_binary_is_safe` 体现了项目对供应链安全的高度重视

## 6. 兼容性分层设计
- **新特性 vs 旧版本**：脚本试图同时兼容 Docker Compose 的新旧版本，但未能维持所有函数调用的一致性
- **兼容性回退链断裂**：`up -d --pull never` 虽然不是 pull 命令，但同样是 Compose 调用，且引入了新参数，必须纳入同一兼容性策略考量

## 7. 环境变量驱动的逻辑分支
- **隐蔽的 Bug 源**：Dev 模式通常通过环境变量控制，容易被主逻辑路径忽略（如 `stop_verified_updater` 中的 `elif` 链条漏掉了 Dev 场景）
- **强制演练要求**：审查此类代码时，应强制演练所有环境变量组合下的执行流
