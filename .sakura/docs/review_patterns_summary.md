# 审查反思关键模式总结（基于 459 次审查反思）

## 1. 审查质量核心指标

### 覆盖度评估
- **局部精准 vs 全局失守**：增量审查易陷入局部精准但全局失守的陷阱
- **PR级阻断表必须强制出现**：历史遗留问题必须在每次审查中追踪
- **全链路扫描清单**：配置保存→缓存失效→读取路径必须完整检查
- **小变更文件不可集体忽略**：≥3个≤10行变更文件须逐文件说明意图

### 准确度评估
- **严重程度一致性**：同一问题在报告各处的严重程度标记必须一致
- **上下文感知判断**：评估问题影响时需紧密结PR的上下文
- **决策逻辑一致性**：存在未闭环critical→decision降级为comment/request_changes
- **suggestion锚定效应**：初始偏低会导致后续追踪力度下降，应主动升温

### 完整性评估
- **意图理解充分**：审查需准确理解PR的意图和上下文
- **PR描述与diff量级差异须标major**：描述说"优化配置"实际是架构变更
- **增量审查摘要须含"抬头步骤"**：PR描述-增量一致性+历史问题状态

## 2. 增量审查决策硬规则
- **评分双轨制**：区分"增量质量分"与"PR整体可合并评估"
- **历史major阻断评分≤8**：满分须通过"历史major清零"硬性门槛
- **quick策略评分上限8**：除非显式执行完整检查点并声明
- **approve须逐项声明历史问题状态**：≥minor已知问题须声明已修复/延续存在
- **request_changes必须对应明确major/blocking**

## 3. 关键架构审查模式
- **行数少≠风险低**：实例缓存将无状态变有状态是架构级变更
- **提示词即接口契约**：修改约束须追踪下游解析代码隐式假设
- **格式契约级联故障**：各模块须独立解析、独立降级
- **安全边界调整须含原始设计确认**：判定"误伤"时须说明原始预期场景
- **队列服务固定审查维度**：入队幂等、消费并发、确认/重试、死信、积压

## 4. 防御性编程模式
- **镜像一致性原则**：对称结构防御逻辑须镜像检查边界条件
- **大小写归一化贯穿性**：归一化后须追踪后续所有使用点
- **布尔标志参数全路径传播**：grep所有调用点逐个判定
- **缓存生命周期显式声明**：有效范围、与对象生命周期匹配、内存增长风险

## 5. 经验教训核心
- **确认问题消失≠确认修复完备**：须验证替代方案到位
- **测试数量≠路径覆盖**：先画路径树再标注覆盖
- **全量重审的"全量"指影响面**：变更点的下游调用链扫描
- **approve不等于沉默**：零评论approve在审计追溯时等同未审查
- **PR描述"降维"是危险信号**：将架构变更描述为小优化应警觉

## 6. 依赖更新审查模式（PR441-PR456）

### 6.1 审查失误高频模式
- **"一行变更"认知陷阱**：diff行数少≠风险低，major升级仅改一行是常态
- **审查工具自身失效**：输出格式校验失败导致审查质量归零（PR454、PR456）
- **评分超限**：quick策略下给出9/10或10/10，违反8/10硬性上限（PR444、PR448）
- **证据链缺失**：声明"未使用废弃API"时未附grep命令和结果

### 6.2 标准化审查流程
1. 确认版本升级幅度（patch/minor/major）
2. major升级→逐条核对Changelog Breaking Changes
3. grep项目代码确认调用点和受影响API
4. 输出"命令→结果→结论"完整证据链
5. 自检评分是否在策略允许范围内

### 6.3 自动化工具集成审查
- Dependabot分支命名与Gitflow冲突是结构性问题，须在仓库配置层面解决
- PR描述可能与最终diff不一致，以合并后的主diff为准
- 审查自动化PR的首要任务是验证"工具输出的合规性"，而非代码本身
