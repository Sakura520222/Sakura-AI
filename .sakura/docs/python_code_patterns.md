# Python 代码模式

## 1. "消失的守卫"模式
- **重构陷阱**：在简化配置时，倾向于移除"显式的计数器/边界"（如 `max_tool_iterations`），将其替换为"隐式的全局约束"（如 `timeout`），但在实施过程中往往只完成了移除，而遗漏了新约束的实现
- **风险点**：这种模式导致代码失去物理硬约束，在 LLM 应用中极度危险

## 2. "僵尸配置"模式
- **定义-承诺-使用脱节**：配置在配置层定义、在文档中承诺、在国际化中翻译，但在执行层完全不可达
- **架构断层**：这反映了项目在架构重构时，配置契约与实际实现链路出现了断层
- **典型案例**：`agent_team_max_runtime_minutes`

## 3. 防御性编程的分布不均
- **缺乏统一输入层**：代码库中存在多处处理 `api_key` 的逻辑（`account_probe`、`setup_service`、`role_config`），但缺乏统一的输入清洗层
- **使用点防御**：开发者倾向于在"使用点"做防御（如本次 PR 的 `probe_account`），而不是在"入口点"做规范
- **风险**：这是一种脆弱的依赖关系，容易在不同业务路径间产生不一致行为

## 4. 适配器模式下沉
- **依赖脆弱性**：`build_headers` 等逻辑封装在适配器层，导致上层业务逻辑（如 `role_config`）可能直接传递原始数据
- **依赖下层适配器**：依赖下层适配器或探测逻辑来处理脏数据，是一种脆弱的依赖关系

## 5. 错误处理同构性差
- **逻辑相似但处理不同**：`setup_service.test_ai_api` 与 `account_probe` 在处理认证失败时逻辑相似（均为 401），但错误文案和处理逻辑未同步更新
- **用户体验割裂**：这会导致用户体验割裂

## 6. 渐进式功能扩展
- **清晰但可能积累冗余**：项目在现有框架上逐步添加功能，代码结构清晰但可能积累少量"脚手架"式冗余（如未使用的字典）
- **示例**：Telegram 通知框架上逐步添加功能（事件类型、用户偏好）

## 7. 模块化通知管道
- **职责分散**：通知逻辑分散在 `notifications.py`（核心逻辑）、`telegram_service.py`（数据访问）、`agent_team_worker.py`（触发）中
- **职责划分明确**：职责划分明确，但增加了跨文件追踪难度

## 8. 三层防御式规范化
- **逐层降级处理**：`_coerce_tool_call_to_dict` → `_normalize_tool_calls_inplace` → `_extract_tool_call_fields`，针对 SDK 对象/dict/字符串（checkpoint 损坏）逐层降级处理
- **历史痛点**：说明项目中 tool_call 的序列化/反序列化一直是痛点，历史上有过数据损坏

## 9. 提前创建消除竞态
- **存在即锁定**：将 review record 创建移到代码索引之前，用"存在即锁定"替代"查询后创建"
- **经典竞态修复模式**：这是经典的竞态修复模式

## 10. 双分支异常收尾
- **Exception 和 CancelledError**：分别处理但都更新状态为 FAILED
- **僵尸 review 的生产事故**：说明之前有过僵尸 review 的生产事故
