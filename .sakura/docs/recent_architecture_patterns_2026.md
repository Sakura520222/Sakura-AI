# 架构决策与模式总结 (2026)

## 一、Epic 级 Issue 分阶段拆解与“双轨制”治理架构

### 1.1 Epic 拆解与 Quick Wins 隔离
- **大方案分阶段切分**：对于涉及多模块重构、部署流程优化（如 Docker 镜像解耦）或统一通知中心建设等 Epic 级提案，必须强制拆解为“可独立合并”的子阶段（如 P0、P1、P2）。
- **缺陷修复与架构演进双轨推进**：当 Epic 提案中包含现有生产缺陷修复（如死循环忙等待、TypeError）与长期架构重构时，须将阶段 1 的紧急 Bug 修复提取为独立小 PR 先行合并，防止大型架构变动阻塞缺陷修复落地。
- **契约与防线前置预警**：在实施增量更新或模块解耦时，需提前识别现有的强 Schema 校验（如 `manifest.py` 严格 schema 匹配）及硬编码校验链（如 `jobs.py` 镜像状态机校验），防范破坏既有契约。

---

## 二、文档与代码交叉校验模式 (Docs-Code Cross-Verification)

### 2.1 事实对齐审查
- **代码事实驱动**：修改系统功能、触发规则、权限或 API 契约相关文档（如 `docs/*.md`）时，禁止纯文本静态阅读。必须找出对应实现代码，逐条核对逻辑断言（如正则匹配规则、HTTP 状态码、路由 Path、默认开关机制）。
- **废弃模块重构收敛**：废弃大型子模块（如旧消息通道）时，采用“保留函数存根/命令行但解耦注册 + 精简 API + 文档打标`[已停用]`”的收敛路径，杜绝虚假描述误导 API 消费方与运维人员。

---

## 三、前端 Jinja2 / Alpine.js 渐进增强架构

### 3.1 轻量 UI 与防线封装
- **集中化格式化纯函数**：HTML 模板脚本中封装纯函数统一处理 UI 文本拼接与降级，避免在多处轮询或回调中重复拼接。
- **优雅降级与渐进增强**：UI 样式修复优先推荐利用模板中已有的脚本/样式框架（如 Alpine.js 或原生 `<details>` 标签），提升体验的同时避免引入新依赖或重构风险。
