# 369次审查反思架构决策总结

## 一、分层架构决策

### 1.1 架构分层原则
- **API层**：处理HTTP请求、参数验证、CSRF检查
- **服务层**：业务逻辑处理、事务管理、缓存操作
- **数据访问层**：数据库操作、ORM模型管理
- **路由层禁止直接操作数据库**：所有数据库操作必须通过服务层

### 1.2 事务边界决策
- **服务层自治事务模式**：服务方法内部自行commit，路由层统一commit
- **批量操作savepoint模式**：循环中使用`begin_nested()`替代全局rollback
- **事务外的外部写入必须支持补偿或异步**：先外部存储后DB commit失败时必须有补偿回滚或记录异常供重试

### 1.3 权限与安全决策
- **权限策略单一真实源**：所有角色判断调用策略函数
- **安全操作必须记录审计日志**
- **外部可见链接必须通过统一链接服务生成**

## 二、配置管理架构

### 2.1 配置体系设计
- **配置三层穿透**：Settings → yaml_config → 硬编码默认值
- **动态配置系统**：`get_dynamic_config`统一接口，处理None/非法值降级并记录warn
- **配置默认值必须唯一声明于`config.py`**：禁止双源默认值

### 2.2 配置生命周期管理
- **配置键废弃时应同时标记其所有读取点**：并规划迁移或移除路径
- **避免出现"僵尸配置"**：代码中引用但UI中不可见的配置
- **配置的源与用分离风险**：当配置的读取点与写入点分离时，要警惕两者脱节的风险

### 2.3 配置验证层次性
- **前端验证（min）→ 后端验证（类型转换）→ 消费点验证（默认值）**：需形成完整链条
- **配置默认值四端一致性**：新增配置项需验证前端/后端/文档/配置中心默认值一致

## 三、AI与检索架构

### 3.1 AI系统架构
- **集中式结果解析器**：AI输出清洗收敛于`result_parser.py`
- **LLM API集成**：支持多种大语言模型API
- **RAG向量检索**：基于向量相似度的检索系统

### 3.2 工具插件化架构
- **统一工具注册与调用**：所有工具通过统一接口注册
- **工具插件化**：支持动态加载和卸载工具

## 四、数据存储架构

### 4.1 数据存储决策
- **MySQL**：主数据库，存储用户数据、配置、历史记录
- **Redis**：缓存、会话、限流、任务队列
- **内存回退字典**：实现大小/TTL限制，作为Redis降级方案

### 4.2 数据库操作规范
- **新增DB模型的datetime字段**：必须使用`datetime.now(timezone.utc)`，禁止utcnow
- **session异常后状态污染**：捕获DB异常后session可能inactive，必须显式rollback()或close()
- **批量操作savepoint模式**：循环中使用`begin_nested()`替代全局rollback

## 五、前端架构

### 5.1 前端架构决策
- **自包含WebUI**：HTML模板内嵌所有资源
- **Alpine.js**：轻量级前端框架
- **HTMX**：HTML增强，实现无JavaScript的AJAX交互
- **Tailwind CSS**：样式框架，支持暗色模式

### 5.2 模板安全规范
- **模板JS插件安全规范**：强制使用`|tojson`进行JS上下文转义，禁止仅用`|e`
- **模板中内联SVG装饰图标**：必须添加`aria-hidden="true"` + `focusable="false"`
- **新增WebUI模块必须检查"四一致"**：侧边栏链接、表单action、JS fetch、重定向URL与路由前缀一致

### 5.3 路由与中间件决策
- **显式标记优于路径推断**：使用`mark_webui_request` + `request.state.is_webui`替代排除法分类
- **FastAPI斜杠重定向处理**：对空路径装饰器（`@router.get("")`）的使用需标准化，避免遗漏路径变体
- **中间件-路由协同验证**：修改中间件ALLOWED_PATHS或路由优先级时，必须检查两者交互是否产生循环或覆盖漏洞

## 六、异步与并发架构

### 6.1 异步编程决策
- **异步调用方式必须统一**：同一模块内禁止混合`create_task`与`await`
- **asyncio.create_task创建的后台任务必须在服务shutdown时有机会完成**：或在文档中明确说明"允许丢失"
- **同步函数中使用get_running_loop().create_task时必须评估线程安全性**：无法创建任务时记录warning日志

### 6.2 并发安全决策
- **惰性资源重建函数必须实现幂等性和并发安全性**：如`reset_xxx_semaphore`
- **单例模式线程安全检查**：针对延迟初始化的单例，强制审查竞态条件（如使用锁或线程安全初始化器），标记为minor

## 七、i18n国际化架构

### 7.1 i18n门面模式
- **i18n门面模式**：`render_template`统一注入`_()`和`lang`
- **翻译覆盖完整性**：所有用户可见字符串必须使用翻译键
- **i18n先行实践**：预先添加翻译键是良好实践，避免了合并后的翻译缺失

## 八、热点文件管理架构

### 8.1 热点文件复杂度管理
- **热点文件复杂度管理**：承载过多业务逻辑的文件（如webhook.py）需特别关注跨逻辑审查
- **核心文件关联扫描**：对webhook.py等热点文件，即使"quick"策略也需跳跃式全量扫描
- **增量审查关联扫描清单**：为核心业务文件建立变更关联检查清单，自动检查任务创建、配额检查等关联逻辑

### 8.2 事务边界架构
- **事务边界模糊审查**：配额检查与任务创建在不同事务中时，需评估数据最终一致性挑战
- **服务层事务边界规范**：强制要求服务层函数不执行commit，仅flush；路由层统一commit
- **批量操作事务一致性**：检查部分失败时是否回滚或记录补偿日志

## 九、安全架构决策

### 9.1 安全架构原则
- **所有JSON API端点（除公开只读）必须显式使用CSRF依赖或头校验**：防止CSRF攻击
- **明文敏感字段存储必须加密**：新增DB列存储api_key/secret/token时必须使用加密
- **Shell命令白名单禁止前缀匹配**：必须解析第一个token精确匹配并拒绝shell元字符

### 9.2 支付系统安全架构
- **支付网关实例缓存规范**：高频调用场景必须评估网关实例缓存
- **支付网关时区明确化**：API时间戳参数需显式指定时区
- **Webhook幂等性验证**：强制验证事件重复处理逻辑

## 十、审查流程架构

### 10.1 审查流程决策
- **增量审查强制关联扫描清单**：对于关联Issue的PR，即使文件未变更，也必须检查相关测试文件的覆盖完整性
- **版本发布PR强制全量审查**：对于版本发布类PR，即使采用"quick"策略，也必须对核心功能变更进行关联扫描
- **增量审查覆盖度下降风险**：增量审查未充分扫描跨文件影响，建议对支付类PR强制执行全量重审或关联扫描清单

### 10.2 审查质量评估框架
- **覆盖度**：是否覆盖核心变更，识别重构中的关键问题
- **准确度**：严重程度判定是否合理，决策逻辑是否一致
- **完整性**：是否理解PR意图和上下文，深度是否足够

## 十一、技术债务管理架构

### 11.1 技术债务跟踪机制
- **未修复历史问题必须关联issue号**：否则阻断合并
- **连续3轮未根治问题自动升温**：升级为major→critical，第4轮自动生成issue
- **长期技术债务的风险评估**：对事务一致性等长期问题给出尖锐的风险提示

### 11.2 配置生命周期架构
- **配置键废弃时应同时标记其所有读取点**：并规划迁移或移除路径
- **避免出现"僵尸配置"**：代码中引用但UI中不可见的配置
- **配置的源与用分离风险**：当配置的读取点与写入点分离时，要警惕两者脱节的风险

## 十二、新增架构决策（基于369次审查）

### 12.1 资源操作安全架构
- **配额消耗类操作纳入强制检查**：与支付安全同等级别
- **资源操作闭环验证**：必须追踪从"预留/消耗"到"最终释放/结算"的完整生命周期
- **事务边界审查强化**：优先建议在同一个事务中完成，或明确设计补偿/回滚逻辑

### 12.2 增量审查优化架构
- **增量审查强制关联扫描清单**：对于关联Issue的PR，即使文件未变更，也必须检查相关测试文件的覆盖完整性
- **版本发布PR强制全量审查**：对于版本发布类PR，即使采用"quick"策略，也必须对核心功能变更进行关联扫描
- **增量审查覆盖度下降风险**：增量审查未充分扫描跨文件影响，建议对支付类PR强制执行全量重审或关联扫描清单

### 12.3 测试审查强化架构
- **安全校验边界测试强制要求**：对URL验证、金额解析等安全关键逻辑，必须新增边界测试用例（如`//evil.com`、零金额订单），并纳入阻断级检查
- **支付事务原子性检查**：任何支付状态变更必须评估与关联操作的事务一致性，标major
- **辅助函数直接测试强制规则**：独立纯函数必须有直接单元测试，覆盖边界情况（None、负数、无效输入），标major

### 12.4 配置管理强化架构
- **常量定义检查**：新增测试或功能时，必须验证引用的常量（如版本号）在项目中正确定义且文档化
- **路径解析健壮性**：在模块级别定义`REPO_ROOT`时，强制添加存在性检查
- **支付金额语义明确化**：强制要求金额解析函数返回`Optional[int]`，`None`表示解析失败，避免0的歧义

## 十三、协议/格式迁移架构决策（基于最新审查）

### 13.1 协议迁移规范
- **新旧协议映射表**：格式重构PR必须提供对比表格，列出每种输入在新旧行为下的差异
- **全局替换验证证据**：全局性模式替换必须提供grep/lint静态搜索证据，仅检查diff不够
- **行为契约变更声明**：重构类PR须以对比表格声明关键输入的新旧行为差异，评估下游消费者影响
- **重构PR完成度声明**：明确"本次完成目标的哪部分"和"已知遗留技术债"

### 13.2 资源生命周期架构
- **关闭循环防御编程**：遍历资源列表关闭时必须try...finally，确保单个失败不影响剩余
- **模块级缓存治理**：dict/对象池缓存必须有容量上限、清理策略或弱引用
- **动态参数白名单**：getattr反射访问外部配置字段名必须做白名单校验

### 13.3 Agent Team状态机架构
- **多worktree隔离**：per-repo异步锁 + per-task worktree实现任务间代码隔离
- **PR状态转移矩阵**：PR opened → review → feedback → iteration → push → new review → close/dismiss
- **决策引擎中枢**：变更decision_engine.py必须扫描所有调用方是否适配新数据语义

### 13.4 Shell/Agent输出安全架构
- **双层输出限额**：执行阶段防内存膨胀 + 模型上下文阶段防token溢出/注入
- **命令日志安全边界**：日志中的命令/URL/header必须限长+敏感信息模式脱敏
- **多执行路径一致性**：同类Shell执行能力存在多条路径时安全策略必须统一
