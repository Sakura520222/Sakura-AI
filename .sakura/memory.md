# 项目记忆

累计反思 455 次

## 核心审查原则

- **PR 描述与 diff 一致性强制校验**：描述提到但 diff 未体现至少标 minor；安全/DB/依赖变更标 major。
- **PR 内提交主题一致性**：新增提交与 PR 描述/历史提交属不同子系统时，必须标注偏离。
- **审查决策与严重程度一致**：`request_changes` 必须对应明确可执行的 blocking/major。
- **历史问题状态需证据**：标记修复必须给出代码位置或扫描依据。
- **提示词/配置文本变更的下游对齐**：修改提示词格式约束时，必须追踪下游解析代码，未验证至少标 minor。
- **小变更文件批量审查**：PR 中 ≥3 个变更量 ≤10 行的已有文件，逐文件说明意图和影响。
- **历史 major 阻断评分上限**：存在前序 major 未修复时，增量评分 ≤8，决策须 request_changes 或附条件 approve。
- **决策完整性声明扩展至 ≥minor**：approve 时若存在未解决已知问题（≥minor），须逐项声明状态。

## 增量审查专项

- **完整性验证**：区分"增量通过"与"PR 可合并"；历史阻断问题逐项列明。
- **双重视角**：微观（增量质量）+宏观（增量在 PR 全局中的位置）。
- **PR 描述-增量差异说明**：摘要中必须声明本轮增量范围与 PR 描述的差异。
- **"抬头步骤"**：看 diff 前先读 PR 描述 + 历史问题清单，最后逐项勾选。
- **增量评分双轨制**：显式区分"增量质量分"与"PR 整体可合并评估"。
- **终态缓存一致性检查**：所有终态 report 方法须验证是否调用缓存清理（如 `finalize=True`），遗漏 = major。

## 重构类变更审查

- **全仓扫描验证**：模式化替换须提供全仓静态搜索证据。
- **数据源替换三层检查**：X→Y 需验证(1)数据结构兼容(2)消费方适配(3)行为规则迁移。
- **语义迁移零遗漏**：A 统一迁移为 B，残留 A = blocking。
- **布尔标志参数全路径传播**：新增布尔参数须 grep 所有上层入口，禁止仅验证修改过的调用点。
- **"确认消失 ≠ 确认完备"**：移除危险代码后须验证替代方案到位。

## 代码质量与安全

- **安全修复"向前一步"**：全仓扫描同类模式。
- **区分安全漏洞与校验误报**：Security 异常首要鉴别"防线被击穿"还是"误伤"。
- **明文敏感字段禁止**：api_key/secret/token 必须加密。
- **恒定回退值是阻断信号**：须追问调用方依赖，标 major。
- **静默失败路径升级**：核心链路失败无告警且数据丢失 = major。
- **异常兜底日志**：`except Exception` 须含异常对象或 `exc_info=True`。
- **实例缓存生命周期显式声明**：须要求(1)有效生命周期声明(2)与对象生命周期匹配(3)内存增长评估。
- **缓存作为状态层需逃脱路径**：worker crash 后恢复、重启后冷启动。
- **"软引用"对称删除**：删除文件须 grep README、CHANGELOG 等非编译器检查的引用。
- **内部错误信息禁止泄漏至用户界面**。

## 测试与验证

- **"覆盖函数"≠"覆盖行为"**：先问参数触发哪条代码路径。
- **同源/镜像偏差**：同作者编写或测试数与修改点精确一致时警惕。
- **早返回路径字段集一致性**：多早返回同构字典时主动对比字段集。
- **热点文件变更需开销说明**：已知热点的任何新增应说明开销影响。

## 架构与模式

- **核心逻辑调用方扫描**：修改核心决策时列出并分析调用方适配。
- **事件驱动闭环**：webhook+worker+DB 查状态、重复/乱序、并发、唯一约束。
- **状态机逃脱路径**：每个中间状态须提供超时或异常逃脱路径。
- **标识符跨异步链路验证清单**：初始化→传递→消费→异常→终态→反向影响点。
- **异步标识符漂移风险**：增量消费模型下标识符可能变化，须验证中途切换场景。

## Issue 分析专项

- **重复检测证据链**：须含 {被引标题} + {相似点} + {差异点} + {结论} 四要素。
- **产品契合度首道过滤**：与核心功能无关的提议先从定位判断。
- **合规风险 → wontfix**：不映射为 low 优先级。
- **`security` 标签边界**：仅用于已有漏洞，不用于假设性风险。
- **功能提议三阶判断**：① 定位契合 → ② 合规可行 → ③ 优先级。
- **"AI 自主传参"需验证信息可用性**：AI 如何获知可选值是可行性阻断点。
- **回退策略不可静默产出错误**：AI 指定分支却回退默认 = 基于错误上下文产出错误结论。
- **格式契约级联故障**：每个字段须独立解析、独立降级。
- **回退默认值须标记"分析失败"**：与正常结果须可区分。
- **Meta/自引用 Issue**：递归检测必修；边界场景置信度 ×0.7 衰减。
- **可行性需含"可验证性"维度**。
- **可行性粒度应均匀或说明差异原因**。

## 经验教训

- **"正确语义"≠"安全变更"**：关注是否有代码依赖"错误行为"。
- **"纯文本变更"≠零风险**：提示词被下游隐式依赖时等同修改接口。
- **技术债"可接受"须有行动建议**。
- **跨模块直通数据流是脆弱点**：中间层变更不触发下游适配检查。
- **审查精力按"变更行数×架构关键度"分配**。
- **高评分=穷尽检查点，而非"没看到大问题"**。满分须通过历史 major 清零门槛。
- **增量隧道视野**：完成 diff 后强制回头读 PR 描述问"代码能被描述覆盖吗"。
- **suggestion vs major 锚定效应**：首次标签偏低会降低后续追踪力度。
- **"未来风险"suggestion 须建议代码追踪手段**（如 TODO）。
- **UI 行为缺陷优先考虑 bug**：用户说"不该发生"≠ enhancement。
- **`good first issue` 隐性门槛**：分析已识别的"注意 X"本身就是门槛。
