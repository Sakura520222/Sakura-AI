# 项目记忆

累计反思 16 次

## 核心审查原则

- **降级输出强制规范**：所有 fallback 路径须附带唯一错误码、显式标记失败状态；禁止硬编码静态字符串伪装正常结果。
- **审查输出有效性前置检查**：审查系统自身必须完成格式合规性校验，校验失败时生成标准化错误评论。
- **审查系统本身的可观测性**：审查系统的输出格式可能变更或解析存在bug，工具链故障直接导致审查质量归零。
- **工具链配置变更审查清单**：涉及CI配置、linting配置的PR，强制使用专项清单评估规则变更影响。
- **大规模格式化PR差异化审查策略**：文件数>20的格式化PR，重点审查工具配置合理性，简化代码级审查。
- **证据链比结论重要**："无发现"也需输出验证命令和结果，所有正面结论必须伴随可验证的证据。

## 依赖更新审查专项

- **依赖更新深度审查规则**：主版本号升级即使只改一行，也必须评估项目实际调用点，对照Changelog破坏性列表逐项确认。
- **依赖更新审查增强**：强制摘要关键Bug修复和特性变更（安全、数据一致性），提升审查信息密度。
- **Major依赖升级验收清单**：经CHANGELOG确认无破坏性变更，也应强制增加`[x] 已评估核心库升级风险并附明确验证要求`。
- **安全库审查双保险**：CHANGELOG审查+项目内调用点保守性评估+明确建议端到端功能验证。
- **"无害"变更保持审查深度**：防止确认偏误链，强制完成完整风险评估清单（包括查看Release Notes）。

## 工具集成与知识管理

- **工具链同步闭环**：引入外部工具必须完成"同步-验证"闭环：配置工具→验证产出物符合项目规范→必要时修改项目规范。
- **自动化PR的人工校准角色**：识别自动化与项目独特规范之间的错配，将其转化为对项目配置的改进。
- **知识库维护规则**：知识库更新应遵循"增量追加"或"精确修改"原则，禁止整体覆盖式重写；元数据修改须提供计算依据。
- **审查知识库变更须严谨**：知识库的变更应被视为与代码变更同等重要的审查项，需要逐项说明理由。

## 增量审查与流程

- **增量审查的上下文陷阱**：增量审查容易陷入"只看diff"陷阱，对文档修改应提供修改前后关键内容对比。
- **增量提交与审查反馈错位**：审查反馈应驱动修复提交，而不仅仅是积累新的历史记录。
- **持续追踪阻断性问题**：好的增量审查应持续追踪并验证先前提出的阻断性问题是否已解决。
- **"最简单"变更的"最严格"审查**：一行依赖升级恰恰需要最严格地执行依赖更新审查规则。

## 经验教训

- **审查工具自身是审查第一道关卡**：工具链任何故障都直接导致审查质量黑洞，维护工具稳定性与维护项目代码同等重要。
- **"无评论"不等于"无问题"**：自动化审查场景下，"无评论"可能源于工具故障，审查者必须对"空结果"保持高度警惕。
- **确认偏误链防范**：高评分极易引发确认偏误，代码越好越先做负面检查。
- **自动化工具的盲区与脆弱性**：自动化工具的工作流集成点可能成为信息断点，工具自身出错会直接导致审查质量归零。
- **规则执行的强制性**：反思核心不是制定更多规则，而是建立确保现有规则被100%执行和验证的机制。
