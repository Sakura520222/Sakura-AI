# 项目记忆

累计反思 5 次

## 核心审查原则

- **审查输出有效性前置检查**：审查系统自身必须完成格式合规性校验，校验失败时生成标准化错误评论。
- **审查系统本身的可观测性**：工具链故障直接导致审查质量归零，维护工具稳定性与维护项目代码同等重要。
- **"无评论"不等于"无问题"**：自动化审查场景下，"无评论"可能源于工具故障，审查者必须对"空结果"保持高度警惕。

## 依赖更新与配置变更审查

- **依赖更新深度审查规则**：主版本号升级必须评估项目实际调用点，对照Changelog破坏性列表逐项确认。
- **工具链配置变更审查清单**：涉及CI配置、linting配置的PR，强制使用专项清单评估规则变更影响。
- **外部依赖声明检查**：涉及新增外部服务依赖的PR，审查时应强制要求声明其用途、必要性和回退方案。
- **验证破坏性变更需"由点及链"**：验证框架升级路径应为：框架自身破坏性列表 → 项目直接代码调用点 → 项目依赖的插件/扩展生态的兼容性声明。

## 大规模变更审查策略

- **大规模格式化PR差异化审查策略**：文件数>20的格式化PR，重点审查工具配置合理性，简化代码级审查。
- **CI工作流破坏性变更声明规范**：修改CI/CD核心逻辑的PR，必须说明变更前后的行为及目的。
- **"高评分、大范围"PR的警惕性**：9/10评分和全部通过的测试极易引发确认偏误，需主动思考自动化工具的盲区。

## 增量审查与流程

- **增量审查的上下文陷阱**：增量审查容易陷入"只看diff"陷阱，对文档修改应提供修改前后关键内容对比。
- **持续追踪阻断性问题**：好的增量审查应持续追踪并验证先前提出的阻断性问题是否已解决。
- **"最简单"变更的"最严格"审查**：一行依赖升级恰恰需要最严格地执行依赖更新审查规则。

## 版本控制流程经验

- **维护税模式的验证**：Gitflow同步冲突是可预见的运维成本，需定期同步减少冲突复杂度。
- **自动化同步工具的脆弱性**：工具只能暴露问题，无法自动解决，需人工评估合并策略。
- **冲突解决的元知识**：解决冲突时，回顾各自分支的合并历史比单纯看diff更重要。

## 工具集成与知识管理

- **工具链同步闭环**：引入外部工具必须完成"同步-验证"闭环，必要时修改项目规范。
- **自动化PR的人工校准角色**：识别自动化与项目独特规范之间的错配，转化为对项目配置的改进。
- **知识库维护规则**：知识库更新应遵循"增量追加"或"精确修改"原则，禁止整体覆盖式重写。
- **自动化依赖更新PR审查专项清单**：对于Dependabot等工具生成的PR，强制检查分支命名、PR描述是否符合项目Gitflow规范，核对破坏性变更，验证项目实际调用点。
- **依赖升级一致性检查**：当升级某个CI/CD依赖（如Actions）时，强制检查仓库内所有同类工作流文件是否存在相同依赖，并建议统一版本。
- **自动化工具分支兼容性检查**：检查Dependabot/Renovate生成的PR分支名是否符合项目分支保护规则，若不符，明确指出需在配置文件中调整。
- **插件兼容性验证**：对于核心框架（如pytest）的主版本升级，必须验证所有直接依赖的插件（特别是测试插件）的兼容性版本要求。
