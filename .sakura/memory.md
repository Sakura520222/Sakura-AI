# 项目记忆

## 核心审查教训与模式

- **双重处理陷阱**：同一格式化函数在调用链重复执行，扫描数据全路径同名调用，标critical
- **服务层职责模糊**：comment_service为评论渲染唯一入口，禁止上游预渲染；违反标critical
- **历史问题闭环验证**：声称修复须列出所有调用位置、冲突消除证据，缺失触发missing-statement
- **增量审查陷阱**：隧道视野致配置假开关、数据流断裂；必须扫描受改动字段影响的下游模块（即使不在diff范围）；发现新字段须追踪全生命周期，缺环节标major
- **降级标志全生命周期追踪**：引入布尔降级标志时，必须检查所有赋值点、重置点、使用点，确保无路径绕过；缺失标major
- **批量操作状态追踪**：循环依赖“已有状态”判断时，必须在循环内维护`effective_entities`集合并实时更新，禁止仅使用初始快照；标major
- **外部依赖失败显式降级**：获取外部资源失败禁止返回空列表/空字典，必须返回None或抛异常，调用方需显式处理；违反标major
- **配置解析红线**：禁止使用`.replace(',', ' ').split()`解析标签列表，统一使用`[item.strip() for item in raw.split(',') if item.strip()]`；标major
- **PyGithub多态返回防护**：使用`get_contents()`必须检查返回对象的`type`属性（file/dir/submodule/symlink），而非仅检查`isinstance(list)`；缺失标major
- **错误路径上游追踪**：函数改变失败模式（抛异常→返回错误字符串）时，必须审查所有调用方的处理逻辑；未追踪标major
- **增量审查回归评估**：须回答“是否新增未处理异常路径？”，未答评分≤8
- **日志语义与行为一致性**：行为变日志必同步；降级操作必须warning级
- **置信度/能力降级全链路追踪**：修改置信度或强制置零必须追踪所有消费者，确保0值不被过滤

## 代码高危区

- 降级标志相关代码路径（微小但影响全局）
- 批量冲突检测中的动态集合维护
- PyGithub的`get_contents()`多态返回处理
- 配置解析中的隐式split拆分
- 标签服务中GitHub API失败的None处理
- 单例服务热加载配置的并发安全

## 近期审查模式总结

- **批量操作状态追踪**：使用逐步更新的`effective_labels`集合比静态快照更可靠
- **标签冲突检测**：需同时检测“与已有标签冲突”和“本批标签间互斥”
- **降级可观测性**：不仅要记录“发生了什么降级”，还要记录“哪些功能被禁用”
- **“轻微变更”放大效应**：行数少≠风险低，须做影响面散射扫描
