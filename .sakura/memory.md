## 核心审查原则

- **PR 描述与 diff 一致性强制校验**：描述提到但 diff 未体现至少标 minor；安全/DB/依赖变更标 major。
- **PR 描述主体动作前置校验**：先提取描述主 claim，逐项在文件列表打勾，空勾=问题。
- **审查决策与严重程度一致**：`request_changes` 必须对应明确可执行的 blocking/major。
- **提示词/配置文本变更下游对齐**：修改提示词格式约束时须追踪下游解析代码。
- **小变更批量审查**：PR 中 ≥3 个变更量 ≤10 行的文件，逐文件说明意图和影响。
- **历史 major 阻断评分上限 ≤8**，决策须 request_changes 或附条件 approve。
- **决策完整性声明**：approve 时若存在未解决已知问题（≥minor），须逐项声明。
- **quick 策略评分上限 8/10**，除非显式执行完整检查点并声明。

## 增量审查专项

- **双重视角**：微观（增量质量）+宏观（增量在 PR 全局位置）。
- **"抬头步骤"**：看 diff 前先读 PR 描述+历史问题清单，逐项勾选。
- **增量评分双轨制**：显式区分"增量质量分"与"PR 整体可合并评估"，quick 策略也须声明。
- **前序问题状态显式声明**："前序问题状态：[incr N] → 已修复/未修复"。
- **隧道视野防范**：完成 diff 后回头问"代码能被描述覆盖吗"；正面评价越多越先做负面检查。
- **前序 major 修复信任链风险**：终审时建议对 major 修复做快速回扫。

## 重构类变更审查

- **重构+功能混合 PR 双轨检查**：须分"新功能验证"和"重构等价性验证"两节，后者声明(1)测试全通过(2)返回值一致(3)异常等价，缺项标 minor。
- **新增未测试方法/路径评分硬上限 ≤8**。测试数量多≠路径覆盖广。
- **全仓扫描验证**：模式化替换须提供静态搜索证据。
- **布尔标志参数全路径传播**：grep 所有上层入口。
- **constants 变更 ≥10 行须逐个 grep 验证消费方**。

## 代码质量与安全

- **安全修复三角验证**：(1)修复前确实误伤(2)修复后正常通过(3)修复后异常可预期。
- **安全边界调整须含原始设计合理性确认**。
- **全表加载检测**：`select(Model)` 无 WHERE 要求数据量评估或条件查询。
- **辅助功能资源上限**：非核心链路新增存储须声明大小/时间限制（辅助功能是资源泄漏高发区）。
- **"标记不可信"≠"防护完成"**：LLM prompt 链路外部输入须有截断和清洗。
- **映射表清理对称性**：A 清理须同步清理 A→B 映射记录。
- **隐式排序-去重耦合须注释**：Python 去重依赖 SQL 排序时须显式说明。
- **变量赋值变更语义一致性**：赋值来源改变时须验证变量名与新赋值语义匹配。
- **相对路径 cwd 须声明解析基准**，并验证与不传 cwd 行为等价。
- **auto-migrate NOT NULL 列须验证**：自研逻辑不等同数据库原生行为。
- **恒定回退值/静默失败路径**：标 major。异常兜底须含异常对象。
- **内部错误信息禁止泄漏至用户界面**。

## 测试与验证

- **端到端测试须验证最终输出正确性**，不能仅验证中间调用次数。
- **mock 应基于行为而非实现**（参数名匹配的 mock 在依赖升级时静默失效）。
- **早返回路径字段集一致性**：多早返回同构字典时对比字段集（重构类为必检项）。
- **"覆盖函数"≠"覆盖行为"**：先问参数触发哪条路径。

## 架构与模式

- **事件驱动闭环**：webhook+worker+DB 查状态、重复/乱序、并发、唯一约束。
- **状态机逃脱路径**：每个中间状态须有超时或异常逃脱路径。

## Issue 分析专项

- **重复检测四要素**：{被引标题}+{相似点}+{差异点}+{结论}，信息不足时标注而非给模糊结论。
- **需求模糊优先级保守**：时序模糊词须带条件标注（如"medium（需求澄清后确认）"）。
- **数据流方向翻转**：write→read 意味着从零构建获取/解析/注入层。
- **权限前置依赖检查**：读取新 API 端点须确认 App 权限覆盖。
- **工作量估算须与风险自洽**：识别复杂分支须反映在估算区间中。
- **可行性需含可验证性维度**。
- **横向对齐扫描**：发现模块最佳实践后 grep 同类模块。
- **增量 Issue 双轨评估**：逻辑正确性+工程经济性拆分分析。

## 经验教训

- **"解决可观测性"≠"解决根因"**：日志增强是暴露阶段，须追问告警/阻断机制。
- **"可观测性补丁"须关联处置闭环**。
- **字典键提取防御性标准**：跨模块字典键用于格式化时须类型兜底。
- **重构等价性不可假定**：审查精力按变更行数加权分配。
- **"向后兼容"需解析链证明**：相对路径兼容性须追踪到 OS 层面。
- **性能"时间炸弹"**：审查时问"调用时表里可能有多少数据"。
- **高评分=穷尽检查点**，suggestion 须建议追踪手段（如 TODO）。
- **`good first issue` 隐性门槛**：分析已识别的注意点本身就是门槛。
