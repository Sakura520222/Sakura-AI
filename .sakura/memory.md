# 项目记忆

## 审查模式与教训
- **增量审查三大陷阱**：1. 隧道视野（只看diff忽略历史架构缺陷）；2. 零评论高分（最危险的走过场）；3. 上下文浪费（无视PR描述中的多轮历史问题）
- **评分决策解耦**：增量代码质量高（9分）≠ PR可合并。存在未闭环 critical 问题时，decision 必须降级为 comment 或 request_changes
- **quick 策略失效**：对大PR（21文件）过滤异常导致仅识别2文件，产生空输出和 unknown 决策。quick 不等于跳过思考，必须有最低输出要求（摘要+理由+问题追踪表）

## 代码高危区与审查要点
- **路径安全**：`if "../" in path` 是错误做法，极易被 `....//` 绕过。必须用 `pathlib.Path.resolve()` 后验证前缀，属 error 级别
- **类型契约**：跨模块传递混用 `dict` 和 Object 是系统性隐患，溯源修复时必须横向排查全局同类模式
- **上帝服务**：单文件超800行且混合核心逻辑与模板管理，属于架构腐化前兆
- **并发与原子性**：单例模式和跨文件写操作是高危区，即使本轮未修改也要在 approve 前确认状态

## 规范演进
- 引入"历史阻断机制"：存在未解决严重问题时，增量审查的 approve 权限被锁定
- 引入"问题状态更新表"：增量审查必须显式标注历史问题是`已修复`、`遗留`还是`待确认`
- 安全相关发现（路径遍历、写权限）强制提升为 error，禁止人工或工具降级为 suggestion

## 遗留关注点
- `github_write_service.py` 是系统性问题高发区（5轮中4轮被标记），合并前必须全量重审其安全边界与并发逻辑
- `sakura_memory_service.py` 的日志增强和回退逻辑可能是排查非原子提交的前置步骤，需关注其实现是否真正解决了回滚缺陷
- 审查工具自身的文件解析/过滤逻辑存在 Bug，需排查大 PR 场景下的文件丢失问题
