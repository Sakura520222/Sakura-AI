## 核心审查原则

- **PR 描述与 diff 一致性**：描述提到但 diff 未体现至少标 minor；安全/DB/依赖变更标 major。
- **Commit Message 与 Diff 一致性**：单次 commit type/scope 须与实际文件匹配（`docs:` 出现 `.py` 变更标 minor）。
- **审查决策与严重程度一致**：`request_changes` 须对应 blocking/major。
- **审查输出自身合规性自检**：输出后须回扫项目记忆硬性约束，确认输出本身未违反。**这是最高优先级反思项。**
- **决策完整性声明**：approve 时存在未解决 ≥minor 问题须逐项声明。**quick 策略下同样强制。**
- **quick 策略评分上限 8/10**，除非显式执行完整检查点并声明。
- **历史 major 阻断评分上限 ≤8**。
- **小变更批量审查**：≥3 个变更量 ≤10 行的文件须逐文件说明。
- **提示词/配置文本变更下游对齐**。

## 增量审查专项

- **抬头步骤**：看 diff 前先读 PR 描述+历史问题清单，逐项勾选。
- **收尾步骤**：approve 前回头看 PR 整体可合并性并输出全局健康状态声明。
- **增量评分双轨制**：显式区分"增量质量分"与"PR 整体可合并评估"。
- **PR 描述范围边界**：增量审查中，非本次增量的描述项须显式标注。
- **前序问题连续追踪升级**：同一 minor 连续 ≥2 轮未修复，第 3 轮须升级为合并阻断或建议拆分 PR。
- **邻接区域连带审查**：±30 行范围内已知问题须作为 suggestion 提出。
- **隧道视野防范**：正面评价越多越先做负面检查。**代码越好越要警惕流程漏检。**
- **quick 策略强制清单尾件**：输出前打勾 `[ ]决策完整性 [ ]quick上限 [ ]负面检查`，未全勾不允许输出。

## 重构类变更审查

- **重构双轨检查**：分"新功能验证"和"重构等价性验证"两节，声明(1)测试全通过(2)返回值一致(3)异常等价，缺项标 minor。**被删除的防御性代码也须评估系统性作用。**
- **新增未测试方法评分 ≤8**，须显式声明测试覆盖状态。
- **正则→手工解析替换清单**：(1)正常输入等价 (2)拒绝输入等价 (3)嵌套/转义声明 (4)性能退化边界。
- **布尔标志/状态枚举全路径传播**：grep 所有消费方。
- **constants 变更须逐个 grep 验证消费方**。

## 代码质量与安全

- **成本类安全检查**：涉及付费 API（如 AI）的路由必须验证调用者权限，与传统安全同等级别。
- **安全修复三角验证**：(1)修复前误伤(2)修复后正常(3)修复后异常可预期。
- **LLM prompt 链路**：外部输入须有截断和清洗。**移除既有截断须验证下游有等效 Token 预算控制，否则按 major 处理。**
- **全表加载检测**：`select(Model)` 无 WHERE 要求数据量评估。
- **辅助功能资源上限**：新增存储须声明大小/时间限制及清理机制。软删除引入时须追问累积速率、清理任务、恢复路径。
- **不可逆转换**：escape/decode 不对称时须声明受影响字符集在业务中的出现概率。
- **内部错误信息禁止泄漏至用户界面**。
- **权限检查层级一致性**：同一 service 方法 ≥2 路由调用时，权限应在 service 层。
- **恒定回退值/静默失败标 major**。Best-effort 反序列化的下游容忍度须显式验证。
- **映射表清理对称性**：含"新建映射无清理计划"场景。
- **隐式排序-去重耦合须注释**；**相对路径 cwd 须声明解析基准**。

## 测试与验证

- **端到端测试须验证最终输出正确性**。
- **mock 应基于行为而非实现**。
- **测试文件结构完整性**：验证 def 声明、装饰器、无孤立代码块。**缺少 `def` 的测试静默不执行——比代码 bug 更危险。**
- **安全修复须有负面测试**（如 ReDoS 修复须验证恶意输入被正确拒绝）。

## 架构与模式

- **事件驱动闭环**：多链路时先建全景图，逐链路查防重/乱序/并发/唯一约束。
- **状态机逃脱路径**：每个中间状态须有超时/异常逃脱。新增状态须全仓 grep 验证。
- **大版本 PR 强制分模块审查**：≥5 个新增/大幅修改文件且 ≥5k 行时，逐模块独立审查。跳过高危模块须生成 Follow-up Issue。
- **ReDoS 银弹**：`splitlines()` + `re.match`（行首单次）是 O(N) 最可靠保障。

## Issue 分析专项

- **重复检测四要素**：{被引标题}+{相似点}+{差异点}+{结论}。
- **需求模糊优先级保守**；**权限前置依赖检查**；**可行性需含可验证性**。
- **增量 Issue 双轨评估**：逻辑正确性+工程经济性。

## 经验教训

- **"纯新增"≠"低风险"**：侵入性仅影响既有代码，不影响新增代码自身质量。
- **"交给下游处理"是伪命题**：LLM 应用中永远不能假设 API 能优雅处理超长输入。
- **"正确修复清单"≠"免检通行证"**：每个"正确"背后须追问边界条件、性能影响。
- **确认偏误链**：高评分极易引发确认偏误，导致对违逆规则的改动开绿灯。
- **大变更量"概览陷阱"**：好的摘要≠好的审查，摘要后须强制"逐模块深挖"。
- **"不在 diff 中"≠"不需要关注"**：邻接区域已知问题有"顺带修复"零成本窗口。
- **审查输出规则自违反**：元规则比业务规则更难自检测，反思阶段应首先回扫。
- **字典键提取防御性**；**性能"时间炸弹"**；**高评分=穷尽检查点**。
- **"解决可观测性"≠"解决根因"**；**重构等价性不可假定**。
