# 项目记忆

## 核心审查教训与模式

- **双重处理陷阱**：同一格式化函数在调用链重复执行，扫描数据全路径同名调用，标critical
- **服务层职责模糊**：comment_service为评论渲染唯一入口，禁止上游预渲染；违反标critical
- **历史问题闭环验证**：声称修复须列出所有调用位置、冲突消除证据，缺失触发missing-statement
- **增量审查陷阱**：隧道视野致配置假开关、数据流断裂；必须扫描受改动字段影响的下游模块；发现新字段须追踪全生命周期，缺环节标major
- **降级标志全生命周期追踪**：引入布尔降级标志时，必须检查所有赋值点、重置点、使用点，确保无路径绕过；缺失标major
- **异常处理器顺序敏感性**：多个@app.exception_handler注册顺序决定优先级，401重定向与全局拦截冲突可能导致认证流断裂，标major
- **跨层导入强制注释**：API模块从WebUI层导入依赖时，必须注释理由，否则标minor
- **全局异常处理器禁止引用业务依赖**：不得解析token、查数据库，仅做格式转换，违反标major
- **重复代码提取权衡性能**：高频场景（如降级日志）6次以上独立调用需批量聚合，避免I/O风暴，标suggestion

## 代码高危区
- 降级标志相关代码路径（微小但影响全局）
- 批量冲突检测中的动态集合维护
- PyGithub的get_contents()多态返回处理
- 配置解析中的隐式split拆分
- 混合认证场景（API与WebUI共用依赖注入）
- Telegram Update对象的message/callback_query多态访问

## 近期审查模式总结
- **支付开关全链路追踪**：新增开关须验证API路由、WebUI路由、命令注册、配额检查、调度任务共5个消费点
- **装饰器统一的风险**：从WebUI导入到API共享时，必须评估独立部署可能性及认证语义差异
- **错误页兜底副作用**：HTTPException拦截未区分401/403，可能破坏预期登录跳转
- **测试隐式全局状态**：禁止依赖conftest.py默认配置，所有外部依赖必须显式mock
- **配额降级可观测性**：6维度分别记录日志，但需评估监控告警是否依赖固定格式
