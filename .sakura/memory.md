# 项目记忆

累计反思 10 次

## 核心审查原则

- **降级输出强制规范**：所有 fallback 路径须附带唯一错误码、显式标记失败状态、脱敏内部错误；禁止硬编码静态字符串伪装正常结果。
- **PR 描述与 diff 一致性**：提到但 diff 未体现标 minor；安全/DB/依赖标 major。
- **审查决策与严重程度一致**；**审查输出自身合规性自检**（最高优先级）。
- **决策完整性声明**：approve 时未解决 ≥minor 须逐项声明，quick 下同样强制。
- **quick 策略评分上限 8/10**；**强制清单尾件**：打勾 `[ ]决策完整性 [ ]quick上限 [ ]负面检查`。
- **依赖更新深度审查规则**：对于主版本号（major）或包含破坏性变更的依赖升级，即使只改一行，也必须评估项目中实际调用点，对照上游 Changelog 破坏性列表逐项确认是否受影响。
- **quick 策略执行校验规则**：输出决策和评分前强制自我校验声明：`[x] quick 上限 (8/10)`，未包含则不允许输出。
- **自动化工具PR流程检查**：对于 Dependabot/Renovate 等工具创建的、旨在更新依赖的 PR，必须检查其源分支和目标分支是否符合仓库配置的 Gitflow/分支策略。若不符合，应在审查中明确指出并建议解决方案。
- **GitHub Actions 大版本升级专项检查**：升级主版本号时强制逐条核对 Breaking Changes，用 grep 搜索被移除或重命名的输入参数，确认现有配置兼容性。

## 增量审查专项

- **抬头**：先读 PR 描述+历史问题清单逐项勾选。**收尾**：approve 前输出全局健康状态。
- **增量评分双轨制**：区分"增量质量分"与"PR 整体可合并评估"。
- **前序问题连续追踪升级**：同一 minor 连续 ≥2 轮未修复，第 3 轮须升级。
- **隧道视野防范**：正面评价越多越先做负面检查。**代码越好越要警惕流程漏检。**
- **增量上下文碎片化风险**：跨增量一致性验证最易失效，须主动防漏。

## 代码质量与安全

- **安全修复三角验证**：(1)修复前误伤(2)修复后正常(3)修复后异常。
- **LLM prompt 链路**：外部输入须截断和清洗。移除截断须验证下游等效 Token 控制。
- **内部错误信息禁止泄漏至用户界面**。
- **恒定回退值/静默失败标 major**。
- **安全库审查的"双保险"原则**：对于安全类核心库升级，CHANGELOG审查只是第一步。第二步必须是对项目内实际调用点进行保守性评估，并明确建议进行端到端功能验证。

## 经验教训

- **确认偏误链**：高评分极易引发确认偏误。**代码越好越先做负面检查。**
- **证据链比结论重要**："检查了使用情况"的结论，没有附上 grep 命令和结果，就是无效的。所有正面结论都必须伴随可验证的证据。依赖更新审查须包含"证据链摘要"。
- **"依赖更新"≠"仅版本号变更"**：依赖库版本号背后包含代码变更。审查者需要养成快速浏览其更新日志的习惯，以洞察本次升级为项目带来的实际收益或潜在风险。
- **"低风险"变更的"高流程成本"**：即使是最简单的依赖版本更新，如果描述不完整，也会带来显著的沟通、审查和后续维护成本。流程严谨性本身是质量的一部分。
- **自动化工具的盲区**：依赖自动化工具极大提高了维护效率，但其工作流集成点（如 PR 生成）可能成为信息断点。审查者的角色之一就是识别并修补这类"人-机协作"的缝隙。
- **审查工具自身可靠性**：审查工具需要确保能正确执行预定义的审查规则。规则执行失守是比漏报代码问题更严重的审查输出错误。
- **CI失败归属声明细化**：当审查者断言"CI失败与本次变更无关"时，应在输出中简述判断依据，避免成为无法追溯的"黑箱结论"。
- **Quick策略评分依据显性化**：在quick策略输出中，用一句话简述评分考量（如"因依赖变更影响有限且CI状态存疑，未达8分上限"），使决策更透明。
- **全量重审的优势**：全量重审强制审查者从全局视角审视PR，有助于发现增量审查中可能因"只看相关代码"而忽略的跨文件影响。
