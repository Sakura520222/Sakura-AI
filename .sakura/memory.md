- **周期性触发模式一致性**：新增周期性功能必须参照现有`_check_and_run()`模式，包括`since_last`/`interval`计算逻辑，标major

## 架构与模式审查要点

- **配置体系扩展应优先复用动态配置体系**：避免硬编码，标major
- **延迟导入的并发安全性**：项目使用异步路由，需评估延迟导入在协程下的竞态条件
- **支付网关实例缓存规范**：高频调用场景必须评估网关实例缓存
- **全量扫描优先**：对于异步路由文件，审查前先执行全文件同步调用扫描
- **模式对比**：新增功能时主动对比现有相似功能的完整实现
- **核心文件关联扫描**：对`webhook.py`等热点文件，即使"quick"策略也需跳跃式全量扫描
- **日志级别策略**：高频执行路径默认debug，仅关键阈值提升info/warning，提供配置开关
- **配置管理一致性**：所有YAML配置键必须在WebUI提供管理界面
- **事务边界模糊审查**：配额检查与任务创建在不同事务中时，需评估数据最终一致性挑战
- **热点文件复杂度管理**：承载过多业务逻辑的文件（如webhook.py）需特别关注跨逻辑审查
- **增量审查关联扫描清单**：为核心业务文件建立变更关联检查清单，自动检查任务创建、配额检查等关联逻辑

## 审查流程与质量控制

- **重构PR整体影响评估**：标记为refactor的PR必须跨文件检查重构规则一致性
- **历史遗留问题风险评估**：涉及数据一致性（配额/资金）的问题不能仅标"优化建议"，必须评估现实风险，标major
- **严重程度一致性**：同一问题在报告各处的严重程度标记必须一致
- **PR描述与变更一致性验证**：审查前首先验证文件清单
- **增量审查强制关联文件检查**：支付类变更必须检查webhook路由、管理后台等调用路径
- **大型PR强制拆分审查**：避免单次审查覆盖度不足
- **重构后测试覆盖自查**：重构PR合并后建议对核心函数进行单元测试覆盖度自查
- **PR描述与实际变更偏差警惕**：审查前验证文件清单
- **全量重审价值评估**：全量重审能识别架构级问题和跨文件一致性，增量审查易陷入局部优化
- **配置变更全生命周期审查**：即使"quick"策略也应检查配置的定义→保存→使用→展示
- **规则应用主动性**：主动将记忆库规则转化为具体审查行动，而非被动识别

## 经验教训与最佳实践

### 审查策略与深度
- **审查需兼顾"树木"与"森林"**：增量审查易陷入局部，重构PR需评估全局模式一致性
- **重构后的"残留"审查**：大型删除PR审查重点从"新增了什么"转向"删除得是否干净"
- **全量重审价值**：全量重审能识别架构级问题和跨文件一致性，对于功能增强型PR能更好地评估整体设计合理性

### 技术模式审查
- **try/finally资源清理时序**：异常抛出时finally块执行顺序是常见错误源
- **事务原子性**：配额消耗与任务创建应绑定在同一事务或补偿机制中
- **配置硬编码审查**：默认值应在单一位置定义，避免多处硬编码
- **loguru日志占位符**：`{}`内先计算再传入，禁止内含条件表达式，标major
- **防御性编程语义精确性**：`if reflection_count == 0`检查需评估是否真正区分"未传入"和"实际为0"，避免逻辑歧义
- **周期性触发模式**：`since_last >= interval`是项目常见模式，审查时应作为模板对比

### 支付与资源安全
- **支付网关时区明确化**：API时间戳参数需显式指定时区
- **Webhook幂等性验证**：强制验证事件重复处理逻辑
- **支付类异常处理必须覆盖数据库连接异常**，标major
- **关键容错路径监控**：配额、支付等关键业务的补偿/清理操作失败，仅记录日志不足，必须同步触发监控指标或告警

### 配置管理最佳实践
- **配置验证层次性**：前端验证（min）→ 后端验证（类型转换）→ 消费点验证（默认值）需形成完整链条
- **i18n先行实践**：预先添加翻译键是良好实践，避免了合并后的翻译缺失
- **配置中心化建议**：建议将默认值定义在单一配置文件中，前后端引用同一常量
- **配置滥用风险防范**：无上限约束可能允许设置极大值，影响审查性能，需增加合理范围验证

### 增量审查反思
- **增量审查局限性**：仅关注增量变更可能遗漏变更对整体架构的长期影响
- **关联扫描重要性**：对于配置类变更，需检查配置与现有其他策略配置的交互影响
- **历史问题持续跟踪**：即使新PR已approve，仍需记录历史问题待后续解决
