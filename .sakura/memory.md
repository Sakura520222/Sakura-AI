# 项目记忆

累计反思 11 次

## 核心审查原则

- **"无评论"不等于"无问题"**：空结果可能源于工具故障，须对"空结果"保持高度警惕
- **CI 失败是最高优先级信号**：若 CI 红灯涉及构建或导入失败，应直接作为阻断项，无需深入代码逻辑即可拒绝对应 PR
- **CI 结果强制阻断**：包含依赖升级的 PR 必须跑依赖兼容性测试，任何红灯直接标记为 error
- **阻断性问题的"语义-分级"一致性校验**：当审查结论中包含"将阻断合并"、"需立即修复"等语义描述时，强制要求将标签设为 `error` 或 `major`
- **修复正确问题不等于审查完成**：增量审查必须包含"上轮未解决问题状态确认"，防止隧道视野
- **删除即变更**：看似简单的"删除配置"实则是"移除安全护栏"，必须验证风险暴露面
- **增量审查强制全库引用搜索**：对于配置键删除、API 接口变更、异常类新增等，必须执行全仓库搜索确保无遗漏引用
- **大规模单次提交的风险**：单个 commit 改动 20+ 文件、+22k 行易遗漏细节，推荐拆分为功能/模块粒度的多个 PR
- **文档-代码双向验证**：文档中提到的安全模型、环境变量、网络策略必须在代码中实现，否则标记为 error

## 依赖与外部服务

- **依赖升级审查清单化**：针对 Major/Minor 版本升级，建立"Breaking Changes 核对清单"，覆盖运行时环境、API 兼容性和上下游消费端
- **依赖升级的"行为严格化"风险评估**：当依赖升级将默认行为从"宽松（warn/ignore）"变为"严格（error/fail）"时，必须显式评估对 CI 稳定性的潜在冲击
- **镜像标签与参数版本的强绑定**：使用特定版本支持的参数时，必须检查镜像标签是否显式固定（如 `mysql:8.4` 而非 `mysql:latest`）

## CI 与工作流

- **CI 失败是最高优先级信号**：任何 GitHub Actions 失败必须标记为 `error`，且合并前必须提供全绿 run 链接
- **Shell 脚本错误码强制对齐**：所有 `.sh` 脚本的 `return`、`exit` 必须返回 0-255 之间的明确错误码，CI 步骤中使用 `set -e`
- **Smoke 测试有效性**：新增 CI 步骤须验证测试脚本内部逻辑完备性，而非仅检查步骤存在性
- **依赖文件缓存统一规则**：`setup-python` 的 `cache-dependency-path` 必须指向项目根目录下的 `requirements.txt`、`pyproject.toml` 或 `poetry.lock`，并标注对应的安装方式

## 核心模块

- **能力声明一致性检查**：新增模型必须在 `builtin_declarations` 中声明其能力集合，CI 加入自动校验
- **元数据传递完整性**：跨模块调用返回对象必须显式包含能力集合，缺失视为 error
- **压缩器状态同步约定**：涉及 `context_compressor` 的文件必须在模型名称变更后调用 `compressor.set_model(name)`
- **单元测试命名规范**：针对能力驱动的功能，测试文件统一以 `test_<module>_capabilities_*.py` 命名
- **回退路径覆盖**：增量审查强制检查回退代码路径是否仍被单元测试覆盖
- **Mock 与生产代码同步**：测试层的 mock API 必须与生产实现保持一一对应，建议提供统一的系统调用 wrapper

## 前端与交互

- **多语言项目 i18n 同步**：任何文案变更必须自动关联检查翻译文件（如 `zh-CN.yaml` 与 `en.yaml`），作为固定审查项
- **单一真值源意识**：涉及 URL、版本号等常量时，从中心位置（如 `branding.py`）引用，避免硬编码

## 安全与错误处理

- **细化"错误文案透传"规范**：明确区分 `ValueError` 中哪些属于 `USER_INPUT_ERROR`（应透传）和 `INTERNAL_ERROR`（应脱敏），并在 Webhook 层建立对应处理分支
- **异常捕获粒度**：禁止在生产代码中出现 `except Exception:`，必须捕获具体异常并标注 `# USER_INPUT_ERROR` 或 `# INTERNAL_ERROR`
- **跨语言错误映射**：Shell 脚本的 `fail` 与 Python 异常必须在文档中保持一一对应，建立"错误码/日志"对照表
- **安全增强标签建议**：对 sandbox 或 isolation 类架构改进，建议补充 `sandbox` 或 `isolation` 标签

## Issue 分析规范

- **分类准确性**：根因是功能异常（如越界错误）属于 `bug`，标记 `enhancement` 需与 `bug` 同时出现
- **标签体系规范**：统一使用 `bug / enhancement / documentation / performance` 等主标签，使用复选标签（如 `bug + backend + file-tool`）
- **重复检测策略升级**：构建多维度相似度模型：① 错误类型（异常类名）② 触发文件路径 ③ 参数范围 ④ 关联分支/SHA
- **优先级评估模型**：引入影响度评分（业务阻断、回归风险、用户可见性），阻断阈值决定优先级

## 增量审查

- **全局风险关联**：未解决的阻断性问题是当前 PR 的阻断项，结论须声明未覆盖历史问题
- **历史遗留项显式结案**：增量审查必须包含"历史遗留项状态追踪"，对上一轮 Request Changes 逐一标记为 `[已修复]` / `[未修复]` / `[已过时]`
- **大幅度功能引入的全链路兼容性审查**：超过 500 行新增代码的 PR 必须执行：① API 兼容性对比表 ② 数据库迁移回滚脚本检查 ③ 关键路径测试覆盖率 ≥ 90%
