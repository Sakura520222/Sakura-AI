# 项目记忆

## 常见代码问题和审查要点

- **清理函数入参None安全性**：公共清理函数接收可能为None的DB对象时，必须检查内部是否安全处理None，标major
- **UUID截断必须注释**：任何将UUID截断（如[:8]）用于标识的代码，必须注释说明用途、碰撞概率、不用于持久化唯一键，标minor
- **返回值语义变更须同步调用方变量名**：函数返回值语义变更时检查调用方变量名是否保持语义一致，标suggestion；跨文件超过3处升级为major
- **取消路径必须抽取公共清理函数**：凡有2个及以上取消/中断检查点，必须复用同一清理函数，标major
- **新增状态枚举的全链路审查**：新增枚举值必须检查数据库ENUM/迁移、历史数据回填、API返回、WebUI模板/i18n/过滤器、SSE事件发送与前端接收，标major
- **并发模型注释强制**：实例级可变状态用于async单例时，必须注释依赖asyncio单线程或无竞态，标minor
- **延迟导入必须注释原因**：函数体内import若无注释说明循环引用原因，阻断合并，标major
- **bool是int子类的审查陷阱**：isinstance(v,int)过滤时若值域检查能排除False则安全，否则改为type(v)is int并注释
- **session异常后状态污染**：捕获DB异常后session可能inactive，必须显式rollback()或close()，禁止仅注释声称“自动恢复”，标major
- **rollback后必须验证session可用性**：rollback()后若无expunge_all()或重新begin()，标major
- **批量操作使用savepoint而非全局rollback**：循环中调用含rollback()的函数，建议使用begin_nested()，标suggestion
- **静默覆盖资源必须记录日志**：替换/覆盖Event、Lock、Queue时，必须记录debug日志，标major
- **返回值0的二义性**：函数返回0无法区分真无操作与调用失败，建议返回tuple或自定义结果对象
- **惰性重置遗漏读取路径**：所有读取用户配额/限流/统计类字段的路径（WebUI、API、管理员面板）必须调用重置/刷新函数，标major
- **公共函数事务行为变更审查**：rollback改为savepoint等事务边界变化时，必须审查所有调用方的事务假设，标major
- **孤儿版本号变量检查**：`__version__`定义处若全仓库无导入使用，应标记为suggestion并注释用途

## 近期审查模式总结

- **连续未修问题升温**：同一问题连续2轮从suggestion升major，连续3轮阻断合并并自动生成issue；实际风险低时可在PR中显式记录决策理由豁免
- **增量审查必须输出历史未解决问题清单**：标注本次是否处理，未处理须说明理由；同时须输出来自未修改文件的受影响调用方列表
- **公共函数副作用须用⚠️标注**：修改传入列表或对象状态时必须在docstring中标注
- **幂等性日志平衡**：高频场景跳过检查的日志改为条件变化时输出；幂等性注释必须包含“对不存在的记录”行为
- **多检查点行为收敛**：多阶段长任务取消检查点行为差异须在方法注释中说明
- **返回值语义变更的强制扫描**：返回值类型/含义变化时，必须扫描所有调用方（含跨仓库如Telegram模块）
- **版本号单一真实源**：项目必须定义唯一版本号来源，其他位置通过导入引用；SQL种子文件中的版本号改用CI注入或启动时插入

## 规范建议和经验教训

- **返回值语义分离**：task_key（业务标识）与task_id（日志追踪）解耦是良好关注点分离，但API响应字段名应与内部变量名同步
- **asyncio Event取消模式**：Event仅信号不支持取消原因，如需传递改用Queue或Future；注册event必须在create_task之前
- **复合返回值的风险**：字符串拼接返回值不易扩展且调用方难以类型安全使用，优先使用结构化类型（NamedTuple/dict）
- **增量审查的调用方检查**：修改变更文件时须扫描导入该模块的所有调用方及API响应消费者
- **注释vs结构决策**：若设计缺陷用注释而非代码修复，审查应追问未来修改者是否可能忽略注释
- **连续多轮major集中模块**：应建议暂停新功能专门重构该模块
- **状态变更全链路清单标准化**：建议创建固定检查表（DB ENUM→模型枚举→API序列化→WebUI模板→i18n→SSE事件→状态转换矩阵→前端JS接收）
- **SQLAlchemy异步session陷阱**：捕获异常后session进入inactive，仅rollback()可恢复但会丢弃未提交变更；优先使用async with session.begin()模式；begin_nested()在外层已begin时行为不同须注释
- **配额类问题分析模板**：定位所有写入/消耗路径（重置逻辑是否触发）+ 所有读取路径（是否调用重置），重点检查WebUI、API、定时报表、Webhook、管理员面板

## 需特别关注的领域

- **取消/中断检查点的一致性**：所有取消路径的资源清理必须统一，避免遗留状态；取消检查点传递的变量必须与当前实际值一致；`should_skip`等快速返回路径不能遗漏检查
- **asyncio并发竞态**：webhook多次触发、Event注册/注销配对、单例跨event loop使用
- **SQLAlchemy异步session事务边界**：取消路径中检查session有效性，异常后重建；禁止在非独占session的库函数中调用rollback()；savepoint重构须审查调用方事务预期
- **返回值0的二义性**：dismiss_bot_reviews等函数返回0无法区分真无操作与调用失败
- **SSE事件发送与接收**：新增状态时必须检查所有发送SSE事件的点是否覆盖该状态，以及前端JS/EventSource监听器是否处理该状态
- **状态机完整性**：引入新状态时必须审查所有状态转换路径、回退是否允许，以及cancelled等状态的允许入向状态
- **API响应字段语义漂移**：字段名变更须评估breaking change风险等级（低/中/高），若有外部依赖须同步更新文档
- **WebUI直接读库绕过业务逻辑**：审查所有展示配额、使用量的SQL/ORM查询，判断是否绕过了重置/刷新函数
