## 核心审查原则

- **"无评论"不等于"无问题"**：空结果可能源于工具故障，须对"空结果"保持高度警惕
- **"无评论"须附验证说明**：明确的搜索依据使"无评论"成为可验证的积极结论，而非简单的"没看到问题"
- **工具容错要显式**：自动审查因格式/解析错误中断时，报告必须明确呈现错误信息，防止误判为无风险
- **审查结论须逻辑自洽**：风险识别与决策间须有严格因果，识别阻断项却批准会损害可信度
- **最简单变更须最严格审查**：简单字符串替换可能隐含API契约变更，须保持额外警惕
- **高评分PR确认偏误警惕**：9/10评分易引发偏误，须主动寻找边缘安全与全链路完整性问题
- **PR描述风险点强制回应**：描述中"需确认"/"注意"/"未执行"等声明必须逐项转化为已知风险项并在决策中说明接受理由
- **阻断性问题的"语义-分级"一致性校验**：当审查结论中包含"将阻断合并"、"需立即修复"等语义描述时，强制要求将标签设为 `error` 或 `major`，禁止使用 `minor` 或 `suggestion`，以确保开发者对优先级的感知准确
- **修复正确问题不等于审查完成**：增量审查必须包含"上轮未解决问题状态确认"，防止隧道视野
- **破坏性修复的"双重确认"机制**：涉及代码删除（尤其是上轮误粘贴导致的大量删除）的修复 PR，必须明确执行"恢复完整性检查"，确保没有残留垃圾代码或丢失原有逻辑
- **修复 PR 需防止"隧道视野"**：在修复严重错误时，容易只关注"把错误的删掉"，而忽略"把对的补全"。必须同时关注"恢复逻辑"和"补全测试"两个维度
- **源头治理优于末端治理**：对于脏数据清洗，应推动在数据源头（持久化前）处理，而非各消费点补丁
- **删除即变更**：看似简单的"删除配置"实则是"移除安全护栏"，必须验证风险暴露面
- **CI 失败是最高优先级信号**：若 CI 红灯涉及构建或导入失败，应直接作为阻断项，无需深入代码逻辑即可拒绝对应 PR
- **变量名命名的上下文污染风险**：生产代码中出现典型的 Fixture 命名风格变量（如 `memory_bridge`）应作为发现"代码错位"的嗅探点
- **"好意"可能带来"毁灭性"后果**：补齐测试覆盖过程中必须警惕对生产代码的"误伤"
- **文档与代码的"单向真值"原则**：文档/注释不可作为代码行为验证依据，必须在代码中找到实现，否则判定为Bug
- **"默认行为可能随版本漂移"原则**：即使默认值在新版本中未改变（如 `archive: true`），也必须验证当前代码的行为在旧版本和新版本中是否一致，避免依赖隐式假设

## 依赖与外部服务

- **主版本升级深度审查**：对照Changelog破坏性列表逐项确认实际调用点
- **跨版本升级的"中间态"检查**：当依赖从旧版本直接跳升至新版本时，不能只看两端差异，必须回溯并验证中间所有版本的破坏性变更（如 Node 版本要求、参数行为变化）
- **依赖升级审查清单化**：针对 Major/Minor 版本升级，应建立标准化的"Breaking Changes 核对清单"，覆盖运行时环境、API 兼容性和上下游消费端
- **依赖升级的"行为严格化"风险评估**：当依赖升级将默认行为从"宽松（warn/ignore）"变为"严格（error/fail）"时（如 hash 校验、安全检查），必须在审查结论中显式评估对 CI 稳定性的潜在冲击
- **依赖升级的Breaking‑Changes检查清单**：Major/Minor升级需对照上游Breaking Changes逐项核对API参数/返回值、默认行为是否改变及兼容层实现
- **外部CLI依赖版本特性清单**：使用Docker/Compose等工具的特定参数时，必须显式标注要求的最低版本号并在初始化阶段检查
- **外部依赖声明检查**：新增外部服务须声明用途、必要性、回退方案及部署环境要求
- **运行时依赖声明**：新增HTTP健康端点等调用须明确降级方案、网络策略及环境要求
- **镜像标签与参数版本的强绑定**：使用特定版本支持的参数时，必须检查镜像标签是否显式固定（如 `mysql:8.4` 而非 `mysql:latest`）
- **外部依赖版本解耦的"前缀安全"校验**：当测试代码试图解除对第三方依赖的精确版本锁定时，禁止使用过于宽泛的匹配（如仅 `@` 或 `:`），必须强制要求包含版本类型标识的前缀（如 `@v` 或 `:v`）。防止非生产环境引用（如 `@main`, `@dev`）被意外放行

## CI与工作流

- **可重用工作流权限验证**：调用方权限须是被调用方所有job权限的并集，GitHub Actions `permissions` 是覆盖操作
- **自动化分支白名单化**：在分支保护规则或校验逻辑中，必须显式添加 `dependabot/**`、`renovate/**` 等自动化工具分支为例外允许的前缀，或增加豁免逻辑，避免阻塞安全更新
- **无检出作业上下文完整性**：未配置checkout的作业须检查是否拥有执行所需的环境变量和上下文
- **Smoke测试有效性**：新增CI步骤须验证测试脚本内部逻辑完备性，而非仅检查步骤存在性
- **CI结果的严重性分级**：CI检查失败应默认标记为 `error` 或 `minor`，禁止降级为 `suggestion`，除非有明确豁免理由
- **CI结果强制阻断**：包含依赖升级的PR必须跑依赖兼容性测试，任何红灯直接标记为 error

## 核心模块

- **重大版本升级清单**：接口兼容性、导入链验证、配置向后兼容性
- **核心模块影响半径**：列举所有直接导入者评估影响
- **遗留路径的强制测试覆盖**：当重构涉及包含 `nullable` 字段或历史遗留兼容逻辑（如 `pr_number=None`）的代码块时，必须强制检查是否存在对应的测试用例
- **`nullable` 字段的回退分支强制覆盖**：针对数据库中可空字段的业务逻辑，必须强制要求包含"字段为 None 时"的测试用例，以验证回退逻辑是否正确
- **测试代码隔离检查**：生产代码路径中严禁出现测试框架特定符号（如 `@pytest`、`unittest.mock`、特定 `assert` 用法）。建议引入 Lint 规则自动检测
- **重构中的 SQL 语义验证**：在进行涉及查询条件合并的重构时，审查清单应增加"SQL 逻辑等价性检查"一项，特别关注 `AND/OR` 优先级及空条件集的处理
- **动态查询条件构建规范**：针对 ORM 查询，当出现 if/else 分支导致查询语句大面积重复（差异仅在于 1-2 个 where 条件）时，应强制建议采用"条件列表累加"模式
- **增量中的"替换即变更"验证**：任何被替换的代码块（尤其是涉及条件判断的语句）必须进行逻辑等价性校验，防止新代码误删关键判断分支
- **正则严格性评估**：解析安全关键信息的正则须评估过严或过松的风险
- **多级回退链路测试**：每级失败场景须有测试覆盖，确保最终版本有效或明确报错
- **进程管理复杂性**：单纯的PID文件管理不足，应验证 `/proc/<pid>/stat` 和 `cmdline` 双重校验作为安全基线
- **循环约束的等价替换验证**：移除显式循环计数器时，必须强制验证是否存在等效退出条件（`asyncio.wait_for`、`deadline`、信号量）
- **"无界循环"显式声明规则**：移除 `max_iterations` 或 `timeout` 导致 `while True` 的变更，必须强制在文档/注释中显式声明"无自动终止机制"，并推荐配套进程级恢复方案
- **LLM应用的无限循环风险**：LLM Agent 中的 `while True` 配合模型自决退出极度危险，必须在代码层面强制保留物理硬约束
- **配置项活跃性强制验证**：新增或保留配置项必须提供非配置代码中的读取路径（"消费点"）。仅用于文档或预留的配置必须有明确 `TODO` 或废弃标记
- **死配置清理验证标准**：删除配置键的PR必须包含全仓库引用搜索证据，特别检查动态字典和翻译文件，防止运行时 `KeyError`
- **重构陷阱**：警惕打着"简化/重构"旗号移除关键安全检查的变更
- **动态模型信息的统一获取**：将模型名称解析抽象为公共函数或类属性，所有能力判断统一调用，避免硬编码空字符串
- **能力判断的防御式写法**：调用前先检查模型名是否为空，若空则用默认模型或抛出明确异常
- **元数据同步是隐蔽风险点**：跨层状态如模型名、能力集合在多路径代码中必须保持一致
- **测试是防回归的唯一保险**：高测试覆盖率（含空字符串、覆盖能力、压缩回退）是功能修复的保障
- **回退逻辑必须显式标记**：在注释或文档中标注 "TODO: 未来删除"，防止长期遗留
- **配置变更审查**：新增或修改配置项必须在文档说明默认值与作用，并提供类型/范围校验
- **回归行为验证**：涉及功能开关的改动需提供开关开启/关闭的两套测试
- **异常捕获粒度**：禁止使用裸 `except Exception`，必须捕获具体异常并标注处理意图
- **能力声明一致性检查**：新增模型需在声明中声明能力集，CI加入自动校验
- **元数据传递完整性**：跨模块调用返回对象必须显式包含能力集合，缺失视为 error
- **回退路径覆盖**：增量审查强制检查回退代码路径是否仍被单元测试覆盖
- **压缩器状态同步约定**：涉及压缩器的文件必须在模型名称变更后调用 `compressor.set_model(name)`
- **单元测试命名规范**：针对能力驱动的功能，测试文件统一以 `test_<module>_capabilities_*.py` 命名

## 前端与交互

- **前端错误码映射清单**：涉及状态判断的后端错误码必须在前端维护类型定义或注释映射
- **Mock与实现API对齐检查**：测试中的mock必须与生产代码API一一对应（如`os.chown` vs `os.fchown`），防止非root环境下隐藏权限错误
- **浏览器存储恢复竞态评估**：使用 `sessionStorage`/`localStorage` 状态恢复时，须评估多标签页/多窗口竞态（重复轮询、状态变更、焦点争夺）
- **轮询机制审查清单**：涉及轮询的变更须验证：间隔值、指数退避、最大重试/超时、去重作用域（单标签页 vs 跨标签页）、服务端限流
- **内联JS测试覆盖率加权**：模板内联JS测试提取成本高，审查应适当提高对测试覆盖率的期望或明确标注覆盖缺口
- **隐式状态转换验证**：异步错误处理不能只看 `catch` 块直接代码，须追踪副作用（状态重置、函数回调）最终影响
- **Jinja内联JS审查策略**：不能仅做 `node --check` 语法验证，须关注模板表达式替换后的运行时类型问题
- **数据模型迁移的过渡期兼容性**：修改持久化数据结构时，必须强制审查"旧数据读取路径"的兼容性逻辑，显式处理字段缺失时的回退策略

## 文档审查

- **文档-代码双向验证**：修正文档时须反向抽查同文档中其他相关命令/配置描述是否过时
- **强化"非功能范围变更"审查规范**：删除或实质性修改文档/配置文件，必须在 PR 描述或提交信息中显式声明理由及迁移映射，否则视为阻断项。防止开发者以"清理"为名删除关键规则
- **文档即代码的验证深度**：当文档更新提及行为描述时，必须验证代码中是否有对应的实参支撑，避免文档承诺代码未提供的能力
- **操作指南验证**：命令参数定义、前提条件说明、命令顺序依赖须全部验证
- **用户视角测试**：评估术语一致性、步骤清晰度、错误处理指导，模拟目标用户阅读体验
- **隐含假设检查**：是否假设特定OS、目录结构等环境
- **文档变更配套测试**：关键文档变更应配套自动化文档测试，将文档视为可测试制品
- **文档算术验证**：文档涉及资源计算（如"剩余9个连接"）时，必须提供计算公式及依据（总限制 - 应用占用 - 系统预留 = 余量）
- **数值计算的源码溯源**：禁止直接采信PR描述或注释中的计算结果，必须强制在代码库中定位实际定义处进行现场反推计算
- **警惕PR中的"算术题"**：PR描述包含的任何计算逻辑都是高风险区，必须通过代码或配置独立验证
- **领域术语定义一致性**：确保文档中对"上限"、"溢出"等词汇的解释与所用框架（如SQLAlchemy）的官方定义一致

## 安全与错误处理

- **安全脱敏粒度分级**：区分"内部实现细节"（堆栈/路径/SQL）与"用户输入验证信息"，后者可安全返回。每个 `except` 块对外响应须注释标注错误类别（`# USER_INPUT_ERROR` / `# INTERNAL_ERROR`）
- **细化"错误文案透传"规范**：明确区分 `ValueError` 中哪些属于 `USER_INPUT_ERROR`（如未触发审查、权限不足，应透传）和 `INTERNAL_ERROR`（如 DB 连接失败，应脱敏），并在 Webhook 层建立对应的处理分支
- **敏感数据入口规范化原则**：API Key、Token等外部输入的敏感凭证，必须在第一次进入系统的边界进行规范化（strip/trim）和校验，禁止在业务逻辑层临时清洗
- **错误处理策略一致性**：同一PR引入多种错误处理模式须说明理由或统一
- **错误分类完备性**：新增错误码须检查翻译文件覆盖、边界防御测试、传播链各环节非法输入处理
- **跨层错误码传播强制检查**：在IPC层或底层Service层引入新错误码时，必须强制检查Backend路由映射层和Frontend的errorLabels/翻译文件是否同步加入
- **运行时环境隔离**：进程生成/环境变量注入须验证子进程隔离可靠性及父进程退出的影响
- **错误响应函数不可黑盒信任**：须验证其实现细节（HTTP状态码、响应结构等）
- **宽泛异常捕获的精细化陷阱**：`except Exception` 后想区分 `ValueError` 和 `RuntimeError` 需额外判断，易出错。长远应在入口层做参数校验
- **跨库迁移的API假象**：标准库向第三方库迁移时，须核查"参数静默失效"风险，如 loguru 的 `exc_info=True`
- **配置变更的文档同步**：新增开关需在项目文档同步更新，避免运维不知情
- **动态模型名称获取的可靠性**：`metadata.model` 缺失或命名变化会导致功能失效，需加入结构化校验并在缺失时回退
- **安全增强类Issue归类**：以修复安全隐患为核心的 enhancement，优先级评估与标签应更突出安全属性
- **安全增强标签建议**：对 sandbox 或 isolation 类架构改进，建议补充 sandbox 或 isolation 标签

## 增量审查

- **关联性验证**：即使只看增量提交，也须主动验证与整体变更意图一致
- **全局风险关联**：未解决的阻断性问题是当前PR的阻断项，结论须声明未覆盖历史问题
- **历史遗留项显式结案**：增量审查必须包含"历史遗留项状态追踪"，对上一轮 Request Changes 逐一标记为 `[已修复]` / `[未修复]` / `[已过时]`
- **邻域代码"触类旁通"检查**：修改函数内逻辑时，必须检查同一作用域下其他资源对象（HTTP Client、DB连接、文件句柄）的生命周期管理是否正确
- **PR自证逻辑全局应用**：当 PR 提供修改依据（如测试用例证明某 API 无效），必须将该依据作为全局搜索条件验证残留点
- **异步资源生命周期强制检查**：对于 Python 的 `async with ... as client` 模式，必须审查所有 `client` 调用点是否严格位于缩进块内部
- **全链路影响分析**：修改核心数据结构处理逻辑时，必须检索所有读取该字段的代码路径并确认是否同步修改
- **Dev模式对等性验证**：涉及进程生命周期管理的函数，必须审查Dev模式与生产模式的逻辑等价性
- **路径锚定的上下文无关性测试**：对于可被多入口调用的脚本，必须包含"非项目根目录调用"的测试用例
- **"Fail-Closed" 边界判断**：宁可误报（体验受损）不可漏报（安全风险），区分误报与漏报的原则性权衡
- **触发全量验证的条件**：涉及"核心控制流变更"或"配置项删除"的PR，即使增量审查也应触发全量验证模式（如全库搜索配置引用）
- **增量审查强制全库引用搜索**：对于配置键删除、API接口变更、异常类新增等，必须执行全仓库搜索确保无遗漏引用或KeyError

## Shell脚本与守护进程交互

- **Shell脚本"Client化"趋势**：脚本通过REST API与后台守护进程通信，处理JSON响应，审查需关注跨组件逻辑验证
- **API调用中的隐式默认值审查**：禁止假设服务端默认行为（如空body `{}` 被解释为"使用默认值"而非"智能推断"），必须查阅服务端代码确认默认值
- **空Body的陷阱**：`curl --data '{}'` 往往被服务端解释为"使用默认值"，而非"无操作"或"保持当前状态"
- **多路径失败语义一致性**：存在主路径和回退路径的关键操作，必须审查两条路径在无需更新、网络不可达、权限不足等场景下表现是否一致
- **守护进程交互的幂等性**：涉及Daemon/IPC调用的脚本变更，必须验证重复调用是否会导致服务端状态紊乱或竞态条件
- **跨组件逻辑验证的必要性**：仅修改客户端但依赖服务端特定行为的PR，必须跳转到服务端代码验证处理逻辑，防止"客户端以为发送了A，服务端理解成了B"
- **UX细节决定成败**：错误信息必须对操作者具有可读性和指导性，区分"失败"和"无需操作"是用户体验的关键
