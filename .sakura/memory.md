## 核心审查原则

- **PR 描述与 diff 一致性强制校验**：审查前必须核对 PR 描述、提交信息、文件清单和实际 diff；描述提到但 diff 未体现至少标 minor；安全/数据库/依赖变更标 major。
- **PR 描述列表是"风险信号"而非"完成清单"**：作者列出的修改点通常就是实际修改的点，对比列表与全仓调用点可发现遗漏；数量不匹配时必须标 major。
- **PR 内提交主题一致性检查**：新增提交主题与 PR 描述/历史提交属于不同子系统时，必须标注偏离，建议拆分或补充描述。
- **审查决策与严重程度一致性**：`request_changes` 必须对应明确、可执行的 blocking/major 问题。
- **历史问题状态需证据**：不能把未重新验证的历史问题写成"已修复"；标记修复必须给出代码位置或扫描依据。
- **结构化评论质量**：只有具体、可定位、可操作的问题才能生成 review comment。
- **配置生命周期管理**：新增/废弃配置需检查前后端、文档、配置中心默认值一致；数值配置需 min/max。
- **公共/基类变更调用方扫描**：修改基类核心循环、公共方法时，必须列出调用方并检查适配情况。

## 增量审查专项规范

- **增量审查完整性验证**：区分"当前增量通过"与"整个PR可合并"；历史阻断问题逐项列明。
- **增量审查决策完整性声明**：approve 时若存在历史 major 问题且本轮未覆盖，必须明确说明。
- **增量审查的"双重视角"**：微观（增量代码质量）+宏观（增量在整个 PR 和历史上下文中的位置）。
- **增量审查的"完整性幻觉"风险**：对"清理/统一"类 PR，即使只看增量也应检查"同类问题是否还有残留"，鼓励建议作者提供全仓搜索证据。

## 重构类变更审查要点

- **重构完整性全仓扫描验证**：全局性、模式化替换的 PR，需提供或自行执行全仓静态搜索证据，证明旧模式已完全清除。
- **重构类PR的完成度声明**：架构迁移或模式统一的 PR，应要求说明"完成了目标的哪一部分"以及"已知的遗留技术债"。
- **行为契约变更声明**：重构以"统一行为"为目标时，必须清晰列出新旧行为差异。
- **返回值枚举扩展全调用点扫描**：修改函数返回值集合（新增枚举值、异常类型、错误码）时，必须列出所有调用点并逐个确认适配；仅检查 PR 描述中提到的点不够，必须通过 Grep 独立验证。
- **辅助函数迁移完整性校验**：新增辅助/公共函数以统一处理逻辑时，必须列出所有应使用的调用点，逐项说明已迁移或未迁移原因；未完成迁移的至少标 minor。
- **语义迁移 PR 的"零遗漏"标准**：将 A 统一迁移为 B 时，任何残留的 A 都是 blocking 级别问题。

## 代码质量与安全审查

- **安全修复必须"向前一步"**：即使变更很小，也应检查同类路径是否存在相同模式，建议全仓扫描并记录为技术债。
- **第三方 API 字面量匹配是高危反模式**：`== "deleted"` 类 Bug 源于凭记忆写状态值，必须核对官方文档，常量定义处应注释完整枚举。
- **"恒定回退值"是强制阻断信号**：可选参数回退值在所有正常路径下恒为同一值时，必须追问原因及是否有调用方依赖旧签名，标 major。
- **字符串匹配关联删除是高危反模式**：用标题相等性关联删除在标题变化时静默失效，应使用显式 ID 绑定。
- **解耦操作必须验证下游适配**：移除两个数据结构间隐式耦合时，必须列出 B 的所有消费方确认不会出错。
- **配置解析函数参数来源校验**：动态获取字段名用于 `getattr` 时必须白名单校验。
- **明文敏感字段存储禁止**：DB 列存储 api_key/secret/token 必须加密，标阻断。

## 测试与验证规范

- **测试"覆盖了函数"≠"覆盖了行为"**：审查时应先问"参数/数据能触发哪条代码路径"。
- **测试与代码的同源偏差**：同一作者编写的测试和代码共享认知盲点，不能因"测试覆盖全面"就放松代码路径独立验证。
- **测试覆盖与 PR 描述的镜像偏差**：新增测试数量与 PR 描述修改点精确一致时，应警惕测试仅覆盖了作者"想到的"路径。
- **去重/聚合逻辑边界测试强制**：使用 Counter/groupby 等去重时必须补充极端边界测试。
- **Fake/mock 需贴近生产语义**：必须模拟生产过滤/排序/limit/异常/返回结构。
- **集成测试参数必须触发关键分支**：涉及阈值/裁剪的逻辑，测试数据量必须 > 阈值或显式设置小阈值。

## 架构与模式审查

- **核心逻辑变更的调用方扫描强化**：修改核心决策或公共数据结构时，必须列出并分析调用方适配情况。
- **事件驱动闭环审查**：webhook+worker+DB 类变更重点查状态、重复/乱序事件、并发更新、唯一约束冲突。
- **配置比较规则显式化**：元组比较判断配置变更时应注释字段顺序和目的，或重构为字典比较。

## 经验教训与最佳实践

- **小控制流变更也是契约变更**：`break`→`return` 等变化可能跳过日志、清理、状态落库或恢复逻辑。
- **统一模式≠统一行为**：迁移到公共依赖后，要检查外部状态码、响应体、前端调用和历史契约是否改变。
- **"正确的语义"≠"安全的变更"**：修正历史错误行为时，要关注是否有代码依赖那个"错误行为"。
- **小变更的"为什么"比"是什么"更重要**：增量极小的变更应将精力放在设计决策合理性论证上。
- **"惰性重建安全"不能跳过异常审查**：已验证安全的内部方法被新调用点引入时，仍需重新评估调用上下文的错误处理。
- **局部配置刷新完整性追问**：添加刷新时必须列出同一流程中所有使用该配置的执行点，说明为何其他点不需要刷新。
- **技术债"可接受"须有行动建议**：结论为"当前可接受"的 suggestion 必须给出后续行动，禁止以"可接受"为终结。
- **过滤/丢弃操作日志规范**：除记录过滤数量外，必须在 debug 级别输出被过滤元素的标识信息。
- **增量审查需"向后看"和"向前想"**：验证增量是否修了旧问题，评估修复是否彻底，预测新变更是否引入语义风险。
