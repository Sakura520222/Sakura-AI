## 常见代码问题和审查要点

- **PR 描述与 diff 一致性强制校验**：审查前必须核对 PR 描述、提交信息、文件清单和实际 diff；描述提到但 diff 未体现至少标 minor；安全/数据库/依赖变更标 major。
- **审查决策与严重程度一致性**：`request_changes` 必须对应明确、可执行的 blocking/major 问题；"无重要问题/仅建议"不得 request_changes。
- **历史问题状态需证据**：增量审查中不能把未重新验证的历史问题写成"已修复"；标记修复必须给出代码位置或扫描依据。
- **结构化评论质量**：只有具体、可定位、可操作的问题才能生成 review comment；报告摘要、评分、表格片段不得转成评论。
- **公共/基类控制流变更调用方扫描**：修改基类核心循环、公共方法时，必须列出调用方并检查返回值、异常传播、日志、副作用。
- **配置生命周期管理**：新增/废弃配置需检查前后端、文档、配置中心默认值一致；数值配置需 min/max；读取点需 None/非法值降级。
- **DB schema 变更全链路审查**：新增列/索引/唯一约束必须检查迁移文件、nullable/default、历史数据回填、约束冲突、跨库兼容。
- **i18n 与 UI 完整性**：新增 UI 元素必须同步翻译文件；缺失标 major。
- **明文敏感字段存储禁止**：新增 DB 列存储 api_key/secret/token 必须加密，标阻断。
- **延迟导入注释**：函数体内 import 必须说明循环依赖原因，格式如 `# 延迟导入：避免 A → B 循环依赖`。
- **loguru 日志格式**：使用 `logger.info("xxx {}", value)`，避免 f-string；但 `{}` 内不要放条件表达式。
- **第三方异常继承需验证**：涉及 redis/aiohttp/SQLAlchemy 等异常分类时，必须查源码或 MRO，禁止仅凭异常名推断。
- **测试断言规范**：关键业务和兼容性断言必须有失败消息；直接导入第三方测试依赖需在依赖文件显式声明。
- **Webhook 处理器行为一致性**：处理同一事件类型的多个 webhook handler，其前置检查、核心逻辑、日志输出和错误处理模式应保持一致。
- **幂等性审查要点**：审查幂等性改进时，要同步检查所有调用方是否适配了新的返回值语义。
- **相似代码块对比审查**：当变更涉及多个结构相似的模块时，应系统性对比它们在相同上下文下的实现。
- **封装函数迁移验证**：当把内联逻辑迁移到现有封装函数时，应明确检查并记录调用方是否需要适配返回值语义的变化。
- **测试清理验证**：删除测试用例前，必须明确指出其功能已被哪些现有测试所覆盖，并简要说明覆盖的等价性。
- **提交清单核对规则**：增量审查时，必须核对PR描述中的提交数量、提交信息与最终diff的变更文件数量、内容是否一致。
- **共享逻辑测试覆盖专项检查**：当发现多个模块使用同一函数/模式时，应检查测试是否至少覆盖一个完整路径。
- **条件分支事务行为测试规范**：涉及commit/rollback条件调用的代码，测试应同时断言正向和反向行为。
- **PR原子性与描述一致性**：审查时需检查提交集合是否内聚。混杂的PR应标记为minor或suggestion，建议作者拆分。
- **机械性替换完整性验证**：当PR目标是进行全局性、模式化的代码替换时，应要求作者提供全量扫描结果。
- **重构类变更的完成度检查**：对于旨在统一风格或模式的变更，应评估其完成度。部分完成的重构应被视为技术债。

## 架构与模式审查要点

- **长连接监听循环异常分层**：SSE/WebSocket/Redis PubSub 中，禁止 `except ...: continue` 无日志、无退避、无退出条件。内层只处理可恢复的 idle timeout；连接断开应传播到外层退避重连。
- **异步路由同步 I/O**：异步路由中的同步 I/O 必须 `asyncio.to_thread()` 包装，标 major。
- **FastAPI 参数校验先于业务逻辑**：认证/CSRF/权限字段若期望 401/403，不应依赖必填 `Form(...)`/`Header(...)` 触发 422。
- **WebUI/Dashboard API 认证链路**：新增 API 时，必须检查函数级、router 级、include_router 级、中间件级认证。
- **CSRF 依赖模式区分**：表单路由用 `require_csrf`，Header/JSON 路由用 `require_csrf_header`。
- **Shell 安全校验必须覆盖隐式执行**：除 `;`、`&&`、`||`、`|`、`&`、反引号外，必须检查 `$()`、process substitution、重定向组合。
- **日志中的用户输入脱敏**：Shell 命令、URL、header、环境变量等入日志前默认限长并脱敏 token/password/key/secret。
- **Agent 会话起始消息规范**：所有 agent conversation 优先使用 `[system, user]` 起始模式。
- **框架 API 迁移依赖约束**：适配新 API 时，必须检查 requirements/pyproject、最低/最高版本、传递依赖兼容矩阵。
- **模板渲染封装一致性**：WebUI 路由优先使用统一 `render_template()`/`error_page()`。
- **时间语义审查**：duration/latency/elapsed/timeout 必须用 `time.monotonic()`/`perf_counter()`；真实事件时间用 timezone-aware datetime。
- **状态机变更审查**：涉及 worker/task/status/webhook 的 PR，应要求审查新增状态、允许的前置/后置状态、重复/乱序事件行为。
- **Webhook 事件幂等检查**：webhook 处理变更必须检查签名验证覆盖新增分支、重复投递幂等、延迟事件防护。
- **并发安全审查**：审查涉及状态机转换、共享内存缓存或"读取-检查-执行"操作的变更时，必须进行并发场景分析。
- **权限过滤中禁止 truthiness 判断**：对 user/tenant/org/repo 等 scope 字段，必须用 `if scope is not None` 而非 `if scope`。
- **Worker 资源清理**：_cancel_events、_background_tasks、pending prompts 等资源必须在终态、异常、提前 return 时清理。
- **Fake/mock 与生产查询一致性**：fake session 的过滤、排序、limit、异常行为必须模拟生产查询；复杂查询宜补 sqlite/集成测试。
- **事件驱动闭环审查**：webhook+worker+DB/Agent Team 类变更重点查状态进入/退出、重复/乱序/延迟事件、并发更新、唯一约束冲突。

## 支付与资源安全

- **支付事务边界**：任何支付状态变更必须评估与服务发放、配额消耗等关联操作的事务原子性或补偿机制。
- **外部回调安全降级**：验签失败或配置缺失必须返回明确 401/403，禁止静默放行。
- **GET 请求禁止写操作**：RESTful GET 路由不得修改数据库状态。
- **支付网关启用开关**：所有支付网关公共函数入口必须检查对应网关启用状态。
- **Webhook 幂等性与时区**：验证重复事件处理；API 时间戳参数需显式时区。
- **金额解析语义**：金额解析函数应返回 `Optional[int]`，`None` 表示失败，避免 0 歧义。

## 审查流程与质量控制

- **审查先验步骤**：先读 PR 描述与文件清单，再核对 diff；标出"描述提到但未体现"和"代码改了但描述未提到"。
- **增量审查范围声明**：明确本轮只验证增量还是全量；历史上下文不能替代当前 diff 校验。
- **评分反映 PR 整体目标**：不能只因局部代码正确给高分；若依赖约束、描述、测试或验收目标未完成，应降分并明确风险。
- **严重程度唯一**：同一问题不得同时标 minor/major；存在未修复 major 且仍 approve 必须解释非阻断原因。
- **测试覆盖审查**：安全解析辅助函数、金额/URL 校验、异常分类、框架兼容性、公共依赖行为需直接单测或 HTTP/集成测试。
- **观测/展示类测试**：health/status/dashboard metrics、启动耗时、格式化函数等低风险功能也需轻量测试字段存在、类型、缺状态降级。
- **机械性替换审查**：全仓搜索旧调用点只是第一步，还需确认新参数在每个上下文可用、类型正确、运行时路径和 mock 签名同步。
- **小 PR 不放松元量检查**：即使只是 lint/loguru 清理，也要核对 PR 描述、关联 Issue、历史问题状态和最终决策是否一致。
- **增量审查完整性验证**：增量审查必须区分"当前增量提交通过"与"整个 PR 可合并"；历史阻断问题状态必须逐项列明。
- **Release PR 描述与 diff 强制核对**：Release/changelog 型 PR 中，若描述列出功能集合但当前增量 diff 未体现，应至少标记为 suggestion/minor。
- **历史问题修复验证责任**：标记历史问题"已修复"时，必须基于当前 diff 的具体代码位置确认；未验证的只能说"本轮未覆盖"。
- **结构化评论质量收紧**：只有具体、可定位、可执行的问题才能生成 review comment；审查摘要、评分、历史状态表不得进入 comment 列表。
- **严重程度与决策一致性**：存在未修复 major 且仍 approve 必须解释非阻断原因；日志可观测性、测试 fake 不一致等一般不应轻易标 major。
- **增量审查决策的完整性声明**：当给出approve决策时，若存在历史major问题且本轮未覆盖，必须在审查报告中明确说明。
- **同步I/O修复的审查清单**：修复同步I/O阻塞问题时，审查者应：1) 确认所有同类问题调用点是否一并修复；2) 检查包装后的函数签名、异常传播、返回值是否与调用方预期一致。
- **增量审查中历史问题修复验证的分级要求**：核心问题必须在当前diff中重新验证修复证据；一般问题可接受"未引入回退"+"修复迹象"，但需声明验证范围。
- **loguru采用渐进式策略**：建议明确"所有新增日志必须使用{}占位符，现有f-string日志在修改时应顺手转换"的渐进式采用策略。

## 经验教训与最佳实践

- **小控制流变更也是契约变更**：`break`→`return`、`continue`、异常捕获范围变化都可能跳过日志、清理、指标、状态落库或外层恢复逻辑。
- **日志是可观测性契约**：误报最大迭代、静默吞异常、完整敏感命令日志都会影响排障和安全；日志变更按功能/安全变更审查。
- **异常处理不是捕获越多越好**：关键是捕获更准；网络 timeout、连接重置、Broken pipe、认证/协议错误应分类处理。
- **统一模式不等于统一行为**：迁移到公共依赖或封装后，要检查外部状态码、响应体、前端调用和历史契约是否改变。
- **结构测试不能替代行为测试**：检查路由挂了依赖有价值，但安全修复必须验证真实请求响应。
- **Fake/mock 需贴近生产语义**：SQLAlchemy fake session、API fake、LLM fake 必须模拟生产过滤/排序/limit/异常/返回结构。
- **绝对化表述要谨慎**：避免"完美解决/无遗留风险"；更稳妥写"已解决当前已知关键问题，未发现新的阻断风险"。
- **事件驱动闭环先画状态/时序表**：webhook+worker+DB/Agent Team 类变更重点查状态进入/退出、重复/乱序/延迟事件、并发更新、唯一约束冲突捕获。
- **增量审查边界明确**：增量审查天然容易只确认当前提交修复了一个点，却忽略整个 PR 是否仍有未解决阻断问题；应在报告中固定声明历史阻断问题复核状态。
- **测试"能通过"与"有意义地验证了新行为"是两个层次**：函数签名或行为契约变更时，要主动审查相关测试的 mock/fake 配置是否准确反映生产环境预期行为。
- **相似代码块的"找不同"**：当变更涉及多个结构相似的模块时，审查应像"找不同"一样系统性对比，任何不一致都可能是缺陷或技术债。
- **修复的"涟漪效应"**：修改公共函数签名必须像审查其初始实现一样，系统性扫描所有调用方，确保新参数在每个上下文可用。
- **"用户可见"与"系统内部"的错误处理分层**：面向用户的接口错误处理应以用户体验和恢复为先；内部服务可更倾向暴露错误以便快速发现。
- **Review 报告需要二次清洗**：自动生成的审查报告中混入摘要、checklist、结论时，会降低 review comment 信噪比；只有带文件路径、行号、问题、影响、建议的内容才进入评论列表。
- **测试的"有效性"维度**：对于引入缓存或状态机的代码，测试的有效性不仅在于"功能正确"，还在于验证缓存失效/命中、状态转换、资源清理等预期行为是否被正确断言。
- **异步/同步边界警觉**：审查任何异步IO密集型服务时，应优先扫描其内部是否调用了可能阻塞事件循环的同步IO或CPU密集操作。
- **架构债务的早期识别**：对"两个类有几乎相同逻辑"的识别是高质量的审查产出。这不仅是代码重复，更是未来变更不同步的风险源头。
- **增量审查的"完整性幻觉"风险**：增量审查天然聚焦于当前提交，但必须清晰声明"未覆盖"的范围，以管理评审者和读者的预期。
- **小重构也要验证语义一致性**：即使是简单的函数调用替换，也必须深入理解新旧代码在参数、返回值、异常处理和副作用上的细微差别。
- **错误处理的"可观测性"维度**：except块不是垃圾箱。恢复错误处理不等于吞没错误。审查时不仅要检查错误是否被捕获，还要检查错误信息流向了哪里。
- **增量审查需"向后看"和"向前想"**：不仅要验证增量是否修了旧问题，更要评估修复是否彻底（是否覆盖了所有同类问题），并预测新变更是否引入了语义风险。
- **测试"等价性"判断需谨慎**：判断旧测试是否被新测试完全覆盖，不能仅看测试数量或名称，需深入对比测试场景、mock点和断言。
- **技术债的显性化**：当发现技术债时，审查意见不仅是"建议修复"，更可以量化技术债并建议创建后续Issue进行跟踪，使其成为可管理的项目任务。
