## 架构与模式审查要点

- **JSON解析场景需特别关注**：转义顺序、边界条件，建议引入单元测试
- **函数提取重构后必须检查**：是否所有调用点均使用新函数
- **全量重审价值**：功能重构后强制执行全量审查，识别系统性问题
- **配置体系扩展应优先复用动态配置体系**：避免硬编码，标major
- **延迟导入的并发安全性**：项目使用异步路由，需评估延迟导入在多线程/协程下的竞态条件
- **支付网关实例缓存规范**：高频调用场景（如Webhook）必须评估网关实例缓存，避免对象创建开销
- **全量扫描优先**：对于异步路由文件，审查前先执行全文件同步调用扫描，再聚焦具体变更点
- **模式对比**：新增功能时，主动对比现有相似功能的完整实现，避免模式遗漏（如功能开关）
- **竞态条件评估**：在异步环境中，延迟导入需额外评估并发安全性，避免隐式竞态

## 审查流程与质量控制

- **Issue 分类准确性检查**：对 `question` 类 Issue，优先检查代码/文档是否已覆盖，避免过度标记为缺陷
- **PR 描述与变更一致性验证**：强制要求 PR 描述与实际变更文件列表一致，审查前首先验证文件清单
- **增量审查必须检查关联文件**：强制检查相关翻译文件、路由配置和i18n键完整性
- **增量审查强制关联文件检查**：对于支付类变更，增量审查必须检查 webhook 路由、管理后台等直接调用网关的路径，避免功能碎片化
- **全量审查触发条件**：功能重构或新增模块后强制执行全量审查
- **历史问题修复验证**：必须结合测试用例验证功能完整性
- **大型PR强制拆分审查**：大型PR必须强制拆分审查，避免单次审查覆盖度不足
- **增量审查全文件扫描**：对"异步路由同步调用"类问题执行全文件扫描，确保一致性
- **动态配置测试覆盖验证**：新增配置读取逻辑必须补充单元测试（mock `get_dynamic_config`）
- **"quick"策略强制关联文件检查**：即使增量审查采用"quick"策略，也需强制扫描关联文件，避免功能碎片化
- **支付类审查优先检查安全配置**：支付类Issue必须在设计阶段引入安全审查，避免XSS和敏感数据泄露
- **PR描述与实际变更偏差警惕**：需警惕PR描述与实际变更的偏差，审查前验证文件清单
