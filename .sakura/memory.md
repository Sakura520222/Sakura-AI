# 项目记忆

累计反思 10 次

## 核心审查原则

- **PR 描述与 diff 一致性**：提到但 diff 未体现标 minor；安全/DB/依赖标 major。**可枚举功能点须逐项勾选，未勾项直接标 minor。**
- **PR 描述数字交叉验证**：文件数/行数与实际 diff --stat 差异超 10% 须标 minor。
- **审查决策与严重程度一致**；**审查输出自身合规性自检**（最高优先级）。
- **决策完整性声明**：approve 时未解决 ≥minor 须逐项声明，quick 下同样强制。
- **quick 策略评分上限 8/10**；**强制清单尾件**：打勾 `[ ]决策完整性 [ ]quick上限 [ ]负面检查`，未全勾不允许输出。
- **历史 major 阻断评分上限 ≤8**。
- **小变更批量审查**：≥3 个 ≤10 行文件须逐文件说明。
- **提示词/配置文本变更下游对齐**：修改面向用户错误提示须 grep i18n 键值检查所有语言文件。

## 增量审查专项

- **抬头**：先读 PR 描述+历史问题清单逐项勾选。**收尾**：approve 前输出全局健康状态。
- **增量评分双轨制**：区分"增量质量分"与"PR 整体可合并评估"。
- **PR 描述范围边界**：非本次增量描述项须显式标注。
- **前序问题连续追踪升级**：同一 minor 连续 ≥2 轮未修复，第 3 轮须升级。
- **前序问题关闭溯源**：标记"已修复"须：当前 diff 含相关变更，或显式引用历史增量编号。禁止无依据翻转。
- **suggestion 生命周期追踪**：连续 ≥3 轮未处理须标注"长期搁置"并评估降级关闭。
- **邻接区域连带审查**：±30 行已知问题须 suggestion 提出。
- **隧道视野防范**：正面评价越多越先做负面检查。**代码越好越要警惕流程漏检。**
- **增量上下文碎片化风险**：跨增量一致性验证最易失效，须主动防漏。

## 重构类变更审查

- **重构双轨检查**：须声明(1)测试全通过(2)返回值一致(3)异常等价。**建议物理占位符 `[重构双轨:(1)___(2)___(3)___]`。**
- **重构中功能扩展检测**：PR 标题为"重构/统一"但 diff 含验证放宽/接受范围扩大时，须独立评估。
- **等量替换强制逐点说明**：文件 +N/-N 且 N≤30 须列 before→after 并声明等价。
- **新增未测试方法评分 ≤8**。
- **布尔标志/状态枚举全路径传播**：grep 所有消费方。
- **Check Run / webhook / worker 链路**：清理逻辑必须有唯一匹配条件；只能按可证明的占位对象收敛，禁止用“非当前值”排除式删除活跃任务。并发/重试/乱序下要保留相似对象测试。
- **预创建资源接管协议**：异步接管对象必须有稳定 ID 与清理兜底；关注 queued→in_progress→completed/cancelled 全路径、失败回收、重试孤儿状态。

## 代码质量与安全

- **成本类安全检查**：付费 API 路由须验证权限。
- **安全修复三角验证**：(1)修复前误伤(2)修复后正常(3)修复后异常。
- **LLM prompt 链路**：外部输入须截断和清洗。移除截断须验证下游等效 Token 控制。
- **全表加载检测**：`select(Model)` 无 WHERE 要求数据量评估。
- **`/health` 等可观测性端点视为接口**：字段值变更须验证外部监控消费方兼容性，不仅 grep 代码内硬编码。
- **内部错误信息禁止泄漏至用户界面**。
- **权限检查层级一致性**：≥2 路由调用同一 service 方法时，权限应在 service 层。
- **恒定回退值/静默失败标 major**。

## 架构与模式

- **事件驱动闭环**：多链路先建全景图，逐链路查防重/乱序/并发。
- **状态机逃脱路径**：每个中间状态须有超时/异常逃脱。
- **变量生命周期审计**：循环外初始化变量的所有消费点须整体审查，确认每处值与预期一致。
- **大版本 PR 强制分模块审查**：≥5 文件且 ≥5k 行时逐模块独立审查。
- **AI Provider/配置重构**：分类优先按 enhancement + configuration，必要时补 refactor；要拆解 provider 协议、模型发现、推理参数、Wizard、迁移与默认值，避免把大范围配置演进粗分为 other。

## 经验教训

- **"纯新增"≠"低风险"**；**"交给下游处理"是伪命题**；**"正确修复清单"≠"免检通行证"**。
- **确认偏误链**：高评分极易引发确认偏误。**代码越好越先做负面检查。**
- **"良好重构"是等价性验证的麻醉剂**：越标准的重构越需要强制双轨声明。
- **正面评价密度与负面检查力度须反相关**：高评分场景强制先输出负面检查结果。
- **增量上下文碎片化**：跨增量一致性验证最易退化为"勾选 exercise"。
- **"不在 diff 中"≠"不需要关注"**；**审查输出规则自违反**：元规则比业务规则更难自检测。
- **"解决可观测性"≠"解决根因"**；**重构等价性不可假定**。
- **状态/身份/回收三者必须绑定**：外部 Check Run、worker 接管、删除清理若语义脱节，优先怀疑并发误伤与生命周期悬挂。
