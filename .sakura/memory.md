## 审查流程与质量控制

- **重构PR整体影响评估**：标记为refactor的PR必须跨文件检查重构规则一致性
- **历史遗留问题风险评估**：涉及数据一致性（配额/资金）的问题不能仅标"优化建议"，必须评估现实风险，标major
- **严重程度一致性**：同一问题在报告各处的严重程度标记必须一致
- **PR描述与变更一致性验证**：审查前首先验证文件清单
- **增量审查强制关联文件检查**：支付类变更必须检查webhook路由、管理后台等调用路径
- **大型PR强制拆分审查**：避免单次审查覆盖度不足
- **重构后测试覆盖自查**：重构PR合并后建议对核心函数进行单元测试覆盖度自查
- **PR描述与实际变更偏差警惕**：审查前验证文件清单
- **全量重审价值评估**：全量重审能识别架构级问题和跨文件一致性，增量审查易陷入局部优化
- **配置变更全生命周期审查**：即使"quick"策略也应检查配置的定义→保存→使用→展示
- **规则应用主动性**：主动将记忆库规则转化为具体审查行动，而非被动识别
- **注释与代码一致性检查**：注释更新后需验证其描述是否与当前代码逻辑完全匹配，避免误导
- **路由变更关联扫描**：即使增量审查，也需检查变更文件对其他路由模块的潜在影响，防止碎片化修复
- **版本兼容性测试**：通过单元测试验证依赖版本约束，是一种有效的预防性质量保障手段
- **PR 描述与代码一致性**：PR 描述清晰说明变更目的和测试命令，有助于审查者快速理解上下文

## 经验教训与最佳实践

### 审查策略与深度
- **审查需兼顾"树木"与"森林"**：增量审查易陷入局部，重构PR需评估全局模式一致性
- **重构后的"残留"审查**：大型删除PR审查重点从"新增了什么"转向"删除得是否干净"

### 技术模式审查
- **try/finally资源清理时序**：异常抛出时finally块执行顺序是常见错误源
- **事务原子性**：配额消耗与任务创建应绑定在同一事务或补偿机制中
- **配置硬编码审查**：默认值应在单一位置定义，避免多处硬编码
- **loguru日志占位符**：`{}`内先计算再传入，禁止内含条件表达式，标major
- **防御性编程语义精确性**：`if reflection_count == 0`检查需评估是否真正区分"未传入"和"实际为0"，避免逻辑歧义
- **周期性触发模式**：`since_last >= interval`是项目常见模式，审查时应作为模板对比

### 支付与资源安全
- **支付网关时区明确化**：API时间戳参数需显式指定时区
- **Webhook幂等性验证**：强制验证事件重复处理逻辑
- **支付类异常处理必须覆盖数据库连接异常**，标major
- **关键容错路径监控**：配额、支付等关键业务的补偿/清理操作失败，仅记录日志不足，必须同步触发监控指标或告警

### 配置管理最佳实践
- **配置验证层次性**：前端验证（min）→ 后端验证（类型转换）→ 消费点验证（默认值）需形成完整链条
- **i18n先行实践**：预先添加翻译键是良好实践，避免了合并后的翻译缺失
- **配置中心化建议**：建议将默认值定义在单一配置文件中，前后端引用同一常量
- **配置滥用风险防范**：无上限约束可能允许设置极大值，影响审查性能，需增加合理范围验证

### 增量审查反思
- **增量审查局限性**：仅关注增量变更可能遗漏变更对整体架构的长期影响
- **关联扫描重要性**：对于配置类变更，需检查配置与现有其他策略配置的交互影响
- **历史问题持续跟踪**：即使新PR已approve，仍需记录历史问题待后续解决
- **审查策略平衡**："quick"策略在简单PR中足够，但需警惕增量审查的局限性。对于涉及多文件、配置或架构变更的 PR，应主动执行关联扫描
- **文档漂移风险**：注释更新后代码逻辑变更可能被忽视，建议结合代码搜索工具验证注释引用的逻辑是否仍存在
- **路径匹配边界验证**：验证 `startswith` 等匹配方式是否覆盖所有边界（如 trailing slash、大小写）
- **配置硬编码推动集中化**：对路径排除等易变逻辑，推动集中配置化以降低维护成本

### 新增经验教训总结

#### 测试与质量保障
- **测试断言完整性**：新增测试必须验证所有关键字段，断言应提供失败描述消息
- **版本兼容性测试**：通过单元测试验证依赖版本约束，是有效的预防性质量保障手段
- **测试依赖显式声明**：测试文件直接导入的第三方库应在依赖文件中显式声明

#### 支付系统安全
- **支付事务边界**：任何支付状态变更必须评估与关联操作的事务原子性
- **外部回调安全降级**：验签失败或配置缺失时必须返回明确错误，禁止静默放行
- **GET 请求写操作禁止**：RESTful 路由中，GET 请求不得修改数据库状态

#### 路由与中间件
- **中间件-路由协同验证**：修改中间件或路由优先级时必须检查交互是否产生循环或覆盖漏洞
- **注释意图强制要求**：涉及循环、重定向、权限放行的代码，注释必须解释"为什么"
- **路径排除集中化**：特殊路径应维护为配置常量，避免硬编码散落

#### 版本兼容性
- **第三方库版本冲突检查**：主动检查 SQLAlchemy 与异步数据库驱动等版本兼容性
- **配置参数兼容性陷阱**：关注异步数据库连接池配置参数的兼容性问题
- **版本兼容性测试覆盖**：版本兼容性测试应覆盖所有直接依赖的临界版本，而不仅是传递依赖（如 SQLAlchemy 约束 aiomysql，但测试应显式验证 aiomysql）
- **依赖矩阵测试**：对于多依赖兼容性场景（如 SQLAlchemy + aiomysql），建议添加组合版本测试

#### 增量审查优化
- **增量审查强制关联扫描清单**：对于关联 Issue 的 PR，即使文件未变更，也必须检查相关测试文件的覆盖完整性
- **版本发布 PR 强制全量审查**：对于版本发布类 PR，即使采用 "quick" 策略，也必须对核心功能变更进行关联扫描
- **增量审查覆盖度下降风险**：增量审查未充分扫描跨文件影响，建议对支付类 PR 强制执行全量重审或关联扫描清单
- **关联扫描重要性**：对于配置类变更，需检查配置与现有其他策略配置的交互影响

#### 安全与测试
- **安全校验边界测试强制要求**：对 URL 验证、金额解析等安全关键逻辑，必须新增边界测试用例（如 `//evil.com`、零金额订单），并纳入阻断级检查
- **支付事务原子性检查**：任何支付状态变更（如 `confirm_payment`）必须评估与关联操作（如服务发放）的事务一致性，标 major
- **辅助函数直接测试强制规则**：独立纯函数（如 `_to_minor_units`）必须有直接单元测试，覆盖边界情况（None、负数、无效输入），标 major
- **测试文件职责强制检查**：新增测试必须放置在与其测试功能匹配的文件中，否则标记为 `major`

#### 配置管理
- **常量定义检查**：新增测试或功能时，必须验证引用的常量（如版本号）在项目中正确定义且文档化
- **路径解析健壮性**：在模块级别定义 `REPO_ROOT` 时，强制添加存在性检查（如 `assert (REPO_ROOT / "requirements.txt").exists()`）
- **支付金额语义明确化**：强制要求金额解析函数返回 `Optional[int]`，`None` 表示解析失败，避免 0 的歧义
