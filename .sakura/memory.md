# 项目记忆

累计反思 10 次

## 核心审查原则

- **"无评论"不等于"无问题"**：空结果可能源于工具故障，须对"空结果"保持高度警惕
- **"无评论"须附验证说明**：明确搜索依据，使其成为可验证的积极结论
- **审查结论须逻辑自洽**：风险识别与决策间须有严格因果，识别阻断项却批准会损害可信度
- **最简单变更须最严格审查**：简单字符串替换可能隐含API契约变更，须保持额外警惕
- **高评分PR确认偏误警惕**：9/10评分易引发偏误，须主动寻找边缘安全与全链路完整性问题
- **对比分析是发现设计问题的利器**：跨文件对比可有效暴露过度脱敏、策略不一致等问题
- **PR描述风险点强制回应**：描述中"需确认"/"注意"/"未执行"等声明必须逐项转化为已知风险项并在决策中说明接受理由
- **验证边界声明是最诚实的风险清单**：作者主动声明的未验证场景，比审查者事后发现的遗漏更危险
- **修复正确问题不等于审查完成**：增量审查必须包含"上轮未解决问题状态确认"，防止隧道视野

## 依赖与外部服务

- **主版本升级深度审查**：对照Changelog破坏性列表逐项确认实际调用点
- **外部依赖声明检查**：新增外部服务须声明用途、必要性、回退方案及部署环境要求
- **运行时依赖声明**：新增HTTP健康端点等调用须明确降级方案、网络策略及环境要求

## CI与工作流

- **可重用工作流权限验证**：调用方权限须是被调用方所有job权限的并集，GitHub Actions `permissions` 是覆盖操作
- **无检出作业上下文完整性**：未配置checkout的作业须检查是否拥有执行所需的环境变量和上下文
- **Smoke测试有效性**：新增CI步骤须验证测试脚本内部逻辑完备性，而非仅检查步骤存在性

## 核心模块

- **重大版本升级清单**：接口兼容性、导入链验证、配置向后兼容性
- **核心模块影响半径**：列举所有直接导入者评估影响
- **正则严格性评估**：解析安全关键信息的正则须评估过严或过松的风险
- **多级回退链路测试**：每级失败场景须有测试覆盖，确保最终版本有效或明确报错

## 前端与交互

- **前端错误码映射清单**：涉及状态判断的后端错误码必须在前端维护类型定义或注释映射
- **浏览器存储恢复竞态评估**：使用 `sessionStorage`/`localStorage` 状态恢复时，须评估多标签页/多窗口竞态（重复轮询、状态变更、焦点争夺）
- **轮询机制审查清单**：涉及轮询的变更须验证：间隔值、指数退避、最大重试/超时、去重作用域（单标签页 vs 跨标签页）、服务端限流
- **内联JS测试覆盖率加权**：模板内联JS测试提取成本高，审查应适当提高对测试覆盖率的期望或明确标注覆盖缺口
- **隐式状态转换验证**：异步错误处理不能只看 `catch` 块直接代码，须追踪副作用（状态重置、函数回调）最终影响
- **Jinja内联JS审查策略**：不能仅做 `node --check` 语法验证，须关注模板表达式替换后的运行时类型问题

## 文档审查

- **文档-代码双向验证**：修正文档时须反向抽查同文档中其他相关命令/配置描述是否过时
- **操作指南验证**：命令参数定义、前提条件说明、命令顺序依赖须全部验证
- **用户视角测试**：评估术语一致性、步骤清晰度、错误处理指导，模拟目标用户阅读体验
- **隐含假设检查**：是否假设特定OS、目录结构等环境
- **文档变更配套测试**：关键文档变更应配套自动化文档测试，将文档视为可测试制品

## 安全与错误处理

- **安全脱敏粒度分级**：区分"内部实现细节"（堆栈/路径/SQL）与"用户输入验证信息"，后者可安全返回。每个 `except` 块对外响应须注释标注错误类别（`# USER_INPUT_ERROR` / `# INTERNAL_ERROR`）
- **PR描述风险点强制回应**：PR中"需确认"/"注意"等风险提示必须逐项回应，PR描述是风险清单而非背景阅读
- **错误处理策略一致性**：同一PR引入多种错误处理模式须说明理由或统一
- **错误分类完备性**：新增错误码须检查翻译文件覆盖、边界防御测试、传播链各环节非法输入处理
- **运行时环境隔离**：进程生成/环境变量注入须验证子进程隔离可靠性及父进程退出的影响
- **错误响应函数不可黑盒信任**：须验证其实现细节（HTTP状态码、响应结构等）
- **宽泛异常捕获的精细化陷阱**：`except Exception` 后想区分 `ValueError` 和 `RuntimeError` 需额外判断，易出错。长远应在入口层做参数校验
- **跨库迁移的API假象**：标准库向第三方库迁移时，须核查"参数静默失效"风险，如 loguru 的 `exc_info=True`

## 增量审查

- **关联性验证**：即使只看增量提交，也须主动验证与整体变更意图一致
- **全局风险关联**：未解决的阻断性问题是当前PR的阻断项，结论须声明未覆盖历史问题
- **增量文档审查扩大半径**：修正一处文档应自然联想到同段落其他步骤的准确性
- **历史遗留项显式结案**：增量审查必须包含"历史遗留项状态追踪"，对上一轮 Request Changes 逐一标记为 `[已修复]` / `[未修复]` / `[已过时]`
- **相邻同构块强制遍历**：修改 `try-except` 多分支或连续 `if-elif-else` 时，必须显式检查相邻分支是否需要同步修改
- **PR自证逻辑全局应用**：当 PR 提供修改依据（如测试用例证明某 API 无效），必须将该依据作为全局搜索条件验证残留点
