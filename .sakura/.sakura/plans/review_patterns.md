# 审查模式与最佳实践

## 增量审查模式

### 覆盖度评估
- **核心问题精准定位**：确保所有关键变更点都被覆盖
- **遗漏点检查**：注意 PR 描述中提到的其他功能可能未在本次增量中体现
- **跨文件影响扫描**：检查新增代码对其他模块的影响

### 审查质量评估
- **准确度**：严重程度判断是否合理，避免误判
- **完整性**：充分理解变更意图，即使只审查增量部分
- **上下文理解**：主动查看 PR 整体描述，理解更大范围的变更意图

## 配置变更审查模式

### 配置对称性检查
1. **写入路径**：配置如何保存到数据库/文件
2. **缓存失效**：配置更新时如何清除缓存
3. **默认值对比**：新旧默认值是否一致，不一致时的影响评估

### 配置上限审查
- **物理上限对齐**：评估单任务最大耗时、模型调用成本
- **消费方隐式上限验证**：检查调用方是否有隐式上限（如 Semaphore、数据库连接池限制）

## 异步任务审查模式

### 任务生命周期管理
- **创建方式统一**：同一模块中禁止混合 `create_task` 与 `await`
- **Shutdown 处理**：确保后台任务在服务关闭时有机会完成
- **错误处理**：同步函数中使用 `get_running_loop().create_task` 时，必须评估线程安全性

### 任务可见性
- **任务 ID 记录**：考虑统一封装 `safe_create_task` 并记录任务 ID
- **异常捕获**：fire-and-forget 模式必须完全捕获内部异常

## 错误处理审查模式

### 错误分类
- **可恢复错误**：使用常量集合定义，避免硬编码字符串匹配
- **不可恢复错误**：明确区分并处理

### 日志规范
- **loguru 日志风格**：必须使用 `{}` 占位符风格，禁止 f-string
- **日志级别**：未初始化用 info，异常用 warning

## 测试审查模式

### 测试覆盖要求
- **正反用例**：包含边界条件和异常场景
- **Fallback 路径测试**：同步 fallback 中的异步分支需要集成测试验证
- **Mock 辅助类复用**：提取为模块级 fixture 共享，避免重复定义

### 测试断言规范
- **引用生产常量**：禁止硬编码数值
- **验证关键参数值**：Mock 方法若接收但忽略参数，应添加断言

## 历史问题追踪模式

### 升温机制
- **连续 3 轮未修复**：自动升温为 major→critical
- **第 4 轮自动生成 issue**：必须关联 issue 号
- **Suggestion 疲劳归档**：第 1 轮评估降级，第 2 轮强制降级，第 3 轮强制归档

### Issue 关联规范
- **强制关联**：未修复的 major 问题必须关联 issue 编号
- **PR 描述要求**：必须包含 `#issue-number` 或 `TODO(issue-xxx)` 引用

## 代码质量审查模式

### 代码重复检测
- **跨文件检测**：增量审查必须扫描两个及以上文件中 >10 行相同的逻辑
- **强制抽取公共函数**：重复逻辑必须提取为公共函数

### 导入规范
- **延迟导入注释**：函数体内 import 必须注释循环引用原因
- **冗余导入清理**：文件顶部已导入某模块，函数内再次导入且未使用别名或延迟必要性的，应要求合并或删除

## 前端与模板审查模式

### 安全规范
- **JS 上下文转义**：强制使用 `|tojson`，禁止仅用 `|e`
- **SVG 装饰图标**：必须添加 `aria-hidden="true"` + `focusable="false"`

### 一致性检查
- **四一致检查**：侧边栏链接、表单 action、JS fetch、重定向 URL 与路由前缀一致
- **模板变量命名**：统一 active_page 前缀

## 审查输出规范

### 增量审查必须输出
1. **已检查的规则清单**（最少 10 条）
2. **历史未解决问题清单并升温**
3. **未直接测试但依赖的调用链**
4. **全链路扫描清单**：配置保存→缓存失效→读取路径

### PR 描述要求
- **配置迁移完整性检查表**：避免增量审查遗漏跨模块影响
- **配置上限验证**：消费方隐式上限验证结果
